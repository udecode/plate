## Brief

### What will change?

Iteration 2's plan panel found suggestions still waiting on each other. Now rejecting an Enter no longer waits on suggestions touching its link, except in one case below, and the link rejoins the same way in any click order.

### What could go wrong?

A rejected Enter's link can stay split until a suggestion touching it is decided. If two suggestions set one property on a half and one also unwraps it, they must be decided together. Iteration 4 redesigns that.

## Teach

Review stores a suggested Enter inside a link as a cut that splits the link into two halves. Rejecting the Enter puts them back together. Deciding suggestions one at a time in any order, or all at once, must give the same document.

On next, the reject waits for pending suggestions that change its halves, while unwrapping or removing a half waits for the Enter. Where those two waits meet, some pairs could only be decided together.

Now the reject never waits on what touches the link. When the rejoin depends on a pending suggestion, the reject applies and the halves rejoin at the first later decision that settles them. Two suggestions setting one property on a half still make the reject wait, as on next. Unwrapping one half unlinks only that half. An Enter between paragraphs keeps next's rules.

## Main changes

- `outcomeOf` in `packages/plitejs/src/authored/facts/facts.ts` reads a cut tag under a stored reject verdict as rejected, so a held cut leaves the review list and the waits on its Enter release. `keptMembers` in `packages/plitejs/src/authored/tree/resolve.ts` keeps a rejected cut's tags only while the run holds it. `settleNode` in `packages/plitejs/src/authored/facts/settle.ts`, and `decideFormats` while a cut is held, keep the split's history undecided, so admission never lands a held split's give-back early.
- A rejected cut inside a line holds instead of waiting. When its verdict has a touching pending change, probes that disagree or more touching changes than the probe cap, the join callback in `resolveIn` and the pre-pass for a cut across two lines return `defer`. `joinRejectedCuts` in `packages/plitejs/src/authored/tree/cuts.ts` then keeps both halves and their tags, and a removed left fragment whose own cut is held holds the cut too.
- When two suggestions set one key on a half outside the split's history (`Half.stacked`, where an Editing write does not count), they wait on each other, so a held cut would decide ahead of them in orders next never reaches. A cut this run rejects then first reads its verdict with no unwrap or wrap of a half, in its probes too (`Probe.readsLifts`). Where that reading waits, the cut waits on the same changes except those between the halves or enclosing them, because those can wait on the cut. Otherwise it holds like any cut inside a line. When no half has an unwrap or wrap, that reading and the held one agree, so the cut reads its halves once and the probe budgets hold. Reading an accepted unwrap of a half there would settle at once a reject that no order of single steps reaches. A cut an earlier decision rejected never waits (`cutVerdict` in `resolve.ts`). It holds until a later run settles it. So a writer that arrives after the reject, typed or merged from another client, cannot turn the hold into a wait that drops the cut. When the cut passes over the left half it ends, because that half lifts or its own cut is held, this reading still runs on that stored half, so the two writers wait as next makes them wait. Its probes join that stored half too (`Probe.passes`), so the reading settles where next settles.
- A block split keeps next's waits and verdicts exactly. Only a cut inside a line counts an unwrap or wrap of a half as touching, and only such a cut reads the lift verdicts below (`readsLifts` in `verdictOf`).
- For a cut inside a line, `verdictOf` in `packages/plitejs/src/authored/tree/halves.ts` gives `gone` when the decision lifts the left half's children out, so the right half takes back what the split dropped, and `apart` when it lifts the right half's. So an unwrap stays on the half it targets. Content that survives between the halves keeps them apart, text included, because once a held cut lands in a later decision, the resolver cannot tell text an unwrap lifted there from text typed there. An element the decision lifts counts through what it lifts. A pending unwrap or wrap of a half counts as touching such a cut, as one of an element between the halves does for every cut. `Half.lifted` reads the lift from the claims `halfOf` already read, so the read budgets hold. Before it counts any touching change, `verdictOf` gives `apart` when something between the halves stays whatever the pending changes decide: text with no pending insertion, deletion, split or join, or an element no pending change removes or lifts. The left half must not be able to lift, since a lifted left half gives `gone`. So text an Editing write put between the halves keeps the reject from waiting on suggestions past the probe cap, as on next.
- `joinRejectedCuts` passes a cut whose left fragment the decision lifts to the fragment before it in its family, as `relinkCuts` does after a removed fragment, and holds the cut when that fragment's own cut is held. When the cut holds there, the fragment it now joins takes the cut's end tag, because the lifted fragment leaves with its tags. A probe that finds such a relinked left half holds the cut too, so an emptied and unwrapped middle piece of a link split twice gives one ref, not two. A removed left fragment passes the cut on the same way. While a pending removal or unwrap of a middle piece could still pass the next cut on to the first piece, the cut before the middle piece holds (`middleMayMove` in `resolve.ts`), so a later decision still finds the way back to the first piece. That cut still reads two writers of one key on a half first, so they wait as next makes them wait. When no fragment before a lifted left half remains, the right half takes back only the dropped keys the lifted half holds or carries a format tag for (`reclaimFrom`). So when an earlier rejected Enter kept the first piece apart, the ref that piece holds never comes back on the last piece. A removed left half with no fragment before it still gives every dropped key back, as on next, because once its removal lands nothing records what it held.
- `joinRejectedCuts` takes a `follows` test from `resolveIn`. A fragment follows a split when it carries that split's start tag or one of its split-history tags, and that tag is not rejected. A left fragment that follows a split makes the cut's verdict apart, so the fragment before that split keeps what this cut's split dropped, and the piece after it never takes the dropped ref back. The resolver and `settleNode` keep the split's history on a pending cut's left half, and the decision reads each history tag as undecided. So the decision that settles that cut still finds the split its left half follows.
- In `resolveList`, an emptied inline element no longer waits on its own unwrap or removal, and a lifted inline element no longer waits on a removal that tags every child, because neither leaves text to lift or remove. An element counts as inline when its parent allows text or the schema declares it inline, so this holds where the schema leaves the paragraph undeclared. So two suggestions that empty and unwrap the middle piece of a link split twice decide one at a time.
- When any verdict is stored, a proposing write whose runs hold a rejected cut resolves those runs as an Editing write does (`touchesHeldCut` in `packages/plitejs/src/authored/authored.ts`, read with the contexts the write minted). A run spans the blocks the write touched and one text block on each side. It resolves under the editor's resolve schema inside the run's containers, as a decision does, so a metadata property never keeps the halves apart and a property the schema allows only under an outer container still compares. A cut with only one side in the runs stays held (`holds` in `AuthoredResolveOptions`). So a held cut lands on the write that removes the last change it waits on, when that write's runs hold both halves. Otherwise it lands at the next decision that settles it, or at a later write whose runs hold both halves.
- `cutVerdict` hands each cut verdict the outer run settled to the probes it starts (`Probe.known`), so a probe that tries a pending removal both ways reads that cut as the outer run did. A probe also keeps each cut the outer run holds as held (`Probe.held`), so it never lands a cut the run leaves standing.
- `joinRejectedCuts` hands the verdict the stored fragment that holds the cut's end. On next it handed over the first fragment of a joined run. So when a probe rejected an earlier Enter of the same link, that Enter's rejoin took in the left half, the probe no longer found it, and it read the cut as apart. The cut's verdict then depended on whether an unrelated suggestion was still pending.
- `keepsContent` reads the first line's content from what the decision settles, with no timestamp read, so `deletesBeforeJoin`, `JoinMoment` and `joinOf` go. The right piece then stands in an emptied line's place, as it does when the deletion was decided first.
- An unwrap of a half no longer reaches the rejoined link in `joinedShell`, which reverses iteration 2's pick.
- `joinedShell` keeps a left format tag only for a key the left half supplies, as its comment already says. On next it keeps every left format tag, so a tag rejected in the joining run restores the left half's earlier value over the value the right half supplies. When that earlier value is the omitted default, the joined link stores the url or omits it depending on whether the right half's accepted tag is still there to apply after it.
