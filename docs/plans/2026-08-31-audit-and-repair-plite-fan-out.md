### Immutable index cache decision

- Cause: `PLITE-FANOUT-INDEX-CACHE-012`. A cache hit calls `Object.isFrozen` on the entire root array before consulting its WeakMap. In this runtime that native check enumerates array properties; the existing immutable index is already the authority.
- Best API: retain `DocumentIndex.fromValue`; delete redundant validation before a known-immutable cache hit. No new layer, cache, public method or contract.
- Plite Plan: consult the existing WeakMap first. Unknown inputs retain the constructor's cloning/freeze checks; mutable inputs never enter the cache under their mutable identity. Historical snapshots remain immutable.
- Pre-acceptance intervention: 100 cached reads at 100k blocks take 1,398.772 ms on the current path versus 0.0063 ms with cache-first lookup. A proxy observes one own-property enumeration per old cache hit and zero on the target path.
- Canonical red: all four 100/1k/10k/100k cohorts fail the work guard; worst 100-read p95 is 2,548.06 ms. Frozen budget: zero cache-hit property enumeration and p95 below 16.67 ms. Artifact: `docs/plans/artifacts/plite-fan-out-audit/immutable-index-cache-red.json`.
- Correctness red: 70 existing document-change tests pass; the added immutable-cache locality test fails with one enumeration instead of zero. It also checks mutable-input isolation and retained historical snapshots.
- Owner: `core/change/document-index.ts`; exact canonical query benchmark and document-change contracts must pass before continuing the open Yjs cold-path repair.
- Exact rerun: all query guards pass; 100 cached reads worst p95 0.01 ms versus 2,548.06 ms red, with zero property enumeration. All 71 document-change tests pass. No timing budget changed.

### Cold snapshot catalog decision

- Cause: `PLITE-FANOUT-SNAPSHOT-CATALOG-013`. Constructing the lazy identity index eagerly walks every node to collect element types. The runtime full-index counter misses this separate traversal. One key lookup must not compile an unrequested catalog.
- Best API / Plite Plan: keep the canonical SnapshotIndex and its existing type query; defer collection until the first type query or explicit full enumeration. Reuse the same catalog, collect it once, and release the active child tree after full enumeration as before. No new public index, namespace, hook or cache.
- Hard laws: stable node identity, exact type-query order, historical snapshots, and type queries after identity enumeration. The added test checks both request orders and repeated type queries.
- Pre-fix correctness: 71 document-change tests pass. The new construction-work test observes 100 root-node reads for an unrequested catalog instead of zero. The complete Yjs rerun still fails its unchanged first-inbound runtime-ID budget at 6.827 ms; the corresponding artifact is `yjs-cold-index-red.json`.
- Frozen owner guard: zero construction node reads, exactly one root-node read for the final leaf lookup, and cold lookup p95 below 16.67 ms across 100/1k/10k/100k blocks. The existing Yjs 1 ms runtime-ID gate remains unchanged.
- Canonical query benchmark adds cold-index work and timing rows before production changes. Its red artifact and the exact post-fix rerun must be retained.
- Canonical red: all four cohorts fail locality; 100k cold lookup p95 is 86.09 ms. Artifact: `docs/plans/artifacts/plite-fan-out-audit/cold-snapshot-catalog-red.json`.
- Exact rerun: all query guards pass, zero construction reads and one lookup read through 100k, with cold lookup p95 below the runner's 0.01 ms rounding precision. All 544 core/identity/architecture/Yjs contracts pass; the final empty-type-query addition also passes all 72 document-change tests.

### Batched text publication decision

- Cause: `PLITE-FANOUT-TEXT-BATCH-014`. Applying one canonical change with 120 text replacements publishes the same 10k-block root 120 times. Each replacement copies common ancestor arrays and rebuilds their offsets. This is O(changes × ancestor width), not unavoidable immutable publication.
- Causal probe: 120 text replacements at 10k take 353.34 ms and produce 120 root publications. A disposable one-publication implementation takes 55.78 ms even while rebuilding the entire document index. Exact values and untouched identity match. `batched-text-publication-probe.json` records the source identity and explicitly labels these single samples.
- Best API: retain the public DocumentChange contract; generalize the existing private grouped-property updater to grouped node updates. Delete duplicate per-replacement publication for pure text batches. No additional public owner, cache or layer.
- Plite Plan: resolve replacement ranges against the immutable input; accumulate each leaf's final text in reverse offset order; reuse the existing path trie to publish each common ancestor once. Preserve the single-change path and structural/token fallback. Property batching uses the same generalized owner.
- Hard laws: exact text (including multiple edits in one leaf), unchanged node identity, retained historical values, inverse, serialization and follow-up edits. Mixed structural changes retain their existing path.
- Pre-fix correctness: 72 document-change tests pass; the new batch test fails with 25 publications instead of one. Canonical `core-document-change-current` gains 100/1k/10k batches, a one-publication work guard and a frozen 16.67 ms p95 budget. Its obsolete direct DocumentChange constructor is replaced with the existing internal factory; parity and original comparison gates remain unchanged.
