# Settle shown values at the cost of what a commit changed

Status: executed: step 5's full protocol runs as suggested task t_982c0e6a

This iteration replaces how the settle stage of [Settle shown block ids wherever their last suggestion is decided](2026-10-24-shown-settlement.md) finds the groups to judge. That plan's step 6 timed the built stage at f3c51a7df1 and missed its frozen budget. While a suggested move of a 1,000 line section is pending, 1,001 elements show a value, and every keystroke anywhere reads all 1,001 of their groups. Typing there took 1.71 times as long as with the stage off, and a remote keystroke 5.98 times, against a budget of 1.3. The same-code noise was 0.163 and 1.294, so the timing runner judged both misses conclusive. As that step says, the holder-index row went back to `architect`. Runners on Opus, Astra and Sol each designed a stage whose work follows what a commit changed, and an Opus judge picked the Opus design with three grafts. Settlement's law, its output and every proven case stay as the shown-settlement plan built them.

## Brief

### What will change?

Typing next to a large pending suggestion stays fast. The editor now looks at shown ids only when a change could affect them, so a keystroke anywhere else does no extra work.

### What could go wrong?

If the editor misses a change that should settle a shown id, that block keeps its stand-in id until a later change. A test check after every change catches that. The editor saves its record only after a change succeeds.

## Teach

After every change, the editor checks whether any block can now take the real id it shows. Today it checks every such block every time. A pending move of 1,000 lines gives 1,001 blocks a shown id, so each keystroke makes 1,001 checks that all come out the same.

A block can only become ready when something it depends on changes: a block's properties, a decision, a spare block, or a pending insertion going away. Typing changes only text. So a quick test runs first, and when the change touched none of these, the editor skips the check.

Some changes do touch blocks, such as an Enter or a decision. For those, the editor keeps a small record per id value: how many blocks store it, which are stuck, and which wait on a decision. It then checks only the values whose record the change moved. A value that 1,000 blocks store costs one number, not 1,000 reads.

## Main changes

- **A quiet gate runs first.** Before the settle stage moves any index, it asks whether the commit can change an input of any group's readiness. A commit can do that only through an element's properties or structure, a verdict, a spare record, a root's creation or deletion, or an insertion count that turns a decided mark's outcome. An undo or redo changes readiness only through these same inputs, so the gate does not check for one. A commit that does none of these leaves every group as it was, so every shown group still waits and the stage returns null. Typing, in Editing or Suggesting, local or imported, touches text leaves only, so it reads no holder and no group.
- **Insertion counts are an input.** A rejected format or deletion mark stays pending while its replacement insertion exists. Deleting that insertion's last character is a text-only keystroke that writes no verdict, yet it can make a group ready. Admission then rewrites the holder's block, so the gate sees the flip in the admitted change. `decidedIn` names each decided incarnation whose insertion count changed sign, and both the gate and admission read it.
- **A per-value record, if the gate is not enough.** Step 3 times a Suggesting Enter and a decision import beside the pending move. If either misses, step 4 builds the Opus design. Each value keeps a slot of counts, and a holder that cannot wait counts only as a storer. The stage reads only the values whose slots the commit moved, plus those that a decided mark or a moved owner reaches, so readiness is judged from the change. The worklist, the place check, the block rebuild and the closed history entry stay as built.
- **Owners come from the document.** A root's owners are the elements whose type declares a content root and whose `childRoots` names it, so no binding path history decides readiness.
- **The record is saved on success.** The record moves inside the transaction and becomes the ledger's only once the transaction commits.
- **The oracle and two new checks.** The whole-document oracle keeps running as a transaction guard. A test-only guard also checks that a fresh record built at each committed document equals the ledger's. A differential check settles each commit's pre-settlement document with both the fast path and the whole-document form, and expects the same output, which catches an alias dropped too early or a wrong winner.

## Three realistic failures

- **A missed input.** A commit changes something readiness reads that the gate or the record does not watch, so a ready group keeps its alias until another commit. Guarded by the whole-document oracle after every commit in the authored-shown and spare-collaboration suites, and by a case for each of the gate's element, record and root checks that fails with that check removed.
- **A stale record.** A failed transaction leaves the record at a document the ledger never committed. Guarded by publishing on success, the abort case, and the fresh-record equality guard.
- **A wrong winner.** The record's storer count or document order differs from the whole-document form's, so a different element takes the value. Guarded by the differential check and step 3 of the shown-settlement plan's peer cases.

Blast radius: the settle hook's callers are `admitTransactionDraft` and `repairLoadedDocument`; the closing pass and the recorder read `ValueHolders`. A rollback reverts this iteration's commits, which leaves the built stage, correct and over budget.
