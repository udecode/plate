# A caret in a line the preview adds, and an insert after that line

Status: executed
Topic: authored
Playbook: plan

Pursue, on two wrong results that diff panel round 3 of `docs/plans/2026-10-24-authored-joined-line-end.md` found. That plan's log sends both here, and the two plans land together. Previews are read-only, so edits run through the editor, which shows the stored lines. With the caret stored at the end of a joined line, commands act there and the editor shows the caret there. The preview, though, draws any forward caret stored there in the empty line it adds after the join, even one the editor set or typing just moved. So the preview shows the caret one line below where commands act. The fix draws a caret in an added line only while the preview's own placement there stands. The second result is a framed write after an added line, such as a plugin that appends a line at the end. The commands write the added line and then the new one, but the stored result accepts to the new line alone. Next refused that write with `diverged`. The joined-line-end build resolves such a write instead of taking it, and its divergence check skips that window. The ledger now compares every window that held an added line with what the commands wrote, and a whole-root rebuild after one too, so it refuses that write again. Diff round 2 found that comparison and the test-only law at odds. A line added before the joined line leaves the added line unneeded, so accepting drops it and the law threw, while the comparison refused Enter in the first line for the same drop. Accepting may now drop added lines that end their list untouched, in both checks. Diff round 3 found two more wrong results. The comparison refused Enter at the end of the last line, because the accepted list can reuse an added line's object for the empty line Enter stored. It now drops leftover added lines from the end of what the commands wrote before it compares. A plugin frame that typed into an added line, then moved or added a line after it, threw. A write inside an added line now records that whole line as written.

## Brief

### What will change?

The last review round of your ledger-law fix found two bugs, and both fixes have landed. The preview shows the caret in an added line only when you put it there. The editor now refuses a write whose result would change once you accept everything, apart from leftover added lines at the end.

### What could go wrong?

Edits at that caret change the line above, so Backspace deletes that line's last letter. After a toggle, the preview draws the caret there until you type or move it. Some writes next stored are now refused. The tests ran in a simulated browser only, and nobody tried it in a real one.

## Teach

A review preview shows the document with every pending suggestion accepted. When accepting leaves the root short of lines, the preview adds empty ones that nothing stores. Previews are read-only, so edits run on the stored lines.

When you put the caret in an added line, the editor stores it at the end of the line above, and the preview draws any caret stored that way in the added line. So after you type at the end of a joined line, the preview draws the caret one line below the letter. And when a plugin appends a line after an added line, the saved document drops that added line.

Now the preview shows its own caret in an added line only until something moves it. Wherever there was an added line, the ledger checks the write against what accepting the saved document gives and refuses a mismatch. Added lines left over at the end don't count.

## Main changes

- The lens draws a forward caret at the end of a text in the added line after it only when its caller asks. The authored plugin asks only while core's placement generation equals one that a preview's own placement in an added line got, and only for previews of that kind, accepted or proposed. The lens reports such a placement when it lifts it, and the plugin keeps the generation core mints for it until a newer placement commits, so an update that rolls back keeps the drawing. A preview commit maps its carets with the same answer and caches each answer apart (`packages/plitejs/src/authored/ledger/preview-lens.ts`, `packages/plitejs/src/authored/ledger/ledger.ts`, `packages/plitejs/src/authored/authored.ts`).
- The ledger already refuses a command frame's write when a window it resolves shows other than what the commands wrote there, but it compared only windows that a follower or a move leaves unsettled. It now also compares each window that held a line completion built, and the whole root when a frame's write rebuilds a root that held one. The refusal is `diverged`, or `reordered` when only the order differs (`packages/plitejs/src/authored/ledger/level.ts`, `packages/plitejs/src/authored/ledger/projection.ts`).
- Lines completion built that end what the commands wrote may be gone once accepted, since nothing written needs them. The comparison and the framed law both drop such lines from the end of the written list while it is longer than the accepted one, then compare. The resolver records the lines it builds in a registry the two checks read. An untouched added line keeps its object from the projection to the frame, and the accepted side can reuse that object for an equal empty line the write stored, so neither check asks the registry about the accepted list (`packages/plitejs/src/authored/ledger/runs.ts`, `packages/plitejs/src/authored/ledger/projection.ts`, `packages/plitejs/src/authored/authored.ts`).
- A preview commit's `selectionBefore` is where a view last read that caret, with the drawing answer it had then. So once a view has read a caret drawn in an added line, the commit that types after it reports the caret moving from there. With no read after the placement, the commit starts from where a view last read the caret, as diff round 3 measured (Opus W2) (`packages/plitejs/src/authored/ledger/preview-lens.ts`, `packages/plitejs/src/authored/ledger/ledger.ts`).
- The recorder records a step that writes only inside a line the projection added as that whole line, inserted as written. The stored document holds no token of that line, so every position in it mapped to one stored place, and a later step of the same frame, such as a move or an insert after the line, landed inside the line's text and threw (`packages/plitejs/src/authored/tree/record.ts`).
