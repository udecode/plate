# Keep a moved link's written url by storing values whose default depends on place

Status: superseded by docs/plans/2026-10-21-cut-join-classes.md after the benchmark gate's miss on type-history-100
Page: https://claude.ai/artifact/6fWoW4f5Mt5gDbCfCw9mch
Playbook: bug-fix

## Brief

### What will change?

Rejecting a split keeps both values one change wrote on its halves, even when the right half moves into another kind of block. The editor now saves a set value whose default changes with place, and that schema's fingerprint changes.

### What could go wrong?

Two links or text runs can stay apart when only one has the value set, and documents grow. Such a schema's old rooms and files need a version bump. A url unset under a heading still reads the paragraph's default.

## Teach

A link's url can have a default that changes with where the link sits, such as one url under a paragraph and another under a heading. Today, if you set a url equal to that default, the editor saves nothing.

Rejecting an Enter can move the right half of a link from a heading back into a paragraph, where its set url shows the paragraph's default instead. The last fix rebuilt the old place while deciding, so results depended on decision order.

Now, when a default changes with place, the editor saves every value someone sets, even the local default. A value nobody set still shows the default where it is now. Rejecting the split compares what's saved, so other decisions can't change the result. Properties in an exclusive group, such as subscript next to superscript, keep today's rule, because a saved value would switch the partner off. So do defaults only an unlisted element type can use.

## Public API

The call stays the same. What gets saved changes when the same property has a different default somewhere else, and so does that schema's fingerprint.

```ts before
// packages/plitejs/test/authored-tree-cuts.test.ts
schema.elementProperty('url', omittedDefault('u'), {
  target: target.and(target.type('link'), target.parent(target.type('paragraph'))),
}),
schema.elementProperty('url', omittedDefault('w'), {
  target: target.and(target.type('link'), target.parent(target.type('heading'))),
}),
// tx.nodes.set({ url: 'u' }) on a link in a paragraph stores the link with no url
```

```ts after
// packages/plitejs/test/authored-tree-cuts.test.ts
schema.elementProperty('url', omittedDefault('u'), {
  target: target.and(target.type('link'), target.parent(target.type('paragraph'))),
}),
schema.elementProperty('url', omittedDefault('w'), {
  target: target.and(target.type('link'), target.parent(target.type('heading'))),
}),
// tx.nodes.set({ url: 'u' }) on a link in a paragraph stores url: 'u'
```

## Rules

A rejected split inside an element joins its pieces only when every property reads the same on both once the decision is made. A property a piece lacks reads as the schema's default for the piece's type and place, unless the property's default depends on place. The document stores every value someone writes for such a property, even one equal to the default where its node sits, and a missing value reads the default where the node sits now. So the pieces compare what is stored, a written value moves with its element, and a value nobody wrote reads its new place. Where the schema leaves that default out, a piece with a written value and a piece with none stay apart, even when both read the same value. Where it saves the default up front, a written default and a filled one are the same bytes, so those pieces join. A property's default depends on place when the declarations that apply to some type the schema lists give it more than one default, at least one leaves its default out, and none puts it in an exclusive group. A declaration that only an unknown type the schema preserves can match does not count, so a value written there is lost when its node moves into such a type, as on next, and decide task t_546ba394 owns it. An empty line anchor keeps no such value, and an unset stores nothing, so an unset piece reads the default where it sits now. On the right piece, a property reads as the left piece's when the right piece has no value of its own and the split took the value. A piece has no value of its own when no write stands on it and its value is missing, the local default, or a default that some declaration of the property saves up front, because a filled default keeps the value of the place where the split filled it. The split took the value when the split's record kept the left piece's value, or when the value is missing and the piece's type now drops the property on split. So an untagged value in a saved document that equals a default some declaration saves up front joins under the left piece's value, as on next. And after a retype to a type that drops the property on split, a right piece with no value joins under the left piece's value, where without the retype the pieces would stay apart. A read is settled when no undecided suggestion is on it, no pending split took it off and no undecided type change of the piece would change its rule. The join reads the pieces' ancestors as they stand. So when a split rule depends on an ancestor, which no schema in this repository declares outside tests, a suggested change to that ancestor can still change the result by order. Pieces whose settled reads differ stay two elements, so neither value is lost. Pieces kept apart still wait on a pending removal of either piece, which could give the other piece back what the split dropped or bring it next to another piece of the same element. Anything else waits on the suggestions, splits and type changes that settle it. Two changes can each wait on the other, and deciding them together completes. While a split is pending, every accepted or Editing write on its right piece stays recorded, so a write that matches what the split dropped never reads as the drop. The one exception is an Editing write back to the value below, which withdraws the same author's writes just before it. So when one author writes a value and unsets it, the pieces can join, and when a second author unsets it, they stay apart. A right piece that joins lands its accepted suggestions and waits on the undecided ones the left piece lacks. A removal lands nothing itself, as on next, so a write accepted in one decision with the removal of every link that carries it never lands, and a reader rejected later reads the value below it. Suggested task t_4293d5c9 owns that order. A decision that removes content waits on each undecided write inside it that a suggestion on content the decision keeps reads, unless a suggestion on kept content also carries that write, which lands it. The wait keeps the write for a reader decided after it. A reader rejected before the write lands reads the value below that write, as on next, and suggested task t_048448ff owns that order. An Editing delete does not wait, and the wait does not see a reader in another value root, so those removals still lose the write, as on next. Suggested task t_4293d5c9 owns them. When the pieces are not already apart for good, the reject also waits on each suggestion that would add or remove an element between the pieces. The reject does not wait on a suggested unwrap of an element between them, so that case can still change by order, as on next. Suggested task t_ab434358 owns it. At the fold this replaces the rule the last attempt added beside the rule that a rejected split rejoins its pieces, the rule on which Editing marks stay stored gains a format on a pending split's right piece, and the schema's rule on omitted defaults gains the exception for a default that depends on place.
