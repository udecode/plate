# Read each piece of a rejected cut one way in every decision order

Status: superseded by docs/plans/2026-10-20-cut-join-moves.md after the diff panel's third round
Page: https://claude.ai/artifact/FwpfS6h4GdVEp8osXhYJTZ
Playbook: bug-fix

## Brief

### What will change?

Rejecting a link's split keeps both urls when the halves differ, in every order. A few cases still depend on order, as on next, such as a suggested unwrap between the halves, and Open work names each one's owner.

### What could go wrong?

A reject can wait on other splits, type changes, elements between the halves or deleting either half. A deletion can wait on a pending write kept content reads. Two changes can block each other. More rejects leave two links.

## Teach

Splitting a link that is under review makes two pieces. Rejecting the split glues them back into one link.

The last attempt compared the pieces as they looked then, so pieces that lost a property to another split, used a schema default or got deleted read wrong. The result depended on decision order, and values could be lost.

Now the glue reads each piece's property as the stored value or the schema's default for that piece, plus whether a split took it off. It counts a pending type change of the piece and reads its block as it stands. A write on the right piece is kept until its split is decided, so it never reads as the split's removal. The glue joins when both reads are settled and equal, keeps two links when they differ, and otherwise waits. A deletion lands nothing itself, as on next. It waits for a pending write inside it that a suggestion on kept content reads, unless kept content also carries that write. When rejecting the split merges the right block back into a block of another type, a moved link whose url a kept write left at its old block's default keeps that default, so the halves keep both urls. A link nobody gave a url reads its new block, as on next, and accepting a suggested merge gives what an Editing merge gives.

When every type's reads are final and differ, the fragments stay apart. When the types disagree, the join waits on the type changes behind them, and otherwise on both sides' pending cuts and undecided tags. When the right fragment joins, its tags leave with it. The join lands what `decideKey` lands for them, key by key, as before this plan, and waits on the undecided ones whose write id the left fragment lacks. When the fragments are not already apart for good, the join also waits on each undecided insertion or deletion that could add or remove a non-text node between them. ## Rules

A rejected split inside an element joins its pieces only when every property reads the same on both once the decision is made. A property a piece lacks reads as the schema's default for the piece's type and place. On the right piece, a property the schema drops on split reads as the left piece's until someone writes it. A read is settled when no undecided suggestion is on it, no pending split took it off and no undecided type change of the piece would change its rule. The join reads the pieces' ancestors as they stand. So when a property rule depends on an ancestor, which no schema in this repository declares outside tests, a suggested change to that ancestor can still change the result by order. When rejecting a split merges a block into one of another type, each moved element whose property a kept write left at its old block's default keeps that default, so neither half's value is lost. A property nobody wrote reads the new block, as on next, and an accepted merge gives what an Editing merge gives. A text property, and a property that has no default under the old block, still read the new block, so a value one change wrote there can be lost, as on next. Suggested task t_ab434358 owns them. Pieces whose settled reads differ stay two elements, so neither value is lost. Pieces kept apart still wait on a pending removal of either piece, which could give the other piece back what the split dropped or bring it next to another piece of the same element. Anything else waits on the suggestions, splits and type changes that settle it. Two changes can each wait on the other, and deciding them together completes. While a split is pending, every accepted or Editing write on its right piece stays recorded, so a write that matches what the split dropped never reads as the drop. The one exception is an Editing write back to the value below, which withdraws the same author's writes just before it. So when one author writes a value and unsets it, the pieces can join, and when a second author unsets it, they stay apart. A right piece that joins lands its accepted suggestions and waits on the undecided ones the left piece lacks. A removal lands nothing itself, as on next, so a write accepted in one decision with the removal of every link that carries it never lands, and a reader rejected later reads the value below it. Suggested task t_4293d5c9 owns that order. A decision that removes content waits on each undecided write inside it that a suggestion on content the decision keeps reads, unless a suggestion on kept content also carries that write, which lands it. The wait keeps the write for a reader decided after it. A reader rejected before the write lands reads the value below that write, as on next, and suggested task t_048448ff owns that order. An Editing delete does not wait, and the wait does not see a reader in another value root, so those removals still lose the write, as on next. Suggested task t_4293d5c9 owns them. When the pieces are not already apart for good, the reject also waits on each suggestion that would add or remove an element between the pieces. The reject does not wait on a suggested unwrap of an element between them, so that case can still change by order, as on next. Suggested task t_ab434358 owns it. At the fold this replaces the rule the last attempt added beside the rule that a rejected split rejoins its pieces, and the rule on which Editing marks stay stored gains a format on a pending split's right piece.
