## Brief

### What will change?

Each preview paragraph shows its own cards, as the task asked. The next branch added its own map for edits beside a pending merge, so this run rebuilt the work there, with one map for cards, typing and badges.

### What could go wrong?

Some edits beside a pending merge refuse. Bold there formats what the preview shows, even text saved elsewhere. A command naming its own place can still edit outside the selection, as on next. Preview cards read by key or path.

## Teach

A preview shows the document with every suggestion accepted, or every one rejected. That can hide or merge paragraphs. While a merge is pending, a paragraph split off the merged line, or put between its halves, shows after the merged line.

Cards, typing and badges need to know which saved text sits at a spot in the preview. Today the sidebar guesses by position, so a paragraph below a hidden one shows its neighbour's card. Meanwhile the next branch added rules for saving edits beside a pending merge, with its own map of where moved text shows.

Now one map, built from where the preview puts each piece, tells cards, typing and badges what they need: which cards a paragraph shows, where a key lands and which paragraphs an edit touched. The next branch's edit rules stay, and its second map goes away.

## Hard cuts and app migration

- `at` on a preview view takes a node's key or path, and names a node of the preview, a block or one of its texts. A key resolves only in the view. A point or a range throws `AuthoredPlaceError`, exported from `plitejs/authored`, on a preview, because no product code reads one there; on an intent view both keep today's meaning. The owner editor reads its own preview the same way, and no option reads stored places from a preview. An app that read a preview with a stored place, such as a record's `ranges`, reads through an intent view instead.
- In this repository, six places pass a place to a preview read or anchor on one, and a seventh selects a stored range on the editor it was opened from. `useSuggestionGroups`, `useSuggestionChanges`, the discussion's `targetGroups` and `blockThreadCount` already hold a view place, so they only drop their index mapping, and `useSuggestionChanges` passes its path instead of a range it builds from the view's text. A path read shows a block's own changes, so on any view a nested paragraph's `useSuggestionChanges` no longer returns its container's pending wrap or unwrap, as `useSuggestionGroups` already does; the container's own hook still returns it. `useSuggestionGroups(blockKey)` reads the cards of the block with that key, so a nested key no longer reads its top-level block's cards; this repository mounts badges only on top-level blocks. The docx export maps comments onto a preview through its own diff (`projectAuthoredRange` in `authored/format.ts`) and is not changed here, and so does the comment toolbar, which selects a change's stored `ranges[0]` and can select a neighbour under a preview (Open work). The discussion popover turns a suggestion's stored `ranges[0]` into a view block and a DOM range; under a preview it now anchors, on both the suggestion and the change route, on the block whose trigger was pressed last, by key, when that block shows the open thread, and positions by that block's element instead of a stored range. It forgets that block when the view changes. When that block does not show the open thread, no popover opens, so a thread opened from a list under a preview opens none unless its block's trigger was pressed last (Open work). `packages/plitejs/test/react/decoration-manager-contract.test.ts` reads a view range on an Accepted preview and paints the returned stored ranges into the view, which this change makes wrong; it asserts the hidden insertion's id instead and stops painting stored ranges on a preview.
- A page cursor from a read with `at` works only on a view with the same root and preview mode. A cursor from a read without `at` keeps working on any view.
- `SuggestionDiscussionBlock` in the copied discussion loses its `blockIndex` prop, and `blockThreadCount` takes the block key. An app with a copied `discussion.tsx` re-copies it or makes the edits in the Public API pairs above.
- `AuthoredChange.revision` no longer counts where a change other than a split or join sits inside its block, so an edit earlier in the block leaves it alone. A join, split, wrap or unwrap's revision also ignores the text and the leaves inside its element, and still changes when a child block is added or removed or changes its shape, or children of different shapes swap. A split or join's revision keeps today's path inside its top-level block, so a block that lands among or leaves from the blocks ahead of it, or ahead of one of its ancestors, in that block still changes it, while reordering, replacing or retyping the blocks ahead of it keeps it, as today. A change's `ranges` can now move while its revision stays the same, so an app that caches `ranges` reads them again after each document change. A decision on a structure change no longer refuses as stale after someone types or formats text inside it, and still refuses after its child blocks change.
- Edits beside a pending join keep next's law. Backspace and Delete across a moved piece's edge, and a selection over moved pieces, record the merge next lowers them to, in both intents. ## Main changes

- `resolveAuthoredChildren` in `packages/plitejs/src/authored/tree/resolve.ts` reports `placements`, the landings that pass a shown line or change a shown container, and `hidden`, the blocks a preview hides whole with the shown block each collapses into. Next's `reordered` report goes once the breaks parity test passes.
- `packages/plitejs/src/authored/ledger/order.ts` is deleted. `ledger/level.ts` and `ledger/places.ts` own each run's order, its breaks and range placement, for the frame, the recorder, review reads and the delta. A written run keeps no order, and a window holding a follower claim or a move source resolves and is checked against the resolution.
- `CommandProjectionMap` in `packages/plitejs/src/core/command-document.ts` gains `moved`, `nodePath`, `projectRange` and `reorders`, and the frame binds a moved block's key on a fresh index build and asks `projectRange` for every caret and range on a reordered root.
- The recorder's moved-content throws carry a refusal reason, a property-only step maps each token through `rebaseProperties`, and next's in-order property grouping goes.
- Projections drop a held member by next's `stores` rule, so the first build's `withoutHeld` and the gate's held-line clause go.
- `PairedChanges.breaks` in `ledger/pairs.ts` becomes `joinsAndSplits`, so `breaks` names only the map's breaks.

### Facts that set the shape

- **U records a crossing Bold wrongly.** The frame bolds `bc`, the recording accepts to `b` alone, and U's test-build frame law throws (`merge-next/upstream-our-plugin-a1.log:337`). ### Owner and data

One owner per mode: `ReviewLedger.modeOf(mode) → ModeProjection.sync(stored) → RootProjection extends Level`. A `Level` is one sibling list with measured slots, including the `ORDERED_RUNS` measure a container slot rolls up from its child level (O:packages/plitejs/src/authored/ledger/level.ts:46, 182-218). Each slot holds a `Run`. A resolved run's `order.segments` are stored token ranges in shown order, built by replaying placements on the element tree, so a move into another parent or a move inside a move is a pair of non-adjacent segments. `placesOf(run)` is the only position map (O:packages/plitejs/src/authored/ledger/places.ts:194-302, 651-664). Its clients are `mapOf` for the frame and the recorder, `viewPlaces` for reads and publication, and `assertShowsWritten` for the gate. A written run keeps `order: null`, and nothing adds an order to it later.

### Range placement

`Level.projectRange(low, high)` replaces O's hull widening, O's two crossing tests and U's ends-only mapping:

1. A range from the root's stored start to its stored end places over the whole projected root, so select-all keeps a moved last block.
2. Otherwise each end maps on its own, the start forward and the end backward, past added content. An end inside blocks the projection hides whole maps from their edge on its side, because a run's order can group hidden blocks with the segment after them. Nothing widens to stored content shown elsewhere, as next's M6 requires (U:packages/plitejs/test/authored-tree-commands.test.ts:1031-1044).
3. A range with letters whose image runs backward refuses `crosses`, where U collapses it to a caret (U:packages/plitejs/src/core/command-frame.ts:483-485).
4. A range with letters whose image has none while the projection shows some of those letters elsewhere refuses `crosses` for every step, before the frame would turn it into a caret. Content the projection hides, such as a pending deletion under Proposed, never counts, so a range whose letters it hides becomes a caret, as U's T1 cases pin. Any other image places, and every step records it, a format included.
5. A range or caret that meets an ordered run without exact alignment refuses `unaligned`.

Rules 4 and 5 visit only the ordered runs `orderedRunsIn` finds, and no other code a key reaches walks ordered runs. O's `unaligned` is not ported, and its `orderedSpans` walk stays only as a reader for the recording laws. A format records its image like a deletion or typing does, as M6 pins for those. So Bold from `b` to `x` also bolds the `c` and `uv` the preview shows between them, and Bold on Sol's crossed deletion from the second letter to the end bolds `acc` and leaves the moved `ff` plain (`merge-next/panel-p0/lead-probes/range-probe-a1.log`). Refusing those formats walked the image's letters, which grew with the blocks a range spans, so the "format refusal" Defaults row leaves it to a design of its own. An image with no letters refuses under rule 4 when the selected letters show elsewhere. Turned into a caret, it would run no property step, so a format would set the typing mark and save nothing (`merge-next/panel-p1/lead-probes/format-probe-base-a1.log`). On a move inside a moved quote this map gives both ends one place, so a format would bold nothing where next bolds every letter (`merge-next/panel-p2/lead-probes/nested-bold-base-a1-a1.log`). Next's tests turn a range with letters into a caret only where the projection hides those letters. A mutant that throws at that collapse fails only T1's six cases in `authored-tree-commands.test.ts`, three properties of `authored-tree-recording-laws.slow.ts` and one of its folded-defect cases, and in each the selected letters are struck or replaced (`merge-next/panel-p2/lead-probes/mutant-collapse-plitejs-test-a1.log` and `mutant-collapse-recording-laws-a1.log`).

### Breaks

- **Within a run.** A break is a pair of shown-adjacent segments that are apart in storage. Its projected position is `alignment ? alignment.mapPos(right.start, -1) : right.start`, and its sides are the left segment's stored end and the right segment's stored start.
- **Run edges.** U's zero-length sentinels at 0 and at the run's stored length turn a moved first or last shown piece into a break at the run's own edge (U:packages/plitejs/src/authored/ledger/order.ts:249-268). The next run starts at this run's stored end, so no pairing across runs is needed.
- **Nested containers.** A retained container's open and close tokens never move, so its edge is never a break by itself. `ContainerPlaces` shifts the child level's breaks past the open token, and `Level.breaks` adds slot offsets from `STORED_LENGTH` and `OUTPUT_LENGTH`.
- **Moves across parents.** A container that lands outside itself resolves with its siblings as one run, so the tree replay emits such a move as non-adjacent segments in that run. Child levels never apply it a second time.
- **Coincident cuts** keep distinct `(at, before, after)` triples; only identical triples deduplicate.
- **An invalid placement graph**, such as a missing anchor, a cycle or a duplicate token, is an invariant failure and never falls back to an ordinary diff.
