# Store the values people write, so a rejected cut or a retype never loses one

Status: partial: give-back waits on its next plan iteration
Topic: cut-join
Playbook: bug-fix

## Brief

### What will change?

Rejecting an Enter or split keeps differing halves apart, and a retype or reload keeps every written value. The give-back of a split's dropped value goes back to planning. A Yjs fix for duplicated blocks lands now.

### What could go wrong?

Schemas with a left-out default, Plate's included, get a new fingerprint, so older and newer editors refuse each other's saves and rooms until migrated. Until the give-back lands, rejecting a split whose left half is gone still loses its value.

## Teach

A schema can give a property a default and leave that default out of the saved document. Today the editor also leaves out a value someone wrote when it equals the default where the node sits. After that, "never written" and "written as the default" look the same.

That blur causes every finding the redesign plan's panel raised. A rejected cut cannot tell a dropped value from a written one, so it merges halves that differ. A retype or a move reads the new block's default where a person wrote a value, or crashes when the new block requires it. Two decision orders give two results, because one order drops a written value before a retype and the other keeps it.

This plan stores every written value, then lands the cut-join and give-back slices on that rule. An older editor cannot read the new saves safely, so the schema fingerprint changes and each side refuses the other's saves until migrated.

## Design

Every storage shape keeps slice 1a's `heldProps` at both of its call sites, the decision and the admission settle, because a written value still has to leave a place that cannot hold it.

**Storage.** The architect run picked "store every written value" (`docs/plans/artifacts/cut-join-values/redesign/architect-1/synthesis.md`), and its cross-judge picked the same base. A key that is present was written and a key that is absent was never written, so "written" has one owner and needs no list of special keys. Two exceptions remain. An Editing write that an Editing removal takes away again leaves no trace, whoever removes it (S19), and a move drops a written value its new place cannot hold when that value was the left-out default everywhere the node stood (S22, S32). `docs/plans/2026-10-22-carried-moves.md` owns the second one, and until it lands such a move refuses. The storage slice deletes the two strips in `editor-schema.ts`, the `omittedDefault` repair branch, and the `omit-default-property` code of `EditorSchemaRepairCode` with Plate's HTML mapping of it. It never adds cand-2's `storageLawOf`. It also does these:

- **Fence.** Every schema that declares a property with `omitDefault` gets a storage revision, a `storageRevision` field of the canonical model and of the generated contract, apart from the contract's existing `revision`, so it enters the fingerprint. An older editor then refuses the new editor's envelopes, rooms and saved history (G3), and the new editor refuses theirs. An older generated contract has no such field and still reads with its own fingerprint, so Plate's `migrateDocument` can take it as a source. That path needs a named schema, and the app bumps its version and supplies a step and the old fingerprint. An app whose schema identity is derived loads the envelope's children instead. Plate's fingerprint changes too, as it already does with most kit changes, and its first-party saved bytes stay the same. Saved children load without the fence and go through the upgrade below. A Yjs room has no migration, so the app exports the room's children with the older editor and seeds a new room. The new editor cannot open a document kept only in a room until someone exports it. Saved children also reach an older editor without the fence, so it can still crash on a new save that holds a pending written default.
- **Upgrade.** When a load meets a key that a node lacks under pending tags, it stores the key's tip value when that tip is one set write, the place holds the key and the value equals a default that place leaves out. Only a load runs it, so a live editor never brings back a pending default that a decision dropped. A later load does bring it back once a retype gives the key a place again (`docs/plans/artifacts/cut-join-values/storage/round1-fixes/probe-e-fixedb-a1.log`). That is the state an older editor's strip leaves, even after a later retype changed the default (G4, S43). A removal tip, Editing or pending, keeps the key absent (S29). An older editor leaves the same state when someone directly removes a value it had already left out, because that removal records nothing. The upgrade reads it as the stripped write, so after a retype the node reads the written value where the older editor reads the new place's default.
- **Give-back.** When the left half is gone, a value on the right half beats what the split copied there for that key, unless it is the split's own output: absent, a default that any place fills for that key, or a generated value. Any place counts, because a retype after the cut can leave the old place's fill behind (S40). So a later write survives (S15, S16, T10, S3), and a fill never replaces the copied value (S25, S27, S41).
- **Compile checks and typing.** An exclusive group skips a member that holds a default its declaration leaves out, and counts a member that holds a default its place fills, as next does. A schema fails to compile when the declarations that cover one exclusive member's key leave out different defaults (S24), or when the split rules that cover one key differ by place (S28), so the keys a split drops never depend on where the piece stands later. A prefix key covers every key it matches, so it meets an exact key in both checks. The check groups element and text properties apart, because the `authored` key preserves on a text split and drops on an element split. Typing compares stored values, and `toggle-mark` has one activity test.
- **Moves.** A move, merge, wrap, unwrap, split, retype or transfer, Editing or proposed, can carry a stored value to a place where its key cannot stand. The storage slice refuses every such value. Next refuses the same move when the value is not the key's default (S23), but applies it when the value is the left-out default, because next never stored it. So S22, S32, S33 and S34 fail on the storage slice alone. A decision or preview that lands a merged block's children under a block of another type also carries such a value there, and only the joins slice judges them at that block through `heldProps`. Without it, a proposed join of a paragraph storing such a value previews with an error and accepts as invalid, where next applies it. So the slice lands only with the moves build and the joins slice (Defaults). The push panel's second round found the slice's first moves mechanism wrong in three cases, and the run reverted it (decision log, round 2). `docs/plans/2026-10-22-carried-moves.md` designs it again. A paste of copied content is not a move, so it refuses such a value where next applied it.
- **From the classes shape.** Plate's heading split reset is tied to the break that causes it, and a round-trip test checks that a saved written default loads back unchanged.

**Cut record.** The keys a split drops come from the key's one split rule, and the cut's own change holds the type and property tags it wrote, such as Plate's heading reset (S7). Under a container whose content program has a prefix slot, that change also tags the right half's type, even when the type stays the same, so the join can undo a forced type, such as a title's continuation, and tell it from a later direct retype (S42). A proposed removal of the left half waits on the cut, as on next, and lands in the same call (S36). The give-back copy plan, `docs/plans/2026-10-23-giveback-copy.md`, replaced how a rejected cut gives back what the split dropped. A proposed split copies the left half's tags on each dropped key onto the right half, each marked with the cut's change, under one tag of that change, and stops writing `kept`. Rejecting the cut reads those copies when the right half's own writes leave only the split's output, so the rejection reads no other node (T11, S20, S37, S38). A settled write on the right half still hides them (S39).

**Joins.** A rejected cut compares its halves by what each reads at its place, over every key that is not metadata, so an element id never keeps halves apart (S7). It compares them with the cut's own change undone, its type and property tags included. A cut saved without a forced-type tag, by next or before the joins slice, treats the right half's type as forced when the content program builds that type at that slot after the left half's type (S6, S30). In such a save a direct retype like S42's looks the same, so it joins as on next. On the right half, a key the split drops reads as the left half's when it holds the split's own output, as Give-back defines it (S26). The rejection decides at once only when every accept-or-reject combination of the pending changes that touch the halves gives the same verdict, and otherwise waits on them (T1, T3). Equal halves join and keep `{ ...right, ...left }`, and halves that differ in every combination stay apart at once (T6). Halves join at once only when every combination stores the same joined values, so the saved bytes never depend on the decision order. These pending changes count:

- a change to a compared key on either half, including writes on the right half to a key the cut dropped (S18). So with a tag on the left half alone, for a key the split dropped, the halves join at once while the right half holds the split's output there (S13), and the rejection waits once the right half holds its own value (S35);
- an insertion, removal or split between the halves, other than the deciding change's own content (S8, S9, S21);
- a change to the place that can drop a compared key or change its default (S4, S5, S17).

The joins slice tries at most 8 combinations, which is 3 touching changes, and past that the rejection waits. Benchmark's decide-latency probe measures the cost. An Editing type change keeps the halves apart (T24, S42). The joins slice judges content a decision moves into another block, through a merged block, a rejected cut's join or a landed line, at that block through `heldProps`. Moved content is a node the resolver places under a parent other than its parent in the input. S17's proposed Backspace keeps its links' refs under their paragraph in the review document, because a proposed join leaves content in place. The moves plan lets that proposal record, and accepting it drops the refs at the heading through `heldProps` (Defaults). The joins design is `docs/plans/artifacts/cut-join-values/joins/architect-1/synthesis.md`. The proposed view of a pending block join lands the joined block's children in the receiving block, never inside an inline element of it, which fixes S14's throw (S14, S31).
