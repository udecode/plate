# Settle shown block ids wherever their last suggestion is decided

Status: executed: step 6's full protocol runs as suggested task t_982c0e6a
Playbook: plan

This iteration finishes phase B of [Suggest, preview and decide in an editor that makes block ids](2026-10-23-construction-values.md) and lands with it and with [Spare blocks in a shared room](2026-10-24-spare-collaboration.md). The second diff panel of the spare iteration found that a shown value, the frame id an inserted block shows while a suggestion keeps its own fresh id, settles only inside the decision of the person deciding. When two people decide the last two suggestions that hold one shown value at the same time, both keep the stale value after they merge, until anyone decides again. The same panel found that round 1's fix for shown values a block's place cannot hold drops them on unrelated decisions and changes the saved value with decision order. These findings are rows 78, 79 and 80 of the spare iteration's decision log. An architect arena with Opus, Astra and Sol runners and an Opus judge picked the Opus design, in which authored admission settles shown values on every commit and load over the ledger's holder index. Probes then ran each premise of that design, and the plan panel's three rounds closed 13 critical gaps in it, 5, 6 and 2. The second round moved settlement into a stage of its own after admission's other repairs. The third closed a settling undo step to later merges, and gave the line-start handover a narrower key set than the emptied-place comparison.

## Brief

### What will change?

You asked for Suggesting with block ids, and a review found that two people deciding at once leave a block with a stand-in id. Now every editor puts in the real id once the last related suggestion is decided.

### What could go wrong?

Every editor now writes the real id, so two people may write the same value at once. A join that two people's rejections free at once can stay stuck. Putting in the real id always gets its own undo step.

## Teach

A suggested split or copy gives the new block its own fresh id, so the original block keeps its id while the suggestion is pending. The new block also stores a note of the id it shows in the suggested view. Once every related suggestion is decided, one block takes the shown id for real and the note goes away.

Today only the editor of the person who decides makes that swap, inside the decision. A decision that arrives from someone else, an undo, a redo or a load never makes it, so two people who decide at once both keep the note.

This plan makes the swap the last step of every change and every load, on every editor. That step rechecks only the ids still shown somewhere. Typing never adds one, so typing stays fast. Every editor writes the same result. A redo works the swap out again instead of repeating it.

## Main changes

- **Settlement runs after admission.** `DocumentAdmission` gains an optional `settle` hook. `admitTransactionDraft` runs it once per commit, after the admission loop and the unique repair, and admits its repair through `commit` once, as it admits the unique repair. `repairLoadedDocument` runs it last. Authored admission implements it with `settleShown`, which reads the admitted value, the stored value the commit started from, the facts and the ledger's holder index. It writes each winner's shown value as an ordinary property change by path, so the value reaches the room the way every admission repair does, and the Yjs code does not change. Settlement keeps every node it does not change identical, so a commit in a document whose showers all wait gets no repair. It writes a value only where no element stores it, so the unique repair has nothing to do after it, and settling its own output writes nothing. The resolver loses its settlement tail, `settledOf`, `heldShownMembers` and the alias term of `dropsValue`, so a decision's own view no longer shows settled values, and the settle stage writes them in the same commit.
- **Each commit reads every group that shows a value.** After every admitted commit and load, no ready group keeps an alias. The ledger's holder index lists every element that shows a value, across roots and unbuilt spares, and settlement reads each one's group against the current document and facts. No list of changed holders exists, so a verdict, an insertion count, a spare record or a root owner that turns a group ready settles it in that commit. Settlement reads each group once per commit, however many of its elements show a value. The settling loop is a worklist keyed by each value a winner releases, so a chain of showers, each waiting for the next one's value, visits each contender once per release instead of once per pass. An alias lives only while a holder of its group is pending, and typing adds none. In a document with no pending copy, settlement reads no group. The whole-document form, which walks every root instead of the index, serves the order checker and the invariant test.
- **A wider holder.** `ValueHolders` replaces `StoredBlocks`. Each holder records its block-local standing. That is the stored claims on it or above it in its block, retained ones included, the contexts it belongs to, the type tags on it and every ancestor, its own tags on the key, and whether it is inside an unbuilt spare. `isPendingHolder` reads that standing against the facts. A holder inside a content root also waits on the elements that own that root. Their standing lives in other blocks, so the memo keeps none of it. At settle time settlement judges each such root once. It rebases the owner root's owned-root index from the stored document's index with `rebaseElementOwnedRootIndex`, so no commit builds an index from scratch. It lists every owner binding of the root through a new internal accessor beside `getElementOwnedRootGrammarBindings`, which returns one owner per grammar. It reads each owner from the admitted value at the path `resolveElementOwnedRootPath` gives, because a binding can keep an older copy of its owner without the owner's newest tags. The holder is pending while any owner is pending, each owner judged the same way, up to the main root. Settlement keeps each root's standing until it ends, and a root it reaches again while judging that same root adds nothing. So a cycle of shared roots ends, and a root with 1,000 owners is judged once, not once per holder. That waits longer than needed for a shared root that another owner keeps, which is rare. A root lives as long as its owners, and Suggesting an owner's deletion leaves the root's blocks unmarked. Without that term, a value in a card's body would settle while the card's deletion can still remove it. The closing pass reads only stored-element holders, as the Command values law says; settlement also reads container-spare holders.
- **History replays are judged again.** Undo keeps a settling commit's settle writes apart and builds the redo step without them, so redo brings back each loser's `as` key and each winner's earlier stored value and `as` key. The settle stage then judges those groups under the current document, as it judges a fresh commit. [Redo a settling decision by taking settlement back](2026-10-25-redo-settlement.md) builds this. A redo with no new holder writes the decision's bytes, and a redo after someone added or removed a holder settles as a fresh decision would.
- **A settling commit is its own undo step.** Core tags a commit whose settle stage changed anything. The history plugin starts a new entry for it, as it does for `history-push`, and closes that entry, so the next commit starts another one. No entry then composes an alias's creation with its settlement and loses the alias that redo brings back. No later edit composes into a settlement either, where taking the settlement back on redo would also take back the edit. History merges a commit into an earlier entry only under an explicit `history-merge`, or for native text input inside the merge window (`history-plugin.ts:749-800`). So the only undo steps that split are an app's explicit merge into or out of a settling commit, and typing that deletes a group's last pending holder, with the keystroke after it.
- **Load settles once, last.** `authoredAdmission.load` no longer settles. `repairLoadedDocument` runs the authored load, the unique repair and the orphan-root removal, then the settle stage, so no settlement sees a root the load drops, and loading the result again changes nothing. The stage runs even when the earlier repairs change nothing. A load with no editor or ledger, such as a DOCX import or a migration through the `repair` capability (`authored.ts:1502`), settles with the whole-document form.
- **Placement is judged once.** A ready group judges each element that shows a value at its decided type and place, and drops a value that place cannot hold. Since a pending type tag above the element keeps the group waiting, no later decision can change that place.
- **Peers write the same bytes.** Settlement calls no generator, orders roots by `documentRootsOf`, merges several `as` members per key in canonical set order and writes one member or none, so every editor that admits the same document writes the same repair, and settling its own output writes nothing.
- **The round 3 spare fixes ship here, corrected.** The round 3 patch used one set, every key a split drops, for two jobs. The emptied-place comparison ignores those keys when it asks whether an empty line matches a split line, and the line-start handover moves their values. Core now keeps two sets. `splitDroppedKeysOf` returns element keys that every declaration drops on split, content keys included. The comparison and its format veto ignore them, since the two halves of a split always differ on them. `handoverKeysOf` returns those of them that `retypeDropOf` passes, the check `unique` already requires, and only the handover moves them. `retypeDropOf` passes only element metadata, so no content value moves. A quote's emptied last line then takes back the text of a rejected split below it in every decision order. For a key the handover does not move, the rejoined line keeps the value of the line its text came from. Joining the text into the quote one decision at a time keeps the same value, and step 2's two narrowed-id cases store it in every order. So a narrowed id such as `target.group('block')` beside an inline type still hands over and the line takes the quote's spare id, an id narrowed to `target.type('paragraph')` stays with the text's own line, and a content value never moves. A `unique` key always hands over, because the compiler refuses a `unique` property that `retypeDropOf` rejects. So Plate's block id, which is unique, still moves under a schema that keeps unknown types. A key that is not unique stays with its own line when the schema keeps unknown types in a place that admits them, and step 2 changed that case's expected value. No retype can drop a handed-over key from either line, so the handover keeps its rule of no wait and no place check. The round 3 patch also took content keys and keys a retype drops. A container's prefix check reads each child's required value through the schema, so an omitted default counts. The spare iteration's third diff panel logged both patches open with this build as their stop.

## Premises

Each premise of the base design, run against existing code before the pick.

- **Admission sees every commit.** A probe that counted `authoredAdmission.commit` and `.load` calls found one commit for a local decision, its undo and its redo, one for a peer's decision on the receiver, and two loads and one commit for a late joiner (`admission-routes-a1.log`). Load never readmits after its unique repair or its orphan-root removal, which the code shows at `repairLoadedDocument`, so load settles once, after both. A commit admits its unique repair after the admission loop (`admitTransactionDraft`), which is where the settle stage goes.
- **Readiness only moves one way.** Holders emptied by a change with no claim on them, at root level and inside a quote, accepted or rejected, and a decision on a context-carried holder, store equal bytes in every order that is not blocked (`readiness-run4-a1.log`, cases B2 to B4). Case B1 differs across orders only in the spare ids each fresh editor mints when it loads, which the probe compared byte for byte. Case A2 contradicts the premise for a context insertion. The holder reader treats an element whose only claim is a context `in` member as unclaimed, so the pending predicate reads contexts.
- **A retained mark leaves in the commit that lands it.** This fails under concurrency. Two peers that each reject one of a retained join's two blockers leave the join stored with nothing pending, on both peers, in both delivery orders, while the same two rejections on one editor land it (`landing-probe-3-a1.log`, case B1). A withdrawal by the blocker's author lands it, and a strike leaves an empty pending insertion someone can still decide (case B2). This plan keeps the group waiting in that state and leaves landing to its owner.
- **Redo can replay bytes.** This fails the Command values law. A holder written outside history, through a skipped write or a peer, survives undo into redo, and redo then writes the settlement while that holder is pending (`landing-probe-3-a1.log`, case B3). Peers agree and no id repeats, but a pending holder placed before the shower would take the value in a fresh decision, so a historic commit settles again.
- **A whole-document walk may cost too much per commit.** Today's unindexed pass with one shown value costs 0.56 ms at 1,000 paragraphs and 6.2 ms at 10,000 (`scale-settle-a1.log`). The base arm of step 8's Suggesting run costs 8.2 ms per keystroke and 16 ms per Enter at 10,000 with ids (`bench/final/suggesting-3a60882d80-measurements-2.json`; `scale-base-ops-a1.log` failed before it timed anything). So that walk would add about 39% to an Enter. That ratio is inferred from two unpaired runs on a host whose load average was 13 to 24, so it rules out nothing by itself. It only points at reading showers through the index, and step 6 decides.

The losing candidates handled cases the base dropped. This plan adopts their redo, which works the result out again instead of replaying it (cand-1 and cand-3); the settle stage does the work, and history keeps a settling commit's settle writes apart so redo can leave them out. Admission-time structural landing (cand-1 and cand-3) stays a deferred row, because two peers' identical landings need their own proof. An element-granular holder index (cand-1 and cand-3) is decided by step 6's quote cohort.
