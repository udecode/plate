# Review tree pivot: shared dependency contexts, one review owner

Status: building: P1.8 waits on its plan panel
Playbook: plan

The Suggesting cost run closed with three costs it could not fix inside today's design, and the current tree fails the keys plan's frozen budget: line D on four Suggesting select-all-delete cells, with two more cells at 20,000 blocks too slow to count (`docs/plans/artifacts/2026-10-13-review-tree-pivot/m2/judge-ctl-count-3-a2.log`). The owner's word on 2026-10-13 was to hard pivot instead of finishing the constrained design, so this plan replaces it. Today a run typed inside someone's pending insertion copies every enclosing insertion's mark, which is right in meaning and quadratic in size. After the pivot the run keeps its own claims and one `in` member naming an immutable context record that lists the changes it rests on, so stored review data grows linearly and every saved document keeps its meaning. Context and verdict records live in two named roots that bind to top-level Yjs types, which merge when two peers create them at once. Decisions keep today's physical writes and add a verdict record per change incarnation, which keeps an accepted change accepted when another peer types inside it at the same moment. One review owner per editor then replaces the command projector, the preview cache and the change index, and advances from each commit's changed ranges, so a key costs the same at 100 and 5,000 blocks. Its execution playbook is the Build playbook. [The suggestions plan](2026-10-12-suggestions-complete.md) waits on this plan for its P2.4 docs, `best-api repair` and benchmark rerun, and [the cost run](2026-10-13-suggesting-cost-benchmark.md) pivots its three open costs here.

## Brief

### What will change?

Per your hard pivot, suggestions get rebuilt. Typing in a long document full of suggestions costs the same as in a short one, nested suggestions store one link each, and accepting gives the document each author saw.

### What could go wrong?

We rebuild the editor's core list of blocks for speed, and every edit goes through it. Two people deciding one suggestion opposite ways at the same moment can still lose text, as today.

## Teach

Suggestions live in the document. Each piece of suggested text carries marks that say which change made it and whether it adds or removes text.

Today, text Bob types inside Alice's pending insertion carries Alice's mark as well as Bob's, so rejecting Alice's insertion removes it too. Nest two hundred suggestions and the innermost text carries two hundred marks, and the document stores 40,000. After every key, three helpers also rebuild a copy of the whole document, so long documents type slowly.

After the pivot, Bob's text carries Bob's mark and one link to a small shared record listing what it sits inside. Records live in a hidden part of the document that every collaborator shares, and they stay after the text around them is deleted, so rejecting Alice's insertion still removes everything typed inside it. One tracker per editor then redoes only what a key touched.

## Document shape

The recorder writes this when Bob types `X` inside Alice's pending `hers`. The resolver, the change index, paint, Yjs, history and DOCX read it through `reviewOf`.


A node's pending dependencies are its own claims plus the changes its context lists, minus whatever a verdict settles. Every reader applies today's rule to that set: a node goes when any change in it is rejected. A context record is immutable, its id hashes its content (its base context and its member), and it is never removed while a room is live, so a dependency outlives every fragment of the insertions in between. Text Carol types inside Bob's `X` points at a context whose base is Alice's context, so a run stores one link however deep it sits. At a boundary, new text rests on the exact intersection of its neighbors' sets, which can need a second record when the neighbors' contexts are not nested. Every claim names an incarnation. A claim without `inc` belongs to `<change>@<at>`, which every peer derives the same way and a minted change id already makes unique. A change id proposed again after its decision starts a new incarnation whose claims carry `inc`, minted by the writer's runtime, so two peers doing it in the same millisecond differ and old claims, verdicts and captured revisions never touch it. A root context has no `base`. A record carries its hash as `ctx`, never `id`, so element-id admission cannot read two equal records as a duplicate element. A decision writes today's removals and one record per incarnation it decides in `roots.$authored-verdicts`; an accept verdict keeps what a concurrent split copies accepted. A split claim on a piece cut from a line that a pending join merges carries that join's incarnation as `follows`. A reject turns a replacement's deletion claims into held members, `{ "kind": "held", ... }` with the claim's other fields, which no reader takes for a claim, so the restored text reads plain to the recorder, commands, DOCX and paint alike. While that incarnation still holds pending insertion content, such as a peer's late typing inside the rejected new text, the settle pass makes them deletion claims again, and holds them again once that content goes.

## Hard cuts and app migration

- The recorder stops copying enclosing insert marks onto new text. A stacked insert set stays a valid document with today's meaning, so loading one is compaction for size, never a correctness step: `compactClaims` turns it into contexts by membership, attributing nothing by time or id order. No published release holds review-tree marks: plitejs's only version, 0.0.1, is from 2026-08-26, platejs's `54.0.0-beta.1` from 2026-06-17, and the review tree's `marks.ts` first landed in `c01399d08b` on 2026-10-11 (`docs/plans/artifacts/2026-10-13-review-tree-pivot/probes/published-a1.log`, `docs/plans/artifacts/2026-10-13-review-tree-pivot/probes/published-platejs-a1.log`).
- A claim of a change id proposed again after its decision gains `inc`, and `AuthoredMark` gains an optional `inc`; a node's `authored` set gains the `in` member, which `readAuthoredMarks` leaves out. Hand-written marks without `inc`, such as the registry demos' seeded suggestions (`apps/www/src/registry/examples/playground-demo.tsx:26-85`), stay valid as the legacy incarnation `<change>@<at>`, and the Plite example's mark list (`apps/www/src/app/(app)/examples/plite/_examples/authored-changes.tsx:206`) reads through `reviewOf` so it never lists `in`. The marks validator's rule of one author and one time per change id (`packages/plitejs/src/authored/tree/marks.ts:236-242`) becomes one author per change id, and `propose({ changeId })` with a decided id starts a new incarnation instead of keeping the first time (`packages/plitejs/src/authored/authored.ts:921-926`).
- `read.value()` gains `records['authored-contexts']` once a document holds a pending insertion inside another, and `records['authored-verdicts']` once any change is decided; apps already save the whole value (`apps/www/src/registry/examples/suggestion-persistence-demo.tsx:63`). A saved value missing a context its runs name is refused at load with a diagnostic that says to save `read.value()`, not `children`.
- A Yjs room seeded before the change upgrades in place: its fingerprint matches the new schema's base fingerprint, computed without the contributions that declare metadata roots. The binding writes the new schema envelope, admission compacts the imported document, and the binding writes that repair back to the room. A client from before the change then fails the fingerprint check with today's message.
- `read.groups()` returns `{ items, cursor }`, and a group summary drops its `changes` array for `changeCount` and gains `colorSlot`, with members read through `read.changes({ group })`. Its callers outside tests are `useSuggestionGroups` (`packages/platejs/src/react/features/suggestion/useSuggestion.ts:84`), the copied sidebar and paint through that hook (`apps/www/src/registry/components/editor/suggestion.tsx:87`, `:108`) and the copied discussion panel (`apps/www/src/registry/components/editor/discussion.tsx:309-333`, `:429`); no page under `content/docs` names `groups()` (`git grep`, 2026-10-13). `api.subscribeChanges` passes `{ changed, removed, groups, blocks }` instead of an id list; its caller is `packages/platejs/src/react/features/suggestion/suggestion-view.internal.tsx:79`. Phase 3 runs `best-api repair` on both shapes.
- Phase 2 deletes `command-projection.ts`, `carryReadPreviewKeys`, the preview and index WeakMaps and the rebuilt change-index cache, with no compatibility path. Phase 1 leaves them untouched; they call the kernel, so they read the new shape through `marksOf` without being ported. The pure resolver and indexer stay in `src` as the one kernel that `projectAuthoredDocument` and the ledger's first build call; its production callers are DOCX export and import, AI capture and the V54 migration (`git grep`, 2026-10-13).

## Risks

- Every edit goes through the new core sequences. A defect there reaches plain editing too. The core and plitejs partitions, the plain-Plate arm of lines A to C and the page spec guard it, and the phase reverts on its own.
- Two peers deciding one change opposite ways at the same moment both land, as today (`packages/plitejs/test/authored-tree-collab.test.ts:205-229`): a replacement loses both sides, and a fill and the child it replaces can both go.
- A peer can receive a run that names a context before the context itself (`docs/plans/artifacts/2026-10-13-review-tree-pivot/probes/causal-ref-a1.log`). Admission holds that remote commit until the record arrives; a defect there shows a stalled peer, not a wrong outcome.
- Context and verdict records grow by one per nested recording event and one per decided incarnation, and only offline compaction shrinks them. Phase 1's keep decision gates lines F and G on a document holding 10,000 of each.
- A Word re-save could break the Plate part's bookmarks. Import then refuses under the default loss policy instead of guessing. Word is not installed on the build machine, so no test uses a file Word itself saved; the round-trip test renumbers ids, drops date milliseconds and splits runs as Word does when it saves. Import also refuses, under the default policy, a file where someone changed a block holding a suggestion in Word, a decision made in Word included.

## Main changes

- The recorder writes a run's own claims and at most one `in` member, minting a context record only for a new nesting context or a non-nested boundary. Fills rest on the changes they complete, so text later typed into a fill depends on them.
- A decision writes today's removals and one verdict per incarnation it decides; a plugin pass then settles what a concurrent split copied over the changed runs only.
- One `ReviewLedger` per owner editor derives previews, command projections, location maps and the change list from marks and records, advancing from each commit's changed ranges.
- The command frame maps positions through the ledger's projection map instead of composing the projection change with every command.
- Core keeps the top-level list and sibling indexes as persistent sequences, materializing arrays only for a whole-value read, and the Yjs binding stops reading the whole value on every local commit.
- One recorder serves both intents. An Editing write records what Suggesting records, under a reserved change that reads as accepted, and accepts its own claims in the same commit. It keeps only a join or split whose landing waits on another pending change. Where a write's reach holds no other author's pending change, Editing writes the plain edit directly, and only the rest records and accepts.
- A piece split off a line a pending join merges names that join, and lands right after the joined line once both are accepted, so a line split beside a pending join stays inside the container the join reaches.
- Revisions hash a change's own incarnation-qualified content with block-relative paths, so content moving above a change no longer makes it stale; edits to covered content still do.
- A preview mode costs nothing per commit while no view shows it.
