## Brief

### What will change?

The plan check refuses a ticked step that cites a proof file a decision row marked as not passed, until a later row proves or accepts that file. New rows of that kind name the file they grade.

### What could go wrong?

Unlabeled rows protect nothing. A context citation of a not-passed file fails until it moves to the log. Once synced, the log helper refuses unlabeled marking rows, about 93 a day by an inferred count.

## Main changes

- A decision row names a proof file as `proof: <path>` in its evidence only when its verdict is that file's proof of a plan step passing or failing, one label per file. A row whose verdict grades no file, tracks a finding, a bug or other work outside the step, or comes from a reviewer in any phase, writes `proof: none`. A label is `proof:` at the start of the evidence cell or after whitespace, a semicolon or a backtick, then whitespace, then `none` or a path that contains the run directory's root, and it ends at whitespace, a semicolon, a comma or a closing backtick; anything else after `proof:`, such as `runtime proof: real click` or `a proof:...:captured`, is no label. The path is read through the citation reader `status.mjs` already has, so its trailing punctuation, `:<line>` and `#L<line>` drop as they drop for citations, and it must exist.
- `decisions-check.mjs append` refuses every new row whose result starts with `partial`, `open`, `gap`, `blocked` or `inconclusive` and that carries no valid label, whatever else it cites, and refuses an invalid label only on those rows and on `accepted` rows. It skips rows in a `review` phase, as the path check does, and those rows change no state. Within one `append --from` batch, earlier rows count before later ones. The check of a whole log does not ask for labels, so no row written before this lands fails it.
- A `superseded`, `corrected` or `reverted` row needs no label and changes no state. When the proof it replaces no longer holds, the lead also appends a labeled `partial` row on that proof.
- `decisions-check.mjs` takes `accepted` as a status word. `append` refuses an `accepted` row unless its `proof: <path>` label names a file whose latest labeled verdict is not passed, accepted before or not, and its `word: <word>` is an option of a Word cell in the Defaults of the plan beside the log. The word ends at a semicolon or at the end of the cell. A partial proof logged before labels existed is accepted by first appending a labeled `partial` row on it.
- `plan-open.mjs` reads the plan's own decision log in order, and fails when that log does not parse. For each labeled file it keeps a verdict and an acceptance. A labeled row of the five statuses above sets the verdict to not passed and drops any acceptance. A labeled `accepted` row sets the acceptance, replacing an earlier one. A labeled row whose result starts with one of the proven words `decisions-check.mjs` already defines sets the verdict to passed. Unlabeled rows change nothing.
- It refuses a box closed since the base whose line, or a line indented directly under it, cites a file whose verdict is not passed and whose acceptance is missing or names a word that is no longer an option of the plan's Defaults. That includes a file the box cites only as context, such as an earlier attempt, a base control or an open bug's probe, because the check cannot tell context from proof. The refusal names the three ways out: rerun the proof, log its acceptance, or move a context citation to the decision log.
- To read the Defaults, the check blanks fenced and commented lines, where a fence opens with three or more backticks or tildes and closes only with the same character at least as many times. It reads the section with the moved table reader, takes every table whose header starts with Decision, Pick, Alternative and Word, and finds the Word column by its header. It splits each cell on commas and the word "or", and compares without case, straight or curly quotes, backticks, bold marks or trailing punctuation.
- Each labeled path and each box citation is keyed by its path relative to the project root, so a relative, a `./` and an absolute spelling name the same file.
- `status.mjs` gains the table reader and its fence and row helpers from `plan-page.mjs`, and the status-word reader and the proven words from `decisions-check.mjs`, moved without change. `plan-page.mjs` and `decisions-check.mjs` import them. `plan-page.mjs` keeps its own section finder and its result colors, and gives `accepted` the color of a proven result, which changes how three existing ellie rows that start with `accepted` render.
- The block's Plans and trails rule states the label, the refusal, the `accepted` row and the labeled `partial` row that withdraws a replaced proof. Its Todo list and close rule adds the `accepted` row to the acceptance it already describes.
- The block's Backlog sentence for the parent plan's lesson 1 changes, because S3 showed the runtimes reading it two ways. An item whose script or check already exists is not built again. When it repeats because that script went unused, its mechanism is a hook or check that runs or demands the script where the mistake happens, built under the same test as any repeat item. Every other Backlog item still names its `owner:` and a dated or observable `stop:`. This reverses part of lesson 1, which `8acd6ea` added.

## Ways past

The Corrections rule lists each way to pass the new check without fixing the proof. The build tries each one. A way that passes blocks the check until an existing mechanism closes it or a `look` Defaults row accepts it; the Defaults row on known ways past accepts ways 1 to 14. A box that closes with `skip:` and cites no file is the block's own escape, which names its reason, so it is a limit, not a way past.

1. An `accepted` row whose word is a real option of an unrelated Defaults row, such as "hold", which 6 of 42 real Defaults tables offered on 2026-10-07. The check lets it through because the page shape tells writers to leave file paths out of Defaults rows, so a word cannot be tied to its proof there.
2. One `accepted` row unlocks every closed box that cites its file, including a box for a step its Defaults row never covered. The check lets it through because the row carries no step key; adding one is another field on every acceptance.
3. An owner's reversal that edits a Defaults row's Pick but keeps its Word cell, so the `accepted` row still passes. The check lets it through because the row records no Pick text; adding it is another field on every acceptance.
4. A false clearing row written through `append`, such as `verified` with a label on the partial file. The check lets it through because it cannot judge a row's truth; the decision-trail review reads the records only for the runs it covers.
5. Deleting or rewriting a labeled row in the working tree, committed or not, or writing a row by hand instead of through `append`. The whole-log check could compare committed rows, but it does not today, and requiring labels there would fail rows already written.
6. A row that grades a file but writes `proof: none`, or labels the wrong file. The check lets it through because it cannot judge which file a verdict grades.
7. A failing proof never logged with a marking row and closed on a proving row. The react review's type check was one until its `partial` row was written; its box cited a log that ends `exit=1` and passed. The check reads the exit line, but a red run legitimately ends non-zero, so a non-zero exit cannot refuse a box by itself.
8. A box that cites a file the labeled row did not name: a later attempt with no row, a copy, the run directory, or the proof's command. The check keys state by file, so another file has no state.
9. A box that cites a run-directory file by its bare name, which the citation reader never reads. On 2026-10-07, 23 real closed boxes did, by round 7's Opus probe; the build recounts it with its own logged pattern.
10. A labeled row in another plan's decision log, which the check does not read, because each plan owns its log. This plan's own panel rounds sit in the parent plan's log, so this plan's boxes are judged only by the rows its build writes in its own log.
11. The parser gaps the parent plan accepted: a space inside a cited path, a link target with brackets and a box line after a blank line. On 2026-10-07, 2 real closed boxes used the last one, out of 33,752 lines that matched `^\s*- \[x\]` in `docs/plans/*.md` at 15:08 UTC. A cited path that holds a glob, a range or a placeholder is skipped by the block's own rule.
12. A typo in a label path that names another existing file. The check lets it through because the path exists.
13. A withdrawal logged only as `superseded`, `corrected` or `reverted`, without the labeled `partial` row the block asks for. The check lets it through because the Defaults pick on verdicts makes those rows change nothing.
14. `PSTACK_BASE` left unset after an owner's commit, or set to a commit after the box closed. The check lets it through because it judges only lines added since the base it is given; the block already asks for the intake base after an owner's commit.
15. An `accepted` row with no `word:` that `plan-open.mjs` reads before `append` ran on it. The build closes it, because `plan-open.mjs` reads such a row as no acceptance.

## Delivery

The build follows sync-pstack's Lesson mode in dotai's checkout on main, edited in place, under the block's Other sessions rule.

- Each slice is the smallest set of cases that leaves the code coherent, and a refusal lands with the block sentence that teaches it. Its new test first fails for the named defect in a `git archive` export of `HEAD` with the test added, so the checkout never holds a failing test.
- A slice that changes `decisions-check.mjs`, `plan-open.mjs`, `status.mjs` or `plan-page.mjs` runs the old and new corpus over plate-2, ellie and plate-2-kb-rw, each twice: once with `PSTACK_BASE` at a commit from before that project's `docs/plans` existed, so every closed box is judged, and once at the default base. - A slice that changes the label reader, the citation reader in `status.mjs` or `append` replays a fixed set saved at the build's start: each project's rows outside a `review` phase whose result starts with `partial`, `open`, `gap`, `blocked` or `inconclusive`, written before the build's first row, leaving out this plan's log. The new `append` must give each row the old one's diagnostics plus exactly the missing-label message, and, once the replay adds `proof: none`, exactly the old one's.
- After the last slice, the build's own decision rows go through dotai's `decisions-check.mjs`, so the label rule binds them as lesson 13 says, and the diff panel reviews the build's diff within the block's cap of three rounds. Then the lead runs build-workflow, the suite and validate-skills, and commits and pushes as Lesson step 5 says. That commit is P.
