Decision brief:
- outcome: exact recursive application values without making every TypeScript
  access re-evaluate the complete dynamic plugin/schema grammar, plus one
  predictable element mutation API across all node plugins.
- chosen shape: raw descriptors infer lightweight capabilities; one closed
  `defineEditor(name, definition)` entry generates named recursive declarations
  and a structural schema contract; a generated branded `EditorKit` binds both
  at runtime. Every element plugin receives default `insert`, `set`, and
  `remove` methods under its capability name, with one plugin-authored override
  winning when it adds semantics.
- strongest rejected alternative: keep recursively inferring exact final
  `Value` from every raw plugin tuple and merely add more lazy providers or
  depth caps. That preserves the compiler bomb and creates a kit-size-dependent
  precision cliff.
- consequence: `PlateEditor<typeof RawPlugins>` keeps exact capabilities and
  descriptor-local element types but an intentionally broad editor-wide
  `Value`; `PlateEditor<typeof GeneratedEditorKit>` owns the exact generated
  `Value`, children relations, named roots, properties, and schema API.

```ts
// editor.generated.ts — conceptual output
import definition from './editor';

export interface TableElement {
  children: TableRowElement[];
  colSizes?: number[];
  marginLeft?: number;
  type: 'table';
}

export interface TableRowElement {
  children: (TableCellElement | TableCellHeaderElement)[];
  type: 'tableRow';
}

export interface TableCellElement {
  children: BlockElement[];
  type: 'tableCell';
}

export type Value = readonly BlockElement[];

export const EditorKit = bindGeneratedEditor(definition, {
  fingerprint: 'fnv1a64:…',
  schema: generatedSchemaTypes,
});

export type Editor = PlateEditor<typeof EditorKit>;
```

Normal consumption has no explicit type argument:

```tsx
import { EditorKit } from './editor.generated';

const editor = usePlateEditor({
  initialValue,
  plugins: EditorKit,
});

editor.children; // exact generated Value
editor.api.markdown.serialize(); // inferred lightweight capability
```

Every generated element plugin gets the same three root/transaction mutations:

```ts
editor.update.callout.insert({ icon: '💡', variant: 'info' });
editor.update.callout.set({ variant: 'warning' });
editor.update.callout.remove();

editor.update.table.insert({ colCount: 3, rowCount: 2 }); // semantic override
editor.update.table.set({ marginLeft: 24 }); // generated default
editor.update.table.insertRow(); // distinct custom operation

editor.update((tx) => {
  tx.table.set({ marginLeft: 32 });
  tx.table.insertColumn();
});
```

Raw kits and generic package ownership use the exact descriptor portal:

```ts
const table = editor.plugin(BaseTablePlugin);

table.update.set({ marginLeft: 24 });
```

The namespace is `BaseTablePlugin.name`; insertion, matching, and persistence
use `BaseTablePlugin.type`. Equality is never assumed.

Findings:
- `PlateEditor<TPlugins>` currently computes a separate schema plugin graph and
  attaches lazy `EditorNodeTypeProvider` / `EditorValueTypeProvider` witnesses,
  but those witnesses still call the recursive installed-schema conditional
  types for each concrete kit.
- The registry `EditorKit` is a large transitive composition and declares
  `type MyEditor = PlateEditor<typeof EditorKit>`, the exact expansion site that
  must become a generated named contract.
- Plite already owns exact generic `tx.nodes.insert/set/remove/...`, compiled
  schema fingerprints, structural schema deltas, and History/Yjs mismatch
  rejection. Generation should compile and serialize those truths rather than
  introduce a second schema model.
- Table currently owns a custom `update.insert` that builds a sized grid and

  schema construction, not another mutation engine.

  concrete declarations as derived contract artifacts. That is the closest

- The production mutation scan found 25 element-schema source files and 18

  projecting all `nodes.*` methods would create nonsensical APIs and is
  rejected.

Decisions and tradeoffs:
- Generate only at the closed application editor boundary -> package authors
  retain fast local inference and apps retain exact recursive documents.
- Make raw-tuple global Value intentionally broad -> no size thresholds, depth
  knobs, or randomly disappearing precision.
- Use one same-name override over synthesized defaults -> semantic plugins keep
  the obvious `table.insert` path without generic/custom alternatives.
- Restrict defaults to `insert/set/remove` -> strong discovery without dumping
  the full low-level node taxonomy under every plugin.
- Keep schema JSON and declarations committed -> editor typecheck does not
  depend on running arbitrary app code first; `--check` catches drift.
- Keep runtime fingerprint verification -> generated types cannot silently
  describe a different installed grammar.
- Generate migration evidence and scaffolding, never meaning -> Plate does not
  own application storage, deployment ordering, rollback, or Yjs room cutover.
- Add a real public CLI package -> this is user tooling, not repo-only
  `@plate/scripts` and not runtime `platejs` bundle weight.
- Reject a public flat-plugin requirement, recursive type depth option,
  hand-written generated mirrors, automatic case/identity migration, and
  separate `insertTable`/generic-insert paths.
