## Blunt architecture verdict

Lexical is strongest as a concrete browser editor and regression corpus. Its
core architecture is not a better substrate for Plite:

- Lexical binds document representation, schema, mutation, serialization, and
  DOM rendering to node classes and ambient synchronous editor context
  (`../lexical/packages/lexical/src/LexicalNode.ts:408`,
  `../lexical/packages/lexical/src/LexicalUpdates.ts:101`).
- Plite's plain JSON values, compiled schema, canonical `DocumentChange`,
  immutable `TransactionSpec`, extensible selections, multi-root model,
  transactional extension publication, and host-owned DOM/React layers are
  stronger current owners.
- Lexical's one materially stronger architecture detail is typed extension
  dependency output. Plite's lifecycle is better, but its dependency edges and
  multi-provider capabilities still use strings plus caller-supplied generics
  (`packages/plite/src/interfaces/editor.ts:2119`,
  `packages/plite/src/interfaces/editor.ts:1969`).
- Lexical's directional caret is a credible performance lead, not an accepted
  change. Plite already has snapshot indexes, anchors, paths, and generator
  queries. No current benchmark proves another public position abstraction
  pays for itself.

## Material candidate: typed extension dependency graph

This is the only Lexical-origin architecture change that currently clears the
material-value gate. It closes a real type/ownership hole while preserving
Plite's superior transactional publication.

### Why it clears the gate

Current Plite uses string names for required and peer edges:

```ts
import { createEditor, defineEditorExtension } from "@platejs/plite";

const HostExtension = defineEditorExtension({
  api: {
    host: {
      read(): string {
        return "host";
      },
    },
  },
  name: "host",
});

const ConsumerExtension = defineEditorExtension({
  dependencies: ["host"],
  name: "consumer",
  peerDependencies: ["optional-dom"],
  api(_editor, context) {
    const hosts = context.capabilities<{
      read(): string;
    }>("host");

    return {
      consumer: {
        read: () => hosts[0]?.read(),
      },
    };
  },
});

const editor = createEditor({
  extensions: [HostExtension, ConsumerExtension],
});
```

Problems proven by the live type/source shape:

- `'host'`, `'optional-dom'`, and the capability `'host'` are unrelated
  strings; TypeScript cannot reject a typo or infer the output.
- `capabilities<T>(name)` makes the consumer assert `T`; provider and consumer
  can silently disagree.
- `peerDependencies` are not optional in Plite. Missing peers throw before
  publication (`packages/plite/test/extension-methods-contract.ts:470`).
- Plate already uses plugin descriptor references for dependency inference, so
  string edges are substrate functionality hidden by product glue.

Lexical proves a better typing direction:

```ts
import { defineExtension } from "lexical";
import {
  buildEditorFromExtensions,
  declarePeerDependency,
} from "@lexical/extension";

const HostExtension = defineExtension({
  build() {
    return {
      read(): string {
        return "host";
      },
    };
  },
  name: "host",
});

const OptionalDOMExtension = defineExtension({
  build() {
    return { focus(): void {} };
  },
  name: "optional-dom",
});

const ConsumerExtension = defineExtension({
  build(_editor, _config, state) {
    const host = state.getDependency(HostExtension).output;
    const dom = state.getPeer<typeof OptionalDOMExtension>(
      OptionalDOMExtension.name
    )?.output;

    return {
      focus: () => dom?.focus(),
      read: () => host.read(),
    };
  },
  dependencies: [HostExtension],
  name: "consumer",
  peerDependencies: [declarePeerDependency(OptionalDOMExtension)],
});

const editor = buildEditorFromExtensions(ConsumerExtension);
```

Do not copy Lexical's mutable config or builder lifecycle. The proposed Plite
direction is descriptor-owned edges and typed outputs on top of the current
candidate publication:

```ts
import { createEditor, defineEditorExtension } from "@platejs/plite";

const HostExtension = defineEditorExtension({
  api: {
    read(): string {
      return "host";
    },
  },
  name: "host",
});

const OptionalDOMExtension = defineEditorExtension({
  api: {
    focus(): void {},
  },
  name: "optional-dom",
});

const ConsumerExtension = defineEditorExtension({
  api(_editor, context) {
    const host = context.use(HostExtension);
    const dom = context.optional(OptionalDOMExtension);

    return {
      readAndFocus() {
        dom?.focus();
        return host.read();
      },
    };
  },
  dependencies: [HostExtension],
  name: "consumer",
  optionalDependencies: [OptionalDOMExtension],
});

const editor = createEditor({
  // Required descriptors enter the compiled graph once. Optional descriptors
  // never auto-install.
  extensions: [ConsumerExtension],
});

editor.api.consumer.readAndFocus();
```

The exact terminal names (`use`, `optional`, `optionalDependencies`) need
`best-api`; the architecture law does not:

1. required and optional edges use descriptor identity, not caller strings;
2. required dependency output is inferred from the descriptor;
3. optional output is inferred as `T | undefined`;
4. required dependencies have explicit install/ownership semantics;
5. optional dependencies never auto-install;
6. all output resolution happens against one immutable candidate;
7. no candidate output is visible before atomic publication;
8. reconfiguration, schema validation, field staging, activation, rollback,
   cleanup, and ready callbacks remain Plite-owned.

### Proposed internal shape

Current:

```ts
type EditorExtension = {
  dependencies?: readonly string[];
  peerDependencies?: readonly string[];
  api?: EditorExtensionApiFactory | EditorExtensionApiMap;
};

type EditorExtensionRegistry = {
  capabilities: Map<string, unknown[]>;
  extensions: Map<string, RegisteredEditorExtension>;
};
```

Target:

```ts
type AnyEditorExtension = EditorExtension<any, any, any>;

type EditorDependencyEdge = Readonly<{
  extension: AnyEditorExtension;
  kind: "optional" | "required";
}>;

type CompiledEditorExtension = Readonly<{
  descriptor: AnyEditorExtension;
  edges: readonly EditorDependencyEdge[];
  name: string;
  order: number;
  output: Readonly<Record<string, unknown>>;
  owners: ReadonlySet<AnyEditorExtension>;
}>;

type EditorExtensionRegistry = Readonly<{
  byDescriptor: ReadonlyMap<AnyEditorExtension, CompiledEditorExtension>;
  byName: ReadonlyMap<string, CompiledEditorExtension>;
  // Multi-provider aggregation remains a typed facet/capability descriptor,
  // not a caller-generic string.
  revision: number;
}>;
```

Use descriptor identity only for runtime-installed extension configuration;
document/history/Yjs serialization remains stable JSON and never depends on
live object identity.
