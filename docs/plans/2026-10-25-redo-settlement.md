# Redo a settling decision by taking settlement back

Status: executed
Playbook: plan

This iteration replaces how a redo of a settling commit decides its shown values, which [Settle shown values at the cost of what a commit changed](2026-10-25-settle-readiness.md) left to the put-back that [Settle shown block ids wherever their last suggestion is decided](2026-10-24-shown-settlement.md) built. Every round of that iteration's diff panel found the put-back storing a wrong value: round 1 a rejected format's id kept from before the replay (row 41), round 2 two elements storing one unique id (row 49), and round 3 both again, on a rejection that restores the shown value and on a rejection that restores another element's old value (rows 54 and 55). Both round fixes assumed the put-back can decide stored values in the settle stage, after admission's repairs and the uniqueness repair. A control that drops that premise, by moving the put-back ahead of the uniqueness repair, passed every earlier probe and the full plitejs suite. It then failed a case two runners named: one update that writes a shower's id directly and frees the value it shows. Writing `b` and writing `c` there settle to the same stored bytes, while a fresh editor keeps each value, so no rule that reads only the stored change can pass both. Runners on Opus, Astra and Sol designed the redo. This plan adopts the Opus design with one part of Sol's, which a prototype showed it needs. Round 1 of the plan panel moved that part into the redo step's own change. Undo builds the change redo applies from the actual undo's inverse, without what the original's settle stage wrote. So redo brings back the document from before the undo, without those writes, and decides those ids again. A peer's write to the same id survives on either stack, and redo has nothing to fall back to. Round 2 dropped a variant that also left out what the undo itself settled, because its redo matched neither the document from before the undo nor a fresh insertion. Round 1 had also left renames out of the redo, and round 3 put them back, because deciding a rename again gave a block a new id on a plain undo and redo.

## Brief

### What will change?

Redo decides settled ids again instead of copying them back. A suggestion added between undo and redo no longer makes redo store an id it holds, or one id twice. Review of your suggested Enter split caught both.

### What could go wrong?

Redo still copies back other fixes, like renamed duplicate ids. If a suggestion added after the undo holds a block's old id, redo gives it back, as plain edits would. Saved history under Plate's id plugin likely fails to load.

## Teach

A block can show an id it cannot store yet, because a pending suggestion holds that id. Once nothing pending holds it, the editor writes the id into the block. That write is settling, and it gets its own undo step.

Redo replays that step, settling included. If a peer added a pending holder between undo and redo, the replay stores an id it should not. Today a fix-up guesses which writes were settling and takes them back. Each round of review caught a wrong guess.

Now the undo step also keeps the reverse of what settling wrote. On undo, the editor builds the redo step by reversing the undo, and takes the settling back too. So redo brings back the document from before the undo, without settling, and the editor decides again. Renames that kept ids unique come back as they were. Redo skips a value it would not change, so a peer's change stays.

## Public API

`Batch`, the step type that `getHistory(editor)` returns in each stack, gets one optional field that only undo steps carry. A redo step's `change` stays what redo applies, and it now leaves out what the original commit's settle stage wrote. No call changes. The field is `unsettle`, since `HistorySettlement` already names the pending result of a history call (`docs/vision/plite.md`).

```ts before

  readonly effects: readonly EditorEffect[];

  readonly selectionBeforeRoot?: string;
}
```

```ts after
// packages/plitejs/src/history/history.ts
export interface Batch<_V extends Value = Value> {
  readonly change: DocumentChange;
  readonly effects: readonly EditorEffect[];
  readonly selectionAfter: Selection;
  readonly selectionAfterRoot?: string;
  readonly selectionBefore: Selection;
  readonly selectionBeforeRoot?: string;
  /** On an undo step whose commit settled shown values: the change from the step's base that takes back what the commit's settle stage wrote. A redo step never has it. */
  readonly unsettle?: DocumentChange;
}
```

## Main changes

- **Settlement is recorded apart.** When a commit's settle stage changes the document, core composes what the settle stage and the closing pass wrote after the uniqueness repair, and keeps it on the commit. History reads it only on the steps it saves, so core does not repeat history's rule for which commits those are. When that change writes anything but element properties, the commit keeps none and core reports a lifecycle error. That commit's redo then replays its settle writes with nothing to take them back, and the tests fail on the error. Only history reads it. A commit that does not settle pays nothing, which is every keystroke the quiet gate passes.
- **Undo builds a redo without settlement.** Such an undo step keeps the inverse of that change as `unsettle`. When the undo completes, history composes the actual undo's inverse with `unsettle`. Core's change module turns each element property the result writes into one write from the undone document, drops a write that ends where that document has it, and writes a set-valued property as the members it adds and removes. That is the redo step's `change`. It brings back the document from before the undo, without what the original's settle stage wrote. The older redo steps take `unsettle` as a mapping, so each still starts where the one above it ends. Any undo or redo whose step comes out empty, with no effects, pushes no step on the other stack. The copy that builds the redo step from the undo step (`history-plugin.ts:694-698`) drops `unsettle`, so a redo step never carries it.
- **Redo replays without settlement.** Redo applies the step's `change` in one historic update, as today, so the document it hands to admission is the one the original commit had before it settled, with skipped edits mapped in. The settle stage then decides those values as it does for a fresh commit. The first pass's repairs, the uniqueness repair's renames and what the recorder recorded replay as stored, as on `next`, and the uniqueness repair checks every replayed id again. The redo records `unsettle` from its own commit when it settles.
- **The put-back is gone.** Nothing in the settle stage reads history any more, so the settle hook's commit loses its `historic` and `recorded` fields, and the four put-back helpers and `settledOver` are deleted.
- **The field moves with its step.** `unsettle` starts at its step's base, and a skipped edit maps it beside the step's change with the skipped edit's priority, so a key a later edit wrote drops out of it. The step's change keeps the replay's priority, so undo restores what it restores today. The correction that completes an undo against the document it reached (`history-state.ts:1118`) writes a set-valued property as the members it adds and removes. `settlePendingHistoryReplay`, which copies a step with a new change, drops `unsettle`.

## Three realistic failures

- **The inverse drifts from its step.** A skipped edit to the shower's own id maps the replay and the inverse apart, so redo writes the old id over the peer's, or takes back the peer's id while the step waits on the undo stack. The prototype without one write per property failed the first beside a pending shower, and the round 1 prototype fails the second (`b-k1-after3-a1.log`). Guarded by a same-key skipped write while the step sits on each stack, compared with its reference.
- **Redo falls back to settlement.** If anything kept the settled change beside the one redo applies, a skipped edit that empties the second would bring the first back. The redo step holds only its `change`, and an emptied change drops the step. Guarded by Opus's Editing-write trace and Sol's removal trace from round 1, each compared with its reference.
- **A step keeps a stale field, loses one or starts at the wrong document.** A path that copies a step without mapping `unsettle`, a redo that settles nothing but keeps the old one, or an undo the uniqueness repair renamed would take back writes at the wrong document or none. Guarded by repeated undo and redo cycles where one redo waits and a later one settles, by a renamed undo that asserts the undo commit differs from the plain inverse, by Sol's insertion whose undo settles with an older redo step beneath it, and by the codec's refusals.

Blast radius: `Batch` is read by `history-plugin.ts`, `history-state.ts` and `history-codec.ts`, and no other package reads it (`git grep -w Batch` outside `plitejs/src/history`). The settle hook's callers are `admitTransactionDraft` and `repairLoadedDocument`. The one-write-per-property operation has one caller, history. A rollback reverts this iteration's commits, which brings back the put-back and its three open findings.

## Losing candidates' cases
