Findings:
- Current final evidence before this run: three-editor cold 10.36 s; warm
  schema-changing median 6.065 s and p95 6.231 s; 46 tests and 155 assertions.
- The hot path does two independent jobs per generation: esbuild evaluates the
  runtime definition, then TS7 materializes exact property types. Publication
  is already negligible on unchanged artifacts.
- TS7 exposes request/server timing and CPU profiling privately; use those
  before guessing at compiler micro-optimizations.
- Profiling 11 warm operations recorded 2,322 TS7 requests, 87.780 s aggregate
  server processing, and only 1.119 s transport overhead. One focused run put
  virtually all wall time in the exact root-type query plus semantic diagnostics;
  property printing was about 40-60 ms and warm snapshot updates about 7-116 ms.
- Trial 1 queried only aliases that own JSON schema properties. It improved one
  cold sample cohort from 10.90 s to 10.44 s median (4.2%, below the 10% bar),
  while warm p95 regressed from 6.237 s to 7.190 s. A later retained-state run
  remained worse. Reverted.
- Trial 2 removed the concurrent semantic diagnostic request while keeping root
  error-type guards. Cold median regressed to 12.42 s and warm p95 to 7.365 s.
  The risk/benefit was clearly bad. Reverted.
- Final unchanged production source measures 10.65 s cold median and 6.522 s
  warm p95. This matches baseline variance and proves no major retained win.

Decisions and tradeoffs:
- Define a major improvement as >=10% on cold median or warm p95. This is large
  enough to dominate ordinary local variance; smaller composable wins may be
  kept but do not reset the two-miss stop counter.
- Preserve exact materialization and all recovery tests; caches or skipped
  diagnostics that can lie about changed inputs are rejected.
