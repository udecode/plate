# One map of a preview's places for review reads and Suggesting edits

Status: superseded by `docs/plans/2026-10-19-preview-places-on-next.md`, because its rebase onto next met a second owner of the same map, and that plan builds the architect winner on next
Playbook: plan

**Pursue, with a third design. Plite maps a preview's places through the order in which the resolver lands each piece, and the command frame, the recorder, anchors, review reads and the review delta all use that one map.** Under a preview, `read.groups({ at })` and `read.changes({ at })` read `at` as a place of the stored document, so `useSuggestionGroups`, the discussion's target panel and its thread counts each turn a view key into its view index and read the stored block there, which gives a paragraph below a hidden or inserted block another block's card (`docs/plans/artifacts/2026-10-17-preview-review-places/probe/base-index-map-a1.log`). ## Brief

### What will change?

In both previews, each paragraph shows only its own cards. While checking that, the review found that typing beside a paragraph a pending merge moves edits the wrong one and can erase someone's text, so that gets fixed too.

### What could go wrong?

While a merge is pending, Plate refuses some edits beside a paragraph it moves, such as Enter inside the merged line, in Editing too; today they save the wrong result. Preview card reads take only a paragraph's key or path.

## Teach

A preview shows the document with every suggestion accepted, or every one rejected, which can hide or merge paragraphs. While a merge is pending, a paragraph split off the merged line, or inserted between its halves, shows after the merged line.

Cards, typing in Suggesting mode and badges need to know which saved text sits at a spot in the preview. Today they share a map that keeps saved order. On a moved paragraph it lands on the neighbour, so the sidebar shows the wrong card and a keystroke can be saved as deleting another author's paragraph. One person gets there alone by inserting a paragraph above a line a pending merge pulls up.

Now the code that builds the preview also reports where it moved each paragraph. The map uses those moves, so every letter in the preview points back to its own saved letter. Cards, typing and badges share that map, so they agree with what you see.

## Hard cuts and app migration

- `at` on a preview view takes a block key or a path, and names a block of the preview. A key resolves only in the view. A point or a range throws `AuthoredPlaceError`, exported from `plitejs/authored`, on a preview, because no product code reads one there; on an intent view both keep today's meaning. The owner editor reads its own preview the same way, and no option reads stored places from a preview. An app that read a preview with a stored place, such as a record's `ranges`, reads through an intent view instead.
- In this repository, six places pass a place to a preview read or anchor on one, and a seventh selects a stored range on the editor it was opened from. `useSuggestionGroups`, `useSuggestionChanges`, the discussion's `targetGroups` and `blockThreadCount` already hold a view place, so they only drop their index mapping, and `useSuggestionChanges` passes its path instead of a range it builds from the view's text. A path read shows a block's own changes, so on any view a nested paragraph's `useSuggestionChanges` no longer returns its container's pending wrap or unwrap, as `useSuggestionGroups` already does; the container's own hook still returns it. `useSuggestionGroups(blockKey)` reads the cards of the block with that key, so a nested key no longer reads its top-level block's cards; this repository mounts badges only on top-level blocks. The docx export maps comments onto a preview through its own diff (`projectAuthoredRange` in `authored/format.ts`) and is not changed here, and so does the comment toolbar, which selects a change's stored `ranges[0]` and can select a neighbour under a preview (Open work). The discussion popover turns a suggestion's stored `ranges[0]` into a view block and a DOM range; under a preview it now anchors, on both the suggestion and the change route, on the block whose trigger was pressed last, by key, and positions by that block's element instead of a stored range, so a thread opened from a list can sit on another paragraph (Open work). `packages/plitejs/test/react/decoration-manager-contract.test.ts` reads a view range on an Accepted preview and paints the returned stored ranges into the view, which this change makes wrong; it asserts the hidden insertion's id instead and stops painting stored ranges on a preview.
- A page cursor from a read with `at` works only on a view with the same root and preview mode. A cursor from a read without `at` keeps working on any view.
- `SuggestionDiscussionBlock` in the copied discussion loses its `blockIndex` prop, and `blockThreadCount` takes the block key. An app with a copied `discussion.tsx` re-copies it or makes the edits in the Public API pairs above.
- `AuthoredChange.revision` no longer counts where a change other than a split or join sits inside its block, so an edit earlier in the block leaves it alone. A join, split, wrap or unwrap's revision also ignores the text and the leaves inside its element, and still changes when a child block is added or removed or changes its shape, or children of different shapes swap. A split or join's revision keeps today's path inside its top-level block, so a block that lands among or leaves from the blocks ahead of it, or ahead of one of its ancestors, in that block still changes it, while reordering, replacing or retyping the blocks ahead of it keeps it, as today. A change's `ranges` can now move while its revision stays the same, so an app that caches `ranges` reads them again after each document change. A decision on a structure change no longer refuses as stale after someone types or formats text inside it, and still refuses after its child blocks change.
- In Editing and in Suggesting, on every intent view, while a join is pending, Backspace or Delete across the edge of a piece it moves, a selection that holds a moved piece without where it lands, Enter or a block inserted at that edge, and a framed edit whose saved result would show in another order under Proposed refuse as unrepresentable. On Sol's crossed deletion that is 7 of 12 Enter positions in both intents: the end of `aa`, each point of the struck `bb` and each point of the joining `cc`. At the base each of the 7 saves a result other than the Enter the frame ran, and in Suggesting 4 of them leave a live preview unlike a fresh load (`docs/plans/artifacts/2026-10-17-preview-review-places/panel/origins-d1/seat-a/probes/probe-enter-outcomes-head-a1.log`, `docs/plans/artifacts/2026-10-17-preview-review-places/panel/origins-d1/seat-a/probes/probe-enter-outcomes-base-a1.log`). Typing, Backspace and Delete at the point inside a merged line where a moved paragraph was cut out still record, and so does a format such as Bold over a selection that holds a moved piece with where it lands, as select-all does. A format over a selection that would also reach a paragraph shown between its ends refuses, as other edits there do. Select-all Delete refuses where a joined line and its follower sit in a quote; today it deletes only the first paragraph and leaves a live preview unlike a fresh load (`docs/plans/artifacts/2026-10-17-preview-review-places/build/step2/lead-d-select-all-delete-base-a1.log`). Today they record a join or deletion of the wrong paragraphs, or place a new paragraph below one it was typed above.
- Records keep their shape. `AuthoredChange.ranges` and the location fields of `details` stay places of the stored document, and their JSDoc now says so.

## Design

The design came from a third `architect` bakeoff of three runners and a blinded cross-judge, run on the second plan review's findings (`docs/plans/artifacts/2026-10-17-preview-review-places/architect-3/design.md`). Every Codex seat failed its ping on a ChatGPT login without the gpt-6 models, so all three runners and the judge ran on Opus with different directions. The judge picked the narrow frame fix as the base, 25 against 26 for "identity everywhere" and 14 for "the resolver writes the map", because the second candidate's lead comes from parts that graft onto the first, and not the other way round (`docs/plans/artifacts/2026-10-17-preview-review-places/architect-3/judge/answer.md`). Round 1 of the plan review proposed a smaller design that keeps followers in stored order and refuses Suggesting where a preview still reorders, on the premise that one editor's commands never save a reordered run. That premise is false, as the next paragraph shows, and the stored-order rule fails the resolver test that pins the pivot law (`docs/plans/artifacts/2026-10-17-preview-review-places/panel/origins-r1/r1-proto/unit-a1.log`), so the permutation stays. The round brought back cand-3's fixed association and cand-2's tracked positions. Round 2 found that the refusals let through a write at a move edge and a write whose saved result shows in another order, that the delta named only blocks that gained a change, and that waking badges on a card's summary reread every badge of a long card on each key. The Refusals, Delta path and Revision paragraphs below take its fixes. Round 3 found that the edge rule refused typing at the point inside a merged line where a moved paragraph was cut out, that every command runs in the frame, so the refusals reach Editing on an intent view, that the delta missed blocks a decided change left and the badge of a block holding a nested change, that a split's revision missed a paragraph inserted between its halves, and that a card summary still walked a card that sits in one block. The Places, Refusals, Read path, Delta path and Revision paragraphs take those fixes.
