## Brief

### What will change?

Keys and Plate's heading, quote and divider rules will act on the document you'd get after accepting everything. A prototype fixes the heading and divider cases but still mishandles other people's crossed-out text, bolding around crossed-out letters, and line joins.

### What could go wrong?

It's the biggest change to suggestions yet. Keys may slow down on huge documents, so a speed test runs first. Next to crossed-out text, the editor types your letter instead of the browser. Backspace stops stepping over crossed-out letters.

## Teach

Suggestions keep crossed-out text and pending line joins inside the document you edit. Accepting everything removes the crossed-out text and merges the joined lines.

Today each key decides on the document with its crossed-out parts still in it. Plate's rules for headings, quotes and dividers run first and see those parts. A heading's start can be mid-line once accepted, and a divider can hide behind a crossed-out line. So the key does the wrong thing, and every fix so far patched one case.

After this change, a key runs on the document as it reads with everything accepted, Plate's rules and all. The editor then writes the result back into the document you edit, as plain edits in Editing or as suggestions in Suggesting. Accepting everything then matches a plain editor, because a plain editor made the decision. Writes the browser makes by itself, like composing an accented letter, still land where they land today.

## Public API

A command definition says how its input's locations land in the accepted document, and a selection-only command says it never changes content. Built-in commands that take a location, such as `insertText` with `options.at`, add `locate`. A command whose input holds no location says `locate: false`. A command with input that says neither throws while suggestions are on. When `locate` returns null, the input's location does not exist in the accepted document, and the command does nothing. Selection commands such as `move` add `selection: true`. A plugin's transaction methods declare theirs on the method itself: `txLocate(locate, method)`, where `locate` maps the method's whole argument list, or `false`. `locateAt(index, ...keys)` places the targets of an options argument, `at` by default, and `txSelection(method)` marks a method that only moves the selection, such as the affinity plugin's caret placement. This replaces the approved wording, "in a `locate` map keyed by method name", because TypeScript cannot type such a map from the update factory's inferred return, and many Plate methods carry their location in a second argument. A node key or a node passed as a target names its node in both documents, so `place.location` returns it as given.

- `landUnitDeleteTarget` and `landRangeDelete` go once M5's caller census shows only commands reach them. `landTextWrite` and slice fitting's landing stay. They own where a physical write lands, for composition, DOM repair and a drag's destination, and the frame calls `landTextWrite` to place a stored caret.
- Typing and pasting inside crossed-out letters land after them, so the proof route's "typing splits the deletion" and "paste inside struck text splits the deletion" pins change, and Editing keeps another author's crossed-out block when a key joins across it. IME composition keeps writing at the caret.
- Backspace and Delete next to crossed-out letters remove the nearest live letter in both modes. The changed pins are `apps/www/tests/browser/authored-review.spec.ts` "Backspace and Delete remove struck text in Editing" and "Backspace steps leftward and Delete rightward over struck text in Suggesting", and `packages/plitejs/test/authored-tree-record.test.ts` "steps Backspace over struck text in Suggesting without changing it" and "steps Delete over struck text in Suggesting without changing it". Those two record tests call primitives, which keep writing the stored tree, so each gets a command twin with the new expectation and keeps its primitive form.
- A command with input that declares neither `locate`, `locate: false` nor `selection: true`, or a plugin method called with arguments that declares neither `txLocate` nor `txSelection`, throws while a command document is registered. Third-party commands and methods that take input must declare before they run with suggestions on.
- App code that edits through primitives inside its own `editor.update` callback keeps deciding on the stored document. Commands and plugin transaction methods are the editing intents that enter the frame. `createInputRules.ts` drops its `content: true`, which the frame makes redundant.

## Main changes

- `src/core/command-document.ts` (new, internal) owns the frame. The authored tree registers a provider whose `project` returns the accepted document and the change from the stored document to it, or null when nothing is pending. Each command's frame comes from a projection kept per top-level run. A run is the blocks a pending join or split binds together, with the removed blocks between them. The projection is carried from one stored document to the next. It compares the two documents' top-level blocks by identity from both ends, resolves again only the runs in the changed window, and gives the accepted index one replacement there. Removed blocks next to each other become one deletion, and a join reaches back only to the nearest block that stays. Each run's change comes from walking its tokens, joins at any depth included, and the resolver's output checks it. When the walk does not give that output, a character alignment does: each live letter keeps its place, the struck letters and every token of a removed block go, a joined block's opening goes, and between two letters the tokens match from both ends, then by longest common run. The generic diff is the last fallback. When accepting removes every top-level block, the whole document resolves instead, so the root keeps the line its completion gives. A block with no marks is read directly and never cached. The accepted document is the stored index with the projection's change applied, and every frame's runtime index, the native probe's included, is the stored index mapped through that change, so the frame's nodes keep the stored nodes' keys. M1b checked the projection against an unmemoized one.
- The frame places the stored selection before the command runs. A caret first lands where a text write lands, through `landTextWrite`, then maps through the change. A caret no surviving line can take, as in a quote whose every line is struck, maps backward into what replaces its line, so it stays in the line completion gives there. A range places its start forward and its end backward, so stored content at its edges stays out, and ends that cross collapse to the caret rule. The update's implicit target is placed the same way.
- Four entries open a frame: command evaluation (`editor.update.command`, `tx.command`, `evaluateCommand`, `evaluateCommandWithState`), a plugin transaction method called from outside a frame, such as a shortcut's, the native-equivalence probe, and the correction pass at the end of an update. The frame places a plugin method's location arguments through its `locate`, as it does a command's. The probe evaluates the command in a frame, lifts its spec without committing, and admits the browser's write only when the lifted spec inserts the same text at the physical stored caret. Frames never nest. A command flagged `selection` runs on the stored document. A command or plugin method with input that declares no placement throws.
- Transpose becomes a semantic command, so its reads, replacement text and caret come from the frame.
- Inside a frame, `state`, the spec's `tx` and captured `editor.read` calls read the accepted document. A spec built in a frame carries the stored children it was framed on. Applied in the frame, it applies there. Applied later, as paste and the native multi-range delete do, `applyTransactionSpec` reopens a frame on the same projection and lifts it, and it throws when the stored children changed since. Effects, annotations, tags and after-commit handlers the command adds move to the update. An effect's value leaves the frame through its `map`, with the mapping the recorder uses for the frame's selection. A result that holds only effects still records them.
- Recording runs at a checkpoint before each frame and once at the end of the update. Each recording after the first starts from the document, selection and draft steps the last one left, and records only the steps after them. The recorder input gains the update's identity, and the authored recorder mints one change id and one time per update. One update still makes one commit and one undo step. The correction pass runs in a frame at the end of the update, so Plate's corrections decide on the accepted document. Representation upkeep stays on the stored draft.
- The lift is the recorder's existing fold, seeded with the frame's change instead of `identity`. The seed comes from the resolver's own walk. A generic diff of the two documents can align a kept leaf as removed and inserted again, and the next edit to that leaf then records nothing. The projection is canonical, so equal neighboring text merges as it would in a plain editor. A grapheme or a transpose that crossed-out letters split then decides as plain Plate does. Five rules apply in token terms, and only to a frame's recording, so a physical write records as today:
  1. The fold never repeats what the seed removed. A delete over it records nothing, a join over a pending join adds no second join, and a split at a boundary a pending join removes marks that boundary instead of making a new block.
  2. A property change on an accepted text range reaches every stored piece the range covers.
  3. A write into schema-completed content, the root's included, first records that content as the writer's insertion.
  4. A move's landing copies the stored source span through its move link, so another author's marks on the moved text stay. Whole crossed-out nodes at either edge of the span stay where they are, because only the visible span moved.
  5. In Editing, a removal never removes another author's crossed-out content. Crossed-out text and blocks inside the removed span stay where they were, and the live letters inside another author's crossed-out block go. An element the command removes stays when it holds such content and takes that content's delete mark, so accepting their change removes it and rejecting it brings it back. A crossed-out block a merge would leave inside text moves after the merged block. When only whole crossed-out blocks lie between the joined lines, the recorder moves the second line's content before them instead. The document comes out the same, and the change is the size of that line rather than of the crossed-out blocks.
- To map a path back through a change, the key index reads the change's sections instead of inverting the change, which copied everything the change removed. Section lookups in a change are binary searches. The key map collects the nodes a change touches one section at a time, and a key map that publishes rebases an overlay past 256 assignments. On today's code, the fixes other than the backward map take a letter typed after select all then Backspace at 5,000 blocks from 30 to 34 ms down to 3.6 to 3.9 ms.
- The resolver computes the accepted projection and its change in the walk that accepting runs, so decisions, frames and paint read one join rule. A joined line keeps the first line's type and properties, as a plain merge does. The resolver judges whether the first line is empty by the deletions made before the join, so deleting its text later keeps its type. A decision maps the selection through that change.
- A step can move a caret across a removal into a stretch the next step of the same command replaces, as a block join followed by its text merge does. The caret then sits at that replacement, so a Delete that joins a line starting with crossed-out letters leaves the caret before that line's live text.
- Where the frame hides every letter of a leaf, the accepted leaf is empty, so both its edges sit at the caret. In Suggesting, a write at the far edge, such as Enter's split, takes the leaf's stored edge on the caret's side. So Enter before a line's crossed-out letters moves them to the new line with the caret, as the owner's key sequence expects.
- A mounted editor resolves a command's implicit target from the DOM caret, which is a stored position. Inside a frame it resolves against the stored selection and is placed into the frame like the selection. Before this, a letter typed with the caret inside a crossed-out block landed at that offset in the next line.
- In test builds, once a frame's recording commits, a hook on the command document, `checkRecorded`, projects the stored document with an unmemoized `projectAuthoredValue` and compares it with what the frame wrote and where it left the caret. `PLITE_LAW_CHECK=0` turns it off for the work pins that count mark reads.
