# Authored: record each step, mark each piece of text

Status: executed: closed 2026-10-10 after the decision-trail review; the formats and links iteration is next
Playbook: plan

This iteration continues `docs/plans/2026-10-08-authored-review.md`. That plan's Phase 1 build panel ended at its round cap with six critical classes open in how the review tree records and resolves structure, so its Phase 2 waits for this one.

## Brief

### What will change?

For "go poteto authored": suggestions stop losing text when you move, paste, join or split content inside quotes and lists. Every edit is tracked as it happens, and each piece of text remembers who changed it. Two things went back to how they worked before review: deciding several formatting suggestions on the same text, and rejecting an Enter pressed inside a link. A follow-up plan fixes both.

### What could go wrong?

Until then, when the same text has several pending formatting suggestions, the result can depend on which one you decide first, and rejecting an Enter inside a link leaves the link split. Big edits across blocks are still slower in Suggesting than in normal editing, and the speed check missed 5 of its 180 targets. Suggesting the deletion of a large block sends about ten times more data to collaborators than today.

## Teach

A suggestion is stored as a small tag on the text it changes. Today the editor finishes a whole edit first, then works out the tags from the before and after documents. When one edit moves a paragraph and types into it, that comparison can't tell moved text from new text, so it tags the wrong letters. A block marked deleted also lends its tag to everything inside it, so text moved out of the block loses the tag.

The new design tags each step as it happens, the way the ProseMirror suggestion libraries do. Each letter carries its own tag, so moving it keeps the tag, and the editor tracks where a moved block or passage came from. A joined paragraph merges into the nearest kept paragraph before it, wherever that paragraph now sits. If accepting one change would remove something another pending change needs, the editor asks you to decide both together.

## What other editors do

This iteration read `../prosemirror-suggest-changes` at `653fba7` and `../manuscripts-track-changes-plugin` at `62f4d19` without running them, and probed plain Plite editing in `structural/probes/steps-a1.log` and `identity-and-merge-a1.log`. A `git grep` of Lexical `dd5c41b`, Slate `945a484` and Tiptap `91c51be` for track changes and suggestion modes found no change tracking. Every editor that tracks changes records one edit operation at a time and keeps the review state on the text it covers.

| Editor | When an edit is recorded | Where a deletion's review state lives | How a paragraph join is stored |
| --- | --- | --- | --- |
| prosemirror-suggest-changes `653fba7` | Each step of the original transaction, against that step's own document, rebased through earlier steps (`withSuggestChanges.ts:99`) | A `deletion` mark on the text, or a node mark on a block | A deleted node boundary inside a `deletion` mark |
| manuscripts track-changes `62f4d19` | Each step, by a per-step tracker (`transactionProcessing.ts:35`) | A `tracked_delete` mark or a `dataTracked` node attribute | A tracked structure change on the joined nodes |
| Word (OOXML) | Each edit operation | `w:del` around each deleted run | A deleted paragraph mark on the left paragraph |
| Plain Plite editing | Each builder step: typing and a block move are one step, Enter two, a text move a deletion then an insertion, a cross-level delete five (text deletes, a lift, sibling merges) | Not applicable | Not applicable: it merges the innermost text blocks |
| This review tree today | Once per transaction, from the composed change | On the element, inherited by its descendants | A `join` mark on the right block, merged into whatever sibling is left at decision time |

## Document shape

A whole-block suggestion marks the block and every text inside it, so moved text keeps its state. Plite's loader, serializers and the Yjs binding read this shape.

```json before
{ "type": "quote", "authored": [{ "kind": "delete", "change": "c1", "author": "alice", "at": 1 }],
  "children": [{ "type": "paragraph", "children": [{ "text": "gone" }] }] }
```

```json after
{ "type": "quote", "authored": [{ "kind": "delete", "change": "c1", "author": "alice", "at": 1 }],
  "children": [{ "type": "paragraph", "authored": [{ "kind": "delete", "change": "c1", "author": "alice", "at": 1 }],
    "children": [{ "text": "gone", "authored": [{ "kind": "delete", "change": "c1", "author": "alice", "at": 1 }] }] }] }
```

## Main changes

- The builder already keeps every step it applies; it becomes the one owner of the transaction's step list. Adopting a prepared spec appends the prepared draft's own steps. A schema rebind or plugin migration keeps the steps and appends its migration change as an unrecorded step, as history and collaboration changes already are. The recorder slot moves to `core/document-recorder.ts` and folds the recorded steps through a review draft, a change draft over the review document, so each step reuses that draft's indexes. It rebases each step through a position map from the plain draft into the review draft, as `prosemirror-suggest-changes` does, maps every live anchor through that map, and the slot adopts the review draft instead of applying the recorded change again. Commands still run with plain semantics; nothing records mid-transaction.
- Wrap and unwrap name their origin, because they reach the builder as `replaceChildren`. A move needs an explicit link from its copy to its source, and three kinds exist. One is a builder move step. Another is a transfer move: transfer tags its removal and insertion steps with one move id and the source, for text ranges across blocks, for nodes and for moves between roots. The last is a node that a step removes and re-inserts as the same node object, which the builder's prepared tokens keep. Equal content alone is never a move, because typing the same letters inside struck text must not inherit the deletion. Without a link, a removal plus an insertion records as a deletion plus an insertion. Leaf splits and leaf merges apply their text boundaries to the review draft unmarked; a property change either one makes on a text, such as a split that drops a property, records as a format change of that text, never of `authored`; a leaf merge whose texts are not next to each other in the review draft is dropped. The canonical pass's corrections are not recorded: the review draft runs its own canonical pass, and the resolver repairs a container a decision leaves underfull.
- Content marks live on the text they cover. Recording a whole-block insertion or deletion marks the block and every text inside it. Text typed or inserted later inside that block carries no mark, and the block stays while anything inside it survives. Typing over a selection and toggling a mark take their replacement properties through the receiving schema's copy policy, so typed text never inherits `authored` from the text it replaces. No validator ties an element's mark to its texts, because Editing and concurrent inserts legitimately leave unmarked text inside a marked block; the recording laws check the rule instead. Content reads decide from a text's own marks, so Find, input rules and AI see live text inside a struck block. This deletes the strike push-down, the edited-children pre-pass, the removed-range filter and the resolver's mark carrying.
- A suggested move strikes the source with the mover's deletion, stacked over other deletions and over the mover's own pending insertion, which a move never withdraws, and inserts a copy built from the source as the review draft holds it, with its marks, struck text and pending joins, plus the mover's insertion, so one decision settles both halves. Backspace after a quote moves a paragraph and then merges it, so it shows as that move plus a join.
- Only text blocks carry joins and splits. Accepting a join merges its block into the nearest preceding text block that the decided set keeps, without leaving a container that set keeps. When that block keeps no content, the decision removes it and the joining block keeps its own type and properties, as Editing's merge does (`editor/should-merge-nodes-remove-prev-node.ts`). When no such block exists, the join drops and its block stays. Merging or splitting containers, such as two quotes, records as a move of their children plus the deletion or insertion of the container.
- The resolver runs in two phases. Phase one applies decided joins, splits, wraps and unwraps against the input document, left to right. Phase two removes the text a decision removes, then each container whose own mark the decision settles and that keeps nothing inside, then repairs underfull containers. A container keeps anything that survives inside it, and a container emptied without its own mark settled stays, as it does in Editing. A decision waits on four things: every pending mark of a node it removes or empties, including the shell an unwrap removes; pending content and enclosure marks of the block a join merges into; pending joins whose target it removes; and, for a decision on a container's own deletion, pending insertions and deletions inside that container. `decide` takes accepted and rejected changes in one call, so changes that wait on each other decide together, and a blocked result names the smallest set to decide with it. A result is `applied`, `unchanged`, `blocked` with that set, or `invalid` when the schema refuses the resolved document, naming the changes involved.
- Clipboard decode and external drop pass the decoded slice through the receiving schema's copy policy before any command sees it. Transfer checks its landing on the plain draft, before the recorder rewrites it, and returns a landing read from an anchor after the commit.

Cases the losing candidates handle that the base handles differently, each a graft or a limit:

1. A join whose target another decision removes: the others resolve it by construction; the base skips targets the decided set removes and makes the remaining decisions wait, and both decide together. Limit.
2. A join with a pending insertion between the joined blocks: the join waits on that insertion's decision, and the two decide together in one `decide` call. Limit.
3. Withdrawing your own insertion outside a move: the others keep it recoverable; the base removes it, confirmed on today's tree (`structural/probes/must-answer-a1.log`, case withdrawal). Limit, as a Defaults row.
4. Named roots and open slices on paste: graft; the decode-boundary policy runs on every decoded root.
5. Leaf-mark size: the others avoid it; the base pays it, measured in `structural/probes/leaf-size-a2.log`. Limit, as a Defaults row.
6. Moves: graft, explicit links held for the transaction. A relocation with no link records as a deletion plus an insertion, and a block moved while a pending join extends it carries that join; rejecting the join afterwards leaves both blocks at the new place. Limits, as Defaults rows.
7. Concurrent formats over items Yjs inserts or re-creates: text another client types inside a range being struck gets the deletion, Suggesting text typed there carries both marks, and the tail of a paragraph another client splits or drags in Editing loses the deletion. Today's element-owned marks lose text the same ways. Limit, asserted in S5.

## Failures, blast radius and rollback

Three realistic failures this change could cause:

1. A command whose step shape the per-step rules don't cover records the wrong marks. The recording laws run over real commands in both intents against a reference that replays the history, and a test records one transaction directly, through a prepared spec and across a schema rebind, and expects one result.
2. A decoder added later skips the copy boundary and lets foreign marks in. The boundary lives in the one decode function every DOM paste and drop calls, and a test pastes through each decoder.
3. Per-step recording costs too much on multi-step edits in large documents. The speed probe runs on a disposable prototype before anything else is built, against the frozen P1.13 budgets and the frozen rule in `structural/bench/rule-v2.json`.

Blast radius: the recorder slot is internal and only `authoredTreeProof` registers a recorder, so plain editing never takes the new recording path; typing over a selection drops copy-dropped properties from the typed text in every editor, which changes nothing for a schema without such properties; the builder's step list grows no new data, since it already keeps applied steps; wrap and unwrap gain an origin that existing listeners ignore; the decode boundary touches every paste and external drop in every editor, and a mark-free payload passes through unchanged; transfer's landing check moves earlier in the same transaction with the same comparison, and its returned landing maps through an identity map when no recorder runs. Rollback: revert this iteration as one unit, which leaves Phase 1's tree and the parent plan's reopened P1.14 in place.
