## Main changes

- `tooling/scripts/knowledge/` has two files. `kb.mjs` is the command line, and `knowledge.mjs` holds the private parsers, the index, the query, the gaps and the checks. Test titles come from a syntax parse of each test file (`@babel/parser`). The parse reads `it`, `test` and `describe` modifiers and conditions, `test.skip(...)` statements in a body or scope, and Playwright's `testInfo.skip(...)`, so comments, skipped groups and files that skip themselves never count as running. It does not read node:test's `{ skip }` option or `t.skip()`, and it trusts that a helper under `packages/*/test` runs because a partition test imports it. `pnpm kb <query>` resolves a rule ID, a family, a scope, an issue ref, one or more paths, a benchmark target, an editor or plain words to keys. It then follows each key's relationships, rule to tagged tests to their issue tags and back, and ranks the joined results into one bounded card. The card ends with a write-back footer naming the file where each finding belongs. It reuses the ledger's own `lookup` (with `--detail` forwarded) for the scope section and `searchResearch` for research runs.
- A test that proves a rule or guards an upstream issue says so at the end of its title, as `[EDIT-TABLE-TAB-001]` or `[slate#6034]`. The tag records the relationship only. `kb` derives for each test which check runs it (`pnpm check`, plite CI on pull requests, a manual or dispatch-only browser run, or none for `__deferred__` specs), on which browser engines, and whether it or its `describe` is skipped.
- Nothing moves. Each store keeps its path, and `kb` reads every store's current format through one adapter per format.
- `kb homes` derives a home for every file under the research roots from its path or from `docs/research/homes.tsv`. K14 fails on a research file with no home, on a `docs/research/sources/<folder>/` with no README, on a README that does not link a page homed there, on an editor README that does not link its ledger or harvest, and on a `homes.tsv` row whose path no longer exists. Its link and stale-row forms join `kb check` with phase 3's research write-back; its no-home form stays a proof each phase gate runs. K15 fails on a folded file that changed, a new file anywhere under a folded directory, a `folded.tsv` row that differs from the base commit's copy, and a row removed while its file still exists. `kb write` is how this run writes a home. It creates or rewrites a file atomically, appends to a section, replaces one exact string, or removes a unit's span when an accepted verdict allows it. It refuses a write that removes a kept unit's span, and it logs each write. The resolve, fold and quote scripts beside `kb` run the compiles, and `kb pins <home>` prints the revisions a home's pages cite.

**Compile.** Every compile in phases 2, 4 and 5 follows one rule. Each compile step names its source manifest before any reader starts, from a listing that does not depend on the readers: `git ls-files` over the step's stores, `git show --diff-filter=D` for step 2.8 and the batch script for phase 5. A batch is up to 400 KB of one manifest's sources, or one larger source read in line chunks: in phase 2, one home's slice of step 2.5's manifest or a slice of step 2.6's, 2.7's or 2.8's; in phase 4, one store's; in phase 5, one cluster. A source with several homes is compiled once, in the slice of its first home, and its units may land in any of them; the sources with no home form one slice, and their units land in the homes the second reader names. A reader reads each source file in full and splits it into units that together cover every non-blank line. An image or other binary file gets one unit of its own, a record disposition, so every source has at least one unit. Each unit is covered, citing the quoted span in its home that holds the whole fact (a rule ID alone does not count); added, written in the batch folder and landed in its home once accepted; or dropped, with its reason. Knowledge prose is compiled whether or not its file is live. The one exception is operational state. A file whose path matches the resolve script's link-only list is covered by the home's link to it instead of a copy, and the script refuses a link-only unit in any other file. The list holds a harvest's `test-index.md` and `inventory.md`, a ledger table that `build-closure-ledger.mjs` generates, ProseKit's `issue-closure-ledger.tsv`, the live decision inputs `wordgard/full/issue-decisions.mjs` and `slate/full/classify-delta.mjs`, `docs/maintainer/queue.md`, `docs/sync/shadcn/deltas.json` and the redirect map. Step 4.1 adds a path only with a decision row naming the script or workflow step that writes it. The lead runs `unslop` on each batch's added units in the batch folder before the second reader reads. A home's README lists its area pages by topic, each with a link and a short takeaway, and links `kb pins <home>`; the facts, the home's conflicts and gaps included, live in the area pages. The law file, `markdown-editing-spec.md`, never splits, per the Defaults row "Behavior law layout". A raw recall sample is five dropped units per batch, or more when a step names a larger count, drawn by the resolve script in hash order with its seed logged. After the batch lands, a reader who neither wrote nor accepted them judges it against the homes, with the run's earlier removals beside it. A miss sends that batch's accepted drops to a fresh second reader, whose restored units land before the next batch. Limit: a judge who overlooks a still-true fact is not caught. The compile's claim holds for the blobs it read; content a live source gains later reaches the homes through its writer's write-back in phase 3, or through the next sweep.

**Resolve.** One session runs the compile, a batch at a time. First readers run as parallel subagents, and a fresh second-reader subagent checks each batch against its sources and the homes as they stand after every earlier batch. It saves its verdicts as a TSV. It also sees the batch's other added units, and a unit can be covered by an accepted added sibling. It gets the obsolete, withdrawn and removed verdicts and the obsolete drops this run recorded for its target homes, and drops a unit whose fact one of them covers, citing it. A unit whose source is stronger than a removal, such as a test or a measurement against a weak source, goes to Open work for the owner instead of landing. No script checks these judgments. The resolve script builds the batch's resolved file from those verdicts. It fails when a listed source has no unit, when a non-blank source line belongs to no unit, when a unit has no accepted verdict, when a sibling cover cites a unit that is not an accepted added unit of the batch, and when a law unit's ID is a wildcard family or shared within the batch. A rejected unit is applied again in the second reader's exact words and checked again, and a drop resolves only when the second reader accepts its reason. The resolved file records each source's path and the blob it was read at.

**Land.** The lead lands a resolved batch with `kb write`. A unit for a home goes to the home's area page for its topic, `<topic>.md`, created on the topic's first unit and continued in a new numbered page each time it would pass 100 KB. A lesson lands as one `- **Title** text` bullet, the shape `kb` parses, on the existing `plate-notes` page for its topic when one fits. A law unit is a `proposed` rule with a new ID, under the `###` subsection or `##` section it names, or in a new `##` section with its Authority line after the section it names. A gap unit becomes a line under its rule ID in a `## Compiled gaps` section of `current-evidence.md`, the file AGENTS.md's Source authority names for evidence gaps, citing a tracked or folded source by its path and a step 2.8 source as `<sha>:<path>` with the parent commit's full SHA. A step 4.4 unit replaces its citing line. A fold, a reader repoint, an evidence-input removal or a test tag runs only after the batch that lands what it points at. When a session stops mid-landing, the next one compares the batch's resolved file with the homes and lands the units not yet there; the quote check at the gate catches a unit landed twice or not at all.

`kb write`, built in step 2.2, writes the homes, which are the READMEs and area pages under `docs/research/sources`, the law file and `current-evidence.md`, and the citing lines step 4.4 replaces. It has four operations: create a file atomically, append text to the end of a section, replace one exact string that occurs once, and remove a unit's quoted span. A section's heading must occur once, and the section ends at the next heading of the same or higher level outside any fence, found by the knowledge module's parser. Each operation is refused when it lowers the count of a kept unit's quoted span in the file, unless that unit's accepted verdict calls for the change: an obsolescence or withdrawal verdict for a removal, or a move verdict whose new span the operation writes or already stands in a home. A withdrawal is a drop reason applied after landing, and the second reader holds it to a drop's standard. So a rewrite of a line a span crosses, a removal of text another unit also cites and a move whose new span is missing are refused. It logs each write with its kind, step, batch, session, unit key and file. A new file is marked intent-to-add with `git add -N` when it is created, so `git ls-files` and K7 see it before the Stop hook stages it. Related edits, such as an area page and its README link, a fixed citation and its K7 baseline removal, or a fold's pointer line and its `folded.tsv` row, land in the same turn, and the checks run at the gates. Generators and formatter passes run as the project's rules say, `pnpm run prepare` after a rule edit and `pnpm lint:fix` on the task's code paths.

Before each phase gate and before the close, the quote script reports every resolved unit by its disposition. A kept or moved unit has its quoted span in its home or target, the new home for a move. An obsolete or withdrawn unit has the verdict the second reader accepted and `kb write` applied. A dropped unit has its accepted reason, and a unit sent to the owner has its Open work item. Any other unit is lost. The second reader resolves it again against the current homes and the change that removed its span, which is its commit or, while uncommitted, the file's diff against `HEAD`. It resolves as covered at a new span that stands in a home; obsolete, with the commit or code that made it false; or removed, with that change's reason, such as a weak source. A change that claims a move or a duplicate resolves only through the span it points to. A lost unit whose fact appears nowhere else and whose removal shows no reason gets the second reader's accepted verdict saying so and becomes an Open work item for the owner. The second reader keeps a removed fact out, as the resolve rule says, and no script checks that judgment. A recall sample checks a verdict-cited drop against its verdict, not against its home. No gate waits on the owner. The quote check fails on a lost unit that has neither a new resolution nor that accepted verdict.

Compiling and folding are separate. The run compiles every source in a phase's population, and folds a file only when it is historical. A file is live when a workflow, script or build writes it, or uses it as an operational input that changes what the code or a workflow produces. A reader that only checks, indexes or cites a file, such as `kb`, K7, the citation baseline, the review ledger's scope members, the generated `.agents/skills` mirrors or a URL route, does not make it live. Before folding a file that a review scope lists as a member or evidence input, the step moves that entry to the file's home. A workflow step that reads a file to learn from it is pointed at the file's home in the same turn as the fold. A live file stays live: compiled, linked from its home and not folded. A folded Markdown file gains a pointer line naming its homes, after any YAML frontmatter; other files get none. `docs/research/folded.tsv` lists each folded file with its folded blob, and a row ending in `/` folds a directory. The fold script refuses a blob that is not the pointer line plus the resolved blob, so a file that changed between the read and the fold is compiled again first. K15 fails when a folded file changes, when a new file appears anywhere under a folded directory, when a `folded.tsv` row differs from the base commit's copy, and when a row is removed while its file still exists. Retiring a folded file removes the file, its row and its K7 baseline entries in one turn. A folded file keeps its K7 baseline entries, and its units carry any recoverable conclusion into the home.
