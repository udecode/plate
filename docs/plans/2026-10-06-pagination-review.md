# Pagination: render paged Plate editors through EditorContent

Status: executed: built, reviewed in seven diff rounds and verified; waiting on your commit
Playbook: plan

Pursue, reaffirming `2026-10-04-pagination-audit`. A Plate app still cannot paginate with its plugins. `platejs/pagination/react` is `export * from 'plitejs/pagination/react'`, so the only paged component a Plate app can import is the raw Plite `PagedEditable`, which receives none of `EditorContent`'s piped renderers, DOM handlers, shortcuts, slots, content attributes or `PlateRoot` view binding. The public guide teaches exactly that, inside a `Plate` component that `platejs/react` does not export. The target stands. Plate gets one paged content component in `platejs/pagination/react`, built as `EditorContent` with Plite's `PagedEditable` as its editable, and the Plate facade drops the raw `PagedEditable`. `next` returned `pagination`; the ledger marked the audit stale because 14 member files changed after it read `fe0e9599a6`, and none of those changes touches the gap.

The plan builds it in three phases under the Build playbook, `.agents/playbooks/build.md`. Phase 1 replaces `EditorContent`'s inherited editable override with one private content view that takes its editable as a typed render function, built instead as an editable component plus its props (step 1.2's deviation). That also fixes a defect in shipped code. A plain editor nested in a slot of `VirtualizedEditorContent` renders virtualized today (probe in Evidence); no current route nests one, by a `git grep` of `VirtualizedEditorContent` consumers in `apps/www`. Phase 2 repairs Plite's paged view. Even without Plate, it replaces its editable host when measurement recovers, keeps blocks at an old snapshot's positions after a failed measurement, places elements on the wrong box when a wrapper surrounds them, hardcodes a text color and depends on CSS that only the Plite example ships. Phase 3 adds `PagedEditorContent`, cuts the raw component from Plate, and adopts the entrypoint graph, packed checks, docs and a browser-proved demo. The design came from a three-runner `architect` arena with an Opus cross-judge; Evidence holds the synthesis and six probes run at `HEAD`.

## Brief

### What will change?

Plate gets one paged editor component that shows plugin features on pages. First, a nested editor stops copying its parent's display mode, and the page view stops replacing itself or keeping old positions after an error.

### What could go wrong?

The app supplies page sizes and line heights for nested blocks; a block type it misses turns pages off. A table taller than a page overlaps the next page, and element padding does not move text.

## Public API

A Plate app paginates today through the raw Plite editable, inside a component the package does not export.

```tsx before
// content/docs/(guides)/pagination.mdx
import { createPretextPageLayoutEngine } from 'platejs/pagination';
import {
  PagedEditable,
  usePageLayout,
} from 'platejs/pagination/react';
import { Plate, useCreateEditor } from 'platejs/react';

<Plate editor={editor}>
  <output>{layout?.pages.length ?? 0} pages</output>
  <PagedEditable
    ref={editableRef}
    engine={engine}
    page={{ margins: 72, preset: 'letter' }}
    pageView={{ gap: 24, mode: 'single' }}
    renderPage={renderPage}
  />
</Plate>
```

```tsx after
// content/docs/(guides)/pagination.mdx
import { createPretextPageLayoutEngine } from 'platejs/pagination';
import {
  PagedEditorContent,
  usePageLayout,
} from 'platejs/pagination/react';
import { EditorRoot, useCreateEditor } from 'platejs/react';

<EditorRoot editor={editor}>
  <output>{layout?.pages.length ?? 0} pages</output>
  <PagedEditorContent
    ref={editableRef}
    engine={engine}
    page={{ margins: 72, preset: 'letter' }}
    pageView={{ gap: 24, mode: 'single' }}
    renderPage={renderPage}
  />
</EditorRoot>
```

## What other editors do

The comparison in `docs/plans/topics/pagination.md` stands, and this plan read no new editor source, because the decision turns on Plate's own content composition and Plite's placement contract, not on how another editor paginates. ProseMirror, Lexical, Slate and Tiptap's open-source core ship no paged editable; Tiptap Pages positions blocks with CSS floats and needs its own table kit, which the subject records as a failure taxonomy rather than a design to copy.

## Main changes

- `EditorContent`'s body moves into a private `EditorContentView` that renders its one editable as JSX with the forwarded ref. `EditorContent` passes `Editable`, `VirtualizedEditorContent` passes `VirtualizedEditable` with its window props, and `PagedEditorContent` passes `PagedEditable` with its page props, so no React context selects an editable and no untyped props bag overrides Plate's computed props.
- Plite's `PagedEditable` renders one tree in its flow and paged states, its layouts provider is always present, it never reuses a previous snapshot after a failed measurement, and a placement that disappears is cleared. Measurement recovery, a lagging version or a failed measurement never replaces the host or leaves blocks at old positions.
- Plite places each element's outermost box that holds only that element through a `data-editor-placed` attribute and four registered CSS variables, which one rule applies over the box's own styles, so a renderer keeps owning its inline styles. Each call to the placement ref clears the box the previous call placed, and React and every ref merge that forwards it deliver a detach as a call with null, so a detach or a layout change clears the box in its commit. The placement ref changes with its node binding, as the base's element ref did, so an edit rebinds the element before the renderer's own layout effects and re-places the edited block in the same commit. Each projected run is positioned against its real containing box in that box's own CSS pixels, so a scale transform on the page view does not move it; each box and containing box is measured once per read (by code reading; the read-count probe shows the per-text-node reads gone, not the per-box bound).
- Each measured run renders as one positioned container outside the leaf and outside decoration segments, with no fixed color; the break marker sits only at a line's last source boundary, and the paged component renders its own break rule.
- Publication converges: a component that passes inline `fragmentation` or `typography` and reads `usePageLayout` settles, and a later document change still publishes.
- Placement moves out of `editable-text-blocks.tsx` into its own module, `editable-element-placement.tsx`, the run-container grouping lives in `editable-text-containers.tsx`, one `useHydrated` hook replaces four copies of the hydration flag, and one `getElementTransformScale` in `editable.tsx` replaces the drop cursor's two copies of the scale math. The run projection stays in `pagination/react.tsx`, which grows from 1214 to 1399 lines, and `editable-text.tsx` goes from 991 to 999 (`wc -l` against `git show HEAD`).

### Requirements

- Plate applications import `platejs`, never `plitejs`, and Plate source imports `plitejs` only in exact facade, proxy or replacement leaves (`VISION.md` Boundary Law).
- `EditorContent` is Plate's content primitive (`docs/vision/plate.md:33-36`), so a mounted Plate editable renders through its plugin pipeline.
- Pagination is view-owned derived geometry. The mounted paged component owns measurement, page surfaces, omission and scroll stability; `measurePages` is the separate one-shot headless job (`docs/vision/plite.md:235-238`, `:740-747`).
- Plate adds no pagination plugin, kit, store or second runtime (`docs/research/decisions/pagination-ownership.md`, Design lanes).
- An optional peer stays behind its explicit subpath (`docs/vision/common.md` Boundary Law), so `@chenglou/pretext` must not become reachable from `platejs/react`.
- Fragmentation is text, one atomic owner or all direct element children, and a top-level block that is not one inline flow needs a plan or measurement throws (`packages/plitejs/src/pagination/index.ts:414-508`).
- Explicit omission (`virtualize`) and the exact-host `usePageLayout` read keep working.

### Lanes

- Keep the identity facade and fix only the guide's import: loses. The guide would compile, and a paged Plate editor would still render no plugin components, handlers, shortcuts or slots.
- Delete `platejs/pagination` and `platejs/pagination/react`, the strongest deletion: loses. Pagination is a job Vision names, and the Boundary Law forbids a Plate app from importing `plitejs`, so Plate apps would lose it entirely.
- A paged `EditorContent` in `platejs/pagination/react` over one private content view: wins. It adds no runtime and keeps Pretext behind the pagination subpath. The entrypoint graph gains edges from `pagination/react` to `react-core` and `pagination`, and `pagination/react` leaves the `proxies` partition, because `react-core` depends on `dom` and `history`, which sit in `proxies` (`tooling/entrypoints/entrypoint-dag.mjs:402-409`, `:479-487`).
- The same component in `platejs/react`: loses. `react-core` would gain `plitejs/pagination/react` as an external, so a plain `import 'platejs/react'` statically reaches the Pretext chunk.
- A new `platejs/react/paged` file entrypoint: loses. It creates a second public pagination React home beside `platejs/pagination/react`.
- A public `EditorContent` prop that takes the editable, or a public hook that returns the piped renderers: loses. The prop breaks per-variant inference, and the hook leaks pipeline assembly into app code.
- Moving Plate's render pipeline into Plite: loses. Plite stays free of Plate product rendering policy.
