Decision brief:
- outcome: Replace Plate's implicit property inference and Plite's thin
  property registries with one explicit, compiled, JSON-native schema model.
- chosen shape: Plain `Element`/`Text` values; shared value descriptors;
  distinct text-property and element-property declarations; structural target
  queries; compiled grammar/property/lifecycle/codec indexes; atomic schema
  configuration and migration.
- strongest rejected alternative: Import Wordgard's `Node`/`Plot`/`Leaf`/`Mark`
  classes, single `param`, sorted `Mark.Set`, DOM shapes, and class-identity
  configuration. Those mechanisms buy local schema neatness by throwing away
  Plite's better JSON, multi-root, collaboration, history, and extension model.
- consequence: This is a real hard cut. Plate plugins migrate from
  free-floating node/schema flags plus `elementProperties`/`textProperty` to
  top-level `type`, `schema.element`, `schema.mark`, and explicit property
  contributions; every
  property becomes registered and targetable; the old global merge, matcher
  ambiguity, and correction-as-schema-cleanup paths disappear in the same
  execution.
- identity DX: ordinary Plate editors omit identity and receive the exact
  deterministic semantic fingerprint. Explicit `id/version` is optional
  durable lineage for persistence, collaboration, and migrations across
  fingerprint changes. Plite compilation, not each caller, owns the one
  complete identity descriptor.

## Blunt current-state finding

Plite already has the better document engine. Its plain JSON model, strict JSON
codec, multi-root grammar, fitted slices, canonical `DocumentChange`,
transactional extension configuration, History validation, and Yjs bridge are
stronger foundations than Wordgard's class graph.

Its schema declaration layer is weaker. The compiler is still a set of maps
plus runtime lookups, property ownership is split between nested element specs
and a separate text registry, and legacy Plate made the problem worse by
globally copying every non-element plugin's `node.elementProperties` onto every
element
type. Indent is the clean proof of the bug: schema compilation permits
`indent` everywhere, then a semantic correction deletes it from nodes the
feature did not mean to target
(`packages/core/src/lib/editor/withPlite.ts:327-452`;
`packages/indent/src/lib/BaseIndentPlugin.ts:54-73,161-197`).

Wordgard gets property targeting, semantic groups, defaults, wrapping, and
mark lifecycle metadata more coherently into its schema. The architecture to
build is not Wordgard transplanted into Plite. It is Wordgard's explicit
semantics compiled onto Plite's JSON/change/runtime model.

## Verdict vocabulary

- `keep`: retain the Plite mechanism; it is the better foundation.
- `steal`: take the Wordgard semantic essentially as-is.
- `rearchitect`: take the useful idea but express and compile it through
  Plite-native JSON descriptors and transactions.
- `hard-cut`: delete the named current Plite/Plate mechanism as the target
  lands.
- `reject`: do not adopt the Wordgard mechanism.

## Final public API

These target signatures define the hard-cut public shape. They are not
compatibility designs or placeholders for a second API.

### Shared value semantics, distinct placement

```ts
import {
  defineEditorSchema,
  definePropertyPolicy,
  element,
  property,
  schema,
  target,
} from '@platejs/plite';

type CommentRef = {
  id: string;
  resolved: boolean;
};

const ColorValue = definePropertyPolicy<string>({
  id: 'color-value',
  validate: isColorValue,
  version: 1,
});

const CommentValue = definePropertyPolicy<CommentRef>({
  id: 'comment-value',
  validate: isCommentRef,
  version: 1,
});

const Bold = schema.textProperty(
  'bold',
  property.boolean(),
  {
    target: target.group('textBlock'),
    inclusive: true,
    split: 'preserve',
    typeChange: 'preserve-if-allowed',
  }
);

const Color = schema.textProperty(
  'color',
  property.string({ policy: ColorValue }),
  {
    target: target.group('textBlock'),
    split: 'preserve',
    typeChange: 'preserve-if-allowed',
  }
);

const Comments = schema.textProperty(
  'comments',
  property.set(property.json<CommentRef>({ policy: CommentValue })),
  {
    target: target.group('commentable'),
    split: 'preserve',
    typeChange: 'preserve-if-allowed',
  }
);
```

`property.*` describes only JSON value laws: kind, validation, canonicalization,
default/omission, structural equality, and a built-in merge algebra. Custom
validation is carried by a frozen `definePropertyPolicy({ id, version,
validate })`; schema fingerprints include only the policy ID/version. Inline
closures, default factories, and arbitrary equality/key callbacks are rejected
because they make schema identity unstable or mutable behind an unchanged
revision.
`schema.textProperty` and `schema.elementProperty` describe placement and
editing laws. They are deliberately distinct:

- text properties need inclusivity, insertion inheritance, text split/range
  behavior, and text-leaf canonicalization;
- element properties need actual parent/root context, element split/wrap/type
  change behavior, and element construction defaults;
- both share target queries, validation, equality, persistence IDs, and
  collaboration-safe merge strategies.

const Image = element({

The compiler expands `properties` into element-property registrations targeted
to exactly `image`. This is sugar for ownership, not global merging.

### Cross-cutting and targeted properties

```ts
const Indent = schema.elementProperty(
  'indent',
  property.number({ policy: PositiveInteger }),
  {
    target: target.and(
      target.group('indentable'),
      target.root()
    ),
    split: 'preserve',
    typeChange: 'preserve-if-allowed',
  }
);

const CellMetadata = schema.elementProperty(
  'cellMetadata',
  property.json<CellMetadataValue>({ policy: CellMetadataValuePolicy }),
  {
    target: target.and(
      target.group('tableCell'),
      target.parent(target.type('tableRow'))
    ),
    split: 'drop',
    typeChange: 'drop',
  }
);

const SuggestionMetadata = schema.elementProperty(
  schema.key.prefix('suggestion_'),
  property.json<SuggestionData>({ policy: SuggestionDataPolicy }),
  {
    target: target.group('suggestible'),
  }

```

Targets are a frozen, serializable AST, not arbitrary callbacks. The compiler
supports `type`, transitive `group`, `root`, actual `parent`, `and`, `or`, and
`not`. Key patterns are exact or registered, non-overlapping namespaces. Two
selectors that can claim the same key fail schema compilation. Declared-content
targets stay deferred until a concrete consumer proves the need.

The schema contribution callback runs while Plate builds the immutable

The hard answer to the suspicious APIs:

- `isLeaf: true` semantically implies a boolean text property. Because this is
  a hard cut, the final API deletes `isLeaf` and declares
  `schema.mark: property.boolean(...)`.
- `textProperty` and `elementProperty` should share `property.*` value
  factories. They must remain distinct property registrations.
- Indent is not a node and must not pretend to be one. It contributes an
  element property with explicit targets.
- Global element-property merging is plainly too permissive and is deleted.
- Plate's `mark` is declaration vocabulary only. No `Mark` class, mark array,
  or non-JSON value enters Plite documents.

### Custom schema and atomic reconfiguration

```ts
const articleSchemaDefinition = {
  unknown: 'reject',
  groups: {
    commentable: {},
    indentable: { extends: ['block'] },
  },
  elements: {
    image: Image,
    paragraph: {
      groups: ['commentable', 'indentable'],
      content: schema.content.text({ default: 'text', min: 1 }),
    },
  },
  properties: [Bold, Color, Comments, Indent],
  root: {
    content: schema.content.group('block', { min: 1 }),
  },
} as const;

const ArticleSchema = defineEditorSchema(articleSchemaDefinition);

const PersistedArticleSchema = defineEditorSchema({
  ...articleSchemaDefinition,
  id: 'article',
  version: 1,
});

const articleSchemaSlot = defineExtensionSlot('article-schema');

const editor = createEditor({
  extensions: [articleSchemaSlot.of(ArticleSchema)],
});

editor.update.extensions.reconfigure(articleSchemaSlot, ArticleSchemaV2, {
  migrate: ({ document }) => ({
    ...document,
    children: document.children.map((node) =>
      'type' in node && node.type === 'paragraph'
        ? { ...node, type: 'body' }
        : node
    ),
  }),
});
```

Without `migrate`, reconfiguration succeeds only when the current document is
valid under the candidate schema. With `migrate`, Plite stages the candidate,
builds a canonical `DocumentChange`, validates the result and change laws, then
publishes the configuration and document in one commit. Setup/cleanup remains
post-publication extension lifecycle work; it cannot observe a half-published
schema.

`defineEditorSchema` infers:

- the valid element `type` union;
- element property keys and values by type;
- text property keys and values;
- roots/groups/property IDs;
- the editor's default `Value` where no explicit wider value is supplied.

`ArticleSchema` uses its exact semantic fingerprint as identity.
`PersistedArticleSchema` adds optional durable lineage for data that must span
compatible schema evolution. Supplying only `id` or only `version` is invalid;
the compiler completes exactly one identity in either mode. The identity is
discriminated as `{ kind: 'derived', fingerprint }` or
`{ kind: 'named', id, version, fingerprint }`. Lineage is excluded from the
fingerprint, so naming the same semantics cannot alter semantic compatibility.

Open JSON editors remain possible through
`defineEditorSchema({ unknown: 'preserve', ... })`. Closed schemas never infer
openness from the presence or absence of roots.

The primary root is always implicit: `target.root()` addresses it and the
singular `root` declaration configures it. `target.root(name)` and `roots`
exist only for additional named roots. Public declarations, diagnostics, and
examples never expose the runtime's internal primary-root sentinel.

## Compiled internal representation

```ts
interface CompiledEditorSchema {
  readonly fingerprint: string;
  readonly identity:
    | Readonly<{ fingerprint: string; kind: 'derived' }>
    | Readonly<{
        fingerprint: string;
        id: string;
        kind: 'named';
        version: number;
      }>;
  readonly revision: number;
  readonly unknown: 'reject' | 'preserve';

  readonly elements: {
    readonly byType: ReadonlyMap<string, CompiledElement>;
    readonly groups: ReadonlyMap<string, ReadonlySet<string>>;
    readonly allowedChildren: ReadonlyMap<string, ReadonlySet<string>>;
    readonly allowedParents: ReadonlyMap<string, ReadonlySet<string>>;
    readonly contentPrograms: ReadonlyMap<string, CompiledContentProgram>;
    readonly defaultPlans: ReadonlyMap<string, ConstructionPlan>;
    readonly wrapperPlans: ReadonlyMap<string, readonly WrapperPlan[]>;
  };

  readonly properties: {
    readonly byId: ReadonlyMap<string, CompiledProperty>;
    readonly exactKeys: ReadonlyMap<string, CompiledProperty>;
    readonly keyPrefixes: readonly CompiledKeyPrefix[];
    readonly elementAllowedByType: ReadonlyMap<string, ReadonlySet<string>>;
    readonly textAllowedByParentType: ReadonlyMap<string, ReadonlySet<string>>;
    readonly lifecycle: ReadonlyMap<string, CompiledPropertyLifecycle>;
    readonly mergeStrategies: ReadonlyMap<string, CompiledMergeStrategy>;
  };

  readonly roots: ReadonlyMap<string, CompiledRoot>;
  readonly vocabulary: CompiledSchemaVocabulary;
  readonly diagnostics: readonly SchemaDiagnostic[];
}
```

Compilation is pure and revision-owned:

1. Canonicalize and deep-freeze contributed descriptors.
2. Resolve exact element, root, property, and prefix-key ownership.
3. Resolve hierarchical groups, including compiler-owned `all`, `element`,
   `text`, `inline`, `block`, and `textBlock` groups.
4. Prove type/key-selector/default/codec conflicts before publication.
5. Compile content ASTs, parent/child matrices, root programs, and cardinality.
6. Prove every required content branch has a terminating construction plan.
7. Compile finite wrapper plans; retain a bounded revision-local cache only for
   context-sensitive fitting.
8. Compile property target sets plus contextual parent/root predicates.
9. Compile default, validation, equality, split, type-change, inclusion,
   canonicalization, and change-lowering strategies.
10. Publish one immutable artifact and stable vocabulary to Plite, host codecs,
    History, Yjs, and Plate adapters.

Properties are stored once. Element specs contain property IDs, not copied
descriptors. Hot type/group/property queries use immutable maps/sets and
revision-local memoization; denser representations are justified only by
benchmarks. Actual parent/root target predicates receive a path-aware
validation context; they do not rerun schema composition. Diagnostics retain
contributor extension/plugin IDs for humans and agents. Public validation
diagnostics identify a named root or `null` for the primary root plus the exact
path/node/property context; compiler-only primary-root sentinels never cross the
API boundary.

### Performance and memory acceptance

Benchmarks use the same pinned machine/runtime, warm-up, corpus, and sample
count before and after. A noisy one-off is not evidence.

- A synthetic closed schema with 100 element types, 200 exact properties, 20
  namespaces, 30 groups, and 4 roots compiles at p95 under one 16 ms frame.
- Warm type/group/property/allowed-parent queries perform no rule traversal or
  schema composition. Record absolute latency and work counts before/after;
  retain a comparative speed claim only when the pinned baseline supports it.
- Repeated wrapper lookup performs no BFS or factory probing after the first
  revision-local result.
- Full validation and representative open-slice fitting on the existing large
  corpus keep correctness and record before/after latency; any regression must
  be explained and bounded by the recorded baseline rather than a fabricated
  percentage.
- Cross-cut property descriptors are stored exactly once. Sparse target
  membership may scale with real property/type edges, but never by copying
  descriptors into every type; retained schema heap on the synthetic corpus is
  at least 25% below the current Plate-expanded representation.
- Semantically identical reconfiguration does not compile or increment schema
  revision; record its absolute before/after cost.

Findings:
- Plite's engine substrate is already better; replacing it with Wordgard would
  be a downgrade.
- Wordgard's strongest transferable idea is not the `Mark` class. It is that
  every property is declared, targeted, validated, and lifecycle-aware inside
  one compiled schema.
- Plite's shared-value descriptor duplication is cosmetic debt; Plate's global
  element-property merge is correctness debt.
- `isLeaf: true` plus a boolean descriptor is redundant. The final Plate shape
  is `schema.mark: property.boolean(...)`.
- Text and element property placement cannot be merged internally without
  losing real editing laws.
- Indent belongs in an explicit schema property contribution, not `node`.
- Wordgard's class identity, one-param tags, Mark arrays, DOM-in-core shapes,
  and one-document assumption are not useful extraction candidates.

Decisions and tradeoffs:
- The schema is closed by explicit policy, never by root count.
- Type/group/root/actual-parent queries are declarative and compilable.
  Arbitrary matcher callbacks are rejected from closed schema identity and key
  ownership; declared-content targets remain deferred without a consumer.
- Custom JSON validators remain possible, but collaboration merge behavior is
  restricted to law-bearing registered strategies.
- Host rendering priority/spanning/attribute targets are codec metadata, not
  model semantics.
- Hierarchical groups are adopted. Roles are limited to generic kernel
  behavior; Plate owns product roles.
- Property targets replace placement cleanup, not relational semantics. Node-ID
  uniqueness, column-width sums, list numbering, and comment/suggestion
  cross-property consistency remain commands or semantic corrections.
- The existing Plite fitter, correction engine, extension publication model,
  History format strategy, and Yjs `DocumentChange` bridge are evolved, not
  replaced.
