# Suggest, preview and decide in an editor that makes block ids

Status: building: phase B, step 6 of 13
Playbook: plan

This iteration does the rest of suggested task t_f821f679. Under a schema whose element id generates, Carol's suggested Enter inside a link, or in the text after it, left the paragraph unchanged. Every element generator turns Suggesting and previews off (`constructsValues` in `packages/plitejs/src/authored/refusal.ts`), because a preview or a decision that builds a block calls the generator, so two reads of one document could show different ids. It is the "values a fill constructs" plan that step P3.1 of [Suggestions complete](2026-10-12-suggestions-complete.md) sends out, and it must meet the redesign's Construction values stop ([Authored redesign](2026-10-11-authored-redesign.md) line 172). Its first draft kept a removed block in place of a built one, and its first plan panel showed that cannot work. The third architect replay picked stored spare blocks instead. It also takes back the line-start fix that [Generated values](2026-10-23-generated-values.md) reverted after its third diff round, in a narrower form.

## Brief

### What will change?

Suggesting works in editors that give blocks ids. Enter splits a block, and rejecting it gives the block back with its id. Previews, exports and decisions never make an id, because each suggestion stores the spare blocks it could need.

### What could go wrong?

In editors with block ids, each pending suggestion stores small hidden blocks, and the schema fingerprint changes, so saved documents and rooms need a migration. Exports now complete an emptied quote, and export suggestions under block ids instead of refusing.

## Teach

Plate can give every block an id. The schema says how to make one, and the editor calls that maker whenever a new block appears, such as the second half of an Enter.

Suggesting is off in such editors today. Showing or deciding a suggestion can need a new block, such as a line in a quote whose every line is struck out, and building that block called the id maker again. Two reads could then show different ids, and two decision orders could store different ones.

After this plan, only writes make ids. A suggestion that could empty a container stores a spare block for it, made when the suggestion is written. A read or a decision that needs a block takes the first spare in a fixed order that no earlier build used, so every read and every order shows and stores the same ids. A new schema fingerprint keeps out older editors, which would build their own.

## Public API

DOCX export completes its projection through the editor it already holds, as Markdown and HTML export do after this plan.

```ts before
// packages/platejs/src/docx/export/lib/exportDocx.tsx
const projected = projectAuthoredDocument(stored, { projection });
```

```ts after
// packages/platejs/src/docx/export/lib/exportDocx.tsx

```

A projection with an editor can refuse a document whose pending changes need a block and store no spare, such as one written by another tool. Callers that branch on `ok` already handle it.

A schema that generates a supported element value writes storage revision 2 into its contract, so its fingerprint changes and an older editor's contract parse refuses it.

## Hard cuts and app migration

- No public export is removed. The refusal code `authored-generated-values` keeps its name and now names a generated element property outside the supported set: one whose target reads its parent or the root, a pattern key, a set value, or content that drops on split. No first-party schema declares one. `authored-uncovered` is new.
- A schema that generates only text properties keeps what next allows. Suggesting and previews work, and a decision that completes an empty leaf runs the text generator inside resolution, as on next. A schema that generates both a text property and an element value keeps next's refusal, so Suggesting and previews stay off under it; for storage and load repair it counts as a schema that generates an element value.
- A generated element property that names no split policy now drops on split, so Editing gives the second half of a split a fresh value instead of a copy. `ElementIdPlugin` already drops its id on split. A schema that wants the copy names `split: 'preserve'`.
- `ElementIdPlugin` keeps its options, its check that stored ids are unique and its throw on a local duplicate. When a collaborative merge leaves two blocks built from one spare, the authored admission repairs it before the plugin's check reads it. Its lookups read stored ids under a preview, as on next.
- Schemas that generate a supported element value move to storage revision 2. Their saved envelopes and Yjs rooms need the migration that adding any property already needs (`fence-cost-a2.log`), and an older editor refuses the new ones (`p2-storage-revision-a2.log`).
- `projectAuthoredDocument` without an editor keeps working as on next, as a structural read that never completes a container. DOCX import and the v54 migration write spares and project through their schema, so no first-party caller relies on it for a valid document. Removing it is a hard cut nobody asked for, so it waits in Open work.

## Main changes

- **Line-start metadata.** When a rejected split's left half keeps no content, the right half stands in its place as on next, and now takes the left half's decided metadata values for each key whose target holds on every element type at every place, such as Plate's block id. A retype or a move can never drop such a value, so taking it adds no wait and no place check. A chain of standing lines passes the first line's values along. The standing line drops its own format tags on the keys it takes, as a mid-line join drops the right half's. When one decision lands a split piece in a container it empties (`emptiedPlaceOf` in `tree/resolve.ts`), it compares the empty line's values with the piece's on every key except these, its veto on a piece with a pending format tag skips tags on these keys, and the piece takes the empty line's values for them, the built line's and not the removed one's, as a standing line does after the container was completed first. Any other metadata key stays lost at a line's start, as on next.
- **Validity table.** Each decision, withdrawal, resolving read and live export opens a table for that run alone (`readingCovered` in `core/property-validity.ts`). A cover pass first checks every stored value of a validated key, format tag histories, cut `kept` values, spare blocks and `as` values included, once per validator and canonical value. Resolution, decide's document check, a decision commit's construction check and a live export's check of what it projected then read the table and call no validator on a stored value. An export's view and serializer check the projected document again outside the table, as next's did. A detached conversion opens no table around its input check or its check of what it projected. Each root's resolution then fills its own table and drops it, so a detached Markdown export of the gate's document judges 95 values where next judged 78. Detached HTML and plain text judge 69 where next judged 52, and live exports judge 43 where next judged 52 (`r3-export-counts-a1.log`, `r1-export-counts-base2-a1.log`). `readingCovered` drops the table when the run returns, so it holds no value past it, and a decision judges each stored value once, where next judged most of them twice. The values completion can write, a schema's defaults and its construction plans' values, are judged once per compiled schema, so once per editor and once per detached conversion, the first time a cover pass reads it (`completionValueVerdicts` in `tree/holds.ts`). Each plan value is judged only by the properties its element type allows, through the kind check first, and every later run adds those verdicts after its own. On the first run under a compiled schema, a stored value equal to one of those values is judged twice, once by the cover pass and once for the schema. A schema compiled again, such as with a new validator or validation version, judges them again. A validator that throws gets its throw recorded, so a later read rethrows it instead of calling the validator again, and any other result reads as a boolean. When a reader meets a value no cover pass checked, such as one a generator made, the run judges it once and adds it to its table. A decision therefore judges each value it generated once. Decide's check judges it after resolution, where next judged it twice, unless resolution reads it first, as when a landed line takes a generated key or a generator builds through another schema; next judged those inside resolution too. No runtime check enforces that resolution judges no stored value. The validator tests check it for the cases they decide (`r3-validator-phase-a1.log`, where `1d6d319837` judges stored values inside resolution in `r3-validator-phase-base2-a1.log`).
- **One resolve schema.** `storedResolveSchemaOf(schema, document)` replaces `ownershipResolveSchemaOf`. It completes through the compiled schema alone, over a detached schema API with its own representation editor, because a format compilation's editor does not expose the schema it compiles. The capability's projection for Markdown, HTML, DOCX and detached conversion completes through it. Live decides and previews keep `authoredResolveSchemaOf(editor)`, so the nodes they canonicalize keep their node keys. `resolveSchemaOver` builds both schemas with next's completion. The capability's projection runs with every property generator off (`withoutGeneration` in `core/editor-schema.ts`), so an export never calls one. An export whose build needs a generated value throws, such as an emptied quote's line under a schema that generates a text property, where next's export of that document threw too. The editor's schema still generates until spares land in step 6, so after phase A an editor decides and previews as next does. Step 6 masks element generation there. A built subtree that needs no generated value comes out as today, and one that needs a generated value takes a spare block or refuses as `authored-uncovered`, so the capability's projection returns a refusal again and `projectPlateFormatDocument` throws its message. DOCX export projects through `projectPlateFormatDocument`, as Markdown and HTML do. With generators off, the capability's projection drops next's refusal of every pending change under a schema that generates an element value. It projects an outcome that builds no generated value, as next's DOCX export did, and throws when the outcome needs one. Markdown, HTML and plain text exports of such a document, which next refused, now project too. An export without a projection counts pending changes through the capability's `pending` instead of projecting. DOCX import fits the structural proposed projection of its review arm through its target's schema, then compares it with the proposed arm. The comparison leaves out the keys the schema generates, since each arm fits its own document and gets its own ids. The AI chat serializes the whole document with its records. Step 6 moves its Markdown of selected blocks to a pick from the whole document's projection. This also fixes a bug next has for every schema whose build there needs no generated value: the proposed Markdown export of a quote whose only line is crossed out throws "requires at least 1 children".
- **Spare blocks.** A spare is a hidden member of a container's review set, `{ kind: 'reserve', change, type, slot, node }`, where `slot` names a construction site of `type`'s content program (a prefix index or a minimum ordinal) and `node` is the element completion builds there, made by the schema's constructor when the suggestion is written. The root's spares live in a record set, `authored-reserves`. A write that leaves a pending claim of a change that can remove a container's child or change its type stores one spare per slot for every type that container can take (its stored type and the values of its type tags) whose completion builds an element with a generated value. A format claim on a child stores none. When the recorder defers a fill at a container's maximum, the spare it stores for that slot is the command frame's own element. Plain schemas never store one.
- **Reads and decisions take spares.** A decision that builds a slot from a spare marks that spare built, a field the member keeps, so the slot stays built whatever later happens to its block: an edit, a move out of the container, or another block with equal values. A read treats the spares the outcome it shows would build as built, without storing the mark. A build that needs a generated value looks at the changes whose removal or type claim the outcome applies and takes a spare of the canonically first one. At a prefix index it takes that change's spare for the index; below a minimum it takes the one for the lowest ordinal that no spare of the container marks built. A read never removes a spare. A decision keeps a container's spares while a pending claim could remove one of its children or change its type, so a later decision sees which slots an earlier one built; it drops them all once none could, and merges the spare sets of containers a join or landing merges. A container that needs two blocks therefore builds the same two in every order, one per decision or both at once. Builds and waits stay next's: `completeLevel`, `waitOnBuild`, `waitOnPrefix` and `underInsertions` in `tree/resolve.ts`. `emptyLineOf` builds too, and since step 2 a landed piece keeps its line's values, so it takes a spare and marks it built only when its piece lands.
- **Command values.** The recorder's fills and `completeProposed` build shapes, with generation masked. Before the recording returns, a closing pass projects the touched windows as `proposed` and walks them beside the command's final frame. An inserted element whose frame value another stored element holds, as its stored value or as its `as` value, whichever change wrote it, stores a freshly generated value and an `as` member that shows the frame value; any other inserted element stores the frame value; a kept element gets a format tag with the frame value. A difference on any other key refuses the write as `diverged`, as the ledger does today. A decision writes an `as` value onto its holder once no holder of that value is pending.
- **Split policy.** A generated element property whose declaration names no split policy drops on split, so the second half of a split gets a fresh value in Editing and in the command frame. Today it keeps the value, which gave the card's link halves one id.
- **Admission.** Loading a document whose pending changes lack spares stores them, as a load repair, the way `ElementIdPlugin` fills missing ids. A load is an initial value, a value replace outside an update tagged `collaboration`, a DOCX import, the v54 migration, or a reconfiguration that activates a schema needing spares, even one that leaves the document's bytes unchanged. Content from a Yjs peer is never repaired: storage revision 2 keeps older editors' rooms out, so room content holds the spares its writer stored, and a build that finds none refuses as `authored-uncovered`. A paste or duplicate that carries pending changes drops the spares it copied and runs the write rule as a recording does. When two spares share a change, type and slot, a build takes the one whose node comes first in canonical JSON.
- **Concurrent decisions.** When a Yjs merge leaves two blocks built from one spare, the authored admission's commit repair, which the Yjs controller already sends back to the room, removes the later one when the two are still equal and otherwise gives it the container's next unbuilt spare. Every peer derives that repair from the same merged content. When no spare is left, the repair generates a value, so two peers can write different ones until the room keeps one, as concurrent Editing does.
- **Fence.** `storageRevisionOf` in `schema-compiler.ts` returns 2 for a schema that holds a supported generated element value, 1 for one with `omitDefault`, and nothing otherwise. An older editor's contract parse accepts only none or its own revision, so it refuses these envelopes and rooms, and never decides with a block of its own making. The contract diff counts any change of storage revision, either way, as one that needs a migration.

## Failures and rollback

- Each pending suggestion stores a hidden spare block for each container it touches whose completion needs a generated value, about 60 bytes each, and only under such schemas.
- Under such schemas the recorder always inserts a fill instead of keeping a struck shell, except at a container's maximum, where it defers the fill as next does and stores the command's element as that slot's spare. Next refuses these schemas today, so no stored document changes.
- When two peers decide at once and the Yjs merge leaves a container empty, the remote commit's ordinary completion builds it with a fresh id, as concurrent Editing does. When both build from the same spare, the authored admission's repair removes the later block while the two are equal, so both peers hold one block. That is a merge, not a decision order.
- A document whose pending changes store no spare, such as one another tool wrote, gets its spares when it loads, so a viewer that only reads it sees ids that hold for that load.
- The card's probe schema names no split policy for its id, so after this plan its link's second half gets a fresh id in Editing, in the proposed view and once accepted. That schema leaves `paragraph` undeclared, and the schema canonicalizes only declared element types (`editor-schema.ts` near line 2595), so neither mode gives the new paragraph an id; the same probe with `paragraph` declared gives it a fresh one. A schema that names `split: 'preserve'` for a generated key keeps a copy on purpose. A pending split then stores a fresh value on the second half and shows the kept one through `as`, and accepting writes the copy, as Editing does.
- A built block's id can come from a rejected suggestion's spare. Ids carry no meaning to a reviewer.
- Schemas with a supported generated element value, `ElementIdPlugin`'s among them, move to storage revision 2. Their saved envelopes and rooms need the migration that adding any property needs (`fence-cost-a2.log`), and an older editor refuses the new ones (`p2-storage-revision-a2.log`). Without that fence an older peer drops the review set holding a member it does not know (`fence-base-a2.log`), or stops publishing, and any decision it makes builds a block with an id of its own making.
- Markdown and HTML exports of a container a projection empties now complete it, for every schema.
- Under a schema that generates an element value, Markdown, HTML and plain text exports of a document with pending changes, which next refused, now export, as next's DOCX export did. Until spares land in step 6, one whose outcome needs a generated value throws "An export cannot generate a property value."
- Rejecting an Enter at a line's start drops a pending suggestion that only set the new line's id, as rejecting a mid-line Enter drops the right half's tags.
- Metadata keys whose target leaves out some type or reads the place, and compared values a split drops, stay lost at a line's start, as on next.
- A schema that generates only text properties still runs the generator inside resolution when a decision completes an empty leaf, as on next. One that also generates an element value still refuses Suggesting.

Phases A and B land as their own commits and keep the refusal. Phase A keeps generation in completion, so the only decisions it changes under a generating schema are step 2's: a rejected split at a line's start, and a split landing in a container the same decision empties. Phase A reverts alone. Phase B reverts alone only before any document is saved at storage revision 2; after that, its envelopes and rooms are refused once the revision is gone, so a revert needs a forward fix. Phase C lifts the refusal and lands only after both; reverting C restores the refusal.
