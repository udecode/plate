# Suggest, preview and decide in an editor that makes block ids

Status: executed: phases A, B and C landed on next
Playbook: plan

This iteration does the rest of suggested task t_f821f679. Under a schema whose element id generates, Carol's suggested Enter inside a link, or in the text after it, left the paragraph unchanged. Every element generator turns Suggesting and previews off (`constructsValues` in `packages/plitejs/src/authored/refusal.ts`), because a preview or a decision that builds a block calls the generator, so two reads of one document could show different ids. It is the "values a fill constructs" plan that step P3.1 of [Suggestions complete](2026-10-12-suggestions-complete.md) sends out, and it must meet the redesign's Construction values stop ([Authored redesign](2026-10-11-authored-redesign.md) line 172). Its first draft kept a removed block in place of a built one, and its first plan panel showed that cannot work. The third architect replay picked stored spare blocks instead. It also takes back the line-start fix that [Generated values](2026-10-23-generated-values.md) reverted after its third diff round, in a narrower form.

## Brief

### What will change?

Suggesting works in editors that give blocks ids. Rejecting an Enter restores the split block with its id. Previews and exports never make an id. A decision makes one only when another block took the id a suggestion set aside.

### What could go wrong?

Saved documents and rooms with block ids need a migration. If another block took the id a suggestion set aside, the final ids depend on decision order. Two timing checks stayed too noisy, and a follow-up task reruns them.

## Teach

Plate can give every block an id. The schema says how to make one, and the editor calls that maker whenever a new block appears, such as the second half of an Enter.

Suggesting is off in such editors today. Showing or deciding a suggestion can need a new block, such as a line in a quote whose every line is struck out, and building that block called the id maker again. Two reads could then show different ids, and two decision orders could store different ones.

After this plan, writes make ids. A suggestion that could empty a container stores a spare block for it, made when the suggestion is written. A read or a decision that needs a block takes the first spare in a fixed order that no earlier build used, so every read and every order shows and stores the same ids. The exception is a stored block, such as one written after the suggestion, that repeats a spare's id. The decision that builds that spare gives the built block a fresh id, which differs from the preview, so the stored ids then depend on decision order. A new schema fingerprint keeps out older editors, which would build their own.

A projection with an editor can refuse a document whose pending changes need a block and store no spare, such as one written by another tool. Callers that branch on `ok` already handle it.

## Hard cuts and app migration

- No public export is removed. The refusal code `authored-generated-values` keeps its name and now names a generated element property outside the supported set: one whose target reads its parent or the root, a pattern key, a set value, or the content role. No first-party schema declares one. `authored-uncovered` is new.
- A schema that generates only text properties keeps what next allows. Suggesting and previews work, and a decision that completes an empty leaf runs the text generator inside resolution, as on next. A schema that generates both a text property and an element value keeps next's refusal, so Suggesting and previews stay off under it; for storage and load repair it counts as a schema that generates an element value.
- Under a generated element property outside the supported set, a decision that builds an element still runs its generator inside resolution, as on next, and so do the v54 migration and DOCX import. Resolution masks only the generators of the properties that store spares, so a text generator that builds through another schema still runs that schema's generators.
- A generated element property that names no split policy now drops on split, so Editing gives the second half of a split a fresh value instead of a copy. `ElementIdPlugin` already drops its id on split. A schema that wants the copy names `split: 'preserve'`.
- `ElementIdPlugin` keeps its options, its check that stored ids are unique and its throw on a local duplicate. When a collaborative merge leaves two blocks built from one spare, the authored admission gives the later block another id before the plugin's check reads it. Its lookups read stored ids under a preview, as on next.
- Schemas that generate a supported element value move to storage revision 2. Their saved envelopes and Yjs rooms need the migration that adding any property already needs (`fence-cost-a2.log`), and an older editor refuses the new ones (`p2-storage-revision-a2.log`). Reconfiguring to a schema that stores no spares removes every spare and every `as` member, and each block keeps the value it stores, so the document keeps nothing an older editor drops.
- `projectAuthoredDocument` without an editor keeps working as on next, as a structural read that never completes a container. DOCX import and the v54 migration write spares and project through their schema, so no first-party caller relies on it for a valid document. Removing it is a hard cut nobody asked for, so it waits in Open work.

## Main changes

- **Line-start metadata.** When a rejected split's left half keeps no content, the right half stands in its place as on next, and now takes the left half's decided values for each key `handoverKeysOf` in core returns. Those are the element metadata keys that every declaration drops on split and that no retype can drop, which is the check `unique` already requires, such as Plate's block id. A retype or a move can never drop such a value, so taking it adds no wait and no place check. A chain of standing lines passes the first line's values along. The standing line drops its own format tags on the keys it takes, as a mid-line join drops the right half's. When one decision lands a split piece in a container it empties (`emptiedPlaceOf` in `tree/resolve.ts`), it compares the empty line's values with the piece's on every key except those `splitDroppedKeysOf` returns, every element key that every declaration drops on split, content keys included, since the two halves of a split always differ on them. Its veto on a piece with a pending format tag skips tags on those keys. The piece takes the empty line's values for the handed-over keys, the built line's and not the removed one's, as a standing line does after the container was completed first, and keeps its own value of every other key. Any other metadata key stays lost at a line's start, as on next.
- **Validity table.** Each decision, withdrawal, resolving read and live export opens a table for that run alone (`readingCovered` in `core/property-validity.ts`). A cover pass first checks every stored value of a validated key, format tag histories, spare blocks in containers and in the root's record set, and `as` values included, once per validator and canonical value. Resolution, decide's document check, a decision commit's construction check and a live export's check of what it projected then read the table and call no validator on a stored value. An export's view and serializer check the projected document again outside the table, as next's did. A detached conversion opens no table around its input check or its check of what it projected. Each root's resolution then fills its own table and drops it, so a detached Markdown export of the gate's document judges 95 values where next judged 78. Detached HTML and plain text judge 69 where next judged 52, and live exports judge 43 where next judged 52 (`r3-export-counts-a1.log`, `r1-export-counts-base2-a1.log`). `readingCovered` drops the table when the run returns, so it holds no value past it, and a decision judges each stored value once, where next judged most of them twice. The values completion can write, a schema's defaults and its construction plans' values, are judged once per compiled schema, so once per editor and once per detached conversion, the first time a cover pass reads it (`completionValueVerdicts` in `tree/holds.ts`). Each plan value is judged only by the properties its element type allows, through the kind check first, and every later run adds those verdicts after its own. On the first run under a compiled schema, a stored value equal to one of those values is judged twice, once by the cover pass and once for the schema. A schema compiled again, such as with a new validator or validation version, judges them again. A validator that throws gets its throw recorded, so a later read rethrows it instead of calling the validator again, and any other result reads as a boolean. When a reader meets a value no cover pass checked, such as one a generator made, the run judges it once and adds it to its table. A decision therefore judges each value it generated once. Decide's check judges it after resolution, where next judged it twice, unless resolution reads it first, as when a landed line takes a generated key or a generator builds through another schema; next judged those inside resolution too. No runtime check enforces that resolution judges no stored value. The validator tests check it for the cases they decide (`r3-validator-phase-a1.log`, where `1d6d319837` judges stored values inside resolution in `r3-validator-phase-base2-a1.log`).
- **One resolve schema.** `storedResolveSchemaOf(schema, document)` replaces `ownershipResolveSchemaOf`. It completes through the compiled schema alone, over a detached schema API with its own representation editor, because a format compilation's editor does not expose the schema it compiles. The capability's projection for Markdown, HTML, DOCX and detached conversion completes through it. Live decides and previews keep `authoredResolveSchemaOf(editor)`, so the nodes they canonicalize keep their node keys. `resolveSchemaOver` builds both schemas with next's completion. The capability's projection runs with every property generator off (`withoutGeneration` in `core/editor-schema.ts`), so an export never calls one. An export whose build needs a generated value throws, such as an emptied quote's line under a schema that generates a text property, where next's export of that document threw too. The editor's schema still generates until spares land in step 6, so after phase A an editor decides and previews as next does. From step 6 on, completion there masks the generators of the properties that store spares, and every other generator runs as on next. A built subtree that needs no generated value comes out as today, and one that needs a generated value takes a spare block or refuses as `authored-uncovered`, so the capability's projection returns a refusal again and `projectPlateFormatDocument` throws its message. DOCX export projects through `projectPlateFormatDocument`, as Markdown and HTML do. With generators off, the capability's projection drops next's refusal of every pending change under a schema that generates an element value. It projects an outcome that builds no generated value, as next's DOCX export did, and throws when the outcome needs one. Markdown, HTML and plain text exports of such a document, which next refused, now project too. An export without a projection counts pending changes through the capability's `pending` instead of projecting. DOCX import fits the structural proposed projection of its review arm through its target's schema, then compares it with the proposed arm. The comparison leaves out the keys the schema generates, since each arm fits its own document and gets its own ids. The AI chat serializes the whole document with its records. Step 6 moves its Markdown of selected blocks to a pick from the whole document's projection when the view shows stored blocks; in a projected view the selected blocks are already the projection's. This also fixes a bug next has for every schema whose build there needs no generated value: the proposed Markdown export of a quote whose only line is crossed out throws "requires at least 1 children".
- **Spare blocks.** A spare is a hidden member of a container's review set, `{ kind: 'reserve', change, type, slot, node }`, where `slot` names a construction site of `type`'s content program (a prefix index or a minimum ordinal) and `node` is the element completion builds there, made by the schema's constructor when the suggestion is written. The root's spares live in a record set, `authored-reserves`. A write that leaves a pending claim of a change that can remove a container's child or change its type stores one spare per slot for every type that container can take (its stored type and each type its type tags write or restore) whose completion builds an element with a generated value, except for a type and slot where the container already holds an unbuilt spare that still fits, meaning its node has the type completion builds there and is valid where it is stored, validators and content rules included. A format claim on a child stores none. When the recorder defers a fill at a container's maximum, the command frame's own element becomes that slot's spare, replacing any unbuilt one. Plain schemas never store one.
- **Reads and decisions take spares.** A build that needs a generated value takes the container's unbuilt spare for the type and slot it builds. At a prefix index that is the spare for the index, and below a minimum it is the spare for the lowest ordinal that still has one. When two peers stored a spare for one slot at once, it takes the one whose node comes first in canonical JSON. A spare taken somewhere other than where it was stored, as when an ancestor's decision unwraps its container, takes each default its new place adds and drops each value its new place forbids. A decision that builds a slot marks every spare of that type and slot built, a field the member keeps, so the slot stays built whatever later happens to its block: an edit, a move out of the container, or another block with equal values. A later write that removes that block stores a new spare for the slot. A read treats the spares the outcome it shows would build as built, without storing the mark. Because a write stores no spare where an unbuilt one that fits exists, every decision order finds the same spare at each slot, whichever change's claim the outcome applies. A read never removes a spare, and a change to a root's spare records alone has the view resolve that root again, as a schema change does. A decision keeps a container's spares while a pending claim could remove one of its children or change its type, a join one of its children follows included, as the write rule reads it, so a later decision sees which slots an earlier one built; it drops them all once none could, and merges the spare sets of containers a join or landing merges. A container that needs two blocks therefore builds the same two in every order, one per decision or both at once. A decision that drops a root an element owns deletes that root's spare records, as an Editing removal of the owner does. Builds and waits stay next's: `completeLevel`, `waitOnBuild`, `waitOnPrefix` and `underInsertions` in `tree/resolve.ts`, except that `waitOnPrefix`'s trial completions take from the spares as they stood before their level's own build. `emptyLineOf` builds too, and since step 2 a landed piece keeps its line's values, so it takes a spare and marks it built only when its piece lands.
- **Command values.** The recorder's fills and `completeProposed` build shapes, with generation masked. Before the recording returns, a closing pass projects the touched windows as `proposed` and walks them beside the command's final frame. An inserted element whose frame value another stored element holds, as its stored value or as its `as` value, whichever change wrote it, stores a freshly generated value and an `as` member that shows the frame value; any other inserted element stores the frame value; a kept element gets a format tag with the frame value. A difference on any other key refuses the write as `diverged`, as the ledger does today. A settle stage after admission settles `as` values at every commit and every load, one key at a time. A group is a value and every element that stores it, shows it or gets it back when a pending tag is rejected, with every other value of the key such an element holds. A group waits while any of its holders is pending. A holder is pending while a stored claim on it or on an ancestor in its block is pending, while a context it belongs to carries an undecided insertion, while a tag on its key or a type tag on it or any ancestor is pending, and while any element that owns the content root it sits in is pending, each owner judged the same way up to the main root. Once a group waits on nothing, the stage works in the unique repair's document order and until nothing changes. The first element that shows a value of the group, whose decided type and place can hold it and whose value no other element stores, writes it, counting the values earlier writes release. Every other element that shows a value of the group drops it and keeps the value it stores. A redo replays a commit without what its settle stage wrote, so the stage settles those values again under the current document. A commit whose settle stage changed anything is its own undo step and takes no later merge.
- **Split policy.** A generated element property whose declaration names no split policy drops on split, so the second half of a split gets a fresh value in Editing and in the command frame. A property an element declares among its own properties names no policy, so a generated one always drops. Today it keeps the value, which gave the card's link halves one id. A generated property with the content role stays outside the supported set whatever its split policy and keeps the refusal, since a rejected split compares content values, which an `as` member would hide.
- **Admission.** Loading a document whose pending changes lack spares stores them, as a load repair, the way `ElementIdPlugin` fills missing ids. A load is an initial value, a value replace outside an update tagged `collaboration`, a DOCX import, the v54 migration, or a reconfiguration that activates a schema needing spares, even one that leaves the document's bytes unchanged. Content from a Yjs peer is never repaired: storage revision 2 keeps older editors' rooms out, so room content holds the spares its writer stored, and a build that finds none refuses as `authored-uncovered`. Shown values settle on content from a Yjs peer too, because the settle stage runs on every commit, and each peer's settle repair reaches the room as the unique repair's renames do. A paste or duplicate that carries pending changes drops the spares it copied and runs the write rule as a recording does. A load also replaces each unbuilt spare that no longer fits, such as after a schema changes a container's default child or a validator now rejects it, and drops the spare records of a root the document does not hold. Under a schema that stores no spares, it removes every spare and every `as` member, so each block keeps the value it stores. Whether a block could take the value it shows depends on decisions that a load cannot make.
- **Concurrent decisions.** This phase covers one peer deciding at a time. Two peers that accept one change at once each build the container's block from the same spare, so the merged room holds two blocks with one id. When a decision changes a container's spares and its children in one commit, the Yjs bridge also deletes the container and inserts it again. [Spare collaboration](2026-10-24-spare-collaboration.md) fixes both and lands with this phase. Phase B no longer has the commit repair that renamed later copies of a repeated generated value, because it also renamed values two blocks share on purpose, such as a day stamp.
- **Fence.** `storageRevisionOf` in `schema-compiler.ts` returns 2 for a schema that holds a supported generated element value, 1 for one with `omitDefault`, and nothing otherwise. An older editor's contract parse accepts only none or its own revision, so it refuses these envelopes and rooms, and never decides with a block of its own making. The contract diff counts any change of storage revision, either way, as one that needs a migration.

## Failures and rollback

- A pending suggestion stores a hidden spare block for each slot of a container it touches whose completion needs a generated value and that holds no unbuilt spare yet, about 60 bytes each, and only under such schemas.
- Under such schemas the recorder always inserts a fill instead of keeping a struck shell, except at a container's maximum, where it defers the fill as next does and stores the command's element as that slot's spare. Next refuses these schemas today, so no stored document changes.
- When two peers decide at once and the Yjs merge leaves a container empty, the remote commit's ordinary completion builds it with a fresh id, as concurrent Editing does. When both build from the same spare, this phase alone stores two blocks with one id; [Spare collaboration](2026-10-24-spare-collaboration.md), which lands with it, closes that case.
- A document whose pending changes store no spare, such as one another tool wrote, gets its spares when it loads, so a viewer that only reads it sees ids that hold for that load.
- The card's probe schema names no split policy for its id, so after this plan its link's second half gets a fresh id in Editing, in the proposed view and once accepted. That schema leaves `paragraph` undeclared, and the schema canonicalizes only declared element types (`editor-schema.ts` near line 2595), so neither mode gives the new paragraph an id; the same probe with `paragraph` declared gives it a fresh one. A schema that names `split: 'preserve'` for a generated key keeps a copy on purpose. A pending split then stores a fresh value on the second half and shows the kept one through `as`, and accepting writes the copy, as Editing does.
- A built block's id can come from a rejected suggestion's spare. Ids carry no meaning to a reviewer.
- Schemas with a supported generated element value, `ElementIdPlugin`'s among them, move to storage revision 2. Their saved envelopes and rooms need the migration that adding any property needs (`fence-cost-a2.log`), and an older editor refuses the new ones (`p2-storage-revision-a2.log`). - Rejecting an Enter at a line's start drops a pending suggestion that only set the new line's id, as rejecting a mid-line Enter drops the right half's tags.

Phases A and B land as their own commits and keep the refusal. Phase A reverts alone.
