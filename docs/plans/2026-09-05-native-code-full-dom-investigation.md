## Historical finding — withdrawn after final replay

**This timing claim is not certified. Final unchanged-source baselines varied
from 12.66 s to 2.59 s, and direct input comparisons did not clear materiality.
The CSS change is reverted. See Final disposition below.**


The current implementation is not the best achievable without virtualization.
The owning choice is `apps/www/src/registry/components/editor/code-block.tsx:149`:
the code text host receives `display: contents`. Changing that host to
`display: block` before hydration materially reduces actual-route mount time
while retaining every line, character and token element.

| Chrome profile, same source-first dev route | Fresh mounts, seconds | Median |
|---|---|---|
| Current `display: contents` | 21.243, 18.619, 18.146 | 18.619 s |
| Temporary `display: block` | 4.313, 5.180, 3.955 | 4.313 s |

The median reduction is **76.8%**, about **4.3 times faster**. Even the slowest
control is well below the fastest baseline. This clears the predeclared
materiality threshold. Three samples per mode establish this large local
difference; they do not establish p95 or production performance.

Every accepted row retains **10,000 lines, 448,889 code characters and 30,042
editor descendant elements**. The text flow reports 60,000 segments, including
plain text segments. There is no virtualization, skipped content, truncated
fixture or disabled highlighting.

## Causal evidence

Final complete timeline captures on the current server:

| Rendering phase | Current host | Block host |
|---|---|---|
| UpdateLayoutTree / style recalculation, total | 16,011.1 ms | 604.5 ms |
| Layout, total | 299.0 ms | 126.6 ms |
| Paint, total | 9.2 ms | 4.7 ms |

These are separately profiled samples, excluded from the unprofiled mount
medians. The browser rendering cost changes when the host display property
changes; it is not an unavoidable 10,000-line layout floor. This does not
identify the exact Chromium internal algorithm responsible for the slow
`display: contents` update.

The CPU profile attributes much of the initial stall to a selection layout
effect because its browser read flushes pending rendering work. That stack
alone is not evidence of a 15-second JavaScript selection algorithm.

Selector statistics also do not justify blaming one expensive selector:
the complete instrumented capture totals about 867 ms of selector matching,
far less than its instrumented style time. The first selector capture lost
data and is retained as rejected evidence. The second is complete and used
only for attribution, never as a mount sample. Chrome documents the method in
[CSS selector statistics](https://developer.chrome.com/docs/devtools/performance/selector-stats).

An already assembled DOM clone attached in roughly 0.54 seconds, and a
mounted-host child replacement took roughly 0.82 seconds. These exploratory
controls exclude actual editor initialization and warmed browser state differs;
they are not accepted product mount comparisons.
