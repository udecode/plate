## Teach

In Plite, a suggestion is a pending change saved in the document. An app reads them a page at a time and accepts or rejects them with one call. That call says whether it worked, whether the change moved since it was read, or whether a related change has to be decided too.

There are two extra reads. One tells you what a decision would return without applying it. The other limits a page to changes made in a time window. Nothing in this repo or the sibling apps calls either, and nothing on screen shows what they return. The docs even tell apps to run the check before every bulk decision, so each decision runs twice.

Both go, and nothing replaces them in the docs. An app just makes the decision and reads the answer, which already says what happened. To filter by time, an app checks the time stored on each change in a page.

A caller that pages a time window filters each page instead. `createdAt` is the earliest author-clock time among the change's marks still in the document, so it can move later when that mark goes (`probe-panel-r1-head-a1.log`, section C2). A filtered page can come back empty while a later page holds matches, so the caller reads on with the cursor. A cursor records every query option but `cursor` and `limit`, and `changes` throws `Stale authored page cursor.` when the next query differs (`authored.ts`, the `fingerprint` of `changes`). So a cursor saved from a time-filtered query cannot continue the new loop, and the caller starts paging again:

```tsx
// before
const page = authored.read.changes({ from: since, limit: 50 });

// after
const recent: AuthoredChange[] = [];
let cursor: string | undefined;
do {
  const page = authored.read.changes({ cursor, limit: 50 });
  recent.push(...page.items.filter((change) => change.createdAt >= since));
  cursor = page.cursor ?? undefined;
} while (cursor);
```

The loop compiles (`type-probe4-plate-base-a1.log`). At page size 1 it finds every change made since the time, in document order; reading only the first page misses two of three (`probe-migration-head-a1.log`, `probe-migration-nocursor-a1.log`).

A query that still carries `from` or `to` without TypeScript seeing it returns unfiltered pages with no error. That covers untyped JavaScript and a typed query kept in a variable or spread into the call when it also sets another option, such as `limit`, because TypeScript checks extra keys only on a fresh object literal. A stored query that sets only `from` or `to` shares no option with the type, so TypeScript rejects it (inferred from its weak-type check; step 1's type probe checks it on the build tree). The filter ignores keys it does not know, while the cursor still records them, so such a caller's pages stay consistent with each other; that is inferred from the source of `changes`, and the type probe's stored and spread cases show the compile side on the build tree. A bulk decision over such a page can then decide changes outside the window.
