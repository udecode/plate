# Commit composed text through the insert-text command

Status: partial: the macOS input-method drive and the typing gate on a quieter host wait
Playbook: plan

**Pursue, second iteration.** [The first iteration](2026-10-26-native-ime-struck-text.md) sent every desktop composition through the insert-text command, so a word composed inside another author's crossed-out text lands after it. Its third diff review found three faults, and each mechanism had already used its one replacement. A composed word and a typed letter landed apart at a bold link's end, because the input runtime pins the browser's target for a caret only on an unmarked leaf. A handler that takes the word without editing could run twice. The cleanup of the browser's drawn copy deleted text by content in hosts the composition never touched. Two architect arenas on three models settled both mechanisms. The plan panel's first round then found that this plan still landed a composed word after the crossed-out text, against the card and the law, so a third arena designed that landing. Every caret input pins the browser's target exactly when a typed letter does, so where text lands no longer depends on which branch handled it. When a composition starts, Plite snapshots the one text host the browser draws in, and after the commit it puts that host back only where the model disagrees. The first arena's repair kept the browser's DOM changes from the integrity observer, but probes showed the observer cannot tell the browser's edits from React's, so a second arena replaced it. The third arena's pick lifted any write near the stored caret to it. The panel's second round and a probe showed that window splits nothing beside a link and overrides a handler's own place, so a prototype stamped insert-text's own write instead, and the recorder puts that write at the stored caret. It split every probed shape where the command writes in the stored place's element. The panel's third round found four cases that still failed where the review commit's bridge works: a word right before a link, a handler's redirect to the same place, the undo of a handler that emits an effect, and a decorated host. So a stamped commit's frame keeps its caret in the stored place's element, the claim keys on the dispatcher's own destination, history merges a composition's batches with reversible effects, and a host split into segments restores.

## Brief

### What will change?

Composed words now go through the same command as typed letters, so typing plugins see them, and inside another author's crossed-out text they still split it. Tested in three browsers, not with a real input method.

### What could go wrong?

A real Japanese or Korean input method may still move or double the word. A late bold fix skipped review. Typing speed went unmeasured under load. Safari's path still drops bold when composing over bold text, as on next.

## Teach

Under review, typed text goes through the insert-text command, where Plate's typing plugins such as input rules, the link exit and Copilot run. A word confirmed with a desktop input method skipped it, so it split another author's crossed-out text and no plugin saw it.

Now every confirmed word goes through the command and names the place the browser drew it when a typed letter does. Typed letters land after another author's crossed-out text, but the law lets a composition keep writing at the caret. The command decides on the text without the crossed-out letters, and Plite records the command's own write at the caret where the composition started, which splits the deletion.

While you compose, the browser draws the word itself. Plite notes what that spot showed when the composition starts, and after the commit puts its text back where the model disagrees, so React draws the model. Where anything but that text changed, Plite redraws the paragraph.

## Main changes

- One function, `dispatchUserText` in `mutation-controller.ts`, hands user text to `editorCommands.insertText`, and every collapsed branch of `applyModelOwnedTextInput` calls it, which deletes the condition computed twice at `mutation-controller.ts:944-946` and `:984-987`. For `insertText` and `insertFromComposition` it pins the browser's target as `at` exactly when typed text does today, on an unmarked leaf with no active marks, and otherwise runs the command at the selection. A composition whose target lies in content the command view hides, such as crossed-out text, passes that stored point as `at`, because the word lands at the stored place. With marks pending it runs at the selection instead, as typed text does, because insert-text applies pending marks only to a write with no `at` (`insert-text.ts:202`), and the frame still places the stamped caret in the stored place's element. A handler that reads the shown caret, such as the link exit at a link's end, then leaves it alone. Plate's input-rule gate counts that stored point as the caret when it equals the collapsed selection, so input rules still run on a word composed in hidden text. A rule that continues with only new text and leaves its draft empty keeps that stored point, so its text still lands at the composition's place. The link exit's own gate still skips anything but a range. The inline equation rule drops its own copy of the old gate, which the plugin's gate already runs before any rule. Every collapsed branch first writes the target as the selection when the view does not hold it and then restores the pending marks, as typed text's fast path does at `:911-912`. A range always passes `at`, and `insertFromYank`, `insertReplacementText` and every other input type keep passing `at` as today. Typed letters, Chrome's compositionend fallback, Safari's final `insertFromComposition` and a final input claimed after compositionend all call it, and the native-equivalence probe (`runtime-before-input-events.ts:113-124`) builds its command with the same rule. The Android replay keeps its own call, which sends no `at`, and marks a collapsed commit as a composition like the desktop routes.
- For a composition commit, `dispatchUserText` stamps the insert-text invocation it starts. The stamp holds the stored place the composition writes at, which is the caret or the start of the selection it replaces, and the destination the dispatcher passed, which is the pinned target or none. The outermost command frame keeps the stamp, which never enters command input, so no handler sees, strips or forwards it. When that frame places the stamped invocation's caret and destination, a point beside an inline goes to the side that holds the stored place's element, so a caret hidden in crossed-out text right before a link stays outside the link. Typed text keeps today's placement. The insert-text command's own build claims the stamp for its final text write when the destination it builds from is the one the dispatcher passed and nothing has placed the caret since the frame began. The editor counts those placements only while a stamped frame runs, so typing and every other update count nothing. A handler cannot write through a nested insert-text command, because the command registry refuses one as a recursion cycle. The claim belongs to the draft it was made in, so a draft the frame discards releases it. The builder tags the steps the claimed write makes. The stamp stays unclaimed in each of these cases: a handler passes a new destination, even at the same place, or places the caret in a draft it keeps; a later command in the same update writes; the frame discards the draft; or another caller, such as an input rule's draft, runs `tx.text.insert`.
- The recorder lowers a tagged step at the stamp's stored place when the command wrote into the element that holds that place, judged by the element's identity through the projection's node map, not by its depth and type, and records the word with the leaf properties the command wrote it with, as a typed letter at that caret takes the live marks (`authored-tree-commands.test.ts:433`). Otherwise the command's write stands where the shown text put it. Every other step, the caret and every effect map as before. So a composed word splits the deletion, a typed or pasted letter at the same caret still lands after it, and the framed-law check (`authored.ts:535`) still compares the recording with what the command wrote. The leaf rule reads properties from the written leaf, so it holds where that check is off.
- A frame that carries a composition stamp maps its caret from an expanded selection's start, where `authored.ts:2165-2175` takes only a collapsed one today. The pre-delete at compositionstart runs with a stamp too, which has no text to claim and only marks its frame, so the authored plugin reads no history annotation. So a pre-delete that removes a word between crossed-out halves leaves the caret between them, and a reconversion or a Korean re-composition there splits the deletion again.
- A composition's pre-delete over a selection and the commit that follows it carry the composition's grouping identity (`nativeGroupingInput`), so one undo restores both. A collapsed commit keeps the grouping each route gives it today, so Korean syllables on Safari's direct route undo as they do now. The history owner merges a composition's batches even when either carries a reversible effect, such as the one Copilot's insert handler emits, and keeps each effect in order. A commit whose handler takes the word and only emits an effect keeps the composition's grouping and merges with its pre-delete too. A batch that only carries effects merges with the composition's other batch whichever comes first, so a handler that emits an effect on the empty insert at compositionstart still undoes in one step. Today it merges no batch with effects (`history-plugin.ts:803`, `history-merge-policy.ts:387-404`). A session effect still keeps its own batch.
- Each composition gets a terminal receipt, pending until its one commit attempt claims it or the composition is cancelled. A commit that changes nothing, a refusal and an exception each end the composition, and the guard against the late final input goes in before teardown. The receipt also resolves at teardown whenever no final input is owed: an Escape cancel, an externally owned or Android end, and the expiry of the guard against the late final input. None of these installs a guard. Some compositions end with no commit attempt, because the editor turned read-only during them or a key arrived and compositionend never came. One terminal operation then cancels the receipt, settles the lease and ends the composition's session, so the next ordinary input starts its own undo step. When a fallback that returns early waits for a late final input that never comes, the receipt expires on the guard's timeout, and an expiry cancels only the receipt that is still current. The input runtime publishes the receipt through one view-state read beside `isComposing`, which the authored plugin reads, and that read stays pending while any Editable on the editor owes a word. A claim keeps it pending until the commit it admits returns, so that commit records under the intent its composition began in. The fallback claims the receipt only once it has a usable target and dispatches, so a fallback that returns early, on a WebKit host, under the compositionend-precedes-final-input quirk or with no text, leaves the late final input to commit. The beforeinput adapter claims a settled composition's final input before its node-selection branch (`runtime-before-input-events.ts:540-581`).
- The authored plugin applies an intent switch requested during a composition once that composition's terminal receipt resolves, committed or cancelled, instead of when composing ends (`authored.ts:1546-1560`). So the word records under the intent its composition began in on every route, a fallback that returns early included. Composing ends where it does today, so readers of `isComposing`, such as the combobox (`comboboxOwner.internal.ts:370-385`), see each commit as they do now. A key that ends a composition with no compositionend runs its command before the view-state listener runs. So each authored update first applies a waiting switch whose composition no longer owes a word, and the listener then has nothing left to apply.
- At compositionstart, a composition lease in a new `composition-lease.ts`, held by the Editable's runtime, snapshots the child lists and text values of the text host that holds the DOM focus, which are what React last rendered there. It takes that host whenever the DOM focus resolves to the model caret's position, a neighboring leaf's edge included, so a word drawn at the next leaf's start still gets a lease; today's anchor needs an exact match (`composition-state.ts:133`). Plite's own writers, React's leaf render, `syncChangedTextToDOM` (`use-plite-node-ref.tsx:575`) and the integrity observer's repair write nothing inside the leased host until the lease settles. Each writer queues its write, and the observer leaves the host's mutations to the settle.
- After the commit attempt, the lease compares the host with its snapshot, whatever renderer drew it. When only the text of the host's editable string nodes changed, it keeps the DOM with no write if the host holds one editable string node, the browser inserted one run at one offset and the model leaf equals the snapshot with that run there. A host whose string sits under a decoration, or that holds several strings, restores instead, because React keeps a segment whose props did not change. Otherwise it restores those text nodes, so React's queued write draws the model. Any other change rebuilds the lowest containing block, such as a child list the browser or another writer changed, an emptied line's placeholder, a dropped host, or a descendant that rendered on its own, like a badge that reads a store. Plain, decorated, custom and injected-props hosts, the suggestion plugin's leaves among them, take the same verdict. A DOM focus in another host at the settle rebuilds that host's block too. Outside a leased host the integrity observer works as before.
- On Safari's direct route the lease keeps its host protected, from the integrity observer too, until the browser's compositionend settles it, even after composing ended.
- A composition over a selection captures the blocks the selection covers before the browser deletes them, and after the commit rebuilds those still mounted, the block holding the selection's start included.
- When another composition starts before React has rendered the previous commit, the new compositionstart renders it synchronously first. React's selection effect then puts the DOM caret after the landed word before the browser draws the next syllable, and the new lease snapshots that render.
- The change deletes `removeUnmanagedCompositionTextNodes` and its walk over every mounted text host.
- The kernel authority audit drops its composition bridge and audits `composition-state.ts`.
- `composeText` in `@platejs/test` gains a mode that draws the preedit into the DOM as a browser does and sends each engine's event order, so Firefox commits through compositionend and the fallback as Chromium does, with the one `input` event Gecko sends, and WebKit through `deleteCompositionText`, which erases the preedit, then a final `insertFromComposition` before compositionend.

## Public API

No public call changes. Inside the input runtime, every caret input reaches the insert-text command the same way.

```ts before
// packages/plitejs/src/react/editable/mutation-controller.ts
if (
  inputType === 'insertFromComposition' &&
  !inputController?.state.isReplayingAndroidCommand
) {
  tx.text.insert(data, marks !== undefined ? {} : { at: target });
  return;
}
tx.command(editorCommands.insertText, {
  ...(collapsed && marks !== undefined ? {} : { options: { at: target } }),
  text: data,
});
```

```ts after
// packages/plitejs/src/react/editable/mutation-controller.ts
dispatchUserText(editor, tx, {
  composed: inputType === 'insertFromComposition',
  marks,
  target,
  text: data,
});
```
