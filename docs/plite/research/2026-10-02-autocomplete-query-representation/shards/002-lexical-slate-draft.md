# Trigger autocomplete in Lexical, Slate and Draft.js mention

Scope is autocomplete (mention, slash or component picker, emoji). The research asks one question. Does the query live in ordinary document text with a tracked range, or in a separate input element?

Revisions read:

- Lexical `/Users/zbeyens/git/lexical` at `dd5c41b13193efa9ab1574234d8593d2c9e4f988`. Paths below are relative to `packages/`.
- Slate `/Users/zbeyens/git/slate` at `945a484df2497e4c448b33f417b0de2a49840032`.
- Draft.js mention, read from the published packages `@draft-js-plugins/mention@5.3.0` (`lib/index.esm.js`, npm shasum e6fb373f) and `draft-js@0.11.7` (`lib/*.js`). Both were unpacked into `draftjs/` in this scratch dir. Line numbers refer to the published dist files, not to the upstream TypeScript source.

Grades:

- A means local source read.
- B means a detailed issue or PR was read.
- C means docs or an example.
- D means a search hit only.

"Inferred" marks a behavior I derived from the code and did not run.

## Slate (site/examples/ts/mentions.tsx)

Slate core has no autocomplete or mention code. A git grep for `mention` in `packages/slate-react/src` and `packages/slate-dom/src` found nothing. Everything below comes from the example, which counts as grade C for product behavior, plus core source (A) where cited.

| Dimension | Finding | Grade |
| --- | --- | --- |
| 1. Query representation | The query is ordinary document text. React state holds `target: Range`, `search: string` and `index` (`site/examples/ts/mentions.tsx:41-43`). `onChange` recomputes them on every change (`:106-130`). On select it calls `Transforms.select(editor, target)` and then `insertNodes` with an inline void `mention` element (`:78-79`, `:179-205`). That void is the finished mention, not the query. A related pattern exists in `site/examples/ts/editable-voids.tsx:76-100`. It puts a native `<input>` inside a block void, with its value held in local React state outside the document, and the comment "Need contentEditable=false or Firefox has issues with certain input types" (`:79`). | A (example), C |
| 2. Activation | Any change (typing, selection, paste) re-runs `onChange` (inferred). The menu opens when the collapsed selection has `^@(\w+)$` before it, measured as one Slate word unit plus one character back, and whitespace or the end after it (`mentions.tsx:109-121`). A bare `@` never opens it (#5844, open). `\w` is ASCII only, so CJK, accented or hyphenated names stop matching. #4570 (open) reports that `@R2-` closes the list, and a maintainer notes that `unit: 'word'` also breaks it. It closes when the selection is expanded, when the match is lost (`:129`), or on Escape (`:82-85`). Escape only clears `target`, so the next change reopens it (inferred). Blur has no handler. Selecting an option and Enter or Tab end the query (`:75-81`). | A, B |
| 3. IME / composition | The example's `onKeyDown` has no `isComposing` or 229 check (`mentions.tsx:61-90`). Slate calls the user `onKeyDown` before its own composing gate. The code is `isEventHandled(event, attributes.onKeyDown) \|\| ReactEditor.isComposing(editor)` (`packages/slate-react/src/components/editable.tsx:1575-1578`). So Enter or Tab during IME composition with an open list inserts the mention (inferred). `\w+` already keeps CJK queries from opening the list. Core resets a stale composing flag when `nativeEvent.isComposing === false` (`editable.tsx:1565-1572`). The mention element renders its children differently on macOS (#3490) and other platforms (PR #5360) to avoid IME breakage around the void (`mentions.tsx:270-284`). | A, B |
| 4. Android | #5357 (Android plus Gboard). Pressing Enter to complete and then space duplicated the last name, and backspace multiplied the text. PR #5360 fixed it by moving the FEFF spacer after the mention. The PR says Gboard "sees the text before the cursor and tries to include that in the autocomplete" next to voids. Still open: #5183 (selecting an inline void does not summon the keyboard on Android) and #5680 (the keyboard hides when backspace removes an inline element). The keydown path runs `androidInputManager.handleKeyDown` first (`editable.tsx:1560`). | B, A |
| 5. Screen-reader ARIA | The editor is `role="textbox" aria-multiline` (`editable.tsx:1032-1033`), with user attributes spread after it (`:1035`). The example's portal and options carry no role or aria attributes (`mentions.tsx:139-173`; git grep for aria and role in the file found none). #2572 ("Let's make Slate accessible!", open) asks to put combobox aria on the contenteditable. | A, B |
| 6. Input rules inside the query | Not found. The mentions example installs only `withMentions`, `withReact` and `withHistory` (`mentions.tsx:52-55`). Markdown shortcuts is a separate example. | A |
| 7. Undo | `slate-history` merges consecutive `insert_text` ops, so the query is in history (`packages/slate-history/src/with-history.ts:129-151`). `set_selection` is not saved (`:157-163`). Undo therefore restores `@que` as selected text, and `onChange` does not reopen the list because the selection is not collapsed (inferred). | A |
| 8. Collaboration | Not found in the repo. There is no collaboration package. Because the query is document text, a CRDT binding would broadcast it (inferred). | A |
| 9. Keyboard | The editor keeps focus. Keys reach the menu through the `Editable onKeyDown` prop, which runs before Slate's default handling and suppresses it once `preventDefault` has been called (`mentions.tsx:61-90`, `:132-137`, `editable.tsx:1575-1578`). The click handler re-selects the stored `target` anyway and never refocuses the editor (inferred). | A |

## Pressure on Plate

All three editors put the query in ordinary document text, so none of them ships the input-in-inline-void design. The evidence on each side follows.

### For a transient native input inside an inline void

- **Key routing turns into cross-plugin coupling when the query is document text.** Lexical's menu competes in the editor command bus at priority LOW (`LexicalMenu.tsx:467-598`). Tables won arrows until `lexical-table` learned to sniff the root's `aria-controls === 'typeahead-menu'` (#5819 / PR #5820, `LexicalTableSelectionHelpers.ts:2499-2510`). The playground source says a bare `:` menu "would steal paragraph breaks" (`EmojiPickerPlugin/index.tsx:78-80`). Draft calls its own swap of key callbacks "a really nasty way" (`:583-586`). In Slate, keydown from a nested input skips the editor's handlers entirely (`dom-editor.ts:502-516`, `editable.tsx:1556-1559`). Grades A and B.
- **The query freezes during composition in every in-document design.** Lexical returns early while composing (`LexicalTypeaheadMenuPlugin.tsx:288-290`). Draft composition mode does not push state, and #2543, #1673 and #1431 show users who saw no suggestions until they typed a space. A native input's `value` and `input` events track the composing text, so filtering could follow it live (inferred, not tested). Grades A and B.
- **Document-wide transforms see the query.** Lexical markdown shortcuts and the playground emoji transform carry no typeahead guard (`MarkdownShortcuts.ts:540-599`, `EmojisExtension/index.ts:45-61`). An input keeps the query out of the transform pass. Grade A for the code, and the conflict itself is inferred.
- **Collaboration and history noise.** Peers see partial `@que` text, and undo of a completion restores the query. In Lexical the menu then reopens because the listener filters neither historic nor collaboration tags (`LexicalTypeaheadMenuPlugin.tsx:279-335`). A transient input keeps the session local and out of history. Grade A, behavior inferred.
- **Session lifetime is explicit.** In Lexical and Slate, Escape reopens on the next keystroke (`LexicalTypeaheadMenuPlugin.tsx:250-267`, `mentions.tsx:82-85`, inferred). Draft needed an `escapedSearch` memo keyed by decorator offset (`:965-970`). A mounted input's lifetime is the session. Grade A.
- **ARIA host.** The in-document designs either annotate the whole multiline document root as a combobox (Draft `:1056-1066`) or put `aria-activedescendant` and `aria-controls` on a `role=textbox` root (Lexical `LexicalMenu.tsx:386-398`, `:723-724`). A native input is a conventional single-line combobox host (inferred; the WAI-ARIA combobox pattern was not read this session).

### Against an input element (for ordinary text)

- **No surveyed editor does it.** Lexical (`getTextUpToAnchor`), Slate (`Editor.string` in `onChange`) and Draft (decorator range) all keep the query as text (A). Slate's only input-in-void precedent is a block void form with state outside the document (`editable-voids.tsx:76-100`, C).
- **A nested input makes the editor filter every bubbled event class from it.** Slate shipped composition filtering only in Oct 2025. Before that, Chinese IME in an input inside a void inserted the composed text at the editor's previous caret (#5840, fixed by PR #5965; `editable.tsx:1277`, `:1338`, `:1350`). Copy and cut have separate filters (`:1381`, `:1399`). Plate's beforeinput, keydown, selectionchange and paste paths would each need the same filter. Grades B and A.
- **Browser bugs around inputs in `contenteditable=false`.** Firefox broke arrow keys and typing (#1744, with the workaround of `contenteditable` on the input). Focus was stolen from inputs in voids (#2504). Chrome 127 reverted the selection when a click in a void made an input appear (#5791). All three are closed but show a regression-prone area. Grade B.
- **Focus transfer on Android.** Selecting an inline void does not summon the keyboard (#5183, open). Removing an inline element hides the keyboard (#5680, open). An input-in-void design moves focus into a void on trigger and back to the contenteditable on completion or cancel, which hits both paths (inferred applicability). Gboard's word-level autocomplete misreads text around voids (PR #5360). Grade B.
- **Composition at the trigger boundary.** With an input, the trigger character is typed into the contenteditable and the input must mount and take focus mid-typing. On IME and Android keyboards that can split or drop a composition in progress (inferred; no source tested this). The in-document designs avoid a focus change entirely.
- **Pointer handling is neutral.** Draft's mousedown `preventDefault` (`:387-397`) keeps focus without an input. Lexical relies on state-held selection and refocus (`LexicalSelection.ts:3901-3914`). Grade A.

### Side findings

- Lexical uses fixed DOM ids (`typeahead-menu`, `typeahead-item-<i>`) that collide across editors. Draft uses per-instance ids (`LexicalMenu.tsx:314`, `:723`; Draft `:565`, `:696`). Grade A.
- In Lexical, `if (isRangePositioned !== null)` compares a boolean to null, so it is always true and the positioning-failure branch is dead (`LexicalTypeaheadMenuPlugin.tsx:315-321`). Grade A.
- Lexical's `isSimpleText()` gate excludes TextNode subclasses from typeahead (#6269, open). Grades A and B.
