# Reviewer A: adversarial review of the local proof-lane synthesis

Scope: `arena/synthesis.md`, candidate-1 (`usage.md`, `sketch.ts`, `rationale.md`), `judge.md`, shards 003 to 009, checked read-only against the repository at `cf15725603` plus the working tree.

## Findings

### 1. [critical] The release gate cannot consume a locally produced receipt
**Location**: synthesis item 2 ("`check-plite-release-proof.mjs` stops duplicating device checks and calls the validator"); `tooling/scripts/check-plite-release-proof.mjs:39-44, 168-239, 242+, 646-676`; `.github/workflows/release.yml:187-190`
**Finding**: The raw-mobile lane is one lane in a release manifest that the checker accepts only from a GitHub Actions run: `PLITE_RELEASE_PROOF_EVENT = 'workflow_dispatch'`, workflow path `.github/workflows/plite-ci.yml`, repository `udecode/plate`, and exactly one `plite-release-proof` artifact, verified through the GitHub API. The design's producer is a laptop with an emulator or phone attached. No path in the synthesis moves the local bundle (JSON, five videos and per-step screenshots per receipt) into that CI artifact. AGENTS.md:44 says "Screenshots and run artifacts are never committed", so the bundle cannot travel through git. CI has no device, so it cannot produce the bundle either. The checker's lines 646-676 also read `lane.environment.devices[]`, a manifest summary, not a receipt bundle. "Calls the validator" therefore needs a new artifact pointer as well as a new code path. A smaller mismatch: the checker runs under `node` (v22 here), and the validator is extensionless TypeScript source that only Bun imports today (`mobile-device-proof.mjs` imports `packages/test/src/proof/index.ts` under Bun). The node checker would have to import the built `@platejs/test/proof` dist.
**Evidence**: `validatePliteReleaseProofRun` rejects any run whose `event` is not `workflow_dispatch` or whose workflow path differs. `resolvePliteReleaseProofArtifact` requires `total_count === 1`. Intent item: "receipt schema 2 for the raw-mobile release gate". As designed, schema 2 has no route into that gate.
**Suggestion**: Decide the producer authority for `raw-mobile` explicitly. Either pull `raw-mobile` out of the CI manifest into a separately signed local attestation with its own digest chain (a local `release-proof/raw-mobile` bundle checked by commit and digest, never by producer run), or state that the gate stays unreachable and do not build the gate rewiring yet (see finding 12).

### 2. [critical] The witness rule accepts CDP composition and CDP key events, and the bypass test checks neither
**Location**: synthesis item 1, Witness ("A character tap must produce a `keydown` with key `Unidentified` followed by `beforeinput`, or a composition event"); item 3 bypass test; `packages/test/src/playwright/ime.ts:9-38, 284-322`
**Finding**: Both branches of the rule can be forged by the input paths the lane exists to exclude:
- CDP `Input.imeSetComposition` fires trusted composition events with no keydown (shard 006 §3). That satisfies "or a composition event". It is the repository's own `composeText` path (`ime.ts:309-321`).
- CDP `Input.dispatchKeyEvent({ type: 'rawKeyDown', key: 'Unidentified', windowsVirtualKeyCode: 229 })` followed by `Input.insertText` gives a trusted `keydown Unidentified` and then a trusted `beforeinput insertText`. Shard 006 even proposes that exact sequence as its CDP fallback.
- The harness's own `enableCompositionKeyEvents` dispatches an untrusted `keydown` with `key: 'Unidentified'` at `compositionstart` (`ime.ts:24-35`). The rule does not require `isTrusted`, and `native-event-trace.ts` records neither `keydown` nor `isTrusted` today.

The bypass test replays only `adb shell input text` and bare `Input.insertText` (shard 009). Those are the two inputs the rule was designed around, so the test proves the rule matches its own examples. Re-running `judgeDeviceWitness` in the release validator cannot catch a deliberate bypass either, because the producer writes the JSON it judges.
**Evidence**: shard 009's table has no row for `imeSetComposition` or `dispatchKeyEvent`. The judge's "only design that closes ... the CDP `insertText` bypass" holds only for bare `insertText`.
**Suggestion**: Make the structural check the claim. Record the lane's CDP protocol traffic per run, either with a wrapped session or Playwright's protocol logger, and fail on any `Input.*` method. Add `imeSetComposition` and `dispatchKeyEvent(229)` rows to the device bypass test. Require `isTrusted` and, after a probe on Gboard Korean, a per-update `keydown 229` for compositions instead of "or a composition event". Describe the JSON re-check as a consistency check, not as bypass proof.

### 3. [critical] `updateCount` per scenario contradicts what real Gboard sends
**Location**: `packages/test/src/proof/raw-mobile-proof.ts:7-24, 254-266`; `tooling/plite/donor/proof/mobile-device-scenarios.json` (`autocapitalization`: "type one autocapitalized word", `updateCount: 1`); candidate-1 `validateRawMobileProof` TODO ("final snapshot updateCount matches RAW_MOBILE_SCENARIOS"); synthesis item 2
**Finding**: The validator fails any receipt whose final `updateCount` differs from the scenario constant. Shards 004 and 009 show English Gboard committing one `insertText` per letter. `. hello` in the autocapitalization case is 7 commits, not 1, and the new rows (autocorrect `cant`, space, `go`; `@bi` plus an option tap; a pending Korean word) are multi-commit by construction. The design also says `keyboard.type` "does not promise text" because the keyboard decides. A fixed commit count is the same promise in another form. Either every honest editing receipt fails, or the producer has to massage `updateCount`.
**Evidence**: The synthesis moves `requires` into data on `RAW_MOBILE_SCENARIOS` but never revisits `updateCount`. The candidate sketch keeps the check.
**Suggestion**: Drop the fixed count. Express each scenario's invariant as a predicate over the final snapshot, using the same `requires` data (for example "model text matches /\. Hello$/", "exactly one mention node"), and delete the `mobile-device-scenarios.json` duplicate, which has no code consumer.

### 4. [critical] The receipt reporter can mint proof from a flaky case
**Location**: candidate-1 `DeviceReceiptReporter` TODO ("for each key with >= 5 passed runs"); usage.md (`--repeat-each=1` as a CLI override); `.agents/rules/verify.mdc:52-55`
**Finding**: "At least 5 passed" is not "5 runs, all passed". `pnpm --filter plite test:device --repeat-each=10` with 7 passes and 3 failures writes a receipt. `retries: 0` lives only in the config, and the plain Playwright CLI accepts `--retries=2`. Unlike `apps/plite/scripts/plite-browser-runner.mjs:69-77`, nothing forbids the override, so retried passes can also count. verify.mdc:53-54 says "One failure keeps the case open."
**Evidence**: The reporter reads results from attachments keyed by (platform, scenario, identity). Nothing in the sketch or the synthesis inspects failed results or `result.retry`.
**Suggestion**: In `onEnd`, emit a receipt only when every result for the key passed, `retry === 0`, and the count is exactly the configured `repeatEach` (at least 5). Otherwise write an explicit refusal into the bundle log.

### 5. [critical] The native event trace is a 100-entry ring buffer, so order correlation and the audit both break
**Location**: `packages/test/src/playwright/native-event-trace.ts:25, 45, 377-383`; candidate-1 `createDeviceKeyboard` TODO ("n0 = trace length; ... poll trace until an event past n0"); candidate-1 `audit` (runs over the final trace)
**Finding**: The trace caps at `maxEntries ?? 100` and `splice`s the front. Once a run produces about 100 entries, `entries.length` stays constant. "Poll until length > n0" then waits 1500 ms and reports a false `keyboard-not-delivered`, or attributes the wrong events. A single letter tap with the planned `keydown` and `pointerdown` additions produces four to six entries (keydown, beforeinput, input, selectionchange or two), so roughly 20 taps fill the buffer. Worse, the end-of-run `audit`, the safety net for "what types cannot stop", sees only the last 100 entries. Unattributed input earlier in the run passes silently: the same fake-green shape the lane exists to remove.
**Evidence**: `pushEntry` trims to `innerMaxEntries`. Entries carry `timestamp: Date.now()` but no sequence number.
**Suggestion**: Give entries a monotonic `seq` and correlate on it. Drain the trace into the run recorder after every step instead of reading it once at the end. Either size the buffer per run, or fail the run when it overflows.

### 6. [warning] `connectOverCDP` applies Playwright's focus emulation by default
**Location**: synthesis item 1 ("stock Chrome ... no Chrome command-line switches"); shard 004 attach (`chromium.connectOverCDP('http://localhost:9333')`); playwright-core 1.61.0 `coreBundle.js:37045-37049`, `types.d.ts:23415-23426`
**Finding**: The fidelity case for the Android lane rests on running Chrome without automation overrides. Without `noDefaults: true`, Playwright still sends `Emulation.setFocusEmulationEnabled` to every main frame of the default context, and its media emulation applies as well (`noDefaults` "Defaults to `false`"). Shard 006 already found that `document.hasFocus()` lies under that emulation. Window-level focus and blur are exactly what D20 (#6022, keyboard dismissal and a jumping caret) and the focus-owner checks after each step are meant to observe. Shard 004's probe ran with the default, so its focus observations carry the override.
**Suggestion**: Attach with `noDefaults: true`, assert in `doctor` that it took effect (for example, `document.hasFocus()` turns false when the device is backgrounded), and rerun the shard 004 option-tap probe under it.

### 7. [warning] Suggestion-strip taps and `tapNative` break the lane's own "no UiAutomation during measured runs" rule and its witness
**Location**: synthesis item 1 ("never dumped during a measured run because the dump attaches UiAutomation"); item 3 ("a suggestion-strip tap over a partial word after a bold leaf"); candidate-1 rationale ("no suggestion-strip picking in v1"; "Only calibration and `tapNative` use `uiautomator dump`")
**Finding**: The words in the suggestion strip change on every keystroke, so tapping a named candidate means reading the strip during the run, which takes a dump (UiAutomation) or a screenshot OCR the design rejects. A suggestion tap is also not a key tap. It probably arrives as `insertReplacementText` or a composition commit with no `keydown Unidentified` (shard 005 grades it "Unknown"), so the per-run `audit` ("every insert `beforeinput` must sit in a keyboard step with the IME signature") flags it `unattributed-input`. The synthesis grafted this case from shard 005 while candidate-1 had explicitly excluded it, and nothing reconciles the two. `tapNative` has the same problem: by the design's own premise (P5, inferred), a mid-run dump can switch Chrome's renderer accessibility on for the remaining warm runs in that worker. Runs 2 to 5 then differ from run 1.
**Suggestion**: Either remove the suggestion case from Phase 2's keep/revert gate, or design a `keyboard.suggest(index)` step: fixed calibrated slot rects, a witness keyed to replacement input types, and a "UiAutomation attached" mark in the receipt. Restart Chrome, or quarantine the worker, after any `tapNative`.

### 8. [warning] Five repeats can split across devices when more than one is attached
**Location**: candidate-1 `defineDeviceConfig` TODO ("workers = attached device count"); `openDeviceSession` ("serial = sortedSerials[workerInfo.parallelIndex]"); reporter keyed by identity digest
**Finding**: Playwright schedules each `repeatEach` repetition as its own unit and spreads units over workers. With an emulator and a phone attached, a case's five repeats can land 3 on one device and 2 on the other. Neither identity then reaches five runs, and no receipt is written, silently in the gate's eyes (`missing`). Emulator and physical evidence also mix within a single command.
**Suggestion**: Make one Playwright project per attached serial, each pinned to its device and to one worker, instead of one worker per device in a shared project.

### 9. [warning] The CSS-to-screen mapping for content touches is gone from the synthesis
**Location**: synthesis item 1 (`touch.tap | press | drag(target)` on model points, handles, test ids, roles and selectors); candidate-1 `ScreenTransform` and `toScreen` (a per-navigation overlay calibration tap); candidate-1 probe P3 (unrun); judge graft "Split `resolveTextOffsetPoint` out of `clickTextOffset`" (dropped)
**Finding**: Every content touch has to turn a CSS point into a screen pixel while Chrome's toolbar and the keyboard resize the viewport. The synthesis keeps the API and drops both the mechanism and the graft that owns "where is model point P". Candidate-1's mechanism injects an overlay into the page under test and absorbs a tap on every run. It depends on P3: does `preventDefault` on `pointerdown`/`touchstart` leave focus and the keyboard alone? Nobody probed that. Shard 009 settled only the key map.
**Suggestion**: Bring the `resolveTextOffsetPoint` graft back. Check every content touch with the touch witness: record the page-side `touchstart` `clientX/clientY`, compare it with the intended CSS point, and fail beyond a few pixels. Then any transform source fails closed and no overlay tap is needed. Make P3, or its replacement, a Phase 2 entry probe.

### 10. [warning] Device preflight and restore do not survive a crash, and they change contributors' own phones
**Location**: candidate-1 `DeviceRestoreToken` (an in-memory `Map`), `openDeviceSession` ("Running setup twice converges"); synthesis graft "Gboard settings are set by the setup command and read back"
**Finding**: The originals live only in the worker's memory. After a crash or a Ctrl-C between preflight and teardown, the next preflight records animation scale 0, locked rotation and stay-awake as the "originals" and later restores the phone to those test values. That converges, but to the wrong state on a personal phone. Gboard settings changed through accessibility automation (personalized suggestions off, extra languages) have no restore path in the design at all. The macOS lane has the same shape: a killed worker skips the `finally` that reselects U.S., which leaves the owner's system input source on Pinyin.
**Suggestion**: Persist the first-seen originals per serial, or per host for TIS, under the cache directory. Never overwrite an existing token. Have `doctor` restore a stale token before preflight. List every Gboard setting change in the receipt, and restore it in `plate-device setup --undo`.

### 11. [warning] No cross-process lock on a device, the bundle or the HID input stream
**Location**: candidate-1 rationale decision 6 ("Each worker owns one device ... No locks"); reporter ("read the existing bundle, replace ..., write once")
**Finding**: This repository routinely has several agent sessions working in one checkout (AGENTS.md: "When `git status` shows work the task did not write..."), and `verify` is named as a runner. Two `test:device` processes on the same serial interleave taps. Two reporters doing read-modify-write on one bundle path lose updates. Two macOS IME runs post HID keys into each other's Chrome. The harness already has a precedent for this in `withExclusiveClipboardAccess`.
**Suggestion**: Take an exclusive lock file per adb serial and one per host for the HID and TIS lanes. Write the bundle through a temporary file and an atomic rename.

### 12. [warning] Receipt schema 2 and the gate rewiring are built before anything can satisfy them
**Location**: synthesis item 2, Phase 2; "The release gate's `ok` stays physical-only on both platforms"; item 10 (iOS deferred to Phase 3 "behind a probe")
**Finding**: `ok` needs physical receipts for every scenario on both Android and iOS. Phase 2 has an emulator, no phone (Open risks), and no iOS. Phase 3's iOS path is a simulator (`connectHardwareKeyboard: false`), and iOS physical signing through WDA is not in the open risks. So the reporter, schema 2, coverage cells, bundle merging, the scenario revision and the checker rewiring all ship in Phase 2 and produce nothing the gate can accept. The Android gates Phase 2 targets (D20, G02, G03) need pass and fail across five warm runs, which Playwright's own results already provide.
**Suggestion**: The cut: Phase 2 ships the device fixture, the witness, the six cases and the bypass test, with Playwright results as the proof. Move schema 2, the reporter and the gate changes to a phase that starts when a physical phone and an iOS producer exist. That removes `reporter.ts`, the bundle-merge logic and the checker rewrite from Phase 2. This applies the synthesis's own subtract-before-you-add rule to its receipt layer.

### 13. [warning] A published `@platejs/test/device` entry and `plate-device` bin for a maintainer-only lane
**Location**: synthesis item 1; `packages/test/package.json` (public, `54.0.0-beta.0`, `sideEffects: false`, an optional `@playwright/test` peer)
**Finding**: The synthesis puts adb plumbing, emulator setup, Gboard settings automation and device-settings mutation into a published package's public surface. That means semver, docs and support for external users. The evidence names no external job for it: every gate in shard 003 belongs to Plate itself. AGENTS.md's redesign rule requires every public noun and package entry to earn its place against "a proven independent current user job."

### 14. [warning] "Stand-ins fail loudly" covers one of three silent fallback branches and adds a second labeling system
**Location**: synthesis item 4; `packages/test/src/playwright/harness-input.ts:114-209`; `clipboard.ts:143-164`; `types.ts:733-745`, `scenario-replay.ts:1124-1154`
**Finding**: `pasteText` and `pasteHtml` fall back silently in three places. (a) When the clipboard write throws, they go to `insertDataThroughHandle`, which is the normal case off Chromium, since only Chromium grants clipboard permission (verify.mdc:275). (b) `pasteHtml` skips native paste entirely and dispatches a synthetic event on WebKit and on mobile emulation (`requiresSyntheticHtmlPasteTransport`). (c) The synthetic path also runs when native paste "changed nothing". The design throws only in (c), so the Firefox, WebKit and Pixel 5 projects keep silent stand-ins. `{ transport: 'handle' }` also misnames branch (c) for `pasteHtml`, which uses a synthetic `ClipboardEvent`, not the handle. "Labeled in the trace, and proof assertions reject labeled steps" names neither the trace (kernel trace? native trace? scenario replay?) nor which assertions count as "proof". `selection.select` and `collapse` appear 454 times as legitimate setup, so a broad reading breaks the suites and a narrow reading does nothing. Meanwhile `BrowserTransportClaim` and `classifyScenarioTransportClaim` already exist as the transport-labeling owner, as self-declared strings.
**Suggestion**: The simpler move: delete the fallbacks and make each stand-in its own verb (`pasteTextThroughHandle`, `pasteHtmlThroughEvent`, `pressSynthetic`), so the call site names its transport and no label-and-reject machinery is needed. Retire `classifyScenarioTransportClaim`'s string sniffing in favor of the verb that was actually called.

### 15. [warning] A blanket `caret: 'initial'` breaks the existing differential pixel classifiers and blinks on non-Chromium engines
**Location**: synthesis item 5 ("Pixel and caret assertions pass `caret: 'initial'` and set CSS `caret-animation: manual`"); `apps/www/tests/browser/code-block-selection.spec.ts:21-25`, `link-floating-toolbar.spec.ts:27-30`, `comment.spec.ts:401`, `suggestion.spec.ts:37`
**Finding**: Those classifiers diff two captures and pass `caret: 'hide'` deliberately, so a caret column does not count as a changed pixel. Turning the caret on for "pixel assertions" adds caret pixels to every one of them. Shard 006 verified `caret-animation: manual` only on Chromium 149 and Chrome 154. Playwright's Firefox and WebKit builds are unverified, and that spot is where a visible caret turns blink into flake. Item 5 also omits the positive, negative and duplicate controls that `regression-oracles.md:471-484` requires before any caret-paint claim. Shard 006 specified them.
**Suggestion**: Scope item 5 to caret-paint assertions only. Make it a helper that sets both options together, refuses engines without `caret-animation`, and runs the three controls.

### 16. [warning] The page-handle opt-in has a wider blast radius than Phase 1's keep/revert check
**Location**: synthesis item 6 and Phase 1 ("keep or revert by its focused tests and one Plite and one www browser run"); shard 007 §6
**Finding**: Handle readers outside apps/plite and www drive their own pages: `packages/platejs/scripts/code-block-text-flow-browser.mjs` (routes `http://plate-benchmark.local/`), `packages/plitejs/benchmarks/react-text-flow-browser-matrix.mjs`, `benchmarks/editor/benchmarks/plate-code-block-browser.mjs`, `plite-external-text-entry.mjs`, `benchmarks/slate-v2/donor/browser/react/*.mjs`, `apps/www/scripts/run-homepage-input-perf.mts` and `tooling/e2e/node-selection.test.ts` (from `git grep --untracked -l`). Each needs its own install call, or it breaks, and one Plite run plus one www run would not notice. The item exists to save production bytes, yet the keep/revert gate omits shard 007's bundle measurement (`__pliteBrowserHandle` should show 0 hits). The install-timing contract is also unspecified. `useRuntimeBrowserHandle`'s layout effect has 12 dependencies and none of them is the registry, so an `installBrowserHandle()` that runs in a root component's effect runs after the children's layout effects and never attaches on the first mount.
**Suggestion**: List every reader in the plan. Make the gate include the bundle measurement. Specify module-top-level installation, or have the hook subscribe to the registry.

### 17. [warning] Narrowing the Pixel 5 project removes the only mounted-editor coverage of Plite's Android input path
**Location**: synthesis item 8; `packages/plitejs/src/dom/utils/environment.ts:85-89` (`platform = isAndroid ? 'android'` from `ANDROID_USER_AGENT_RE.test(userAgent)`); `.agents/rules/verify.mdc:314`

### 18. [warning] The www suite as a pre-PR gate breaks serving-source identity, and its budget is unknown
**Location**: synthesis item 9; `apps/www/playwright.config.ts:40-48` (`reuseExistingServer: true`, port 3000, `workers: 1`, `fullyParallel: false`); `apps/www/package.json:35-37`; `.agents/rules/verify.mdc:182-184`
**Finding**: The local commands already exist (`test:www-browser:chromium|firefox|webkit`), so the only new part of item 9 is the gate, and the gate is unspecified: which projects, which specs, inside `pnpm check` or beside it? `reuseExistingServer: true` on :3000 silently runs the suite against whatever server holds the port. Shard 004's probe used another session's dev server, and verify.mdc forbids reusing "ports or source paths from another checkout." The suite is serial with 295 tests per project and an unrecorded wall time (shard 003), which conflicts with the "no hours of end-to-end suites" constraint. The device receipts share the identity gap: `build.commit` comes from the runner's `git HEAD`, not from the served artifact.
**Suggestion**: Use a dedicated port with `reuseExistingServer: false`, or check the server's build identity. Run Chromium only, choose specs with an affected-file planner like `check-plite.mjs dev`, measure one full run before calling it a gate, and stamp a served-build id into each device receipt.

### 19. [warning] The macOS IME lane is sequenced last, posts HID events with a TOCTOU gap, and holds the Android lane to a stricter Chrome standard
**Location**: synthesis item 7 and Phase 3; shard 006 §2 and §7; playwright-core `coreBundle.js:34433-34470, 42529`
**Finding**: (a) Sequencing. G01 and #5137 are the cheapest open gate and block a live PR (shard 003: "G01 ... is the cheapest to close"). The lane shares only the `keydown`/`isTrusted` trace extension with the Android work, yet it waits behind all of Phase 2. (b) The helper checks the frontmost pid and then posts with `CGEventPost(kCGHIDEventTap)`, which goes to whatever app is frontmost when the event is delivered. A notification or a user click in between types Pinyin into another app, possibly the owner's own Chrome (same bundle). `CGEventPostToPid` was not considered. (c) The Android rationale rejects `_android.launchBrowser` because of Playwright's automation switches (`--allow-pre-commit-input`, `--disable-field-trial-config`). The macOS lane uses Playwright's desktop launch with `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`, which applies the same `chromiumSwitches()` list (`coreBundle.js:42529`). That list includes `--disable-backgrounding-occluded-windows` and `--disable-renderer-backgrounding`, which bear on the activation and paint claim.
**Suggestion**: Move item 7 into Phase 1 next to the trace extension. Probe `CGEventPostToPid` for IMK routing. Apply one fidelity rule to both lanes: either launch user-equivalent Chrome with `--remote-debugging-port` and a dedicated profile and attach with `noDefaults`, or drop the switch argument from the Android rationale.

### 20. [warning] The scenario-list revision is not a list, and Android evidence is applied to iOS
**Location**: synthesis item 2 ("keep 7, merge 6, split `composition-ime` into three, drop the two swipe rows, and add rows for marks, suggestion taps, autocorrect, triggers and pending input"); shard 005 §3-4
**Finding**: In shard 005, the three-way split of `composition-ime` is S1, S6 and S7. The "add rows" list names S6 (triggers) and S7 (pending input) again, so they are counted twice. ### 21. [warning] One bundle file per platform conflicts with a single-file validator and gate
**Location**: synthesis graft ("there is one bundle file per platform"); `tooling/plite/donor/proof/mobile-device-proof.mjs` (reads one `test-results/release-proof/mobile-device-proof.json`); `raw-mobile-proof.ts:285-296` (requires both platforms in one bundle)

### 22. [nit] `bootId` does not prove the runs were warm
**Location**: synthesis graft ("`bootId` proves the runs were warm")
**Finding**: `boot_id` stays the same when Chrome restarts, and a restored quick-boot snapshot (`plate-device-ready`) brings back the boot id from snapshot time. So it cannot tell one session from the next, or a warm tab from a cold browser.

### 23. [nit] The device-kind unions disagree

### 24. [nit] The bypass test needs a hidden back door that the design does not define
**Location**: synthesis item 3 ("the witness must fail ... a CDP `Input.insertText` step on the device"); item 1 ("The built-in `page`, `context` and `browser` fixtures throw")
**Finding**: With `page` throwing and no CDP access in `DeviceEditor`, the bypass test cannot send `Input.insertText` unless the lane exposes an internal escape hatch. Left undefined, that hatch tends to leak into the public fixture.
**Suggestion**: Name an internal-only module, outside the `device` entry's exports, that the bypass test imports, and add a lint rule that bans it from `*.device.test.ts` outside that one file.
