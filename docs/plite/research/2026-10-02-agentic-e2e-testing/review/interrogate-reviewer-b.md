# Reviewer B findings: local proof-lane synthesis

Scope read: `arena/synthesis.md`, `arena/judge.md`, `arena/task.md`, `candidate-1/{usage.md,sketch.ts,rationale.md,notes.md}`, shards 003, 004, 005, 006, 007 and 009, and the repository files the brief names. Everything was read-only. Line numbers are from the current worktree.

## Findings

### 1. [critical] Schema 2 receipts cannot reach the release gate the design says they feed
**Location**: synthesis item 2 ("`check-plite-release-proof.mjs` stops duplicating device checks and calls the validator"); `tooling/scripts/check-plite-release-proof.mjs:22-43, 457-511, 646-676, 800-897`; `.agents/rules/release-lanes.mdc:61-70`; `docs/plans/2026-08-22-bind-plite-release-proof-to-source.md:68`
**Finding**: The design treats the receipt validator and the release gate as one owner, with duplicated checks. They are two different gates that read two different documents, and the real release gate accepts evidence only from GitHub Actions.
- `check-plite-release-proof.mjs` never parses receipts. It downloads one `plite-release-proof` artifact from a successful `workflow_dispatch` run of `.github/workflows/plite-ci.yml` in `udecode/plate`, through the GitHub API (`:39-43`, `:457-511`, `:863-866`). It then checks a lane manifest whose `raw-mobile` entry carries `environment.devices[]` with flat `deviceName` and `browserName` fields (`:646-676`). This is not the receipt shape, so "calls the validator instead" has nothing to call it on.
- `release-lanes.mdc:61` says the verifier "reads no caller-local manifest". `:69-70` says "accepting an operator-supplied manifest would recreate the fake authority this gate rejects". The bind-to-source plan says "a caller-provided `passed: true`, transport label, or nonempty commit is not release evidence" (`:68`).
- A local device lane produces exactly an operator-supplied bundle. `device.kind` "read from `getprop`" is still a field in JSON written on the operator's machine. Running `judgeDeviceWitness` again in the validator checks only that the JSON is internally consistent. It proves nothing about where the JSON came from.

So the stated intent, "receipt schema 2 for the raw-mobile release gate", has no path into `pnpm release` (`package.json:89`, run from `release.yml:187`). The owner's no-new-minutes constraint, read together with the existing provenance law, makes the design self-contradictory as written.
**Evidence**: Trace `run()`: `verifyPliteReleaseProofProducer` (GitHub run, workflow, artifact), then `downloadPliteReleaseProofBundle`, then `validatePliteReleaseProofManifest`, then `verifyPliteReleaseProofArtifacts`. No call reaches `validateRawMobileProof`. The only consumer of the receipt bundle is `tooling/plite/donor/proof/mobile-device-proof.mjs:95-103`, a separate local command (`test:mobile-device-proof:raw`).
**Suggestion**: Make the trust model an explicit decision in the plan before Phase 2. One option is to split raw-mobile out of the GitHub-produced `release-ready` manifest into its own commit-bound local claim profile. That rewrites `release-lanes.mdc` and the bind-to-source law and names the operator as the attesting party. The other option keeps the law and uses a self-hosted runner on the owner's machine, with the device attached, as the `workflow_dispatch` producer for that one lane. Self-hosted jobs consume no GitHub-hosted Actions minutes. Either way, delete the "stops duplicating device checks" claim, because the two checks validate different documents.

### 2. [critical] The suggestion-strip case and `tapNative` contradict the lane's own no-UiAutomation rule, and nothing in the API can drive them
**Location**: synthesis item 1 ("never dumped during a measured run because the dump attaches UiAutomation"), item 3 ("a suggestion-strip tap over a partial word after a bold leaf"), item 2 (new receipt rows for "suggestion taps" and "autocorrect"); candidate-1 `rationale.md` decision 2 ("Only calibration and `tapNative` use `uiautomator dump`") and "What it does not do: … no suggestion-strip picking in v1"; `sketch.ts:311-312`
**Finding**: The synthesis adopts shard 005's case 2 and a "suggestion taps" receipt row from a base design that excluded suggestion picking on purpose. It adds no mechanism to replace it.
- Suggestion candidates are dynamic Gboard-window content, so a cached key map cannot hold them.
- The only verb that reaches native UI is `device.tapNative(label)`. It needs a live `uiautomator dump`, which attaches UiAutomation in the middle of a measured run. That is what item 1 forbids.
- The witness has no rule for a candidate tap. A candidate tap is neither a `keys` step nor a page `touch`. Its delivery is a multi-character `insertText` or `insertReplacementText` with no single planned key. So `classifyTap` returns `keyboard-plan-diverged`, or `audit` returns `unattributed-input` (`sketch.ts:406-416, 512-524`).

As specified, first-slice case 2 is not implementable without breaking the fidelity rule the calibration subsystem exists to protect.
**Evidence**: `DeviceKeyboard` exposes only `type`, `tap`, `use` and `shown` (`sketch.ts:266-280`). `DeviceStep` has no candidate variant (`:128-140`). `KeyDelivery` has no replacement variant (`:118-125`).
**Suggestion**: Either drop case 2 and the "suggestion taps" row from the first slice, or add a first-class `device.keyboard.pick(candidate)` step with its own witness rule. Then decide openly whether a live dump during that step is acceptable, which depends on finding 6.

### 3. [critical] Correlating taps by trace length breaks on the existing trace's 100-entry ring buffer and on event ordering
**Location**: `sketch.ts:526-535` (`n0 = trace length; android.touch(tap); poll trace until an event past n0 or 1500 ms; classifyTap`), `:406-416` (`audit` windows by step); `packages/test/src/playwright/native-event-trace.ts:25, 45, 377-381, 438-440`
**Finding**: The lane reuses `startBrowserNativeEventTrace`, which keeps at most `maxEntries` (default 100) and trims the front with `entries.splice(0, entries.length - innerMaxEntries)`. That causes three failures.
- Once a run passes about 100 entries, the length stops growing. Every later tap then times out as a false `keyboard-not-delivered`, or is matched to the wrong entries. Each tap records `keydown`, `beforeinput`, `input` and one or more `selectionchange` events, so a Korean composition case or the mention-plus-backspace case gets there quickly.
- The poll returns on the first new entry. The first entry of a Gboard tap is `keydown Unidentified`, so `classifyTap` sees a keydown with no `beforeinput`. That reads as not delivered, even though the witness rule needs keydown followed by `beforeinput`. The tap's own `input` and its `selectionchange` (recorded on `document`, `:440`) then land past the next tap's `n0` and are charged to the next tap.
- `audit` defines step windows by index. After a trim, indices shift, and early unattributed input that was dropped is never audited. The audit passes vacuously for that prefix.

On a no-retry, five-run lane this is either flake that never passes, or a witness that sees less than it claims.
**Evidence**: The ring buffer is at `native-event-trace.ts:377-381`. The sketch's "Correlation is by order, not clocks" is the judge's determinism justification (`judge.md`, candidate-1 Determinism 3).
**Suggestion**: Give each trace entry a monotonic `seq` and correlate by `seq`, never by array length. Make the lane's trace unbounded per run, or fail loudly on overflow. End each tap window on a terminal event (`input` after `beforeinput`, or a composition event) plus a short quiet period. Exclude `selectionchange` from the delivery match.

### 4. [warning] Four parallel claim vocabularies, and "fail loud" covers only one of three paste fallbacks
**Location**: synthesis item 4; `packages/test/src/playwright/harness-input.ts:114-191`; `types.ts:733-745` (`BrowserTransportClaim`), `scenario-replay.ts:1124-1164` (`classifyScenarioTransportClaim`); `proof/mobile-transport-proof.ts:4-103`; the new witness and receipt `transport`
**Finding**: Proof strength is already labeled three ways, and the design adds a fourth.
- `BrowserTransportClaim` is a caller-declared string, classified by substring sniffing (`normalized.includes('handle')`).
- `BrowserMobileTransportId` and its capability matrix list `human-soft-keyboard` as unsupported for every transport (`:42-47`). That contradicts the new lane outright, and the synthesis never says what happens to the matrix. `mobile-device-proof.mjs:104-145`, the non-raw branch, becomes a tautology once the Appium ids go. The public exports `classifyBrowserMobileTransportProof`, `getBrowserMobileTransportProofMatrix`, `extractAppiumDebugSnapshot` and `parseAgentBrowserBatch` are pinned in `packages/test/test/proof/package-scripts.test.ts:19-35` and `packages/platejs/test/public-package-import-smoke.slow.ts:169-185`.
- Item 4 adds trace labels plus "proof assertions reject labeled steps". No such notion exists in the harness, and the design names no trace and no assertion.
- The witness and receipt `transport` would be the fourth.

Item 4 itself is half done. `pasteText` and `pasteHtml` fall back in three places: `writeClipboardText` throws and the handle is used (`:126-131`), `shouldUseSyntheticHtmlPaste` sends a synthetic event (`:167-170`), and a native paste changes nothing (`:151-153, 191`). Item 4 covers only the third. On Firefox and WebKit, where automation gets no clipboard permission (`verify.mdc:275-277`), the first branch fires before any check, so those engines stay silently stand-in. `{ transport: 'handle' }` also misnames the `pasteHtml` fallback, which is a synthetic paste event, not a handle write. It also clashes with the harness's existing `transport?: 'native' | 'synthetic'` (`types.ts:890, 1101, 1420`). Labeling setters also misses the worst leak shard 007 found. A handle `selectRange` leaves `modelSelectionPreference.reason = 'browser-handle'`, so the next real `page.keyboard.type` runs as model-owned input (`selection-controller.ts:683-712`, inferred in the shard). The labeled step is the setter, but the contaminated step is the native one after it, and that one looks like proof.
**Suggestion**: The simplification is to derive claims from observed evidence, not declared strings. The native trace, with `seq`, `isTrusted`, keydown `key` and `keyCode`, plus the kernel trace's existing `browser-handle` origin and `nativeAllowed: false` (shard 007, `browser-handle.ts` `runCommand`), already holds what is needed. One pure judge maps a step's evidence to a claim for desktop, Android and macOS alike. Delete `classifyScenarioTransportClaim`'s substring sniffing and the `BrowserMobileTransport*` capability matrix in the same wave, update the two pinned export lists, and give all three paste fallbacks one explicit opt-in such as `fallback: 'synthetic-event' | 'handle'`. Then flag a native step that follows a handle-set selection.

### 5. [warning] A CDP attach is not neutral: Playwright turns on focus and media emulation unless told not to
**Location**: synthesis item 1 ("stock Chrome … `chromium.connectOverCDP` (no Chrome command-line switches)"); `playwright-core@1.61.0/types/types.d.ts:23413-23426`; `lib/coreBundle.js:37045-37049`; shard 004 Setup
**Finding**: The fidelity argument, rated 3 by the judge, counts only command-line switches. By default, `connectOverCDP` applies `Emulation.setFocusEmulationEnabled` to every attached main frame and applies Playwright's media emulation defaults, `reducedMotion` and `colorScheme` among them. The public option `noDefaults: true` disables both for the default context ("focus emulation is not enabled, and media emulation options … are not applied"). Shard 004 and shard 009 attached with plain `connectOverCDP('http://localhost:9333')`, so the prior evidence ran with focus emulation on. Case #6022 is about keyboard dismissal and caret jumps after a toolbar tap, which is focus behavior. Case D15 showed that motion preference changes outcomes. Under focus emulation, `document.hasFocus()` and window focus events lie (shard 006, `coreBundle.js:37049`).
**Suggestion**: Attach with `connectOverCDP(endpoint, { noDefaults: true })`, use only the default context (never `browser.newContext()`, which reapplies the overrides and a 1280x720 viewport), and record the attach options in the receipt identity.

### 6. [warning] The calibration subsystem rests on an unmeasured premise, and the design applies that premise inconsistently
**Location**: synthesis item 1 (key map cached, "never dumped during a measured run"); candidate-1 `notes.md` P5 ("inferred … It justifies keeping UiAutomation out of runs"); synthesis item 10 (iOS through Appium XCUITest)
**Finding**: The fingerprint cache, `keyboard-layout-stale`, layer `after` learning and the absorbed calibration tap all exist to avoid UiAutomation during runs, and the effect of UiAutomation on Chrome was never measured. Three things weaken it.
- If the premise holds, `calibrateKeyboard` runs `uiautomator dump` in the same Chrome session that later runs the measured cases (`sketch.ts:537-547`). Whether Chrome turns its renderer accessibility off again after the client disconnects is also unmeasured, so the protection may already be gone.
- Phase 3 accepts XCTest, which is accessibility-driven, attached for the whole iOS run. If the concern is real, it applies to WebKit too. If it is not, the Android machinery is pure cost.
- A live dump per keyboard step would handle Gboard updates, the suggestion strip (finding 2) and native menus with no cache at all.
**Suggestion**: Measure P5 before writing package code. Compare Chrome's accessibility state, using `dumpsys accessibility` and a page-side probe, with and without a dump, and compare event traces for the same taps. If it makes no difference, delete the calibration cache, the fingerprinting and the stale-layout failure, and read the IME window live. If it does make a difference, calibrate in a separate Chrome session and restart Chrome before measured runs.

### 7. [warning] The reporter mints a receipt from "at least five passed runs", which ignores failures
**Location**: `sketch.ts:606-615` ("for each key with >= 5 passed runs … build the receipt"); `verify.mdc:52-55`
**Finding**: `--repeat-each=8` with two failures leaves six passes, so the reporter writes a receipt. The verify law says "One failure keeps the case open." The receipt keeps only passing runs (`AtLeastFive<RawMobileRun>`), so the bundle cannot even show that a failure happened.

### 12. [warning] The visible-caret item has no owner in `@platejs/test`, a false premise and a Chromium-only stabilizer
**Location**: synthesis item 5; `apps/www/tests/browser/code-block-selection.spec.ts:20-25`; `suggestion.spec.ts:455, 591, 1656, 1741, 2019, 2162`; `tooling/e2e/font-size-selection.test.ts:210, 378`; `packages/test/src/playwright/caret-visibility.ts`
**Finding**: "Playwright's default `caret: 'hide'` is why no repository pixel check ever saw a caret" is false. The repository already passes `caret: 'initial'` eight times. The remaining `caret: 'hide'` uses are deliberate. The code-block and table classifiers compare selection-highlight pixels and hide the caret so blinking cannot add noise. `@platejs/test` has no pixel assertion. `caret-visibility.ts` is DOM geometry. So "pixel and caret assertions pass `caret: 'initial'`" names no owner, and applying it across the board would break the classifiers that hide the caret on purpose. `caret-animation: manual` was measured only on Chromium 149 and Chrome 154 (shard 006). It is inferred to be ignored on Firefox and WebKit, where captures would keep blinking.
**Suggestion**: Scope this item to caret claims. Add one harness capture helper that sets `caret: 'initial'`, adds `caret-animation: manual` on Chromium, and falls back to a burst capture with a union check on other engines. Use it only where a caret is the claim. Leave the selection classifiers alone.

### 13. [warning] The handle installer's caller list is incomplete, and its ordering and external break are unstated
**Location**: synthesis item 6 ("apps/plite, www and the Plite contract test call it"); shard 007 section 1
**Finding**: Drivers outside apps/plite and www read the handle. Three of them build their own pages and would fail with "Missing Plite browser handle": `benchmarks/slate-v2/donor/browser/react/huge-document-browser-trace.mjs` (its own `createServer`), `packages/platejs/scripts/code-block-text-flow-browser.mjs` (route-fulfilled `plate-benchmark.local`) and `packages/plitejs/benchmarks/react-text-flow-browser-matrix.mjs`. Three more read it from pages I did not trace: `benchmarks/editor/benchmarks/plate-code-block-browser.mjs` (`localhost:3100`), `plite-external-text-entry.mjs` and `cross-editor-adapters.mjs`. Three `packages/plitejs/test/react` files read the handle, not one. External `@platejs/test/playwright` users, taught in `15-editing-behavior.mdx`, break at `openExample`'s ready gate. That needs a changeset, docs and a clear error. Install order also matters. Child layout effects run before parent effects, so an install inside a root component's effect misses the first `Editable` mount, and the 12-dependency effect may never rerun. Install has to be a module-scope call. Moving trace retention behind the installer changes per-event production work, which changes the baselines the benchmark methodology rebuilds for (`benchmark/references/methodology.md:126-129`).
**Suggestion**: List every page-building driver as a migration site. Make `installBrowserHandle()` idempotent and module-scope, and have the ready gate throw "handle not installed". Add the changeset and docs line. Rebaseline the affected benchmarks in the same slice.

### 14. [warning] The macOS lane is a second native lane with its own witness rule, no receipt and no crash recovery
**Location**: synthesis item 7; shard 006 sections 6-7
**Finding**: The Android witness lives in `@platejs/test/proof` (`judgeDeviceWitness`). The macOS rule ("trusted `keydown` keyCode 229 between composition events") is an ad hoc spec assertion. Its home is shard 006's `homepage-native-ime.spec.ts` plus a Swift helper compiled into a cache. That gives two native-delivery judges with two shapes, and the desktop OS-IME claim has no receipt. `TISSelectInputSource` changes the user's input source for the whole system. Shard 006 restores it in a `finally`, but a SIGKILL, a worker crash or Ctrl-C skips the `finally` and leaves the owner's Mac on Pinyin. The frontmost-pid check before each key also leaves a race window before the post.
**Suggestion**: Use one witness judge with a per-platform signature table: Android Gboard `keydown key 'Unidentified'`, macOS IMK `keyCode 229, isComposing`. Both lanes should call it. Have the helper restore U.S. on startup as well as in `finally`, the same restore-token pattern as the Android preflight.

### 15. [warning] Witness gaps: Enter and Backspace bypasses pass, and `isTrusted` is dropped
**Location**: `sketch.ts:96-108` (`DeliveredEvent` has no `isTrusted`), `:189-194` ("Enter and Backspace … need only the beforeinput"); synthesis item 3 bypass test
**Finding**: Because Enter and Backspace need only `beforeinput`, `adb shell input keyevent KEYCODE_ENTER` cannot be told apart from a Gboard Enter tap. Those keys back the `enter` and `backspace` receipt rows. The bypass test covers only `input text` and CDP `Input.insertText`. `DeliveredEvent` drops `isTrusted` even though the sketch adds it to trace entries (`:232-236`). An untrusted `KeyboardEvent('keydown', { key: 'Unidentified' })` from page or app code inside a keys window, followed by a text insert, satisfies the rule.
**Suggestion**: Require `isTrusted: true` on every witnessed event. For Enter and Backspace, require the IME's signature as observed in calibration. Gboard's Enter may arrive as `keydown key 'Enter'`, while `input keyevent` may differ in `keyCode`, `code` or repeat fields. This needs measuring. Add `input keyevent` to the bypass test.

### 20. [nit] `plate-device setup` ships machine provisioning in a published library
