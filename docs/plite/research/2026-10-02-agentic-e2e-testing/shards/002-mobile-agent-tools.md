## Pressure on Plate

**(a) Gboard composition on Chrome Android at /blocks/mention-demo, then a tap on an option.** No tool's text command can produce it. agent-device commits text through its test IME or sends `input text` key events (A, text-input.ts:45-67, TestInputMethodService.java:139). argent, MiniSim and e2e use `input text` or agent-device (A). The one credible route is real touches on Gboard's own keys. agent-device with `open --no-test-ime` keeps Gboard, its snapshot includes the IME window (A, AccessibilityTreeCapture.java:104-124), and `press x y` injects a real touch there (A, input-actions.ts:34). argent's `gesture-tap` does the same through simulator-server (A). Typing a word key by key that way should make Gboard drive `setComposingText`, and the option tap is another real touch while the word is still composing. That is inferred, not run (D). Neither tool can read the editor model in Chrome. Plate's own playwright-core 1.61.0 can. `_android.devices()` then `device.launchBrowser()` gives a Chrome-for-Android `BrowserContext` whose `page.evaluate` reads the model through the existing harness, and `device.input.tap(point)` injects device touches (A for the API, playwright-core@1.61.0 types/types.d.ts:22035-22110, 23106-23117; it is marked experimental and needs "Enable command line on non-rooted devices" in chrome://flags). A run counts as proof only if the page records `compositionstart` and `compositionupdate` from Gboard before the tap, so the harness must log composition events, not just the final value.

**(b) iOS Safari typing with autocorrect.** agent-device and argent can open the page in Safari on a simulator (A). Their text paths are XCUITest `typeText` plus a private synthesizer (agent-device) and HID key presses (argent). Whether either triggers autocorrect replacement is not settled by any source I read (D); argent's hardware-key path probably skips the predictive bar (D). The higher-fidelity route is again tapping the on-screen keyboard's keys with real touches through agent-device `press` or argent `gesture-tap`, which needs the software keyboard visible (agent-device commands.md:509 shows the runner depends on it). The blocker is the oracle. No tool reads Safari page JavaScript (A by grep across all five). Plate would add either a WebKit remote-inspector client for the simulator (Appium remote debugger, ios-webkit-debug-proxy or safaridriver with `safari:useSimulator`; none read in this shard, D), or a dev-only page-side reporter that posts the editor value, selection and the `beforeinput` inputType log (expect `insertReplacementText` from autocorrect) to a host endpoint. A simulator shares the host loopback and an Android emulator reaches the host at 10.0.2.2 (A, e2e packages/mobile/src/engine.ts:81-84), so the reporter works under any driver.

**(c) TalkBack or VoiceOver announcing the active option.** Nothing here can prove it (A, grep across all five). MiniSim only turns TalkBack on (A, Adb.swift:119-141). agent-device and argent read the accessibility tree that a screen reader would consume, including Chrome tab content on Android (A, argent tools/describe/platforms/android/index.ts:78-100). That proves exposure, such as the option's role, name and selected state, not that `aria-activedescendant` changes get spoken. A TalkBack proof needs a speech capture, such as TalkBack's developer speech logging read from logcat, which I did not verify (D). VoiceOver does not run in the iOS Simulator (D, common knowledge, not from these sources), so VoiceOver needs a physical device and a human or a dedicated capture rig.

**What Plate needs to add.** First, a Play Store emulator lane (Gboard and Chrome preinstalled). agent-device's own CI shows that image boots headless on `ubuntu-latest` with KVM through android-emulator-runner (A, .github/workflows/android.yml:63-70). Second, a Chrome-Android page handle through `playwright._android` (already a dependency) or a raw `adb forward ... localabstract:chrome_devtools_remote` CDP session. Third, a Gboard key-coordinate map from `uiautomator dump` or an agent-device snapshot. Fourth, a composition-event log in the page. iOS needs a macOS runner (A, both tools' CI) plus the page-side reporter. Screen-reader announcements stay a manual or device-lab gate.

**Cheapest credible path.** Prove (a) with Playwright `_android` on a Play Store emulator, typing through real taps on Gboard keys and reading the model through `page.evaluate`. agent-device is optional there, useful for locating keys and tapping, but not required. Defer (b) until the page-side reporter exists, then drive Safari key taps with agent-device or argent. Keep (c) as a named unproven gate with an exposure-only tree check as a partial guard.
