[2026-09-23-history-async-replay-api](../review-records/2026-09-23-history-async-replay-api.json) — **pursue**. Pursue a replay-lifecycle redesign while retaining Promise<HistoryResult> as the public undo and redo return type. The Promise is the only honest single signature once one history head may await server-first comment mutation; restoring sync, returning a sync-or-Promise union, splitting undo methods, or removing comment creation from the shared order all lose a stated requirement. The current implementation is still not a best API: ordinary replay mutates before returning Promise.resolve while session replay crosses an await, native callers commonly discard the result, and session replay globally rejects editor publication without exposing pending state. A slow provider can therefore create an invisible locked editor and a blocked shortcut result with no consumer. The durable target is one uniformly scheduled replay queue with observable pending direction/state, mounted input and controls owned by that lifecycle, and explicit blocked/error handling; the detailed concurrency contract must decide whether interaction is disabled, buffered, or safely cancelled before implementation.

### 2026-09-23: 2026-09-23-history-async-replay-api

[Immutable record](../review-records/2026-09-23-history-async-replay-api.json) — review; pursue; observation stale.

Pursue a replay-lifecycle redesign while retaining Promise<HistoryResult> as the public undo and redo return type. The Promise is the only honest single signature once one history head may await server-first comment mutation; restoring sync, returning a sync-or-Promise union, splitting undo methods, or removing comment creation from the shared order all lose a stated requirement. The current implementation is still not a best API: ordinary replay mutates before returning Promise.resolve while session replay crosses an await, native callers commonly discard the result, and session replay globally rejects editor publication without exposing pending state. A slow provider can therefore create an invisible locked editor and a blocked shortcut result with no consumer. The durable target is one uniformly scheduled replay queue with observable pending direction/state, mounted input and controls owned by that lifecycle, and explicit blocked/error handling; the detailed concurrency contract must decide whether interaction is disabled, buffered, or safely cancelled before implementation.

Question: Is making editor.api.history.undo() and redo() uniformly Promise-based the best public contract after fallible external comment replay joined local history?

- Keep the current Promise signature and implementation unchanged: rejected because it has synchronous and asynchronous observation timing under one return type, silently discarded native outcomes, and no public pending state despite an editor-wide publication fence.
- Restore synchronous undo and redo: rejected because server-first comment replay can reject or await network work before the branch may safely move; synchronous success would lie or require unsafe optimistic compensation.
- Return HistoryResult | Promise<HistoryResult>, or add undoSync and undoAsync: rejected because callers must know the hidden top-batch kind before choosing or narrowing the API, spreading history internals through every consumer.
- Remove comment creation from editor history or add a Comments-only stack: rejected because it loses the requested A/B/C user order or creates two competing shortcut owners.
- Make Comments local-first and persist after synchronous replay: viable only as a different product contract. It removes the async requirement by abandoning server-first canonical publication and must not be imposed on applications that require authorization before local publication.
- Retain Promise<HistoryResult> and redesign one replay lifecycle: strongest target. Schedule all replay through one queue, expose pending direction/state, make mounted input and controls honor it, and ensure blocked/error outcomes are consumed. Keep the branch and external mutation atomic under an explicit concurrency policy.
