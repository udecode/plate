Question: Should reusable registry items use name-only plugin dispatch, exact descriptors, or generated application contracts for optional cross-feature capabilities?

- Use name-only plugin dispatch across all registry items: reject. It discards descriptor inference where a component already owns or imports the feature and lets typos compile.
- Import FilesPlugin directly in DndKit: reject. It makes independently installable Dnd depend on the Files feature and its optional Files SDK peer solely for one optional integration.
- Use the generated EditorKit contract to type the Dnd callback: reject. The reusable item would inherit the demo application graph, and callback configuration cannot prove the runtime installation.
- Move descriptor-coupled wiring to the full app EditorKit: type-safe and honest at that root, but it removes automatic DndKit-plus-FilesKit composition or requires another adapter/configuration noun. It does not beat one confined late-bound call under the explicit decoupling requirement.
- Add a type-only Files contract, caller generic or global name-to-capability registry: reject. Each recreates the dependency, duplicates a drifting contract or lets a generic manufacture an installed capability.
- Keep descriptor portals everywhere else and one guarded tx.plugins.has('files') plus tx.plugin('files') boundary in DndKit: selected. The runtime name is the decoupling contract; focused behavior tests cover installed and absent Files.
