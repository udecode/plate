### 2026-09-16: 2026-09-16-fixed-toolbar-scroll-ownership

[Immutable record](../review-records/2026-09-16-fixed-toolbar-scroll-ownership.json) — review; pursue; observation stale.

Pursue deleting the FixedToolbar editor subscription, ResizeObserver and inline-padding save/restore protocol by making the copied panel allocate a toolbar row outside the actual content scrollport.

Question: Should FixedToolbar measure itself and mutate an editor scroll container, or should copied editor layout eliminate the overlap?

- Keep/configure: the current effect assumes every toolbar obstructs the selected editor scrollport, contradicted by external and shared consumers.
- Change API: optional editor lookup or a reusable measuring hook can avoid one failure but preserves incorrect placement and style ownership.
- Add primitive: a toolbar obstruction registry or new Plite scrolling API is unnecessary; the substrate already honors CSS scroll padding.
- Delete/merge: remove the overlap and all height synchronization from the default composition; retain presentational FixedToolbar and its kit plugin for their current independent jobs.
- Move ownership: copied editor layout owns height and scroll placement; beforeContainer is an existing slot for toolbar placement when used inside the appropriate outer frame.
- Replace architecture: a flex/grid panel with a non-scrolling toolbar row and a shrinking content scroll area removes the protocol entirely. CSS scroll padding remains an escape for deliberately overlapping custom UI.

Proof limits: Source review only; no browser or performance run for a replacement. The mocked toolbar test asserts the chosen implementation protocol, not containment or selected-editor availability. Proposed layout still needs bounded/page scrolling, shared-toolbar startup, zoom/custom heights, selection and exact AI menu replay. No new JavaScript runtime machinery or speed claim is accepted. Broad UI and AI scope proof statuses are unchanged.
