### 2026-09-12: 2026-09-12-authored-scalability

[Immutable record](../review-records/2026-09-12-authored-scalability.json) — review; pursue; observation stale.

Question: Should authored-change scalability come from continued local optimization or a redesign of persistence and current-state reconstruction?

- Keep/configure: bulk decode and snapshot optimization remain the strongest smaller comparator and measured wins stay. They do not eliminate dependence on reconstructing current state from every stored operation.
- Change existing API/format: use the native authored and existing codec/effect owners for directly loadable live records, pending content, durable positions and a causal frontier; preserve ordinary initialValue/value persistence unless a real history-retention job requires a new public contract.
- Add primitive: reject a generic loader, trust flag, background replay controller or app-managed snapshot cache. They relocate work or add coordination without establishing coherent ready-to-edit state.
- Delete/merge/move: remove full operation replay as the authority for current state; separate historical payload lifetime from live review facts. Do not delete origin identity, pending dependencies, collision facts, property precedence or compensation facts still required by current consumers.
- Replace architecture: compare a compact live checkpoint against an identity-bearing retained-content representation that derives views without executing the historical edit sequence. This can remove more mapping work but is not selected or measured.
- Plain marks/ranges: reject as a complete replacement for native authored state because inserted/deleted structure, causal dependencies, stable anchors and selective compensation are current jobs. Reintroducing those semantics recreates authored state.
- Replace whole substrate or mandate a CRDT: not selected; no matched evidence shows that this removes more permanent complexity while retaining native/schema/review laws. Transport checkpointing already exists, while its authored payload still contains all operations.

Proof limits: Pursue authorizes further design only. Neither a direct live checkpoint nor a retained-content replacement was prototyped, benchmarked or accepted in this review. The current headless matched repair proves Bun 6.22s to 2.54s and Node 7.24s to 2.44s for 10055 pending insertion operations; 337 authored/Yjs tests, types and lint belong to that existing implementation. ProseMirror marks (16.6/31.8ms) lack equivalent causal history; plain document comparison is separate. All-pending load is not fixed merely by archiving closed history. Complete-load, first-edit, decisions, save, memory, malformed checkpoint, dependency/conflict, stable-anchor and delayed-peer proof must gate the selected representation. No browser/native, general scalability, all-feature API audit, new performance gain or publication claim is made. ### 2026-09-13: 2026-09-13-authored-direct-checkpoint-implementation

[Immutable record](../review-records/2026-09-13-authored-direct-checkpoint-implementation.json) — review; pursue; observation stale.

Pursue is now implemented and proven. One versioned authored checkpoint owns current facts and exact projection state; checksum-bound retained operation bodies stay cold. Registered codecs decode before the generic initial-metadata detachment pass, so safety no longer deep-copies the checkpoint twice. Public calls remain unchanged, load-time operation reduction and pending replay are deleted from the current path, and the Plate suggestion UI consumes the native owner.

Question: Does the directly loadable authored checkpoint merit replacing load-time operation reduction and pending-projection replay?

- Keep tuning replay: rejected because the old path still executes historical operations and pending projection work on every open.
- Persist a duplicate opaque live-state mirror beside the log: rejected by the earlier 44.25 MB slower control and its two-authority corruption risk.
- Encode the complete checkpoint as one opaque payload string: rejected because it shifts too much cost into save and enlarges the payload.
- Chosen target: direct current facts and projections, versioned migration, compact tuple records, and checksum-bound cold retained bodies under the authored owner.
- Public loader, cache, trust mode, worker, or background replay: cut because each adds coordination or hides ready-to-edit work without owning a separate user job.

Proof limits: The performance result is a deterministic all-pending 10,000-paragraph load benchmark with three samples per runtime, so it supports medians and ranges rather than tail percentiles. ### 2026-09-16: 2026-09-16-authored-writer-identity

Stop making author identity optional for accepted edits through the authored engine. Every non-empty document write is emitted as one authored edit operation; proposal=false changes still carry causal identity, rebase pending work and support retained selective history. The registry failure was composition wiring, and the current demo supplies userId: 'demo'. The runtime wording is inaccurate: a non-empty author ID is required, while authentication remains application policy.

Question: Should Plite allow ordinary accepted edits without an author ID when the authored capability is installed?

- Chosen target: keep one authored operation path for accepted and proposed writes; require a current author ID for either path, while allowing read-only authored views without one.
- Validate identity only in proposing mode: rejected because accepted edits are proposal=false authored operations that rebase pending work and participate in retained history and compensation.
- Generate an anonymous or system author inside Plite: rejected because it fabricates domain attribution, weakens same-author rules and makes persistence depend on an implicit identity lifecycle.
