# Plite: commands and transforms

## Deletion

- Forward and backward expanded deletes of the same range give the same result across same-text, block-spanning and inline-spanning selections: `packages/plitejs/test/snapshot-contract.ts:6620`, `deletes equivalent forward and backward expanded selections across text, block, and inline boundaries`, an inverse-direction matrix adapted from Lexical's selection tests to catch anchor and focus drift. Source: `c70bacbd4a:docs/plite/research/2026-06-14-selection-paste-undo-oracles/README.md:40-44`, `lead-ledger.tsv:5`.

## Insert break

- `applyInsertBreak` does nothing for a node selection, because a node selection can be disjoint and has no truthful break target (`packages/plitejs/src/editor/insert-break.ts:39-55`). Only a collapsed text selection inside a non-inline void inserts the root's default block after the highest void and selects it (`insertDefaultBlockAfterSelectedBlockVoid`, `packages/plitejs/src/editor/block-void-break.ts:16-60`). So the void path says nothing about Enter on a selected object; Plate's caption Enter policy owns that case. Read 2026-10-08; the correction first appeared in `docs/plite/research/2026-09-21-media-object-editable-content/README.md:166-169`.

## Public mutation surface

- Plite has no public mutable editor fields (`editor.selection`, `editor.marks`, `editor.children`, `editor.operations`) and no free `Transforms` namespace: state is read through `editor.read` and written through `editor.update` groups, because stale-by-default public state caused regressions and free transforms bypassed lifecycle ownership. Check on 2026-10-08: `git grep -n -P '\beditor\.(children|selection|marks|operations)\b' -- packages/plitejs/src packages/platejs/src` finds nothing, and no source exports a `Transforms` namespace; the public lifecycle is `docs/vision/plite.md:242-252`. Source: `c70bacbd4a:docs/research/systems/slate-v2-perfect-plan-steal-reject-defer-map.md:171-193` (2026-04-23).

- **Setting a property to `null` or `undefined` removes it.** On a raw `createEditor()` on 2026-10-08, `tx.nodes.set({ foo: null }, { at: [0] })` and `tx.nodes.set({ foo: undefined }, { at: [0] })` each left the node without `foo`, as `tx.nodes.unset('foo', { at: [0] })` does. `setNodes` records the old value but leaves a null or undefined value out of the new properties (`packages/plitejs/src/transforms-node/set-nodes.ts:281-286`). `setNodesChange` then deletes each key that is absent from the new properties or `null` in them (`packages/plitejs/src/core/change/root-change.ts:3129-3135`). The legacy fixture `packages/plitejs/test/transforms/setNodes/split/text-remove.tsx` (`editor.nodes.set({ someKey: null }, …)`) passes in the slow fixture walker (run 2026-10-08). This matches legacy Slate's `setNodes`. The April 2026 ledger skipped legacy Slate's raw `set_node` fixtures `remove-null` and `remove-undefined` as legacy sentinels, but Plite has no public raw operation to apply them to, so that skip marks no behavior difference. Source: `c70bacbd4a:docs/plite-draft/ledgers/legacy-plite-test-files.md:650-652`.

- **Only the one-shot form of an update method dispatches its semantic command.** `editor.update.selection.set(range)` lowers to `editorCommands.select`, so a plugin's select handler sees it; the same call as `tx.selection.set(range)` inside `editor.update((tx) => ...)` runs the transaction primitive and dispatches nothing, and `set(null)` never dispatches. The lowering is attached with `defineSemanticUpdateMethod` (`packages/plitejs/src/core/semantic-update-method.ts:16-27`) and applied only by the one-shot proxy (`packages/plitejs/src/core/editor-lifecycle-api.ts:459-474`); `selection.set` lowers a non-null target to `command(editorCommands.select, { target })` (`packages/plitejs/src/core/public-state.ts:5921-5969`). 'maps every semantic one-shot helper to exactly one command' (`packages/plitejs/test/command-spec.test.ts:621`) pins the one-shot side for every helper. A Bun probe against `packages/plitejs/src` on 2026-10-08, with a `handle(editorCommands.select)` plugin, recorded `select` for one-shot `set(range)` and nothing for `tx.selection.set(range)` in a callback or for one-shot `set(null)`; the probe was not committed. A policy that must observe every programmatic selection write cannot rely on the select command alone. Source: the June 2026 repair that routed the public selection write through command middleware (`c70bacbd4a:docs/plans/2026-06-28-plate-next-tested-package-test-file-gate.md:237`).

## Read-only views

- **A read-only view refuses updates.** `Editable` sets the editor view read-only from its `readOnly` prop. Command dispatch and view updates then throw `Cannot update a read-only editor view.`, at a layer below any test handle. Evidence: `packages/plitejs/src/core/command-registry.ts:189`, `packages/plitejs/src/editor-runtime-view.ts:1149,1237,1329,1345`, `packages/plitejs/src/react/editable/runtime-root-engine.ts:134-140`, `:160`, checked 2026-10-08.

- **A document view is a schema-checked, read-only reader with no selection and no commit.** `createEditorView(editor, { document })` validates the document against the editor's schema on every call: a caller that mutates an accepted document object and passes it again gets an `EditorSchemaValidationError` ('revalidates a mutable caller document on every document view', `packages/plitejs/test/schema-identity-contract.test.ts:255`), and a document outside the schema throws ('refuses updates and documents outside the schema', `packages/plitejs/test/editor-runtime-view-contract.ts:2537`). Reads, plugin reads and plugin APIs resolve against the document, while `read.selection()` and `read.lastCommit()` return `null` and the source editor's value and last commit stay as they were (`:2383`). A plugin read that reaches back into the source editor's document while the view reads throws 'Editor read its own document while a document view was reading.' (`packages/plitejs/src/core/document-view-read.ts:45-52`), but a schema query on the source, such as `read.schema.isBlock`, still answers ('refuses a source read made while the view reads', `editor-runtime-view-contract.ts:2417`). A root view derived from it keeps the document, stays read-only with no last commit, and refuses an authored projection (`:2504`). The 7 document-view tests and the schema test passed on 2026-10-08. Vision states the read-only view, the source-read refusal and derivation (`docs/vision/plite.md:254-260`, `:640-642`), not the schema-query exemption, the empty selection and commit or the per-call validation. Limit: the source's claim that the view never notifies subscribers was not checked. The rest of the unit (createEditor, `isEditor`, one-shot and grouped reads and writes) is `docs/vision/plite.md:242-253`. Source: `c70bacbd4a:docs/plite/reference/public-docs/libraries/plite.mdx:29-53`; tests read 2026-10-08.

## Keyboard commands

- **Editing-key behavior goes in command middleware, shortcuts in `onKeyDown`.** In the raw Plite examples, custom Backspace, Delete and Enter behavior is command middleware, while shortcuts and widget navigation stay in `Editable onKeyDown`. The tables example's `table()` plugin uses `handle(editorCommands.delete, ...)` so Backspace at a cell's start and Delete at its end do nothing, and `handle(editorCommands.insertBreak, ...)` so Enter inside a cell does nothing, while Tab moves between cells from `onKeyDown` (`apps/www/src/app/(app)/examples/plite/_examples/tables.tsx:177-185`, `:205-247`). The markdown-shortcuts example uses command middleware too, handling `delete` and `insertText` and wrapping `insertBreak` (`apps/www/src/app/(app)/examples/plite/_examples/markdown-shortcuts.tsx:103-181`), and the richtext example's exit-on-Enter is `around(editorCommands.insertBreak, ...)` while its block, mark and clear-formatting hotkeys run from `onKeyDown` (`apps/www/src/app/(app)/examples/plite/_examples/richtext.tsx:395`, `:436-460`). The fork's 2026-05-18 table-transform decision set this split, calling table-cell Backspace, Delete and Enter model behavior; the `transforms.deleteBackward`, `deleteForward` and `insertBreak` slots it named became `commands` middleware (`831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/ledgers/fork-issue-dossier.md:7391-7438`). Limit: read from the example sources on 2026-10-08; this is example practice, and no package test enforces it.

## Read and update boundaries

- **A read cannot start a write.** Inside a plain `editor.read(...)` callback, `editor.update(...)`, a direct `editor.update.<group>.<method>()` call and an update that applies a canonical change all throw `editor.update cannot be started inside editor.read outside an active update` from the update entry (`packages/plitejs/src/core/public-state.ts:6969-6973`); the transaction runner repeats the check for any other write entry with `editor writes cannot be started inside editor.read` (`assertCanStartEditorWrite`, `:1162-1174`, called at `:9150`). A read holds one committed snapshot, so a write there would mix two editor states. Tests: `packages/plitejs/test/read-update-contract.ts:204` ('rejects nested transaction writes inside a plain read'), `:227` (canonical change writes) and `:254` (direct update methods). Nesting an update inside an update is the separate rule at `docs/vision/plite.md:440-441`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/07-editor.mdx:39`.

- **An update's `tx` reads its draft; `editor.read` stays committed until publication.** Inside `editor.update`, after `tx.nodes.insert(...)` puts a `zero` paragraph at `[0]`, `tx.text.string([0])` is `zero` while `editor.read.text.string([0])` is still `alpha` (`packages/plitejs/test/query-contract.ts:2586`, 'transaction queries see the live draft while ambient reads stay committed'; `packages/plitejs/test/native-transaction-spec-contract.test.ts:37` holds the same for a spec build). A probe on 2026-10-08 read the same two values and `zero` from `editor.read` after the update. So a helper inside an update reads through the active `tx` (`docs/vision/plite.md:440-441`). A prepared `TransactionSpec` from `state.transaction(...)` carries an opaque base of editor, revision, draft epoch and parent context (`packages/plitejs/src/core/public-state.ts:6551-6556`); applying or extending it on another editor or after another commit throws 'Cannot apply a transaction spec to a different editor.' or 'Cannot apply a stale transaction spec.' (`:6407-6434`; test 'rejects stale and cross-editor spec composition', `packages/plitejs/test/command-spec.test.ts:1824`, which exercises `extend`). This model replaced the operation-era path in July 2026. Normal transforms used to build a public `EditorIntent`, which was exactly `Readonly<Operation>`, call `applyIntent` and then `changeFromIntent`, while `createTransactionSpec` mutated editor-owned WeakMap state and rolled it back (`docs/plans/2026-07-18-wordgard-plite-full-architecture-ledger.md:156`, `docs/plans/2026-07-19-wordgard-plite-final-extraction.md:154`, `:267-269`). The hard cut moved transforms to an isolated draft and a native `DocumentChangeBuilder` with one frozen publication, and moved ambient reads inside transforms to `tx` (execution row 3, `c70bacbd4a:docs/plans/2026-07-19-wordgard-plite-final-extraction-execution.md:402`). Public operation middleware went with it, because an operation stream must not remain a second truth (`docs/plans/2026-07-18-wordgard-plite-full-architecture-ledger.md:156`); read middleware and command `handle` and `around` interceptors remain (`docs/vision/plite.md:387`, `:460-463`). On 2026-10-08 the `plitejs` root exports no `EditorIntent`, `applyIntent` or `Transforms`, and `packages/plitejs/src` and `packages/platejs/src` contain no `editor.tf`, `editor.transforms` or `changeFromIntent`. Limit: the kernel plan still lists its transaction benchmark gate as `pending` (`c70bacbd4a:docs/plans/2026-07-19-plite-native-transaction-kernel.md:181`). Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/ledgers/plite-transforms-api.md:15-18`, `:44-45`.

- **A throwing update publishes nothing.** When the callback of `editor.update` throws, Plite discards every staged change. In 'discards staged changes when the update callback throws' (`packages/plitejs/test/transaction-contract.ts:685`), a `tx.nodes.set` inside the callback is visible through `tx.children()`; after the throw, the visible state, the snapshot version and the last commit equal their values from before the update. 'internal transaction discards staged changes when a later write throws' (`packages/plitejs/test/accessor-transaction.test.ts:266`) checks the visible state the same way. Both passed on 2026-10-08. This replaced the fork draft's operation batch engine (`applyBatch` and `withBatch`, later `withTransaction`), whose April 2026 ledger dropped the engine's partial-commit failure semantics for rollback on throw; `packages/plitejs/src` has none of those three names today. Limit: only these two tests were read; a plugin's `beforePublish` veto (`docs/vision/plite.md:408-411`) was not checked. Source: `c70bacbd4a:docs/plite-draft/ledgers/legacy-plite-test-files.md:20`, `:1085-1086`.

## Edit pipeline

- **Behavior that changes editor state belongs in the transaction pipeline, not in an `Editable` event prop.** The retired Plite editing-behavior guide gave each stage of an edit one owner: the browser event; the `Editable` handler, which runs app props first (`plitejs/react`); input import of DOM or native selection (`plitejs/react`, `plitejs/dom`); command dispatch through pure plugin command handlers; one `editor.update` transaction; one root-aware `DocumentChange`; changed-range corrections; one commit that history, React, replay, collaboration and proof observe; render and DOM selection repair; then `@platejs/test` proof. Its rule: intent reaches the editor by many browser paths, so an `Editable` event prop suits UI-local interception, while behavior that changes editor state goes into plugin `commands` and transactions, where another input path still reaches it. The current owners match: public DOM handlers run before built-in commands (`docs/vision/plite.md:391-394`), one editing kernel per mounted `Editable` routes keydown, beforeinput, input, selectionchange, paste, cut, drop and repair (`:722`), and a command-backed one-shot update such as `editor.update.text.insert(...)` runs the installed command handlers while `tx.text.insert(...)` never redispatches a command (`content/docs/(guides)/plugin-methods.mdx`, "Pure command builders"). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/15-editing-behavior.mdx:8-40`.

## Implicit targets

- **An explicit `at` skips target resolution; an implicit target resolves once per transaction.** Inside a transaction, `resolveTarget` returns a caller's `at` unchanged. Only when `at` is absent does it resolve the implicit target, once per transaction snapshot, which caches the result (`packages/plitejs/src/core/public-state.ts:7621-7640`). Resolution goes through the editor runtime's target bridge (`resolveTargetRuntimeImplicitTarget`, `packages/plitejs/src/core/target-runtime.ts:20-52`), which writes a changed result back as the current selection (`resolveImplicitTarget`, `public-state.ts:7586-7592`). A mounted `Editable` installs that bridge, and it resolves the target through its input controller, which may first sync the DOM selection into the editor (`packages/plitejs/src/react/editable/runtime-target-bridge.ts:8-43`). With no mounted bridge, the model selection is the target. So a write with an explicit location never reads the DOM selection. `resolveTarget` stays internal: it sits only on the `EditorTransaction` draft view type (`packages/plitejs/src/interfaces/editor.ts:2067-2079`), which the `plitejs` root does not export (`packages/plitejs/src/index.ts`, checked 2026-10-08). Source: `c70bacbd4a:docs/plite/absolute-architecture-release-claim.md:58-64` (2026-04-24); code read 2026-10-08. Limit: read, not run; no test was cited for the explicit-`at` path.

## Commit record

- **What an `EditorCommit` carries and who reads which part.** The commit type holds `changes` and `inverseChanges` (canonical `DocumentChange` values), `effects`, `annotations`, `tags`, `before` and `after` snapshots, `selectionBefore` and `selectionAfter` with their named roots (`undefined` for the primary document), `selectionChanged`, `version`, `previousVersion`, `dirtyStateKeys` and `changed`. `changed` is a set of lazy queries (`has`, `hasAny`, `hasNodeKey`, `paths`, `nodeKeys`, `nodeKeysAll`, `topLevelRanges`) derived from the canonical change and the snapshot indexes (`packages/plitejs/src/interfaces/editor.ts:3522-3591`). There is no command field and no flat eager impact flag. The 2026 architecture contract split the consumers: replay and mapping read `changes`; history applies the inverse change with inverted effects; React, DOM and layout read `changed`; analytics and policy read tags, effects and annotations. Source: `c70bacbd4a:docs/plite/references/architecture-contract.md:65-84`; type read 2026-10-08. Limit: the consumer split is the contract's statement, and the consumers were not traced one by one.
