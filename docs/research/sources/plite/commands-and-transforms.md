# Plite: commands and transforms

## Deletion

- Forward and backward expanded deletes of the same range give the same result across same-text, block-spanning and inline-spanning selections: `packages/plitejs/test/snapshot-contract.ts:6620`, `deletes equivalent forward and backward expanded selections across text, block, and inline boundaries`, an inverse-direction matrix adapted from Lexical's selection tests to catch anchor and focus drift. Source: `docs/plite/research/2026-06-14-selection-paste-undo-oracles/README.md:40-44`, `lead-ledger.tsv:5`.

## Insert break

- `applyInsertBreak` does nothing for a node selection, because a node selection can be disjoint and has no truthful break target (`packages/plitejs/src/editor/insert-break.ts:39-55`). Only a collapsed text selection inside a non-inline void inserts the root's default block after the highest void and selects it (`insertDefaultBlockAfterSelectedBlockVoid`, `packages/plitejs/src/editor/block-void-break.ts:16-60`). So the void path says nothing about Enter on a selected object; Plate's caption Enter policy owns that case. Read 2026-10-08; the correction first appeared in `docs/plite/research/2026-09-21-media-object-editable-content/README.md:166-169`.

## Public mutation surface

- Plite has no public mutable editor fields (`editor.selection`, `editor.marks`, `editor.children`, `editor.operations`) and no free `Transforms` namespace: state is read through `editor.read` and written through `editor.update` groups, because stale-by-default public state caused regressions and free transforms bypassed lifecycle ownership. Check on 2026-10-08: `git grep -n -P '\beditor\.(children|selection|marks|operations)\b' -- packages/plitejs/src packages/platejs/src` finds nothing, and no source exports a `Transforms` namespace; the public lifecycle is `docs/vision/plite.md:242-252`. Source: `docs/research/systems/slate-v2-perfect-plan-steal-reject-defer-map.md:171-193` (2026-04-23).

## Read-only views

- **A read-only view refuses updates.** `Editable` sets the editor view read-only from its `readOnly` prop. Command dispatch and view updates then throw `Cannot update a read-only editor view.`, at a layer below any test handle. Evidence: `packages/plitejs/src/core/command-registry.ts:189`, `packages/plitejs/src/editor-runtime-view.ts:1149,1237,1329,1345`, `packages/plitejs/src/react/editable/runtime-root-engine.ts:134-140`, `:160`, checked 2026-10-08.

## Keyboard commands

- **Editing-key behavior goes in command middleware, shortcuts in `onKeyDown`.** In the raw Plite examples, custom Backspace, Delete and Enter behavior is command middleware, while shortcuts and widget navigation stay in `Editable onKeyDown`. The tables example's `table()` plugin uses `handle(editorCommands.delete, ...)` so Backspace at a cell's start and Delete at its end do nothing, and `handle(editorCommands.insertBreak, ...)` so Enter inside a cell does nothing, while Tab moves between cells from `onKeyDown` (`apps/www/src/app/(app)/examples/plite/_examples/tables.tsx:177-185`, `:205-247`). The markdown-shortcuts example uses command middleware too, handling `delete` and `insertText` and wrapping `insertBreak` (`apps/www/src/app/(app)/examples/plite/_examples/markdown-shortcuts.tsx:103-181`), and the richtext example's exit-on-Enter is `around(editorCommands.insertBreak, ...)` while its block, mark and clear-formatting hotkeys run from `onKeyDown` (`apps/www/src/app/(app)/examples/plite/_examples/richtext.tsx:395`, `:436-460`). The fork's 2026-05-18 table-transform decision set this split, calling table-cell Backspace, Delete and Enter model behavior; the `transforms.deleteBackward`, `deleteForward` and `insertBreak` slots it named became `commands` middleware (`831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/ledgers/fork-issue-dossier.md:7391-7438`). Limit: read from the example sources on 2026-10-08; this is example practice, and no package test enforces it.

## Read and update boundaries

- **A read cannot start a write.** Inside a plain `editor.read(...)` callback, `editor.update(...)`, a direct `editor.update.<group>.<method>()` call and an update that applies a canonical change all throw `editor.update cannot be started inside editor.read outside an active update` from the update entry (`packages/plitejs/src/core/public-state.ts:6969-6973`); the transaction runner repeats the check for any other write entry with `editor writes cannot be started inside editor.read` (`assertCanStartEditorWrite`, `:1162-1174`, called at `:9150`). A read holds one committed snapshot, so a write there would mix two editor states. Tests: `packages/plitejs/test/read-update-contract.ts:204` ('rejects nested transaction writes inside a plain read'), `:227` (canonical change writes) and `:254` (direct update methods). Nesting an update inside an update is the separate rule at `docs/vision/plite.md:440-441`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/07-editor.mdx:39`.

- **An update's `tx` reads its draft; `editor.read` stays committed until publication.** Inside `editor.update`, after `tx.nodes.insert(...)` puts a `zero` paragraph at `[0]`, `tx.text.string([0])` is `zero` while `editor.read.text.string([0])` is still `alpha` (`packages/plitejs/test/query-contract.ts:2586`, 'transaction queries see the live draft while ambient reads stay committed'; `packages/plitejs/test/native-transaction-spec-contract.test.ts:37` holds the same for a spec build). A probe on 2026-10-08 read the same two values and `zero` from `editor.read` after the update. So a helper inside an update reads through the active `tx` (`docs/vision/plite.md:440-441`). A prepared `TransactionSpec` from `state.transaction(...)` carries an opaque base of editor, revision, draft epoch and parent context (`packages/plitejs/src/core/public-state.ts:6551-6556`); applying or extending it on another editor or after another commit throws 'Cannot apply a transaction spec to a different editor.' or 'Cannot apply a stale transaction spec.' (`:6407-6434`; test 'rejects stale and cross-editor spec composition', `packages/plitejs/test/command-spec.test.ts:1824`, which exercises `extend`). This model replaced the operation-era path in July 2026. Normal transforms used to build a public `EditorIntent`, which was exactly `Readonly<Operation>`, call `applyIntent` and then `changeFromIntent`, while `createTransactionSpec` mutated editor-owned WeakMap state and rolled it back (`docs/plans/2026-07-18-wordgard-plite-full-architecture-ledger.md:156`, `docs/plans/2026-07-19-wordgard-plite-final-extraction.md:154`, `:267-269`). The hard cut moved transforms to an isolated draft and a native `DocumentChangeBuilder` with one frozen publication, and moved ambient reads inside transforms to `tx` (execution row 3, `docs/plans/2026-07-19-wordgard-plite-final-extraction-execution.md:402`). Public operation middleware went with it, because an operation stream must not remain a second truth (`docs/plans/2026-07-18-wordgard-plite-full-architecture-ledger.md:156`); read middleware and command `handle` and `around` interceptors remain (`docs/vision/plite.md:387`, `:460-463`). On 2026-10-08 the `plitejs` root exports no `EditorIntent`, `applyIntent` or `Transforms`, and `packages/plitejs/src` and `packages/platejs/src` contain no `editor.tf`, `editor.transforms` or `changeFromIntent`. Limit: the kernel plan still lists its transaction benchmark gate as `pending` (`docs/plans/2026-07-19-plite-native-transaction-kernel.md:181`). Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/ledgers/plite-transforms-api.md:15-18`, `:44-45`.

## Edit pipeline

- **Behavior that changes editor state belongs in the transaction pipeline, not in an `Editable` event prop.** The retired Plite editing-behavior guide gave each stage of an edit one owner: the browser event; the `Editable` handler, which runs app props first (`plitejs/react`); input import of DOM or native selection (`plitejs/react`, `plitejs/dom`); command dispatch through pure plugin command handlers; one `editor.update` transaction; one root-aware `DocumentChange`; changed-range corrections; one commit that history, React, replay, collaboration and proof observe; render and DOM selection repair; then `@platejs/test` proof. Its rule: intent reaches the editor by many browser paths, so an `Editable` event prop suits UI-local interception, while behavior that changes editor state goes into plugin `commands` and transactions, where another input path still reaches it. The current owners match: public DOM handlers run before built-in commands (`docs/vision/plite.md:391-394`), one editing kernel per mounted `Editable` routes keydown, beforeinput, input, selectionchange, paste, cut, drop and repair (`:722`), and a command-backed one-shot update such as `editor.update.text.insert(...)` runs the installed command handlers while `tx.text.insert(...)` never redispatches a command (`content/docs/(guides)/plugin-methods.mdx`, "Pure command builders"). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/15-editing-behavior.mdx:8-40`.
