# Plite: testing and proof

## Huge-document proof families

- Two first-party browser contract families cover huge documents on the `huge-document` route. `huge-document-virtualized-scroll-stability` asserts no row overlap during immediate scrollbar jumps, no gaps or overlaps after a settled repaint, mounted rows buffered during a native scrollbar drag before React commits the next range, and dynamic-height backward scroll staying near the requested offset. `huge-document-projected-vertical-selection` asserts monotonic focus under repeated Shift+ArrowDown, Shift+ArrowUp reversing the recent focus steps, view markers while native selected text stays empty, no double highlight and a hot-path budget. Code: `packages/test/src/proof/first-party-browser-contracts.ts:164-184`. The scroll family was promoted on 2026-06-12 from route-local Playwright tests so a supervisor can find it (`c70bacbd4a:docs/plite/research/2026-06-12-huge-doc-architecture/README.md:36-38`).

## IME proof transports

- Synthetic composition helpers keep no active DOM composition text node before commit, so they cannot prove what happens when an edit mutates the DOM span inside an active composition; that class needs a helper that observes or mutates the real native composition span. The harness drives native composition through CDP `Input.imeSetComposition` and `Input.insertText` (`packages/test/src/playwright/ime.ts:312-319`) beside its synthetic composition events (`ime.ts:40-75`). Source: `c70bacbd4a:docs/plite/research/2026-06-12-oss-input-selection-architecture/shards/001-input-selection-composition.md:38-42`, `lead-ledger.tsv:5`.

## IME and repair proof families

- First-party contract families name the IME, native-repair and external-paste proof (`packages/test/src/proof/first-party-browser-contracts.ts:185-262`): `ime-composition-formatted-boundaries` (composition inside formatted markup, active-mark cursor-wrapper composition, one replacement of several formatted text nodes, WebKit `compositionend` cleanup of an expanded rich-text selection), `ime-composition-cross-block-repair` (rapid consecutive compositions in separate blocks, cross-paragraph native composition replacing the range once, a synthetic transport that never mutates React-owned expanded DOM ranges, final selection after the committed text), `ime-composition-decoration-refresh` (prop and hook decoration sources refresh while a stepwise synthetic composition stays open, then model, DOM caret and text agree), `native-beforeinput-target-range-repair` (target ranges replace browser substitution spans, stale target ranges are rejected, native partial and mouse-drag replacements undo cleanly) and `external-clipboard-slice-context` (ProseMirror slices, comment-bounded fragments and external table HTML). They were named on 2026-06-12 from ProseMirror's composition, DOM-change and clipboard tests; overlap cancellation is deliberately absent (`EDIT-IME-OVERLAP-CANCEL-001`). Source: `c70bacbd4a:docs/plite/research/2026-06-12-testing-oracles/README.md:31-57`.

## Browser harness primitives

- The browser harness `@platejs/test` (`packages/test/src/playwright/`) provides: selection snapshots of model selection, DOM selection, displayed native and view selection, selected text and caret rects, with a double-highlight flag (`displayed-selection.ts:181`); a clipboard layer with an exclusive cross-process file lock (`.editor-browser-clipboard.lock`, `clipboard.ts:10-15`), native clipboard read and write and synthetic event payloads; IME transports for Chromium CDP native composition (`ime.ts:312-319`), synthetic composition events, a coarse-pointer semantic `insertText` fallback (`ime.ts:213-217`) and direct insertion; and a scenario runner with trace snapshots, runtime-error checks, replay artifacts and reduction candidates (`scenario*.ts`). In June 2026 these primitives were already stronger than the ProseMirror and Tiptap test helpers read for comparison; the gap was naming contract families. Source: `c70bacbd4a:docs/plite/research/2026-06-12-testing-oracles/sources/plite-browser-summary.md:10-24`, `README.md:18-24`.

- The harness clicks a model text offset through `editor.dom.clickTextOffset({ path, offset, clickCount, waitForSelectionSync })` (`packages/test/src/playwright/harness.ts:391`, implemented in `packages/test/src/playwright/dom-text-actions.ts:108`), also a scenario step `kind: 'clickTextOffset'` (`packages/test/src/playwright/harness-scenario.ts:628`). The 2026-06-13 WPT run added it for the repeated text-offset click of its mouse-selection rows, such as Shift+click in `apps/plite/tests/plite-browser/donor/examples/plaintext.test.ts:197`. Source: `c70bacbd4a:docs/plite/research/2026-06-13-wpt-editing-oracles/README.md:299-318`; code read 2026-10-08.

- **The harness caret oracle reads geometry, not pixels.** `editor.assert.caretVisibleInScrollableParent()` and `editor.assert.noVisibleCaretInRoot()` (`packages/test/src/playwright/harness-assertions.ts:122-127`) take the first client rect of the DOM selection range, or the text host's rect when that rect is empty, and call the caret visible when the selection's anchor, its focus and the focused element sit in the root and that rect lies vertically inside the scroll parent's rect within 1 px (`packages/test/src/playwright/caret-visibility.ts:84-110`). They classify no pixels, so a caret in the right place that the browser does not paint still passes. The one caret pixel classifier is local to the native macOS lane's spec, which counts dark vertical runs in an OS `screencapture` (`caretRunsNear`, `apps/www/tests/native/homepage-ime.native.ts:160-196`). Evidence: read 2026-10-08; first read at `cf15725603` (`docs/plite/research/2026-10-02-agentic-e2e-testing/read-log.tsv:367`).

- **The harness API rules.** `@platejs/test/playwright` was designed around editor nouns (editor, selection, range, point, fragment, composition, placeholder, clipboard). Tests go through the harness instead of raw contenteditable selectors, hand-written selection checks or CDP boilerplate; helpers are named for editor intent and keep browser specifics in options; semantic assertions come first, DOM assertions second and raw HTML last. Example routes open through `openExample` (`packages/test/src/playwright/index.ts:223`); a public `openFixture` and a generic `editor.driver()` were rejected until a real backing surface or a second backend exists, so Playwright stays an explicit backend instead of a lane-neutral driver, and neither name exists in `packages/test/src` (git grep, 2026-10-08). The April evaluation rule shipped an API only when it removed repeated pain from the existing suite. Before the `apps/plite` browser suite runs, its runner rebuilds `@platejs/test` when the package's `dist` is stale (`apps/plite/scripts/build-browser-if-stale.mjs`, the `pretest:plite-browser` scripts in `apps/plite/package.json:10-14`). Sources: `c70bacbd4a:docs/plite-browser/api-design.md:380-466`, `c70bacbd4a:docs/plite-browser/next-system-move.md:143-159`, `c70bacbd4a:docs/plite-browser/next-api-candidates-matrix.md:39-46`, `:453-488` (April 2026).

- **Where the harness surface came from.** The April 2026 ranking shipped as today's harness: an `openExample` `ready` option, one object instead of separate wait flags, with `editor`, `placeholder`, `selector`, `text`, `selection` (`'settled'` or an exact snapshot) and `timeoutMs` (`packages/test/src/playwright/types.ts:668-675`), plus a `surface` option with `frame` and `scope` for iframe and shadow-DOM examples (`:679-682`); semantic selection setup through `editor.selection.select` and `collapse`, so tests stop doing raw DOM range surgery; block-level text through `editor.get.blockTexts()` and `assert.blockTexts` instead of a lossy flat text or a reconstructed document; a one-call `editor.snapshot()` that aggregates existing reads (text, block texts, rendered blocks, selected text, model and DOM selection, focus owner, kernel trace, history, last commit, placeholder shape; `packages/test/src/playwright/harness.ts:422-434`); offsets given as a number or a `[min, max]` range (`OffsetExpectation`, `types.ts:636`); `htmlEquals` options `ignoreClasses`, `ignoreInlineStyles` and `ignoreDir` (`:661-663`); clipboard reads `readText` and `readHtml` (`:1420-1421`); and path locators `editor.locator.block(path)` and `text(path)` (`harness.ts:415-418`). Readiness, range offsets and HTML normalization came from Lexical, the getters and selected text from edix, and the snapshot from use-editable's `getState`. Sources: `c70bacbd4a:docs/plite-browser/next-api-candidates-matrix.md:48-451`, `c70bacbd4a:docs/plite-browser/next-api-candidates.md:149-393` (April 2026); code read 2026-10-08.

## Native event trace

- Final-value assertions miss bugs where the model text ends right but the browser selection jumped, `beforeinput` targeted another node, the native composition moved or the DOM changed outside its owner. The harness records the event chain around an operation: `startBrowserNativeEventTrace`, `takeBrowserNativeEventTrace`, `resetBrowserNativeEventTrace` and `stopBrowserNativeEventTrace` (`packages/test/src/playwright/native-event-trace.ts:21`, `:490-521`) capture native `selectionchange`, `beforeinput`, `input` and composition events with the browser selection, `getTargetRanges()`, text-node snapshots, input-time DOM deltas, rects and named anomalies: `composition-mismatch`, `data-content-mismatch`, `inputtype-mismatch`, `missing-beforeinput`, `node-type-change`, `parent-mismatch`, `selection-jump` and `sibling-created` (`packages/test/src/playwright/types.ts:200-211`; test `packages/test/test/browser/native-event-trace.browser.test.ts`). The trace shape came from the `easylogic/contenteditable` playground on 2026-06-13; it validates browser event shape and Plite ownership, not OS candidate-window behavior. Source: `c70bacbd4a:docs/plite/research/2026-06-13-contenteditable-event-trace-oracles/README.md:17-42`, `shards/001-event-trace-anomaly-oracles.md:3-49`.

## WPT invariant map

- WPT invariants that existing Plite proof covered on 2026-06-13: end-of-line image selection and delete map to image route rows (click-select then Backspace, Shift+ArrowRight into an image, vertical arrows into an image); character and line-boundary movement around non-editable spans, and paragraph movement across editing boundaries, map to content-root navigation contracts and editable-void, read-only-inline and synced-block route rows; target ranges fixed at dispatch map to the reconciler contract `beforeinput uses event target range instead of later live DOM selection`; `content-visibility: hidden` text staying out of native selection maps to hidden content staying out of native find until materialized, while model-backed copy includes it by policy; `Selection.deleteFromDocument()` maps to expanded-selection deletion over formatted leaves and top-level blocks, browser Backspace and Delete over a selected range, caret editability and undo; anchor-node removal maps to the detached-endpoint contract; triple-click directionless selection maps to triple-click rows over links and read-only inlines; and horizontal ArrowUp and ArrowDown caret position maps to richtext, image and code-block vertical rows. CSS generated content in `Selection.modify('word')` is out of scope, since Plite never renders model text through pseudo-elements. Source: `c70bacbd4a:docs/plite/research/2026-06-13-wpt-editing-oracles/lead-ledger.tsv:30-39`. Limit: the map names behaviors, not current lines; the June tests moved to `apps/plite/tests/plite-browser/donor/examples/`.

- More WPT mappings from 2026-06-13: a click still moves the caret in an editable root under `user-select: auto | text | none | contain | all` (`apps/plite/tests/plite-browser/donor/examples/plaintext.test.ts:242`); placeholder text never enters native or model selected text (`apps/plite/tests/plite-browser/donor/examples/placeholder.test.ts:49`); forward Delete and `deleteWordForward` target ranges apply exactly over graphemes, preserved spaces and word whitespace; content-delete inputTypes over an expanded selection delete the selected fragment whatever exact `inputType` label the browser reports; contenteditable paste has `event.data === null`; an empty editor with a custom placeholder still focuses one collapsed caret through zero-width line-break rendering; inline and range deletion stay correct while browser `selectionchange` after the delete is imported or repaired, without asserting browser event counts; and native selection inside a shadow root is covered by shadow-DOM caret, model-owned movement and RTL delete rows. Out of scope, as browser API behavior Plite does not own: arbitrary `user-select: none` drag islands, DOM ranges inside empty elements (model points target text leaves), `Selection.collapse()` focus transfer across arbitrary hosts, `selectionchange` task scheduling and the raw `Selection.extend()` matrix. Vertical `writing-mode` caret movement and mixed-bidi `lineboundary` extension stay unclaimed until an accepted plan (`docs/vision/plite.md:676`). Source: `c70bacbd4a:docs/plite/research/2026-06-13-wpt-editing-oracles/lead-ledger.tsv:40-54`.

Source: `c70bacbd4a:docs/plite/research/2026-06-13-wpt-editing-oracles/README.md:8-13`, `:746-750`, `rejected-ledger.tsv:2`; WPT read at `web-platform-tests/wpt@dd54691426c23a08c6f4a0972b2c40965307e5ce`.

## Browser matrix versus raw-device proof

- **Two proof lanes.** Plite keeps desktop browser-matrix proof apart from raw-device receipts. `pnpm check:plite:browser-matrix` (package.json:47) runs the Playwright projects in `apps/plite/playwright.config.ts`: Chromium, Firefox and WebKit desktops plus `mobile` (Pixel 5) and `mobile-webkit` (iPhone 13) emulation. `test:mobile-device-proof:raw` (package.json:126) sets `PLITE_BROWSER_RAW_MOBILE_REQUIRED=1` and requires an Appium receipt from Android Chrome and from iOS Safari for each of the 16 scenarios in `packages/test/src/proof/raw-mobile-proof.ts:7-24`. Neither an emulated mobile project nor a donor's touch-capable desktop context, as in Meowdown or ProseKit, stands in for a raw iOS receipt, and an engine skip should name exactly what that engine cannot synthesize. - **What a raw-mobile receipt must carry, and what produces one.** Beyond the scenario matrix, `validateRawMobileProof` requires each receipt to declare `directAppium: true` with the matching `appium-android` or `appium-ios` transport, a real device (`realDevice: true`, name, model and OS version), the browser and its version, and a build commit equal to the expected 40-character commit; to carry SHA-256 digests for the receipt, its video and every step screenshot; to keep model text equal to DOM text in every snapshot; and to end on the scenario's update count, 0 for the eleven gesture and selection scenarios and 1 for `enter`, `backspace`, `autocapitalization`, `composition-ime` and `native-clipboard` (`packages/test/src/proof/raw-mobile-proof.ts:7-24`, `:114-298`). ## Generated stress replay

- Every generated stress artifact carries reduction candidates, a failed or still-running one included: `createStressArtifact` builds them from the case's steps through `createScenarioReductionCandidates` when the run returned none, and gives each a `STRESS_REDUCTION=<label>` replay command (`apps/plite/tests/plite-browser/donor/stress/stress-utils.ts:141-165`, `:175`). The candidates drop one warm-loop iteration (`<warmLoop>:iteration:<n>`), keep a prefix (`prefix:<n>`) or a suffix (`suffix:<n>`), or drop one step (`without:<n>`) (`packages/test/src/playwright/scenario-replay.ts:724-808`); `packages/test/README.md:162` documents the reduced replay and its separate `.reduction-<label>.result.json` trace. Before June 2026 a failed artifact carried no candidates, because the stress test passed `result.reductionCandidates` only after a successful run. No editor sampled for comparison (Lexical, CodeMirror, WPT) had a stronger automatic shrinker. Source: `c70bacbd4a:docs/plite/research/2026-06-14-generated-stress-replay-reduction/README.md:23-28`, `rejected-ledger.tsv:3`; code read 2026-10-08.

- **Arbitrary browser code runs through `editor.scenario.runImperative` and never counts as a replayable scenario.** Canonical scenario steps must serialize: `editor.scenario.run` refuses a step that does not, with an error that points to `runImperative` (`packages/test/src/playwright/scenario-replay.ts:978-987`). `runImperative(name, callback)` hands the callback a `step(label, action)` that runs the action and records a trace snapshot after it, then returns a frozen result marked `replayable: false`, `reducible: false` and `releaseGateCapable: false` (`packages/test/src/playwright/harness-scenario.ts:83-111`). A free-form native experiment stays traceable without passing as replay, reduction or release-gate proof. Design source: `c70bacbd4a:docs/plite-browser/api-design.md:313-336` (2026-04-03); code read 2026-10-08.

## Harness transports and stand-ins

- **Which harness calls bypass native input.** `@platejs/test/playwright` reads the model through the page handle `__pliteBrowserHandle` on the editor root, with a 20 s ready timeout, and its `insertText`, `insertBreak`, `deleteFragment`, `deleteBackward`, `deleteForward`, `undo` and `redo` call that handle too (`packages/test/src/playwright/constants.ts:1-2`, `harness.ts:530-550`). `type` goes through `page.keyboard.type`; a June 2026 shortcut that sent mobile `type` through the handle hid data-loss and text-order bugs and was removed (`c70bacbd4a:docs/plans/2026-06-07-plite-8h-supervision.md:638`). `press` dispatches an untrusted `keydown` and `keyup` pair on the root for every chord with Control, Meta, ControlOrMeta, Alt or Shift except ControlOrMeta+C, X, V and A, so Shift+Arrow included, and for a plain key when, after focusing, no DOM selection sits in the root and the handle can set one; only the remaining keys go through `page.keyboard.press` (`harness.ts:501-529`, `keyboard.ts:12-110`). A scenario `undo` step presses Meta+Z or Control+Z through that synthetic path on desktop and calls the handle on a `mobile` platform (`harness-scenario.ts:125-139`). For IME, Chromium sends CDP `Input.imeSetComposition` for each step and then `Input.insertText`, while other engines and the `synthetic` option dispatch `CompositionEvent`s (`ime.ts:284-322`). Code checked 2026-10-08. Limit: a green row on these paths proves the editor command, not the browser's native input.

- **Transport claim labels are declared, not observed.** A scenario result carries `metadata.claim`, one of 12 `BrowserTransportClaim` labels: `desktop-native-clipboard`, `desktop-native-ime-composition`, `desktop-native-keyboard`, `desktop-semantic-handle`, `mixed-native-and-semantic`, `mobile-semantic-handle`, `mobile-synthetic-composition`, `playwright-mobile-keyboard`, `playwright-mobile-viewport`, `synthetic-composition`, `synthetic-datatransfer` and `unspecified` (`packages/test/src/playwright/types.ts:759-771`). `classifyScenarioTransportClaim` derives the label from substrings of the scenario's declared `transport` string and its `platform`: a `mobile` platform with no transport becomes `playwright-mobile-viewport`, a desktop one `unspecified` (`packages/test/src/playwright/scenario-replay.ts:1114-1177`). It never inspects the steps, so a scenario that declares a keyboard transport is labelled `desktop-native-keyboard` even if its `press` steps send synthetic chords (inferred from the code, checked 2026-10-08).

- **Unit-level actions are constructed events.** `createTestEditor` in `@platejs/test/react` renders an editor and drives it through Testing Library `fireEvent`: `type` fires one `beforeinput` with `inputType: 'insertText'` and the whole string, a hotkey fires a lone `keydown`, and `paste` fires a plain `paste` event whose stub `clipboardData.getData` returns the same payload for every type. The `browser` entry only snapshots DOM and editor selection and inspects zero-width placeholders (`packages/test/src/browser/index.ts`). Code checked 2026-10-08. Limit: these actions prove how the runtime handles a constructed event in the test DOM, never browser input, layout or IME.

- **The harness fakes the keydown before every composition.** `editor.ime.compose()` (every transport, CDP included), `startSynthetic()` and `enableKeyEvents()` install `enableCompositionKeyEvents`, a capture listener on `window`, installed once per window, that dispatches an untrusted `keydown` with `key: 'Unidentified'` and `keyCode: 220` on the focused element at every `compositionstart` (`packages/test/src/playwright/ime.ts:9-37`, `packages/test/src/playwright/harness-input.ts:284-305`; 'installs composition key events once on the resolved editor surface', `packages/test/test/proof/playwright-ime.test.ts:511`). So in a harness composition row the keydown is script-made and raised from inside the `compositionstart` capture phase; the row proves how the editor reacts to that shape, not to a real IME's keydown. Plite's runtime reads no `keyCode` (no match in `packages/plitejs/src` on 2026-10-08). Evidence: code read 2026-10-08; first read at `cf15725603` (`docs/plite/research/2026-10-02-agentic-e2e-testing/read-log.tsv:366`).

## Browser handle

- **The Plite suite runs against a production export.** The Playwright web server for `apps/plite` runs `pnpm build && pnpm serve`, which serves a static `next build` export from `out`. The web server for `apps/www` runs `pnpm dev:plite`, which is `next dev`. A `NODE_ENV` gate on the test handle would therefore strip it from the Plite suite, so test apps install the handle explicitly. Evidence: `apps/plite/playwright.config.ts:122-126`, `apps/www/playwright.config.ts:53-57`, `apps/plite/scripts/serve.mjs`, checked 2026-10-08; the Defaults row 'Handle installation' in `docs/plans/2026-10-02-proof-device-lane.md`.

- **The page handle was always test-only.** The handle began in April 2026 to back selection and range-ref helpers, then gained `getText`, `insertText` and `undo` for model proof. Every architecture plan since has called it a test and proof surface, not app API. Those plans say not to make proof handles a production extension API and not to add another handle escape hatch, because semantic handle paths hide debt in native transports. Evidence: `docs/plans/2026-04-19-plite-dom-react-tranche-5-6-execution.md:692-700`, `c70bacbd4a:docs/plans/2026-04-21-plite-full-core-editing-coverage-plan.md:144-187`, `docs/plans/2026-04-22-plite-editable-browser-kernel-refactor-plan.md:115-124`, `c70bacbd4a:docs/plans/2026-04-22-plite-editing-kernel-hard-cut-rewrite-plan.md:2084-2094`, `c70bacbd4a:docs/plans/2026-04-22-plite-authoritative-command-kernel-architecture-plan.md:1895-1902`, `docs/plans/2026-04-22-plite-core-api-runtime-perfection-plan.md:403-424`; `packages/plitejs/test/react/kernel-authority-audit-contract.ts:967` calls it 'the test-only browser handle'.

- **A selection set through the handle routes typing like a click.** A 2026-10-02 probe on the richtext example, run on all five Playwright projects (chromium, firefox, webkit, mobile, mobile-webkit), set the selection once through the page handle and once with a real click, then typed and pressed Backspace. The handle path left the preference reason `'browser-handle'` (`preferModelSelection: true`, source `model-owned`) and the click left `'native-selection'` (`preferModelSelection: false`, source `dom-current`), but on both paths `keydown` and `beforeinput` routed model-owned with native input not allowed, and the text came out the same. So the handle's preference changes no input ownership on that route, and the `'browser-handle'` branches in the selection controller, input router, editing kernel and DOM input runtime stayed. At unit level the contract 'browser-handle text input can keep the native fast path' checks only that the `'browser-handle'` reason alone does not force model-owned `insertText` (`packages/plitejs/test/react/selection-controller-contract.ts:1995-2017`). Evidence: `docs/plite/research/2026-10-02-agentic-e2e-testing/sources/browser-handle-preference-probe.result.json`, `docs/plite/research/2026-10-02-agentic-e2e-testing/review/execution-trail/opus-precheck.md:84`. Limit: one example route.

- **What each browser-handle write skips.** In `packages/plitejs/src/react/editable/browser-handle.ts`, `insertText`, `insertBreak`, `insertData`, `deleteBackward`, `deleteForward`, `deleteFragment` and `selectAll` run `runCommand` (`:281-367`), which flushes pending native input, forces model-owned selection preference with reason `'browser-handle'`, opens a `repair` frame, applies the editable command, exports the DOM selection and records a trace with `nativeAllowed: false`. These skip keydown, `beforeinput`, `input`, DOM mutation, composition, clipboard events, Android repair and the app's `onKeyDown` and `onDOMBeforeInput`. `undo` and `redo` dispatch history directly. `applyChange`, `applyValueChange`, `insertTextAt` and `deleteTextAt` are fixture writes through `editor.update` with no event frame. `selectRange` and `focus` stand in for click, drag, keyboard selection and Tab. `setNativeDOMSelection` writes the real `Selection` and dispatches a synthetic `selectionchange`, closest to native but still programmatic. `importDOMSelection` forces an import outside the editor's own trigger and can mask an import bug. `scrollPathIntoView` stands in for user scrolling, and the range anchors are test bookkeeping. Only the input and selection writes are stand-ins; fixture writes are legitimate setup. Source: `docs/plite/research/2026-10-02-agentic-e2e-testing/shards/007-page-handle-audit.md:78-90`; code read 2026-10-08.

- **What the proof oracle needs from the handle.** Doctrine asks for model, DOM, selection, focus owner, legal trace, replayability, follow-up typing and commit metadata. The model value needs `getValue` and its siblings, because virtualized or hidden content is not in the DOM. Selection needs `getSelection`, `getModelSelection`, `getViewSelection` or `getDOMSelection`; the raw DOM selection plus `data-editor-path` serves plain text but not projections. The legal trace and mutation owner need `getKernelTrace`, commit metadata needs `getLastCommit`, and replay needs `getHistory` plus the fixture writes. Identity needs `getNodeKey`, `getPathByNodeKey`, `getElementByPath` and `resolveDOMPoint`, and diagnostics need `getInputState` and the scheduler and external-text reads. Only the focus owner works from the DOM alone. The oracle therefore needs about 15 read methods and no input write. Source: `docs/plite/research/2026-10-02-agentic-e2e-testing/shards/007-page-handle-audit.md:101-114`.

- **An installed browser handle is a write-capable page API.** `applyChange`, `applyValueChange`, `insertTextAt` and `deleteTextAt` accept any update policy, including the `history-skip`, `historic`, `collaboration` and `skip-collab` tags (`packages/plitejs/src/interfaces/editor.ts:860-870`), so a page script can make an edit that never reaches collaborators, cannot be undone, or claims remote origin. Its kernel command writes skip every DOM-level app handler, such as `Editable`'s `onKeyDown` and `onDOMBeforeInput`, while Plite checks `isTrusted` only for the native single-character `insertText` decision (`packages/plitejs/src/react/editable/native-input-strategy.ts:173-182`). `getHistory` returns full undo and redo changes, deleted text included, `getKernelTrace` returns the last 200 selections and event frames, and `getValue` returns content that virtualization keeps out of the DOM. It opens no new trust boundary, because React DOM's production build already puts `__reactFiber$` and `__reactProps$` on host nodes, but it is a stable, undocumented shape third parties could couple to. Read-only enforcement is inferred from source, not run. The handle exists only where an entry calls `installBrowserHandle()`: the Plite app on every build (`apps/plite/src/app/providers.tsx:8`), and www in development or in a build made with `NEXT_PUBLIC_PLATE_BROWSER_HANDLE=1` (`apps/www/src/components/context/providers.tsx:10-17`). Source: `docs/plite/research/2026-10-02-agentic-e2e-testing/shards/007-page-handle-audit.md:152-164`.
