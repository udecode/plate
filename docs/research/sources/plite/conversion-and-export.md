# Plite: conversion and export

## Streaming Markdown previews

- **Streaming reuse converts each finished segment once.** With `previous`, `editor.api.markdown.parseSlice` splits the growing source only at a blank line followed by an unindented block that is not a list item, with no open fence, math block, raw HTML block or registered block tag and no list or indented line before it. It keeps the converted blocks of every finished segment and converts only the text after the last one, and a source with a link reference or footnote definition parses whole (`findMarkdownSegmentBoundaries` in `packages/platejs/src/markdown/lib/internal/markdownSegments.ts:112`, `convertMarkdownSource` in `packages/platejs/src/markdown/lib/internal/markdownConversion.ts:540`). `packages/platejs/src/markdown/lib/markdownContinuation.spec.ts` ('equals a fresh parse at every prefix') checks every prefix of its fixtures against a fresh parse. The 2026-09-28 prototype of this rule (`docs/research/probes/2026-09-28-conversion-boundary/amendment/stream-reuse.ts`; bun 1.3.12, darwin/arm64, shared host at load 4–13) found 3,730 of 3,730 incremental previews, over 26 fixtures each split 26 ways, deep-equal to a fresh partial parse with the same diagnostics. With 64-byte chunks it cut cumulative parse on a rich transcript from 990 to 100 ms at 10 KB and from 24.6 to 0.72 s at 50 KB, and cumulative publication into an editor from 3.55 to 1.01 s and from 88.3 to 22.2 s; CJK transcripts moved alike. Limit: prototype numbers; the adopted code's are under Markdown streaming on the performance page, and `docs/research/decisions/conversion-boundary.md` owns the verdict (`amendment/REPORT.md:9-43`).

- Three measured facts behind the streaming-preview rules that content/docs/(plugins)/(serializing)/markdown.mdx's 'Streaming previews' section teaches (`docs/research/probes/2026-09-28-conversion-boundary/lanes/s4/REPORT.md:8-30`, 2026-09-29). The AI plugin store copies every value it receives, so parser reuse reached readers only once `setPreview` handed back the store's own earlier copy of each reused block, which raised kept blocks in a transport receipt from 0 of 55 to 55 of 55 (`packages/platejs/src/ai/react/AIChatPlugin.ts:1682-1683`). Replacing a whole CJK 50 KB preview through `replaceChildren` took 657–678 ms against 398–417 ms for `value.replace`, which is why a publication with no unchanged leading block replaces the value. On an editor with authored changes every ordinary node write needs an author ID and is recorded as an authored change, and 10 small preview splices grew `meta` to 24 KB, which is why an authored editable preview always replaces the value as a document load.

- Plate deleted its Markdown 'joiner' stream transform, which buffered AI chunks before parsing, because raw chunks with 32 ms preview coalescing beat it everywhere it was measured. `docs/research/probes/2026-09-28-conversion-boundary/lanes/s4/joiner-benchmark.test.ts` (it keeps a copy of the deleted joiner; run 4 of 4 on 2026-09-29, final values identical in every pair) measured joiner to raw: arrival-to-publish p95 from 7.96 s to 36–37 ms (rich 10 KB) and from 46.7 s to 36 ms (rich 50 KB), stream duration from 57.0 to 8.1 s at rich 50 KB, and cumulative work down 24–39%, although each preview costs more because it covers about three chunks. The trade-off is that rich text shows literal inline syntax such as `**ord` in 7–32 previews, each until the next publish at most 32 ms later. The proposed fix is for `partial` to hide a trailing unclosed inline delimiter; today it hides only an unfinished trailing tag (`packages/platejs/src/markdown/lib/types.ts:240-245`) (`lanes/s4/REPORT.md:94-116`).

- **What the restricted streaming prototype did not prove.** The 2026-09-28 prototype admitted only independent plain ASCII paragraphs and ATX headings with a small alphabet, rejecting ordered-list starts and indentation, and sent references, footnotes, fences, lists, registered tags, tables, math, emphasis, code, links, entities, escapes, Unicode and custom transforms to a full-parser fallback, which proves oracle equivalence, not incremental support. It does not establish general incremental Markdown, aggregate byte and node quota enforcement (the admitted path parsed slices separately, so whole-source quotas are another invalidation boundary), complete unchanged-node identity, or a 10/50 KB Chromium win, and its 50 KB sampling target was met for one of five pairs. Source: `docs/research/probes/2026-09-28-conversion-boundary/streaming/README.md:9-12`, `REPORT.md:102-112`. Limit: these limits describe the discarded prototype. The adopted `parseSlice(source, { previous })` reuses converted segments instead (`packages/platejs/src/markdown/lib/MarkdownPlugin.ts:70-85`), parses the whole source when it exceeds `maxBytes`, and gives each new segment only the node budget the earlier segments left (`packages/platejs/src/markdown/lib/internal/markdownConversion.ts:563-566`, `:605-612`).

- **Continued Markdown parses run remark plugins one segment at a time.** With a valid `previous`, `convertMarkdownSource` keeps earlier segments and runs each new segment's source through the whole remark pipeline as its own root (`convertRange`, `packages/platejs/src/markdown/lib/internal/markdownConversion.ts:601-624`, `:641`); the hint stays valid while the editor, compiled mappings, limits, the source prefix and each Markdown mapping owner's public plugin state object match (`:565-580`, `packages/platejs/src/markdown/lib/MarkdownPlugin.ts:106-131`). A remark plugin that reads or rewrites the whole tree therefore sees one segment at a time. On 2026-10-08 (HEAD `c70bacbd4a`, bun 1.3.12, `createTestEditor`) the global transform from the 2026-09-28 streaming probe, which appends the root's child count to every text, gave `One. (4)` through `Four. (4)` from a fresh partial parse of a four-paragraph source but `One. (1)` through `Four. (1)` when continuing a partial parse of its first two paragraphs, and the strict final parse with that hint returned the same `(1)` result, although `docs/research/decisions/conversion-boundary.md:129-131` requires reuse to equal a fresh partial parse. The probe had shown that such a transform makes earlier output depend on later text (`docs/research/probes/2026-09-28-conversion-boundary/streaming/dependency-probe.ts:27-36`), and the report warned that function identity cannot fingerprint mutable closure state (`streaming/REPORT.md:114-122`, `:171-173`). `markdownContinuation.spec.ts` checks prefix equality only with the built-in plugins. Limit: one scratch run with a synthetic transform; no shipped remark plugin was surveyed for whole-tree behavior; state a mapping reads from outside its plugin store also escapes the identity check (inferred from the code).

## Markdown loss accounting

- Markdown property accounting is verified by a round-trip conformance test, not at runtime. A 2026-09-28 probe (`docs/research/probes/2026-09-28-conversion-boundary/amendment/roundtrip-verify.ts`) serialized 44 fixture elements, parsed them back and compared every content property: the read-tracking accounting of that day missed real loss in 6 fixtures (list paragraphs lost `indent` and two lost `listStart` with no `markdown-property-omitted` report, because the list serializer claimed every list property) and reported nothing that survived, but serialize plus parse cost 404.3 ms against 85.7 ms for serialize alone on a 1,400-node corpus (4.7×). The check landed as `packages/platejs/src/markdown/lib/markdownConformance.spec.ts`, which fails when a property that does not survive goes unreported or a reported one survives, comparing list numbering by ordinal; runtime accounting reports every persisted property an encoder did not claim (`packages/platejs/src/markdown/lib/serializer/reportOmittedProperties.ts`).

- Markdown serialization rejects dropped visible content by default (`lossPolicy` defaults to `'reject'`, `packages/platejs/src/markdown/lib/internal/markdownConversion.ts:215`, `:245`), but a persisted property Markdown cannot carry, such as alignment, line height, text indent or a link `target`, is a `markdown-property-omitted` warning under every policy (`serializer/reportOmittedProperties.ts`, whose JSDoc says omission warns instead of failing the export). The 2026-09-28 loss-severity probe (`docs/research/probes/2026-09-28-conversion-boundary/amendment/loss-severity.test.ts`) showed what a stricter rule would break: each of those four cases would fail under `reject`, and `AIChatPlugin` serializes with the default policy through `requireMarkdownData`, which throws on failure (`packages/platejs/src/ai/react/AIChatPlugin.ts:69`, `:465-500`). The same probe found Link's HTML decoder inventing `target: '_blank'` for a link without one; the decoder now keeps `target` only when the source has it (`packages/platejs/src/features/link/lib/BaseLinkPlugin.ts:269-271`).

## DOCX loss policy

- DOCX export's loss classifier fails three diagnostic shapes under `reject`: `resource-omitted`, `unsupported-content` with `action: 'dropped'`, and `lossy-content` except the `named-root` and `document-metadata` features, which warn under every policy as they do in HTML and Markdown (`packages/platejs/src/docx/export/lib/exportDocx.tsx:374-382`). The D1 lane called it a negative list that fails closed for future emitters, but only those two `lossy-content` features are excluded by name; a new diagnostic code is not content loss until someone adds it. An `accepted` export drops a comment whose annotated content the projection removes and reports `authored-lossy-projection` as a warning, as Word drops a comment on a rejected suggestion (`exportDocx.tsx:177-188`). The registry export menu passes `lossPolicy: 'allow'` so the download always completes and toasts report what was lost, and it sets no `allowRemoteImages`, so export adds no network permission; package callers keep the `reject` default (`apps/www/src/registry/components/editor/export-toolbar-button.tsx:206-213`, `export-toolbar-button.spec.tsx:110`). Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/d1/REPORT.md:16-20`, checked against code 2026-10-08.

## DOCX output safety

- Two DOCX safety facts the public docs do not show (checked 2026-10-08). The writer's raw `data-equation-omml` sink writes whatever OMML it receives into `document.xml` (`packages/platejs/src/docx/export/lib/internal/xml-builder.ts:1553-1559`), so calling the writer directly can emit a live `DDEAUTO` field; `exportDocx`'s static rendering drops that markup today, and the final package check, which withholds output outside the passive vocabulary with `invalid-package`, is the defense in depth that `outputSafety.spec.ts` proves with an injected `DDEAUTO cmd.exe` field. On import, DOCX maps each HTML mapping loss to `unsupported-content` with the same action and, under `reject`, rejects every action except `unwrapped` (`packages/platejs/src/docx/import/lib/importDocx.ts:1307-1312`), so an HTML sanitizer removal that keeps visible content must report `unwrapped`, which `HtmlPlugin.ts` does for lossless and label-keeping removals (`packages/platejs/src/lib/plugins/html/HtmlPlugin.ts:3312-3322`). The same lane fixed two writer defects: a link kept only its first child, silently dropping later text, and GIF and BMP media were written without a content type, which made an invalid package (`docs/research/probes/2026-09-28-conversion-boundary/lanes/d1/REPORT.md:33-43`).

- **DOCX import and export do not go through the public HTML parser.** `importDocx` converts the package with Mammoth, parses the HTML with `DOMParser` and decodes it through `compileHtmlElementDecoder`, which applies the installed element mappings without calling the public `parseHtml`; since the conversion-boundary adoption that decoder runs the same whole-tree `sanitizeHtmlDom` pass before document preparation and again after it, so a parent mapping no longer reads an unsafe descendant (on 2026-09-28 a custom DOCX parent mapping persisted a descendant's `javascript:` href). `exportDocx` renders static React HTML with `renderStaticHtmlWithOverrides` and hands it to the DOCX writer instead of semantic HTML encoding, so caller-rendered components can emit hrefs that semantic encoding refuses; on 2026-09-28 a caller component's `data:text/html` href reached the DOCX relationship unchecked. DOCX output now rechecks image sources and navigation hrefs with the shared `decideUrl` role policy in `outputSafety.ts`. Code: `packages/platejs/src/docx/import/lib/importDocx.ts:248-258`, `packages/platejs/src/lib/plugins/html/HtmlPlugin.ts:3503-3555`, `packages/platejs/src/docx/export/lib/exportDocx.tsx:251`, `packages/platejs/src/docx/export/lib/outputSafety.ts:51`, `:136`. Source: `docs/research/probes/2026-09-28-conversion-boundary/safety/review.md:25`, `:28`, `:54-61`, checked against the code on 2026-10-08.

## DOCX exact-source retention

- Exact-source DOCX retention cleared its keep-or-delete gate. On 2026-09-29 (`HEAD` `a7750ad388` plus the D1 lane's changes), 20 of the 23 repository fixtures (87%) passed the passive eligibility vocabulary and all 20 exported byte-identical through exact reuse; 13 of the 15 verified pandoc fixtures were eligible. The three ineligible were `alternate_document_path` (main document at `word/document2.xml`, which import also fails), `legal` (`FILENAME` and `NUMCHARS` fields) and `links` (a `customXml` bibliography store). Across nine sibling clones (pandoc, mammoth.js, docx, docxjs, python-docx, docx-editor, eigenpal-docx-editor, docx-redline-js, docx-cli; nothing downloaded), 314 of 464 files (68%) were eligible and 184 of 285 Word-authored files (65%); the top first blockers were `customXml` data stores (47), Happy DOM parse refusals (18, 15 of them python-docx files with single-quoted XML declarations that browsers accept, so the share is a lower bound), `TOC` fields (9), `a14` drawing extensions (7) and orphaned styles parts (6). A vocabulary limited to parts the writer emits would have admitted 0 of 23, because every Word fixture carries `docProps/app.xml` vectors and VML shape defaults in `settings.xml`, so the vocabulary admits specification-passive items backed by fixtures instead. The repository corpus is small 2008–2016 feature fixtures, so the sibling share is the better estimate of third-party impact. This ran before commit `38914850a0` removed the Plate envelope, which Word files never carry (`docs/research/probes/2026-09-28-conversion-boundary/lanes/d1/REPORT.md:57-88`).

- DOCX source retention is opt-in and lives outside the editor value. `importDocx(input, { retainSource: true })` also returns an opaque `DocxSource`, or `null` with a `source-unavailable` warning when a package part falls outside the passive vocabulary exact reuse admits, and the caller passes it back as `exportDocx(editor, { source })` for exact or source-aware export; without a source, export generates the package from editor content (packages/platejs/src/docx/import/lib/importDocx.ts:77-104; packages/platejs/src/docx/export/lib/exportDocx.tsx:73-79). The 2026-09-15 reassessment chose this after seeing Plate's own toolbar import Word, edit and export Word while losing unrelated Word content; diagnostics make loss honest but do not preserve data. It required the artifact to bind the admitted package, semantic baseline, schema, comments and review projection, to return original bytes only when correspondence proves no change, and rejected hiding package state in editor metadata or adding a `DocxSession` (docs/plite/research/2026-09-15-docx-post-implementation-oss/README.md:25-56; shards/retained-source-and-package-editing.md:98-103). The proposed spelling `retention: 'preserve-when-safe'` with `exportToDocx` shipped as `retainSource` with `exportDocx`.

- Rejected DOCX designs, each with a reopen condition (2026-09-15): an OOXML tree as Plate's canonical model, reopened only if Plate becomes a native DOCX editor; package bytes hidden in editor state or metadata, which add a second implicit lifetime, contaminate generic persistence and can pair with the wrong document; a `DocxSession` or second editor facade, which would duplicate selection, transactions, comments, revisions and save lifetime; whole-ZIP passthrough treated as lossless, since regenerated owned parts still lose unknown content; raw XML surgery as the general export, since it cannot express arbitrary schema edits or configured static serializers; and README fidelity claims treated as proof, since no-op save, package reachability and state persistence fail independently (docs/plite/research/2026-09-15-docx-post-implementation-oss/rejected-ledger.tsv:2-7; shards/retained-source-and-package-editing.md:144-163).

- Retained-source DOCX export follows eight laws from the 2026-09-15 reassessment: retention is opt-in and passes the existing package limits before any bytes become durable state; the source is immutable, opaque, disposable and tied to one import identity, schema fingerprint and semantic baseline; exact reuse needs an unchanged review projection with matching comments and resources, while accepted or proposed projections are semantic transformations; preserve-when-safe names separate dimensions, whole parts, relationship reachability and XML inside parts; every edit maps to a source unit or invalidates it, and unexplained structural changes fall back or fail instead of reusing stale XML; digital signatures, unsafe relationships and other invalidated claims are dropped with diagnostics; `DocxDiagnostic` stays the only compatibility report; and proof compares an allowlist of changed package entries with semantic and review reopen results, the browser workflow, native office readability, memory and complete-operation time, because a no-op package diff or semantic equality alone is not enough (docs/plite/research/2026-09-15-docx-post-implementation-oss/shards/retained-source-and-package-editing.md:165-184). In current source the source-aware path refuses a part for four reasons, active content (signatures, ActiveX, controls, embeddings, VBA, OLE and macros), a conflict with a generated part, an external relationship and an unreachable part (packages/platejs/src/docx/export/lib/sourcePreservation.ts:36-90), though DOCX open gaps on this page notes that the active-content denylist can no longer fire for an eligible source; `pnpm bench:docx` runs a retained-source benchmark (benchmarks/editor/benchmarks/plate-docx-retained-source-benchmark.test.ts). Compliance with each law was not rechecked here.

## Document migration

- **`migrateV54` neutralizes stored URLs the current schema rejects.** The stage runs inside `migrateV54` after the profile and AST stages and before code-block flattening. A string is unsafe when the current schema's own validator for that element and key rejects it, the same check Markdown import uses, so the migration keeps no second role table. A link with an unsafe `url` is unwrapped to its label; an image, audio, video, file or media embed with an unsafe `url` becomes a paragraph of its caption children, else of its text alternative (a file's `name`, other media's `alt`), else is removed; an unsafe optional `sourceUrl` on video or media embed is omitted and the media kept; empty, safe and missing URLs pass unchanged, and a non-string or missing required URL passes unchanged and still fails schema assertion. Cleanup runs bottom-up, so a link inside a caption unwraps before its media is judged, and it covers named roots and every legacy suggestion revision. Persisted selections map moved text explicitly, keep the path of untouched text and fall back to the diff mapping only for text removed with its media. Code: `packages/platejs/src/migrations/migratePlateV54Urls.internal.ts:100-150`, `migratePlateV54Urls.spec.ts`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/v54-safety/REPORT.md:21-49`.

- **The v54 URL cleanup fails closed outside migration.** A current-version document with an unsafe URL still throws the schema validation error, and a stored v54 envelope written under a schema without the URL validators throws `Unknown schema fingerprint for plate@54.`, because adding `validationVersion: 1` to the eight URL descriptors (`url` on link, image, audio, video, file and mediaEmbed; `sourceUrl` on mediaEmbed and video) changed the generated contract fingerprint. Pinned by `packages/platejs/src/migrations/migratePlateV54Urls.spec.ts`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/v54-safety/REPORT.md:17-19`, `:66-70`, `:123-126`.

- **Open lead: a caret before a migrated legacy caption collapses.** A persisted caret in a block before a v53 media element whose legacy `caption` migrates into its children collapses to offset 0, with safe URLs too, so the cause is the profile stage's caption-migration diff mapping, not the URL cleanup. A probe test asserts the defect, and it still passed on 2026-10-08 (bun 1.3.12, HEAD `c70bacbd4a`), so the defect holds: `docs/research/probes/2026-09-28-conversion-boundary/lanes/v54-safety/kit-and-selection.probe.test.tsx:119`. No package test or plan tracks it. Owner: the migration profile's selection mapping in `packages/platejs/src/migrations/migratePlateV54Profile.internal.ts`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/v54-safety/REPORT.md:142-146`.

- **Replacement paragraphs drop the media's block properties.** The paragraph that replaces neutralized media is built fresh, as import builds one, so the media's `id`, indent or list membership and alignment do not carry over. Code: `packages/platejs/src/migrations/migratePlateV54Urls.internal.ts:144`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/v54-safety/REPORT.md:147-149`, checked against the code on 2026-10-08.

- **Migration removals are unreported.** Migration steps have no diagnostic channel, as the conversion-boundary adoption's amendment A4 intends, so media the v54 URL cleanup removes is reported nowhere; only the kept label, caption, alt text or file name remains. Checked: no diagnostic in `packages/platejs/src/migrations/migratePlateV54.ts` or `documentMigrations.ts` on 2026-10-08. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/v54-safety/REPORT.md:166-167`.

## DOCX import and export

- Plate's DOCX file conversion is one detached import and one projection-aware export, both returning structured results. `importDocx` returns `{ ok: true, document, comments, diagnostics }` or `{ ok: false, diagnostics }` and takes package `limits`, a `lossPolicy` and an `AbortSignal` (packages/platejs/src/docx/import/lib/importDocx.ts:77-126). `exportDocx` throws unless `projection` is `'accepted'`, `'proposed'` or `'review'` and returns `{ ok, blob?, diagnostics }` (packages/platejs/src/docx/export/lib/exportDocx.tsx:45-96,435-444); DOCX loss policy on this page covers how it classifies loss. Imported comments carry a target range, author, date, parent, durable id and resolved state (packages/platejs/src/docx/internal/types.ts:29-38). Word clipboard paste is the separate `WordPastePlugin` (packages/platejs/src/docx/paste/lib/WordPastePlugin.ts). This is the target the 2026-09-14 reassessment set: delete `exportAuthoredToDocx`, `ImportDocxResult.nodes` and file-import `rtf`, rename the paste-only `DocxPlugin`, and add structured diagnostics and bounded input (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/final-reassessment.md:8-20); none of the deleted names appears in packages/platejs/src/docx on 2026-10-08.

- Word XML is the only content authority on DOCX import. On 2026-09-14 `importDocx` returned the children of an embedded `editor/authored.json` sidecar whenever one existed, before it opened `word/document.xml`, and validated only JSON shape, so a file edited in Word reimported stale content; a replay confirmed it (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/plate-audit.md:33; README.md:29). The sidecar was later bound by a digest and then removed in commit 38914850a0, 'drop the hidden Plate envelope from DOCX packages'; no `authored.json` or envelope reader remains in packages/platejs/src/docx (git grep, 2026-10-08). Reusing source package content now requires the explicit retained source (see DOCX exact-source retention on this page).

- DOCX export reads the editor value once and derives every emitted part from that capture: `captureExportSnapshot` calls `editor.read.value()` a single time and projects it for the requested projection (packages/platejs/src/docx/export/lib/exportDocx.tsx:100-119). On 2026-09-14 the review export captured a snapshot, awaited conversion and then embedded a fresh `editor.read.value()`, so an edit during the await could split the visible XML from the embedded JSON (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/plate-audit.md:35).

- Review-projection DOCX export reuses the configured static renderer and wraps its rendered hosts in revision markup, and it reports an `unsupported-content` warning when a configured renderer omits its Plate path attributes (packages/platejs/src/docx/export/lib/reviewProjection.tsx:311-376). On 2026-09-14 review export ran a separate `exportAuthoredToDocx` serializer with literal element and mark tables that ignored the configured plugins and static wrapper and dropped table spans, alignment and widths (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/plate-audit.md:37); that function no longer exists.

- DOCX import does a fixed amount of heavy work whatever the revision count: one Mammoth HTML conversion, one package generation, one XML parse, one document diff and one ZIP load, as the revision-import benchmark asserts (benchmarks/editor/benchmarks/plate-docx-revision-import-benchmark.test.ts:247-261, over fixtures of 4, 16, 48 and 96 revisions at :56-80; `pnpm bench:docx` runs it measured). On 2026-09-14 import built a baseline plus one cumulative projection per revision, each repackaging the ZIP and calling Mammoth (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/plate-audit.md:49; shards/final-reassessment.md:45-48). The fix kept a single Mammoth pass that carries revision and comment markers (`importProjection`, packages/platejs/src/docx/import/lib/importDocx.ts:1150-1170) instead of the direct OOXML adapter the audit had ranked strongest.

- No universal conversion plugin, manager or registry has earned a place: Word paste, detached file import and snapshot export stay separate jobs, and merging them with CSV, pagination, comments or the authored runtime serves no current job; private format adapters may own code without new public nouns (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/plate-audit.md:80; rejected-ledger.tsv:6; promotion-packets.md:14).

- DOCX import admits a package only within finite limits before semantic import: by default 32 MiB input, 1,024 entries, 32 MiB per entry, 128 MiB expanded, 4,096 relationships, 2,000 revisions, 5,000 comments, XML depth 128 and 500,000 XML nodes, overridable through `limits`; only stored or deflate entries are accepted, declared and actual expanded sizes are both checked, and any XML part with a document type declaration is refused (packages/platejs/src/docx/internal/docxPackage.ts:21-31,188-191,328-404, checked 2026-10-08). The 2026-09-15 reassessment found this browser-facing boundary stronger than OpenDoc's host limits, Open XML SDK's optional per-part ceiling or docx-redline-js's unbounded ZIP reader, and required retained bytes to pass it first (docs/plite/research/2026-09-15-docx-post-implementation-oss/read-log.tsv:4,10,28,30). That read also listed a compression-ratio bound; neither the file's first commit (e0c1500b95, the same day) nor current source has one. Import calls Mammoth with only a comment-reference style map, so Mammoth's external-file access stays off, and decoded links pass the installed link codec's URL policy (packages/platejs/src/docx/import/lib/importDocx.ts:1158-1161; docs/plite/research/2026-09-14-docx-interoperability-oss/shards/final-reassessment.md:62-64).

- DOCX conversion is asymmetric on purpose. `importDocx(source, options)` is detached and captures plugins and schema before its first await (`packages/platejs/src/docx/import/lib/importDocx.ts:1601-1605`), while `exportDocx(editor, options)` stays editor-bound because export needs the configured static rendering and the adopted editor capture, and it throws a `TypeError` unless `projection` is `accepted`, `proposed` or `review` (`packages/platejs/src/docx/export/lib/exportDocx.tsx:434-444`). A detached DOCX export reopens only for a saved-document caller that brings full rendering configuration; symmetry with import is not such a caller. Source: `docs/plite/research/2026-09-25-document-codec-architecture/rejected-ledger.tsv:14` and `shards/004-editors-and-cross-language-controls.md:67`; code read 2026-10-08.

## Word paste

- Word paste deliberately drops every image and strips table `columnWidths` and cell `borders` and `size` after Word cleanup (packages/platejs/src/docx/paste/lib/WordPastePlugin.ts:328-330,344-353, checked 2026-10-08). The 2026-09-14 audit first asked to preserve them, then corrected itself: keeping Word clipboard media and geometry safely needs a destination media and upload policy, payload-size limits and table-specific evidence, so the omission stays explicit and that policy is deferred rather than silently keeping data URIs, local or CID references, remote resources or Word layout debris (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/plate-audit.md:43; shards/final-reassessment.md:55-60). The audit also noted that the paste path's CSS inlining serves non-Word HTML, so it must not move behind Word detection.

## DOCX export fallbacks

- Several node types export to DOCX through presentation fallbacks, not semantic round trips. The package's `DOCX_STATIC_COMPONENTS`, which export applies as overrides to its static render (packages/platejs/src/docx/export/lib/exportDocx.tsx:251-255), render columns and callouts as tables, equations as their literal LaTeX, headings with an anchor `id` from the export-time node key and TOC entries as fragment links to it, and code blocks with `data-docx-preserve-whitespace`, which the package turns into non-breaking spaces (packages/platejs/src/docx/export/lib/docxStaticComponents.tsx:19-211; packages/platejs/src/docx/export/lib/exportHtmlToDocx.internal.ts:17-25; checked 2026-10-08). The OMML branch needs `data-equation-omml` input and is not a LaTeX-to-OMML converter (packages/platejs/src/docx/export/lib/internal/render-document-file.ts:232-251), and reimport cannot restore a callout or column node. The 2026-09-14 audit found these fallbacks in copied registry renderers (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/plate-audit.md:63-67); the registry `*-static.tsx` files still export `*Docx` variants, but no repository code imports them (git grep, 2026-10-08).

## DOCX proof limits

- The DOCX package roundtrip test normalizes link URLs, and its inline formatting case asserts only that the reimported document has children (apps/www/src/__tests__/package-integration/docx.roundtrip.slow.tsx:102-129, checked 2026-10-08), so it does not show that formatting survives a round trip (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/plate-audit.md:97).

## Formats without an exporter

- CSV and RTF have no document exporter. `CsvPlugin` turns CSV text into a table through `api.deserialize` and a `text/plain` paste format (`packages/platejs/src/csv/lib/CsvPlugin.ts:42`, `:161-172`), and `text/rtf` is read only by `WordPastePlugin` while it prepares pasted Word HTML (`packages/platejs/src/docx/paste/lib/WordPastePlugin.ts:386`). The 2026-09-24 export audit found no evidence for adding either exporter (`docs/plite/research/2026-09-24-export-architecture/shards/001-direction.md:124-126`; code read 2026-10-08).

## Former names

- The 2026-09-25 hard rename changed these conversion names with no aliases, so older plans and research use the left-hand names. Browser transfer: `HostCodec` became `DataTransferFormat` (fields `format` and `owns` became `mimeType` and `claims`, callbacks `parse`, `query` and `serialize` became `decode`, `accept` and `encode`), `hostCodecs` became `dataTransferFormats`, `HostDataSource` became `DataTransferSnapshot`, and `writeHostFragmentData` became `writeDataTransferFragment`. Plugins: `codecs` and `defineCodecs` became `formats` and `defineFormats`, `MarkdownNodeCodec` became `MarkdownNodeMapping`, `PlainTextNodeCodec` became `PlainTextNodeMapping`, `PluginCodecNode` became `PluginFormatNode`, and `HtmlCodecHooks` was deleted in favor of an HTML mapping's `prepareDocument`. HTML: `HtmlApi.deserializeDocument` and `deserialize` became `parse` and `parseSlice`, and `parseHtmlDocument` became `parseHtml`. Markdown: `MarkdownApi.deserialize` and `deserializeInline` became `parse` and `parseInline`, and `deserializeMd` and `serializeMd` became `parseMarkdown` and `serializeMarkdown`. DOCX: `exportToDocx` became `exportDocx`, and `importDocx(editor, source)` became `importDocx(source, { plugins, schema })`. The authored HTML and Markdown entrypoints (`parseAuthoredHtmlDocument`, `deserializeAuthoredHtml`, `renderAuthoredHtml`, `parseAuthoredMarkdownDocument`, `serializeAuthored`) were deleted, and `PropertyJsonValue` merged into `EditorJsonValue`. Later changes replaced parts of this map: `EditorValueCodec`, `EditorValueDecoder` and `defineValuePersistence` no longer exist, and standalone `parseMarkdownSlice` and `parseMarkdownInline` were cut. Source: `docs/plite/research/2026-09-25-document-codec-architecture/affected-export-symbol-diff.tsv`; current names checked with `git grep` on 2026-10-08.

## Public surface by job

- Not every public encode or decode is a document format. The 2026-09-25 classification of the conversion-named public surface (349 rows: 176 keep, 3 defer, 170 unrelated name matches) keeps durable-state encodings apart from external formats: versioned value persistence (`valueCodecs`, `encodeVersionedValue` and `decodeVersionedValue` in `packages/plitejs/src/core/value-codec.ts:427-521`), editor effect and collaboration transports, `pageSettingsCodec` (`packages/plitejs/src/pagination/index.ts:286`) and the selection wire protocol (`encodeEditorSelection` and `decodeEditorSelection`, `packages/plitejs/src/core/selection-protocol.ts:261`, `:286`), which has its own version and validity laws. Document migration (`migrateDocument`, `defineDocumentMigrations` and `migrateV54` under `packages/platejs/src/migrations/`) is a separate persisted-schema job and is never folded into lossy conversion. Structural plain text (`serializePlainText`, `serializeStructuralPlainText`) is a one-way projection named as serialization, not a codec. Source: `docs/plite/research/2026-09-25-document-codec-architecture/api-ontology.tsv` rows 212-350, regenerated after adoption on 2026-09-25; names rechecked with `git grep` on 2026-10-08, when `defineValueCodec` and `EditorValueCodec` from those rows no longer existed.

## HTML parsing

- Browser HTML parsing avoids `DOMParser`. The 2026-09-25 research rejected it because it disables scripts but may still fetch `img` and `iframe` resources and is a Trusted Types sink under a strict CSP, so it cannot promise network isolation. Its Chromium probe materialized parse5 output node by node into the owner document of a detached `template` under `require-trusted-types-for 'script'`: head, body and the editor marker survived, no script ran and no image, iframe or stylesheet request fired (`docs/plite/research/2026-09-25-document-codec-architecture/html-browser-inertness.json`). The shipped code materializes into `document.implementation.createHTMLDocument('')` instead (`createBrowserHtmlDocument`, `packages/platejs/src/lib/plugins/html/htmlAst.ts:566-573`), so that probe did not exercise the shipped document. The standalone parse5 8.0.1 `parse` and `parseFragment` entry measured 151,560 minified and 42,013 gzip bytes (`docs/plite/research/2026-09-25-document-codec-architecture/parse5-browser-bundle.json`), and the research capped parser overhead at 60 KiB gzip, a cap no standing check enforces (`git grep`, 2026-10-08). Source: `docs/plite/research/2026-09-25-document-codec-architecture/README.md:55-58`, `shards/006-saturation-and-final-synthesis.md:43-58`, read-log rows 33-36.

- Node HTML parsing goes through `platejs/html/server`: parse5 builds and serializes the canonical repaired tree, then LinkeDOM materializes it as the element facade Plate's mappings read. LinkeDOM is an optional peer, and the entrypoint throws an install instruction when it is missing (`packages/platejs/src/html/server/index.ts:15-29`). LinkeDOM alone was fast and light but did not match browser tree construction for malformed fragments, and LinkeDOM 0.18.13's `CSSStyleDeclaration` lacked `item()`. The correctness probe passed 10 malformed or conformance cases and 6 Plate conversions with parse5 8.0.1 and LinkeDOM at `fcd88e02`: the canonical tree survived materialization, custom dataset and style mappings worked, and scripts and `javascript:` URLs neither ran nor survived (`docs/plite/research/2026-09-25-document-codec-architecture/html-server-parse5-linkedom-correctness.json`, a focused guard, not the parse5 conformance suite). The rejected happy-dom adapter, one isolated Window per parse with scripting, network, CSS, iframe and computed style off, retained about 320 MB per completed stress parse, and repeated 1.47 MB parses exhausted a 4 GB process; the shard states this in prose, and no stress-cohort JSON was saved. Source: `docs/plite/research/2026-09-25-document-codec-architecture/README.md:59-63`, `shards/006-saturation-and-final-synthesis.md:8-20`, `:34-41`, `:60-69`.

- HTML parsing takes overridable resource limits, by default `maxBytes` 5 MiB, `maxNodes` 100,000 and `maxDepth` 256 (`packages/platejs/src/lib/plugins/html/htmlAst.ts:25-29`). A breach returns `ok: false` with an `html-limit-exceeded` diagnostic naming the limit and no partial document or slice; the test covers `maxBytes` and `maxDepth` (`packages/platejs/src/html/html.spec.ts:109-126`). The 2026-09-25 research required the limits to be checked while parsing or walking, before mappings allocate an editor tree, because schema validity is not a resource budget and each format owns its own limits. Source: `docs/plite/research/2026-09-25-document-codec-architecture/shards/006-saturation-and-final-synthesis.md:71-82`, `shards/003-document-pipelines-and-source-retention.md:58-59`; code read 2026-10-08.

## Fidelity claims

- A conversion claim names one of four fidelity levels: source exact (original bytes or package units are reused), source aware (unchanged regions reuse source through explicit correspondence while changed regions print canonically), semantic (admitted meaning survives while syntax may normalize), or native model (an embedded Plate value rebuilds editor state but proves nothing about the visible external form). Plate's HTML and Markdown promise semantic fidelity only, DOCX keeps an opt-in `DocxSource` for exact or source-aware reuse, and exact review state is the canonical authored JSON. Source: `docs/plite/research/2026-09-25-document-codec-architecture/shards/003-document-pipelines-and-source-retention.md:22-32` (2026-09-25); the current owners are in `docs/research/decisions/import-fidelity.md` (Fidelity and source ownership) and `docs/research/decisions/documents-conversion-fidelity.md`.
