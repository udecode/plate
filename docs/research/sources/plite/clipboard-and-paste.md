# Plite: clipboard and paste

## Paste proof

- Three clipboard proofs came from the 2026-06-12 clipboard research. A native Chromium IME composition stays coherent when a real clipboard paste lands at the composition point: the test writes the browser clipboard, presses the real paste shortcut while the composition is open, commits it, and asserts model text and selection at the adjusted caret (`apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:2825`); a synthetic paste during composition is too weak for this class (`rejected-ledger.tsv:3`). A ProseMirror `data-pm-slice` text slice pastes only its visible text and a table-row slice imports as a table row, neither exposing the slice metadata, on Chromium, Firefox and WebKit (`apps/plite/tests/plite-browser/donor/examples/paste-html.test.ts:1691`, `:1715`). Runtime copy, cut and paste handlers flush pending native text input before app callbacks or model clipboard commands read state (`packages/plitejs/src/react/editable/runtime-clipboard-events.ts:101`, `:154`, `:181`). Source: `c70bacbd4a:docs/plite/research/2026-06-12-oss-clipboard-paste-architecture/README.md:29-43`.

## Paste and copy boundaries

- Pasting into text right before a read-only inline keeps that inline and everything after it (`apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:1587`, from WPT `copy-paste-before-non-editable`); copying hidden or unmounted content writes model-backed data instead of browser DOM serialization (`apps/plite/tests/plite-browser/donor/examples/hidden-content-blocks.test.ts:191`); and when an app `onPaste` mutates `event.clipboardData` and returns false, Plite inserts the mutated payload (`packages/plitejs/test/react/dom-coverage-native-bridge-contract.test.ts:1426`, from WPT `paste-clipboard-change`). Source: `c70bacbd4a:docs/plite/research/2026-06-13-wpt-editing-oracles/lead-ledger.tsv:13-15`.

- When the pasted `text/html` holds the same text as `text/plain`, verbatim or with no element inside its body, as autocorrect and word-prediction pastes do, the Plite richtext and paste-html examples hand the paste to the plain-text fallback so collapsed active marks apply. `isPlainTextClipboardHtml` makes that check (`apps/www/src/app/(app)/examples/plite/_examples/paste-html-import.ts:113-121`, called at `:697` and in `richtext.tsx:384`), and the plain-text fallback applies collapsed active marks (`packages/plitejs/test/dom/clipboard-boundary.ts:2575`). Browser proof: `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:1178`, `keeps active bold after same-html plain paste`. Before June 2026 the transaction-level fallback dropped active marks and an exact-match guard missed browser-normalized wrapper HTML. Source: `c70bacbd4a:docs/plite/research/2026-06-14-selection-paste-undo-oracles/README.md:21-35`; code read 2026-10-08. Limit: the HTML check lives in the examples' `insertData` handlers, not in the runtime.

- More Plite paste rows from the 2026-06-13 run, checked 2026-10-08 under `apps/plite/tests/plite-browser/donor/examples/`. Content pasted outside an inline link's boundaries does not expand it, and plain text pasted inside a link does not split it (`inlines.test.ts:603`, `:740`). ProseMirror slice list items paste without runtime errors (`paste-html.test.ts:1661`); the text and table-row slice rows are already on this page. Executable rich HTML and Word conditional junk are sanitized (`paste-html.test.ts:1449`, `:1492`). Text pasted and HTML dropped inside a same-runtime child root do not steal the outer selection (`editable-voids.test.ts:1166`, `:1305`). Copying a paginated table copies the rows that pagination omits, from the model (`pagination.test.ts:241`). The June run cited these rows under retired `.tmp/plite` paths. Source: `c70bacbd4a:docs/plite/research/2026-06-13-oss-rich-html-paste-clipboard-invariants/README.md:18-28`, `:40-53`.

- Pasting two copied paragraphs into an empty block quote keeps the first paragraph's text in the quote and promotes the second after it as a paragraph, with the caret at the end of the promoted text (`packages/plitejs/test/dom/clipboard-boundary.ts:1861`, 'keeps the target context for the first open block and promotes the tail'). This is the Plite side of Lexical's paragraph-into-quote paste row (`docs/research/sources/lexical/clipboard-and-paste.md`, Block types on paste); the context-menu copy and paste flow in the row before it is product UI. Source: `c70bacbd4a:docs/editor-test-harvester/lexical/plite-processing-ledger.md:132-133`.

- **Each paste and copy route decides content on its own channel.** Word paste prepares Word HTML and decodes it with `decodeHtmlDataTransfer`, so it shares HTML paste's sanitization, unlike DOCX file import (see the DOCX unit); Markdown paste admits what the installed Markdown mappings admit; and copy encodes each MIME type separately, so a safe or absent `text/html` says nothing about the Markdown or plain-text payload written beside it, and plain text holding a URL is not active content. The exact internal clipboard envelope is a separate channel that carries the model slice and never passes through the HTML parser. Code: `packages/platejs/src/docx/paste/lib/WordPastePlugin.ts:384-389`, `packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts`. Source: `docs/research/probes/2026-09-28-conversion-boundary/safety/review.md:29-31`, `:63-67`. Limit: the 2026-09-28 observations of unsafe URLs surviving these routes were closed by the conversion-boundary adoption; only the routing is current, and the internal channel was traced, not driven through an OS clipboard.

## Paste reports

- HTML paste reports every sanitizer removal through `onPasteResult`, lossless ones included. `decodeHtmlTransferWithArtifact` passes each diagnostic of its `allow` parse to `context.report`, taking impact from the diagnostic and treating anything but parser recovery as lossy (`packages/platejs/src/lib/plugins/html/HtmlPlugin.ts:3339-3380`), and removing `<base>`, `<link>`, `<meta>`, `<script>` or `<style>` is lossless (`htmlSafety.ts:22-23`). Browser and Google Docs clipboard HTML usually starts with `<meta charset>`, so most rich pastes carry one lossless 'Removed unsafe HTML element <meta>.' report; a mounted 2026-09-29 receipt showed an unsafe-href paste inserting 'Before LABEL After' with one lossless diagnostic and a dropped image with one lossy one. A consumer that toasts on paste results should ignore lossless reports; on 2026-10-08 no registry component reads `onPasteResult`, the registry toast having been removed by the `2026-09-29-imports-opt-in-paste-result` decision (`docs/research/probes/2026-09-28-conversion-boundary/lanes/html-safety/REPORT.md:134-139`, `:251`; `lanes/s5/REPORT.md:110`).

- **A paste result settles once, after commit or on refusal.** The internal `observeDataTransferInsertion(editor, listener, insert)` in `plitejs/dom` opens one observation per editor runtime owner, and `recordDataTransferOutcome` binds only the first built-in insertion under it, so later insertions and other editors are not attributed to it. A success settles `inserted: true` from `attachTransactionSpecAfterCommit`, which survives `transaction.extend`, continuations and the projected-selection rebase; a refusal, or an insertion that committed no net change, settles `inserted: false` when the observed call returns; inside an open outer update it waits for that update's commit; a throw or rollback settles nothing. Code: `packages/plitejs/src/dom/plugin/data-transfer-format.ts:806-893`, `packages/plitejs/src/core/public-state.ts:926`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/t1/REPORT.md:23-33`, checked against the code on 2026-10-08.

- **Only three mounted paths report a paste result.** The `paste` handler (its whole body, so a refusal reports after repair), `beforeinput` with `insertFromPaste`, and Android's deferred `insertFromPaste` run inside the receiving view's `EditableDOMRuntime.runPaste`, which reads that view's current `onPasteResult` (kept fresh by the same update that sets `onHistoryReplay`) and delivers only while that view stays mounted, never to another view. `insertFromYank`, the browser test handle, a separate programmatic `insertData` call, an `onPaste` handler or `domCommands.insertData` handler that handles the paste without the built-in insertion, and read-only views report nothing through it, and the app or plugin owns those outcomes; an `onPaste` handler that calls `insertData` during the paste gets that insertion's result, as the clipboard guide says. Drops report through the separate `Editable.onDropResult` (`packages/plitejs/src/react/components/editable.tsx:286`, `runDrop` in the same runtime), which no public doc names yet. Code: `packages/plitejs/src/react/editable/editable-dom-runtime.ts:1140-1182`, `runtime-before-input-events.ts:1151-1152`, `runtime-clipboard-events.ts:100`, `packages/plitejs/src/react/hooks/android-input-manager/android-input-manager.ts:681`, test `packages/plitejs/test/react/editable-paste-result.test.tsx:318`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/t1/REPORT.md:35-46`, checked against the code on 2026-10-08.

- **Known silent paste outcomes.** An undiagnosed refusal of a rich slice that then falls back to plain text reports nothing about the rich loss; a paste that commits no net change reports `inserted: false` while `insertData` returns `true`; and a paste inside an outer update that ends with no net change is never reported, because its after-commit hook never runs. Mechanism: `packages/plitejs/src/dom/plugin/data-transfer-format.ts:885-891`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/t1/REPORT.md:171-175`. Limit: stated by the lane on 2026-09-29 and consistent with the current settlement code; no test pins the outer-update case.

## Browser differences

- Browsers disagree on normalizing link URLs in pasted HTML. On 2026-09-29, a trusted Ctrl+V of `<a href="https://example.com">` arrived as `https://example.com/` in Chromium and WebKit, while Firefox's paste and synthetic paste events that bypass the browser clipboard kept `https://example.com`. Plate's `decideUrl` does not normalize an accepted URL (`packages/platejs/src/internal/utils/urlPolicy.ts:63-114`), so a stored link keeps whichever form the browser delivered, and `apps/www/tests/browser/clipboard.spec.ts:66` accepts both (`docs/research/probes/2026-09-28-conversion-boundary/lanes/s5/REPORT.md:253-256`, `:262-267`; Firefox 151, WebKit rev 2311, chromium-headless-shell 149).

## Paste transform points

- Plite has no separate public paste-transform chain like Tiptap's `transformPastedHTML`. With the `dom()` clipboard enabled, foreign data enters through the `dom.insertData` command (`packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:56`), exposed as `editor.api.dom.clipboard.insertData`. A plugin wraps it with `around` command middleware, as `dom()` does itself to tag the resulting transaction `paste` (`packages/plitejs/src/dom/plugin/with-dom.ts:215-228`). `dom({ clipboard: false })` hands parsing and fallback insertion to a host package (`with-dom.ts:110-117`). The June 2026 run recorded the same decision against the older `clipboard.insertData` extension shape, with sanitizer and whitespace normalization proven by the `paste-html` rows. Source: `c70bacbd4a:docs/plite/research/2026-06-13-oss-rich-html-paste-clipboard-invariants/lead-ledger.tsv:7`.

- **The `paste` tag does not mean anything was inserted.** Plite's DOM plugin wraps `domCommands.insertData` and adds the `paste` tag to every result that is not `false`, including a transaction that only moves the selection. The mutation controller also commits a paste-tagged rebase that changes nothing when the insertion is empty. A headless probe registered an `insertData` handler that only moved the selection; it produced a commit with `changes.empty === true` and the `paste` tag. Code that asks whether a paste applied must also check that the commit changed roots, as the test harness does. Evidence: `packages/plitejs/src/dom/plugin/with-dom.ts:215-228`, checked 2026-10-08; `docs/plite/research/2026-10-02-agentic-e2e-testing/review/execution-panel/round2-gpt-6.1-sol.md:5-13` and `round2-opus.md:41`; the empty-insertion commit is `packages/plitejs/src/react/editable/mutation-controller.ts:402-411`; `packages/test/src/playwright/harness-input.ts:93-105`.

- **Raw Plite pastes foreign content as plain text.** The substrate does not know a product schema, so `dom()` registers only a plain-text `DataTransferFormat` (owner `editor-dom`, `createDefaultDataTransferFormatRegistration`, `packages/plitejs/src/dom/plugin/data-transfer-format.ts:419-434`) beside its own fragment payload, and `createDOMDataTransactionSpec` tries the editor's exact fragment, then installed formats, then that plain-text fallback (`packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:692-712`). Rich HTML import comes only from an installed format or a `domCommands.insertData` interceptor: the Plite `paste-html` example ships its own `html()` plugin (`apps/www/src/app/(app)/examples/plite/_examples/paste-html.tsx:23`, `:27`), and the HTML format in Plate's paste order belongs to platejs. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/general/faq.mdx:8-17`; code read 2026-10-08.

## Open paste questions

- Rich HTML pasted into a same-runtime child root inside an editable void inserts its text but drops its marks. A 2026-06-13 Playwright experiment pasted `<strong>` HTML there and failed on Chromium, Firefox and WebKit because no `strong` element appeared. The runtime did not crash, focus did not leak and the outer editor stayed isolated. The editable-voids route renders marks from its model but does not install the rich HTML deserializer that the `paste-html` example adds through its `html()` plugin (`apps/www/src/app/(app)/examples/plite/_examples/paste-html.tsx:27`). Which deserializer a child root uses is therefore an open paste API decision, not a regression. The test was reverted, and no row covers it on 2026-10-08. Lexical's `7635-SELECTION_INSERT_CLIPBOARD_NODES_COMMAND.spec.mjs` is the matching external case. Source: `c70bacbd4a:docs/plite/research/2026-06-13-oss-rich-html-paste-clipboard-invariants/README.md:30-38`, `:55-64`.

## Table fragments

- **Core slice replacement is not table-grid aware.** Pasting a cell slice into a table cell through Plite core merges the first compatible source cell into the active cell and inserts the later source cells as siblings before the existing following cells; positional grid merge belongs to a table plugin. The fixtures `packages/plitejs/test/transforms/insertFragment/of-tables/merge-into-empty-cells.tsx:40-43` and `merge-into-full-cells.tsx:39-42` pin that output, and `merge-cells-with-nested-blocks.tsx` is skipped through the explicit-cut list (`packages/plitejs/test/fixture-claim-overrides.ts:36`, read by `packages/plitejs/test/index.slow.ts:78-83`). In June 2026 all three fixtures were skipped and the run left table-fragment policy open (`c70bacbd4a:docs/plite/research/2026-06-12-table-fragment-semantics/README.md:31-44`); legacy Slate still skips them. Plate's table plugin owns the grid paste (see `docs/research/sources/editor-architecture/tables.md`).

## Coverage boundaries

- When a copied range crosses DOM coverage boundaries, Plite writes one model slice with every `exclude` boundary's covered paths cut out, into plain text, HTML and the editor fragment alike (`getModelSliceWithoutExcludedBoundaries` and `writeDOMRangeData`, packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:243-292,519-562). The test 'composes model and exclude coverage into every clipboard mimeType' copies four paragraphs, Visible, Omitted under a `model` boundary, Excluded under an `exclude` boundary, and End, and expects plain text `Visible\nOmitted\nEnd` with no Excluded in the HTML or fragment (packages/plitejs/test/dom/clipboard-boundary.ts:1624-1680). On 2026-09-11 the same case also exported Excluded, because any `model` boundary exported the whole slice (docs/plite/research/2026-09-11-large-documents-contract/shards/001-native-and-lifetime.md:29-35). Limit: JSDOM unit proof, no OS clipboard session.

## Clipboard envelope

- **The exact clipboard slice travels twice, and both copies carry the editor's `clipboardFormatKey`.** Copy writes the encoded slice under `application/<clipboardFormatKey>` (default `x-editor-fragment`) and, when it also writes `text/html`, stamps the first opening tag with `data-editor-fragment` and `data-editor-fragment-format="<clipboardFormatKey>"`. It leaves HTML that already carries that exact pair unchanged, and wraps the HTML in a `span` that carries the pair when the HTML has no opening tag or already holds another `data-editor-fragment` attribute (`attachFragmentMetadataToHtml`, `packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:118-151`). Paste reads the MIME payload first and falls back to the HTML attribute only when its format attribute equals the key, or is absent while the key is the default (`readClipboardFragmentPayload` and `getFragmentAttribute`, `packages/plitejs/src/dom/utils/dom.ts:267-311`), so editors with different keys never import each other's exact JSON through either copy; `readSlice` reports an invalid payload with `source: 'html' | 'mime'`. The attribute is matched on opening tags with a regular expression, not passed through the HTML parser. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/libraries/plite-react/react-editor.mdx:251-254`; code read 2026-10-08. Limit: neither the source nor the code says why the HTML copy exists, and no OS clipboard run was made.

## DataTransfer format negotiation

- **How `dataTransferFormats` negotiate a paste or copy.** `dataTransferFormats(name, formats)` installs schema-aware MIME formats as one named plugin (`packages/plitejs/src/dom/plugin/data-transfer-format.ts:640`). Compilation rejects the whole configuration when two formats share a `key`, or when two formats claim the same element or schema property for one MIME type and direction; decode and encode claims are checked separately (`:457-493`, `:582-627`). A claim on an unknown element or an uninstalled property also throws (`:544-575`). Formats are sorted in reverse configuration order, so the last configured format gets the first try (`:628`). The built-in plain-text format (owner `editor-dom`, see 'Raw Plite pastes foreign content as plain text') is always placed first before that sort (`withDefaultDataTransferFormat`, `:427-435`, used at `:659` and `:684`), so it runs last. On paste: `accept` returning `false` skips a format; `decode` returns a slice payload or `null`; the payload goes through `ContentSliceApi.fromJSON` inside the same guard, so an invalid one is reported as a `decode` error; and a slice that the `replaceSlice` command refuses passes to the next format without a partial write (`:943-976`). On copy, `writeDataTransferFragment` writes each MIME type once, the first string wins, and a result that is neither a string nor `null` counts as an `encode` error (`:1014-1063`). A throw in `accept`, `decode` or `encode` goes to the editor's lifecycle error sink with `source: 'data-transfer-format'` and the plugin name, MIME type, key and phase, and negotiation continues with the next format (`:58-74`, `:954-956`). Source: `c70bacbd4a:docs/plite/reference/public-docs/libraries/plite-dom.mdx:91-178`; code read 2026-10-08. Limit: read, not run; the tests are in `packages/plitejs/test/dom/data-transfer-format.test.ts`.
