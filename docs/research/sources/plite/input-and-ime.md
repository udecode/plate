# Plite: input and IME

## IME overlap policy

- On 2026-06-12 the IME overlap research asked the owner whether Plite should adopt ProseMirror-style overlap cancellation (checkpoint `ime-overlap-cancellation-taste`) and recommended yes; it rejected merging or rebasing a composition with an overlapping edit because no inspected editor does that and it is harder to prove (`docs/plite/research/2026-06-12-ime-overlap-policy/README.md:88-101`, `rejected-ledger.tsv:2`). Its proposal also asked that renderer and normalizer work never rewrite the active composing node unless the overlap rule ends the composition, that render, selection, caret and textarea writes stay suppressed or go through that cancellation while a composition is active, and that a duplicate or missing `compositionend` never strand composition ownership (`README.md:34-35`, `:76-80`). The question is still open: `docs/vision/plite.md:675` makes IME overlap policy-owned, limits route proof to composition at or beside the edit point, and requires an accepted plan whose proof drives a real native composition span before any runtime overlap work. The candidate rules are `EDIT-IME-OVERLAP-CANCEL-001` and `EDIT-IME-NONOVERLAP-KEEP-001`.

## Model edits beside an active composition

- Two native Chromium IME rows prove model edits beside an active composition: a model insert before the composition point keeps the composition, which commits at the adjusted caret with correct model selection, and a model text removal starting at the composition point keeps the deleted text deleted while the composition commits at that point (`apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:2687`, `:2756`). They cover the non-overlapping class only; an edit that intersects the composition span is policy-owned (`docs/vision/plite.md:675`, candidate rule `EDIT-IME-OVERLAP-CANCEL-001`). Source: `docs/plite/research/2026-06-12-oss-input-selection-architecture/README.md:28-39`.

## Enter during composition

- Plite's keyboard strategy leaves Enter during an active composition to the browser: the keydown comes back handled without `preventDefault()`, the Editable's `onKeyDown` handler does not run and the model stays unchanged, as the package contract `keeps Enter during active composition browser-owned` proves at the routing level (`packages/plitejs/test/react/keyboard-input-strategy-contract.test.ts:1116`). It does not cover an `insertParagraph` beforeinput during composition, and it does not prove native commit-before-line-break behavior on Windows, macOS, Safari or Firefox IMEs, which needs a real IME or device lane. Source: `docs/plite/research/2026-06-13-contenteditable-catalog-oracles/README.md:23-40`, `:58-64`. Candidate rule: `EDIT-IME-ENTER-COMPOSING-001`.

## beforeinput target ranges and payloads

- Plite's beforeinput handling follows WPT. The event's target range, captured at dispatch, wins over a later live DOM selection (`packages/plitejs/test/react/selection-reconciler-contract.test.tsx:1036`); target ranges whose endpoints are block or list elements resolve before the live-selection fallback (`:1127`); a set of several target ranges, as when a delete crosses editing-host boundaries, is never collapsed to its first segment, because the reconciler uses a target range only when exactly one exists (`packages/plitejs/src/react/editable/selection-reconciler.ts:624`, test `:1294`). Insert and delete beforeinput with zero native selection ranges and no target ranges is ignored, while format input still reaches app handlers (`shouldIgnoreDOMBeforeInputWithoutSelection`, `packages/plitejs/src/react/editable/runtime-before-input-events.ts:352-362`; tests `packages/plitejs/test/react/runtime-before-input-events-contract.test.ts:201`, `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:1527`). `insertFromPaste` reads the contenteditable `dataTransfer`, not textarea-style `event.data` (`packages/plitejs/test/react/editing-kernel-contract.ts:329`). `deleteByCut` deletes the selected fragment through the model path (`packages/plitejs/test/react/model-input-strategy-contract.test.ts:862`), but a `deleteByDrag` beforeinput yields no command, because only a drop this editor settled may remove a drag source (`packages/plitejs/src/react/editable/editing-kernel.ts:716-717`, `model-input-strategy.ts:318-320`); the June ledger's claim that both delete the fragment is superseded. Browser `execCommand` DOM mutation is not Plite-owned; its inputTypes map to editor commands, and native history beforeinput applies undo and redo (`apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:7584`). Source: `docs/plite/research/2026-06-13-wpt-editing-oracles/lead-ledger.tsv:2-8`.

- A native `beforeinput` with a format `inputType`, such as `formatBold`, reaches the `Editable` `onDOMBeforeInput` handler once with that `inputType`, and a handler that returns `true` prevents the browser default; `onBeforeInput` is never replayed from a native `beforeinput` (`packages/plitejs/test/react/editable-behavior.tsx:1149`, `:1193`). The 2026-06-13 WPT run counted this raw format exposure among the surfaces Plite owns in place of browser `execCommand` DOM mutation. Source: `docs/plite/research/2026-06-13-wpt-editing-oracles/README.md:66-75`; tests read 2026-10-08. Limit: JSDOM tests with a synthetic `InputEvent`, not a browser row.

- A `beforeinput` event's target ranges may set the edit range even when the live-selection policy is model-owned and blocks DOM selection import. `shouldAllowBeforeInputSelectionImport` allows import when that policy allows it or when the event carries a target range (`packages/plitejs/src/react/editable/runtime-before-input-events.ts:364-371`; contract 'beforeinput target ranges can import even when live DOM selection policy is model-owned', `packages/plitejs/test/react/runtime-before-input-events-contract.test.ts:240`). The reconciler still refuses a target range whose endpoints leave this editor, a collapsed `insertText` target range behind the model caret in the same text (a stale backward range), a collapsed `insertText` range while model selection is preferred, and a collapsed range for a delete input type other than `deleteBy*` (`packages/plitejs/src/react/editable/selection-reconciler.ts:623-700`). So a target range counts as event payload that may name the real edit range, and the live DOM selection stays a separate, noisier signal; Lexical and CodeMirror source make the same split. Source: `docs/plite/research/2026-06-13-beforeinput-target-range-selection-policy/README.md:16-30` (packet P155).

## Native delete and plaintext parity

- WPT-derived route rows pin delete and paste parity on plain routes: pasting rich HTML into the plaintext example inserts its serialized plain text without tags while text and selection advance (`apps/plite/tests/plite-browser/donor/examples/plaintext.test.ts:820`); plaintext delete applies `deleteSoftLineBackward`, `deleteWord` over tabs, multi-code-unit grapheme and repeated preserved-space target ranges exactly (`plaintext.test.ts:1700`, `:1779`, `:1921`, `:2042`), and WebKit hard-line backward delete raises no command error (`:1663`); and word Backspace around an inline link leaves the same text as plain editable text under the same browser key (`apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:1751`). The Plite-owned invariant is exact target-range resolution, not mirroring browser HTML list or table cleanup. Source: `docs/plite/research/2026-06-13-wpt-editing-oracles/lead-ledger.tsv:9-12`.

## Keyboard commands

- **Ctrl+O opens a line above the block.** On Apple hosts, `Hotkeys.isOpenLine` matches Ctrl+O (`packages/plitejs/src/dom/utils/hotkeys.ts:49`), and the editing kernel turns it into the `open-line` variant of the `insert-break` command (`packages/plitejs/src/react/editable/editing-kernel.ts:847`). That variant inserts a default paragraph at the selected block's path and moves the caret to its start (`packages/plitejs/src/react/editable/mutation-controller.ts:749-763`). It does not split the block, because the first split-based version moved or duplicated the following text. It also ignores the caret offset, so in the middle of a block it opens the line above the whole block, not at the caret. Only the block-start case has a browser test (`apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:5032`). Lexical's #399 inserts a line break inside the paragraph instead. Source: `docs/editor-test-harvester/lexical/plite-processing-ledger.md:1048`; code read on 2026-10-08. Limit: the mid-block result comes from reading the code; no test runs it.

## Keyboard replacement over inline voids

- Typing a printable key over an expanded selection that crosses an inline, void or read-only element is replaced through the model in keydown, before the browser mutates the DOM: `selectionSpansNativeTextInputBoundary` detects the crossing and the keydown handler prevents default and applies a model-owned `insertText` (`packages/plitejs/src/react/editable/keyboard-input-strategy.ts:151-172`, `:850-865`). Before the 2026-06-14 fix, Firefox crashed the mentions route with `NotFoundError` after a native select-all replacement, and the row had hidden that by typing through `page.keyboard.insertText()`, which skips keydown. WPT expects an expanded range across atomic content to be a real replacement whose target range keeps text endpoints around the atom (`web-platform-tests/wpt@dd54691426c23a08c6f4a0972b2c40965307e5ce:input-events/input-events-get-target-ranges-non-collapsed-selection.tentative.html:238-256`). Proof: `apps/plite/tests/plite-browser/donor/examples/mentions.test.ts:184`, `keyboard undo restores select-all replacement content`, which presses a real key and skips only the mobile project. Source: `docs/plite/research/2026-06-14-firefox-inline-void-select-all-replacement/README.md:27-40`, `:50-66`; code read 2026-10-08.

## Native text repair timing

- Plite's deferred native text-input repair waits for only 1 ms of idle time (`DEFERRED_NATIVE_TEXT_INPUT_REPAIR_IDLE_MS = 1` in `packages/plitejs/src/react/editable/input-router.ts:72`), so ordinary typing repair gets out of the way quickly while composition and platform edges keep their own guards, the direction ProseMirror and Lexical also take. On 2026-06-13 the change was measured on a 5k-block virtualized document in the retired `.tmp` checkout: typing p95 fell from about 33.3 ms to 24.4 ms and type-ready from about 14.4 ms to 6 ms (no committed run artifact). It proves no raw mobile behavior and does not relax IME guards; add real-device or composition rows before changing the timer again. Source: `docs/plite/research/2026-06-13-native-text-repair-idle-oss-validation/README.md:11-44`.

## Composition

- **The model lags the visible preedit during composition.** In Chromium with CDP's synthetic IME, the DOM showed `Hi @sすず` while the Plite model stayed `Hi @s` until commit, because Plite's DOM input runtime holds the composing text during its composition epoch. A model-derived read, such as an autocomplete query, pauses during composition and catches up on commit; Plate's combobox therefore previews the IME preedit without publishing it (`apps/www/tests/browser/combobox.spec.ts:443`). Source: `docs/research/probes/2026-10-01-autocomplete-ordinary-text/NOTES.md:49-53`. Limit: synthetic IME, not a physical OS or mobile IME.

## Typing provenance

- Plite's native grouping stamp is not a typing signal. The `history.native-grouping-input` annotation holds only `{ origin, composition? }`, with no inputType (`packages/plitejs/src/react/editable/input-history.ts:10-18`), and each mounted input controller gets its own origin. At `fe0e9599a6` every string-data beforeinput (`insertText`, `insertFromPaste`, `insertFromYank`, `insertReplacementText`, `insertFromDrop`) went through `applyModelOwnedTextInput` and got the same origin stamp and the same `dom-text-input, semantic-command` tags, while a `DataTransfer` paste made no such commit and `runPaste` added no tag; a probe calling `applyModelOwnedBeforeInputMutation` with two controllers showed it (`docs/plite/research/2026-10-03-autocomplete-arena/probe-stamp.ts`; its DataTransfer row ran through a stub clipboard that inserts nothing, and its replacement row inserted at a collapsed caret, not a real autocorrect replacement). So the autocomplete owner of that commit opened on a yank, a replacement or a string paste that held a trigger. Plite's later `api.react.subscribeTypedText` reports typing only for `insertText`, `insertCompositionText` and `insertFromComposition` from a mounted controller (`packages/plitejs/src/react/editable/typed-text.ts:38-63`), recording the inputType where the text is written, so string paste, drop, yank and replacement input now report nothing (`packages/plitejs/test/react/typed-text.test.tsx:343-362`). Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:9-30`.

- Android keyboard-clipboard paste reaches Plite as `insertText`, as Plite's own comment says (`packages/plitejs/src/react/hooks/android-input-manager/android-input-manager.ts:1018`), so it cannot be told apart from typing; only a long-press menu paste, which carries a `DataTransfer`, can. At `fe0e9599a6` pending Android diffs also flushed as `'insertText'` whatever their original type; the flush now passes the recorded `diff.inputType` and falls back to `'insertText'` (`:319`). This is the one known case left in which pasted text opens an autocomplete popup, and `subscribeTypedText` documents it (`packages/plitejs/src/react/plugin/with-react.ts:54-63`). iOS autocorrect's `insertReplacementText` re-inserts text the user typed, so any typing policy must decide whether a replacement counts as typing. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:32-37`.

- At `fe0e9599a6` several typing paths did not stamp a mount's origin, so origin-keyed logic never saw them: the `input`-event fallback inserted with no annotation (`model-input-strategy.ts:178-240`); `applyModelOwnedTextInput` ran without a controller on the `dispatchCommand` and `applyEditableCommand` branches (`mutation-controller.ts:1201-1204`, `:1245-1252`) and on the content-root path, whose controller can be undefined (`keyboard-input-strategy.ts:783-788`); a composition without a controller got a fresh origin that matches no mount (`composition-state.ts:676-684`); and external text used its own entry origin (`external-text-runtime.ts:281`, `:850`). `subscribeTypedText` likewise reports nothing without a controller (`packages/plitejs/src/react/editable/typed-text.ts:56-63`); Phase 1b gave the `input`-event fallback its Editable's controller, and it now reports its Editable ('the input-event fallback reports its Editable', `packages/plitejs/test/react/typed-text.test.tsx:391`). The other paths were not rechecked. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:38-42`.

## Keyboard routing

- The Editable calls the app's `onKeyDown` from one site, and only after Android's `handleKeyDown`: for an editable target in a view that is not read-only, Plite calls the Android manager (`packages/plitejs/src/react/editable/keyboard-input-strategy.ts:685`), stops a key while it is composing (`:692-698`) and then calls the app handler (`:700-704`). The Android handler carries the SwiftKey placeholder fix (`packages/plitejs/src/react/hooks/android-input-manager/android-input-manager.ts:1281-1292`), and Android soft keyboards send keyCode 229 for most keys, so any IME-key filter must sit between those two calls and must not return before Android's handler runs. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:44`, `:91`; line numbers checked 2026-10-08.

- WebKit sends an IME's confirming Enter after `compositionend` with only keyCode 229, and Android soft keyboards send 229 for most keys. At `fe0e9599a6` nothing in `plitejs/src/react` handled keyCode 229 (still none on 2026-10-08) and Plate's shortcut table had no composition check, so IME-confirm keys could hit Escape, Tab and Mod+Enter bindings (Copilot, link, AI, Table, indent, code block, exit break). Plate's shortcut dispatch now skips any event with `isComposing` or keyCode 229 (`isImeConfirmKeyEvent`, `packages/platejs/src/react/utils/dispatchPlateShortcut.internal.ts:44-47`), and the combobox owner imports the same check (`comboboxOwner.internal.ts:20`). At `fe0e9599a6`, native listeners outside the Editable's prop still see 229 (`find.tsx`, which guards itself, `NodeSelection.tsx`, `TabbableEffects.internal.tsx`), and copied popups with their own input fields are unaffected. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:90-95`, `judge.md:74`.

- In an owned content root, Plite's capture handler consumes unmodified Enter, Backspace and Delete and stops propagation (`packages/plitejs/src/react/editable/runtime-keyboard-events.ts:94-100`, `:565`, `:613`), and the interactive internal-target keydown branch never calls the app's handler (`packages/plitejs/src/react/editable/keyboard-input-strategy.ts:497-630`); the focused element there is a nested `EditableDOMRoot` that Plite renders (`packages/plitejs/src/react/components/editable-text-blocks.tsx:1679`). So a Plate keydown claim or root ARIA cannot reach the keys or the focused element inside a content root. No first-party Plate plugin declared an owned content root at `fe0e9599a6`. Source: `docs/plite/research/2026-10-03-autocomplete-arena/candidate-2.md:15`, verified in `judge.md:31`, `:36`; line numbers checked 2026-10-08.

## Android Gboard behavior

## Android input path

- **Plite's Android input manager.** `packages/plitejs/src/react/hooks/android-input-manager/android-input-manager.ts` ports Slate's manager: stored text diffs, scheduled actions, the same 25 ms and 200 ms delays (`:84`, `:87`) and Slate's FEFF, clipboard-newline and SwiftKey special cases (`:1015`, `:1021`, `:1085`), with the timers run as scheduler tasks. `compositionend` schedules the model task `android-composition-end`, which clears the composing flag and flushes after 25 ms (`:422-441`), and a selection change schedules `android-selection-flush` after 200 ms when the path changed or diffs are pending (`:1223-1233`). An `insertText` `beforeinput` with text flushes pending diffs first only when no composition is open (`:711-720`); during a composition they stay deferred ('keeps pending text diffs deferred while Android composition is active', `packages/plitejs/test/react/android-input-manager-contract.test.ts:748`). Plite adds repair-echo handling Slate lacks: for 120 ms after its DOM repair moves the caret after a text insert, a collapsed insert on that leaf that lands before the repaired caret moves to it, and a flush drops a diff that only repeats text ending at that caret, unless the user has moved the caret natively since (`:281-310`, `:479-495`; `packages/plitejs/src/react/editable/dom-repair-queue.ts:79`, `:952-967`; 'remaps follow-up text through a live repair echo when the native offset is stale', `android-input-manager-contract.test.ts:812`). Slate PR #5901's guard is wider in Plite: on an Android host the React plugin drops the pending DOM selection after any commit that changes text, not only inside `editor.insertText` (`packages/plitejs/src/react/plugin/with-react.ts:86-92`; 'react clears pending selection before mounted-root Android insertText bridge calls', `packages/plitejs/test/react/with-react-contract.tsx:17`). Plite has no RestoreDOM component (no match in `packages/plitejs/src` on 2026-10-08); as in Slate, a tracked DOM mutation with no pending diff or action forces a rerender (`android-input-manager.ts:1315-1334`). The runtime counts a host as Android when its user agent matches `/\bAndroid\b/i` (`packages/plitejs/src/dom/utils/environment.ts:21`, `:85`). Evidence: code and contracts read 2026-10-08; first read at `cf15725603` (`docs/plite/research/2026-10-02-agentic-e2e-testing/read-log.tsv:344-345`). Limit: the contracts drive the manager with mocked DOM resolution, not a device.

- **Pages the device lane opens leave text services mostly at browser defaults.** The registry `Editor` (`apps/www/src/registry/components/editor/editor.tsx`) sets no `spellCheck`, `autoCorrect` or `autoCapitalize`, and platejs adds none, so `/blocks/mention-demo`, whose shared `demo.tsx` mounts `<Editor />` with no props (`apps/www/src/registry/examples/demo.tsx:24`), runs with the browser's own spellcheck, autocorrect and autocapitalize. Among the Plite examples the device cases open, `richtext` sets `spellCheck` (`apps/www/src/app/(app)/examples/plite/_examples/richtext.tsx:220`) and `custom-placeholder` and `plaintext` set none. Some www demos opt out, such as `apps/www/src/registry/examples/playground-demo.tsx:264` (`spellCheck={false}`). Evidence: searches of `apps/www/src/registry`, the three Plite examples and `packages/platejs/src` for the three props on 2026-10-08; first read at `cf15725603` (`docs/plite/research/2026-10-02-agentic-e2e-testing/read-log.tsv:347`).

- **Android composition takes its own path.** On an Android host the Editable's composition handlers hand `compositionstart` and `compositionend` to the Android input manager and return before the desktop composition session starts or settles: `compositionstart` skips the composition session and its native anchor, and `compositionend` clears the runtime composition state without the pending-end settlement (`packages/plitejs/src/react/editable/composition-state.ts:831-851`, `:1019-1026`). `isAndroidDOMHost` reads the same user-agent platform as the manager (`packages/plitejs/src/dom/utils/environment.ts:85-89`, `:231-232`). So a Gboard device proof cannot close a desktop IME claim, and a desktop CDP or OS IME proof cannot close an Android one. Evidence: code read 2026-10-08; first read at `cf15725603` (`docs/plite/research/2026-10-02-agentic-e2e-testing/read-log.tsv:374`).
