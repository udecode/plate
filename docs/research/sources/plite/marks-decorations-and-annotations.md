# Plite: marks decorations and annotations

## Rendering API boundaries

- The 2026-09-01 rendering API audit (17 references, 85 atomic rows) chose source-owned decoration descriptors with keyed, data-only range attributes and explicit observation and cleanup, and separated four concerns: range paint, positioned UI, durable anchors and application data. `CommentsPlugin` keeps editor projection ownership while applications keep threads and persistence; an earlier proposal to remove `CommentsPlugin` was reversed because copied UI would then have to rebuild editor projection. The audit rejected arbitrary transient segment rendering, a public generic Projection API, raw Plate render, decorate or provider-store props, and a generic Plite view plugin. Current owners: `DecorationSource` with `observe` and `read` (`packages/plitejs/src/interfaces/decoration.ts`), `CommentsPlugin` (`packages/platejs/src/react/features/comments/CommentsPlugin.ts:5`). Source: `docs/editor-audits/reports/rendering-api-editor-audit-2026-09-01.md:16-25`. Limit: these are the decision's boundaries, not a statement that its proposed spelling is today's API.

- In the 2026-09-01 rendering audit's captured decoration-manager experiment, four frozen scale cohorts passed the audit's budgets; on the pathological cohort, retained subscriptions fell from 320,000 to 10,032, mount p95 rose from 58.256 ms to 68.065 ms, and full reads improved from 12.604 ms to 2.865 ms. Source: `docs/editor-audits/reports/rendering-api-editor-audit-2026-09-01.md:27-32`. Limit: a manager-level experiment, not an end-to-end editing or general performance claim, and the revision measured is not pinned in the summary.

## Ownership

- Annotations follow one document model with independent mounted views: the model owns one active canonical selection, each mounted view owns its focus, editability, projection, annotation index and decoration paint, and paint stays view-local (docs/research/decisions/2026-09-20-annotations-ownership.md, where implementation proof corrected the review's per-view selection) (docs/plite/research/2026-09-21-annotation-architecture-oss/lead-ledger.tsv:2; promoted-ledger.tsv:2,7). Monaco shows the same split, one text model serving many editors with per-editor decoration owners. The 2026-09-21 review asked to delete Comments' mirrored model and its mirror anchors; no mirror appears in packages/platejs/src/features/comments (git grep, 2026-10-08). The adoption that followed reports exact-view store assertions and a migrated 8-case two-view browser journey as passing (docs/plans/2026-09-21-annotations-architecture-adoption.md:205); overlap order and omitted-DOM remount are not named there.

- Annotations keep four explicit lifetimes: application metadata such as a comment thread, the persistent target anchor, the exact-view annotation index and decoration paint (docs/plite/research/2026-09-21-annotation-architecture-oss/lead-ledger.tsv:3). Prior art agrees: Lexical keeps `MarkNode` ids in the document but thread records in a separate store, and Automerge marks hold one value per name and do not own rich comment records (facebook/lexical@83e8b4925c6c4f5ecb884036bdfaa2c1a0bb2349:packages/lexical-mark/src/MarkNode.ts:33-167; automerge/automerge@4d2a8f6bfecfb7f1e4fca126e6d2122ac526f903:rust/automerge/src/marks.rs:13-26; read-log.tsv:11,25). Document-resident marks are therefore the wrong default owner for Plate Comments targets.

- Each mounted view keeps its own NodeKey-indexed annotation map, and a borrowed annotation target exposes only `resolve`: `AnnotationAnchor` is `Pick<Anchor<Range>, 'resolve'>` (packages/plitejs/src/annotations/store.ts:25, checked 2026-10-08). The 2026-09-21 review also cut destroy, release, retry, metrics and status from React readers and replaced the generic provider with explicit typed readers (docs/plite/research/2026-09-21-annotation-architecture-oss/lead-ledger.tsv:10; read-log.tsv:4); the `resolve` cut was rechecked in source, and the adoption reports type tests and a runtime property assertion for the reader cuts (docs/plans/2026-09-21-annotations-architecture-adoption.md:202-203).

- Each mounted view and its headless owner clean up their own subscriptions and resources explicitly (packages/plitejs/src/core/editor-view-lifetime.ts:1-29). CodeMirror likewise gives each view explicit plugin lifetimes and viewport-derived paint, but its one-state-per-view topology is not copied (docs/plite/research/2026-09-21-annotation-architecture-oss/read-log.tsv:8,16; lead-ledger.tsv:8). The adoption reports a Strict Mode and unmount contract as passing; bulk retirement is not named there (docs/plans/2026-09-21-annotations-architecture-adoption.md:206).

## Mapping and performance

- Scalar `resolve` stays the public anchor read. For full activation and projection switches, the 2026-09-21 review allowed only a private native resolve-many prototype, modeled on Yjs's batched position conversion with one traversal per node, kept only for a material win in a matched benchmark (docs/plite/research/2026-09-21-annotation-architecture-oss/lead-ledger.tsv:5; promoted-ledger.tsv:4; read-log.tsv:21). That benchmark kept the current baseline and rejected the grouped or batched candidate (docs/plans/2026-09-21-annotations-architecture-adoption.md:140,144,238-240), and no resolve-many API exists in packages (git grep, 2026-10-08).

- No annotation runtime may be called the most performant before a matched run at 1, 2 and 4 mounted views over 1k, 10k and 100k annotations, dense and distributed, recording p50 and p95, work counters and heap (docs/plite/research/2026-09-21-annotation-architecture-oss/lead-ledger.tsv:11; promoted-ledger.tsv:5). The adoption that followed registered that run as the `plite-annotation-view-index` benchmark target (benchmarks/targets/slate-v2.json:917-955; benchmarks/slate-v2/donor/core/current/annotation-view-index.mjs), covering local edit, deletion, move, metadata refresh, activation, projection switch, remount and unmount; a candidate must beat the baseline by at least 20% and 1 ms at p95, or 15% and 8 MiB retained, with no cohort over 10% slower. Its recorded result kept the current baseline and rejected every private candidate (docs/plans/2026-09-21-annotations-architecture-adoption.md:140,144,207,330-332); the result JSON sits in an ignored run directory. Scroll and DOM commits stay with a separate browser lane, outside the headless 100k ceiling (same plan:220-225).

- Retained anchors route through one central listener index keyed by changed NodeKeys, so an ordinary edit refreshes only the anchors on changed nodes, and the annotation store then refreshes candidate IDs per exact view (packages/plitejs/src/core/anchor-state.ts:124-136,259-320,1044-1135,1254-1346; packages/plitejs/src/annotations/store.ts:137-183,227-446; read at working tree b812e914 on 2026-09-21, files present on 2026-10-08, line ranges not rechecked). The 2026-09-21 review kept this as the baseline and allowed chunked or interval collection mapping, such as CodeMirror's `RangeSet` or Monaco's interval tree, only as a private benchmark candidate, never as a replacement for semantic anchors (docs/plite/research/2026-09-21-annotation-architecture-oss/read-log.tsv:2; lead-ledger.tsv:4,6). The adoption's matched benchmark kept this baseline and rejected the collection candidate (docs/plans/2026-09-21-annotations-architecture-adoption.md:140,207).

- Annotation snapshots use a private persistent byte trie (`createStableIdMappedSource`, packages/plitejs/src/internal/view/stable-id-mapped-source.ts, used by packages/plitejs/src/annotations/store.ts:22). Its tests bound copying at 10k items (packages/plitejs/test/react/stable-id-mapped-source.test.ts:116-200 at b812e914), which shows complexity, not a wall-time or retained-heap advantage over simpler immutable snapshots; the 2026-09-21 review kept it private pending a dense and sparse update benchmark that deletes or simplifies the loser (docs/plite/research/2026-09-21-annotation-architecture-oss/read-log.tsv:5-6; lead-ledger.tsv:7). That benchmark kept the trie baseline and rejected the simpler-snapshot candidate (docs/plans/2026-09-21-annotations-architecture-adoption.md:140,238-240).

## Deletion policy

- Anchors have two deletion policies, `drop` and `nearest` (`AnchorDeletionPolicy`, packages/plitejs/src/core/anchor.ts:81). Comments use `nearest` for durable recovery (packages/platejs/src/features/comments/BaseCommentsPlugin.ts:1024,1092, checked 2026-10-08); `drop` is terminal only for locally observed lifetime and must not be promised as a convergent persisted collaborative target. Prior art supports that narrowing: Yjs relative positions and Automerge cursors move to a nearest boundary on deletion and offer no terminal absence, Yjs's exact local undo following is not a cross-client guarantee, and ProseMirror bookmarks map through changes and leave any nearest fallback to the resolver (ProseMirror/prosemirror-state@ffad5d9450a0b93438be53a801deee1a223a81bf:src/selection.ts:195-203,309-318; docs/plite/research/2026-09-21-annotation-architecture-oss/read-log.tsv:3,7,10,20,24; lead-ledger.tsv:9). The adoption made local `drop` terminal for ordinary and authored anchors and reports 107 core, history and authored cases plus a core and Yjs replay as passing (docs/plans/2026-09-21-annotations-architecture-adoption.md:69-70,201).

## Overlay substrate

- **Plite's overlay substrate is node keys, anchors and snapshot range projection.** The Slate v2 proof that older pages call runtime ids, bookmarks and projection slices lives in `packages/plitejs` under other names. Live node identity is the opaque `NodeKey`, which a snapshot index maps to and from paths (`packages/plitejs/src/interfaces/editor.ts:2013-2025`). A durable location is an `Anchor` with an association and a deletion policy; it resolves in its capture view by default or in another view of the same model, and a range anchor saves as versioned `EditorDocumentRange` JSON (`packages/plitejs/src/core/anchor.ts:84`, `:268`, `:327-341`). Decoration sources project a range into per-text segments with `projectRangeInSnapshot`, which keeps the last range and its segments for each immutable snapshot and reuses them for an equal range (`packages/plitejs/src/range-projection.ts:10-21`, `packages/plitejs/src/react/decoration-source.ts:748`). No `Bookmark` type or projection store remains in `packages/plitejs` (searched 2026-10-08). Source: `c70bacbd4a:docs/research/entities/slate.md:22`.

## Decoration refresh during typing

- **Typing maps decorations and rereads sources once input settles.** The April 2026 decoration roadmap required that a decoration refresh never break caret, selection or IME truth: a refresh could wait while input was active, and the urgent caret lane had to keep working instead of blocking on a source read. The shipped manager does this for plain typing. A commit tagged `native-text-input` or `dom-text-input` that changes only text defers the source reread: when the change is a pure text insertion, the manager first maps the existing decoration ranges through it without calling any source `read`, and it schedules one reread of the pending sources after two animation frames and 50 ms without further input, and at most 250 ms after the first pending input; any other document commit rereads at once (`packages/plitejs/src/react/decoration-source.ts:1629-1668`, `:1745-1766`). Tests: 'maps native insertions immediately and revalidates the source after input settles', 'coalesces a rapid input burst before reading sources' and 'bounds pending input age when frames are delayed and ignores frames after teardown' (`packages/plitejs/test/react/decoration-manager-contract.test.ts:895`, `:343`, `:299`). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/decoration-roadmap.md:473-502`. Limit: JSDOM package tests with fake timers, code read 2026-10-08; the roadmap's refresh shape (paths, selection scope, sync or deferred mode, generation token) did not ship, and `DecorationRefresh` takes only `'all'` or node keys (`packages/plitejs/src/interfaces/decoration.ts:25-27`).

## Why decorations and annotations split

- **Legacy `decorate` failed on four axes, so Plite split paint from anchors.** Legacy Slate's one `decorate(entry)` callback carried render-time marks, cross-node overlays, externally driven highlights and comment or cursor anchors at once. The April 2026 Plite decorations cluster read the upstream issue corpus as one bad abstraction boundary that fails four ways: semantic loss when leaf props flatten overlapping same-key payloads (#3383); invalidation cost when decorations computed at the root are intersected down the tree (#4993, #4483); DOM and selection drift when externally timed updates restructure leaves (#5987, #3309, #3162, and the debounced repro in PR #4997); and no lifetime or ownership for persistent anchors such as comments (#4477). The per-issue mechanisms are on the plate-notes rendering page. The split is now law: Decoration owns inline paint, Annotation owns durable logical ranges, and selection or keyed cursor owners feed exact-view geometry (`docs/vision/plite.md:597-600`). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/decorations-annotations-cluster.md:1-16`, `:1211-1215`. Limit: the four axes are the cluster's synthesis of upstream threads, not a rerun of them.

## Decoration invalidation

- **Decoration sources declare no dirtiness; the manager rereads changed entries.** The April 2026 roadmap planned per-source dirtiness classes (`always`, `selection`, `text`, `node`, `annotation`, `external`, `custom`), with a full refresh for a source that declared none (`c70bacbd4a:docs/plite-draft/decoration-roadmap.md:1383-1445`). That did not ship: a `DecorationSource` is only `id`, optional `observe` and per-entry `read` (`packages/plitejs/src/interfaces/decoration.ts:29-37`). The manager subscribes to `commit`, returns when the commit changed no document, and otherwise queues every source for the commit's `changed.nodeKeysAll('decoration')` keys, which join the changed, touched, path and selection keys, widened to the whole subtrees of the changed nodes when the commit changed structure or properties (`packages/plitejs/src/react/decoration-source.ts:1703-1744`, `packages/plitejs/src/core/commit.ts:932-943`). External state reaches a source only through `observe`'s `refresh`. So a selection-only commit rereads nothing, and a text edit rereads every source at the changed entries, not only the sources that depend on text. Limit: code read 2026-10-08; no benchmark was run here.

## Text-range helper

- **`NodeApi.findTextRanges` turns text matches into ranges for decoration sources.** It takes a node or snapshot root, a query and `{ caseSensitive? }` (`packages/plitejs/src/interfaces/node.ts:162-176`, `:258-268`). A string query is literal. A `RegExp` uses its own flags and leaves the caller's `lastIndex` unchanged. A callback returns custom offsets, and invalid offsets are ignored. Empty and zero-width matches are skipped. Matches span adjacent leaves of one text run but never join separate runs; on a live editor root, the compiled schema joins text through inline descendants without crossing a block boundary. Tests: `packages/plitejs/test/find-text-ranges-contract.ts:21`, `:41`, `:54`, `:90`, `:105`, `:130`, `:158`, `:182`. The May 2026 plan kept it a range helper, not a search feature: no whole-word or locale options and no `editor.api.search` in raw Plite. Plate's find plugin calls it case-insensitively (`packages/platejs/src/features/find/lib/BaseFindPlugin.ts:42`), and the copied find UI's tests spy on it (`apps/www/src/registry/components/editor/find.spec.tsx:228`). Source: `c70bacbd4a:docs/plite/references/pr-description.md:904-908`; code and test titles read 2026-10-08, not run.
