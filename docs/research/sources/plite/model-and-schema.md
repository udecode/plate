# Plite: model and schema

## Document replacement and corrections

- Replacing an authored document folds schema corrections into the load. `editor.update.value.replace(doc)` used to throw 'Document replacement cannot mix with ordinary writes.' on an editor with authored changes whenever a correction wrote after the replacement in the same transaction; with EditorKit, `TrailingBlockPlugin` adds a paragraph after a final table or column group, so Markdown ending in either failed to load. The cause was ordering: `runEditorTransaction` settles the draft (element-owned roots, representation, `correctDocument` corrections, plugin publication) after the update callback, but the authored runtime marked the load complete inside the callback. Core now hands its settlement boundary to the authored runtime through an internal `NativeAuthoredTransaction.settle()` called right after the callback (`packages/plitejs/src/core/authored-runtime.ts:38`, `core/public-state.ts:9163`). A replacement moves through `loading`, `loaded` (ordinary writes still throw) and `settling` (correction writes fold into the load) (`packages/plitejs/src/authored/authored.ts:244-252`, `:2373-2388`, `:2917`), and it commits once as the corrected document, with no authored operation and history reset. A correction that would change a loaded document carrying retained authored changes throws 'Corrections cannot change a loaded document with authored changes.' and rolls back, because mapping saved positions through inserted content has no operation identity; plain loads such as Markdown import and streaming are unaffected. Rejected: authored running corrections itself (a second settlement owner that runs corrections twice and ignores `skipCorrections`) and a public origin field on the transaction-change context. Tests: `packages/plitejs/test/authored-ingress-contract.test.ts`, 'folds schema corrections into a loaded document with … input' and 'loads authored changes only when corrections keep their saved content' (`docs/research/probes/2026-09-28-conversion-boundary/lanes/authored/REPORT.md:3-38`, 2026-09-28).

## Text direction

- Plate has no text-direction or writing-mode owner: a search of `packages/platejs/src` and `packages/plitejs/src` on 2026-10-08 found no block direction property and no CSS `writing-mode` handling, only Plite's caret-level `getTextDirection` for RTL arrow keys (`packages/plitejs/src/react/editable/caret-engine.ts:119`). Native bidi caret movement is a different job from an explicit document direction. The 2026-09-09 proposal is a schema-backed block property under Plate's style and model owner, with no global direction engine or duplicate caret state; until a product contract exists, no all-features parity claim can include direction. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/experiments.md:124-126`.

## Atom and object elements

- `atom: true` makes an element's descendants non-traversable: a 2026-09-21 probe found that a text block holding `abc` exposes offsets 0 to 3 to character traversal and only offset 0 once the element is atom (`docs/plite/research/2026-09-21-media-object-editable-content/README.md:65-68`). The schema compiler also rejects an explicit `slice.preserveContext` on an atom or void element with `invalid-slice-policy`, because such an element exposes no editable child content (`packages/plitejs/src/core/schema-compiler.ts:4550-4563`, read 2026-10-08). So atom cannot model an editable caption; the `object` role does (`docs/research/decisions/media-object-content.md`).

- Object semantics guard generic editing, not explicit commands. A generic `splitNodes` at a point or range inside an object returns without splitting unless the caller passes its own `match`, and a range split stops climbing at an object (`packages/plitejs/src/transforms-node/split-nodes.ts:190-203`, `:373-379`, read 2026-10-08). The 2026-09-21 review set the rule: a generic split, merge or delete must not duplicate, merge away or discard the asset, intentional duplicate, delete and supported conversion commands stay explicit, and caption exit builds the target's default block rather than a clone of the media node (`docs/plite/research/2026-09-21-media-object-editable-content/README.md:150-156`). The accepted operation matrix is in `docs/plans/2026-09-21-object-elements-with-editable-children.md`; the merge and delete guards were not rechecked here.

## Persistence

- Only persistence keeps the `codec` noun: the sole exported names containing it are `valueCodecs` and `pageSettingsCodec` (`git grep` over the package sources, 2026-10-08). `EditorValuePersistence` (`packages/plitejs/src/interfaces/editor.ts:432`) owns the current `encode` and `decode` pair, a positive envelope `version` and optional decode-only `legacyDecoders`, and reusable `valueCodecs` pairs spread into it (`packages/plitejs/src/core/value-codec.ts:367-440`). The 2026-09-25 design kept a separate `EditorValueCodec` beside it; that type no longer exists, and `EditorJsonValue` is the one shared JSON value type now that `PropertyJsonValue` is gone (`git grep`, 2026-10-08). The laws are tested in `packages/plitejs/test/value-codec.test.ts`: every canonical JSON value round-trips without narrowing, supported previous versions decode while the current version is always written, values JSON would coerce or omit are rejected, and untrusted frozen input is detached. Source: `docs/plite/research/2026-09-25-document-codec-architecture/shards/005-local-ontology-and-best-api.md:41-56`, `shards/002-typed-codecs.md:43-55` and `lead-ledger.tsv:3`.

- **Canonical JSON admits only plain data.** Persistence output, document properties and `DocumentChange` payloads pass one check, `isEditorJsonValue`, and `snapshotEditorJsonValue` and `assertEditorJsonValue` apply the same rules (`packages/plitejs/src/core/value-codec.ts:122-170`, `:278-320`, `:561`). It admits `null`, booleans, strings, finite numbers other than `-0`, and arrays and records whose prototype is the intrinsic `Array` or `Object` one (records may have a null prototype) holding only enumerable own data properties under string keys, with no holes and no cycle (`:30-107`). It rejects `undefined`, `bigint` (by its `typeof` switch), `NaN`, infinities, `-0`, functions, symbols, `Date`, `Map`, class instances, `Array` subclasses, accessors, symbol keys, extra non-index array properties, sparse arrays and circular objects (`packages/plitejs/test/value-codec.test.ts:348`, 'rejects every value shape that JSON would coerce or omit', which covers every listed shape except `bigint`; `packages/plitejs/test/schema-contract.ts:57` for document properties at create and update; `packages/plitejs/test/document-change.test.ts:2578` for change deltas), while plain values built in another realm pass (`packages/plitejs/test/value-codec.test.ts:314`). The `EditorJsonValue` type (`packages/plitejs/src/interfaces/json.ts`) states none of these runtime rules. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/10-serializing.mdx:61-64`, whose list omitted `-0`; `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/11-normalizing.mdx:20` states the same contract for nodes.

## Schema compilation

- **A schema-less editor stays open; a complete schema closes it, decoded changes included.** `createEditor` without a complete schema compiles a default whose `unknown` policy is `'preserve'` (`packages/plitejs/src/core/schema-compiler.ts:62-81`), so it admits an unknown element `type` and arbitrary element and text fields, and the app alone gives fields such as `url` or `bold` their meaning. A complete schema defaults to `unknown: 'reject'` (`:3395`; `docs/vision/plite.md:130-133`). The test 'keeps schema-less editors permissive and closes schema-bound documents' (`packages/plitejs/test/schema-contract.ts:232`, which sets `unknown: 'reject'` explicitly) shows that creation then refuses an unknown element type, an undeclared root and an unknown element property, and that an update applying a decoded `DocumentChange` which adds an unknown element property throws and leaves the document unchanged. `BaseElement` still requires a string `type` (`packages/plitejs/src/interfaces/element.ts:16-20`). The retired Plite concept pages taught the open form as the normal model ("Your app owns the product-specific fields"); `docs/vision/plite.md:110-117` makes schema the first-party shape truth. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/01-interfaces.mdx:6-7`, `:26`, `:51-52`, and `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/02-nodes.mdx:58-72`, `:95-102`.

- **Schema declarations are frozen data, and plugin order never picks a winner.** The `property.*`, `schema.content.*` and `target.*` builders return frozen, serializable declarations; targets compose `target.type`, `types`, `element`, `elements`, `group`, `root`, `parent`, `and`, `or` and `not`, never a callback (`packages/plitejs/src/core/schema-definition.ts:729-733`, `:896-900`, `:942-976`). Compilation sorts contribution records by plugin name, not install order (`packages/plitejs/src/core/schema-compiler.ts:3329`, `:3364-3368`), and treats competing ownership as an error: two plugins that declare the same element type, group or root throw `EditorSchemaCompileError` with a `duplicate-element-type`, `duplicate-group` or `duplicate-root` diagnostic naming both owners (`collectSchemaOwnershipConflictDiagnostics`, `:1212-1278`), a plugin that contributes schema twice fails with `duplicate-schema-contribution` (`:3339`), and two complete schemas fail with `duplicate-complete-schema` (`:3352`). Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/reference/public-docs/concepts/19-schema.mdx:86-91`, `:225-228`; code read 2026-10-08. Limit: the source also says plugin order does not decide defaults; only the ownership-conflict and record-ordering paths were read.

- **Open-world vocabulary stays grammar-bound.** A schema counts as complete when it declares `root` (`isCompleteSchemaDeclaration`, `packages/plitejs/src/core/schema-compiler.ts:91-93`). Without one, compilation adds a derived base record, `plite:derived-base-schema`: its root admits any non-text element with a `paragraph` default, and its `paragraph` holds text plus the installed inline and inline-void types unless a plugin owns `paragraph` (`:63-89`, `:100-156`, `:3361-3368`). Preserve is not a free pass: an undeclared element type is valid only where its parent's compiled content reports `allowsUnknownElements`. Under `unknown: 'preserve'` an `open` rule admits unknown elements, a `not` rule admits them unless its excluded rule does, `any` admits them when one nested rule does and `all` only when every nested rule does, while `text`, `type`, `types` and `group` rules never do; under `'reject'` no rule does (`compileContentRule`, `:2103-2249`). The schema guide says only that `not` can admit undeclared types (`content/docs/(guides)/schema.mdx:67`), and its builder table omits `schema.content.open` (`packages/plitejs/src/core/schema-definition.ts:1443-1445`). Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/reference/public-docs/concepts/19-schema.mdx:269-289`; code read 2026-10-08. Limit: read from source with no test run; the source's claims that undeclared properties are kept as JSON values and that the unknown policy enters schema identity were not rechecked.
