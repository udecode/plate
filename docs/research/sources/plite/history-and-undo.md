# Plite: history and undo

## Selection repair after undo

- When undo or redo restores an expanded view selection, the history focus repair asks only for a force render, and only when history requires one; it never asks for a caret repair, because the view-selection projection draws an expanded selection rather than one native caret. A collapsed selection still gets a focused `repair-caret` that prefers the model selection (`packages/plitejs/src/react/editable/history-focus.ts:135-155`). The skip came from the June 2026 200k-block undo-delete work, where restoring an expanded projected selection had paid DOM caret repair. Source: `docs/plite/research/2026-06-12-huge-doc-architecture/README.md:736-769`. Limit: the June numbers ran on the removed staged lane and are not repeated here.

## Transaction extenders and undo batches

- **Extender edits stay in one batch.** When a transaction extender adds edits to a command, those edits must stay in that command's isolated undo and redo batch. The Plite regression 'keeps extender-added edits in one isolated undo and redo batch' in `packages/plitejs/test/history/integrity-contract.ts` (near line 160) wraps `insertText` with `state.transaction.extend` to add `!`. It then checks the extender text and an adjacent explicit batch across two undos and two redos. The file passed 12/12 on 2026-09-02. Donor: Wordgard `wordgard/wordgard@b5ad0d057e2790c8cf971c85a9d2fb7e4a82da54:test/test-history.ts` lines 410-428 (docs/editor-test-harvester/wordgard/report.md:120, 164).

## Skipped updates and node identity

- Undo after a history-skipped edit that revives a removed node's identity keeps both nodes. Starting from `[one, two]`, removing `one` and then inserting at index 1, with `history: 'skip'`, a copy of `one` that carries its identity gives `[two, one']`. Undo used to give `[one, one']`, because the relocation repair read the undo's insertion at position 0 as an edit inside `two`, losing `two` and reusing its key. Undo now gives `[one, two, one']`: the restored duplicate gets a fresh key and the live node keeps the revived key, as `mapChangedNodeKeys` specifies, and redo returns `[two, one']`. Test: 'preserves a key revived by a skipped edit when undo restores the same content' (`packages/plitejs/test/history/history-contract.ts:326`); source `docs/research/probes/2026-09-28-conversion-boundary/lanes/p1/REPORT.md:172-188` (2026-09-29).

## Redo after a new edit

- A new edit after undo starts a fresh undo batch and clears redo: after typing `a` and undoing it, typing `b` leaves one undo entry and no redo, and redo then changes nothing (`packages/plitejs/test/history/history-contract.ts:1649`, 'clears redo history when a new edit follows undo'). Lexical regression #1055 checks the same stack law from the other side (`docs/research/sources/lexical/history-and-undo.md`). The next ledger row, Lexical's playground HTML and helper setup, is harness detail. Source: `c70bacbd4a:docs/editor-test-harvester/lexical/plite-processing-ledger.md:942-943`.

## Merge policy

- Plite history merges consecutive property-only commits on the same node into one undo step, so changing a block attribute again and again undoes in one step: `shouldMergeBatch` merges two `properties` groups with the same target node, root and scope when neither batch carries effects (`packages/plitejs/src/history/history-merge-policy.ts:335-366`), and the history plugin skips the merge for an explicit push or a session effect (`packages/plitejs/src/history/history-plugin.ts:769-800`). ProseMirror #1302 ('When repeatedly updating an attr, history groupDelay does not work') prompted it. Proof: `packages/plitejs/test/history/history-contract.ts:1721` ('merges repeated block property changes into one undo unit'). Source: `c70bacbd4a:docs/editor-issue-harvester/prosemirror/full/checkpoints/issues-1292-1329.md:16`, `:21`; code read 2026-10-08.

## Edits outside history

- Plite history rebases saved undo batches through edits made with `history: 'skip'` and drops a saved batch that a skipped delete consumed, so undo neither resurrects nor corrupts skipped content; restored node keys and named roots also rebase across skipped edits, and a skipped remote edit keeps one composition batch whole. Proof: `packages/plitejs/test/history/history-contract.ts:1272` ('rebases saved undo batches across local history-skip document edits'), `:1294` ('drops saved undo batches deleted by local history-skip edits'), `:1330`, `:231` and `:1967`. ProseMirror's skipped-edit tests prompted the drop row. The source names the earlier `withoutSaving` API and `plite-history` package, now `history: 'skip'` in `packages/plitejs` (checked 2026-10-08).

## Live-session replay

- **How a live-session replay is tracked.** A replay whose head batch carries a `history: { replay }` effect first commits an annotation-only claim (`history.replay-claim`) that sets `pendingReplay`, while the claimed entry stays at the branch head. Object identities travel in side maps keyed by request number (`PENDING_HISTORY_REPLAY_CLAIMS`, `PREPARED_HISTORY_REPLAYS`), because annotations are structured-cloned. A recorded edit during the wait marks the claim edited, forces a new batch boundary and, for a redo, detaches the entry before the edit clears the redo branch. The receipt `{ group, version, claimVersion }` is recorded against the result object in a private WeakMap for the mounted runtime's focus repair, and an activation check skips settlement into history that was retired or replaced mid-replay. Code: `packages/plitejs/src/history/history-plugin.ts:170`, `:214-217`, `:236-237`, `:924-931`, `packages/plitejs/src/history/history-state.ts:66-77`, `:690-723`, `packages/plitejs/src/core/public-state.ts:722-775`. Source: `docs/research/probes/2026-10-05-history-replay-result/grounding-how.md:9-15`, checked against the code on 2026-10-08.

- **A pending live-session replay blocks every other replay.** While a claim is pending, `undo()` and `redo()` return `{ status: 'busy' }` before reading the branch, even when the head is text typed during the wait, and `read.history.hasUndo()` stays true because the claimed entry remains at the head; `useEditorHistory` returns `pending` beside `canUndo`, so a control reads both. VS Code drops a repeat press during a locked undo the same way. Code: `packages/plitejs/src/history/history-plugin.ts:1049`, `packages/plitejs/src/react/hooks/use-plite-history.ts:102-106`. Source: `docs/research/probes/2026-10-05-history-replay-result/grounding-how.md:93-94`.

- **The four-case settlement table places a claimed entry by call order.** `busy` enforces one replay at a time, because a second request would claim the same head again (a double `mutate`) or reach past it out of order. A live-session undo that settles `applied` after an edit made during the wait drops the entry instead of reviving a redo the edit cleared; a redo settled after such an edit is spliced at its claim-time undo anchor, below the edit, so the next undo removes the typed text before the comment; a `blocked` settlement keeps the entry as the next target unless an edit already cleared it from redo. Replayed effects are mapped through remote changes queued during the wait. The source reports the final branches match replaying at call time with the owner's eventual outcome over 1,684,893 checked sequences. Code: `packages/plitejs/src/history/history-state.ts:727-850`. Source: `docs/research/probes/2026-10-05-history-replay-result/grounding-how.md:130-135`. Limit: the sequence check was not rerun here.

- **Clearing `pending` after a failure is one more update that can fail.** A failure after the claim settles `failed` by running a blocked settlement update; if that update throws too, `pending` stays set and every later replay returns `busy` until the history plugin deactivates and clears its state, because replacing the history value with `replaceHistoryState` keeps the claim. A clearing error that differs from the original cause is reported first, then the cause; an identical one is reported once. Code: `packages/plitejs/src/history/history-plugin.ts:967-979`, `:1206`, `packages/plitejs/src/history/history-state.ts:1123-1139`. Source: `docs/research/probes/2026-10-05-history-replay-result/panel-r1/r1-opus.md:61-62`, `panel-diff-r1/d1-opus.md:20-25`, `panel-diff-r2/d2-opus.md:13-16`.

- **The claim version is recorded where the claim commits.** History stores `commit.version` as `claimVersion` in the claim branch of its commit handler and copies it into the private replay receipt, because the replay owner and claim observers can publish their own updates before `undo()` returns, and a version read after the call would mistake such a commit for the claim. The mounted runtime repairs selection and focus only when the settlement is the commit right after the claim (`receipt.version === (receipt.claimVersion ?? version) + 1`) and no later commit followed. Code: `packages/plitejs/src/history/history-plugin.ts:599-628`, `packages/plitejs/src/react/editable/editable-dom-runtime.ts:1093`. Source: `docs/research/probes/2026-10-05-history-replay-result/panel-r1/r1-sol.md:23-31`, also `r1-astra.md:25-33` and `panel-r2/r2-opus.md:32-35`.

- **Comments is the only live-session replay owner.** `commentCreationHistoryEffect` looks up the runtime's `replayCreation` in a registry and refuses synchronously with `comments-owner-unavailable` when none is installed, so that refusal settles inside the `undo()` call. `replayCreation` calls `enqueue` before its first `await`, so it takes the thread's per-thread queue slot during the replay call and a later local mutation of that thread queues behind it. The queued run checks the live thread against the transition's `previous` and first message ID, restores the anchor on redo and calls `commitMutation`, which awaits the app's `mutate`, rechecks staleness and only then writes through `setThread`. Every failure, a `mutate` throw included, comes back as a typed `blocked`, so History never sees a Comments rejection (see Open leads). Code: `packages/platejs/src/features/comments/BaseCommentsPlugin.ts:84-98`, `:725-747`, `:748-810`, `:815-910`. Source: `docs/research/probes/2026-10-05-history-replay-result/grounding-how.md:34-39`, checked against the code on 2026-10-08.

## Open leads

- **Open lead: a settlement failure after the owner applied leaves a stuck head.** If Comments' `mutate` succeeds and `setThread` removes the thread locally and on the server, but History's settlement update then throws, the replay settles `failed` and keeps the entry at the head; every later undo that reaches it runs `replayCreation`, finds the thread gone and returns `blocked comments-thread-changed`, so older history is unreachable until reload, and `failed` does not say whether the external effect happened. VS Code instead clears the affected stacks on failure. The path is rare: commit-observer errors are caught by `runEditorObserver` (`packages/plitejs/src/core/public-state.ts:8676`), so the settlement update throws only on a clone, guard or validation defect, and Comments rechecks the thread before calling `mutate`, so a retry cannot persist twice. Tracked as open work, staging Comments' local publication inside History's settlement update: `docs/plans/topics/history.md:136`, sketch in `docs/research/probes/2026-10-05-history-replay-result/arena/label-C.md`. Source: `docs/research/probes/2026-10-05-history-replay-result/panel-r1/r1-opus.md:13-21`, `panel-r2/r2-opus.md:23-30`, `arena/judge.md:61`, `:69-71`, `panel-diff-r1/d1-opus.md:38`.

- **Open lead: a throwing Comments listener turns an applied replay into a refusal.** After `setThread` writes the thread and anchors, it fans out to annotation change listeners (`annotations.refresh`, whose store calls listeners without a boundary), the active-id subscriber (`setActive`, then `refreshIds` and refreshers) and the thread, data, draft, pending and visible listeners, none behind an error boundary; a throw reaches `replayCreation`'s catch, which returns `blocked comments-mutation-failed` and drops the error while the thread is already gone, so every retry returns `comments-thread-changed`. Code: `packages/platejs/src/features/comments/BaseCommentsPlugin.ts:438`, `:453-475`, `:665-724`, `:895-910`, `packages/plitejs/src/annotations/store.ts:307`. Tracked: `docs/plans/topics/history.md:137`. Source: `docs/research/probes/2026-10-05-history-replay-result/panel-r2/r2-opus.md:3-11`, also `r1-astra.md:3-13`, `r1-sol.md:3-11`, `r2-astra.md:3-11` and `r2-sol.md:5-13`.

- **Open lead: a Comments storage error never reaches History's failure owner.** When the app's `mutate` throws or rejects during a creation replay, `replayCreation` catches it, discards the cause and returns `blocked comments-mutation-failed`; History sees a refusal, so neither the lifecycle sink nor its `reportError` fallback reports the error. The entry is kept, as TaskHub-22 requires. Code: `packages/platejs/src/features/comments/BaseCommentsPlugin.ts:895-910`. Tracked: `docs/plans/topics/history.md:138`. Source: `docs/research/probes/2026-10-05-history-replay-result/panel-r2/r2-sol.md:27-35`.

## Selection after undo and redo

- **Undo restores the selection from before the update.** When one update moves the selection and then edits, undo restores the selection the editor had before that update, not the one set just before the edit, and redo restores the selection after the edit. In 'undo restores transaction-start selection when selection import shares a text commit', an update moves the caret from offset 0 to 3 and inserts `X` there; undo gives `abcdef` with the caret at 0, and redo gives `abcXdef` with the caret at 4 (`packages/plitejs/test/history/history-contract.ts:1861`). 'restores transaction-start selection when selection changes before the first document change' does the same with the insert at another offset (`:743`), and 'redo preserves explicit selection after the document change' keeps a selection set after the edit for redo (`:1902`). On 2026-05-13 the fork recorded the opposite for its udecode/slate#9: a checkpoint taken before the first document change, so undo of that same shape returned the caret to the edit point (`831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/ledgers/fork-issue-dossier.md:6843-6900`); the current tests pin the result that entry called the bug. In the browser, where the caret import and the typing arrive as separate events, undo still returns the caret to the edit point ('keyboard undo restores caret after middle-line typing', `apps/plite/tests/plite-browser/donor/examples/plaintext.test.ts:2397`). Limits: the fork's record of the May fix was marked superseded on 2026-05-21, when history moved to inverse `DocumentChange` values with rooted selection checkpoints (`52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-13-plite-history-leading-selection-imports-are-batch-preconditions.md:4-5`, `:23-25`), and no record found says the transaction-start rule was chosen over the edit point; no browser row checks a caret import that lands in the same update as typed text.

- **Undo and redo bring back pending insertion marks with the caret.** A collapsed text selection carries its pending insertion marks (`SelectionApi.isText` accepts `marks` only on a collapsed selection, `packages/plitejs/src/interfaces/selection.ts:188-200`), and History stores each batch's selections with them, so undo and redo restore the active marks along with the caret. In 'round-trips pending insertion marks through selection history' (`packages/plitejs/test/history/history-persistence-contract.spec.ts:452`), `tx.marks.set({ bold: true })` at offset 2 of `body` and an insert of `!` leave bold pending; after the history goes through `History.toJSON` and `History.fromJSON` into a new editor, undo puts the caret back at offset 2 and redo at offset 3, and `read.marks()` is `{ bold: true }` both times. 'preserves text selection metadata across native burst undo and redo' (`packages/plitejs/test/history/history-contract.ts:655`) restores the selection's `affinity` and `marks` as well: undo gives back `backward` with `{ italic: true }`, and redo gives `forward` with `{ bold: true }`. Setting a mark at a collapsed selection is not its own undo step (Batch integrity on this page). `docs/vision/plite.md:493` says History stores selections but does not mention marks. Source: `c70bacbd4a:docs/plite/references/architecture-contract.md:155-158`; tests read 2026-10-08, not run.

## Update policy and installed History

- **A `history` policy needs the History plugin, checked by type and at runtime.** `EditorUpdatePolicyFor<E>` offers `history` only when the editor has a History transaction group (`packages/plitejs/src/interfaces/editor.ts:1868-1872`), so `update({ history: 'skip' })` on an editor without History is a type error (`packages/plitejs/test/generic-update-policy-contract.ts:33`). An untyped call throws "Editor update history policy requires the history plugin." before it changes anything (`assertUpdatePolicy`, `packages/plitejs/src/core/editor-lifecycle-api.ts:40-57`): the text and the snapshot version stay as they were ('rejects history policy before mutation when history is not installed', `packages/plitejs/test/update-policy-contract.ts:204`). A configured facade checks again on every call, so an `editor.update({ history: 'skip' })` facade created while History was installed throws once History is removed ('revalidates History when invoking a cached semantic facade', `:359`). A policy with only `tags` needs no plugin. Plate installs History by default (`content/docs/api/editor-api.mdx`, "Updating state"), so the check matters for raw Plite and for hosts that remove History. The JSDoc says only "Requires an installed History plugin." (`packages/plitejs/src/interfaces/editor.ts:883`). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/api/nodes/editor.mdx:232-235`; `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/07-editor.mdx:111-114` says the same.

- **React editors do not install History.** `createEditor` from `plitejs/react`, which `useEditor` calls, installs only `react({ dom: dom({ clipboardFormatKey }) })` ahead of the caller's plugins, and its doc comment says to install history explicitly for undo and redo (`packages/plitejs/src/react/plugin/with-react.ts:170-197`, `packages/plitejs/src/react/hooks/use-editor.ts:50`). The raw examples pass `history()` themselves (`apps/www/src/app/(app)/examples/plite/_examples/richtext.tsx:157`). The retired migration guide and fork page said the normal React setup includes history and showed `history({ enabled: false })` to turn it off; that is no longer true. `history({ enabled })` still exists (`packages/plitejs/src/history/history-plugin.ts:122`), and the React control hook is `useEditorHistory` (`packages/plitejs/src/react/index.ts:144-149`). Source: `c70bacbd4a:docs/plite/reference/public-docs/migration.mdx:442-496`, `c70bacbd4a:docs/plite/reference/public-docs/why-this-fork.mdx:186`; code read 2026-10-08.

## Batch integrity

- **Batch integrity laws.** One outer transaction is one undo unit ('treats one outer transaction as one undo unit', `packages/plitejs/test/history/integrity-contract.ts:133`). The `new-batch` update policy and `tx.history.newBatch()` each start a fresh batch, and the `skip` policy records nothing (`:221`, `:248`, `:275`). History saves no commit that only sets the selection, runs a movement command or adds a mark at a collapsed selection (`:292`, `:313`, `:345`), and it captures a committed batch before a subscriber that reenters and edits again can mix into it (`:398`). Automatic groups split at the exact `newBatchDelay` idle boundary (`:79`), 500 ms by default (`content/docs/(guides)/history.mdx:59`). The April 2026 ledger stated these laws through legacy-shaped seams, `withNewBatch`, `withoutMerging`, `withoutSaving` and `writeHistory`; only `writeHistory` survives, as an internal function (`packages/plitejs/src/history/history-state.ts:967`). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/ledgers/plite-history-api.md:49-56`; tests read 2026-10-08.
