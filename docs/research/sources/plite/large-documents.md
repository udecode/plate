# Plite: large documents

## Huge-document architecture

- Plite's huge-document shape is hybrid: mounted DOM where it exists, an explicit DOM coverage boundary for every unmounted range, model-owned (projected) selection where DOM is absent, and materialization before an unmounted range is edited. Each unmounted top-level range registers a boundary with `reason: 'viewport-virtualization'`, `copyPolicy: 'model'` and `selectionPolicy: 'materialize'` (`packages/plitejs/src/react/viewport-boundary.tsx:15-45`), and TanStack Virtual drives the mounted window through `useVirtualizedRootPlan` (`packages/plitejs/src/react/virtualized/use-virtualized-root-plan.ts`). The 2026-06-12 huge-document research concluded this shape was right and that no rearchitecture was due (`c70bacbd4a:docs/plite/research/2026-06-12-huge-doc-architecture/README.md:20-25`). Limit: the June run also had `auto` and `staged` strategies; today `virtualized` is the only viewport runtime type (`packages/plitejs/src/react/components/editable.tsx:45-50`).

## DOM coordinates over unmounted content

- Exact DOM resolution stays exact over virtualized content: `DOMEditor.resolveDOMPoint` and `resolveDOMRange` return `null` for a point or range with no mounted DOM (`packages/plitejs/src/dom/plugin/dom-editor.ts:189-190`, `:553-570`), and callers that must know what covers the gap use the editable DOM runtime's `domCoverage.resolveDOMPointOrBoundary` and `domCoverage.resolveDOMRangeOrBoundary`, which return the covering boundary instead (`packages/plitejs/src/dom/plugin/dom-coverage.ts:750-783`, tests in `packages/plitejs/test/dom/dom-coverage.ts`). Unlike CodeMirror, Plite has no public estimated-coordinate API; the 2026-06-12 research decided not to add one (`c70bacbd4a:docs/plite/research/2026-06-12-huge-doc-architecture/README.md:99-128`).

## Virtualized selection endpoints

- The virtualizer's range extractor always keeps the top-level rows of both selection endpoints mounted, plus the selected and promoted top-level indexes, and leaves every other off-window row unmounted; during a native scrollbar drag it raises overscan to at least 96 rows (`packages/plitejs/src/react/virtualized/use-virtualized-root-plan.ts:22`, `:95-113`, `:133-176`). The 2026-06-12 decision, taken from CodeMirror's extra one-line viewports, retains endpoint rows rather than whole endpoint page units so the DOM budget holds; widen it only when a bug proves the larger DOM cost is needed (`c70bacbd4a:docs/plite/research/2026-06-12-huge-doc-architecture/README.md:130-159`).

## Selection over partial DOM

- Plite keeps huge-document vertical selection native only where DOM coverage is reliable and projects it from the model where DOM is partial. ProseMirror can leave ordinary shifted vertical selection to the browser because its whole document is in the DOM; with virtualization the target line may be absent, so a native selection selects the wrong thing or nothing and brings back wrong targets and double highlighting. Pure native virtualized selection was rejected twice for this reason. Source: `c70bacbd4a:docs/plite/research/2026-06-12-huge-doc-native-selection/README.md:7-14`, `:116-123`; `c70bacbd4a:docs/plite/research/2026-06-12-huge-doc-architecture/README.md:1199-1200`. ProseMirror and Lexical stay behavioral and performance baselines for huge documents, not architecture targets for partial-DOM selection (`c70bacbd4a:docs/plite/research/2026-06-12-huge-doc-architecture/README.md:1172-1176`).

## Rendering mechanisms

- Full DOM, grouped or staged DOM, `content-visibility: auto` and viewport omission are different editing contracts, so a fast omitted-DOM result never proves equal full-DOM performance, and each mode's results stay separate. Full DOM keeps every block and every native service. Grouped or staged rendering saves some reconciliation, layout and paint but not model scans, full-text highlighting or retained DOM, and containment can change geometry, overlays and activation. `content-visibility: auto` keeps the DOM and skips offscreen layout and paint, but not DOM construction, model work or JavaScript effects, and first activation, intrinsic sizing, print and selection need proof. Viewport omission avoids most offscreen DOM creation but not model, history, collaboration or parser work, and it changes coordinates, selection, Find, print and accessibility. Plite's virtualized mode was experimental in September 2026 and is not a default, and the large-documents decision later cut Plite's own `auto`, `staged` and automatic-segment modes (`docs/research/decisions/large-documents-rendering-api.md:162-163`), so a staged comparison now needs an external comparator. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/virtualization.md:1-14`.

## Deferred virtualization experiments

- Three virtualization experiments stay deferred until their named cost is measured. Page visibility: `packages/plitejs/src/pagination/page-mount-plan.ts` filters every item (line 237), and a binary search is valid only if pages are ordered, non-overlapping intervals, which spreads, dynamic heights and retained pages can break; count inspected pages per frame at 800, 5,000 and 20,000 pages first. Containment: try `content-visibility: auto` on the existing block owner with measured intrinsic sizes (the staged group owner it also named was cut), and reject it if native Find, focus, print, range geometry, accessibility or dynamic-height anchoring change. Window snapshots: one immutable `{ items, ranges, totalSize, revision }` value per measurement change could replace repeated mutable TanStack reads, but must prove no tearing, stale geometry, missed resize or extra render. Any viewport-omission comparison counts first click and type in an omitted block, backward scroll, scrollbar drag, selection and copy across omitted content, and native Find or print. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/virtualization.md:50-58`; the large-documents decision keeps the page-scan question deferred (`docs/research/decisions/large-documents-rendering-api.md:179`).

## Virtualization proof matrix

- A virtualization claim runs this matrix against full DOM, staged or grouped DOM, containment where it applies, and viewport omission, keeping each mode's results separate: cold activation (mount, click and type in an initially omitted block, jump to a far anchor, first resize); warm text (typing burst, Backspace, Delete, marks, split and join, soft break, undo and redo); scroll (wheel or touchpad, PageUp and PageDown, Home and End, fast reversal, scrollbar thumb, long horizontal lines) with no blank frame, jumping anchor or lost caret; selection (drag across range boundaries, Shift navigation, select-all, offscreen endpoints, double and triple click); clipboard across omitted blocks, including large payloads and an external round trip; rich layout (tables, merged cells, loading images, font swaps, equations, nested views, custom block renderers); multi-view (one model in two differently scrolled views, portals, duplicate IDs, a read-only view); IME composition across scroll and resize; editor and native Find; print and export; accessibility; and teardown with long-scroll and remote-update soak. Five trace samples are diagnostic, not a p95 or p99, and viewport emulation proves neither mobile input nor screen-reader behavior. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/virtualization.md:60-79`.

## Measured virtualized costs (2026-09-09)

- On 2026-09-09 the registered virtualized pagination burst passed (a 65.3 ms burst against 62.0 ms for its staged control, 334 retained document nodes), but the real-editor pagination target, with five observations per operation, showed slow complete recipes: click to caret 108.0 ms, drag selection 190.3 ms, click then insert break then type 364.6 ms against 284.0 ms for the same edit preselected, undo and redo 182.0 ms, and a 200 ms long task. The gap between preselected and click-first recipes makes first-interaction ownership the attribution target. A 5,000-block virtualized trace mounted 15 blocks with 4,985 pending, and selection took 72.2 ms before materialization against 49.9 ms after; the artifact's `*ToPaint` clocks are frame opportunities. The full huge-document target failed its legacy comparison (worst p95 ratio 7.97 against a 1.5 limit) with zero correctness failures, and Event Timing in a 752-case journey run saw 432 ms for repeated staged Shift+ArrowDown and 264 ms for 10,000-block staged and 20,000-block partial-DOM select-all, paste and undo journeys. The receipts sit in an ignored run directory a fresh checkout lacks, and the staged mode and much of the virtualized rendering code have changed since; rerun the named target before citing a number. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/virtualization.md:81-104`.

## Measuring virtualized modes

- Measure input-to-model commit, input-to-paint where a recorder supports it, complete settlement, DOM count, retained heap, allocated bytes, layout and style work, and blank or jumping frames separately. Two `requestAnimationFrame` callbacks give a frame opportunity, not verified paint, and PerformanceObserver Event Timing detects stalls but censors fast events and stops before asynchronous editor work completes. For scroll, report p50, p75, p95 and maximum frame intervals and dropped or blank frames over a fixed trajectory, with scroll distance and rendered range; first activation includes materialization and focus restoration; native Find and print include the time and memory needed to expose the whole document. More overscan trades memory and mount work for fewer blank frames, so a default cannot come from one warm forward-scroll trace. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/virtualization.md:106-112`.

## Pagination canvas

- Plate adds no pagination layout runtime of its own. `platejs/pagination/react` re-exports Plite's paged types and `PagedEditorContent`, which renders Plate's renderers, handlers and slots through Plite's `PagedEditable` and forwards its `virtualize` flag (packages/platejs/src/pagination/react/PagedEditorContent.tsx:20-58; packages/platejs/src/pagination/react/index.ts:1-12, checked 2026-10-08). The 2026-09-11 read found the same thin-facade shape (docs/plite/research/2026-09-11-large-documents-contract/read-log.tsv:23).

- Pagination owns its viewport, page and unit visibility, canvas extent and page coordinates, and mounts content directly in canvas coordinates. `PagedEditable` keeps its own viewport store and mount plan and renders through `WindowedEditable` with a viewport plan whose `coordinateSpace` is `'canvas'`; that plan renders descendants without the translated row wrappers of the `'flow'` plan that `VirtualizedEditable` uses (packages/plitejs/src/react/components/windowed-editable.internal.tsx:49; packages/plitejs/src/react/viewport-plan.ts:20; packages/plitejs/src/react/components/editable-text-blocks.tsx:1634-1668). On 2026-09-11 pagination instead passed three layout arrays through the generic TanStack-backed plan, which rebuilt page maps and a total height pagination already knew, and the example subtracted a virtual offset from canvas coordinates; an instrumented probe counted 214, 2,014 and 20,014 warm page reads at 100, 1,000 and 10,000 pages where a direct projection read 2 (docs/plite/research/2026-09-11-large-documents-contract/shards/002-pagination-and-cost.md:8-40,51-67). Those were property reads on the removed path, not latency. Limit: single and spread pages, borders and padding, zoom, RTL and fragmented tables still need browser proof (same shard:64-67).

- **Pagination validates the fragmentation plan against the node and never drops oversized content.** A fragmentation provider answers `text`, `atomic` or `direct-children`; pagination derives every path from the document snapshot, so callers pass none ('lowers atomic owners and exact direct children without caller paths', `packages/plitejs/test/pagination/page-layout-contract.test.ts:217`), and it throws for a `direct-children` plan over a block whose children are text and for a non-finite or negative atomic size (`:332`). An atomic block larger than the page content box is placed once on its page and the following block starts a new page (`:394`, 'places oversized content once and following content on a new page'), and a custom engine that changes a declared atomic size fails with 'Pagination engine changed an atomic block size.' (`packages/plitejs/src/pagination/index.ts:1073`). Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/reference/public-docs/libraries/plite-pagination/index.mdx:94-96`; tests and code read 2026-10-08, not run. Limit: the source's claim that oversized content expands the occupied page geometry was not checked against the snapshot rects.

- **Cold pages can use estimated lines while active blocks measure exactly.** On 2026-05-31 a virtualized single-page pagination route with an 800-row table and 990 generated stress pages loaded in 1,217.8 ms with a 539.7 ms scroll settle, against 648.5 ms and 216.5 ms for the staged control, although its DOM stayed bounded; a CPU trace put the time in layout composition, where Pretext prepared every cold block (`prepareWithSegments`). The fix let a caller supply the layout engine and estimate cold blocks. Today `createPretextPageLayoutEngine` takes an `estimateBlock` callback that decides per text block whether to measure or estimate (`packages/plitejs/src/pagination/index.ts:207-216`, `:1369-1374`, `:1625-1638`), and `createEstimatedLines` keeps hard line breaks while spreading characters at about eight pixels each over the content width (`:674-700`). The 2026-05-31 review named the correctness traps: an estimator that ignored hard newlines, and painting a split selected block as one native-flow box, so native flow stayed limited to single-fragment blocks. Source: `c70bacbd4a:docs/transplant/slate-v2/archive/docs/plans/2026-05-31-pagination-virtualized-rows800-perf.md:89`, `:95-108`, `:114-115`; code read 2026-10-08. Limit: the numbers came from the retired `.tmp/slate-v2` checkout with no committed artifact, and the staged control lane no longer exists.

## Explicit omission surfaces

- Plite omits document DOM only on request. Plain `Editable` renders every top-level node. `VirtualizedEditable`, from the `plitejs/react/virtualized` subpath, windows top-level blocks through TanStack Virtual and throws a `RangeError` for a non-positive `estimatedBlockSize` (default 32) or a negative or fractional `overscan` (default 2) (packages/plitejs/src/react/virtualized.tsx:23-47). `PagedEditable` takes `virtualize`, default `false`, and filters page items and fragments to the viewport only when it is true (packages/plitejs/src/pagination/react.tsx:947,1104-1179). The 2026-09-11 large-documents review ranked this dedicated-subpath shape as the challenger to a `virtualize` prop on `Editable`, and rejected an async backend loader, a global window store, a new height index, a public virtualizer factory and passthrough backend config (docs/plite/research/2026-09-11-large-documents-contract/README.md:72-93; shards/003-package-and-initial-render.md:53-58). The `domStrategy` modes, the auto threshold and the staged segments it cut no longer appear in packages/plitejs/src (git grep, 2026-10-08). Limit: source reading; no browser run stands behind this entry.

## Rejected mechanisms

- The 2026-09-11 large-documents review rejected, each with a reopen condition: a fix that keeps only the outer host stable while active children remount; redefining layout-fragment coordinates or adding a root CSS marker to compensate for a duplicated page transform; a second global window store or bespoke height tree; a find-policy field that performs no search; treating full DOM as a certificate for browser, assistive-technology or clipboard services; re-adding hidden-key slicing; and an empty server shell or permanent error for an unbounded container (docs/plite/research/2026-09-11-large-documents-contract/rejected-ledger.tsv:2-9; shards/002-pagination-and-cost.md:73-79). Plite still publishes omitted top-level ranges as endpoint-only `EditableViewportBoundary` entries with anchor and focus NodeKeys and an index range (packages/plitejs/src/react/components/editable-text-blocks.tsx:1624-1633), the historical E19 shape.

## Mounted identity and composition

- `VirtualizedEditable` keys each mounted row by its top-level NodeKey inside one `data-editor-virtualized-viewport` parent (packages/plitejs/src/react/components/editable-text-blocks.tsx:1634-1665), so a block that stays in the window keeps the same keyed parent as the window moves. The 2026-09-11 helper `createVirtualizedTopLevelItemGroups` keyed row groups by their first and last item index, and with the shipped key hierarchy overlapping item 1 was replaced when the window moved from [0,1,2] to [1,2,3]: a retained item key under a different keyed parent does not keep its DOM (docs/plite/research/2026-09-11-large-documents-contract/shards/001-native-and-lifetime.md:13-18). Limit: current retention is read from source only, with no IME, browser or multiple-view proof.

- No Plite viewport plan receives the composing block. `VirtualizedEditable` passes `useVirtualizedRootPlan` the selection paths, the selected top-level index and one promoted index (packages/plitejs/src/react/virtualized.tsx:62-80), and paged windowing keeps only selected and promoted paths (packages/plitejs/src/pagination/react.tsx:1135-1154). `getPagedEditableMountedPageIndexes` accepts `composingTopLevelIndex` but nothing in the repository calls it (packages/plitejs/src/pagination/page-mount-plan.ts:163; git grep, 2026-10-08). The 2026-09-11 review found the same gap when that helper was called only by tests (docs/plite/research/2026-09-11-large-documents-contract/shards/001-native-and-lifetime.md:19-23). Retaining the composing block's model path is not enough: ProseMirror's view keeps the composing text node itself alive while it reconciles children (ProseMirror/prosemirror-view@ca4c78e9b56f1b164c0b3758b59d8748f11b7534:src/viewdesc.ts:765-852; same shard:53-55). Keeping an IME composition alive while its block scrolls out of the window is unproven.

## Coverage boundaries and materialization

- `materializeBoundary` reports whether a handler accepted the request, not whether the target DOM committed: it returns `missing-boundary` for an unknown id, `unhandled` while composing or when no handler accepts, and `handled` as soon as one registered handler returns true (packages/plitejs/src/dom/plugin/dom-coverage.ts:684-711). `DOMCoverageBoundary` registers its boundary and its materialize handler in layout effects (packages/plitejs/src/react/components/dom-coverage-boundary.tsx:98-115). The 2026-09-11 review asked for distinct requested, committed, cancelled and failed states built on the root DOM scheduler, not a new public promise or global queue (docs/plite/research/2026-09-11-large-documents-contract/shards/001-native-and-lifetime.md:24-28); still open on 2026-10-08.

- A coverage boundary follows NodeKeys, so a structural edit cannot leave it covering the wrong path. On each new snapshot index the registry re-resolves every boundary (`syncRegistryToEditor`, `packages/plitejs/src/dom/plugin/dom-coverage.ts:435-459`): the owner moves by its NodeKey, and when `coveredRuntimeRanges` is set each covered endpoint is resolved by its NodeKey. If the owner or an endpoint is gone, or an endpoint has left the owner, as a split, merge or remove of covered content can do, the boundary is dropped from the registry; a boundary with only path ranges rebases them from the owner's old path to its new one (`resolveBoundary`, `resolveCoveredPathRanges`, `:183-288`). Tests: `packages/plitejs/test/dom/dom-coverage.ts:1233` ('invalidates a boundary when split moves covered runtime outside its owner') and `:1251` (merge). Boundaries are bucketed by top-level index, and a range whose first and last top-level indexes differ by more than 128 (`ROOT_SPAN_INDEX_LIMIT`) goes to one catch-all bucket (`:305-370`), so a point lookup checks only its own bucket and the catch-all. The May 2026 design sized this for a 5,000-block, 100-boundary stress case without an interval tree. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/developer-experience/2026-05-02-plite-dom-incomplete-work-should-start-with-internal-coverage-boundaries.md:107-120`. Limit: the bucketing was read from source on 2026-10-08, and the stress case was not rerun.

- **DOM coverage is per mounted view.** `DOMCoverage.create(editor)` returns an independent coverage session for one mounted view (`packages/plitejs/src/dom/plugin/dom-coverage.ts:542-550`). Each session keeps its own boundary registry and materialize handlers, and `destroy()` clears them (`:552-575`). `registerBoundary` returns a disposer that removes the boundary only while its own registration is still current, so a stale disposer cannot remove a later registration with the same boundary id (`:717-729`). Two views of one editor therefore keep separate registrations. Source: `c70bacbd4a:docs/plite/reference/public-docs/libraries/plite-dom.mdx:201-226`; code read 2026-10-08, not run.

## Native services

- Mount counts and a full model slice do not certify native browser services over omitted content. Browser Find, print, accessibility and rich HTML copy each need their own product decision and native proof lane, and a windowed editor's mounted `innerHTML` is not a document export; full-content export goes through the static renderer (docs/plite/research/2026-09-11-large-documents-contract/shards/001-native-and-lifetime.md:39-42; shards/003-package-and-initial-render.md:67-70; rejected-ledger.tsv:7). The `nativeSurfaceComplete` flag that review rejected as such a certificate has since been deleted. No native Find, assistive-technology, print or OS clipboard lane was run.

## Packaging and first render

- Only the `plitejs/react/virtualized` entry imports TanStack Virtual, which stays an optional peer (packages/plitejs/package.json:213-226; sole importer packages/plitejs/src/react/virtualized/use-virtualized-root-plan.ts:1-5, git grep 2026-10-08). Pretext is also an optional peer, imported by `plitejs/pagination` (packages/plitejs/src/pagination/index.ts:1-11), so ordinary editor setup does not need it. The build forbids `react` and `react-dom` in the root and headless pagination entries and keeps bare imports with `deps.neverBundle` (packages/plitejs/tsdown.config.mts:24-33; tooling/config/direct-package.config.mts:67). On 2026-09-11 the plain React entry still imported TanStack statically: a resolver probe that withheld it loaded the root entry and failed the React entry, and whole-entry reachable unminified bytes were 1,352,547 (root), 2,693,503 (React) and 2,773,781 (pagination React) from the real tsdown config with declarations off (docs/plite/research/2026-09-11-large-documents-contract/shards/003-package-and-initial-render.md:5-26). Those bytes predate the subpath split and are not bundle, gzip or parse cost.

- Complete-DOM server output grows with the document. On 2026-09-11 Node rendered the built runtime without `window` or `document` on a fixture of one unique short paragraph per block; full rendering emitted 31,423, 315,342 and 3,196,023 bytes for 100, 1,001 and 10,000 blocks (docs/plite/research/2026-09-11-large-documents-contract/shards/003-package-and-initial-render.md:28-42). The auto and staged columns of that run measured modes that no longer exist. Until a scroll element exists, including on the server, `VirtualizedEditable` renders a deterministic window of the first min(8, count) blocks plus any retained selected or promoted index (packages/plitejs/src/react/virtualized/use-virtualized-root-plan.ts:196-201; packages/plitejs/src/react/viewport-plan.ts:153-168), the bounded initial window the review preferred over an empty server shell (same shard:60-65). Neither path has a measured hydration, readiness or first-input result.

## Chunking

- **Why child-count chunking is not a Plite foundation.** Legacy Slate's chunking is opt-in, since `withReact` sets `getChunkSize` to return `null`, and it is skipped for blocks whose children are inline (`ianstormtaylor/slate@945a484df2497e4c448b33f417b0de2a49840032:packages/slate-react/src/plugin/with-react.ts:26`; `ianstormtaylor/slate@945a484d:packages/slate-react/src/hooks/use-children.tsx:51-53`). The April 2026 chunking review found it did two jobs: it limited React rerender and reconcile work after broad subtree invalidation, and it grouped blocks into coarse islands that `content-visibility: auto` could skip. It read the nested-edit cost of Slate #4141, where one deep text edit rerendered many ancestors, as a render-breadth defect, not a missing chunk API. Its fix is immutable committed snapshots, stable node keys and per-node selector subscriptions, with the target that a leaf edit rerenders only the leaf, its element and selection-aware UI; a runtime that still needs chunks for ordinary nested edits has failed. That is the reason behind `docs/vision/plite.md:61` and the lack of public chunk controls (`:547-549`); the `react-rerender-breadth` target measures leaf, ancestor and selection rerender breadth (`benchmarks/targets/slate-v2.json`), and the per-node subscriptions show in the 30,008 selector stores profiled for 10,000 paragraphs on the performance page. The review's other proposals, semantic islands, an always-live editing corridor and default occlusion outside it, were not adopted: ordinary `Editable` mounts the complete DOM and omission is an explicit choice (`docs/vision/plite.md:732-736`). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/references/chunking-review.md:21-112`, which says 'legacy plite-react' for legacy slate-react after the rename; Slate source reread 2026-10-08.
