# Plite: drag and drop

## Performance evidence

- On development builds in Chromium (the `native-bench5` packets, 3 × 120 samples per cohort), Plite's native drag driver measured moving-pointer dragover p95 0.4 ms against 0.1-0.2 ms for the React DnD baseline at 1,000 blocks and 0.8 ms against 0.2 ms at 5,000 blocks, inside the frozen budget of baseline p95 plus max(1 ms, 5%). Drag start, drop and teardown were faster at both sizes (single samples per packet). Drag listeners went from 62 at rest and 4,072 (1,000 blocks) or 20,072 (5,000 blocks) after activation to 58 and 72 at both sizes, so activation no longer grows with block count. Source: `docs/plans/2026-10-01-dnd-transfer-benchmark.md:200`, `:207-212`; the JSON packets were local run artifacts that a fresh checkout lacks. Limit: this does not show native is faster in general, and neither Pragmatic Drag and Drop nor modern dnd-kit was measured.

## Ownership

- Native drag events flow to Plite's DOM source and landing and then to Plite transfer, and the copied handle, menu and move shortcuts call the same transfer, which owns the document, schema, selection and history. The registry `DndKit` is unrelated to the npm `dnd-kit` library: `DndPlugin` (`apps/www/src/registry/components/editor/dnd.tsx:423`, exported as the one-plugin `DndKit` at `:451`) installs the block wrapper, the indicator, a root presentation context and the move shortcuts, and `DndRoot` (`:401`) shares a table-selection boolean and tooltip context, not a drag manager. Handles call `editor.api.dom.drag.start`, and a move such as `editor.api.transfer.move({ to: 'next' })` works without the kit, so the kit stays an optional copied preset; moving it into core would put copied React UI in the engine. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:29-45` (its line numbers 414 and 446 predate the current file).

## Replacement experiment

- Adopting Pragmatic Drag and Drop (PDD) would buy maintained browser behavior, not speed. PDD ends a drag whose source vanished on `pointerdown` or on a `pointermove`, but lets the first 20 `pointermove` events pass because Firefox leaks a few after a drag starts (`atlassian/pragmatic-drag-and-drop@abd224dd:packages/core/src/util/detect-broken-drag.ts:22-55`). Plite ends its drag session on the first `pointermove` it sees (`packages/plitejs/src/dom/utils/drag-session.ts:43-44`, `:102`), so a leaked Firefox `pointermove` could end a live drag; that is a source-backed maintenance opportunity, not a reproduced Plite bug. PDD auto-scroll and dnd-kit scrolling own their scheduling and scroll writes, and Plite must keep coordinating scroll writes with selection and repair, so an adapter that keeps Plite's mechanisms and adds a second event owner is a net loss. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:62-64`; code reread 2026-10-08.

- The only replacement shape worth testing is a private PDD gesture lifecycle that feeds Plite's DOM source context, MIME, landing and exact recipient, then the existing transfer or external import and the existing copied UI, with no public backend framework and no new document state. It could delete three things: the random session id with its MIME token and matching (`packages/plitejs/src/dom/utils/drag-session.ts:5`, `:62-65`), replaced by PDD's local payload plus editor context while keeping foreign formats and one recipient; generic native-end and missing-source routing, replaced by a surviving monitor plus view teardown, with cancellation, source removal and unmount tested; and tests of delegated library internals, replaced by upstream tests plus our adapter integration. Key and range anchors, view permissions, source freshness, full MIME export, geometry, admission, repair and history stay editor work, and the composed-scrollport helper also serves mouse selection, so adopting library scrolling cannot delete it. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:66-83`.

- Before any benchmark, a PDD replacement must prove native text source capture with exactly one drop through nested views; an `Editable` portaled into an iframe, which Plite already ships, since PDD uses the global `window`, `document` and `HTMLElement`; same-window foreign text carrying a custom MIME format, since PDD's text adapter exposes plain text and HTML while its external adapter excludes local drags; and cancellation and source removal without losing editor cleanup. Every native bridge or fork it needs counts against the maintenance benefit. Only then compare matched production builds at 1,000 and 5,000 blocks for delivered bytes, mount and unmount listeners and memory, dragover CPU and layout, and scroll frames, against non-regression limits frozen first, and keep the candidate only when the finished integration deletes responsibility; a speedup is not required. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:85-93`.

## Proof ownership

- With either driver, keep the existing editor tests and add one only for a missing failure boundary. A drag library's suite can establish its activation, event ordering, cleanup and scrolling algorithms. Plite core tests own atomic move and refusal, complete copy, roots, suggestions and history; mounted-editor tests own native selection and focus, follow-up typing, external data, a single recipient, cancellation and scroll coordination; copied-UI tests own that handles, the indicator, menus and shortcuts call the intended actions. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:116-125`.

## Driver choice

- The 2026-10-02 drag-library review recorded when each rejected library would reopen: modern dnd-kit when a concrete pointer or touch block interaction cannot be met by Plite's native handling, since today it would need a parallel native transport and competing DOM owners; React DnD when a current product must integrate with an existing React DnD manager, since it brings back manager and backend coordination without full input or editor coverage. The verdict itself, keep the native driver and defer Pragmatic Drag and Drop, is on `docs/research/decisions/dnd-ownership.md`. On 2026-10-08 no workspace `package.json` depends on Pragmatic Drag and Drop, `@dnd-kit` or `react-dnd`, except the CI-generated playground template, which still lists `react-dnd` and `react-dnd-html5-backend` (`templates/plate-playground-template/package.json:85-86`). Source: `docs/plite/research/2026-10-02-dnd-library-choice/rejected-ledger.tsv:2-3`.
