# Plite: selection and caret

## Native selection inside widgets

- When a focused widget inside the editor, such as an input in an editable void, owns the native selection, projected-selection logic must not hide, steal or misclassify it. Four editable-void rows prove it: the input's range selection stays native-owned and is not mapped as editor selection or double-highlighted (`apps/plite/tests/plite-browser/donor/examples/editable-voids.test.ts:201`), ArrowLeft inside the input stays native (`:354`), `selectionchange` noise from the input is ignored (`:423`), and the outer editor selection comes back after editing the input (`:261`). The lead came from CodeMirror's drawn-selection exception for focused widgets (https://discuss.codemirror.net/t/inability-to-use-selector-with-an-input-widget-when-using-the-drawselection-plugin/8182). The same 2026-06-13 run kept huge-document benchmark counts for mounted and pending top-level rows, boundaries, materialization and projected selection markers separate rather than one DOM budget. Source: `docs/plite/research/2026-06-13-oss-viewport-selection-proof/README.md:31-41`, `lead-ledger.tsv:6`.

## DOM selection import and navigation

- Plite's DOM selection import ignores selections the browser leaves outside live editor DOM: detached text-node endpoints (`packages/plitejs/test/react/selection-controller-contract.ts:1287`), a selection collapsed to the parent of a removed editing host (`:1380`) and an empty Selection after a selected shadow host is removed (`:1470`) each leave the model selection unchanged instead of resolving stale DOM. Import keeps backward anchor and focus order (`packages/plitejs/test/dom/bridge.ts:407`) and never reads `selection.direction`, which double- and triple-click selections leave directionless; nothing consumes `getComposedRanges()`. Navigation never lands inside a `contenteditable=false` island. The inlines example deliberately steps by offset across link boundaries, so before-link, link-start and first-character positions stay distinct where native `Selection.modify('character')` would merge them (`apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:1529`). Deleting the first or last selected character of a link collapses outside the surviving link so follow-up typing does not inherit it, while typing over a selected link character stays inside (`packages/plitejs/test/snapshot-contract.ts:6539`, `inlines.test.ts:672`). A primary click collapses and Shift+click extends a collapsed selection with model and native agreement (`apps/plite/tests/plite-browser/donor/examples/plaintext.test.ts:197`), and focusing an empty editor places one collapsed caret at the first editable position. Source: `docs/plite/research/2026-06-13-wpt-editing-oracles/lead-ledger.tsv:17-26`; `docs/plite/research/2026-06-13-playwright-selectionchange-race-oracles/README.md:17-46`.

## Word movement

- Browser word movement in the plaintext example crosses the symbol runs around a word, backward to the start of leading symbols and forward to the end of trailing ones (`apps/plite/tests/plite-browser/donor/examples/plaintext.test.ts:1465`, from WPT `move-by-word-with-symbol`). Two WPT rows stay open. On 2026-06-13 Chromium word movement in the plaintext route went from offset 0 to 4 over `희진DJ`, where WPT and Unicode word-boundary rules stop at offset 2, and Plite has not decided whether to override browser word movement with Unicode segmentation. An app's `selectstart.preventDefault()` does not veto Plite's model-owned Shift+Arrow extension (no `selectstart` handling exists in `packages/plitejs/src` on 2026-10-08), which `docs/vision/plite.md:676` leaves to an accepted plan. Route oracles attempted for both were reverted. Source: `docs/plite/research/2026-06-13-wpt-editing-oracles/lead-ledger.tsv:27-29`.
