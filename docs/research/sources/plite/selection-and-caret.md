# Plite: selection and caret

## Native selection inside widgets

- When a focused widget inside the editor, such as an input in an editable void, owns the native selection, projected-selection logic must not hide, steal or misclassify it. Four editable-void rows prove it: the input's range selection stays native-owned and is not mapped as editor selection or double-highlighted (`apps/plite/tests/plite-browser/donor/examples/editable-voids.test.ts:201`), ArrowLeft inside the input stays native (`:354`), `selectionchange` noise from the input is ignored (`:423`), and the outer editor selection comes back after editing the input (`:261`). The lead came from CodeMirror's drawn-selection exception for focused widgets (https://discuss.codemirror.net/t/inability-to-use-selector-with-an-input-widget-when-using-the-drawselection-plugin/8182). The same 2026-06-13 run kept huge-document benchmark counts for mounted and pending top-level rows, boundaries, materialization and projected selection markers separate rather than one DOM budget. Source: `docs/plite/research/2026-06-13-oss-viewport-selection-proof/README.md:31-41`, `lead-ledger.tsv:6`.

## DOM selection import and navigation

- Plite's DOM selection import ignores selections the browser leaves outside live editor DOM: detached text-node endpoints (`packages/plitejs/test/react/selection-controller-contract.ts:1287`), a selection collapsed to the parent of a removed editing host (`:1380`) and an empty Selection after a selected shadow host is removed (`:1470`) each leave the model selection unchanged instead of resolving stale DOM. Import keeps backward anchor and focus order (`packages/plitejs/test/dom/bridge.ts:407`) and never reads `selection.direction`, which double- and triple-click selections leave directionless; nothing consumes `getComposedRanges()`. Navigation never lands inside a `contenteditable=false` island. The inlines example deliberately steps by offset across link boundaries, so before-link, link-start and first-character positions stay distinct where native `Selection.modify('character')` would merge them (`apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:1529`). Deleting the first or last selected character of a link collapses outside the surviving link so follow-up typing does not inherit it, while typing over a selected link character stays inside (`packages/plitejs/test/snapshot-contract.ts:6539`, `inlines.test.ts:672`). A primary click collapses and Shift+click extends a collapsed selection with model and native agreement (`apps/plite/tests/plite-browser/donor/examples/plaintext.test.ts:197`), and focusing an empty editor places one collapsed caret at the first editable position. Source: `docs/plite/research/2026-06-13-wpt-editing-oracles/lead-ledger.tsv:17-26`; `docs/plite/research/2026-06-13-playwright-selectionchange-race-oracles/README.md:17-46`.

- A collapsed Backspace from just after an inline link deletes the link's last character and keeps follow-up typing inside the link: in the inlines example, Backspace at offset 0 of the text after the link, then typing `tail`, puts `tail` inside the link (`apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:773`, `keeps typing after a link-boundary Backspace inside the link`). Only explicit deletion of a selected first or last link character collapses outside the link. The 2026-06-13 WPT run cited a row named `keeps typing after a link-boundary Backspace outside the link`, which no longer exists. Source: `docs/plite/research/2026-06-13-wpt-editing-oracles/README.md:276-297`; test read 2026-10-08. Limit: Plite inlines example, desktop projects only.

## Word movement

- Browser word movement in the plaintext example crosses the symbol runs around a word, backward to the start of leading symbols and forward to the end of trailing ones (`apps/plite/tests/plite-browser/donor/examples/plaintext.test.ts:1465`, from WPT `move-by-word-with-symbol`). Two WPT rows stay open. On 2026-06-13 Chromium word movement in the plaintext route went from offset 0 to 4 over `희진DJ`, where WPT and Unicode word-boundary rules stop at offset 2, and Plite has not decided whether to override browser word movement with Unicode segmentation. An app's `selectstart.preventDefault()` does not veto Plite's model-owned Shift+Arrow extension (no `selectstart` handling exists in `packages/plitejs/src` on 2026-10-08), which `docs/vision/plite.md:676` leaves to an accepted plan. Route oracles attempted for both were reverted. Source: `docs/plite/research/2026-06-13-wpt-editing-oracles/lead-ledger.tsv:27-29`.

## Inactive selection

- A primary pointer press into a nested editor clears the outer editor's inactive selection paint before `mousedown`, while the outer model range stays available for restoration; secondary and non-primary presses, presses whose nearest `contenteditable` ancestor is `false`, and marked controls keep the paint. A capture-phase `pointerdown` listener on the existing document focus coordinator does it, added and removed with the coordinator's first registration and last unregistration (`packages/plitejs/src/react/inactive-selection.ts:92-108`, `:109-132`). Before the September 2026 fix, trusted `pointerdown` and `mousedown` both saw one stale paint wrapper. Proof: 56 focused tests and five native Chromium replays (`docs/plans/2026-09-10-editor-performance-execution.md:94-97`). Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/experiments.md:118-122`.

## Repair-induced selectionchange

- Plite does not read a `selectionchange` caused by its own DOM repair back as user intent. Arming a repair sets `selectionChangeOrigin = 'repair-induced'` for a guard window (`packages/plitejs/src/react/editable/dom-repair-queue.ts:195-215`). The input runtime classes repair-induced and programmatic-export selectionchange as model-owned and refuses to import it as native intent (`packages/plitejs/src/dom/plugin/dom-input-runtime.ts:452-457`, `:524-533`). In June 2026 the research kept this guard after a single unattributed browser long task. Like Lexical and ProseMirror, it treats selectionchange as a shared async browser signal. Source: `docs/plite/research/2026-06-12-browser-longtask-selection-oracles/lead-ledger.tsv:3`.

## Triple-click

- Plite's browser rows prove that a triple-click selects only the clicked block (checked 2026-10-08 under `apps/plite/tests/plite-browser/donor/examples/`). A paragraph that starts with a link, or that holds a read-only inline, selects as one whole paragraph (`inlines.test.ts:969`, `:1009`). Backspace or paste after a triple-click replaces a paragraph that ends with a link (`inlines.test.ts:1183`, `:1218`). A browser triple-click selects, deletes and replaces the current rich-text block (`richtext.test.ts:7254`, `:7310`, `:7353`). Triple-clicking the last table cell selects only that cell's text (`tables.test.ts:164`). The 2026-06-14 run also cited a `select.test.ts`, which no longer exists. Source: `docs/plite/research/2026-06-14-selection-triple-click-inline-normalization/lead-ledger.tsv:2`.

## Pointer selection

- Plite treats a Firefox collapse of an inline-link drag selection as a browser bug to repair from evidence: on mouseup it replays the expanded DOM range captured during the drag, but only in Gecko, only after the pointer moved and not for a click inside already selected text (`shouldReplayMouseUpDOMSelection`, `packages/plitejs/src/react/editable/root-interaction-dom-selection-replay.ts:121-136`, called from `packages/plitejs/src/react/editable/root-interaction-controller.ts:1927-1929`). `apps/plite/tests/plite-browser/donor/examples/visual-native-selection-smoke.test.ts:320` ('inline link drag selection has one native highlight') proves model, native and DOM agreement with no double highlight. ProseMirror and Lexical follow the same rule, native selection is pointer-owned and is synced or restored only from captured evidence, and neither they nor WPT had a more specific Firefox rule (2026-06-14). Source: `docs/plite/research/2026-06-14-firefox-inline-selection-mouseup/README.md:14-20`, `shards/001-pointer-selection-sync.md:29-32`; code read 2026-10-08.

## Object and caption navigation

- **Reverse vertical entry into a caption infers visibility from text length.** Moving up into media from the text after it enters a populated caption first (`EDIT-CAPTION-NAV-005`) and stops on the owner for an empty one (`EDIT-CAPTION-NAV-006`); the caret engine decides by `NodeApi.string(node).length > 0` and then places the caret by DOM geometry at the previous line's horizontal position. That tracks Plate's current media rendering, which hides an empty caption unless the caption or asset is active, but the public `object: true` schema role has no visibility contract. Horizontal owner navigation reads direction from the nearest `[dir]` around the Editable or its computed style, so an RTL child inside an LTR editor is unproven. Code: `packages/plitejs/src/react/editable/caret-engine.ts:530-537`, `:612-626`, `packages/plitejs/src/interfaces/schema.ts:393`. Proof on 2026-09-22: 41 Plite React tests and 14 media caption Chromium cases. Source: `docs/research/raw/2026-09-22-caret-navigation-robustness-observation.md:13-32`. Limit: nothing proves mixed direction, non-media object layouts, media embed reverse traversal or other browsers.

- **Plain horizontal arrows inside a text leaf skip the direction read.** Before owner navigation, the caret engine returns early for a collapsed caret strictly inside a text leaf, so an ordinary ArrowLeft or ArrowRight never reads computed direction; only a caret at a leaf edge or a node selection reaches `getHorizontalModelReverse`. Code: `packages/plitejs/src/react/editable/caret-engine.ts:652-667`. Source: `docs/research/raw/2026-09-22-media-object-arrow-final-proof.md:3`, checked against the code on 2026-10-08.

## Focus

- Plite has two focus stores, and neither tells two Editables over one view apart. At `fe0e9599a6`, `api.react.isFocused` read `IS_FOCUSED` (`dom-editor.ts:1707`) and `read.view.isFocused` read view state (`editor-runtime-view.ts:178`, `public-state.ts:4491`); a window blur keeps the flag true on purpose (`packages/plitejs/src/react/editable/selection-reconciler.ts:192-199`, unchanged on 2026-10-08); focus moving into a nested Editable leaves the outer one focused (`selection-reconciler.ts:219-233` then); a new view copies its source's focus (`editor-runtime-view.ts:1293`); and mounted Editables share their view's state (`:110`). That is why the autocomplete owner still detects another editor's focus with a `[data-editor="true"]` DOM check (`packages/platejs/src/react/features/combobox/comboboxOwner.internal.ts:251-258`); a per-mount focus fact needs a new Plite query. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:46-50`.

- An exact per-view focus flag would change many readers. `useEditorFocused` feeds the floating toolbar, footnote, mention, tag, horizontal-rule and media components and `BlockPlaceholderPlugin`, so nested-view exactness would drop outer toolbars and selection rings, and a flag that flipped on window blur would make them flicker on every tab switch; Copilot's auto-trigger and the link toolbar also read focus. Inside Plite, DOM selection export (`selection-reconciler.ts:1049` at `fe0e9599a6`), Android selection reapply, the root engine, the native-history fallback and raw `useFocused` read it, and selection export relies on the window-blur stickiness to restore the selection when the user returns to the tab. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:84-88`.
