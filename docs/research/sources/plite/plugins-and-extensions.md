# Plite: plugins and extensions

## Read middleware

- **Read middleware nests in plugin order, delegates at most once and stays a pure read.** A plugin's `readMiddleware` wraps a declared `editorReads` descriptor with `around`. Handlers nest in plugin order, the first installed outermost: two handlers log `first:before`, `second`, `first:after` (`packages/plitejs/test/read-middleware-contract.test.ts:25`, export projections at `:98`). `next()` may take a replacement input and may run at most once; a second call throws "handlers may delegate only once" (`packages/plitejs/src/core/read-registry.ts:201-213`, test `:191`). A handler that skips `next()` decides the result, such as `false` to veto a schema-selectable node (`:64`), and an explicit `undefined` stands (`:215`). The handler runs inside the read boundary, so starting `editor.update` there throws, even from a lazy generator's cleanup (`:80`, `:281`), and during a command its `state` sees the transaction draft (`:240`). Two read descriptors with the same id cannot both install (`:167`). The public docs name the slot and none of these rules (`content/docs/api/core/plate-plugin.mdx:483-484`); `docs/vision/plite.md:387` says only that core-read policy composes through `readMiddleware`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/08-plugins.mdx:354-396`.

## Runtime installation and reconfiguration

- **Installing or replacing a plugin at runtime commits with the document or not at all.** `editor.install(plugin, { migrate? })` installs a plugin dynamically and returns its cleanup (`packages/plitejs/src/interfaces/editor.ts:1862-1865`). `tx.plugins.reconfigure(slot, input, { migrate? })` replaces one named plugin slot when the surrounding update commits (`:636-645`). Live reconfiguration never fills schema defaults implicitly: when the candidate schema rejects the current document, `migrate` must return the complete structural document, and the candidate document and plugin revision publish together or not at all (`:626-634`). Tests: 'publishes a dynamic plugin migration and schema atomically', 'requires an explicit migration when candidate root defaults change the document', 'stages reconfiguration until one committed configuration revision', 'does not activate staged configuration when the update aborts' and 'rolls back document and configuration when candidate activation fails' (`packages/plitejs/test/plugin-configuration.test.ts:526`, `:1288`, `:1357`, `:1398`, `:1426`). The activation contract (`beforePublish` vetoes, `afterPublish` observes) is `docs/vision/plite.md:405-419`. The retired page taught this as `editor.extend`, which Plite cut in favor of `editor.install` (`docs/vision/plite.md:249-253`). Source: `c70bacbd4a:docs/plite/reference/public-docs/libraries/plite.mdx:138-178`, with the same contract in `c70bacbd4a:docs/plite/references/architecture-contract.md:136-142` and `c70bacbd4a:docs/plite/absolute-architecture-release-claim.md:109-114`; code read 2026-10-08, tests not run.

## Change listeners

- **`on.transactionChange` sees each change step inside the update; `on.commit` runs after publication.** A plugin's `on.transactionChange` runs synchronously each time the update records a canonical change, before publication. Its context holds that step's `change`, lazy `changed` queries in the step's final coordinates, the `before` and `after` document values and the active `tx` (`EditorTransactionChangeContext`, `packages/plitejs/src/interfaces/editor.ts:2663-2675`; dispatch at `packages/plitejs/src/core/public-state.ts:8319-8370` and `:8622-8630`). In a probe on 2026-10-08, one update with two `tx.text.insert` calls produced two calls, which read the draft through `tx` (`one!`, then `one!?`) while `editor.read` still returned `one`, and then one `on.commit` after the callback returned. Plugin listeners do not run while `state.transaction(...)` builds a spec: the dispatcher passes only scoped observers in a spec context (`public-state.ts:8343-8349`, `:8624-8630`), and the probe's spec build produced no call. The changed paths stay on the edited node: one insert in a 20,000-block document reports only `[10000]` and `[10000, 0]` ('keeps transaction changed paths bounded in a 20k-block document', `packages/plitejs/test/transaction-contract.ts:559`; plugin notification at `:456`). `on.commit` is documented as 'Called after an editor commit is published' (`content/docs/api/core/plate-plugin.mdx:146`), but the public docs never name `transactionChange`. Source: `c70bacbd4a:docs/plite/references/pr-description.md:720-722`; code read and probe run 2026-10-08. Limit: whether a listener may write through `tx` was not checked.
