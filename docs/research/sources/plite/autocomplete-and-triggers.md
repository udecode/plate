# Plite: autocomplete and triggers

## Query representation

- Plate keeps a trigger autocomplete's query (mention, slash, emoji) in ordinary editor text and does not host it in an input element. Among the external designs read on 2026-10-02, only Atlassian's type-ahead keeps the query out of the document. It pays with custom history steps and browser workarounds, and no surveyed editor shows Android proof for isolating the query. Plate's 2024 input element existed for assistive technology, so the current owner gives the editor root combobox semantics instead. While an occurrence has a popup, `ComboboxOwner.syncAria` sets `role=combobox`, `aria-haspopup=listbox`, `aria-autocomplete=list` and `aria-expanded` and drops `aria-multiline`. While the popup is open it also sets `aria-controls` and `aria-activedescendant`. It restores the root's own attributes when the query closes (`packages/platejs/src/react/features/combobox/comboboxOwner.internal.ts:199-232`; test 'makes the editor root a combobox for the occurrence and restores it after', `packages/platejs/src/react/features/combobox/useCombobox.spec.tsx:282`). No real screen-reader run (VoiceOver with Safari and Chrome, NVDA with Chrome) has happened by 2026-10-08. That run decides whether a polite live region is also needed, and it is the one result that could reopen isolation. Source: `docs/plite/research/2026-10-02-autocomplete-query-representation/README.md:26-43`; decision `docs/research/decisions/autocomplete-ownership.md:16-28`.

## Input rules and suggestion mode

- In Plate's ordinary-text design, text substitutions rewrite text inside an open autocomplete query. A 2026-10-02 jsdom probe ran on the working tree (HEAD `cf15725603` plus uncommitted autocomplete work) with `AutoformatKit`, `BasicMarksKit`, `MentionKit` and `EmojiKit`. With the popup still open, typing turned `@(c)` into `@©`, `@a->b` into `@a→b`, `@1/2` into `@½`, `@x~2~` into `@x₂~`, `@x^2^` into `@x²^` and `@a==b==` into `@a≡b≡`. Mark rules such as `@a*b*` did not fire. The old native-input design never ran input rules on the query. On 2026-10-08 the registry's text substitutions are still disabled only inside code blocks (`apps/www/src/registry/components/editor/autoformat.tsx:10-23`), and whether autoformat should skip an open query is undecided. Source: `docs/plite/research/2026-10-02-autocomplete-query-representation/shards/004-plate-probes.md:9-28`.

- In suggesting mode, completing a mention leaves one pending suggestion that holds the mention and no struck-through query. A 2026-10-02 jsdom probe with `BaseSuggestionPlugin` and `userId: 'alice'` typed `@Aa` and clicked `Aayla Secura`. The accepted value stayed `Hi `, and no `@Aa` remained in the rendered DOM. Source: `docs/plite/research/2026-10-02-autocomplete-query-representation/shards/004-plate-probes.md:30-35`.

## Composition and Android emulation

- A 2026-10-02 probe in Playwright Chromium on `/blocks/mention-demo` typed `@`, sent CDP `Input.imeSetComposition` with `biggs`, then clicked or tapped an option. On desktop both designs inserted the mention. The ordinary-text design kept focus on the editor, kept the preedit out of the model while the DOM previewed `@biggs`, and filtered to one option. Under Pixel 5 emulation, both designs committed the preedit into the model early and put the caret at offset 11 instead of 6. So the caret fault is in Plite's Android input path at HEAD `cf15725603`, before any combobox code. Under that profile the old design never opened its popup, and the new design refused the tap with focus on `BODY`. Emulation is not a device: CDP composition on desktop Chromium with an Android user agent is not Gboard. These rows give no evidence for the input element and no Android proof for either design. The caret fault is an open gate in `docs/research/decisions/autocomplete-ownership.md` (Open gates). Source: `docs/plite/research/2026-10-02-autocomplete-query-representation/shards/004-plate-probes.md:37-57`.

- **The emulated mention caret fault did not occur with real Gboard.** On the `Pixel_9_API_36_Play` emulator (Chrome 146.0.7680.177), typing `@biggs` on Gboard into `/blocks/mention-demo` put the model caret at offset 6 with the popup showing `Biggs Darklighter`, and a later tap on that option inserted the mention with the editor still focused. The offset-11 caret fault that Pixel 5 emulation with CDP composition produced did not occur, because English Gboard sent each letter as a committed `insertText` with no composition, with the suggestion strip on. So that emulated fault says nothing yet about Gboard, and whether a composing keyboard or a physical phone reproduces it is unchecked. One run per step on 2026-10-02 (`docs/plite/research/2026-10-02-agentic-e2e-testing/shards/004-android-device-probe.md:29-31`); the `mention-taps` device case later passed five warm runs (see 'Android device lane' on `docs/research/sources/plite/testing-and-proof.md`). Source: `docs/plite/research/2026-10-02-agentic-e2e-testing/shards/004-android-device-probe.md:38-45`.

## Screen-reader semantics

- In Chromium's accessibility tree, a contenteditable root with `role=combobox`, `aria-expanded=true` and `aria-haspopup=listbox` exposes the same combobox state the old input exposed: `combobox`, `expanded`, `hasPopup: listbox`, controls and active descendant. Its paragraph content stays exposed, and focus and IME stay in the editor. On a `textbox`, `aria-haspopup` alone adds only the popup flag. This comes from a 2026-10-02 probe with CDP `Accessibility.getPartialAXTree` on `/blocks/mention-demo`. The axe-core 4.11.2 role tables allow `aria-activedescendant` and `aria-autocomplete` on `textbox` and treat `aria-controls` and `aria-haspopup` as global. They allow `aria-expanded` only where the role takes it: `combobox` requires it, and `textbox` does not allow it. Both the old and new demo pages held one empty polite live region. This is a platform-API result only; how screen readers treat a root whose role changes while it has focus is unobserved. Source: `docs/plite/research/2026-10-02-autocomplete-query-representation/shards/004-plate-probes.md:83-101`, `:69-73`.

- Plite already has one polite live region per Plite React provider for screen-reader announcements: `screenReaderAnnouncementEffect` (`packages/plitejs/src/core/screen-reader-announcement.ts:13`), rendered by `EditorAnnouncementLiveRegion` (`packages/plitejs/src/react/components/editor-announcement-live-region.tsx:174`, `aria-live="polite"` at `:194`). The arena judge chose it as the autocomplete fallback instead of a live region in copied UI. The judge also noted that every query keystroke is a full editor commit with collaboration encoding and asked for a query-typing cohort; the typing probe now has one (`apps/www/scripts/run-combobox-typing-probe.mts:149`). Source: `docs/plite/research/2026-10-03-autocomplete-arena/judge.md:62-63`.

## History of the query representation

- Plate's query representation has moved twice. Through v33, mentions used a transient inline `mention_input` element whose query was its Slate text children. Slash copied that design on 2024-04-29 (c469c75a9b). Only emoji and the generic `createComboboxPlugin` and `getTextFromTrigger` path read the query from paragraph text. v34 (PR #3168, `@udecode/plate-combobox` 34.0.0, released 2024-06-06, by Joe Anderson) made `ELEMENT_MENTION_INPUT` and `ELEMENT_SLASH_INPUT` void and moved the query into an Ariakit `<Combobox>` native input. The 2026 design is plain text with combobox ARIA on the Editable. It is not a return to v33's text-children inline, whose focused element had no combobox semantics. Source: `docs/plite/research/2026-10-02-autocomplete-query-representation/shards/005-plate-history.md:12-18`.

- The only stated reason for v34's void and native input is assistive technology. In a 2024-05-03 comment on PR #3168, Joe Anderson wrote that a void was the only way he found to make assistive technology consistently recognise the caret as inside a combobox. He named no screen reader, browser or failure, and he gave the reason only when a reviewer asked. Nobody reviewed the void choice, and the changesets frame v34 as an API change with no accessibility rationale. Ariakit arrived in the same prototype commit (437738e89a) but was treated as a swappable UI layer. IME was not a live driver: the v33 Chinese-IME defect (#1501) was traced to legacy Slate (ianstormtaylor/slate#5540, selection leaving the inline at composition start) and closed as fixed on 2024-02-07. In 2023 the lead maintainer called the input element a Notion-like product choice (#2429). The likely mechanism is inferred: v33's focused element had no combobox wiring, because its downshift `getInputProps` result was discarded, so the void moved focus onto an element announced as a combobox. Whether ARIA on the contenteditable was tried in 2024 is unknown; only Joe Anderson can say. Source: `docs/plite/research/2026-10-02-autocomplete-query-representation/shards/005-plate-history.md:20-28`, `:45-66`.

- Both earlier designs had their own defects. The v34 native input, 2024 to 2026: `autoFocus` on it threw a Slate DOM-resolution error (437738e89a). Undo needed a crash guard and `forwardUndoRedoToEditor` to bridge two undo stacks (4a5c168e96). Rerendering stopped keystrokes from reaching it in Chrome and WebKit, and `selectionchange` on inputs worked only in Firefox (PR #3285). Refocusing it hit a Chrome bug (#3853). `cancelInputOnBlur: false` left orphaned inputs until PR #4408. The cancel reinsertion point regressed twice (#4031 to PR #4322, #4778 to PR #4940). PR #4762 (2025-12-14) stopped popovers opening for every collaborator, a bug class v33 had fixed in 2022 (#1461). The v33 text-children inline: undo crashes (#1284; #3103 and PR #3107); insert and normalization crashes (#1232, #1843, #2533); blur cleanup bugs (#2609, #2919); typing closing it depending on the slate-react version (#1549); problems with paste into the query and with Android trigger detection (#1230, D#2408); and a singleton store that let plugins interfere (#2429, #1926, #1339). Its plain-text path also let the range grow past the query (#2304). Most v33 defects belong to the transient inline, not to text queries, and no source links them to the v34 decision. That no screen-reader issues were reported after v34 is not evidence that the input worked for assistive technology. Source: `docs/plite/research/2026-10-02-autocomplete-query-representation/shards/005-plate-history.md:29-43`, `:117`, `:120-123`.

## Other trigger systems

- Plate has a second trigger system outside the combobox: `AIChatPlugin` takes its own `trigger: readonly string[] | RegExp | string` and `triggerQuery: ((editor: Editor) => boolean) | null` (`packages/platejs/src/ai/react/AIChatPlugin.ts:134-137`, default trigger `' '` at `:181`), documented in `ai.mdx` and `ai.cn.mdx`. `CopilotPlugin`'s `triggerQuery({ editor })` is a different option with a different signature (`packages/platejs/src/ai/react/CopilotPlugin.tsx:68`). A rename of combobox trigger fields must not search-and-replace either. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:56`.

## Built owner

- At `fe0e9599a6` no first-party plugin used a RegExp combobox trigger (only `AIChatPlugin` takes one), no `combobox` field name collided in `packages/*/src`, the combobox owner was the only caller of `settleInput` outside Plite, and the projected-editing capture path ended at the same single keydown gate. On 2026-10-08 the first and third still hold: the first-party triggers are `@`, `/`, `:` and `[^`, and the owner is the only `settleInput` caller outside Plite (`packages/platejs/src/react/features/combobox/comboboxOwner.internal.ts:109`). Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:109-113`; the judge re-verified the RegExp and settleInput claims (`judge.md:25`, `:32`).

- Autocomplete keeps its query as ordinary document text and gives each mounted Editable that hosts a popup one private `ComboboxOwner`, found by element in a module `WeakMap` (`packages/platejs/src/react/features/combobox/comboboxOwner.internal.ts:61`). An occurrence is two range anchors: the trigger span with deletion `'drop'`, so replacing or deleting the trigger ends it, and a `typedExtent` from the trigger start to the caret with association `'outward'` and deletion `'nearest'`, which grows with typing and bounds the query (`:45-50`, created at `:309-317`); the match is recomputed, never stored. Feature policy is `ComboboxState` (`trigger` as a string, a string array or a per-character RegExp, `triggerPreviousCharPattern`, a `triggerQuery` veto, `maxQueryLength` and `queryPattern`, all required; `packages/platejs/src/features/combobox/lib/combobox.ts:11`), read live from the plugin store. Popups are `afterEditable` slot components that call `useCombobox` through the copied `InlineCombobox`. Only typed input opens an occurrence; anchors map it through every commit, remote and historic ones included; it closes when the match no longer reads, on Escape or dismiss, after completion, when a newer trigger replaces it or when its popup unmounts, and the last popup unmount disposes the owner. Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:3-13` (trace at `fe0e9599a6`), rechecked against the current owner on 2026-10-08.

- Activation: at `fe0e9599a6` the owner read Plite's private input tags (`dom-text-input` or `native-text-input`, none of `collaboration`, `historic` or `paste`) and required one pure collapsed insertion; it now listens to `api.react.subscribeTypedText` (`comboboxOwner.internal.ts:427`) and opens only while the view is focused and editable, meaning connected, not read-only and the view's own DOM root (`:260-266`, `:281`). `findTypedTrigger` walks backward over sibling text leaves only, stops at any non-text node and reads at most the typed length plus the longest trigger plus one character; a string trigger must end inside the typed text, and a RegExp trigger is tested per typed character. Among popups in mount order, which is plugin order, a strictly later trigger start wins, so the first-mounted popup wins a tie, and `triggerQuery` vetoes each candidate (`:284-303`). Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:14`.

- Query reading (`comboboxOwner.internal.ts:350-400`, `packages/platejs/src/features/combobox/lib/combobox.internal.ts:176-215`): both anchors must resolve, the selection must be collapsed in this editable view with no other editor focused, the trigger and the caret must share root and parent with only text siblings between them, the caret must lie between the trigger end and the typed extent's end, and the trigger text must be unchanged; the query is the text from the trigger end to the caret. `isComboboxQuery` (`combobox.internal.ts:69-81`) rejects a query longer than `maxQueryLength`, one that starts with whitespace, a newline and any character failing `queryPattern`, with the pattern's `g` and `y` flags stripped. While composing, the query previews the DOM text from the trigger end to the caret, now read through Plite's `api.dom.textToCaret` (`comboboxOwner.internal.ts:391`) instead of the `Range.toString()` with U+FEFF stripping used at `fe0e9599a6`; when the model read fails mid-composition, the previous match is kept and marked composing. The owner listens to `input` because composition events can precede the DOM update. Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:15`.

- Keys, focus and ARIA: the owner claims keys through a one-slot, element-keyed registry (`packages/platejs/src/react/utils/editableKeyDown.internal.ts`) that runs before Plate's shortcut table and plugin handlers (`packages/platejs/src/react/components/EditorContentView.internal.tsx:242-243`). Plite calls that handler only for editable targets in a view that is neither read-only nor composing, and a `true` return makes Plite call `preventDefault` but never `stopPropagation` (`packages/plitejs/src/react/editable/keyboard-input-strategy.ts:684-704`, `:418-431`). The owner takes only Enter, Tab, ArrowUp, ArrowDown and Escape, with no modifier including Shift, outside composition and keyCode 229, and only while its popup is open with a match (`comboboxOwner.internal.ts:52`, `:323-345`); the popup's handler goes first, and an unhandled Escape closes. The copied `InlineCombobox` returns `false` when no items render, so Enter still breaks the line. A document `focusin` refreshes the match, which ends when the active element sits under another `[data-editor="true"]` element, including a second view of the same document. The owner is the only writer of the root's combobox ARIA, set imperatively in `syncAria` (`:199`). Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:16`.

- Completion requires the popup to own the occurrence and the offered match to be current, then calls `api.react.settleInput()` and refuses unless it returns true and the view is not composing (`comboboxOwner.internal.ts:109-110`). `settleInput` refuses an active composition with no pending end, flushes a Plite-owned pending end, cancels a foreign one and flushes Android and pending native text, but never ends an active composition, so the copied `InlineCombobox` lets an option's mousedown blur the editor while composing (`apps/www/src/registry/components/editor/inline-combobox.tsx:223-225`); history replay uses the same settle. Inside one `view.update({ history: 'new-batch' })` (`comboboxOwner.internal.ts:120`) the owner rechecks the anchors, a collapsed selection, editability, element read-only state at the trigger start and the query, deletes from the trigger start to the caret, places the caret and runs the feature callback. A failed check throws a private error that rolls back and returns `false`; a `false` return refuses; a promise-returning callback throws a `TypeError` after rollback (`:155`); other throws propagate after rollback. Undo then restores the literal query and caret with no popup. `selectAfterInline` places the caret after an inserted inline for the generated insert, `MentionPlugin.insert` and the footnote insert. Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:17`.

- A plugin's slots are skipped in read-only views only when the plugin is `editOnly` (`isEditOnly(plateReadOnly, plugin, 'slots')`, `packages/platejs/src/react/components/EditorContentView.internal.tsx:283`, `:301`). Slash and emoji are `editOnly` (`BaseSlashPlugin.ts:18`, `BaseEmojiPlugin.ts:32`) and mention and footnote are not, so keeping a popup out of a read-only view takes the owner's own editable gate, not the slot. Source: `docs/plite/research/2026-10-03-autocomplete-arena/judge.md:66-69`.

## Open device and accessibility questions

- Still open for autocomplete on 2026-10-08: whether Plite can end an active composition during an option activation and keep focus with Gboard and iOS keyboards, since `settleInput` refuses rather than ends one (`packages/plitejs/src/react/editable/editable-dom-runtime.ts:989-1009`); whether Android commits a typed `@` as a replacement, which the typed-text report would not count as typing (`packages/plitejs/src/react/editable/typed-text.ts:38-42`); and which element holds focus, and so should carry the combobox ARIA, inside an owned content root, where autocomplete is not built. The screen-reader run, WebKit's confirming Enter and the Pixel 5 tap fault are tracked as open gates in `docs/research/decisions/autocomplete-ownership.md:180-205`. ## Feature popups

- The copied `InlineCombobox` (`apps/www/src/registry/components/editor/inline-combobox.tsx`) keeps an Ariakit store, passes its shown state as `open`, dismisses a query that ends in whitespace with no items, anchors the popover at the start of the match range and completes each item with its own render's match. Feature defaults: mention `@` with the shared previous-character pattern `/^\s?$/`, which the copied kit widens to `/^$|^[\s"']$/` to admit quotes (`apps/www/src/registry/components/editor/mention.tsx:188`); slash `/`, with a copied `triggerQuery` that vetoes inside code blocks and guarded items that return `false`; emoji `:` with a shortcode `queryPattern`, `filter={false}`, `hideWhenNoValue` and synchronous search; footnote `[^` with no previous-character rule and a create option that refuses a reference that became defined. All four cap a query at 75 characters (`BaseMentionPlugin.ts:47-51`, `BaseSlashPlugin.ts:11-15`, `BaseEmojiPlugin.ts:24-28`, `BaseFootnotePlugin.ts:125-129`). Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:18`.

## Stored input migration

- Documents saved with v53 autocomplete input nodes cross `migratePlateV54Inputs` (`packages/platejs/src/migrations/migratePlateV54Inputs.internal.ts`), which runs first in `shapeDocument` (`packages/platejs/src/migrations/migratePlateV54.ts:63`), turns each input into its trigger followed by its meaningful children or stored value, in the main and named roots, and maps a selection point inside an input to the end of its restored text. The trigger is the input's own stored `trigger` string when it has one; only an input without one falls back to the first-party default from the v53 manifest, because a detached migration cannot read app configuration (`migratePlateV54Inputs.internal.ts:13-17`, `:43-48`). Runtime creation, corrections and format parsing accept only the current schema. Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:19`, `contract.md:21` (trace at `fe0e9599a6`); the stored-trigger rule rechecked 2026-10-08.

## Per-keystroke cost

- Per keystroke the autocomplete owner does bounded work: each typed-text report runs one character-bounded trigger scan per mounted popup (`packages/platejs/src/react/features/combobox/comboboxOwner.internal.ts:284-303`, `packages/platejs/src/features/combobox/lib/combobox.internal.ts:147-151`), every commit and every `input` event on the Editable refresh the match (`comboboxOwner.internal.ts:432`, `:440-442`), and every `useCombobox` render calls `syncAria` (`packages/platejs/src/react/features/combobox/useCombobox.ts:113-116`). The key-to-paint contract and its development-server results, including the cut from 800 to 4 node reads per keystroke when the scan was bounded, are on `docs/research/decisions/autocomplete-ownership.md:218-231`. `apps/www/scripts/run-combobox-typing-probe.mts` now asserts popup state and computes a paired pass or fail against an A/A baseline (`:79-92`, `:343-364`). Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:21` (trace at `fe0e9599a6`), rechecked against the current owner on 2026-10-08.

## Known gaps

- Built-owner traps found at `fe0e9599a6`: `complete` captures the occurrence before `settleInput()`, so if settling commits text that replaces the occurrence, the old anchors resolve null and the call refuses; `complete` does not recheck `isAnotherEditorFocused` or `triggerQuery`; `open` reaches the hook one render late; the ARIA attributes are written imperatively on a React-rendered element, so an app that passes `aria-controls` itself contends with the owner (the owner now restores an app-written value on close, `packages/platejs/src/react/features/combobox/useCombobox.spec.tsx:311`); and the key registry holds one handler per element, so a second claimant silently replaces the first. Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:33-38`.

- The built owner works around missing Plite primitives. Still in place on 2026-10-08: a `[data-editor]` DOM check plus document `focusin` to learn which Editable holds a shared selection, because Plite's focus flag trails the DOM; the key-claim `WeakMap` around the Editable's `onKeyDown`, blind to keys Plite's capture handler consumes in content roots; owner discovery through an element-keyed `WeakMap` instead of a context; no operation that ends a composition, so the copied popup lets the option's mousedown blur the editor; a matcher that walks sibling leaves by index and maps offsets back to points by hand, because Plite has no text-run read; refusal by throwing, because Plite has no transaction abort; a second anchor that exists only to bound the query; and `settleInput` falling back to 'not composing' when no runtime is mounted. Replaced since `fe0e9599a6`: the private-tag typing check (now `subscribeTypedText`), the DOM-Range preview with U+FEFF stripping (now `api.dom.textToCaret`) and the owner-local keyCode 229 check (now the shared `isImeConfirmKeyEvent`). Source: `docs/plite/research/2026-10-03-autocomplete-arena/grounding.md:40-51`.

## Ownership arena

- On 2026-10-03 an arena compared owners for ordinary-text autocomplete at `fe0e9599a6`. Three Opus runners each designed one direction, and an Opus cross-judge scored them out of 24 on six criteria (laws by mechanism, ownership and lifetime, interface depth, scale, proof and subtraction; `docs/plite/research/2026-10-03-autocomplete-arena/rubric.md`): a Plate host per mounted Editable, with trigger policy compiled from a plugin declaration and a popup mounted only for its occurrence, scored 20; a neutral Plite typeahead host 18, losing on seven public Plite names for one consumer; the built per-Editable owner 15; and a query kept outside document text in a view-local input 11, losing on two undo stacks, IME moved out of Plite's input runtime and device-only proof. No runner or judge ran code, and every cost figure in the candidates is a prediction. The synthesis is `docs/plans/2026-10-03-autocomplete-occurrence-host.md`; on 2026-10-08 its Phase 1a repairs and Phase 1b Plite reads are built, and Phase 2 (a `combobox` declaration field, `slots.combobox` and a `ComboboxPlugin` host) waits on its best-api-review gate. Source: `docs/plite/research/2026-10-03-autocomplete-arena/README.md:1-18`, `judge.md:27-47`.
