# Rendering, decorations and overlays

These lessons come from retired solution notes, Plite references and decoration roadmaps, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`.

## Rendering

- **`Editable` sets inline styles on the editable root.** They are `position: relative`, `white-space: pre-wrap`, `overflow-wrap: break-word`, `z-index: 0`, and a transparent caret when read-only; a projected view selection forces `caretColor: transparent` even over user styles. Inline styles beat stylesheet classes, so a class such as `whitespace-normal` on the content loses without a warning; override with the `style` prop, `disableDefaultStyles` (which `EditorContent` forwards) or `!important`. `plate-components.mdx` says only "Passed to Plate `Editable`". Code: `packages/plitejs/src/react/components/editable.tsx:515`. Source: `plite/reference/public-docs/concepts/09-rendering.mdx`.
- **Leaf renderers get `leafPosition` when decorations split a text node.** When decorations split one text node into segments, Plate leaf renderers receive `leafPosition` (`start`, `end`, optional `isFirst` and `isLast`). Use it only when the presentation depends on the segment, such as rounding only the outer corners of a highlight. The type is public but no public doc mentions it. Code: `packages/platejs/src/lib/types/RenderLeafProps.ts:18`, `packages/plitejs/src/interfaces/text.ts:71`. Source: `plite/reference/public-docs/concepts/09-rendering.mdx`.
- **Leaf and text pipes check mark ownership before walking renderers.** `pipeRenderLeaf` and `pipeRenderText` first check whether the leaf owns any registered simple mark key, and only then walk the ordered renderer entries, so inactive leaf and text renderers are never called. The old mark-bundle cost (10k bold leaves: 586 ms with the basic bundle, 406 ms direct) came from visiting inactive sibling renderers while the DOM was already about the same, so equal DOM does not mean equal runtime cost. Walking every simple mark on every leaf sped up marked leaves but slowed plain leaves in rich paragraphs. Code: `packages/platejs/src/react/utils/pipeRenderLeaf.internal.tsx:205-221`, `pipeRenderText.internal.tsx:154-171`, `pipeRenderLeaf.spec.tsx:309`. Source: `solutions/performance-issues/2026-04-04-mark-bundle-tax-comes-from-inactive-leaf-and-text-renderer-fan-out.md`.
- **A bulleted list item renders as its paragraph.** The registry `ListKit` configures `ListPlugin` to inject `role=listitem` and `display: list-item` through `inject.nodeProps`, and `BlockList` returns `undefined` for bulleted items, because a per-item `<ul><li>` wrapper costs one list container per item. A DOM count probe, not a timer, found one `<ul>` and one `<li>` per item, 30k of each in the list-only lane, and removing the wrapper cut the list-only mount from about 1564 ms to about 872 ms (2026-04-04). Ordered and task items still pay the wrapper. Path-free inject props keep `pipeRenderElement`'s plain element fast path. Code: `apps/www/src/registry/components/editor/list.tsx:40`, `apps/www/src/registry/components/editor/block-list.tsx:20`, `packages/platejs/src/react/utils/pipeRenderElement.spec.tsx:484`. Source: `solutions/performance-issues/2026-04-04-flattened-list-rendering-must-not-wrap-every-item-in-its-own-list-container.md`.
- **The placeholder sets the root's minimum height.** The placeholder is an absolutely positioned overlay that adds no height, so `EditableTextBlocks` measures the mounted placeholder with a `ResizeObserver` and sets that height as the root's `minHeight`; otherwise a tall or wrapping placeholder draws outside the editor box. Code: `packages/plitejs/src/react/components/editable-text-blocks.tsx:1558-1604`, `packages/plitejs/test/react/rendered-dom-shape-contract.tsx:611`. Source: `solutions/logic-errors/2026-04-04-v2-placeholder-primitives-should-own-overlay-attrs-and-style.md`.
- **The DOM coverage warning waits one macrotask.** The dev check that reports "omitted editable child without a DOM coverage boundary" runs on the next macrotask, because iframe and portal children register their DOM bridge entries one turn after their parent. A microtask check reported mounted children as missing. A browser row asserting that the warning stays silent waits a short, bounded delay after the interaction. The `setTimeout` carries no comment. Code: `packages/plitejs/src/react/components/editable-rendered-element.tsx:88`. Source: `solutions/ui-bugs/2026-05-02-plite-iframe-mounted-dom-nodes-need-path-metadata-fallback.md`.

- **Caption state reads the live node, not the element prop.** A focused empty caption once rendered blank with no placeholder because the shared `Caption` component read an element prop that stayed stale while Plite's DOM text flow owned typing, and its focus hook passed a facade `Range` without `kind` to `SelectionApi.isText`, which accepts only `kind: 'text'` and so always failed. The component now derives emptiness from `editor.read.nodes.get(path)` through `useEditorSelector`. Code: `apps/www/src/registry/components/editor/caption.tsx:68-74`, `packages/plitejs/src/interfaces/selection.ts:188-201`. Source: `docs/research/raw/2026-09-22-media-caption-focused-empty-proof.md:1-8`.

- **Server-rendered demo values must not generate ids or timestamps.** In March 2026 the homepage playground hydrated with a mismatch on `data-table-cell-id`: the node-id plugin filled missing ids with random `nanoid()` values during editor setup, some example values held `createdAt: Date.now()` at module scope, and server and client each built their own copy of the content. Element ids no longer reach the DOM (`packages/platejs/src/react/components/plate-nodes.spec.tsx:46` asserts no `data-block-id`), and the comment demo values use fixed ISO timestamps (`apps/www/src/registry/blocks/editor-ai/components/editor/rich-text-editor-value.ts:2416`). But `ElementIdPlugin` still generates `nanoid()` ids by default (`packages/platejs/src/lib/plugins/element-id/ElementIdPlugin.ts:55`), the `normalizeStaticValue` helper the fix added no longer exists, and `apps/www/src/registry/examples/values/date-value.tsx:8` still computes `today` with `new Date()` at module scope. Keep module-scoped demo values deterministic, and when a hydration diff names an attribute backed by node data, inspect how the value was generated before changing React rendering. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-03-28-static-demo-values-need-deterministic-ids-and-timestamps-for-hydration.md`.

- **React 19 cleanup removes compatibility code, not selection timing.** The April 2026 cleanup of Plite's React layer replaced `forwardRef` wrappers and `ref as any` with React 19 ref props, and one-shot constructor `useMemo` calls with lazy `useState`. It kept two patterns that look dated and still carry behavior: layout effects that write the DOM selection before paint, and the benchmark-backed `React.memo` on descendant content. Both are still there: the repair engine exports a pending model selection from a layout effect (`packages/plitejs/src/react/editable/runtime-repair-engine.ts:86`), and `EditableDescendantContent` is `React.memo(EditableDescendantNodeInner)` (`packages/plitejs/src/react/components/editable-text-blocks.tsx:1175`). `docs/vision/plate.md:1074-1076` bans `forwardRef` and React 18 compatibility code, but no rule says what to keep, so move a selection write out of a layout effect only with browser selection proof, and drop that memo only with a rerender benchmark. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-04-07-plite-react-19-2-cleanup-should-remove-forwardref-not-selection-layout-effects.md`.

- **React code reads live core state through three facades.** Plite's React layer reads live nodes, texts and selection, and writes marks, selection and target runtimes, through `packages/plitejs/src/react/editable/runtime-live-state.ts`, `runtime-selection-state.ts` and `runtime-mutation-state.ts`; inside `packages/plitejs/src/react` only `runtime-live-state.ts` and `runtime-editor-api.ts` name the core `getEditorLive*` readers. The April 2026 cut moved those reads out of hooks, components, browser handles, selection reconciliation, DOM repair, Android input and clipboard code, so fallback order, runtime-id lookup and selection read policy have one owner. No test pins the boundary (inferred from a search of `packages/plitejs/test`), so a new direct import passes every check. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-04-27-plite-react-public-selectors-must-stay-model-truth.md`.

- **Meet the React hook rules with lazy state and selector factories, not refs.** Oxlint runs `react/refs`, `react/use-memo`, `react/preserve-manual-memoization`, `react/set-state-in-effect` and `react/immutability` as errors (`oxlint.config.ts:749-759`); they enforce React's ref and memoization semantics, not only React Compiler eligibility. A mutable cache that same-render reads need lives in a stable cell from a lazy `useState(() => ...)`, not in `ref.current`. A one-shot constructor is a lazy `useState`, not `useMemo(fn, [])`. Selector-local memory, such as the last active history root, lives in a selector factory created once (`createHistoryRootSelector`, `packages/plitejs/src/react/hooks/use-plite-history.ts:81-91`), because mirroring it into state from an effect fails `set-state-in-effect` and costs a cascading render. In May 2026 passing `attributes.ref` through Plite render props was the one ref pass-through that needed a call-site exemption; no `react/refs` suppression remains in `packages/plitejs/src`, and the only one in the packages is a block disable around `useDeepCompareMemo` (`packages/platejs/src/react/internal/useDeepCompareMemo.ts:4-17`). Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-11-plite-react-hooks-refs-lint-needs-real-render-fixes.md`.

- **Every element fast path keeps injected props.** An April 2026 render cut computed `inject.nodeProps` attributes on the plain fast path but passed raw attributes to the wrapped path, so indent, text-align and list-item props vanished whenever a `belowNodes` wrapper (now `wrapNodeChildren`) or directional affinity was active, while the benchmark stayed fast. Today `pipeRenderElement`'s fast branches render through `FastIntrinsicElement` or `FastElementWithPath`, both of which compute injected attributes through `getFastInjectedAttributes` (`packages/platejs/src/react/utils/pipeRenderElement.internal.tsx:101-130`, `:152`, `:255`), and a directional element under active `wrapNodeChildren` slots takes the full `PluginElementWithPath` path (`:420-492`), pinned by `pipeRenderElement.spec.tsx:552` (directional path) and `:599` (active `wrapNodeChildren` slots). The same cut narrowed bulleted list-item injection to paragraphs, and heading list items lost their markers; the registry `ListKit` now targets heading, paragraph, blockquote, code block, details and image (`apps/www/src/registry/components/editor/list.tsx:51-58`), and `list.spec.tsx:99` tests the query and transform but renders no non-paragraph list item. A fast path that skips the generic node-props pipeline must prove every surviving branch, and a list optimization must be checked on a non-paragraph item. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/performance-issues/2026-04-07-fast-element-paths-must-preserve-injected-props-and-non-paragraph-list-semantics.md`.

## Decorations

- **Why decorations are scoped per node.** Legacy `decorate` computed every decoration at the root and passed the flat list down, so every level reran `Range.intersection` against large sets; on mixed-depth trees such as long code blocks that intersection became the bottleneck and local redecoration was lost (Slate #4993). Flattening into leaf props also kept only one of two overlapping same-key payloads with different metadata (#3383). Current sources decorate per entry into node-key buckets and test overlapping identity; a root-level decoration list would reopen both failures. Code: `docs/vision/plite.md:40`, `packages/plitejs/src/react/decoration-source.ts`, `packages/plitejs/test/react/decoration-rendering-contract.test.tsx:593`. Sources: `plite/decorations-annotations-cluster.md`, `plite/decoration-roadmap.md`.
- **Why external state reaches a decoration source only through `observe` or a new `read`.** Slate PR #4997 tried per-node selector subscriptions and cut rerenders, but debounced external updates then caused cursor jumps, ghost DOM text and broken state, and it never landed. The old contract was split too: one side expected a new function identity to mean a full redecorate, while Plate and slate-yjs kept one stable function over changing external state. A `DecorationSource` takes external state either through `observe({ refresh })` with a `nodeKeys` scope for a targeted refresh, or through a new `read` identity, which refreshes that whole source; the async caret browser proof uses the identity path. Code: `packages/plitejs/src/interfaces/decoration.ts:29`, `packages/plitejs/src/react/decoration-source.ts:1462-1478`, `apps/www/src/app/(app)/examples/plite/_examples/decorations-async.tsx:74-83`. Sources: `plite/decorations-annotations-cluster.md`, `plite/decoration-roadmap.md`, `plite/ledgers/fork-issue-dossier.md`.
- **A decoration refresh repairs the DOM selection itself.** A refresh restructures text DOM without an editor commit, so the commit-driven selection export never runs. `Editable` subscribes to the decoration store and requests a force-render repair with model-owned selection plus a selection export after the DOM commit, and skips it while composing. Decoration adapters only refresh their sources and never force-render. In #5987 the highlight appeared while the DOM caret stayed at offset 35 and the model said 41. Code: `packages/plitejs/src/react/editable/decoration-repair-bridge.ts:20`, `apps/plite/tests/plite-browser/donor/examples/decorations-async.test.ts:56`. Source: `solutions/logic-errors/2026-05-23-async-decorate-refresh-must-export-dom-selection.md`.
- **Derived diagnostics store their inputs, not ranges.** Lint results and search matches keep their inputs (mode, query). Ranges kept in React state go stale after a text edit, so highlights or "apply fix" hit the wrong text. The decoration source recomputes from the current document on read, and a count or list beside the highlights reads through `useEditorState` so it follows the same commit; durable user ranges use annotations. Only the linting example and its browser row show the whole pattern; the search-highlighting example stores only its query. Code: `apps/www/src/app/(app)/examples/plite/_examples/linting.tsx:171`, `apps/plite/tests/plite-browser/donor/examples/linting.test.ts:6-57`. Source: `solutions/developer-experience/2026-05-19-plite-derived-lint-decorations-need-snapshot-sources-and-panel-subscriptions.md`.

- **Highlight a code block in one pass over its whole text.** Tokens computed line by line break every token that spans lines; Plate's v46 move from Prism to lowlight (#4122) fixed multi-line tokens by highlighting each code block once. The current decoration source still reads the block's whole string and calls `lowlight.highlight(language, text)`, or `highlightAuto(text)` for `auto`, once per block (`packages/platejs/src/features/code-block/lib/BaseCodeBlockPlugin.ts:901`, `:927-928`), over the one newline-bearing Text a code block holds (`docs/vision/plite.md:545-549`). Keep any future highlighter or code layout from splitting the source by line before it tokenizes. Limit: the spec 'handle multiline code blocks' (`packages/platejs/src/features/code-block/lib/BaseCodeBlockPlugin.spec.tsx:1918`) mocks the highlighter, so no test runs a real token across lines. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/history/migration/v48.mdx:300-302`.

## Pagination

- **Page chrome never wraps the editable.** `PagedEditable` renders each page surface as an absolutely placed sibling of one editor overlay that spans the page stack. `renderPage` gets sizing attributes (fixed `height`, `overflow: hidden`, `pointerEvents: 'none'`) and no document children, the overlay passes pointer events through, only its inner editor layer takes them, and the editable host sets `zIndex: 0` (`packages/plitejs/src/pagination/react.tsx:815-840`, `:1290-1361`; tests `packages/plitejs/test/pagination/react-fragments-contract.test.tsx:1115`, `apps/plite/tests/plite-browser/donor/examples/pagination.test.ts:131`). In May 2026 a page wrapper around the editable showed the text but took every real click, and a `zIndex` set in one example or a fixed height on the wrapper that held the editable only moved the failure. Prove any wrapper around `Editable` by clicking and typing through the real `[contenteditable="true"]` element, because visible text says nothing about hit testing. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-21-plite-layout-source-entry-and-paged-editable-dx.md`.

- **A paged layout binds to one root and to paths, not to element objects.** In May 2026 a layout API that accepted `root` still extracted and projected the primary root, which looked multi-root-ready and was not. Today the snapshot keeps its named root and every text range carries it (`packages/plitejs/test/pagination/page-layout-contract.test.ts:133`), the internal main-root spelling is rejected (`:159`), measurement and paint resolve inside one named-root view (`packages/plitejs/test/pagination/react-fragments-contract.test.tsx:1138`), and `PagedEditable` with `root` wraps itself in `EditorRoot` for that root (`packages/plitejs/src/pagination/react.tsx:1377-1399`). Rendered elements need not be the objects a layout snapshot captured, so render-time lookups key by path: run origins are read per `data-editor-path` (`react.tsx:864`), and cached measured lines are remapped to current source paths (`packages/plitejs/test/pagination/pretext-page-layout-engine.test.ts:241`). An API that accepts `root` needs tests that extraction, snapshots and projection all use it. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-21-plite-layout-source-entry-and-paged-editable-dx.md`.

- **Pretext measures editable text with `pre-wrap`.** CSS-normal whitespace trims trailing collapsible spaces from line ranges, so in May 2026, after spaces were typed at a paragraph end, the model held them while the projected line ended early and the spaces rendered outside the placed line. `createPretextPageLayoutEngine` defaults to `whiteSpace: 'pre-wrap'` and `wordBreak: 'normal'`, keeps both modes in its prepared-text cache key beside the text, font and letter spacing, and caches preparation in the engine closure, not in render (`packages/plitejs/src/pagination/index.ts:1369-1408`). Each inline run is measured with its own font, because fixed-width run estimates left visible gaps between regular, bold and monospace runs. Tests: `packages/plitejs/test/pagination/pretext-page-layout-engine.test.ts:53` (an empty insertion position), `:86` (trailing spaces and hard breaks under `pre-wrap`), `:110` (per-run fonts), and `packages/plitejs/test/pagination/page-layout-contract.test.ts:171`. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-21-plite-layout-source-entry-and-paged-editable-dx.md`.
