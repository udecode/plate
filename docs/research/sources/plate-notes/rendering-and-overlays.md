# Rendering, decorations and overlays

These lessons come from retired solution notes, Plite references and decoration roadmaps, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`.

## Rendering

- **`Editable` sets inline styles on the editable root.** They are `position: relative`, `white-space: pre-wrap`, `overflow-wrap: break-word`, `z-index: 0`, and a transparent caret when read-only; a projected view selection forces `caretColor: transparent` even over user styles. Inline styles beat stylesheet classes, so a class such as `whitespace-normal` on the content loses without a warning; override with the `style` prop, `disableDefaultStyles` (which `EditorContent` forwards) or `!important`. `plate-components.mdx` says only "Passed to Plate `Editable`". Code: `packages/plitejs/src/react/components/editable.tsx:515`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/09-rendering.mdx`.
- **Leaf renderers get `leafPosition` when decorations split a text node.** When decorations split one text node into segments, Plate leaf renderers receive `leafPosition` (`start`, `end`, optional `isFirst` and `isLast`). Use it only when the presentation depends on the segment, such as rounding only the outer corners of a highlight. The type is public but no public doc mentions it. Code: `packages/platejs/src/lib/types/RenderLeafProps.ts:18`, `packages/plitejs/src/interfaces/text.ts:71`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/09-rendering.mdx`.
- **Leaf and text pipes check mark ownership before walking renderers.** `pipeRenderLeaf` and `pipeRenderText` first check whether the leaf owns any registered simple mark key, and only then walk the ordered renderer entries, so inactive leaf and text renderers are never called. The old mark-bundle cost (10k bold leaves: 586 ms with the basic bundle, 406 ms direct) came from visiting inactive sibling renderers while the DOM was already about the same, so equal DOM does not mean equal runtime cost. Walking every simple mark on every leaf sped up marked leaves but slowed plain leaves in rich paragraphs. Code: `packages/platejs/src/react/utils/pipeRenderLeaf.internal.tsx:205-221`, `pipeRenderText.internal.tsx:154-171`, `pipeRenderLeaf.spec.tsx:309`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-04-04-mark-bundle-tax-comes-from-inactive-leaf-and-text-renderer-fan-out.md`.
- **A bulleted list item renders as its paragraph.** The registry `ListKit` configures `ListPlugin` to inject `role=listitem` and `display: list-item` through `inject.nodeProps`, and `BlockList` returns `undefined` for bulleted items, because a per-item `<ul><li>` wrapper costs one list container per item. A DOM count probe, not a timer, found one `<ul>` and one `<li>` per item, 30k of each in the list-only lane, and removing the wrapper cut the list-only mount from about 1564 ms to about 872 ms (2026-04-04). Ordered and task items still pay the wrapper. Path-free inject props keep `pipeRenderElement`'s plain element fast path. Code: `apps/www/src/registry/components/editor/list.tsx:40`, `apps/www/src/registry/components/editor/block-list.tsx:20`, `packages/platejs/src/react/utils/pipeRenderElement.spec.tsx:484`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-04-04-flattened-list-rendering-must-not-wrap-every-item-in-its-own-list-container.md`.
- **The placeholder sets the root's minimum height.** The placeholder is an absolutely positioned overlay that adds no height, so `EditableTextBlocks` measures the mounted placeholder with a `ResizeObserver` and sets that height as the root's `minHeight`; otherwise a tall or wrapping placeholder draws outside the editor box. Code: `packages/plitejs/src/react/components/editable-text-blocks.tsx:1558-1604`, `packages/plitejs/test/react/rendered-dom-shape-contract.tsx:611`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-04-v2-placeholder-primitives-should-own-overlay-attrs-and-style.md`.
- **The DOM coverage warning waits one macrotask.** The dev check that reports "omitted editable child without a DOM coverage boundary" runs on the next macrotask, because iframe and portal children register their DOM bridge entries one turn after their parent. A microtask check reported mounted children as missing. A browser row asserting that the warning stays silent waits a short, bounded delay after the interaction. The `setTimeout` carries no comment. Code: `packages/plitejs/src/react/components/editable-rendered-element.tsx:88`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-05-02-plite-iframe-mounted-dom-nodes-need-path-metadata-fallback.md`.

- **Caption state reads the live node, not the element prop.** A focused empty caption once rendered blank with no placeholder because the shared `Caption` component read an element prop that stayed stale while Plite's DOM text flow owned typing, and its focus hook passed a facade `Range` without `kind` to `SelectionApi.isText`, which accepts only `kind: 'text'` and so always failed. The component now derives emptiness from `editor.read.nodes.get(path)` through `useEditorSelector`. Code: `apps/www/src/registry/components/editor/caption.tsx:68-74`, `packages/plitejs/src/interfaces/selection.ts:188-201`. Source: `docs/research/raw/2026-09-22-media-caption-focused-empty-proof.md:1-8`.

- **Server-rendered demo values must not generate ids or timestamps.** In March 2026 the homepage playground hydrated with a mismatch on `data-table-cell-id`: the node-id plugin filled missing ids with random `nanoid()` values during editor setup, some example values held `createdAt: Date.now()` at module scope, and server and client each built their own copy of the content. Element ids no longer reach the DOM (`packages/platejs/src/react/components/plate-nodes.spec.tsx:46` asserts no `data-block-id`), and the comment demo values use fixed ISO timestamps (`apps/www/src/registry/blocks/editor-ai/components/editor/rich-text-editor-value.ts:2416`). But `ElementIdPlugin` still generates `nanoid()` ids by default (`packages/platejs/src/lib/plugins/element-id/ElementIdPlugin.ts:55`), the `normalizeStaticValue` helper the fix added no longer exists, and `apps/www/src/registry/examples/values/date-value.tsx:8` still computes `today` with `new Date()` at module scope. Keep module-scoped demo values deterministic, and when a hydration diff names an attribute backed by node data, inspect how the value was generated before changing React rendering. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-03-28-static-demo-values-need-deterministic-ids-and-timestamps-for-hydration.md`.

- **React 19 cleanup removes compatibility code, not selection timing.** The April 2026 cleanup of Plite's React layer replaced `forwardRef` wrappers and `ref as any` with React 19 ref props, and one-shot constructor `useMemo` calls with lazy `useState`. It kept two patterns that look dated and still carry behavior: layout effects that write the DOM selection before paint, and the benchmark-backed `React.memo` on descendant content. Both are still there: the repair engine exports a pending model selection from a layout effect (`packages/plitejs/src/react/editable/runtime-repair-engine.ts:86`), and `EditableDescendantContent` is `React.memo(EditableDescendantNodeInner)` (`packages/plitejs/src/react/components/editable-text-blocks.tsx:1176`). `docs/vision/plate.md:1074-1076` bans `forwardRef` and React 18 compatibility code, but no rule says what to keep, so move a selection write out of a layout effect only with browser selection proof, and drop that memo only with a rerender benchmark. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-04-07-plite-react-19-2-cleanup-should-remove-forwardref-not-selection-layout-effects.md`.

- **React code reads live core state through three facades.** Plite's React layer reads live nodes, texts and selection, and writes marks, selection and target runtimes, through `packages/plitejs/src/react/editable/runtime-live-state.ts`, `runtime-selection-state.ts` and `runtime-mutation-state.ts`; inside `packages/plitejs/src/react` only `runtime-live-state.ts` and `runtime-editor-api.ts` name the core `getEditorLive*` readers. The April 2026 cut moved those reads out of hooks, components, browser handles, selection reconciliation, DOM repair, Android input and clipboard code, so fallback order, runtime-id lookup and selection read policy have one owner. No test pins the boundary (inferred from a search of `packages/plitejs/test`), so a new direct import passes every check. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-04-27-plite-react-public-selectors-must-stay-model-truth.md`.

- **Meet the React hook rules with lazy state and selector factories, not refs.** Oxlint runs `react/refs`, `react/use-memo`, `react/preserve-manual-memoization`, `react/set-state-in-effect` and `react/immutability` as errors (`oxlint.config.ts:749-759`); they enforce React's ref and memoization semantics, not only React Compiler eligibility. A mutable cache that same-render reads need lives in a stable cell from a lazy `useState(() => ...)`, not in `ref.current`. A one-shot constructor is a lazy `useState`, not `useMemo(fn, [])`. Selector-local memory, such as the last active history root, lives in a selector factory created once (`createHistoryRootSelector`, `packages/plitejs/src/react/hooks/use-plite-history.ts:81-91`), because mirroring it into state from an effect fails `set-state-in-effect` and costs a cascading render. In May 2026 passing `attributes.ref` through Plite render props was the one ref pass-through that needed a call-site exemption; no `react/refs` suppression remains in `packages/plitejs/src`, and the only one in the packages is a block disable around `useDeepCompareMemo` (`packages/platejs/src/react/internal/useDeepCompareMemo.ts:4-17`). Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-11-plite-react-hooks-refs-lint-needs-real-render-fixes.md`.

- **Every element fast path keeps injected props.** An April 2026 render cut computed `inject.nodeProps` attributes on the plain fast path but passed raw attributes to the wrapped path, so indent, text-align and list-item props vanished whenever a `belowNodes` wrapper (now `wrapNodeChildren`) or directional affinity was active, while the benchmark stayed fast. Today `pipeRenderElement`'s fast branches render through `FastIntrinsicElement` or `FastElementWithPath`, both of which compute injected attributes through `getFastInjectedAttributes` (`packages/platejs/src/react/utils/pipeRenderElement.internal.tsx:101-130`, `:152`, `:255`), and a directional element under active `wrapNodeChildren` slots takes the full `PluginElementWithPath` path (`:420-492`), pinned by `pipeRenderElement.spec.tsx:552` (directional path) and `:599` (active `wrapNodeChildren` slots). The same cut narrowed bulleted list-item injection to paragraphs, and heading list items lost their markers; the registry `ListKit` now targets heading, paragraph, blockquote, code block, details and image (`apps/www/src/registry/components/editor/list.tsx:51-58`), and `list.spec.tsx:99` tests the query and transform but renders no non-paragraph list item. A fast path that skips the generic node-props pipeline must prove every surviving branch, and a list optimization must be checked on a non-paragraph item. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/performance-issues/2026-04-07-fast-element-paths-must-preserve-injected-props-and-non-paragraph-list-semantics.md`.

- **A Plate surface renders `EditorContent`, never Plite's raw `Editable`.** Plate's `EditorContent` renders `EditorContentView`, which wraps Plite's `Editable` with Plate's handler and render pipes (`pipeHandler`, `pipeRenderElement`, `pipeRenderLeaf`, `pipeRenderText`), and `platejs/react` exports no raw `Editable` component. In April 2026 a docs example that rendered raw `Editable` inside Plate's provider, to mirror its Plite pane, threw a Plite-context hook error while the Plite pane rendered, so the crash was first read as a render-prop or data bug. Use raw `Editable` only in pure Plite examples, and when a Plate example misbehaves, check the editable wrapper before render props or node types. Limit: Plate's `EditorRoot` now wraps Plite's `EditorRoot`, so a raw `plitejs/react` `Editable` under it would likely get its context and silently skip the Plate pipes instead of throwing; that is inferred from the code, not run. Code: `packages/platejs/src/react/components/PlateContent.tsx:23-29`, `packages/platejs/src/react/components/EditorContentView.internal.tsx:162-192`, `packages/platejs/src/react/internal/plite-components.ts:11`, `packages/platejs/src/react/components/Plate.tsx:233`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/runtime-errors/2026-04-01-plate-docs-examples-should-use-platecontent-under-plate.md`.

- **Skip a React render only for text the DOM sync actually wrote.** Direct DOM text sync is a capability, not a render-skip rule for every text change: composition, custom leaf or text renderers, decorations and empty text decline it, and React must then render the change. In April 2026 a composing large-document edit left the DOM at `alpha` after the model inserted `alpha!`, because React treated every text operation as handled by the fast path while the sync had correctly declined. Today a node selector skips its update only when every changed text path under it reports `didSyncTextPathToDOM`. A composition fallback test asserts both that DOM sync did not run and that the visible DOM still updated, and composing selection repair checks `rangeCount` before `collapseToEnd()`, which throws on an empty selection. The same note found React event tests that rendered a bare core editor, which lacks the React DOM plugin's change bridge that `Editable` relies on, so they never updated; whether that applies to today's `createEditor` was not checked. Code: `packages/plitejs/src/react/hooks/use-node-selector.tsx:139-150`, `packages/plitejs/src/react/hooks/use-plite-node-ref.tsx:300`, `:467-484`, `:536`, `packages/plitejs/src/react/dom-text-sync.ts:90-119`, `packages/plitejs/src/react/editable/selection-reconciler.ts:1303-1312`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-04-23-plite-react-unsynced-dom-text-ops-must-force-react-fallback.md`.

- **The DOM bridge recovers mounted nodes from guarded path metadata.** Weak maps between DOM nodes and model nodes are the fast path, but an iframe, a custom renderer or a lifecycle gap can leave them behind DOM that is really mounted: in May 2026 clicking the first paragraph of `/examples/iframe` threw `Cannot resolve a Plite node from DOM node` because the iframe DOM carried node markers but no path, and this was not a coverage-boundary case, since nothing was hidden or virtualized. Plite element and text DOM now carries `data-editor-path` and `data-editor-node-key`, and `resolveMountedDOMPath` and `findMountedDOMNodeByPath` accept that metadata only inside this editor's root, for a path the live document still has, and with a matching node key. Point export needs the by-path fallback as well, because it can already know the model path while node maps are still catching up. Accepting arbitrary path attributes would hide real bugs and let foreign DOM into the bridge, so path-tagged DOM outside the editor keeps throwing; test both the recovery of a mounted in-editor node and the throw for a foreign one. Code: `packages/plitejs/src/dom/plugin/dom-node-path.ts:46-65`, `:67-105`, `packages/plitejs/src/dom/plugin/dom-editor.ts:1850`, `:2061-2067`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-05-02-plite-iframe-mounted-dom-nodes-need-path-metadata-fallback.md`.

- **Block annotation UI reads one editor-scope index instead of scanning per block.** Which top-level block owns each comment or suggestion thread is a document-wide question. In April 2026 the block discussion wrappers repaired a mutable `uniquePathMap` during render and rescanned the whole document once per suggestion id, so one render's cost grew with document size times annotation count; the fix derived ownership in one pass per editor version. The current registry `discussion.tsx` builds one store in its discussion controller (`apps/www/src/registry/components/editor/discussion.tsx:450`) that groups comments and authored changes by block `NodeKey`, republishes when threads, authored changes or ownership-moving commits change, and notifies only blocks whose snapshot changed (`:148-262`, `:519-553`). Do not write ownership maps during render. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/performance-issues/2026-04-05-block-discussion-should-build-a-shared-annotation-index-once-per-editor-version.md:23-98`.

- **A DOM-derived update must not assume the whole tree is mounted.** In April 2026 the first Plite large-document shell proof stopped rendering text for far top-level blocks, but `EditableBlocks` rebuilt document text by walking the mounted text-node elements in snapshot order, so typing in one live block would have run out of mounted text nodes and written `''` into every far block. The fix copied unmounted blocks from the committed snapshot and consumed DOM text only for mounted top-level ids. Shells are gone, but `VirtualizedEditable` and virtualized `PagedEditable` still omit DOM on request, so every DOM-to-model path under them needs the same audit, and a partial-mount typing proof checks the committed document, not only timing. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-04-11-shell-only-large-document-islands-must-preserve-far-subtrees-during-dom-reconciliation.md:25-95`.

- **Read `getVirtualItems()` during render; never memoize it on the virtualizer.** The TanStack virtualizer object stays stable while its range changes, so in May 2026 a `useMemo(() => virtualizer.getVirtualItems(), [virtualizer])` froze the window at blocks 1-16: scroll events reached TanStack, but block 1,000 never mounted and the measured-count metric kept its first value. `useVirtualizedRootPlan` reads the items on every render and memoizes only stable inputs such as `rangeExtractor` (`packages/plitejs/src/react/virtualized/use-virtualized-root-plan.ts:174`, `:196-201`), and a `react/incompatible-library` lint exception keeps React Compiler from memoizing the `useVirtualizer` call (`:182`). Derive coverage boundaries from the current mounted range, and prove virtualization by scrolling to a far block and asserting it mounts. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-05-03-plite-tanstack-virtual-items-must-not-be-memoized.md:18-90`.

- **Hard-affinity spacers render only at the caret's boundary, on the simple leaf path.** A mark with `rules.selection.affinity: 'hard'`, such as inline code or kbd (`packages/platejs/src/features/basic-nodes/lib/BaseMarkPlugins.ts:195`, `:257`), whose plugin renders a string tag or no component gets its two `contentEditable={false}` no-break-space spacers only when `isActiveHardAffinityBoundary` finds a collapsed selection at offset 0 or at the end of that leaf, and otherwise renders as its bare tag (`packages/platejs/src/react/utils/pipeRenderLeaf.internal.tsx:24-56`, `:235-263`; the same check in `packages/platejs/src/react/utils/pluginRenderLeaf.internal.tsx:111-139`). A plugin component that renders `EditorLeaf` still gets both spacers on every leaf, because `EditorLeaf` defaults `inset` to the plugin's hard affinity (`packages/platejs/src/react/components/plate-nodes.tsx:350-362`); the registry `CodeLeaf` is one (`apps/www/src/registry/components/editor/code.tsx:10-20`), so the registry code mark keeps the always-on spacer DOM (read from code on 2026-10-08, not run). Before the April 2026 redesign every hard-affinity leaf paid that DOM, though the behavior matters only where the caret sits. The redesign kept affinity semantics in the editor engine, left the plugin config unchanged, and moved the 5,000-block code census on `/dev/editor-perf` from 386.96 ms to 248.19 ms, the direct code plugin leaf lane from 334.55 ms to 264.41 ms and the full code leaf and text pipe from 392.68 ms to 295.71 ms (Plate on legacy Slate, 2026-04-03; raw JSON was in ignored `.tmp/`). The plan named mouse boundary placement and IME caret quirks as its risks. Sources: `c70bacbd4a:docs/performance/2026-04-03-affinity-redesign-plan.md:1-38`, `c70bacbd4a:docs/performance/editor-performance-master-plan.md:67-71`. Limit: the numbers predate the Plite engine; rerun before citing one.

- **Simple marks render as their tag inside the leaf pipe.** `pipeRenderLeaf` sorts each leaf plugin once: a plugin with a string or no leaf component, no render attributes, and no affinity or `hard` affinity becomes a simple entry wrapped directly in its tag with class `editor-<name>`, as long as no plugin injects text node props; every other plugin goes through `pluginRenderLeaf` (`packages/platejs/src/react/utils/pipeRenderLeaf.internal.tsx:101-155`, `:221-274`). In April 2026 routing simple marks directly, instead of back through `pluginRenderLeaf`, moved the standalone lab's 10,000-block marks-basic mount from about 1,387 ms to 1,310 ms and bold-basic from about 673 ms to 597 ms. Added rows for code, subscript and superscript then showed that no single mark explained the remaining gap to legacy Slate; the cost was aggregate composition across many marked leaves. Source: `c70bacbd4a:docs/performance/2026-04-04-standalone-benchmark-gap-analysis.md:335-395`. Limit: noisy local-preview runs in a lab that no longer exists.

- **A leaf or text with no plugin work renders a bare span.** When no leaf plugin, leaf-attribute mark or text inject prop is registered, `pipeRenderLeaf` returns the caller's `renderLeaf` unchanged or a plain `<span {...attributes}>` marked capable of DOM text sync and retained text flow (`packages/platejs/src/react/utils/pipeRenderLeaf.internal.tsx:170-189`). When leaf plugins exist but no text inject prop, `renderLeaf` prop or leaf-attribute mark does, the outer wrapper around the mark tags is a plain `<span>` instead of `getRenderNodeProps` plus `EditorLeaf` (`:191-192`, `:300-314`). In April 2026 these zero-work paths moved the 5,000-block leaf and text pipe lane from 357.46 ms to 298.81 ms and then to 248.76 ms, onto a probe that passed plain span renderers through the same pipes (250.64 ms), which showed the default wrapper cost was gone. Source: `c70bacbd4a:docs/performance/plate-vs-plite-benchmarks.md:619-757`, `:1430-1462`. Limit: Plate on legacy Slate.

- **When the model and the shared document are right but the DOM text is stale, inspect selector fan-out before collaboration encoding.** In May 2026 a public `tx.nodes.split({ at })` from a demo button left the DOM showing `alphabeta / abeta` while the model and Yjs held `alph / abeta`; keyboard Enter rendered correctly because it also moved the selection, and a fan-out shortcut that skipped runtime listeners for top-level structural changes without a selection change skipped the left text. Structural edits that rewrite text, split and merge, are text-render invalidation sources, and public commands called from custom controls need their own browser row. Source: `c70bacbd4a:docs/transplant/slate-v2/archive/docs/solutions/ui-bugs/slate-react-structural-text-dom-sync-2026-05-28.md:21-44`, `:73-89`. Limit: the June fix's commit fields and fan-out flag have no counterpart in today's `packages/plitejs/src` (no `shouldSkipRuntimeFanout`, `git grep` 2026-10-08), so the lesson, not the mechanism, carries over.

- **Renderer return types include the children fallback.** The July static renderer specs needed casts because their owners' return types excluded valid children and wrapper results. Repair the renderer signature instead of casting the test. Source: `docs/plans/2026-07-03-plate-next-static-renderer-spec-any-cleanup.md:69-71`. Current `packages/platejs/src/static/pluginRenderLeafStatic.internal.tsx:20-22` and `pluginRenderTextStatic.internal.tsx:22` declare `React.ReactNode | undefined`, and both renderers return `children` when the plugin does not match (`pluginRenderLeafStatic.internal.tsx:59`, `pluginRenderTextStatic.internal.tsx:55`). Limit: this checks the fallback contract only; the same renderers still pass their props to `getRenderNodeStaticProps` with `as any` (`pluginRenderLeafStatic.internal.tsx:46`, `pluginRenderTextStatic.internal.tsx:42`), read 2026-10-08.

- **An enrichment helper types its caller's props as an input generic.** The static utility cleanup found that `getRenderNodeStaticProps` adds editor and plugin context to input props, but its old signature forced tests to cast those inputs. Give the helper an input generic and describe the enriched output. Source: `c70bacbd4a:docs/plans/2026-07-03-plate-next-static-utils-drift-review.md:296-297`. Current `packages/platejs/src/static/utils/getRenderNodeStaticProps.internal.ts:27-41` takes `TProps extends StaticNodePropsInput` and returns `TProps` intersected with attributes and context, and its spec calls it without casts (`getRenderNodeStaticProps.spec.ts:65`, `:93`). Limit: all six production callers in `packages/platejs/src/static` still pass their props `as any` (such as `pluginRenderLeafStatic.internal.tsx:46` and `pipeRenderElementStatic.internal.tsx:46`), so only the spec exercises the typed path, and the output keeps `RenderNodeProps<any>`; read 2026-10-08.

- **A component-props alias cannot do an adapter's job.** The July editable cleanup found a component-local `React.ComponentProps<typeof Editable>` alias and a cast hiding a Plate-to-Plite prop mismatch. The real adapter had to produce the props Plite expects, including a scroll callback closed over the Plate editor. Source: `docs/plans/2026-07-04-plate-next-editable-props-adapter-cleanup.md:321-322`, `:325-326`. That hook has been replaced, but `packages/platejs/src/react/components/EditorContentView.internal.tsx:174-182` still builds the typed `scrollSelectionIntoView` callback that calls the Plate handler with the Plate editor. Limit: the removed plain-range decoration adapter is history, not current advice.

- **Animation-frame ID zero is a pending frame.** July's Cursor hook used truthiness to test frame IDs, allowing duplicate scheduling and missing cancellation when requestAnimationFrame returned zero. Its regression covered coalescing and immediate cancellation (`docs/plans/2026-07-10-plate-next-csv-cursor-date-package-reviews.md:459-460,506`). Use an explicit absent sentinel and compare against that sentinel. Cursor is retired, but current node-selection scheduling follows this rule: `scheduleUpdate` checks `frame !== undefined`, and cleanup cancels any defined frame (`packages/platejs/src/react/components/NodeSelection.tsx:401-404,467-485`). The current lifecycle fixture allocates IDs above 100000, so it does not itself pin the zero-ID case (`NodeSelection.lifecycle.spec.tsx:60-66`).

- **Static prop composition preserves the plugin's class output.** The July Core review caught static rendering discarding the class returned by the plugin while React retained it (c70bacbd4a:docs/plans/2026-07-10-plate-next-uncommitted-core-files.md:535-536). Current static composition merges the plugin node class, plugin-provided attributes class and caller class before node-prop injection (`packages/platejs/src/static/utils/getRenderNodeStaticProps.internal.ts:52-80`). Its regression asserts plugin, caller and injected alignment classes together (`getRenderNodeStaticProps.spec.ts:84-87`). - **Why decorations are scoped per node.** Legacy `decorate` computed every decoration at the root and passed the flat list down, so every level reran `Range.intersection` against large sets; on mixed-depth trees such as long code blocks that intersection became the bottleneck and local redecoration was lost (Slate #4993). ## Pagination

- **Page chrome never wraps the editable.** `PagedEditable` renders each page surface as an absolutely placed sibling of one editor overlay that spans the page stack. `renderPage` gets sizing attributes (fixed `height`, `overflow: hidden`, `pointerEvents: 'none'`) and no document children, the overlay passes pointer events through, only its inner editor layer takes them, and the editable host sets `zIndex: 0` (`packages/plitejs/src/pagination/react.tsx:815-840`, `:1290-1361`; tests `packages/plitejs/test/pagination/react-fragments-contract.test.tsx:1115`, `apps/plite/tests/plite-browser/donor/examples/pagination.test.ts:131`). In May 2026 a page wrapper around the editable showed the text but took every real click, and a `zIndex` set in one example or a fixed height on the wrapper that held the editable only moved the failure. Prove any wrapper around `Editable` by clicking and typing through the real `[contenteditable="true"]` element, because visible text says nothing about hit testing. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-21-plite-layout-source-entry-and-paged-editable-dx.md`.

- **A paged layout binds to one root and to paths, not to element objects.** In May 2026 a layout API that accepted `root` still extracted and projected the primary root, which looked multi-root-ready and was not. Today the snapshot keeps its named root and every text range carries it (`packages/plitejs/test/pagination/page-layout-contract.test.ts:133`), the internal main-root spelling is rejected (`:159`), measurement and paint resolve inside one named-root view (`packages/plitejs/test/pagination/react-fragments-contract.test.tsx:1138`), and `PagedEditable` with `root` wraps itself in `EditorRoot` for that root (`packages/plitejs/src/pagination/react.tsx:1377-1399`). An API that accepts `root` needs tests that extraction, snapshots and projection all use it. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-21-plite-layout-source-entry-and-paged-editable-dx.md`.

- **Pretext measures editable text with `pre-wrap`.** CSS-normal whitespace trims trailing collapsible spaces from line ranges, so in May 2026, after spaces were typed at a paragraph end, the model held them while the projected line ended early and the spaces rendered outside the placed line. `createPretextPageLayoutEngine` defaults to `whiteSpace: 'pre-wrap'` and `wordBreak: 'normal'`, keeps both modes in its prepared-text cache key beside the text, font and letter spacing, and caches preparation in the engine closure, not in render (`packages/plitejs/src/pagination/index.ts:1369-1408`). - **Per-run iteration needs per-run geometry.** The May 2026 draft-Plite pagination bridge iterated text runs but gave every run the whole line rectangle, so marked leaves painted over one another. Supplying run-scoped rectangles fixed overlap; checking only that the paragraph stayed inside its page would have missed it. Current private projection converts each `run.rect` to canvas coordinates before creating its positioned slice (`packages/plitejs/src/pagination/react.tsx:701-737`). Source: `docs/plans/2026-05-21-plite-pagination-page-flow-fix.md:128-136`. The old public decoration helper is gone; retain the geometry lesson and an adjacent-run overlap oracle, not that API.
