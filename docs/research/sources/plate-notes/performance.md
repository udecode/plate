# Performance diagnosis

These lessons come from retired solution notes, Plite references and ledgers, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`. The numbers are historical; rerun the named target before citing one.

## Where the time goes

- **Native DOM text sync has opt-outs.** Typing updates a text node in place without a React render only when the text is non-empty, has no decoration, and any custom `renderLeaf` or `renderText` is marked with `setDOMTextSyncRendererCapability`. In Plate, an `EditorContent` `renderLeaf` prop, a mark plugin with leaf attributes or a mark that requires model text sync opts the text out; otherwise Plate's compiled leaf renderer marks itself capable. Decorated or custom-rendered leaves therefore pay a React render on every keystroke. Code: `packages/plitejs/src/react/dom-text-sync.ts:52`, `:90-118`, `packages/platejs/src/react/utils/pipeRenderLeaf.internal.tsx:176-188`, `packages/plitejs/test/react/dom-text-sync-contract.ts`. Sources: `plite/reference/public-docs/libraries/plite-react/editable.mdx`, `plite/reference/public-docs/walkthroughs/09-performance.mdx`.
- **Text and selection commits keep the snapshot index stable.** A commit with no structural classification, no element type change and no discarded NodeKey advances the index through `advancePathStableSnapshotIndex` instead of remapping it, which keeps typing cheap on large documents. Before this split, a 2,000-block text insert spent about 41 ms in snapshot build plus 13 ms in rollback cloning, of 59 ms, while React took under 1 ms. Never route a path-changing commit class into this branch. Code: `packages/plitejs/src/core/public-state.ts:507-529`, `packages/plitejs/src/core/snapshot-index.ts:1749`. Source: `solutions/performance-issues/2026-05-01-plite-text-snapshots-should-be-path-stable-for-large-document-typing.md`.
- **Core phase timings come from a global profiler hook.** Set `globalThis.__EDITOR_REACT_RENDER_PROFILER__ = { acceptsCoreDuration(id), record(event) }` to receive `core-time` events from `profileCoreDuration`, such as `transaction-commit-snapshot`, `snapshot-build-index` and `listener-snapshot`. This is how to split transaction cost from React cost, which `performance.mdx` asks for without saying how; the huge-document trace benchmarks use it. Code: `packages/plitejs/src/core/profiling.ts:3`, `benchmarks/slate-v2/donor/browser/react/huge-document-browser-trace.mjs`. Source: `solutions/performance-issues/2026-05-01-plite-text-snapshots-should-be-path-stable-for-large-document-typing.md`.
- **Large paste and cut cost write count and snapshot allocation, not parsing.** In May 2026 the old per-line split-and-insert path took about 3.5 s for 2,000 plaintext lines while split, encode and decode stayed cheap; one schema-fitted slice replacement brought 10,000 lines to about 35 ms. A 50,000-block two-node cut lowered to one change took about 10 ms warm (p50) and about 172 ms cold, the cold cost being snapshot allocation. When large clipboard work regresses, count canonical changes per gesture first, then measure cold snapshot cost apart from warm edits. Code: target `clipboard-large-payload` in `benchmarks/targets/slate-v2.json`. Sources: `plite/ledgers/fork-issue-dossier.md`, `plite/ledgers/issue-coverage-matrix.md`.
- **A first triage before a full profile.** Typing INP under about 100 ms feels responsive. When the editor is much faster in Firefox than in Chrome or Safari, DOM paint dominates; when it speeds up with custom corrections disabled, corrections dominate; otherwise React is the cost. `content-visibility: auto` on every element can cost more than it saves in Safari, where its overhead grows with node count. This is inherited Slate guidance with no Plite workload behind it, so treat it as a lead. Source: `plite/reference/public-docs/walkthroughs/09-performance.mdx`.

- **Compute a diagnostic's location only when a diagnostic needs it.** HTML decoding once computed a tree location for every decoded element with `Array.prototype.indexOf` over its parent's children, which is quadratic in sibling count: a 392 KB `parseSlice` took 4,174 ms and a 788 KB one 17,346 ms. Computing it lazily (`location ??= htmlTreeLocation(root, element)`) brought the 392 KB parse to 542 ms, and the source pass now rebuilds each child list once instead of calling `splice` or `unshift` per removal. Code: `packages/platejs/src/lib/plugins/html/HtmlPlugin.ts:1739`, `:1930`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/html-safety/REPORT.md:84-87`, `:149` (2026-09-29, happy-dom).

- **Do not ask a wide frozen array whether it is frozen on every update.** In JavaScriptCore, `Object.isFrozen` on a frozen 1,179-element array costs about 54 µs and re-freezing it about 76 µs (4 and 7 µs at 120 elements), and Plite's index and snapshot builders asked or re-froze on every update: 15% of end-of-document typing on a 50 KB document. Record arrays as frozen where they are built (`rememberFrozenArray`) and memoize deep-frozen subtrees, so applying a change walks only the nodes it created. The first freeze of each new top-level array, about 9% of that typing loop, is the width cost the plain frozen array model keeps. Code: `packages/plitejs/src/core/change/tokens.ts:174`, `:186`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/p1/REPORT.md:143-152`, `:215-226` (2026-09-29, `lanes/p1/freeze-cost.ts`).

## Benchmark validity

- **Check that the undo burst merged before reading an undo benchmark.** `shouldMergeText` merges contiguous inserts and contiguous deletes on the same target, and batch effects block merging. An unmerged burst makes the lane measure batch policy instead of replay. On 2026-04-11, undo and redo of 20 typed characters on a 5,000-block document took about 490 ms unmerged and about 20 ms merged. Code: `packages/plitejs/src/history/history-merge-policy.ts:303-360`. Source: `solutions/performance-issues/2026-04-11-plite-history-typing-bursts-need-legacy-style-merge-heuristics-before-anything-else.md`.
- **A comparison row needs a baseline that has the behavior.** Before keeping a row as benchmark debt, confirm the baseline implements the measured behavior in its model, not just that a UI control is missing. The legacy huge-document history row failed on a missing undo button, but that example was built with `withReact` only and never had history, so no harness patch could fix it. When the baseline is a different kind of feature, cut the row or record it as not applicable. Source: `solutions/workflow-issues/2026-04-15-benchmark-compare-rows-must-prove-the-legacy-surface-exists.md`.
- **A locality benchmark needs its broad-invalidation comparator.** An overlay, decoration or subscription-breadth benchmark supports a verdict only when it measures the current path, the candidate path and, when relevant, a worst-case broad-invalidation path; a lane that cannot tell them apart proves nothing. The benchmark rule does not name the comparator; the rule on recompute selectivity and subscriber fan-out in `.agents/rules/benchmark/references/performance-review.md:76` is where it would go. Source: `plite/decoration-roadmap.md`.
- **No lane varies the number of inline elements in one block.** The rerender-breadth lanes measure sibling leaves and nested blocks, and `huge-dense-inline-props` on `/dev/editor-perf` measures leaf properties, so a per-keystroke cost that grows with the inline count of one paragraph, the #3430 freeze, would pass every current lane. This is inferred from the target list. Code: `benchmarks/targets/slate-v2.json`, `apps/www/src/app/dev/editor-perf/workloads.ts:232`. Source: `plite/ledgers/fork-issue-dossier.md`.
- **The element-id lane times two paste shapes.** The `element-id-fragment` lane on `/dev/editor-perf` times `tx.fragment.replace` with a raw import (no ids) and a seeded duplicate paste (ids already in the document); `init-dissection` never runs paste-time id work, so init numbers cannot justify import or paste changes. At 5k blocks the old duplicate paste cost 20.06 ms against 5.87 ms for raw import, about 13.9 ms of it in 199 duplicate-id lookups. Element ids now drop on copy through property policy. Code: `apps/www/src/app/dev/editor-perf/workloads.ts:156`, `packages/platejs/src/lib/plugins/element-id/ElementIdPlugin.ts:65`. Source: `solutions/performance-issues/2026-04-03-nodeid-paste-import-needs-insertfragment-benchmark.md`.

- **A text-store win must include materializing the string.** In the 2026-09-09 research a piece-tree text store won on write-only edits, and the win reversed once each edit also materialized the full string, as an editor does to render and read. Removing unused virtualization key copies matched 1,000 boundary cases but stayed an unadopted microbenchmark, not scroll or paint proof. Measure the whole edit-read cycle before adopting a store change. Source: `docs/editor-audits/reports/editor-performance-research-iteration-2-2026-09-09.md:31-33`.

- **A vanished profiler bucket is not a win until the gesture gets faster.** In the June 2026 200k-block undo-delete work, caching the snapshot index by child-array identity removed `snapshot-build-index`, yet undo-delete regressed from 1,524.9 ms to about 1,750-1,769 ms because the cost moved into child replacement (about 722 ms) and DOM path sync (about 648 ms). A loop and path-append cleanup moved `snapshot-build-index` only from 727.3 ms to 721.5 ms while wall time rose from 1,478.1 ms to 1,507.7 ms, and a full-range `slice()` copy left its bucket at about 371 ms with noisy wall time. All three were reverted. Judge a hot-path change by end-to-end gesture time read beside its bucket breakdown, and do not retry shallow traversal cleanup without a microbenchmark that isolates the hot bucket. Source: `docs/plite/research/2026-06-12-huge-doc-architecture/README.md:459-483`, `:528-580`.

- **A post-delete typing burst measures event cadence, not first-key latency.** In the June 2026 200k-block trace, typing after select-all delete took about 2.2-2.7 s, of which keyboard dispatch and beforeinput or input cadence took about 2.1 s and core insert work 10-28 ms. A physical single key and a 17-character `insertText` control both landed near 145 ms, so the default metric was a 17-physical-key burst stress, not slow first-key typing. Two shortcuts that relaxed selection authority for speed were reverted: a same-burst `insertText` no-flush turned the post-delete text into `after 20 dlteeek0`, and releasing repair-induced input to the DOM failed repair contracts and corrupted the typed string. Do not relax native or model selection authority for a typing benchmark without fresh proof that the native and model carets agree and no text reorders. `PLITE_BROWSER_TRACE_AFTER_DELETE_INPUT_MODE=type|insertText` and `PLITE_BROWSER_TRACE_AFTER_DELETE_TEXT` keep the lanes apart (`benchmarks/slate-v2/donor/browser/react/huge-document-browser-trace.mjs:36-48`). Source: `docs/plite/research/2026-06-12-huge-doc-architecture/README.md:306-352`, `:771-900`.

- **Trace payloads stay compact at scale.** At 200k blocks, repair and keydown trace recording that serialized the full child-replacement payload cost about 195-220 ms each on one Delete. Recording operation counts and first and last metadata brought those buckets near zero, and Delete still took about 620-647 ms, which showed the diagnostics were only part of the cost. Keep traces and provider hooks from materializing change lists, and attribute a gesture with diagnostics off as well as on. Source: `docs/plite/research/2026-06-12-huge-doc-architecture/README.md:902-971` (June 2026, Chromium, staged and virtualized lanes).

- **A legacy Slate baseline needs its own performance settings.** Slate's performance guide treats root chunking and `content-visibility` as separate strategies, and the first registered full-DOM comparison omitted the root chunking a fair Slate run needs; the repaired nine-editor packet enables root chunk size 1,000 without `content-visibility`. Configure each comparator the way its own docs recommend before ranking it. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/virtualization.md:16`, `read-log.tsv:5`; the `create-segment-plan.ts` modes the same line cites no longer exist.

- **A browser long task with no Plite time stays unattributed until proven otherwise.** The Long Tasks API reports main-thread tasks over its threshold. Its `TaskAttributionTiming` entries give container-style context, not the function that ran (MDN `PerformanceLongTaskTiming`, W3C Long Tasks API). On 2026-06-12, after the selectionchange-timer fix, a fresh 200k-block trace showed `typeAfterDelete` at 139.8 ms with one 119 ms long task and no Plite profiler or timer duration. Repeat traces and the Playwright behavior proof stayed green. Report such a task as unattributed browser work, and check the profiler and timers before calling it a runtime regression. A single spike is a benchmark-attribution warning, not a reason to revert. Source: `docs/plite/research/2026-06-12-browser-longtask-selection-oracles/README.md:23-28`, `read-log.tsv:2-5`, `rejected-ledger.tsv:5`.

- **Separately timed stages are not a pipeline total.** In the 2026-09-28 streaming probe, fit (`schema.fitDocumentWithReport` plus `assertDocument`) and publication (`update({ history: 'skip' }).value.replace(...)`, which fits again) were timed apart, so their sum double-counts fitting and matches neither AI preview (slice parse, then publication) nor the static demo (document parse with fitting, then publication). Profiler `core-time` events nest the same way, so their inclusive durations must not be summed either. Time the complete operation the consumer runs. Sources: `docs/research/probes/2026-09-28-conversion-boundary/streaming/REPORT.md:57-67`, `BROWSER-REPORT.md:41-46`.

- **A missing observation is inconclusive, never a pass.** On 2026-09-30 synthetic receipts run through the real S5 evaluator passed with differing candidate text (equality was reported but not gated), with every final-text hash absent (equal nulls counted as a match), and with no candidate final clock (filtering left an empty set and `Math.max` returned `-Infinity`); the threshold collector trusted a cached `passed` over a 100 ms reading against a 1 ms limit; coverage declarations counted as measured coverage; and the `core-node-transforms` and `collab-readiness` artifacts emitted all-`ok` rows while 6 of 7 and 7 of 7 recorded inputs no longer matched. The execution replaced these with one evaluator where missing data is inconclusive and contradicting data fails, no fallback clock, a threshold collector that recomputes the verdict and marks a contradicting cached `passed` as `integrity-error`, and per-input receipt admission. Code: `benchmarks/editor/benchmarks/markdown-streaming-measurement.mjs`, `benchmarks/editor/src/index.mjs:820-837`, `benchmarks/targets/README.md` (Run receipts). Sources: `docs/research/probes/2026-09-30-performance-review/REPORT.md:66-104`, `docs/plans/2026-09-30-performance-evidence-execution.md:100`.

- **Count decoration source reads, not only renders.** An overlay change can stay local in React while each decoration source still rereads every entry, so a locality claim needs separate counts of components rerendered, sources rerun and entries reread; React subscriptions alone hide recompute cost. The April 2026 decoration roadmap kept source-scoped and entry-scoped recompute as its last open waves for this reason, with the rule that a source whose dirtiness is unknown refreshes whole instead of painting stale ranges. The `react-rerender-breadth` and `react-huge-document-overlays` targets now report `decorationReadCount` from a probe source that counts its own `read` calls beside the render counts (`benchmarks/slate-v2/donor/browser/react/rerender-breadth.tsx:173-223`, `:993-1011`; `benchmarks/slate-v2/donor/browser/react/huge-document-overlays.tsx:91-143`, `:421-461`), and a refresh names `'all'` or explicit node keys (`DecorationRefresh`, `packages/plitejs/src/interfaces/decoration.ts:25-27`). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/decoration-roadmap.md:1434-1508`, `:231-234`.

- **A performance report becomes a workload lane, not a red test.** The 2026 triage of the 682 open Slate issues first wrote each valid issue as a red-test seed, and performance reports lost their workload in that shape, so from its fifth batch each performance issue got a benchmark seed instead: the smallest workload, the primary metric that should move, a secondary metric, and the missing workload detail when it was not ready. Only 15 issues reached the benchmark map, and most batches added none, which the triage read as the expected result: correctness bugs stay tests. Code: the `issuePressure` maps in `benchmarks/slate-v2/donor/core/current/clipboard-large-payload.mjs:1750-1754` and `benchmarks/slate-v2/donor/core/current/history-retained-memory.mjs:330-332`. Sources: `docs/plite-issues/issue-intelligence-master-plan.md:192-205`, `docs/plite-issues/benchmark-candidate-map.md:236-260`.

- **A timed-out `page.evaluate` keeps running.** `Promise.race` against a timer rejects the wait but does not stop the evaluation inside the page, so the next lane on that page measures beside the old one; in April 2026 one timed-out lane poisoned the rest of its target run. `apps/www/scripts/run-editor-perf.mts` reloads the harness page after a timeout before it retries the job (`recoverHarnessPage`, `:285-294`, retry loop `:405-441`), and `apps/www/scripts/run-table-perf.mts:185` races without a reload and fails the run on the timeout. Register a render waiter before firing the state change it waits for, or a fast render beats the registration and the lane hangs. Two result sources whose row ids differ, such as the old snapshot's `mixed-core-mount` and the live `10_type-middle`, are different benchmark registries: show them as separate rows or normalize them explicitly, never map one onto the other by id. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/logic-errors/2026-04-04-editor-benchmark-viewers-must-keep-live-and-snapshot-rows-separate.md`; the standalone viewer it fixed no longer exists.

- **Which source wakes a store is a third invalidation claim.** The benchmark rule separates recompute selectivity from subscriber fan-out (`.agents/rules/benchmark/references/performance-review.md:76`); the upstream wakeup is a third claim, and a green test of one leaves the other two unproven. In April 2026 projection and annotation stores recomputed selectively yet still woke on every editor commit through broad `editor.subscribe`. The internal source bus derives `commit`, `selection`, `text`, `node`, `decoration`, `root` and `state` from commit metadata (`getSourcesForChange`, `packages/plitejs/src/core/listener-state.ts:60-96`), and `packages/plitejs/test/snapshot-contract.ts:2435` pins that a selection-only commit wakes only `commit` and `selection`. Today the decoration store subscribes to `commit` and returns early when no document changed (`packages/plitejs/src/react/decoration-source.ts:1703-1714`), while inactive selection subscribes to `selection` (`packages/plitejs/src/react/inactive-selection.ts:272`). Prove narrow fan-in by making the broad subscription throw, and prove per-bucket delivery with a structural move that keeps the runtime id. Keep the source API internal until a real need fails without it, and keep a custom string escape hatch in typed tag unions, as `EditorUpdateTag` does (`packages/plitejs/src/interfaces/editor.ts:877`). Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/performance-issues/2026-04-30-plite-source-bus-routing-must-prove-upstream-fan-in-and-runtime-bucket-locality-separately.md`.

- **A field dashboard localizes a regression only with the lab's memory and DOM tags.** The retired production-RUM method asked each field sample to carry, beyond the interaction, cohort, document size, mode, browser, mobile, IME and release that the benchmark rule still asks for (`.agents/rules/benchmark/references/performance-review.md:109`), the visible DOM count, hidden boundary count, decoration, comment and annotation count and custom renderer flags, and to record p50 to p99 interaction latency beside JS heap, DOM node count, mounted group count, listener count, cached index sizes, React scheduler priority and component render or mount counts. Tagged that way, a dashboard answers which cohort, interaction, mode, memory bucket and release regressed. The rule asks the field for only a heap and DOM sample (`.agents/rules/benchmark/references/performance-review.md:193`); the other tags are its lab memory and DOM tags (`:159-171`). The mode values the method listed (off, auto, DOM-present, shell, staged) are retired: DOM omission is an explicit mounted-view choice of the virtualized or paged component (`docs/vision/plite.md:732-735`, `:749`), so the mode tag names the rendering component. Source: `52625e85025313eebd4eeb9be2254249ded58676:.agents/rules/benchmark/references/performance/production-rum-dashboard.md:10-42`. Limit: a dashboard design, not a measured lane; a claim without field data states the gap as lab-only (`.agents/rules/benchmark/references/performance-review.md:109`).

## Tools

- **`perf:editor` presets beyond the public one.** `pnpm --filter www perf:editor --preset <name> --out <raw> --summary-out <summary>` writes the raw JSON and a compact summary in one pass against a running `/dev/editor-perf`. The presets are `layer-0`, `layer-0-smoke`, `layer-1-core-plugins`, `layer-1-core-plugins-smoke`, `layer-3-core-stress` and `public-slate-vs-plate`; only the public one has a package script, and `performance.mdx` documents only `perf:editor:public`. Code: `apps/www/scripts/run-editor-perf.mts:22-28`. Source: `solutions/performance-issues/2026-04-01-layer0-runner-should-write-summary-json-in-the-same-pass.md`.
- **The huge-document demo and the perf page parse their knobs separately.** Both share `createHugeDocumentValue`, the huge-mixed-block workload and an "Open in benchmark mode" link built from the `blocks`, `chunking`, `chunk_size` and `content_visibility` query keys, but each keeps its own `parseNumber` and `parseBoolean`. Change a knob in both parsers, or the manual scenario and the measured one drift apart. Code: `apps/www/src/registry/examples/huge-document-demo.tsx:261`, `apps/www/src/app/dev/editor-perf/page.tsx:131`. Source: `solutions/performance-issues/2026-04-01-huge-document-demo-and-benchmark-should-share-a-query-param-config-contract.md`.

- **A benchmark process loads one copy of each package and records its knobs.** In May 2026 the Plite legacy-compare runners broke three ways: importing source React hit JSX-runtime errors; importing built React beside source core split module-level registries, because Bun resolves a built workspace package's bare imports to workspace source; and runners kept calling hard-cut APIs such as `withReact` and `editor.insertText` from template strings that no typecheck reads. The core compare runners still embed their benchmark as a template string that imports `plitejs` or `slate` by package name inside each repository (`benchmarks/slate-v2/donor/core/compare/huge-document.mjs:31-38`), so a public API cut needs a grep of benchmark template strings. Before mixing source and `dist`, check with `import.meta.resolve` which copy each import loads; record each mode knob, such as the virtualization setting, in the artifact rather than only in the command; and read a benchmark's threshold fields, because exit code 0 shows only that it ran. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/performance-issues/2026-05-01-plite-legacy-compare-benchmark-must-align-bun-workspace-source-and-built-react-surfaces.md`.

## React Compiler

- **Resource lifetimes belong to their owner, not to memoization.** AI sessions are editor-owned with view registration and explicit disposal, Excalidraw subscriptions belong to the mounted drawing API, and code-drawing rendering has cancellation guards plus an Export consumer even while the preview is hidden. Whether React Compiler happens to reuse an object proves none of these lifetimes. Create or attach external resources at their lifecycle boundary, read immutable values during render, and remove a `useMemo` only when correctness survives recomputation; a stable instance needs an explicit owner such as the editor, view or session, not a new global cache. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/react-compiler.md:56-60`.

- **Compiler proof has five separate lanes.** Source eligibility (functions, diagnostics, explicit exclusions, source hashes); emitted package behavior (the real `tsdown` output and an equal-feature external consumer, since a consuming app cannot repair a package compiled before publication); copied-source behavior (a real registry consumer with its own compiler configuration); runtime behavior (off and on controls for mount, structural edits, inline selectors, teardown, strict and concurrent rendering and native selection); and performance (complete-operation distributions, retained heap, render and subscription counts). A generated runtime import proves none of them, and package proof does not prove copied TSX. As of September 2026 only part of the runtime lane and eight performance rows were measured. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/react-compiler.md:62-70`.
