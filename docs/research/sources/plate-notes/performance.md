# Performance diagnosis

These lessons come from retired solution notes, Plite references and ledgers, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`. The numbers are historical; rerun the named target before citing one.

## Where the time goes

- **Native DOM text sync has opt-outs.** Typing updates a text node in place without a React render only when the text is non-empty, has no decoration, and any custom `renderLeaf` or `renderText` is marked with `setDOMTextSyncRendererCapability`. In Plate, an `EditorContent` `renderLeaf` prop, a mark plugin with leaf attributes or a mark that requires model text sync opts the text out; otherwise Plate's compiled leaf renderer marks itself capable. Decorated or custom-rendered leaves therefore pay a React render on every keystroke. Code: `packages/plitejs/src/react/dom-text-sync.ts:52`, `:90-118`, `packages/platejs/src/react/utils/pipeRenderLeaf.internal.tsx:176-188`, `packages/plitejs/test/react/dom-text-sync-contract.ts`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/libraries/plite-react/editable.mdx`, `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/walkthroughs/09-performance.mdx`.
- **Text and selection commits keep the snapshot index stable.** A commit with no structural classification, no element type change and no discarded NodeKey advances the index through `advancePathStableSnapshotIndex` instead of remapping it, which keeps typing cheap on large documents. Before this split, a 2,000-block text insert spent about 41 ms in snapshot build plus 13 ms in rollback cloning, of 59 ms, while React took under 1 ms. Never route a path-changing commit class into this branch. Code: `packages/plitejs/src/core/public-state.ts:507-529`, `packages/plitejs/src/core/snapshot-index.ts:1749`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-05-01-plite-text-snapshots-should-be-path-stable-for-large-document-typing.md`.
- **Core phase timings come from a global profiler hook.** Set `globalThis.__EDITOR_REACT_RENDER_PROFILER__ = { acceptsCoreDuration(id), record(event) }` to receive `core-time` events from `profileCoreDuration`, such as `transaction-commit-snapshot`, `snapshot-build-index` and `listener-snapshot`. This is how to split transaction cost from React cost, which `performance.mdx` asks for without saying how; the huge-document trace benchmarks use it. Code: `packages/plitejs/src/core/profiling.ts:3`, `benchmarks/slate-v2/donor/browser/react/huge-document-browser-trace.mjs`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-05-01-plite-text-snapshots-should-be-path-stable-for-large-document-typing.md`.
- **Large paste and cut cost write count and snapshot allocation, not parsing.** In May 2026 the old per-line split-and-insert path took about 3.5 s for 2,000 plaintext lines while split, encode and decode stayed cheap; one schema-fitted slice replacement brought 10,000 lines to about 35 ms. A 50,000-block two-node cut lowered to one change took about 10 ms warm (p50) and about 172 ms cold, the cold cost being snapshot allocation. When large clipboard work regresses, count canonical changes per gesture first, then measure cold snapshot cost apart from warm edits. Code: target `clipboard-large-payload` in `benchmarks/targets/slate-v2.json`. Sources: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/ledgers/fork-issue-dossier.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/ledgers/issue-coverage-matrix.md`.
- **A first triage before a full profile.** Typing INP under about 100 ms feels responsive. When the editor is much faster in Firefox than in Chrome or Safari, DOM paint dominates; when it speeds up with custom corrections disabled, corrections dominate; otherwise React is the cost. `content-visibility: auto` on every element can cost more than it saves in Safari, where its overhead grows with node count. This is inherited Slate guidance with no Plite workload behind it, so treat it as a lead. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/walkthroughs/09-performance.mdx`.

- **Compute a diagnostic's location only when a diagnostic needs it.** HTML decoding once computed a tree location for every decoded element with `Array.prototype.indexOf` over its parent's children, which is quadratic in sibling count: a 392 KB `parseSlice` took 4,174 ms and a 788 KB one 17,346 ms. Computing it lazily (`location ??= htmlTreeLocation(root, element)`) brought the 392 KB parse to 542 ms, and the source pass now rebuilds each child list once instead of calling `splice` or `unshift` per removal. Code: `packages/platejs/src/lib/plugins/html/HtmlPlugin.ts:1739`, `:1930`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/html-safety/REPORT.md:84-87`, `:149` (2026-09-29, happy-dom).

- **Do not ask a wide frozen array whether it is frozen on every update.** In JavaScriptCore, `Object.isFrozen` on a frozen 1,179-element array costs about 54 µs and re-freezing it about 76 µs (4 and 7 µs at 120 elements), and Plite's index and snapshot builders asked or re-froze on every update: 15% of end-of-document typing on a 50 KB document. Record arrays as frozen where they are built (`rememberFrozenArray`) and memoize deep-frozen subtrees, so applying a change walks only the nodes it created. The first freeze of each new top-level array, about 9% of that typing loop, is the width cost the plain frozen array model keeps. Code: `packages/plitejs/src/core/change/tokens.ts:174`, `:186`. Source: `docs/research/probes/2026-09-28-conversion-boundary/lanes/p1/REPORT.md:143-152`, `:215-226` (2026-09-29, `lanes/p1/freeze-cost.ts`).

- **A commit listener's arity decides whether the listener snapshot is built.** `notifyListeners` builds the listener snapshot for plugin commit listeners only when one declares two parameters (`listener.length >= 2`), so a wrapper that forwards `(commit, snapshot)` to every handler makes each commit pay for snapshot materialization even when the handler reads only `commit`. When the May 2026 rename moved positional `commitListeners` to an object-context callback, the fix kept the internal wrapper at one parameter and exposed `snapshot` as a cached lazy getter; today's `on.commit` wrapper still takes one parameter and passes `getEditorCommitSnapshot(commit, root)`, which returns the commit's own snapshot or, for a non-main root, builds one whose `index` is a lazy getter. When turning a positional listener API into an object context, check whether the old arity carried lazy work, keep expensive context fields behind getters, and test both the metadata-only and the snapshot-reading handler. Code: `packages/plitejs/src/core/public-state.ts:8722-8745`, `packages/plitejs/src/core/plugin.ts:1425-1437`, `packages/plitejs/src/core/commit.ts:143`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-05-18-plite-extension-oncommit-should-keep-snapshot-lazy.md`.

- **Check staging and validation code for quadratic copies before blaming the main work.** In the March 2026 Plite batch engine, staging appended each operation with `[...ops, op]`, and a same-parent insert check cloned the staged list and rescanned it on every insert, so validation cost grew with the square of the batch. Pushing into the private array and storing the staged parent path cut a 5,000-insert batch on an empty document from 394.97 ms to 13.22 ms and a 5,000-prepend batch from 380.33 ms to 5.5 ms, while the per-operation replay control stayed near 2.5 s. Private bookkeeping may mutate in place; only published nodes and snapshots must stay immutable. That engine is gone, so the numbers are historical. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-03-31-plite-applybatch-should-own-the-exact-path-set-node-fast-path.md:84-106`, `:301-329`, `:799`, `:809`.

- **A render that depends on a node's path rerenders whenever a block is inserted before it.** A path is a query against the current tree, and a leading insert shifts every later block. In April 2026 each rendered descendant subscribed to its path and was not memoized, so the top-level prepend of a 200-line paste rerendered every unchanged block: the engine's `insertFragment` took about 1.5 ms while the browser paste lane sat in the mid-70 ms range, and memoizing descendants with path subscription made opt-in brought the frozen huge-document paste lane to a 34.92 ms mean against 48.13 ms for legacy Slate. In May 2026 Plite dropped eager `path` and `index` from element render props for the same reason: fresh eager paths force a rerender of every shifted sibling, and skipped rerenders leave event handlers with stale paths. Today `RenderElementProps` has no `path` or `index` (`packages/plitejs/src/react/components/editable-text-blocks.tsx:583-603`); its `data-editor-path` attribute is DOM metadata that the runtime updates in place after a shift, `EditableDescendantNode` is memoized (`:1319`), and contract tests pin that a leading insert updates shifted DOM paths without rerendering stable custom elements (`packages/plitejs/test/react/provider-hooks-contract.tsx:1903`, `:2011`). `useElementPath()` is the opt-in subscription, and event handlers resolve the path at event time (`content/docs/api/react-hooks.mdx:319-323`). When a paste or insert looks slow in the browser, time the engine call alone before changing core semantics, then look for path-only or structure-only rerenders. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-04-06-plite-huge-document-paste-should-not-rerender-unchanged-descendants.md:26-115`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-05-12-plite-render-props-should-not-carry-moving-paths.md:18-106`.

- **When the engine lane is cheap and the browser lane is slow, count selector subscriptions before redesigning the view.** In April 2026 core-only huge-document typing had dropped to near noise while 5,000-block browser typing took about 71 ms against about 18 ms for legacy Slate chunking. The cost was React fan-out per commit: each text leaf subscribed separately for text, marks and runtime id, each descendant separately for node data, child ids and path, a child resubscribed for text its parent had already resolved, and hot selectors joined and split runtime-id strings. Collapsing each node to one bound selector read, passing resolved text and marks down and comparing arrays directly cut typing to about 65 ms and ready time from about 882 ms to 825 ms. Time the engine alone first, through the `globalThis.__EDITOR_REACT_RENDER_PROFILER__` hook, then count subscriptions and selector work per commit, not only rerenders, before reaching for view architecture such as islands. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-04-11-plite-huge-document-typing-needs-selector-fanout-cuts-before-islands.md:26-127`.

- **Materialize only the part of a coverage boundary the interaction targets.** One boundary can cover many unmounted blocks, which keeps the boundary registry small, but a caret in one of them should mount only its own group. In May 2026 selecting into the middle of a 5,000-block staged document took about 500 ms because materialization mounted the whole coalesced pending boundary; the fix passed the selection range through `materializeBoundary` and mounted only the intersecting groups. The staged mode was later cut, and materialize handlers still receive the target `range` and `rangeRole` (`packages/plitejs/src/dom/plugin/dom-coverage.ts:123-147`, `packages/plitejs/src/react/components/dom-coverage-boundary.tsx:111-122`). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-05-03-plite-dom-present-staging-needs-document-epoch-and-range-materialization.md:28`, `:62-74`, `:82`.

- **A fast path for a user edit stays one undoable change.** In May 2026 a direct snapshot replacement made a large plaintext paste fast and its output test pass, but left `editor.history.undos` empty, so undo could not reverse the paste and change observers saw nothing; the kept fix was one child-window replacement, which current paste fitting publishes as one canonical `DocumentChange`. `value.replace` is a document load that resets local history (`packages/plitejs/src/interfaces/editor.ts:692-699`), never an edit path. When optimizing an edit, assert the change count per gesture and one undo step that restores content and selection, not only the final document. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/performance-issues/2026-05-05-plite-large-paste-fast-path-must-still-be-a-logical-operation.md:32-64`, `:142-162`.

- **A caret move marks only the caret's ancestors as selection-changed.** A commit's `changed.nodeKeys('selection')`, which `changed.nodeKeys('decoration')` also includes, holds the NodeKeys of the before and after selections' points and of their ancestor chains; only an expanded range also walks every node between its edges (`getSelectionNodeKeys`, `packages/plitejs/src/core/commit.ts:198-245`, the walk at `:225`). So a collapsed caret move costs work proportional to the caret's depth, not to the document, while a selection across 200 blocks marks 400 keys. In May 2026, after direct typing on large documents was fixed, select-then-type still paid for a collapsed selection that scanned every indexed path; the note gives no number for that cost. Keep the collapsed case off the document walk; an expanded range may legitimately cover many nodes. Tests: `packages/plitejs/test/snapshot-contract.ts:2214` (a caret move from block 0 to block 1 yields exactly the old and new text and block keys) and `:2484` (a 200-block selection yields 400 keys). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-05-01-plite-text-snapshots-should-be-path-stable-for-large-document-typing.md:36`, `:52`, `:88-94`, `:102`.

- **A specialized path stays only while it beats the general path.** In the March-April 2026 Plite batch engine, a planner-owned path for independent-parent `split_node` and `merge_node` batches became slower than the general engine once that engine batched those families itself. Deleting it brought `Transforms.applyBatch` back in line with manual `Editor.withBatch` (70.4 ms against 70.68 ms for a flat merge batch on 5,000 blocks) with less code (`c70bacbd4a:docs/plite-draft/references/plite-batch-engine.md:305-315`, `:784`). A naive distinct-parent `split_node` overlay was cut for the same reason: it slowed the hot lane (`:79`, `:790`). The engine's rule let a family optimizer exist only while it kept replay semantics and published-node immutability and measurably beat the generic draft path (`:1050-1056`). Re-measure each fast path after the general path improves, and delete the ones that lose. The engine has since been replaced by transactions and `DocumentChange`, so the numbers are historical.

- **Attribute framework cost layer by layer before blaming a plugin.** The April 2026 program held legacy Slate as the floor on an equivalent workload: every millisecond above it needed a reason, and cost that bought no framework value was cut. It fixed the order of work: remove wasted work, move hooks, providers and subscriptions behind the slower branches that need them, precompute stable values, add internal fast paths for plain cases, and redesign an internal boundary only when a measurement shows it is the ceiling. It compared in a hierarchy, baseline against Plate core, Plate core against core plus one plugin, then one plugin against the real bundle, and it ran no plugin census on top of unresolved core cost, because skipping the middle step blames the wrong layer. Swapping store libraries to win one chart was ruled out. Source: `c70bacbd4a:docs/performance/editor-performance-master-plan.md:32-59`, `:1133-1154`. The benchmark rule's `plate-vs-plite-decomposition` lane now asks the same question with Plite as the substrate (`.agents/rules/benchmark/references/methodology.md`, Default Lane Order).

- **A per-node store provider costs several times plain context.** A dedicated `jotai-x` benchmark at 1,000 nodes measured provider-only mounts of 1.44 ms with plain React context, 8.39 ms with a seeded raw Jotai store, and 11.93 to 12.82 ms through the `jotai-x` provider, store API and keyed hook; selector consumers took 2.18, 15.52 and 20.45 to 25.05 ms; mount plus update took 4.28, 32.85 and 39.25 to 42.61 ms. Raw Jotai already cost far more than context, and `jotai-x` added a second cost on top in every lane. Two library cuts shipped with it: an identity read skips `selectAtom`, and a selector read memoizes its derived atom (`udecode/jotai-x@0ff7e8140d611bad6878099e4ca3dee44ba83ddc:packages/jotai-x/src/createAtomStore.ts:518-534`). Source: `c70bacbd4a:docs/performance/editor-performance-master-plan.md:448-523`; script `udecode/jotai-x@0ff7e8140d611bad6878099e4ca3dee44ba83ddc:packages/jotai-x/scripts/bench-store-alternatives.cjs`, output `udecode/jotai-x@0ff7e8140d611bad6878099e4ca3dee44ba83ddc:packages/jotai-x/store-alternatives.perf.json` (April 2026). Limit: a synthetic store benchmark, not an editor mount; Plate's own answer is the lazy Jotai bridge under '`ElementProvider` keeps a small runtime store and builds a Jotai store only on request.'

- **Split the render path into lanes until one lane holds the cost.** The April 2026 dissection added a prebuilt-mount lane (editor created first, so init work is not blamed on React), an init-only lane (construct, init, create-with-value and a pure value pass), a subscriber fan-out lane, and a core-mount ladder: provider only, hook calls only, `Editable` with static props, then the element pipe, the leaf and text pipes, and all render pipes together. At 5,000 chunked blocks the provider and hook calls stayed under 1 ms while static `Editable` took 273.26 ms; the element pipe added about 200 ms, the leaf and text pipes about 85 ms and all pipes about 301 ms, while static `Editable` sat level with legacy Slate's prebuilt mount (271.74 ms), so the render pipes held most of Plate core's prebuilt-mount gap (650.34 ms). Up to 1,000 null-rendering store subscribers barely moved mount and showed up only as update cost. Control rows such as a precomputed-path variant or plain-span renderers rule suspects out, and a fix counts when the production lane lands on the probe that predicted it; a synthetic win the real census lane does not reproduce is reverted, as an outer-wrapper hoist was. The harness keeps these lanes (`prebuiltMount`, `--core-mount-case`, `--fanout-subscribers`, `apps/www/scripts/run-editor-perf.mts:135`, `:744-745`). Source: `c70bacbd4a:docs/performance/plate-vs-plite-benchmarks.md:249-381`, `:1030-1082`, `:1514-1531`, `:1727-1806`. Limit: Plate on legacy Slate with the jotai-era element store.

- **Rewrite an initial value as a value pass, not one live transform per node.** In April 2026 the node-id plugin filled missing ids on load with one `editor.tf.setNodes` per block. Counting and timing each editor call during init showed `setNodes` took 431.05 of 441.45 ms at 5,000 blocks (5,000 calls) and 1,631.13 of 1,651.86 ms at 10,000, while 5,000 `editor.api.node` lookups took 1.50 ms. Walking the value and assigning ids in place cut raw init to 5.29 ms and 10.83 ms, level with the pure normalize lane, with zero `setNodes` and `api.node` calls; runtime normalization kept the editor-operation path. Today `ElementIdPlugin` declares `id` as a schema property with a `generate` function (`packages/platejs/src/lib/plugins/element-id/ElementIdPlugin.ts:58-73`), so filling missing ids belongs to schema fitting rather than to transforms (inferred from the declaration, not traced). When init is slow, count and time each editor operation before blaming traversal. Source: `c70bacbd4a:docs/performance/plate-vs-plite-benchmarks.md:565-618`, `:992-1003`.

- **In a per-node render path, stop recomputing what the caller already knows.** April 2026 probes at 5,000 blocks priced four such costs: an `ElementContent` that called `useElement()` only to read attributes already in its props (487.64 to 436.41 ms), a provider effect that subscribed to the per-node store's `path` to learn whether its node was first instead of reading the `path` prop (426.01 to 368.10 ms in the provider-only lane), full node-prop composition for a plugin with no node props, allowed attributes or inject props (444.36 to 422.40 ms in the rich lane), and rebuilding the plugin context object on every node (504.70 to 484.80 ms). Today `getRenderNodeProps` accepts a precomputed `pluginContext` and skips plugin attributes when no inject props or `render.attributes` apply (`packages/platejs/src/react/utils/getRenderNodeProps.internal.ts:37-60`). Benchmark the same provider with fewer consumers before redesigning a store. Source: `c70bacbd4a:docs/performance/plate-vs-plite-benchmarks.md:758-969`. Limit: Plate on legacy Slate with the jotai-era store.

- **Swapping the store library does not remove a per-node provider.** At 5,000 blocks in April 2026 a provider-only lane took 254.92 ms with plain React context, 308.17 ms with raw Jotai, 310.81 ms with a `zustand-x` store and 351.46 ms with Plate's `ElementProvider`; in a richer lane `zustand-x` was about 28 ms slower than raw Jotai. The cost was one store per node, not the store brand. Two experiments were reverted because they helped one lane and hurt the other (a linked scope chain in place of `jotai-x`'s cloned scope `Map`, and a linked per-node store). One plain bug did ship a fix: `React.useState(createStore())` evaluates its argument on every render although React keeps only the first result, and the lazy form `useState(() => createStore())` cut the direct rich lane from 484.80 to 453.39 ms (`udecode/jotai-x@0ff7e8140d611bad6878099e4ca3dee44ba83ddc:packages/jotai-x/src/createAtomProvider.tsx:90-92`). Batching controlled-prop sync through one writer atom, and skipping the first sync when hydration already wrote the same props, also stayed. Source: `c70bacbd4a:docs/performance/plate-vs-plite-benchmarks.md:1083-1217`.

- **`ElementProvider` keeps a small runtime store and builds a Jotai store only on request.** Each `ElementProvider` holds a scoped runtime store for `element`, `entry` and `path`, created once through a lazy `useState` and synced in a layout effect; it creates a Jotai store only when `useElementStore()` asks for one, and then keeps that store in sync (`packages/platejs/src/react/stores/element/useElementStore.tsx:84-128`, `:235-271`). The exported store surface survives while normal rendering pays no Jotai cost. In April 2026 this cut the 5,000-block provider-only lane from 368.10 to 317.90 ms while the selector lane stayed at 385.05 ms, level with the raw Jotai lower bound. Earlier steps made `useElement()` and `usePath()` read a cheap context first (hook-consumer gap over a no-hook control from 51.16 to 17.49 ms within one batch) and removed a redundant `ElementStoreProvider` layer (selector lane 449.81 to 384.33 ms); a custom per-provider selector subscription benchmarked worse (397.81 ms) and did not ship. A correctness fix came first: hydrating through the generic atom provider let a selector see `entry = null` on its first read. Source: `c70bacbd4a:docs/performance/plate-vs-plite-benchmarks.md:1218-1367`, `c70bacbd4a:docs/performance/editor-performance-master-plan.md:217-446`. Limit: Plate on legacy Slate.

- **Ask whether a provider owns a block before computing its defaults.** In May 2026 the page-layout extractor computed default recursive boxes, text runs and `NodeApi.string` for every block before checking whether a node-layout provider owned it, so a 500-row table paid for every cell although the provider needed only row units, and the `rows=500` pagination route timed out while `rows=8` loaded in about 448 ms. Element children were also all materialized before a renderer could pick a visible range. Check ownership first, compute only what the owner asks for, and where a viewport filter cannot run, such as with no scroll root, render everything rather than hide content. Source: `c70bacbd4a:docs/transplant/slate-v2/archive/docs/plans/2026-05-31-pagination-table-scale-perf.md:77`, `:139-156`, `:174-175`, `:181`. Limit: the May hooks (`nodeLayout` provider units, `slots.children(range)`) are gone; today's pagination asks a fragmentation provider for a `text`, `atomic` or `direct-children` plan (`docs/research/sources/plite/large-documents.md`, 'Pagination canvas').

## Benchmark validity

- **Check that the undo burst merged before reading an undo benchmark.** `shouldMergeText` merges contiguous inserts and contiguous deletes on the same target, and batch effects block merging. An unmerged burst makes the lane measure batch policy instead of replay. On 2026-04-11, undo and redo of 20 typed characters on a 5,000-block document took about 490 ms unmerged and about 20 ms merged. Code: `packages/plitejs/src/history/history-merge-policy.ts:303-360`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-04-11-plite-history-typing-bursts-need-legacy-style-merge-heuristics-before-anything-else.md`.
- **A comparison row needs a baseline that has the behavior.** Before keeping a row as benchmark debt, confirm the baseline implements the measured behavior in its model, not just that a UI control is missing. The legacy huge-document history row failed on a missing undo button, but that example was built with `withReact` only and never had history, so no harness patch could fix it. When the baseline is a different kind of feature, cut the row or record it as not applicable. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/workflow-issues/2026-04-15-benchmark-compare-rows-must-prove-the-legacy-surface-exists.md`.
- **A locality benchmark needs its broad-invalidation comparator.** An overlay, decoration or subscription-breadth benchmark supports a verdict only when it measures the current path, the candidate path and, when relevant, a worst-case broad-invalidation path; a lane that cannot tell them apart proves nothing. The benchmark rule does not name the comparator; the rule on recompute selectivity and subscriber fan-out in `.agents/rules/benchmark/references/performance-review.md:76` is where it would go. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/decoration-roadmap.md`.
- **No lane varies the number of inline elements in one block.** The rerender-breadth lanes measure sibling leaves and nested blocks, and `huge-dense-inline-props` on `/dev/editor-perf` measures leaf properties, so a per-keystroke cost that grows with the inline count of one paragraph, the #3430 freeze, would pass every current lane. This is inferred from the target list. Code: `benchmarks/targets/slate-v2.json`, `apps/www/src/app/dev/editor-perf/workloads.ts:232`. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/ledgers/fork-issue-dossier.md`.
- **The element-id lane times two paste shapes.** The `element-id-fragment` lane on `/dev/editor-perf` times `tx.fragment.replace` with a raw import (no ids) and a seeded duplicate paste (ids already in the document); `init-dissection` never runs paste-time id work, so init numbers cannot justify import or paste changes. At 5k blocks the old duplicate paste cost 20.06 ms against 5.87 ms for raw import, about 13.9 ms of it in 199 duplicate-id lookups. Element ids now drop on copy through property policy. Code: `apps/www/src/app/dev/editor-perf/workloads.ts:156`, `packages/platejs/src/lib/plugins/element-id/ElementIdPlugin.ts:65`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-04-03-nodeid-paste-import-needs-insertfragment-benchmark.md`.

- **A text-store win must include materializing the string.** In the 2026-09-09 research a piece-tree text store won on write-only edits, and the win reversed once each edit also materialized the full string, as an editor does to render and read. Removing unused virtualization key copies matched 1,000 boundary cases but stayed an unadopted microbenchmark, not scroll or paint proof. ## React Compiler

- **Resource lifetimes belong to their owner, not to memoization.** AI sessions are editor-owned with view registration and explicit disposal, Excalidraw subscriptions belong to the mounted drawing API, and code-drawing rendering has cancellation guards plus an Export consumer even while the preview is hidden. Whether React Compiler happens to reuse an object proves none of these lifetimes. Create or attach external resources at their lifecycle boundary, read immutable values during render, and remove a `useMemo` only when correctness survives recomputation; a stable instance needs an explicit owner such as the editor, view or session, not a new global cache. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/react-compiler.md:56-60`.

- **Compiler proof has five separate lanes.** Source eligibility (functions, diagnostics, explicit exclusions, source hashes); emitted package behavior (the real `tsdown` output and an equal-feature external consumer, since a consuming app cannot repair a package compiled before publication); copied-source behavior (a real registry consumer with its own compiler configuration); runtime behavior (off and on controls for mount, structural edits, inline selectors, teardown, strict and concurrent rendering and native selection); and performance (complete-operation distributions, retained heap, render and subscription counts). A generated runtime import proves none of them, and package proof does not prove copied TSX. As of September 2026 only part of the runtime lane and eight performance rows were measured. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/react-compiler.md:62-70`.
