# Performance diagnosis

These lessons come from retired solution notes, Plite references and ledgers, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`. The numbers are historical; rerun the named target before citing one.

## Where the time goes

- **Native DOM text sync has opt-outs.** Typing updates a text node in place without a React render only when the text is non-empty, has no decoration, and any custom `renderLeaf` or `renderText` is marked with `setDOMTextSyncRendererCapability`. In Plate, an `EditorContent` `renderLeaf` prop, a mark plugin with leaf attributes or a mark that requires model text sync opts the text out; otherwise Plate's compiled leaf renderer marks itself capable. Decorated or custom-rendered leaves therefore pay a React render on every keystroke. Code: `packages/plitejs/src/react/dom-text-sync.ts:52`, `:90-118`, `packages/platejs/src/react/utils/pipeRenderLeaf.internal.tsx:176-188`, `packages/plitejs/test/react/dom-text-sync-contract.ts`. Sources: `plite/reference/public-docs/libraries/plite-react/editable.mdx`, `plite/reference/public-docs/walkthroughs/09-performance.mdx`.
- **Text and selection commits keep the snapshot index stable.** A commit with no structural classification, no element type change and no discarded NodeKey advances the index through `advancePathStableSnapshotIndex` instead of remapping it, which keeps typing cheap on large documents. Before this split, a 2,000-block text insert spent about 41 ms in snapshot build plus 13 ms in rollback cloning, of 59 ms, while React took under 1 ms. Never route a path-changing commit class into this branch. Code: `packages/plitejs/src/core/public-state.ts:507-529`, `packages/plitejs/src/core/snapshot-index.ts:1749`. Source: `solutions/performance-issues/2026-05-01-plite-text-snapshots-should-be-path-stable-for-large-document-typing.md`.
- **Core phase timings come from a global profiler hook.** Set `globalThis.__EDITOR_REACT_RENDER_PROFILER__ = { acceptsCoreDuration(id), record(event) }` to receive `core-time` events from `profileCoreDuration`, such as `transaction-commit-snapshot`, `snapshot-build-index` and `listener-snapshot`. This is how to split transaction cost from React cost, which `performance.mdx` asks for without saying how; the huge-document trace benchmarks use it. Code: `packages/plitejs/src/core/profiling.ts:3`, `benchmarks/slate-v2/donor/browser/react/huge-document-browser-trace.mjs`. Source: `solutions/performance-issues/2026-05-01-plite-text-snapshots-should-be-path-stable-for-large-document-typing.md`.
- **Large paste and cut cost write count and snapshot allocation, not parsing.** In May 2026 the old per-line split-and-insert path took about 3.5 s for 2,000 plaintext lines while split, encode and decode stayed cheap; one schema-fitted slice replacement brought 10,000 lines to about 35 ms. A 50,000-block two-node cut lowered to one change took about 10 ms warm (p50) and about 172 ms cold, the cold cost being snapshot allocation. When large clipboard work regresses, count canonical changes per gesture first, then measure cold snapshot cost apart from warm edits. Code: target `clipboard-large-payload` in `benchmarks/targets/slate-v2.json`. Sources: `plite/ledgers/fork-issue-dossier.md`, `plite/ledgers/issue-coverage-matrix.md`.
- **A first triage before a full profile.** Typing INP under about 100 ms feels responsive. When the editor is much faster in Firefox than in Chrome or Safari, DOM paint dominates; when it speeds up with custom corrections disabled, corrections dominate; otherwise React is the cost. `content-visibility: auto` on every element can cost more than it saves in Safari, where its overhead grows with node count. This is inherited Slate guidance with no Plite workload behind it, so treat it as a lead. Source: `plite/reference/public-docs/walkthroughs/09-performance.mdx`.

## Benchmark validity

- **Check that the undo burst merged before reading an undo benchmark.** `shouldMergeText` merges contiguous inserts and contiguous deletes on the same target, and batch effects block merging. An unmerged burst makes the lane measure batch policy instead of replay. On 2026-04-11, undo and redo of 20 typed characters on a 5,000-block document took about 490 ms unmerged and about 20 ms merged. Code: `packages/plitejs/src/history/history-merge-policy.ts:303-360`. Source: `solutions/performance-issues/2026-04-11-plite-history-typing-bursts-need-legacy-style-merge-heuristics-before-anything-else.md`.
- **A comparison row needs a baseline that has the behavior.** Before keeping a row as benchmark debt, confirm the baseline implements the measured behavior in its model, not just that a UI control is missing. The legacy huge-document history row failed on a missing undo button, but that example was built with `withReact` only and never had history, so no harness patch could fix it. When the baseline is a different kind of feature, cut the row or record it as not applicable. Source: `solutions/workflow-issues/2026-04-15-benchmark-compare-rows-must-prove-the-legacy-surface-exists.md`.
- **A locality benchmark needs its broad-invalidation comparator.** An overlay, decoration or subscription-breadth benchmark supports a verdict only when it measures the current path, the candidate path and, when relevant, a worst-case broad-invalidation path; a lane that cannot tell them apart proves nothing. The benchmark rule does not name the comparator; the rule on recompute selectivity and subscriber fan-out in `.agents/rules/benchmark/references/performance-review.md:76` is where it would go. Source: `plite/decoration-roadmap.md`.
- **No lane varies the number of inline elements in one block.** The rerender-breadth lanes measure sibling leaves and nested blocks, and `huge-dense-inline-props` on `/dev/editor-perf` measures leaf properties, so a per-keystroke cost that grows with the inline count of one paragraph, the #3430 freeze, would pass every current lane. This is inferred from the target list. Code: `benchmarks/targets/slate-v2.json`, `apps/www/src/app/dev/editor-perf/workloads.ts:232`. Source: `plite/ledgers/fork-issue-dossier.md`.
- **The element-id lane times two paste shapes.** The `element-id-fragment` lane on `/dev/editor-perf` times `tx.fragment.replace` with a raw import (no ids) and a seeded duplicate paste (ids already in the document); `init-dissection` never runs paste-time id work, so init numbers cannot justify import or paste changes. At 5k blocks the old duplicate paste cost 20.06 ms against 5.87 ms for raw import, about 13.9 ms of it in 199 duplicate-id lookups. Element ids now drop on copy through property policy. Code: `apps/www/src/app/dev/editor-perf/workloads.ts:156`, `packages/platejs/src/lib/plugins/element-id/ElementIdPlugin.ts:65`. Source: `solutions/performance-issues/2026-04-03-nodeid-paste-import-needs-insertfragment-benchmark.md`.

## Tools

- **`perf:editor` presets beyond the public one.** `pnpm --filter www perf:editor --preset <name> --out <raw> --summary-out <summary>` writes the raw JSON and a compact summary in one pass against a running `/dev/editor-perf`. The presets are `layer-0`, `layer-0-smoke`, `layer-1-core-plugins`, `layer-1-core-plugins-smoke`, `layer-3-core-stress` and `public-slate-vs-plate`; only the public one has a package script, and `performance.mdx` documents only `perf:editor:public`. Code: `apps/www/scripts/run-editor-perf.mts:22-28`. Source: `solutions/performance-issues/2026-04-01-layer0-runner-should-write-summary-json-in-the-same-pass.md`.
- **The huge-document demo and the perf page parse their knobs separately.** Both share `createHugeDocumentValue`, the huge-mixed-block workload and an "Open in benchmark mode" link built from the `blocks`, `chunking`, `chunk_size` and `content_visibility` query keys, but each keeps its own `parseNumber` and `parseBoolean`. Change a knob in both parsers, or the manual scenario and the measured one drift apart. Code: `apps/www/src/registry/examples/huge-document-demo.tsx:261`, `apps/www/src/app/dev/editor-perf/page.tsx:131`. Source: `solutions/performance-issues/2026-04-01-huge-document-demo-and-benchmark-should-share-a-query-param-config-contract.md`.
