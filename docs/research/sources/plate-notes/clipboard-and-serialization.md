# Clipboard, paste and serialization

These lessons come from retired solution notes and Plite references, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`, read with `git show 52625e8502:docs/<path>`, unless it names a current plan.

## Copy, cut and paste

- **Outgoing content passes through one read.** Copy and cut (`writeDOMSelectionData`, `writeDOMRangeData`) and drag start (`dom-drag.ts`) all call `editor.read.slice.export()`. A plugin strips transient or private properties from outgoing content by wrapping `editorReads.slice.export` in `readMiddleware`; that does not change what `editor.read.slice.get()` returns. `clipboard.mdx` never names `editorReads.slice.export` or `readMiddleware` for sanitizing outgoing content, while the table clipboard spec already relies on this hook. Code: `packages/plitejs/src/core/editor-reads.ts:44`, `packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:514`, `packages/platejs/src/features/table/lib/BaseTablePlugin.clipboard.spec.tsx:412`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/08-plugins.mdx`.
- **Slice fitting has shape rules the tests pin.** Replacing selected text with a one-text-block fragment keeps the target block's type and props, even when the selection covers a whole one-block document. Over an empty target the copied type now wins (`clipboard-contract.ts:1373`, `:1554`), which reverses the source note's empty-target rule. A code-block fragment merges into the active code line instead of adding a sibling block. A copied list over selected paragraph text splits the paragraph around the list. Paragraphs pasted into a list item keep the first in the item and promote the rest after the list, splitting its tail. The full-document fast path and the generic leaf walk both lost these distinctions, so assert the full tree and the selection, not the text. Code: `packages/plitejs/test/clipboard-contract.ts:1119`, `:1373`, `:1554`, `:1748`, `:2034`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-04-single-block-fragment-replacement-must-preserve-target-block-before-full-document-replace.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-native-list-fragment-paste-must-run-before-generic-fragment-unwrapping.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-nested-clipboard-fragments-must-merge-into-active-text-block.md`.
- **Paste over text inside a link lands outside the link on both paths.** That holds for the fragment path and for the DOM fallback (text/html without a fragment marker, or plain text). The fallback once called `insertText` and inherited the link (`replacedlink`), so a green `insertFragment` test does not prove browser paste; assert link containment, not block text. Code: `packages/plitejs/test/clipboard-contract.ts:1002`, `apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:891`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-html-clipboard-fallback-must-not-inherit-selected-inline-text.md`.
- **Inline voids have no spacer element to mark.** Inline void shells render no `data-editor-spacer`, so clipboard export falls back to another cloned editor element, or wraps a text node in a span, before writing `data-editor-fragment`. Copying a selected inline void once threw on `null.setAttribute` before any payload was written, which broke copy and cut. Void clipboard tests need block-void and inline-void DOM shapes separately, plus a text/plain check for FEFF or neighbor text. Code: `packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:610`, `packages/plitejs/test/dom/clipboard-boundary.ts:3053`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-04-inline-void-clipboard-export-must-not-assume-block-void-spacer-dom.md`.
- **Shift+Delete deletes without cutting.** The hotkey table maps `shift?+delete` to `deleteForward`, and the editing kernel runs it as a model delete at keydown, so the Windows and Linux Shift+Delete cut shortcut removes the selection without writing the clipboard (Slate #2694, never claimed). No test or doc covers it: no cut proof uses Shift+Delete, every keyboard cut proof uses ControlOrMeta+X, and nobody checked the browser's native Shift+Delete behavior on Windows. Code: `packages/plitejs/src/dom/utils/hotkeys.ts:22`, `packages/plitejs/src/react/editable/editing-kernel.ts:856`, `keyboard-input-strategy.ts:1083`. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/ledgers/fork-issue-dossier.md`.

- **The Plite clipboard payload is an exact versioned envelope that fails closed.** Copy writes `{ slice, version: 1 }` under the editor's fragment MIME key (`packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:310`, `:333`). A read accepts only an object with exactly the keys `slice` and `version` at that version; any other payload, including an empty or undecodable one, returns `{ kind: 'invalid', source }` instead of throwing (`:440-475`, `:737-761`; test `packages/plitejs/test/dom/clipboard-boundary.ts:918`). The April 2026 proof chose a versioned namespace over the legacy one and made unsupported payloads and targets fail closed instead of throwing, with core deciding what a fragment means and the DOM layer owning MIME keys, `DataTransfer`, HTML and the plain-text fallback. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/logic-errors/2026-04-03-plite-clipboard-boundary-proof-must-split-fragment-semantics-and-dom-transport.md`.

- **Static selection extraction shares the editable clipboard format owner.** The July static-copy repair removed a Core `setFragmentData(data, originEvent)` API that hand-wrote the Plite fragment format. Current `packages/platejs/src/static/internal/writeStaticSelectionClipboardData.ts:381-398` validates and extracts the rendered static selection, then calls `editor.api.dom.clipboard.writeSlice` with its slice, HTML and plain text, and returns false when no static selection exists so `packages/platejs/src/react/components/PlateView.tsx` prevents the native copy only after a write. Plite's `packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:364-431` owns fragment encoding, metadata attachment and configured transfer representations. Source: `docs/plans/2026-07-03-plate-next-static-clipboard-payload-owner.md:323-338`. Limit: static DOM selection extraction remains a distinct host path; sharing serialization does not prove identical selection geometry. The current call uses the installed clipboard API rather than the plan's direct public helper.

- **Paste routing follows the explicit target.** Test an explicit code-block target while the selection is outside code, and an explicit ordinary target while the selection is inside code. July's migration could insert into the selection instead of the supplied target, or split insertion between them (`docs/plans/2026-07-09-plate-next-code-block-drift-closure.md:371,532-540`). Current `BaseCodeBlockPlugin` resolves `options.at` before classifying the target and preserves the input options while converting the slice to code text (`packages/platejs/src/features/code-block/lib/BaseCodeBlockPlugin.ts:740-780`). Both opposite-target cases remain in its spec at lines 1352 and 1382. The old forward-point-ref implementation is retired; these are model contracts, not physical clipboard proof.

- **A specialized paste handler reports actual insertion.** Image URL paste once swallowed input after its insertion policy rejected the URL. Recognizing an image-looking string is not enough to claim the paste: return a handled transaction only if insertion succeeds, otherwise delegate. Current image command middleware records `tx.image.insert`'s result and returns `next()` when it is false (`packages/platejs/src/features/media/lib/image/BaseImagePlugin.ts:430-452`); media insertion applies its shared URL policy before writing (`BaseMediaPlugin.ts:193-203`, `:359-360`). Source: `c70bacbd4a:docs/plans/2026-07-27-plate-next-sync-all-packages-v17.md:1564`. The same row's canonical clipboard projection fact is already covered by "Outgoing content passes through one read" on this page. Limit: delegation allows another owner to handle the input; it does not guarantee that every rejected URL becomes literal text.

- **Reuse validated slice snapshots without repeating the trust-boundary work.** The July slice audit found that construction cloned and validated content, then internal reuse repeated validation. Keep untrusted ingestion strict, but retain preparation privately for detached immutable snapshots. Current `packages/plitejs/src/core/content-slice.ts` tracks prepared values and caches encoded content and open-depth variants; callers receive no public trusted-input escape hatch. Source: `docs/plans/2026-07-20-wordgard-plite-slice-architecture.md:246-247`, with the preparation design at lines 547-569. Structural trust does not establish compatibility with a different compiled schema.

- **Projected extraction must preserve the selected slice's open edges.** The first July projected-copy implementation called `ContentSlice.closed` and pasted a nested wrapper instead of the selected text. Extract each segment through `state.slice.get`, keep the first segment's openStart and the last segment's openEnd, and validate the assembled slice. Current `packages/plitejs/src/react/editable/projected-clipboard.ts:141-179` follows that path and also carries remapped roots. Source: `docs/plans/2026-07-21-wordgard-plite-schema-contribution-architecture.md:1017`, whose regression expected `xb`. Closing content is an explicit structural transformation, not harmless packaging.

- **A single-line paste fix does not prove multiline paste.** P45 restored collapsed active marks for direct plain-text insertion, but P51 found that multiline branches returned through separate helpers and still produced unmarked text. A failing package case caught that partial fix; P54 then covered replacement of an empty block separately. Sources: `docs/plans/2026-06-13-plite-10h-auto-proof-transport-selection.md:851`, `:854`. The old helpers are gone: current plain-text decoding obtains collapsed selection marks and passes them into both inline and line-block construction (`packages/plitejs/src/dom/plugin/data-transfer-format.ts:450`, `:486`), with populated and empty multiline cases in `packages/plitejs/test/dom/clipboard-boundary.ts:2635`, `:2675`. Preserve the branch coverage when changing the decoder; do not restore the retired helper architecture.

- **Visible copy order and mutation identity need different resolvers.** The May 29 Portable Text harvest fixed copying repeated appearances of one content root by extracting each visible selection segment in order. Reusing mutation-target resolution rejected a copy that had an unambiguous visible result, because repeated appearances make mutation identity ambiguous. Current `getProjectedViewSelectionSlice` iterates `viewSelection.segments.parts` and extracts root-scoped slices (`packages/plitejs/src/react/editable/projected-clipboard.ts:99`), while `createProjectedSelectionTarget` still rejects ambiguous boundary segments (`packages/plitejs/src/react/editable/projected-selection-target.ts:24`). Source: `docs/plans/2026-05-29-plite-portabletext-harvest-plan.md:309-317`, which records focused package and Chromium copy/drop proof. Limit: those are historical runs; current source was inspected, not rerun.

- **An internal fragment marker does not prove useful external clipboard HTML.** In the May fork-issue reproduction, a selected image copied an internal fragment but exported HTML without `<img>` and plain text containing only newlines. The browser range was anchored in the void spacer. Current `packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:576-594` expands the clone before the starting void and after the ending void so the visible element enters external HTML. Assert the internal payload and visible HTML separately; `apps/plite/tests/plite-browser/donor/examples/images.test.ts:973` retains that browser case. Source: `c70bacbd4a:docs/plans/2026-05-10-plite-udecode-open-issues-reproduction-ralplan.md:386-461`, concerning historical fork issue `udecode/slate#7`. No fresh clipboard run was performed.

## Foreign HTML

- **The paste-html example importer owns its whitespace and code rules.** It drops raw newlines from ordinary HTML text but keeps them inside `pre`, `code` and `white-space: pre`. It detects code-source HTML (`pre`, GitHub code tables, multi-line code) before generic table and paragraph deserialization, and CSS `text-align` wins over the legacy `align` attribute. Every paste-html browser test shares this importer, so run the whole file after any change, assert pasted blocks by text and attributes rather than paragraph count, and drive code-source tests through the browser handle's `insertData`. The May 2026 harvest found Chromium's native clipboard flattening Quip-style `<pre>` with `<br>` into paragraphs before the importer saw it. Code: `apps/www/src/app/(app)/examples/plite/_examples/paste-html-import.ts:106`, `apps/plite/tests/plite-browser/donor/examples/paste-html.test.ts:384`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/best-practices/2026-05-09-lexical-htmlcopy-harvest-rows-need-whitespace-and-empty-target-boundaries.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/best-practices/2026-05-09-lexical-codeblock-harvest-rows-need-data-transfer-boundaries.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/best-practices/2026-05-09-lexical-paragraph-node-harvest-rows-need-dom-import-splitting.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/best-practices/2026-05-09-lexical-tab-node-harvest-rows-need-clipboard-browser-proof-boundaries.md`.
- **Block boundaries in foreign HTML.** A generic `<div>` is a block boundary even under a `<span>` (`123<div>456</div>` gives two blocks). A `<p>` holding any block child is split: its blocks are lifted and its inline runs become paragraphs, so no block void stays inside that paragraph. Lexical's `<p><img></p>` is the all-block case. Plate's `HtmlPlugin` lifts every block child the schema disallows in a decoded element and keeps each inline run as that element (`liftDisallowedBlocks`, `packages/platejs/src/lib/plugins/html/HtmlPlugin.ts:2228`, `HtmlPlugin.spec.ts:42`). An image that renders can still be nested wrongly, so assert block text arrays and structure. Code: `apps/www/src/app/(app)/examples/plite/_examples/paste-html-import.ts:273`, `:475`, `:647`, `:652`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-block-only-html-paragraphs-must-not-wrap-block-voids.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-html-div-boundaries-must-survive-inline-wrappers.md`.
- **Word keeps VML shapes inside HTML comments.** In Word clipboard HTML the `<v:shape id o:spid>` markup sits in comments, so DOM queries for `v:shape` find nothing. `getVShapes` scans comment text with a regex for `id` and `o:spid` and drops entries missing either. A refactor back to `querySelectorAll` would silently lose the spid-to-RTF image mapping for pasted Word images. Code: `packages/platejs/src/docx/html/cleanWordHtml.internal.ts:117`, `:225`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-03-24-docx-vml-shapes-must-be-extracted-from-comment-markup-not-domparser-nodes.md`.

- **Sanitize the whole input before any mapping reads it.** On 2026-09-28 per-element guards left three gaps: a DOCX parent paragraph mapping read a descendant's unsafe `href` before the decoder dropped that descendant, the real video figure mapping read its child's tab-obfuscated `java\tscript:` source before the child's guard ran, and the HTML AST pass trimmed but did not reject embedded control characters. The adopted fix sanitizes live DOM once, before a parent mapping can read descendants, and rechecks emitted attributes at output through one URL role policy. Code: `packages/platejs/src/lib/plugins/html/htmlSafety.ts`, `packages/platejs/src/internal/utils/urlPolicy.ts`, tests `packages/platejs/src/lib/plugins/html/htmlSafety.spec.ts:51`, `:85`, `:328`, `:417`. Source: `docs/research/probes/2026-09-28-conversion-boundary/safety/README.md:23`, `review.md:18-25`.

- **Fix an import rule in the importer, never by intercepting paste.** When Chromium's native clipboard flattened Quip-style `<pre>` with `<br>` into paragraphs, an `onPaste` handler in the paste-html example made that row pass but took the paste away from the runtime clipboard strategy: the runtime's `insert-data` command no longer appeared in the kernel trace, and the generated paste gauntlet failed. The kept fix detects code-source HTML in the importer and proves it through the browser handle's `insertData`, the same DataTransfer boundary as Lexical's `CodeBlock.test.ts`. A native paste policy belongs to the runtime with kernel-trace proof, not to an app importer. The paste-html browser file asserts the `insert-data` trace (`apps/plite/tests/plite-browser/donor/examples/paste-html.test.ts:602-617`) and runs the gauntlet ('runs generated clipboard paste gauntlet without illegal kernel transitions', `:2213`). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/best-practices/2026-05-09-lexical-codeblock-harvest-rows-need-data-transfer-boundaries.md:29-43`, `:72-89`.

- **A tree-wide existential query latches its first match.** The old `someHtmlElement` lost a successful match when traversal continued into later siblings (`docs/plans/2026-07-26-plate-next-html-plugin-colocation.md:213-214`). Current `someHtmlElement` returns false from later traversal callbacks once `found` is true, preserving the result (`packages/platejs/src/lib/plugins/html/htmlDom.ts:160-175`). Its regression puts a matching span before a nonmatching strong element and asserts that only DIV and SPAN were visited (`htmlDom.spec.ts:83-96`). A callback return that only stops descent is insufficient unless later sibling callbacks also preserve the first match.

- **HTML precedence belongs to the format mapping.** A July review proposed restoring global plugin priority after HTML ownership consolidation; the proposal was rejected because HTML precedence had a local owner (`docs/plans/2026-07-26-plate-next-html-plugin-colocation.md:215-217`). Current HTML compilation explicitly assigns precedence to mapping-local priority, not plugin application order (`packages/platejs/src/lib/plugins/html/HtmlPlugin.ts:463,876`), and mapping proof exercises delegation to a lower-priority candidate (`HtmlPlugin.mapping.spec.ts:1257`). Limit: the July owner was called a codec; current source uses schema-bound format mappings. This lesson does not prescribe ordering for other plugin contributions.

- **Different CSS classes do not make HTML matchers disjoint.** One element can carry both classes, so an HTML compiler cannot dismiss a same-priority conflict merely because the class tokens differ (`docs/plans/2026-07-26-plate-next-html-plugin-colocation.md:218-219`). Current `matchersOverlap` retains that rule (`packages/platejs/src/lib/plugins/html/HtmlPlugin.ts:1022-1023`), and 'rejects equal-priority overlapping element candidates' declares `section.notice` and `section.callout` and expects editor construction to reject their overlap (`HtmlPlugin.mapping.spec.ts:1220-1254`). Limit: class-token difference alone proves no disjointness; other incompatible matcher constraints can still do so.

- **Mammoth's browser and Node entrypoints need different input keys.** A DOCX roundtrip under Bun failed when it received only Mammoth's browser `arrayBuffer` input. Supplying both `arrayBuffer` and `buffer` let the external entrypoint choose its host-specific key. Current import still supplies both (`packages/platejs/src/docx/import/lib/importDocx.ts:1158-1160`), and `importDocx.spec.ts:64-65` checks that both keys identify the same input. Source: `c70bacbd4a:docs/plans/2026-07-27-plate-next-sync-all-packages-v17.md:1512`. Limit: this is an external-library compatibility boundary; the July cast-free typing claim is no longer true in the current implementation.

- **Clipboard delivery does not establish a route's rich-HTML semantics.** A June 2026 experiment demanded `<strong>` preservation in an editable-void child root before that route owned a rich-HTML parser. Text arrived without the mark, so the proposed oracle was reverted and parser ownership remained a design question. Keep a delivery test separate from the route's assertions about marks, elements and sanitization. Current policy puts table and format interpretation above the neutral fitter (`docs/plans/topics/clipboard.md`), and `packages/test/README.md:162` explicitly limits `pasteHtml` to delivery and ownership proof. Evidence: `c70bacbd4a:docs/plans/2026-06-13-plite-8h-supervision-2026-06-13.md:680`, with the failed experiment described at line 855. The old failure is not evidence of a present child-root defect.

- **A foreign HTML bold tag can be a non-bold wrapper.** The May 2026 Lexical harvest required both Google Docs BIU spans and ordinary semantic `<b>` paste: Google Docs wraps non-bold content in `<b style="font-weight:normal">`, so treating every `b` as bold corrupts imported marks. The current example importer checks explicit non-bold font weights before assigning a bold mark (`apps/www/src/app/(app)/examples/plite/_examples/paste-html-import.ts:132-155`); its browser corpus separately tests Google Docs BIU and semantic bold (`apps/plite/tests/plite-browser/donor/examples/paste-html.test.ts:857`, `:1038`). Preserve both cases when changing mark import. This is the example importer's policy, not proof of every Plate HTML decoder. Source: `c70bacbd4a:docs/plans/2026-05-09-plite-lexical-harvest-test-processing-ralplan.md:55-63`.

- **Prediction-shaped clipboard data must retain the plain-text insertion path.** The May 7 draft-Plite paste example parsed identical text/html and text/plain prediction payloads as rich HTML and threw while replacing formatted text. The fix recognized the plain-text payload and preserved insertion formatting. Current apps/www/src/app/(app)/examples/plite/_examples/paste-html-import.ts:689-697 checks whether text/plain is present and delegates through next() when isPlainTextClipboardHtml recognizes equivalent plain content; HTML-only payloads retain HTML import. Evidence: docs/plans/2026-05-07-plite-mobile-ime-input-runtime-ralplan.md:1634-1651. Limit: this proves importer routing, not actual iOS prediction transport.

## Markdown and persistence

- **Every built list item needs a boolean `spread`.** `mdast-util-to-markdown` joins a list item's children without a blank line only when that `listItem` has a boolean `spread` (`lib/join.js` in 2.1.2, which `remark-stringify` 11 resolves). A `listItem` without it gets a blank line before its nested list even when the parent list has `spread: false`, so `listToMdastTree` sets `spread` on every list and list item in each code path. The bug showed only in the final markdown string while the mdast helper specs passed. Code: `packages/platejs/src/markdown/lib/serializer/listToMdastTree.ts:92`, `:150`, `:224`, `:247`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-03-24-markdown-nested-list-tight-spread-missing.md`.
- **Raw Plite `onValueChange` sees one root's children.** Raw Plite `<EditorRoot onValueChange>` passes `snapshot.children` of the provider's root and fires only when those children change, so an edit to meta or another root never reaches it; persist `editor.read.value()` from `onCommit` instead. Plate's `EditorRoot` passes the full `EditorDocumentValue` under the same prop name. Code: `packages/plitejs/src/react/components/plite.tsx:673-698`; Plate side: `content/docs/(guides)/document-meta.mdx:48`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/libraries/plite-react/plite.mdx`, `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/walkthroughs/06-saving-to-a-database.mdx`.
- **A kept source part that copies the body goes stale on edit.** A source-aware DOCX export regenerates the body and keeps passive source parts around it, so a kept part derived from the body carries text the edit removed. Four members surfaced: the hidden Plate envelope at `editor/authored.json` (cut), the package thumbnail and the extended properties at `docProps/app.xml` with their page and word counts (both dropped on edit with a `source-part-omitted` diagnostic of reason `invalidated`, as are the core properties), and a custom property whose `linkTarget` caches bookmarked body text (still carried, so the custom-properties row breaks the rule below until its bug fix lands). `ROOT_PARTS` gives each admitted root relationship one edit disposition: `regenerate`, `carry` or `drop`. The overlay copies only `carry` parts. A new admitted root type needs a disposition before a source holding it can be retained, and a part that copies body content should never be `carry`. A dropped part that a kept header still reaches stays as that header's content and is not reported omitted. To test a candidate, edit a marker string out of the body and search every part of the edited export for it. Code: `packages/platejs/src/docx/internal/sourceEligibility.ts:202`, `:244`, `packages/platejs/src/docx/export/lib/sourcePreservation.ts:594`, `sourcePreservation.spec.ts:304`, `:369`. Source: `docs/plans/2026-10-06-documents-review.md`.

- **Whitespace between list items is layout, not list content.** The DOCX export list builder skips whitespace-only text children of `ul`, `ol` and `li`. In March 2026 it treated indentation text as content: a list that began with an indentation text node opened a blank paragraph and appended the following `<li>` into it, so `word/document.xml` kept the numbering paragraphs and lost item text such as `Item 1` and `Indented item`. Keep `<li>` a structural boundary that never merges into an open text paragraph, and when a DOCX list keeps its numbering but loses its text, inspect the list reducer before ZIP or XML generation. No spec under `packages/platejs/src/docx` contains `<li>` (searched 2026-10-08), so the skip has no test. Code: `packages/platejs/src/docx/export/lib/internal/xml-builder.ts:454`, `:509`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/test-failures/docx-export-list-whitespace-can-drop-list-item-text.md`.

- **Skipping an image must not skip its later siblings.** Restoring DOCX export's remote-image opt-in exposed child-image branches that used break and truncated the rest of the paragraph; the July review changed those exits to continue (docs/plans/2026-07-11-plate-next-docx-docx-io-emoji-package-reviews.md:438, 725-726). The current child-image loop still continues past disabled or unusable images (`packages/platejs/src/docx/export/lib/internal/xml-builder.ts:2067-2153`). The regression opens word/document.xml and asserts both text runs around a disabled remote image (`packages/platejs/src/docx/export/lib/html-to-docx.spec.ts:42-51`). Limit: this proves sibling preservation for that converter path; it does not establish universal image-format support.

- **Import markers stay private while positions remain public.** DOCX comment preprocessing once leaked its transport markers through returned nodes. The repair stripped the markers and returned comment positions separately, without restoring public token helpers. Current import immutably rebuilds decoded leaves while collecting endpoints (`packages/platejs/src/docx/import/lib/importDocx.ts:1000-1033`), and its public import test checks rich comment records and marker removal (`importDocx.spec.ts:206`). Source: `c70bacbd4a:docs/plans/2026-07-27-plate-next-sync-all-packages-v17.md:1489-1491`. Limit: the old `DocxComment.references: Point[]` signature has been replaced; retain the separation of transport markers and semantic references, not that signature.

- **Normalize external canvas state at the persistence boundary.** Excalidraw's UI payload contained values such as `undefined` and Maps that could not be published as strict editor JSON. The July repair normalized the external payload before saving it. Current `useExcalidrawSync` uses Excalidraw's `serializeAsJSON` and parses its result before publishing node data (`packages/platejs/src/excalidraw/react/useExcalidrawSync.ts:84-111`), so transient canvas state is filtered by the owning serializer.
