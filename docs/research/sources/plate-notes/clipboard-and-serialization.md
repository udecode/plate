# Clipboard, paste and serialization

These lessons come from retired solution notes and Plite references, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`, read with `git show 52625e8502:docs/<path>`, unless it names a current plan.

## Copy, cut and paste

- **Outgoing content passes through one read.** Copy and cut (`writeDOMSelectionData`, `writeDOMRangeData`) and drag start (`dom-drag.ts`) all call `editor.read.slice.export()`. A plugin strips transient or private properties from outgoing content by wrapping `editorReads.slice.export` in `readMiddleware`; that does not change what `editor.read.slice.get()` returns. `clipboard.mdx` never names `editorReads.slice.export` or `readMiddleware` for sanitizing outgoing content, while the table clipboard spec already relies on this hook. Code: `packages/plitejs/src/core/editor-reads.ts:44`, `packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:514`, `packages/platejs/src/features/table/lib/BaseTablePlugin.clipboard.spec.tsx:412`. Source: `plite/reference/public-docs/concepts/08-plugins.mdx`.
- **Slice fitting has shape rules the tests pin.** Replacing selected text with a one-text-block fragment keeps the target block's type and props, even when the selection covers a whole one-block document. Over an empty target the copied type now wins (`clipboard-contract.ts:1373`, `:1554`), which reverses the source note's empty-target rule. A code-block fragment merges into the active code line instead of adding a sibling block. A copied list over selected paragraph text splits the paragraph around the list. Paragraphs pasted into a list item keep the first in the item and promote the rest after the list, splitting its tail. The full-document fast path and the generic leaf walk both lost these distinctions, so assert the full tree and the selection, not the text. Code: `packages/plitejs/test/clipboard-contract.ts:1119`, `:1373`, `:1554`, `:1748`, `:2034`. Sources: `solutions/logic-errors/2026-05-04-single-block-fragment-replacement-must-preserve-target-block-before-full-document-replace.md`, `solutions/logic-errors/2026-05-09-native-list-fragment-paste-must-run-before-generic-fragment-unwrapping.md`, `solutions/logic-errors/2026-05-09-nested-clipboard-fragments-must-merge-into-active-text-block.md`.
- **Paste over text inside a link lands outside the link on both paths.** That holds for the fragment path and for the DOM fallback (text/html without a fragment marker, or plain text). The fallback once called `insertText` and inherited the link (`replacedlink`), so a green `insertFragment` test does not prove browser paste; assert link containment, not block text. Code: `packages/plitejs/test/clipboard-contract.ts:1002`, `apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:891`. Source: `solutions/logic-errors/2026-05-09-html-clipboard-fallback-must-not-inherit-selected-inline-text.md`.
- **Inline voids have no spacer element to mark.** Inline void shells render no `data-editor-spacer`, so clipboard export falls back to another cloned editor element, or wraps a text node in a span, before writing `data-editor-fragment`. Copying a selected inline void once threw on `null.setAttribute` before any payload was written, which broke copy and cut. Void clipboard tests need block-void and inline-void DOM shapes separately, plus a text/plain check for FEFF or neighbor text. Code: `packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:610`, `packages/plitejs/test/dom/clipboard-boundary.ts:3053`. Source: `solutions/logic-errors/2026-05-04-inline-void-clipboard-export-must-not-assume-block-void-spacer-dom.md`.
- **Shift+Delete deletes without cutting.** The hotkey table maps `shift?+delete` to `deleteForward`, and the editing kernel runs it as a model delete at keydown, so the Windows and Linux Shift+Delete cut shortcut removes the selection without writing the clipboard (Slate #2694, never claimed). No test or doc covers it: no cut proof uses Shift+Delete, every keyboard cut proof uses ControlOrMeta+X, and nobody checked the browser's native Shift+Delete behavior on Windows. Code: `packages/plitejs/src/dom/utils/hotkeys.ts:22`, `packages/plitejs/src/react/editable/editing-kernel.ts:856`, `keyboard-input-strategy.ts:1083`. Source: `plite/ledgers/fork-issue-dossier.md`.

- **The Plite clipboard payload is an exact versioned envelope that fails closed.** Copy writes `{ slice, version: 1 }` under the editor's fragment MIME key (`packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:310`, `:333`). A read accepts only an object with exactly the keys `slice` and `version` at that version; any other payload, including an empty or undecodable one, returns `{ kind: 'invalid', source }` instead of throwing (`:440-475`, `:737-761`; test `packages/plitejs/test/dom/clipboard-boundary.ts:918`). The April 2026 proof chose a versioned namespace over the legacy one and made unsupported payloads and targets fail closed instead of throwing, with core deciding what a fragment means and the DOM layer owning MIME keys, `DataTransfer`, HTML and the plain-text fallback. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/logic-errors/2026-04-03-plite-clipboard-boundary-proof-must-split-fragment-semantics-and-dom-transport.md`.

## Foreign HTML

- **The paste-html example importer owns its whitespace and code rules.** It drops raw newlines from ordinary HTML text but keeps them inside `pre`, `code` and `white-space: pre`. It detects code-source HTML (`pre`, GitHub code tables, multi-line code) before generic table and paragraph deserialization, and CSS `text-align` wins over the legacy `align` attribute. Every paste-html browser test shares this importer, so run the whole file after any change, assert pasted blocks by text and attributes rather than paragraph count, and drive code-source tests through the browser handle's `insertData`. The May 2026 harvest found Chromium's native clipboard flattening Quip-style `<pre>` with `<br>` into paragraphs before the importer saw it. Code: `apps/www/src/app/(app)/examples/plite/_examples/paste-html-import.ts:106`, `apps/plite/tests/plite-browser/donor/examples/paste-html.test.ts:384`. Sources: `solutions/best-practices/2026-05-09-lexical-htmlcopy-harvest-rows-need-whitespace-and-empty-target-boundaries.md`, `solutions/best-practices/2026-05-09-lexical-codeblock-harvest-rows-need-data-transfer-boundaries.md`, `solutions/best-practices/2026-05-09-lexical-paragraph-node-harvest-rows-need-dom-import-splitting.md`, `solutions/best-practices/2026-05-09-lexical-tab-node-harvest-rows-need-clipboard-browser-proof-boundaries.md`.
- **Block boundaries in foreign HTML.** A generic `<div>` is a block boundary even under a `<span>` (`123<div>456</div>` gives two blocks). A `<p>` holding any block child is split: its blocks are lifted and its inline runs become paragraphs, so no block void stays inside that paragraph. Lexical's `<p><img></p>` is the all-block case. Plate's `HtmlPlugin` lifts every block child the schema disallows in a decoded element and keeps each inline run as that element (`liftDisallowedBlocks`, `packages/platejs/src/lib/plugins/html/HtmlPlugin.ts:2228`, `HtmlPlugin.spec.ts:42`). An image that renders can still be nested wrongly, so assert block text arrays and structure. Code: `apps/www/src/app/(app)/examples/plite/_examples/paste-html-import.ts:273`, `:475`, `:647`, `:652`. Sources: `solutions/logic-errors/2026-05-09-block-only-html-paragraphs-must-not-wrap-block-voids.md`, `solutions/logic-errors/2026-05-09-html-div-boundaries-must-survive-inline-wrappers.md`.
- **Word keeps VML shapes inside HTML comments.** In Word clipboard HTML the `<v:shape id o:spid>` markup sits in comments, so DOM queries for `v:shape` find nothing. `getVShapes` scans comment text with a regex for `id` and `o:spid` and drops entries missing either. A refactor back to `querySelectorAll` would silently lose the spid-to-RTF image mapping for pasted Word images. Code: `packages/platejs/src/docx/html/cleanWordHtml.internal.ts:117`, `:225`. Source: `solutions/logic-errors/2026-03-24-docx-vml-shapes-must-be-extracted-from-comment-markup-not-domparser-nodes.md`.

- **Sanitize the whole input before any mapping reads it.** On 2026-09-28 per-element guards left three gaps: a DOCX parent paragraph mapping read a descendant's unsafe `href` before the decoder dropped that descendant, the real video figure mapping read its child's tab-obfuscated `java\tscript:` source before the child's guard ran, and the HTML AST pass trimmed but did not reject embedded control characters. The adopted fix sanitizes live DOM once, before a parent mapping can read descendants, and rechecks emitted attributes at output through one URL role policy. Code: `packages/platejs/src/lib/plugins/html/htmlSafety.ts`, `packages/platejs/src/internal/utils/urlPolicy.ts`, tests `packages/platejs/src/lib/plugins/html/htmlSafety.spec.ts:51`, `:85`, `:328`, `:417`. Source: `docs/research/probes/2026-09-28-conversion-boundary/safety/README.md:23`, `review.md:18-25`.

- **Fix an import rule in the importer, never by intercepting paste.** When Chromium's native clipboard flattened Quip-style `<pre>` with `<br>` into paragraphs, an `onPaste` handler in the paste-html example made that row pass but took the paste away from the runtime clipboard strategy: the runtime's `insert-data` command no longer appeared in the kernel trace, and the generated paste gauntlet failed. The kept fix detects code-source HTML in the importer and proves it through the browser handle's `insertData`, the same DataTransfer boundary as Lexical's `CodeBlock.test.ts`. A native paste policy belongs to the runtime with kernel-trace proof, not to an app importer. The paste-html browser file asserts the `insert-data` trace (`apps/plite/tests/plite-browser/donor/examples/paste-html.test.ts:602-617`) and runs the gauntlet ('runs generated clipboard paste gauntlet without illegal kernel transitions', `:2213`). Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/best-practices/2026-05-09-lexical-codeblock-harvest-rows-need-data-transfer-boundaries.md:29-43`, `:72-89`.

## Markdown and persistence

- **Every built list item needs a boolean `spread`.** `mdast-util-to-markdown` joins a list item's children without a blank line only when that `listItem` has a boolean `spread` (`lib/join.js` in 2.1.2, which `remark-stringify` 11 resolves). A `listItem` without it gets a blank line before its nested list even when the parent list has `spread: false`, so `listToMdastTree` sets `spread` on every list and list item in each code path. The bug showed only in the final markdown string while the mdast helper specs passed. Code: `packages/platejs/src/markdown/lib/serializer/listToMdastTree.ts:92`, `:150`, `:224`, `:247`. Source: `solutions/logic-errors/2026-03-24-markdown-nested-list-tight-spread-missing.md`.
- **Raw Plite `onValueChange` sees one root's children.** Raw Plite `<EditorRoot onValueChange>` passes `snapshot.children` of the provider's root and fires only when those children change, so an edit to meta or another root never reaches it; persist `editor.read.value()` from `onCommit` instead. Plate's `EditorRoot` passes the full `EditorDocumentValue` under the same prop name. Code: `packages/plitejs/src/react/components/plite.tsx:673-698`; Plate side: `content/docs/(guides)/document-meta.mdx:48`. Sources: `plite/reference/public-docs/libraries/plite-react/plite.mdx`, `plite/reference/public-docs/walkthroughs/06-saving-to-a-database.mdx`.
- **A kept source part that copies the body goes stale on edit.** A source-aware DOCX export regenerates the body and keeps passive source parts around it, so a kept part derived from the body carries text the edit removed. Four members surfaced: the hidden Plate envelope at `editor/authored.json` (cut), the package thumbnail and the extended properties at `docProps/app.xml` with their page and word counts (both dropped on edit with a `source-part-omitted` diagnostic of reason `invalidated`, as are the core properties), and a custom property whose `linkTarget` caches bookmarked body text (still carried, so the custom-properties row breaks the rule below until its bug fix lands). `ROOT_PARTS` gives each admitted root relationship one edit disposition: `regenerate`, `carry` or `drop`. The overlay copies only `carry` parts. A new admitted root type needs a disposition before a source holding it can be retained, and a part that copies body content should never be `carry`. A dropped part that a kept header still reaches stays as that header's content and is not reported omitted. To test a candidate, edit a marker string out of the body and search every part of the edited export for it. Code: `packages/platejs/src/docx/internal/sourceEligibility.ts:202`, `:244`, `packages/platejs/src/docx/export/lib/sourcePreservation.ts:594`, `sourcePreservation.spec.ts:304`, `:369`. Source: `docs/plans/2026-10-06-documents-review.md`.
