# Input, IME and event handlers

These lessons come from retired solution notes and Plite references, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`.

## Native input

- **Only line-break placeholders drop the FEFF sentinel.** `ZeroWidthString` sets `includeSentinel = !isLineBreak`. Inline edges, void spacers and mark placeholders keep FEFF because no real-browser IME proof exists for them without it. Earlier failing IME proofs came from proof setup, a root click and a fake void wrapper, and a jsdom composition test could not decide either way. With FEFF, Chromium IME passed on inline edges and voids once the proof set the selection semantically and used the real void spacer. Drop FEFF on another path only after a real-browser IME row for that path. Code: `packages/plitejs/src/react/components/zero-width-string.tsx:7`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-03-br-line-break-placeholders-are-already-bridge-compatible.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-03-jsdom-contenteditable-composition-is-not-a-trustworthy-ime-proof.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-03-legacy-line-break-placeholders-still-keep-feff-until-ime-proof-exists.md`, `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/logic-errors/2026-04-04-plite-no-feff-line-break-placeholders-need-dom-owned-br-interiors.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-04-void-like-zero-width-ime-proofs-need-the-real-void-spacer-structure.md`, `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/logic-errors/2026-04-04-inline-edge-ime-proofs-should-set-selection-semantically-before-composition.md`.
- **OS text substitution flushes native text before the replacement.** Autocapitalize or a double-space period sends a native `insertText` beforeinput, mutates the DOM, then sends a model-owned replacement before the matching `input` event. The runtime keeps the native text as pending model work, flushes it at the next beforeinput, and applies the replacement at its expanded target range, not at the selection after the flush. An expanded `insertText` target range is a replacement even when model selection is preferred. The wrong order rendered `I` or `iSI` instead of `IS`. Code: `packages/plitejs/src/react/editable/runtime-before-input-events.ts:432`, `selection-reconciler.ts`, `apps/plite/tests/plite-browser/donor/examples/plaintext.test.ts:2165`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-beforeinput-substitutions-must-flush-native-text-before-replacement.md`.
- **An inputType-only beforeinput needs its own model command.** `insertTranspose` (Ctrl+T on a Mac) carries its intent in `inputType` with no data. Without a command, Plite blocks the native mutation as model-owned text input and drops the edit silently. Transpose swaps the characters around the caret, the previous two at a text end, and a Ctrl+T keydown fallback covers browsers without the event. When harvesting keyboard rows, look for other inputType-only events. Code: `packages/plitejs/src/react/editable/editing-kernel.ts:794`, `keyboard-input-strategy.ts:1158`. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/logic-errors/2026-05-09-inserttranspose-beforeinput-needs-model-owned-command.md`.
- **iOS Korean Backspace stays with the browser.** On iOS with `ko-KR`, `selectDOMInputDefaultActionPhase` moves delete-backward from keydown to the beforeinput phase, matching Lexical's `IS_IOS && ko-KR` guard. Android Backspace and other iOS Backspace stay model-owned at keydown. Android Backspace is the opposite ownership decision and Lexical's evidence covers only iOS `ko-KR`, so do not widen the guard; removing it lets keydown preempt native Korean input. The contract test proves the phase decision, not behavior on a device. Before porting a mobile or IME row from Lexical or ProseMirror, check whether that editor gave the action to the browser or to itself. Code: `packages/plitejs/src/dom/plugin/dom-input-runtime.ts:328`, `packages/plitejs/test/react/keyboard-input-strategy-contract.test.ts`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-05-07-plite-react-ios-korean-backspace-must-stay-native-owned.md`.
- **Android flushes a stored insert early only for a material `insertText` handler.** On Android, typed text waits as a stored native DOM diff and flushes later. `shouldFlushStoredTextDiffForInsertTextHandler` requests an early flush (`scheduleFlush`) only when `probeCommandNativeEquivalent(editor, editorCommands.insertText, { text })` finds an installed handler that would change the result for that text; handlers that return `false` keep the deferred path, and delete diffs never flush early. Plate input rules count as material only for their trigger characters, which is how markdown triggers reach their handlers in the Android contract tests without the retired app-side `scheduleAndroidMarkdownShortcutFlush`; #4532 still lacks raw-device proof. The probe runs the handler chain read-only on every stored Android text insert, so an `insertText` handler must have no side effects and stay cheap. When a shortcut fails on Android, check the probe result for the typed character instead of adding flush calls. Code: `packages/plitejs/src/react/hooks/android-input-manager/android-input-manager.ts:106`, `:1166`, `packages/plitejs/src/core/command-registry.ts:486`, `packages/plitejs/test/react/android-input-manager-contract.test.ts:341-463`, `packages/platejs/src/react/utils/inputRules.spec.tsx:132-145`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/ledgers/issue-coverage-matrix.md`, `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/plite/ledgers/fork-issue-dossier.md`.
- **Native format commands do nothing in Plate by default.** The `formatBold`, `formatItalic`, `formatUnderline` and `formatStrikeThrough` beforeinput events from the Safari and iOS text menus map to no editor command. The runtime marks them app-owned and passes them to `onDOMBeforeInput`, where the Plite hovering-toolbar example toggles marks; no platejs source outside specs handles a format inputType. The retired matrix rows for #3568 and #3586 called this runtime-owned, which the code contradicts. Code: `packages/plitejs/src/react/editable/editing-kernel.ts:784`, `packages/plitejs/src/dom/plugin/dom-input-runtime.ts:769`, `packages/plitejs/test/react/editing-kernel-contract.ts:160`, `apps/www/src/app/(app)/examples/plite/_examples/hovering-toolbar.tsx:54`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/ledgers/issue-coverage-matrix.md`.

- **TablePlugin needs keyCode 229 to reach its keydown handler.** `TablePlugin`'s `on.keyDown` collapses a multi-cell selection when `event.which === 229` arrives (`packages/platejs/src/react/features/table/TablePlugin.tsx:583-584`), so a filter that withheld IME keys from the Editable's `onKeyDown` would break CJK typing over a cell selection. Specs that call `pipeHandler` directly cannot see such a filter (`packages/platejs/src/react/features/table/TablePlugin.onKeyDown.spec.tsx:537`, `:577`); the rendered case 'collapses a multi-cell selection on IME 229 through EditorContent while an Enter shortcut is bound' (`:71`) does. Plate's shortcut table skips IME-confirm keys for shortcuts only (`packages/platejs/src/react/utils/dispatchPlateShortcut.internal.ts:44-47`, `:55`), which leaves this handler working. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:43`, `:117`; checked 2026-10-08.

- **Plite's hotkey matcher owns keyboard-layout policy, and Plate's platform hotkeys bypass it.** Plite matches `event.key` first, falls back to the physical `event.code` (such as `KeyZ`) only for a single-letter spec when the typed key is non-ASCII, as on a Cyrillic layout, never for a remapped ASCII layout, and refuses a Ctrl+Alt spec while `getModifierState('AltGraph')` is true, because many international layouts type ordinary characters with AltGraph (`packages/plitejs/src/dom/utils/hotkey-match.ts:182-227`; tests `packages/plitejs/test/dom/hotkeys.ts:129`, `:138`, `:194`, `:399`). The May 2026 cut replaced the unmaintained `is-hotkey` in Plite and backfilled its upstream cases for aliases, multiple specs, modifier-only keydown, exact and optional modifiers and invalid grammar. Plate's `createHotkey` still sends its Apple and Windows specs, such as Windows redo `ctrl+y`, through `is-hotkey`'s `isKeyHotkey`, and only its generic specs through Plite's matcher; the `platejs` root exports `is-hotkey`'s curried `isHotkey(spec)(event)` while `platejs/dom` exports Plite's `isHotkey(spec, event)` (`packages/platejs/src/lib/utils/hotkeys.ts:1`, `:11`, `:56-89`, `packages/platejs/src/dom/index.ts:4`). When a shortcut misfires on a non-Latin or AltGraph layout, check which matcher ran. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-03-plite-hotkey-dependency-hard-cuts-need-owned-matchers-and-layout-contracts.md`.

- **A prepared delete command is parsed again after selection import.** The input kernel prepares a typed command before `beforeinput` imports the DOM selection. An insert command's payload is final, so the prepared command wins over stale raw event data; a delete command's shape depends on the selection, so it is parsed again from the synced selection, and an imported expanded selection turns a one-character delete into a fragment delete (`packages/plitejs/src/react/editable/model-input-strategy.ts:306-315`). Tests: `packages/plitejs/test/react/model-input-strategy-contract.test.ts:125` (the prepared insert wins) and `:1148` (the delete is refreshed after import). A kernel refactor classifies each command field by whether it is stable before selection import and keeps the native word-delete browser row in its proof. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-04-30-plite-react-beforeinput-delete-commands-must-refresh-synced-selection.md`.

- **One native input makes one model write.** In May 2026 clicking at the end of DOM-present text and typing `a` produced `aa`: the root's native `input` listener and React `onInput` both repaired the same browser insertion, and only the kernel trace showed one `input` event producing two `insert_text` operations. The runtime now claims each native input event in a `WeakSet`, so the second observer skips its text repair while app `onInput`, deferred operations and history still run (`claimDOMInput`, `packages/plitejs/src/react/editable/runtime-input-events.ts:89-95`). When two listeners see one browser event, tag the event so exactly one path changes model text, and assert operations, model selection and follow-up input, not only final text. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-05-03-plite-react-native-input-and-shell-backed-selection-need-single-owners.md`.

- **IME replacement of a selection is one deferred transaction.** In May 2026 replacing an expanded selection across formatted leaves with a Korean IME composition crashed the Chromium page, duplicated text (`가나다가나다`) or left unformatted DOM text outside the model. Deleting the selection at `compositionstart` let React remove leaves that held Chromium's composition endpoints and split one action into two history entries, so one undo removed only the composed text; publishing at `compositionend` or its microtask ran before Blink released the composition; React rerender alone left a memoized leaf's browser-mutated text; and cleanup outside the owned mutation scope was restored by the DOM integrity observer. Now `compositionstart` changes neither document nor selection, and `compositionend` captures the expanded target and model text and finishes in a `timeout` task inside the composition DOM-mutation owner (`packages/plitejs/src/react/editable/composition-state.ts:366-405`, `runtime-composition-events.ts:61`). Final input wins, the fallback commits only when the model text is unchanged, and deletion, insertion, marks and the collapsed caret land in one transaction, so one undo restores both the text and the expanded selection with no forced merge. Tests: `packages/plitejs/test/react/composition-state-contract.test.ts:223`, `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:2592` (CDP `Input.imeSetComposition`). Assert page health, model text, rendered text, marks, caret and one undo. Sources: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-05-07-plite-react-ime-formatted-selection-needs-native-owned-cleanup.md`, `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-05-07-plite-react-ime-replacement-undo-needs-one-atomic-replacement.md`.

- **Plite promises model-owned input, not native `input` event parity.** Typed text is observable as `beforeinput` with its `insertText` data, and Backspace runs as a model-owned keydown delete command, so an app cannot count on a native `input` event for every operation. `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:1907` ('exposes input intent for start insert, number insert, and delete') proves that contract with a probe on the root and a kernel-trace assertion. In May 2026 Slate #5603 and #5669, which ask for native `input` parity, stayed Related on that row instead of closing on model-owned `beforeinput` tests, while #5826 was promoted to Fixes only once a huge-document row clicked the top block, blurred, scrolled to the end and clicked back in (`apps/plite/tests/plite-browser/donor/examples/huge-document.test.ts:2138`). Name the contract an issue tests before claiming it. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/workflow-issues/2026-05-23-plite-issue-claims-need-exact-browser-proof-and-honest-input-contracts.md`; its Bun path tip is in `.agents/rules/verify/references/commands.md:48-55` and its claim surfaces are retired ledgers.

- **Put an example's text-insertion policy on the command, not only on `onDOMBeforeInput`.** Browser proof rows insert text through the editor handle, not through DOM events, so policy that lives only in a DOM event handler passes native typing and fails the command row. In April 2026 the `inlines` URL wrap and the `markdown-shortcuts` `- ` conversion lived in `onDOMBeforeInput` and failed under `editor.insertText(...)`, and `persistent-annotation-anchors` inserted raw nodes where fragment semantics were expected; one shared input-rule surface fixed the first two. Today those examples register the policy as `handle(editorCommands.insertText, ...)` in a plugin's `commands`, which native input and command rows both reach. Do not switch a row to page-keyboard typing to make it pass, keep the row on the editor handle when the contract is model behavior, and give paste-like or fragment buttons fragment insertion (`tx.fragment.replace`), whose merge and replacement rules raw node insertion skips. When a Firefox synthetic paste row needs the handle fallback, import the DOM selection before `handle.insertData(...)`. Code: `apps/www/src/app/(app)/examples/plite/_examples/markdown-shortcuts.tsx:181`, `apps/www/src/app/(app)/examples/plite/_examples/inlines.tsx:168`, `apps/www/src/app/(app)/examples/plite/_examples/persistent-annotation-anchors.tsx:383`. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/test-failures/2026-04-29-plite-browser-command-rows-must-share-app-text-policy-with-native-input.md`.

- **Chrome's `compositionend` fallback writes the model, so it must clean its own DOM text and stand down when the model already won.** Chrome sends no usable `insertFromComposition` `beforeinput`, so `commitChromeCompositionEndFallback` commits the composed text from `compositionend` and then removes unmanaged composition text under Plite text hosts. In May 2026 two failures came from it. A composition spanning decorated text rendered `alすしすしbeta` while `editor.get.modelText()` returned `alすしbeta`: projection-backed text disables direct DOM text sync, so React left the browser's raw `すし` text node between keyed leaf spans, outside every string wrapper, and a model-only assertion would have passed. After a model-owned command replaced the active composition range, the fallback still appended the `compositionend` data, rendering `---すし` instead of `---`; the first guard, which required a `composition-owned` selection source, then broke decorated composition (`albeta` instead of `alすしbeta`), because real DOM composition can report `dom-current` and must still commit. Pair every overlap-cancel row with an adjacent normal composition row, assert model text, visible text, model selection, DOM caret and the composition trace, look in `editor.get.html()` for raw text outside string wrappers when the DOM duplicates correct model text, and keep the cleanup narrow to text hosts and the committed text. These rows prove Chromium desktop behavior, not Android or iOS keyboards. Code: `packages/plitejs/src/react/editable/composition-state.ts:581-640`, `:702-780`, `:905-914`, `packages/plitejs/test/react/composition-state-contract.test.ts:780`. - **After an Android marked insert, one normalization places the caret.** A collapsed insert with active marks splits the text leaf, so a pending point taken from the pre-diff DOM, such as `[0,0]@2` past the end of a one-character leaf, is valid only after `normalizePoint` walks it onto the new marked sibling at `[0,1]@1`. The scheduled action now passes only `at`, so pending diffs still flush and the normalization owns placement. Normalize a point built from pre-diff DOM once, at its runtime owner, assert selection as well as text in input-manager tests, and do not claim a raw-device fix from the package contract, which says nothing about keyboard visibility. - **Flush deferred native-text repair on input idle, not on a timer started by the first input.** In May 2026 a 150 ms timer started by the first input of a burst flushed while Chrome was still delivering characters and corrupted the native text buffer; a resettable idle timer, reset by every input and backed by a longer maximum guard, did not. ## Handler return contracts

- **What "handled" means differs by layer.** In raw Plite `Editable` event props, `true` means handled (keydown also calls `preventDefault`), `false` forces the built-in handler, and `undefined` counts as handled only if the handler called `preventDefault` or `stopPropagation`. A truthy return from `onDOMBeforeInput` skips the runtime command and also calls `preventDefault`, and a nullish one falls back to `event.defaultPrevented`; without that cancel the browser still inserted the text while Plite recorded the event as handled. Plate's `pipeHandler` runs plugin `on.*` handlers first, where a truthy return stops the chain, then the `EditorContent` prop. For paste, drop and keydown that prop's `undefined` counts as handled only on `stopPropagation`; an `onDOMBeforeInput` prop also counts `preventDefault`. So in Plate, `preventDefault` alone never suppresses the built-in paste, drop or keydown. `docs/vision/plite.md` states the Plate side only in general terms. The exported `isEventHandled` and `isDOMEventHandled` (`packages/plitejs/src/react/components/editable.tsx:844`, `:878`) have no caller. Code: `packages/plitejs/src/react/editable/keyboard-input-strategy.ts:418-436`, `clipboard-input-strategy.ts:107-126`, `runtime-before-input-events.ts:72`, `packages/platejs/src/react/utils/pipeHandler.internal.ts:62-90`, `:134`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/libraries/plite-react/event-handling.mdx`, `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/libraries/plite-react/editable.mdx`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/test-failures/2026-05-20-plite-integration-local-editor-stacking-and-project-scope-failures.md`.
- **Native input listeners attach once.** The root `beforeinput` and `input` listeners read the latest app handlers from runtime state (`this.nativeInputHandlers`). App event props need no `useMemo` or `useCallback`, examples should not teach memoizing them, and listener wiring must never depend on callback identity. Code: `packages/plitejs/src/react/editable/editable-dom-runtime.ts:1215-1248`. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/developer-experience/2026-05-14-plite-react-native-beforeinput-formatting-needs-semantic-command-handlers.md`.

## Input rules

- **A mark rule's closing delimiter must sit right before the caret.** The July 2026 input-rule repair found the migrated matcher searching backward for delimiters too broadly, so a delimiter typed earlier, with unrelated text between it and the new trigger, could complete a mark; the fix limited the broad search (`skipInvalid: true`) to the opening delimiter. Source: `c70bacbd4a:docs/plans/2026-07-01-plate-next-create-input-rules-drift.md:34-37`. Current `createMarkInputRule` reads `end` with `editor.read.points.before(selection, { matchString })` and no `skipInvalid`, and reads `start` with `skipInvalid: true` (`packages/platejs/src/lib/plugins/input-rules/createInputRules.ts:44-66`). 'does not match non-adjacent closing mark delimiters' (`packages/platejs/src/react/utils/inputRules.spec.tsx:808`) configures `start: '**'`, `end: '*'`, `trigger: '*'`, types the trigger after `**hello* nope` and expects the literal `**hello* nope*`. The public guide describes `end` only as an optional closing delimiter and never says it must be adjacent (`content/docs/(guides)/plugin-input-rules.mdx:775-777`). Keep a non-adjacent negative case beside each delimiter rule's positive cases; this is package matcher proof, not browser input.

- **Match text across leaves through the Plite traversal.** The July input-rule migration found that a Plate-local point-before helper hid a traversal gap and missed multi-leaf matching. Move that scan into Plite rather than giving each input rule its own string walker. Current `packages/plitejs/src/editor/before.ts:66-210` accumulates text across leaf boundaries, skips empty boundary steps and stops at the containing block. The fixture `packages/plitejs/test/interfaces/Editor/before/after-match-multiple-leaves.tsx` splits `**` across two leaves and expects the point after the match at `[0, 1]`, offset 1. Plate calls these matching options directly in `packages/platejs/src/lib/plugins/input-rules/createInputRules.ts:44-66`. Source: `docs/plans/2026-07-01-plate-next-input-rules-before-api.md:240`, with the failure explanation at :246. Limit: current source and fixture inspected; no test rerun.
