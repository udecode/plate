# Selection, navigation and delete

These lessons come from retired solution notes and Plite references, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`.

## Navigation

- **Character navigation has one owner chain.** `Editor.positions` feeds `before` and `after`, and `selection.move` and character delete reuse them. `positions` gives a selectable void or read-only element one atomic stop (`voids: true` enters its children), and an inline void two stops per crossing, into the atom and out of it. Fix an arrow that skips or overshoots in `positions`, not in React keydown or an example: `unit: 'offset'` tests passed while ArrowLeft and ArrowRight overshot mentions, and a React-side patch would leave two truths for cursor motion. Code: `packages/plitejs/src/editor/positions.ts:55`, `packages/plitejs/src/transforms-selection/move.ts:39`, `packages/plitejs/test/query-contract.ts:2342`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-07-plite-move-should-reuse-before-after-location-seam.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-26-plite-selectable-voids-should-be-atomic-navigation-points.md`.
- **`positions` groups by text block, not by top-level index.** It groups character segments by the nearest non-inline element that holds inlines (`getTextBlockPath`). Grouping by `path[0]` flattened a whole table into one text stream, so ArrowRight from an empty first cell landed at offset 1 of the next cell. Every nested text-block family, such as table cells and columns, needs a start stop per block; the table browser rows covered Enter and Backspace in a cell but not horizontal movement between cells. Code: `packages/plitejs/src/editor/positions.ts:147`, `packages/plitejs/test/query-contract.ts:3522`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-27-plite-positions-must-group-character-navigation-by-text-block-boundaries.md`.
- **Table arrows leave a cell in keydown.** When ArrowUp, ArrowDown or a one-cell Shift+Arrow leaves a cell, `TablePlugin`'s `on.keyDown` handles it and calls `preventDefault`. Letting native selection move first and repairing it at apply time drew a caret or text range in the source cell for one frame. The visual-line edge test compares the client rects of a collapsed caret range with those of the block's range, because model paths cannot see soft wraps; without DOM ranges it falls back to the model block edge, and plain and shifted arrows share one `shouldMove` helper. The `EDIT-TABLE-ARROW*-MULTIBLOCK-001` rows state the outcome but not this ownership. Code: `packages/platejs/src/react/features/table/TablePlugin.tsx:500-640`, `TablePlugin.navigation.spec.tsx:569-749`. Sources: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/logic-errors/2026-03-29-table-arrow-navigation-must-own-moveline-and-visual-line-boundaries.md`, `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/logic-errors/2026-03-31-table-shift-arrow-selection-must-own-keydown-before-native-selection.md`.

- **Around a selectable void, test plain, vertical and Shift-extended movement apart.** Plain ArrowLeft and ArrowRight through an image were already model-owned and green in April 2026, while the other two paths split DOM from model. Shift+ArrowRight before an image let the browser extend to wrapper elements while the model stayed collapsed, and a second press moved the model into the image while DOM focus had already passed it; horizontal Shift movement needs no browser layout, so it is model-owned and runs as a focus-edge move, which the kernel still classifies as `move-selection` with `axis: 'horizontal'` and `extend: true`. ArrowDown from the end of the paragraph before an image put the DOM caret in the image spacer at `[1,0]@0` while the model stayed at `[0,0]@113`, so the image did not render selected; the first `selectionchange` came before Chrome settled the selection around the zero-width spacer, and the fix imported the settled DOM selection after the keydown's default action. Browser rows for selectable voids assert model selection, DOM selection and the visible selected state. Code: `packages/plitejs/src/react/editable/editing-kernel.ts:913-923`, `:982-993`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-04-27-plite-react-void-keyboard-navigation-needs-post-native-sync-and-shift-model-ownership.md`. Limit: the April fix's post-keydown `setTimeout` import is gone (no `setTimeout(` call under `packages/plitejs/src/react/editable` on 2026-10-08), and how today's runtime settles a native vertical move into a void was not traced.

- **Quote shorthand wraps the matched block, not a broader inferred selection.** July Basic Nodes tests failed when blockquote shorthand wrapped the wrong structural target; targeting the current block preserved nested quotes. Source: `docs/plans/2026-07-06-plate-next-basic-nodes-package-review.md:444-445`, with the repair recorded at line 456. Current `packages/platejs/src/features/basic-nodes/lib/BaseBlockPlugins.ts:59` calls `tx.nodes.wrap` with `at: match.blockPath`. The behavior law already permits same-type quote nesting under Block Shorthand Autoformat; this lesson records the targeting mechanism that keeps that behavior.

- **Repair generic selection mapping at the structural transform owner.** July blockquote reverse-Tab proof exposed missing selection remapping during child replacement. The repair belonged in Plite's replacement transform, while the quote gesture remained feature behavior. Source: `docs/plans/2026-07-06-plate-next-basic-nodes-package-review.md:449-451`; line 461 records package proof after that repair. Current `packages/plitejs/src/transforms-node/replace-children.ts:64` maps retained selection endpoints by locating their node references in the replacement children. This mapping has conditions: retained endpoints must be inside the replaced range and their referenced nodes must survive; callers can supply `newSelection` explicitly.

- **Resolve a mutable node path when the action executes.** July `useRemoveNodeButton` subscribed to a path used only by its click handler. The repair read the path on click, and its regression case moved the node before clicking. Source: `c70bacbd4a:docs/plans/2026-07-06-plate-next-callback-subscription-perf-guard.md:453-464`; the regression is described at line 358. Subscribe when rendering or effects need the value; callback-only state should be obtained at execution. The hook and its old lookup API are now retired, so this is historical repair evidence rather than a claim that today's hook reproduces the bug. Current Plite structural mapping still treats paths as mutable, as shown by `packages/plitejs/src/transforms-node/replace-children.ts:64`.

- **No selection is neither collapsed nor expanded.** The July Utils hook used `!selection.isCollapsed()` and therefore treated an absent selection as expanded. The repair used an explicit Plite predicate and moved within/across-block semantics to Plite. Source: `docs/plans/2026-07-06-plate-next-useselection-review.md:71-72`. Current `packages/plitejs/src/core/public-state.ts:3896` returns false from `isExpanded` when selection is absent, and `packages/plitejs/test/state-query-contract.ts:130` asserts false for collapsed, expanded, within-block and across-block predicates with no selection. The old React hook is retired; use the explicit predicates rather than assuming collapsed and expanded exhaust every state.

- **Compare ordered endpoints when direction must not change a command.** Column Select All once escalated a fully selected column only for a forward selection. Comparing `RangeApi.edges(selection)` against the column's start and end fixes the direction dependence. Current Plate retains that comparison (`packages/platejs/src/features/layout/lib/BaseColumnPlugin.ts:100-126`) and a backward full-column regression (`BaseColumnPlugin.spec.ts:454`). Source: `docs/plans/2026-07-12-plate-next-layout-link-legacy-list-package-reviews.md:681`. This is model-command proof; it does not establish browser shortcut behavior.

- **A working child editor does not prove navigation across its boundary.** In the May Plite draft, clicking and arrowing inside the editable-void child root already passed, while ArrowRight from the preceding paragraph left child selection null. The example had rendered a child root without declaring its slot to the navigation schema. Add a separate boundary-entry/exit row before changing the runtime; native controls must not become document-flow roots merely because they share the island. Source: `docs/plans/2026-05-25-plite-editable-void-keyboard-click-navigation.md:121-144`. Today's example declares `contentRoots.body` with `void: 'block'` (`apps/www/src/app/(app)/examples/plite/_examples/editable-voids.tsx:111-123`), and `packages/plitejs/src/react/editable/content-root-owners.ts` discovers owners through compiled schema declarations. The distinct focused-child and boundary browser rows remain at `apps/plite/tests/plite-browser/donor/examples/editable-voids.test.ts:683` and `:782`. Limit: the old singular `contentRoot` and `editable-island` syntax is retired; no browser tests were rerun.

- **Yielding movement to the browser also requires timely model selection import.** An April experiment made collapsed horizontal movement native-owned. ArrowLeft moved the visible caret but left the model at offset eight instead of seven, so the experiment was reverted. Current movement tracing still distinguishes model-owned horizontal compatibility from native vertical layout (`packages/plitejs/src/react/editable/editing-kernel.ts:976-1006`). Source: `docs/plans/2026-04-24-plite-selection-caret-conformance-kernel-plan.md:2466-2540`. Limit: the rejection concerns that draft movement experiment; it does not establish that every horizontal context must always be model-owned or prove native mobile keyboard behavior.

- **Share visible-order invariants before repairing each example.** The May 2026 multi-root, synced-block and hidden-content review found navigation, projected selection, command targeting and DOM coverage sharing responsibility for visible order. The useful repair boundary was shared rooted-point, segmentation and target logic rather than route-local keyboard patches. Current packages/plitejs/src/react/view-boundary-graph-core.ts defines graph nodes and owner identity; view-selection.ts:98-114 derives selection segments from the graph, and editable/content-root-owners.ts:424-432 constructs the graph for navigation. Source: c70bacbd4a:docs/plans/2026-05-26-plite-unified-view-boundary-navigation-architecture.md:169-191. Limit: the later dry-view-boundary-runtime plan retained separate DOMCoverage policy ownership; these reads do not establish one universal graph for every hidden-content policy or fresh browser parity.

- **A repeated projection needs an explicit command-target failure.** A visible selection through repeated copies of one root can map ambiguously onto model ranges. Preserve projection identity and report ambiguity before applying a destructive command. Current packages/plitejs/src/react/editable/projected-selection-target.ts:15-37 distinguishes ambiguous, stale and target results, checking repeated-root ambiguity before resolving ranges; view-boundary-graph.ts:181,229 owns the shared checks and target construction. Source: c70bacbd4a:docs/plans/2026-05-26-plite-unified-view-boundary-navigation-architecture.md:192. Limit: this is an internal resolution contract; its convenience wrapper still returns null for either failure, and no browser behavior was rerun.

- **A classified input command needs an executor for every selection representation.** The May 2026 fork draft classified move-selection in keydown but declined it in the private executor for projected and content-root selections. Sharing content-root navigation with command execution closed that gap before the ordinary root-local fallback. Current `packages/plitejs/src/react/editable/mutation-controller.ts:756-769` still tries `applyContentRootSelectionMoveCommand` before `applyRootLocalSelectionMoveCommand`. Source: `c70bacbd4a:docs/plans/2026-05-29-plite-command-behavior-pipeline-architecture.md:676`; projected-command and content-root-navigation contracts were the focused proof. Limit: classification alone never proves the resulting movement.

- **An undo symptom can originate in the split that history records.** The marked-Enter undo investigation found an unwanted empty leaf before the moved bold word, so the repair belonged to core splitting rather than a public mark-restoration API or React focus repair. The surviving test splits `hey ` before bold `you`, asserts the exact two paragraphs and caret at `[1,0]@0`, then compares the complete visible state after undo with its saved pre-split state (`packages/plitejs/test/history/history-contract.ts:2167`). Current splitting retains dedicated text-boundary and forward-anchor handling in `packages/plitejs/src/transforms-node/split-nodes.ts:368-412`; its conditions have evolved, so the plan's original algorithm wording is historical. Source: `c70bacbd4a:docs/plans/2026-05-07-plite-marked-enter-undo-caret-ralplan.md:509-524`. This is package proof, not browser or collaborative-undo certification.

- **A hidden-content guard must find the next legal point instead of freezing navigation.** The May guard restored the previous selection whenever movement entered hidden content, preventing both unsafe entry and legitimate progress. Current `packages/plitejs/src/dom/plugin/dom-coverage.ts:727` walks beyond covered ranges, tracking `boundaryId:rangeIndex` so several ranges in one boundary do not falsely stop the walk. `react/editable/caret-engine.ts:321-349` collapses ordinary movement and preserves the original anchor for extension. Source: `c70bacbd4a:docs/plans/2026-05-26-plite-arrow-right-paragraph-edge.md:128-151`. The historical boundary policy is now named skip; materialization remains a separate policy.

## Delete

- **`unit: 'character'` has one boundary source.** `getCharacterDistance` serves measurement, `before`/`after` movement and deletion, so reverse delete removes a whole grapheme (Tamil ni, Thai clusters). Legacy Slate's partial combining-mark delete came from a reverse-only branch that was removed on purpose. Distance tests passed while delete diverged, so every new text-unit row needs a delete case too. Code: `packages/plitejs/test/text-units-contract.ts:537`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-plite-character-delete-must-share-text-unit-boundaries.md`.
- **A collapsed delete classifies a structural target before the character walk.** Backspace at the start of an empty editable inline path-deletes the inline. A collapsed delete that reaches an adjacent void or read-only element path-deletes only that atom and keeps the caret through an anchor taken before the removal. A character-range delete there removed the preceding character (#5972: `an !` became `an!`) or removed several adjacent voids in one keypress. The model selection was already right; the native FEFF offset 1 misled a browser-first diagnosis. Code: `packages/plitejs/src/transforms-text/delete-text-collapsed-path-targets.ts:19`, `delete-text-plan.ts:68`, `packages/plitejs/test/delete-contract.ts:1592`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-07-plite-empty-inline-backspace-must-path-delete-the-inline.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-plite-adjacent-block-void-delete-must-path-delete-one-target.md`.
- **An expanded delete removes a selected inline only when the range crosses out of it.** A delete wholly inside an inline keeps the empty shell. Caret placement after a delete splits by shape: a range crossing into a surviving inline, a collapsed forward delete at a text end just before an inline, or staying on the spacer. One generic jump-to-next-inline rule kept moving the failure between range rows and point rows; the legacy `transforms/delete` fixture suite catches it and the local package tests did not. Code: `packages/plitejs/src/transforms-text/delete-text-removal.ts:116`, `delete-text-inline-points.ts:91`, `packages/plitejs/test/delete-contract.ts:489`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-14-plite-delete-selection-normalization-must-distinguish-inline-spacers-from-inline-targets.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-expanded-delete-across-inline-boundaries-must-remove-crossed-inline-ancestors.md`.
- **Delete cleanup stays inside its own prune scope.** `removeEmptyStructuralArtifacts` skips nested blocks outside that scope, because empty table cells, list items and quotes are valid structure. A Backspace after a table once deleted an empty first cell, leaving rows of 3, 4 and 4 cells. Assert row cell counts in the model and the browser, since text assertions miss a ragged table, and treat any whole-document cleanup pass after a transform as suspect. Code: `packages/plitejs/src/transforms-text/delete-text-structural-cleanup.ts:207`, `packages/plitejs/test/delete-contract.ts:1363`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-06-plite-delete-cleanup-must-not-remove-valid-nested-empty-blocks.md`.
- **Delete-fragment commands carry the event-time selection.** The browser delete event can collapse or move the live DOM selection before the model command runs, so the command holds `command.selection`. A triple-click gives a hanging range from block start to the next block start, and Backspace must delete the whole block; it once only emptied the paragraph (#5847). Code: `packages/plitejs/src/react/editable/editable-command-types.ts:13`, `mutation-controller.ts:866`, `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:7310`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-06-plite-react-triple-click-delete-needs-full-block-selection-intent.md`.
- **A full-document delete keeps the first block, emptied.** When that block is a plain paragraph, the result is one empty paragraph and any list shells after it vanish (#2500). When the first block is structured, such as a table, the full-document fast path is skipped and the emptied table survives as the only block. `markdown-editing-spec.md` has no select-all delete row, so a core test pins the table case and nobody chose it as product behavior. Code: `packages/plitejs/test/delete-contract.ts:889`, `:1302`, `:1331`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/ledgers/issue-coverage-matrix.md`.

- **Backspace after empty paragraphs removes one block.** At the start of a top-level block whose previous sibling is an empty, non-void, editable block, a collapsed Backspace path-deletes that one block (`getPreviousEmptyBlockPathAtBlockStart`, `packages/plitejs/src/transforms-text/delete-text-collapsed-path-targets.ts:58-102`). In May 2026, repeated Enter at a document start then Backspace removed every preceding empty paragraph, and Enter, Space, Enter, Backspace erased unrelated earlier empty paragraphs, because the delete ran as a hanging-range cleanup followed by a top-level empty-block sweep. The guard applies to top-level blocks only, and merging a whitespace-only paragraph keeps its cleanup inside the delete range. Tests: `packages/plitejs/test/delete-contract.ts:1403`, `:1444`, `:1472`. They call `tx.text.deleteBackward()`; no browser row presses Enter, Space, Enter, Backspace, the native path the source says programmatic coverage misses. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-21-plite-layout-source-entry-and-paged-editable-dx.md`.

- **A block-start-to-block-start selection excludes its end block.** Deleting a range from the start of block N to the start of sibling block N+2 removes blocks N and N+1 whole and leaves N+2 intact; a range that ends at a block's end includes that block. In May 2026 the model-owned full-block delete fast path removed only block N for such a range, and a narrowed fix fell through to generic text deletion and left an empty heading; the `huge-document-cut` stress family caught it by asserting which block shifted into the cut position (`apps/plite/tests/plite-browser/donor/stress/generated-editing.test.ts:180-184`). The `fragment.delete` editor command, given a range, now collects every fully selected sibling block (`getFullySelectedSiblingBlockPaths`, `packages/plitejs/src/core/editor-commands.ts:249-325`) and removes them with one `tx.nodes.replaceChildren` (`:654-721`). A delete fast path classifies the selection geometry first (same block, adjacent sibling, several siblings, partial text), and its tests include a multi-block start-to-start row; asserting only that a delete command ran misses this. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-plite-full-block-delete-fast-path-must-stop-at-selection-boundaries.md:23-91`.

- **Outdenting out of a list clears its list metadata.** The July cleanup proved root-bullet Backspace through the rendered list demo and recorded removal of list-only metadata, not merely a change of indentation (`docs/plans/2026-07-24-plate-next-list-owner-cleanup.md:335-336,349-350`). The current outdent owner passes `checked`, `listRestart`, `listStart`, `listStyle` and `listType` as properties to unset when indentation leaves the list (`packages/platejs/src/features/list/lib/BaseListPlugin.ts:1401-1414`). Keep the metadata assertion beside the visible plain-block assertion when changing outdent behavior. Limit: the browser result belongs to the July run; this compilation checked current source without replaying the gesture.

- **Cross-block deletion reuses the structural merge owner.** The April editor-method sweep removed a private block-merge implementation because it duplicated nested-container handling, identity preservation and selection rebasing (docs/plans/2026-04-26-plite-core-editor-method-regression-sweep.md:25). Today's mergeBlocksAtPoint remains a thin call to mergeNodes with the point, hanging and voids options (packages/plitejs/src/transforms-text/delete-text.ts:1280-1289). Keep delete planning responsible for choosing the merge, and the structural primitive responsible for performing it. Limit: this does not establish exhaustive correctness for every nested or void combination.

- **Skipping an atom during caret movement must not consume neighboring text during deletion.** Date's arrow fix set `selectable: false`, exposing collapsed deletion's assumption that a traversed boundary also consumed a character. Current `packages/plitejs/src/transforms-text/delete-text.ts:1195-1210` separately inspects offset positions for an adjacent noneditable atom before applying text-boundary expansion; `packages/platejs/src/features/date/lib/BaseDatePlugin.ts:71` owns Date's selectability. Source: `docs/plans/5125-5126-date-navigation-and-comment-activation-regression.md:568-570`, with the architecture decision at lines 642-654. Limit: arrow policy and destructive-input range selection have different owners; Date-specific key or delete overrides would conceal the generic failure.

## DOM selection import and ownership

- **A DOM selection is imported only when both endpoints belong to this editor.** Both anchor and focus must pass `hasSelectableTarget`, and the runtime skips `beforeinput` target ranges while the live selection crosses editor ownership. A nested editor sits inside the parent's void DOM but owns its own endpoints; typed text once replaced a parent range built from a cross-editor selection (`Outer u`, from the Lexical harvest). A model-handle select does not prove this. Prove it with a real native Range from outside to inside and from parent to nested plus a `selectionchange` event, assert no runtime errors, then refocus and type. Code: `packages/plitejs/src/react/editable/selection-controller.ts:555-565`, `selection-reconciler.ts:579-583`, `:660-667`, `apps/plite/tests/plite-browser/donor/examples/editable-voids.test.ts:1381`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-06-plite-react-foreign-dom-selections-must-be-ignored-before-import.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-parent-nested-dom-selections-must-not-import-as-parent-ranges.md`.
- **Controls inside the editor root are native-owned at every root event boundary.** This covers input, textarea, select, button, `[role=button]`, nested editor roots and `contenteditable=false` chrome. Keyboard and input paths stop propagation, native `beforeinput` and `input` use `stopImmediatePropagation` because WebKit kept routing them otherwise, and their keydown yields no editor command. The outer selection comes back on the control's blur without pointer intent, never on its focus, which would steal focus before typing. A raw `root.focus()` after typing in a void's input could send keys into a nested editor, and behavior rows missed shell buttons being classed as native-owned; `assertNoIllegalKernelTransitions` catches that. Code: `packages/plitejs/src/react/editable/input-controller.ts:168`, `runtime-before-input-events.ts:484`, `runtime-focus-mouse-events.ts:115`, `interaction-owner.ts:49`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-22-plite-react-internal-controls-must-be-native-owned.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-23-plite-react-shell-buttons-must-be-internal-targets.md`, `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/logic-errors/2026-04-24-plite-browser-proof-must-separate-model-owned-handles-root-selection-and-usable-focus.md`.
- **`selectionchange` is a hot path.** The runtime throttles it, and the controller classifies ownership with fixed string reasons and cheap root and containment checks before any DOM-to-model conversion. The event fires on user action and on runtime repair, so a bridge that scans the DOM or allocates a rich reason object per event slows typing and selection. Classifier reasons stay private; Plate, Yjs and cursor overlays get only a model Range or null. Code: `packages/plitejs/src/react/editable/runtime-selection-engine.ts:173`, `selection-controller.ts:538`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-05-08-dom-selection-bridges-must-stay-cheap-on-selectionchange.md`.
- **Writes from outside the editor pass `ReactUpdatePolicy.preserveSelection`.** A title field, sidebar input or toolbar text box that must not move DOM selection, steal focus or scroll passes this policy from `platejs/react`. It adds the tags `skip-dom-selection`, `skip-selection-focus` and `skip-scroll-into-view`; `useSetStateField` adds them itself, and `YjsUpdatePolicy.remote` bundles them with `collaboration`, `remote-yjs-import` and `history-skip` for host adapters. No public doc names the policy; `document-meta.mdx` says only "selection-preservation tags", and the old name `PliteReactUpdatePolicy` no longer exists. Code: `packages/plitejs/src/react/update-policy.ts:14`, `packages/plitejs/src/react/hooks/use-state-field.ts:63`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/07-editor.mdx`, `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/14-document-state.mdx`.

- **Do not port another editor's selection debounce or drag hack.** ProseMirror delays its DOM selection sync during a Chrome mouse drag and toggles `draggable` and `contentEditable` around drags (`ProseMirror/prosemirror-view@ca4c78e9b56f1b164c0b3758b59d8748f11b7534:src/selection.ts:55-70`, `src/input.ts:346-370`). That code shows drag selection is browser-specific and subtle. It does not justify adding a hidden debounce to Plite, which proves drag as browser race behavior in dedicated rows instead.
