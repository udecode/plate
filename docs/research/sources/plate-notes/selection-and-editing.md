# Selection, navigation and delete

These lessons come from retired solution notes and Plite references, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`.

## Navigation

- **Character navigation has one owner chain.** `Editor.positions` feeds `before` and `after`, and `selection.move` and character delete reuse them. `positions` gives a selectable void or read-only element one atomic stop (`voids: true` enters its children), and an inline void two stops per crossing, into the atom and out of it. Fix an arrow that skips or overshoots in `positions`, not in React keydown or an example: `unit: 'offset'` tests passed while ArrowLeft and ArrowRight overshot mentions, and a React-side patch would leave two truths for cursor motion. Code: `packages/plitejs/src/editor/positions.ts:55`, `packages/plitejs/src/transforms-selection/move.ts:39`, `packages/plitejs/test/query-contract.ts:2342`. Sources: `solutions/logic-errors/2026-04-07-plite-move-should-reuse-before-after-location-seam.md`, `solutions/logic-errors/2026-04-26-plite-selectable-voids-should-be-atomic-navigation-points.md`.
- **`positions` groups by text block, not by top-level index.** It groups character segments by the nearest non-inline element that holds inlines (`getTextBlockPath`). Grouping by `path[0]` flattened a whole table into one text stream, so ArrowRight from an empty first cell landed at offset 1 of the next cell. Every nested text-block family, such as table cells and columns, needs a start stop per block; the table browser rows covered Enter and Backspace in a cell but not horizontal movement between cells. Code: `packages/plitejs/src/editor/positions.ts:147`, `packages/plitejs/test/query-contract.ts:3522`. Source: `solutions/logic-errors/2026-04-27-plite-positions-must-group-character-navigation-by-text-block-boundaries.md`.
- **Table arrows leave a cell in keydown.** When ArrowUp, ArrowDown or a one-cell Shift+Arrow leaves a cell, `TablePlugin`'s `on.keyDown` handles it and calls `preventDefault`. Letting native selection move first and repairing it at apply time drew a caret or text range in the source cell for one frame. The visual-line edge test compares the client rects of a collapsed caret range with those of the block's range, because model paths cannot see soft wraps; without DOM ranges it falls back to the model block edge, and plain and shifted arrows share one `shouldMove` helper. The `EDIT-TABLE-ARROW*-MULTIBLOCK-001` rows state the outcome but not this ownership. Code: `packages/platejs/src/react/features/table/TablePlugin.tsx:500-640`, `TablePlugin.navigation.spec.tsx:569-749`. Sources: `solutions/logic-errors/2026-03-29-table-arrow-navigation-must-own-moveline-and-visual-line-boundaries.md`, `solutions/logic-errors/2026-03-31-table-shift-arrow-selection-must-own-keydown-before-native-selection.md`.

## Delete

- **`unit: 'character'` has one boundary source.** `getCharacterDistance` serves measurement, `before`/`after` movement and deletion, so reverse delete removes a whole grapheme (Tamil ni, Thai clusters). Legacy Slate's partial combining-mark delete came from a reverse-only branch that was removed on purpose. Distance tests passed while delete diverged, so every new text-unit row needs a delete case too. Code: `packages/plitejs/test/text-units-contract.ts:537`. Source: `solutions/logic-errors/2026-05-09-plite-character-delete-must-share-text-unit-boundaries.md`.
- **A collapsed delete classifies a structural target before the character walk.** Backspace at the start of an empty editable inline path-deletes the inline. A collapsed delete that reaches an adjacent void or read-only element path-deletes only that atom and keeps the caret through an anchor taken before the removal. A character-range delete there removed the preceding character (#5972: `an !` became `an!`) or removed several adjacent voids in one keypress. The model selection was already right; the native FEFF offset 1 misled a browser-first diagnosis. Code: `packages/plitejs/src/transforms-text/delete-text-collapsed-path-targets.ts:19`, `delete-text-plan.ts:68`, `packages/plitejs/test/delete-contract.ts:1592`. Sources: `solutions/logic-errors/2026-05-07-plite-empty-inline-backspace-must-path-delete-the-inline.md`, `solutions/logic-errors/2026-05-09-plite-adjacent-block-void-delete-must-path-delete-one-target.md`.
- **An expanded delete removes a selected inline only when the range crosses out of it.** A delete wholly inside an inline keeps the empty shell. Caret placement after a delete splits by shape: a range crossing into a surviving inline, a collapsed forward delete at a text end just before an inline, or staying on the spacer. One generic jump-to-next-inline rule kept moving the failure between range rows and point rows; the legacy `transforms/delete` fixture suite catches it and the local package tests did not. Code: `packages/plitejs/src/transforms-text/delete-text-removal.ts:116`, `delete-text-inline-points.ts:91`, `packages/plitejs/test/delete-contract.ts:489`. Sources: `solutions/logic-errors/2026-04-14-plite-delete-selection-normalization-must-distinguish-inline-spacers-from-inline-targets.md`, `solutions/logic-errors/2026-05-09-expanded-delete-across-inline-boundaries-must-remove-crossed-inline-ancestors.md`.
- **Delete cleanup stays inside its own prune scope.** `removeEmptyStructuralArtifacts` skips nested blocks outside that scope, because empty table cells, list items and quotes are valid structure. A Backspace after a table once deleted an empty first cell, leaving rows of 3, 4 and 4 cells. Assert row cell counts in the model and the browser, since text assertions miss a ragged table, and treat any whole-document cleanup pass after a transform as suspect. Code: `packages/plitejs/src/transforms-text/delete-text-structural-cleanup.ts:207`, `packages/plitejs/test/delete-contract.ts:1363`. Source: `solutions/logic-errors/2026-05-06-plite-delete-cleanup-must-not-remove-valid-nested-empty-blocks.md`.
- **Delete-fragment commands carry the event-time selection.** The browser delete event can collapse or move the live DOM selection before the model command runs, so the command holds `command.selection`. A triple-click gives a hanging range from block start to the next block start, and Backspace must delete the whole block; it once only emptied the paragraph (#5847). Code: `packages/plitejs/src/react/editable/editable-command-types.ts:13`, `mutation-controller.ts:866`, `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:7310`. Source: `solutions/logic-errors/2026-05-06-plite-react-triple-click-delete-needs-full-block-selection-intent.md`.
- **A full-document delete keeps the first block, emptied.** When that block is a plain paragraph, the result is one empty paragraph and any list shells after it vanish (#2500). When the first block is structured, such as a table, the full-document fast path is skipped and the emptied table survives as the only block. `markdown-editing-spec.md` has no select-all delete row, so a core test pins the table case and nobody chose it as product behavior. Code: `packages/plitejs/test/delete-contract.ts:889`, `:1302`, `:1331`. Source: `plite/ledgers/issue-coverage-matrix.md`.

- **Backspace after empty paragraphs removes one block.** At the start of a top-level block whose previous sibling is an empty, non-void, editable block, a collapsed Backspace path-deletes that one block (`getPreviousEmptyBlockPathAtBlockStart`, `packages/plitejs/src/transforms-text/delete-text-collapsed-path-targets.ts:58-102`). In May 2026, repeated Enter at a document start then Backspace removed every preceding empty paragraph, and Enter, Space, Enter, Backspace erased unrelated earlier empty paragraphs, because the delete ran as a hanging-range cleanup followed by a top-level empty-block sweep. The guard applies to top-level blocks only, and merging a whitespace-only paragraph keeps its cleanup inside the delete range. Tests: `packages/plitejs/test/delete-contract.ts:1403`, `:1444`, `:1472`. They call `tx.text.deleteBackward()`; no browser row presses Enter, Space, Enter, Backspace, the native path the source says programmatic coverage misses. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-21-plite-layout-source-entry-and-paged-editable-dx.md`.

## DOM selection import and ownership

- **A DOM selection is imported only when both endpoints belong to this editor.** Both anchor and focus must pass `hasSelectableTarget`, and the runtime skips `beforeinput` target ranges while the live selection crosses editor ownership. A nested editor sits inside the parent's void DOM but owns its own endpoints; typed text once replaced a parent range built from a cross-editor selection (`Outer u`, from the Lexical harvest). A model-handle select does not prove this. Prove it with a real native Range from outside to inside and from parent to nested plus a `selectionchange` event, assert no runtime errors, then refocus and type. Code: `packages/plitejs/src/react/editable/selection-controller.ts:555-565`, `selection-reconciler.ts:579-583`, `:660-667`, `apps/plite/tests/plite-browser/donor/examples/editable-voids.test.ts:1381`. Sources: `solutions/logic-errors/2026-05-06-plite-react-foreign-dom-selections-must-be-ignored-before-import.md`, `solutions/logic-errors/2026-05-09-parent-nested-dom-selections-must-not-import-as-parent-ranges.md`.
- **Controls inside the editor root are native-owned at every root event boundary.** This covers input, textarea, select, button, `[role=button]`, nested editor roots and `contenteditable=false` chrome. Keyboard and input paths stop propagation, native `beforeinput` and `input` use `stopImmediatePropagation` because WebKit kept routing them otherwise, and their keydown yields no editor command. The outer selection comes back on the control's blur without pointer intent, never on its focus, which would steal focus before typing. A raw `root.focus()` after typing in a void's input could send keys into a nested editor, and behavior rows missed shell buttons being classed as native-owned; `assertNoIllegalKernelTransitions` catches that. Code: `packages/plitejs/src/react/editable/input-controller.ts:168`, `runtime-before-input-events.ts:484`, `runtime-focus-mouse-events.ts:115`, `interaction-owner.ts:49`. Sources: `solutions/logic-errors/2026-04-22-plite-react-internal-controls-must-be-native-owned.md`, `solutions/logic-errors/2026-04-23-plite-react-shell-buttons-must-be-internal-targets.md`, `solutions/logic-errors/2026-04-24-plite-browser-proof-must-separate-model-owned-handles-root-selection-and-usable-focus.md`.
- **`selectionchange` is a hot path.** The runtime throttles it, and the controller classifies ownership with fixed string reasons and cheap root and containment checks before any DOM-to-model conversion. The event fires on user action and on runtime repair, so a bridge that scans the DOM or allocates a rich reason object per event slows typing and selection. Classifier reasons stay private; Plate, Yjs and cursor overlays get only a model Range or null. Code: `packages/plitejs/src/react/editable/runtime-selection-engine.ts:173`, `selection-controller.ts:538`. Source: `solutions/performance-issues/2026-05-08-dom-selection-bridges-must-stay-cheap-on-selectionchange.md`.
- **Writes from outside the editor pass `ReactUpdatePolicy.preserveSelection`.** A title field, sidebar input or toolbar text box that must not move DOM selection, steal focus or scroll passes this policy from `platejs/react`. It adds the tags `skip-dom-selection`, `skip-selection-focus` and `skip-scroll-into-view`; `useSetStateField` adds them itself, and `YjsUpdatePolicy.remote` bundles them with `collaboration`, `remote-yjs-import` and `history-skip` for host adapters. No public doc names the policy; `document-meta.mdx` says only "selection-preservation tags", and the old name `PliteReactUpdatePolicy` no longer exists. Code: `packages/plitejs/src/react/update-policy.ts:14`, `packages/plitejs/src/react/hooks/use-state-field.ts:63`. Sources: `plite/reference/public-docs/concepts/07-editor.mdx`, `plite/reference/public-docs/concepts/14-document-state.mdx`.

- **Do not port another editor's selection debounce or drag hack.** ProseMirror delays its DOM selection sync during a Chrome mouse drag and toggles `draggable` and `contentEditable` around drags (`ProseMirror/prosemirror-view@ca4c78e9b56f1b164c0b3758b59d8748f11b7534:src/selection.ts:55-70`, `src/input.ts:346-370`). That code shows drag selection is browser-specific and subtle. It does not justify adding a hidden debounce to Plite, which proves drag as browser race behavior in dedicated rows instead. Source: `docs/plite/research/2026-06-12-browser-longtask-selection-oracles/shards/001-browser-longtask-selection-oracles.md:41`, `rejected-ledger.tsv:3`.

- **One text node can render as several DOM segments.** Decorations and marks split one model text node into several `[data-editor-string]` or `[data-editor-zero-width]` segments, so a model offset maps to the DOM by summing the true lengths of the earlier segments (`data-editor-length` when present) and placing the remainder inside the segment that holds it, and a DOM point maps back to an offset in the whole text node. The DOM bridge does this in `resolveDOMPointInRoot` (`packages/plitejs/src/dom/plugin/dom-editor.ts:1044-1103`), and the Playwright selection snapshots do it in both directions (`packages/test/src/playwright/selection-snapshots.ts:414-430`). In April 2026 both counted inside one segment, so a selection set at offset 10 inside a later decorated leaf read back as offset 1 or snapped to the first leaf. Any new bridge or test helper that walks text DOM needs the same cumulative mapping. Test: `packages/plitejs/test/dom/bridge.ts:1419`. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/logic-errors/2026-04-04-decorated-multi-leaf-text-needs-cumulative-offset-mapping.md`.

- **Focus never restores a fallback selection over an in-editor caret.** In April 2026 a click inside a projected bold span of the `markdown-preview` example placed the native caret, the delayed focus pass then restored the default model selection over it, and Backspace ran at the wrong place and did nothing. Today `Editable` exports the model selection on focus only for programmatic focus, when the root itself is the target and no pointer started the focus (`packages/plitejs/src/react/editable/runtime-focus-mouse-events.ts:215-238`), and keydown applies each decision's selection policy, importing the DOM selection unless the policy preserves the model's (`applyKeyDownSelectionPolicy`, `runtime-selection-engine.ts:329-382`). The current `markdown-preview` row sets the caret through the browser handle and never clicks inside a projected segment (`apps/plite/tests/plite-browser/donor/examples/markdown-preview.test.ts:38`), so the click-then-Backspace path has no row. Test projected text with a real click and a real key, not only semantic selection. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/logic-errors/2026-04-15-projected-segment-focus-should-not-clobber-dom-caret.md`.

- **A mouse selection stays DOM-owned until mouseup imports it.** In April 2026 a real mouse drag on the hovering-toolbar example left the model selection collapsed while the DOM showed selected text, because Chromium's throttled `selectionchange` can end on an intermediate collapsed selection; then a selection-only export listener added for programmatic selection overwrote the native drag and emptied `window.getSelection()`. Today mouseup imports the final DOM selection unless an app handler or an internal control claims the event (`packages/plitejs/src/react/editable/runtime-focus-mouse-events.ts:384-413`), and model-to-DOM export skips a selection whose origin is `native-user` or whose source is `dom-current` (`shouldExportModelSelectionToDOM`, `selection-runtime.ts:34-58`). Selection-owned UI subscribes through `useEditorSelection`, as the example does (`apps/www/src/app/(app)/examples/plite/_examples/hovering-toolbar.tsx:102`). The current hovering-toolbar rows select through `editor.selection.selectDOM` (`apps/plite/tests/plite-browser/donor/examples/hovering-toolbar.test.ts:31-42`), so none drives a real mouse drag; a change to selection import or export needs one that asserts DOM selection, model selection and the overlay. Sources: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-04-27-plite-react-mouseup-must-import-final-dom-selection-for-overlays.md`, `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-04-27-plite-react-selection-export-listeners-must-skip-dom-owned-selection.md`.

- **A model-backed selection claims the selection source, not only a visual flag.** A select-all over content without complete DOM, called shell-backed in May 2026 and `viewport-backed` now, is a model selection, not a DOM selection waiting to be imported. When only a root attribute marked it, a later `selectionchange` imported the browser's collapsed selection at `[0, 0]` before copy or paste ran. Keyboard select-all in a virtualized viewport now sets the model-selection preference with source `viewport-backed` (`packages/plitejs/src/react/editable/keyboard-input-strategy.ts:809-830`, browser handle at `browser-handle.ts:315-320`), and `selectionchange` skips import while that source holds and the model selection is preferred (`selection-controller.ts:1205-1210`); ordinary mouse and keyboard selection still import. Row: `apps/plite/tests/plite-browser/donor/examples/huge-document.test.ts:838`. After any change to selection or input ownership, run the full examples, because the regression surface crosses voids, mentions, paste, tables, Shadow DOM and large documents. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-05-03-plite-react-native-input-and-shell-backed-selection-need-single-owners.md`.

## Multi-root focus

- **Every root `Editable` stays natively editable.** In a multi-root document each root keeps `readOnly={false}`; active-root state may drive labels, `autoFocus` and chrome handoff. In May 2026 a read-only inactive root rendered `contenteditable=false`, so the first real click on its text could not place a native caret even when React focused the root afterwards, while locator clicks on the root element passed. Today `Editable` always renders `contenteditable="true"` and read-only sets `aria-readonly` instead (`packages/plitejs/src/react/components/editable.tsx:507`, `apps/plite/tests/plite-browser/donor/examples/read-only.test.ts:9`), so that failure no longer occurs; the example still passes `readOnly={false}`. Code: `apps/www/src/app/(app)/examples/plite/_examples/multi-root-document.tsx:151`. Source: `solutions/ui-bugs/2026-05-21-plite-multi-root-chrome-clicks-must-activate-root-before-focus.md`.
- **Focus a root through its mounted view editor.** DOM focus goes through the view editor that `<Editable root>` registers (`getMountedViewEditor`); a view editor made only for model reads and writes owns no DOM node, and focusing one left focus on the previous root after chrome and toolbar-history clicks. Root chrome leaves clicks on string, leaf, zero-width and `[data-editor-node="element"]` targets to the browser's caret placement and restores a root's saved caret only for clicks outside text; treating a paragraph line-box click as chrome reused a stale caret. Code: `packages/plitejs/src/react/editable/root-interaction-resolver.ts:6`, `packages/plitejs/src/react/components/editable.tsx:314`. Source: `solutions/ui-bugs/2026-05-23-plite-react-mounted-root-editor-focus-for-root-chrome-history.md`.
