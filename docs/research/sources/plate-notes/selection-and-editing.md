# Selection, navigation and delete

These lessons come from retired solution notes and Plite references, and no rule, Vision file, spec or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`.

## Navigation

- **Character navigation has one owner chain.** `Editor.positions` feeds `before` and `after`, and `selection.move` and character delete reuse them. `positions` gives a selectable void or read-only element one atomic stop (`voids: true` enters its children), and an inline void two stops per crossing, into the atom and out of it. Fix an arrow that skips or overshoots in `positions`, not in React keydown or an example: `unit: 'offset'` tests passed while ArrowLeft and ArrowRight overshot mentions, and a React-side patch would leave two truths for cursor motion. Code: `packages/plitejs/src/editor/positions.ts:55`, `packages/plitejs/src/transforms-selection/move.ts:39`, `packages/plitejs/test/query-contract.ts:2342`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-07-plite-move-should-reuse-before-after-location-seam.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-26-plite-selectable-voids-should-be-atomic-navigation-points.md`.
- **`positions` groups by text block, not by top-level index.** It groups character segments by the nearest non-inline element that holds inlines (`getTextBlockPath`). Grouping by `path[0]` flattened a whole table into one text stream, so ArrowRight from an empty first cell landed at offset 1 of the next cell. Every nested text-block family, such as table cells and columns, needs a start stop per block; the table browser rows covered Enter and Backspace in a cell but not horizontal movement between cells. Code: `packages/plitejs/src/editor/positions.ts:147`, `packages/plitejs/test/query-contract.ts:3522`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-27-plite-positions-must-group-character-navigation-by-text-block-boundaries.md`.
- **Table arrows leave a cell in keydown.** When ArrowUp, ArrowDown or a one-cell Shift+Arrow leaves a cell, `TablePlugin`'s `on.keyDown` handles it and calls `preventDefault`. Letting native selection move first and repairing it at apply time drew a caret or text range in the source cell for one frame. The visual-line edge test compares the client rects of a collapsed caret range with those of the block's range, because model paths cannot see soft wraps; without DOM ranges it falls back to the model block edge, and plain and shifted arrows share one `shouldMove` helper. The `EDIT-TABLE-ARROW*-MULTIBLOCK-001` rows state the outcome but not this ownership. Code: `packages/platejs/src/react/features/table/TablePlugin.tsx:500-640`, `TablePlugin.navigation.spec.tsx:569-749`. Sources: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/logic-errors/2026-03-29-table-arrow-navigation-must-own-moveline-and-visual-line-boundaries.md`, `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/logic-errors/2026-03-31-table-shift-arrow-selection-must-own-keydown-before-native-selection.md`.

- **Around a selectable void, test plain, vertical and Shift-extended movement apart.** Plain ArrowLeft and ArrowRight through an image were already model-owned and green in April 2026, while the other two paths split DOM from model. Shift+ArrowRight before an image let the browser extend to wrapper elements while the model stayed collapsed, and a second press moved the model into the image while DOM focus had already passed it; horizontal Shift movement needs no browser layout, so it is model-owned and runs as a focus-edge move, which the kernel still classifies as `move-selection` with `axis: 'horizontal'` and `extend: true`. ArrowDown from the end of the paragraph before an image put the DOM caret in the image spacer at `[1,0]@0` while the model stayed at `[0,0]@113`, so the image did not render selected; the first `selectionchange` came before Chrome settled the selection around the zero-width spacer, and the fix imported the settled DOM selection after the keydown's default action. Browser rows for selectable voids assert model selection, DOM selection and the visible selected state. Code: `packages/plitejs/src/react/editable/editing-kernel.ts:913-923`, `:982-993`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-04-27-plite-react-void-keyboard-navigation-needs-post-native-sync-and-shift-model-ownership.md`. Limit: the April fix's post-keydown `setTimeout` import is gone (no `setTimeout(` call under `packages/plitejs/src/react/editable` on 2026-10-08), and how today's runtime settles a native vertical move into a void was not traced.

## Delete

- **`unit: 'character'` has one boundary source.** `getCharacterDistance` serves measurement, `before`/`after` movement and deletion, so reverse delete removes a whole grapheme (Tamil ni, Thai clusters). Legacy Slate's partial combining-mark delete came from a reverse-only branch that was removed on purpose. Distance tests passed while delete diverged, so every new text-unit row needs a delete case too. Code: `packages/plitejs/test/text-units-contract.ts:537`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-plite-character-delete-must-share-text-unit-boundaries.md`.
- **A collapsed delete classifies a structural target before the character walk.** Backspace at the start of an empty editable inline path-deletes the inline. A collapsed delete that reaches an adjacent void or read-only element path-deletes only that atom and keeps the caret through an anchor taken before the removal. A character-range delete there removed the preceding character (#5972: `an !` became `an!`) or removed several adjacent voids in one keypress. The model selection was already right; the native FEFF offset 1 misled a browser-first diagnosis. Code: `packages/plitejs/src/transforms-text/delete-text-collapsed-path-targets.ts:19`, `delete-text-plan.ts:68`, `packages/plitejs/test/delete-contract.ts:1592`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-07-plite-empty-inline-backspace-must-path-delete-the-inline.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-plite-adjacent-block-void-delete-must-path-delete-one-target.md`.
- **An expanded delete removes a selected inline only when the range crosses out of it.** A delete wholly inside an inline keeps the empty shell. Caret placement after a delete splits by shape: a range crossing into a surviving inline, a collapsed forward delete at a text end just before an inline, or staying on the spacer. One generic jump-to-next-inline rule kept moving the failure between range rows and point rows; the legacy `transforms/delete` fixture suite catches it and the local package tests did not. Code: `packages/plitejs/src/transforms-text/delete-text-removal.ts:116`, `delete-text-inline-points.ts:91`, `packages/plitejs/test/delete-contract.ts:489`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-14-plite-delete-selection-normalization-must-distinguish-inline-spacers-from-inline-targets.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-expanded-delete-across-inline-boundaries-must-remove-crossed-inline-ancestors.md`.
- **Delete cleanup stays inside its own prune scope.** `removeEmptyStructuralArtifacts` skips nested blocks outside that scope, because empty table cells, list items and quotes are valid structure. A Backspace after a table once deleted an empty first cell, leaving rows of 3, 4 and 4 cells. Assert row cell counts in the model and the browser, since text assertions miss a ragged table, and treat any whole-document cleanup pass after a transform as suspect. Code: `packages/plitejs/src/transforms-text/delete-text-structural-cleanup.ts:207`, `packages/plitejs/test/delete-contract.ts:1363`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-06-plite-delete-cleanup-must-not-remove-valid-nested-empty-blocks.md`.
- **Delete-fragment commands carry the event-time selection.** The browser delete event can collapse or move the live DOM selection before the model command runs, so the command holds `command.selection`. A triple-click gives a hanging range from block start to the next block start, and Backspace must delete the whole block; it once only emptied the paragraph (#5847). Code: `packages/plitejs/src/react/editable/editable-command-types.ts:13`, `mutation-controller.ts:866`, `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:7310`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-06-plite-react-triple-click-delete-needs-full-block-selection-intent.md`.
- **A full-document delete keeps the first block, emptied.** When that block is a plain paragraph, the result is one empty paragraph and any list shells after it vanish (#2500). When the first block is structured, such as a table, the full-document fast path is skipped and the emptied table survives as the only block. `markdown-editing-spec.md` has no select-all delete row, so a core test pins the table case and nobody chose it as product behavior. Code: `packages/plitejs/test/delete-contract.ts:889`, `:1302`, `:1331`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/ledgers/issue-coverage-matrix.md`.

- **Backspace after empty paragraphs removes one block.** At the start of a top-level block whose previous sibling is an empty, non-void, editable block, a collapsed Backspace path-deletes that one block (`getPreviousEmptyBlockPathAtBlockStart`, `packages/plitejs/src/transforms-text/delete-text-collapsed-path-targets.ts:58-102`). In May 2026, repeated Enter at a document start then Backspace removed every preceding empty paragraph, and Enter, Space, Enter, Backspace erased unrelated earlier empty paragraphs, because the delete ran as a hanging-range cleanup followed by a top-level empty-block sweep. The guard applies to top-level blocks only, and merging a whitespace-only paragraph keeps its cleanup inside the delete range. Tests: `packages/plitejs/test/delete-contract.ts:1403`, `:1444`, `:1472`. They call `tx.text.deleteBackward()`; no browser row presses Enter, Space, Enter, Backspace, the native path the source says programmatic coverage misses. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/developer-experience/2026-05-21-plite-layout-source-entry-and-paged-editable-dx.md`.

- **A block-start-to-block-start selection excludes its end block.** Deleting a range from the start of block N to the start of sibling block N+2 removes blocks N and N+1 whole and leaves N+2 intact; a range that ends at a block's end includes that block. In May 2026 the model-owned full-block delete fast path removed only block N for such a range, and a narrowed fix fell through to generic text deletion and left an empty heading; the `huge-document-cut` stress family caught it by asserting which block shifted into the cut position (`apps/plite/tests/plite-browser/donor/stress/generated-editing.test.ts:180-184`). The `fragment.delete` editor command, given a range, now collects every fully selected sibling block (`getFullySelectedSiblingBlockPaths`, `packages/plitejs/src/core/editor-commands.ts:249-325`) and removes them with one `tx.nodes.replaceChildren` (`:654-721`). A delete fast path classifies the selection geometry first (same block, adjacent sibling, several siblings, partial text), and its tests include a multi-block start-to-start row; asserting only that a delete command ran misses this. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-plite-full-block-delete-fast-path-must-stop-at-selection-boundaries.md:23-91`.

## DOM selection import and ownership

- **A DOM selection is imported only when both endpoints belong to this editor.** Both anchor and focus must pass `hasSelectableTarget`, and the runtime skips `beforeinput` target ranges while the live selection crosses editor ownership. A nested editor sits inside the parent's void DOM but owns its own endpoints; typed text once replaced a parent range built from a cross-editor selection (`Outer u`, from the Lexical harvest). A model-handle select does not prove this. Prove it with a real native Range from outside to inside and from parent to nested plus a `selectionchange` event, assert no runtime errors, then refocus and type. Code: `packages/plitejs/src/react/editable/selection-controller.ts:555-565`, `selection-reconciler.ts:579-583`, `:660-667`, `apps/plite/tests/plite-browser/donor/examples/editable-voids.test.ts:1381`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-06-plite-react-foreign-dom-selections-must-be-ignored-before-import.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-05-09-parent-nested-dom-selections-must-not-import-as-parent-ranges.md`.
- **Controls inside the editor root are native-owned at every root event boundary.** This covers input, textarea, select, button, `[role=button]`, nested editor roots and `contenteditable=false` chrome. Keyboard and input paths stop propagation, native `beforeinput` and `input` use `stopImmediatePropagation` because WebKit kept routing them otherwise, and their keydown yields no editor command. The outer selection comes back on the control's blur without pointer intent, never on its focus, which would steal focus before typing. A raw `root.focus()` after typing in a void's input could send keys into a nested editor, and behavior rows missed shell buttons being classed as native-owned; `assertNoIllegalKernelTransitions` catches that. Code: `packages/plitejs/src/react/editable/input-controller.ts:168`, `runtime-before-input-events.ts:484`, `runtime-focus-mouse-events.ts:115`, `interaction-owner.ts:49`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-22-plite-react-internal-controls-must-be-native-owned.md`, `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-23-plite-react-shell-buttons-must-be-internal-targets.md`, `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/logic-errors/2026-04-24-plite-browser-proof-must-separate-model-owned-handles-root-selection-and-usable-focus.md`.
- **`selectionchange` is a hot path.** The runtime throttles it, and the controller classifies ownership with fixed string reasons and cheap root and containment checks before any DOM-to-model conversion. The event fires on user action and on runtime repair, so a bridge that scans the DOM or allocates a rich reason object per event slows typing and selection. Classifier reasons stay private; Plate, Yjs and cursor overlays get only a model Range or null. Code: `packages/plitejs/src/react/editable/runtime-selection-engine.ts:173`, `selection-controller.ts:538`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/performance-issues/2026-05-08-dom-selection-bridges-must-stay-cheap-on-selectionchange.md`.
- **Writes from outside the editor pass `ReactUpdatePolicy.preserveSelection`.** A title field, sidebar input or toolbar text box that must not move DOM selection, steal focus or scroll passes this policy from `platejs/react`. It adds the tags `skip-dom-selection`, `skip-selection-focus` and `skip-scroll-into-view`; `useSetStateField` adds them itself, and `YjsUpdatePolicy.remote` bundles them with `collaboration`, `remote-yjs-import` and `history-skip` for host adapters. No public doc names the policy; `document-meta.mdx` says only "selection-preservation tags", and the old name `PliteReactUpdatePolicy` no longer exists. Code: `packages/plitejs/src/react/update-policy.ts:14`, `packages/plitejs/src/react/hooks/use-state-field.ts:63`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/07-editor.mdx`, `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/reference/public-docs/concepts/14-document-state.mdx`.

- **Do not port another editor's selection debounce or drag hack.** ProseMirror delays its DOM selection sync during a Chrome mouse drag and toggles `draggable` and `contentEditable` around drags (`ProseMirror/prosemirror-view@ca4c78e9b56f1b164c0b3758b59d8748f11b7534:src/selection.ts:55-70`, `src/input.ts:346-370`). That code shows drag selection is browser-specific and subtle. It does not justify adding a hidden debounce to Plite, which proves drag as browser race behavior in dedicated rows instead. Source: `c70bacbd4a:docs/plite/research/2026-06-12-browser-longtask-selection-oracles/shards/001-browser-longtask-selection-oracles.md:41`, `rejected-ledger.tsv:3`.

- **One text node can render as several DOM segments.** Decorations and marks split one model text node into several `[data-editor-string]` or `[data-editor-zero-width]` segments, so a model offset maps to the DOM by summing the true lengths of the earlier segments (`data-editor-length` when present) and placing the remainder inside the segment that holds it, and a DOM point maps back to an offset in the whole text node. The DOM bridge does this in `resolveDOMPointInRoot` (`packages/plitejs/src/dom/plugin/dom-editor.ts:1044-1103`), and the Playwright selection snapshots do it in both directions (`packages/test/src/playwright/selection-snapshots.ts:414-430`). In April 2026 both counted inside one segment, so a selection set at offset 10 inside a later decorated leaf read back as offset 1 or snapped to the first leaf. Any new bridge or test helper that walks text DOM needs the same cumulative mapping. Test: `packages/plitejs/test/dom/bridge.ts:1419`. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/logic-errors/2026-04-04-decorated-multi-leaf-text-needs-cumulative-offset-mapping.md`.

- **Focus never restores a fallback selection over an in-editor caret.** In April 2026 a click inside a projected bold span of the `markdown-preview` example placed the native caret, the delayed focus pass then restored the default model selection over it, and Backspace ran at the wrong place and did nothing. Today `Editable` exports the model selection on focus only for programmatic focus, when the root itself is the target and no pointer started the focus (`packages/plitejs/src/react/editable/runtime-focus-mouse-events.ts:215-238`), and keydown applies each decision's selection policy, importing the DOM selection unless the policy preserves the model's (`applyKeyDownSelectionPolicy`, `runtime-selection-engine.ts:329-382`). The current `markdown-preview` row sets the caret through the browser handle and never clicks inside a projected segment (`apps/plite/tests/plite-browser/donor/examples/markdown-preview.test.ts:38`), so the click-then-Backspace path has no row. Test projected text with a real click and a real key, not only semantic selection. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/logic-errors/2026-04-15-projected-segment-focus-should-not-clobber-dom-caret.md`.

- **A mouse selection stays DOM-owned until mouseup imports it.** In April 2026 a real mouse drag on the hovering-toolbar example left the model selection collapsed while the DOM showed selected text, because Chromium's throttled `selectionchange` can end on an intermediate collapsed selection; then a selection-only export listener added for programmatic selection overwrote the native drag and emptied `window.getSelection()`. Today mouseup imports the final DOM selection unless an app handler or an internal control claims the event (`packages/plitejs/src/react/editable/runtime-focus-mouse-events.ts:384-413`), and model-to-DOM export skips a selection whose origin is `native-user` or whose source is `dom-current` (`shouldExportModelSelectionToDOM`, `selection-runtime.ts:34-58`). Selection-owned UI subscribes through `useEditorSelection`, as the example does (`apps/www/src/app/(app)/examples/plite/_examples/hovering-toolbar.tsx:102`). The current hovering-toolbar rows select through `editor.selection.selectDOM` (`apps/plite/tests/plite-browser/donor/examples/hovering-toolbar.test.ts:31-42`), so none drives a real mouse drag; a change to selection import or export needs one that asserts DOM selection, model selection and the overlay. Sources: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-04-27-plite-react-mouseup-must-import-final-dom-selection-for-overlays.md`, `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-04-27-plite-react-selection-export-listeners-must-skip-dom-owned-selection.md`.

- **A model-backed selection claims the selection source, not only a visual flag.** A select-all over content without complete DOM, called shell-backed in May 2026 and `viewport-backed` now, is a model selection, not a DOM selection waiting to be imported. When only a root attribute marked it, a later `selectionchange` imported the browser's collapsed selection at `[0, 0]` before copy or paste ran. Keyboard select-all in a virtualized viewport now sets the model-selection preference with source `viewport-backed` (`packages/plitejs/src/react/editable/keyboard-input-strategy.ts:809-830`, browser handle at `browser-handle.ts:315-320`), and `selectionchange` skips import while that source holds and the model selection is preferred (`selection-controller.ts:1205-1210`); ordinary mouse and keyboard selection still import. Row: `apps/plite/tests/plite-browser/donor/examples/huge-document.test.ts:838`. After any change to selection or input ownership, run the full examples, because the regression surface crosses voids, mentions, paste, tables, Shadow DOM and large documents. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/ui-bugs/2026-05-03-plite-react-native-input-and-shell-backed-selection-need-single-owners.md`.

- **After Plite handles an insert or a navigation key, stale DOM reports must not move the model caret.** The browser can report a `beforeinput` target range or a delayed `selectionchange` from the old DOM caret after Plite has already moved the model caret, and trusting it puts the next character at the old position. In April 2026 `page.keyboard.type('Undo Me')` under a Mac Chrome user agent scattered the letters across `/examples/richtext` after Home, while `keyboard.insertText` passed because it sends the whole string as one event; and on the custom-placeholder example, typing `a`, then `b`, then Enter with delays produced blocks `["ab", "b"]`, because Enter re-imported a stale collapsed DOM caret at offset 1 after the transient repair origin had already cleared. The rule that held: once Plite owns the input lane, the model selection stays authoritative until an explicit user selection, decided by selection provenance (`selectionSource` plus the model-selection preference), not only by the transient origin flag. Today `hasAuthoritativeModelSelection` requires a `model-owned` or `viewport-backed` source and either the preference or a programmatic origin, and text-input repair treats a model-preferred, model-owned lane as model-owned. Assert model text through the browser handle as well as the visible DOM, test `keyboard.type` as well as `insertText`, and add delayed per-character rows before structural keys such as Enter. Code: `packages/plitejs/src/react/editable/editing-kernel.ts:570-588`, `packages/plitejs/src/react/editable/input-router.ts:653-656`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-04-21-plite-react-model-owned-input-must-ignore-stale-dom-target-ranges.md`.

- **Import the DOM selection before a model-owned key runs.** The browser owns vertical caret movement and Plite owns horizontal and structural keys, so a model-owned key must first import the in-editor DOM selection unless a model-owned operation is already authoritative. In April 2026 ArrowDown moved the visible caret into paragraph 2 while the model stayed in paragraph 1, and the next ArrowRight used the stale model selection and snapped the caret back. Flushing only the throttled `selectionchange` handler did not help, because the pending event sat in the debounced scheduler; today `applyKeyDownSelectionPolicy` imports the DOM selection for non-internal targets and flushes both the debounced scheduler and the throttled handler. Isolated ArrowLeft and ArrowRight rows never combined a native move with a model-owned one, and handle-based setup that sets only the model selection proved nothing about DOM selection. Test chains such as ArrowDown then ArrowRight, make every helper used in a browser row place the DOM selection too, and keep the internal-control guard before the import so inputs, buttons and nested editors stay native-owned. Code: `packages/plitejs/src/react/editable/runtime-selection-engine.ts:329`, `:345-355`, `:381-382`, `packages/plitejs/src/react/editable/selection-controller.ts:479`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-04-22-plite-react-keydown-must-import-dom-selection-before-model-owned-navigation.md`.

- **A repair-induced `selectionchange` stays model-owned.** After Plite handles a destructive `beforeinput` as model-owned, the DOM repair it schedules fires its own `selectionchange`; if that event enters the pipeline as `dom-current`, a delayed browser selection reopens DOM authority after the model edit was already right. In April 2026 repeated Alt+Backspace on `/examples/richtext` drifted the visible caret from the model; headless Playwright did not always show the visual split, but the kernel trace did, with repair-induced entries reporting `selectionSource: dom-current`. Blocking every native `selectionchange` while the model was preferred fixed that row and broke toolbar selection and paste. The narrow rule: the repair carries a model-owned selection transition, the runtime restores a model-owned source for a repair-induced event when the model is preferred, and only the transient repair origin clears afterwards, so a later real user selection still imports. Prove destructive native edits with model text, visible DOM text, DOM selection containment, a follow-up keystroke and the trace's selection source, since final text alone can look right, and keep toolbar and paste rows green before accepting any broad ignore-DOM-selection fix. Code: `packages/plitejs/src/react/editable/runtime-selection-engine.ts:207-216`. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/ui-bugs/2026-04-25-plite-react-repair-induced-selectionchange-must-stay-model-owned.md`.

- **A collapsed DOM caret on an element is re-exported even when it maps to the model selection.** After a model-owned `insertText` before trailing punctuation in a custom-rendered leaf, the model selection moved past the new character while the DOM selection stayed collapsed on a wrapper span at offset 0, so Chrome painted the caret before the character; model text and model selection assertions both passed (April 2026). Selection export now skips only when the DOM selection maps to the model range and its anchor is a text node (`isCollapsedElementSelection`, `packages/plitejs/src/react/editable/selection-reconciler.ts:1199-1213`). A browser row for model-owned insertion asserts the DOM caret node and offset or the caret rect, and inserts before punctuation and inside a leaf, not only at the end. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/logic-errors/2026-04-22-plite-react-model-owned-insert-must-repair-dom-caret.md:21-63`.

- **Caret autoscroll measures the post-update DOM range.** `defaultScrollSelectionIntoView` takes the collapsed DOM range after selection export or input repair, falls back to the leaf rect when Chrome reports a zero rect, and walks scrollable ancestors inner to outer with Plite's own `scrollRectIntoViewIfNeeded` (`packages/plitejs/src/react/components/editable.tsx:653`, `:784-823`). ## Multi-root focus

- **Every root `Editable` stays natively editable.** In a multi-root document each root keeps `readOnly={false}`; active-root state may drive labels, `autoFocus` and chrome handoff. In May 2026 a read-only inactive root rendered `contenteditable=false`, so the first real click on its text could not place a native caret even when React focused the root afterwards, while locator clicks on the root element passed. Today `Editable` always renders `contenteditable="true"` and read-only sets `aria-readonly` instead (`packages/plitejs/src/react/components/editable.tsx:507`, `apps/plite/tests/plite-browser/donor/examples/read-only.test.ts:9`), so that failure no longer occurs; the example still passes `readOnly={false}`. Code: `apps/www/src/app/(app)/examples/plite/_examples/multi-root-document.tsx:151`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-05-21-plite-multi-root-chrome-clicks-must-activate-root-before-focus.md`.
- **Focus a root through its mounted view editor.** DOM focus goes through the view editor that `<Editable root>` registers (`getMountedViewEditor`); a view editor made only for model reads and writes owns no DOM node, and focusing one left focus on the previous root after chrome and toolbar-history clicks. Root chrome leaves clicks on string, leaf, zero-width and `[data-editor-node="element"]` targets to the browser's caret placement and restores a root's saved caret only for clicks outside text; treating a paragraph line-box click as chrome reused a stale caret. Code: `packages/plitejs/src/react/editable/root-interaction-resolver.ts:6`, `packages/plitejs/src/react/components/editable.tsx:314`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-05-23-plite-react-mounted-root-editor-focus-for-root-chrome-history.md`.

- **An implicit edit follows the selection's root; an explicit rootless location does not.** A mutation without `at` targets the current selection's root (`getMutationRoot`), while an explicit rootless location resolves through `getLocationMutationRoot`: its own root, else the active view or update root, else `main`, which is the rule `locations.mdx` states for the base editor and root-bound views. In May 2026 both cases shared the current-selection-root fallback, so clicking the header root and then a later main-root paragraph stored the main path `[1,0]` under the header root, and the header view's marks read crashed with `Cannot find a descendant at path [1,0]`. The bad root came from the core transaction path, so an example-side focus repair or a fix to the active-root hook could not remove it. Test the exact transition, a header selection followed by a rootless selection at a path only the main root has, with a core runtime or view contract, and assert view marks reads as well as the selection, because focus checks miss the root mismatch. Code: `packages/plitejs/src/core/public-state.ts:2029-2073`; doc: `content/docs/(guides)/locations.mdx:12-13`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/runtime-errors/2026-05-23-plite-rootless-explicit-selections-must-not-inherit-sibling-root.md`.

- **A selection stored for a non-main root carries that root on its points, and ordered typing proves it.** The selection state stamps the root onto every point of a selection it stores for a non-main root and strips it for `main`. In May 2026 a selection imported through the header view was stored rootless, so header `insert_text` operations did not transform it and every key landed at the original offset: pressing `h`, `e`, `l`, `l`, `o` rendered `olleh`, while `document.activeElement` was already the header and the row that clicked the editable element directly stayed green. A focus row asserts `document.activeElement`, that the native selection's anchor is inside the clicked root, and follow-up typing in that root only, and covers text-surface clicks, root-chrome clicks and typing. For an ordering bug, send the keys one by one and assert the reversed string is absent, because one text insertion cannot fail that way: today's text-surface row clicks the header and types with `page.keyboard.type`, while the row that asserts `olleh` is absent inserts `hello` through the browser handle in one call, so it alone cannot catch the reversal. Code: `packages/plitejs/src/core/selection-state.ts:20-82`, `apps/plite/tests/plite-browser/donor/examples/multi-root-document.test.ts:928-947`, `:1243-1249`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/ui-bugs/2026-05-21-plite-multi-root-chrome-clicks-must-activate-root-before-focus.md`.

- **Multi-root focus is decided and proved by the DOM.** Beside the mounted-view-editor failure, May 2026 multi-root work hit three more focus traps. `DOMEditor.focus` skipped refocus because its internal focused flag was stale while the document's active element had moved; today's `focus` reads the root's `activeElement` and has no early return on that flag (`packages/plitejs/src/dom/plugin/dom-editor.ts:1513-1517`). Root chrome and toolbar history called focus with `retries: 1` or `2`, which lost the race against dirty node maps; the default is 50 (`:1400`). And a click on an editable root outside its text went wrong both ways: an inactive blank-root click imported a click-coordinate caret into the middle of a paragraph instead of restoring the root's caret, and a padding click after visiting another root restored the old caret instead of moving to the visible end the user clicked. The fix resolves a range from the click coordinates first and restores the saved caret only when none resolves, as today's root interaction controller still does (`resolveEventRange`, else a coordinate placement; `packages/plitejs/src/react/editable/root-interaction-controller.ts:494-497`, `:1591-1603`). Toolbar history mutates through the root view editor and restores focus through the mounted one, because focus has already left the editor when `onClick` runs. Prove each case on the first click with `document.activeElement.id`, the native selection's root, the exact DOM caret offset, since a root-only check misses a stale offset, and follow-up typing; for a padding click, first leave a stale caret in the same root and visit a sibling root.
