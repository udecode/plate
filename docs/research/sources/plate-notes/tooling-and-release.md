# Tooling, docs build and release

These lessons come from retired solution notes, and no rule, script comment or public doc states them. A reader checked each one against the current tree on 2026-10-06. Each source is a path under `docs/` at commit `52625e8502`; read it with `git show 52625e8502:docs/<path>`.

## Build

- **Turbopack aliases are app-relative.** `resolveAlias` targets must be app-relative paths with forward slashes and a `./` or `../` prefix; absolute filesystem targets fail with "Can't resolve './Users/...'" and "server relative imports are not implemented yet". Both Next configs build their aliases through `toAppImportPath` for this reason, and the helper has no comment saying so. Code: `apps/www/next.config.ts:14-20`, `apps/plite/next.config.ts:11`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-03-11-next-turbopack-react-compiler-workspace-aliases.md`.
- **Example galleries use an explicit importer map.** Route-level galleries map each key to its own `() => import('./_examples/x')`. A template-string ``import(`./examples/${path}`)`` makes the bundler pull in the whole directory, and Next 16 then parsed `custom-types.d.ts` as a module and failed the build. Code: `apps/www/src/app/(app)/examples/plite/plite-example-loaders.tsx:6-20`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-04-16-next-16-webpack-example-imports-must-use-explicit-maps-and-drop-next-config-eslint.md`.
- **Compiled MDX rejects HTML comments.** `<!-- x:start -->` fails with "Unexpected character `!` (U+0021)" in `@mdx-js/mdx` 3.1.1, so a generator that writes replaceable markers into compiled MDX emits `{/* x:start */}`. The registry changelog entries under `apps/www/src/registry/changelog/entries/` hold `<!-- entry: ... -->` and are safe only because the build parses them and never compiles them. Code: `tooling/scripts/generate-ui-changelog-entries.mjs:909`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-04-27-mdx-generated-markers-must-use-jsx-comments.md`.

- **`platejs` react-core cannot import a feature's React entrypoint.** `react-core` is `privateDirectory('react', ['core', 'dom', 'history', 'static'], ...)` and every `react/features/<name>` entrypoint depends on `react-core` (`tooling/entrypoints/entrypoint-dag.mjs:154-167`, `:189-207`, `:407-414`), so code under `react/components`, such as `PlateContent.tsx`, that imports from `react/features/combobox` closes a cycle `tooling/oxlint/entrypoint-dag-plugin.mjs` rejects. A host every editor mounts must live in react-core, which grows every Plate React bundle, or be rendered by a feature plugin. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:45` (read from the code, not run).

- **The API reference build fails on a stale or unlisted export name.** `apps/www/scripts/build-api-reference.mts` throws when an entrypoint export is not included or excluded exactly once in `apps/www/api-reference.config.json`, and when the config names a symbol the entrypoint no longer declares (`:225-241`; skipped under `--init`), so a rename or removal of a public name edits that config in the same change. Source: `docs/plite/research/2026-10-03-autocomplete-arena/blast-radius.md:51-52`.

- **Source path maps list each entrypoint exactly.** In March 2026 `apps/www/tsconfig.json` tried to copy the bundler's source aliases with wildcard rules (`@platejs/*`, `@platejs/*/react`, `@platejs/*/static`). The broad rule matched `@platejs/core/react` as `* = core/react`, so the `/react` rule never applied, TypeScript followed the linked package export into `dist`, and the program mixed source and `dist` types. TypeScript `paths` matching is not the bundler's alias map, so a source graph needs one exact entry per specifier. `tooling/entrypoints/workspace-source-paths.mjs` now writes one exact `paths` entry for every `platejs` and `plitejs` specifier into each tsconfig it lists, `apps/www/tsconfig.json` among them, and `assertWorkspaceSourcePathsGenerated` fails when a file drifts. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-03-12-typescript-workspace-subpath-aliases-in-apps-www.md:36-49`, `:100-104`. Limit: the wildcard failure was seen in March 2026, when Plate shipped separate `@platejs/<pkg>` packages, and was not rerun.

- **DOCX export copies its zip bytes before building the Blob.** JSZip's `generateAsync({ type: 'uint8array' })` returns a value typed `Uint8Array<ArrayBufferLike>`, which TypeScript does not accept as a `BlobPart` with the DOM lib, so `new Blob([buffer])` fails the typecheck. The export copies the bytes with `new Uint8Array(buffer)` first (`packages/platejs/src/docx/export/lib/html-to-docx.internal.ts:44-47`). The copy has no comment, so a cleanup can mistake it for a redundant allocation. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-03-25-typescript-6-upgrade-needs-explicit-paths-and-bun-test-typing.md:123-136`, seen under TypeScript 6.0.2 in March 2026. On 2026-10-08 a scratch probe under the repository's TypeScript 7.0.2 (`--strict --lib esnext,dom`) still rejected `new Blob([buffer])` for a `Uint8Array<ArrayBufferLike>` with TS2322 and accepted the copied array; the probe file was not committed.

- **A clean MDX generator run does not prove the docs prerender.** `pnpm --filter www build:source` runs `fumadocs-mdx`, which compiles MDX and source metadata; `next build` then executes the compiled MDX tree as server components. In the May 2026 move from Contentlayer to Fumadocs, `.source` generated cleanly while the production build failed on every MDX page (`Invalid element at key "component": expected a Zod schema`, a Zod version mismatch in `source.config.ts`) and prerender failed on hook-based MDX components (`Attempted to call useAtom() from the server` for `<PackageInfo>`, and "`AccordionItem` must be used within `Accordion`" for API docs). So a change to an MDX component, `source.config.ts` or anything it imports needs a production build or a request to the rendered route, not only `build:source`; `plate-docs` already warns that an MDX parse proves no route. Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/developer-experience/2026-05-22-fumadocs-mdx-migrations-need-server-safe-source-config-and-mdx-boundaries.md:22-35`, `:127-144`. Limit: seen with Fumadocs v13 in May 2026; the app now pins `fumadocs-mdx` 15.0.10, and the failures were not rerun.

- **A filtered turbo typecheck failure is a task-graph race until the package's own typecheck repeats it.** In March 2026 `pnpm turbo typecheck --filter=./packages/table --filter=./apps/www` reported missing `platejs/static` exports and implicit-`any` cascades while `pnpm --dir apps/www typecheck` passed, because a `www#typecheck` override had dropped `^build`, so www checked while dependency builds rewrote `dist`. `turbo.json:51-59` still gives `www#typecheck` `dependsOn: ["^build"]` while the generic `typecheck` task depends on `^typecheck`. When one package fails only inside a wider filtered run, run that package's typecheck directly, then rerun turbo with `--concurrency=1`; a failure that clears is a race in the task graph, so fix the graph, not TypeScript paths. Source: `c70bacbd4a7523ae3ebfd820cec0ea8ec228e9ad:docs/solutions/test-failures/2026-03-24-turbo-filtered-typecheck-can-lie-when-package-typecheck-passes.md`.

- **Every render surface of a registry demo passes its derived `id`.** The shared registry `Demo` calls `createValue(id)` with the demo slug, so a surface that renders the example without `id={name.replace('-demo', '')}` seeds nothing. In April 2026 `/blocks/toc-demo` returned a 500 while the docs preview, which passed the id, worked, and the failure was first chased as a TOC bug and then on a port that served another checkout. Today the block preview page, `ComponentPreview` and the installation tab each pass it; a new surface must too, and `ComponentPreview` is the reference. Before debugging a route that disagrees with another port, check which checkout that port serves. Code: `apps/www/src/registry/examples/demo.tsx:14-17`, `apps/www/src/lib/block-preview-page.tsx:88`, `apps/www/src/components/component-preview.tsx:65`, `apps/www/src/components/component-installation.tsx:169`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/runtime-errors/2026-04-07-blocks-demo-pages-must-pass-example-id.md`.

- **Data-driven registry reads need explicit output tracing.** `getRegistryItem()` builds file paths from registry metadata and reads them with `fs`, so Next output file tracing, which follows static imports, misses `src/registry/**` and `public/r/**`. In May 2026 the `/api/registry-source/[name]` route, which hydrates the non-initial BlockViewer code tabs, needed its own include beside the docs routes. Local dev and unit tests have the whole filesystem, so they cannot show a missing include, and `dynamic = 'force-static'` did not help, because static generation still reads the files. Today one `'/*'` entry in `outputFileTracingIncludes` covers every route, and `/api/search` carries its own include for `content/docs`. Before narrowing an include, list every runtime caller of `getRegistryItem` or of registry `fs` reads, and prove the change with a standalone production build, not a local test. Code: `apps/www/next.config.ts:120-122`, `apps/www/src/app/api/registry-source/[name]/route.ts:28`, `apps/www/src/lib/rehype-utils.ts:308`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/runtime-errors/2026-05-26-registry-api-routes-need-output-file-tracing-for-source-backed-code-tabs.md`.

- **The barrel generator exports every source file its exclusion pattern does not name.** `pnpm brl` runs barrelsby with one exclusion pattern: `__tests__`, names containing fixture, template, spec or internal, `.test.ts[x]` and `.d.ts`. A spec helper colocated with source under any other name becomes public API. In March 2026 it exported `./Plate.slow` and `./cleanWordHtml.slow` after the slow-lane rename, and `./tocHookMocks`, a shared hook-test mock helper, from a public hooks barrel. Keep spec-only helpers under `__tests__`, which verify's testing reference reserves for package-local helpers, and add any new test suffix to the pattern in the same change, as the script's comment says. A search on 2026-10-08 found no colocated mock or test-util file under `packages/*/src` outside `__tests__` or a test suffix. Code: `tooling/scripts/brl.sh:52-53`. Sources: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/workflow-issues/2026-03-25-barrelsby-must-not-export-colocated-test-mock-helpers.md`, `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/solutions/workflow-issues/2026-03-23-barrelsby-must-ignore-slow-test-files.md`.

- **A proof command can mutate the package metadata it is meant to verify.** In June 2026, a Core typecheck built dependencies through `plate-pkg p:build`, which repeatedly rewrote three Plite packages' typed export maps. Repatching the manifests did not fix the cause; changing those packages to `tsdown` stopped the mutation. Source: `c70bacbd4a:docs/plans/2026-06-28-plate-next-tested-package-test-file-gate.md:308-318`. Today's consolidated `packages/plitejs/package.json` also builds with `tsdown`. The three old package paths and the commit-class decision beside this finding are obsolete; this is a lesson about finding the mutating command, not a current release verification.

- **Do not rebuild a dependency's emitted artifacts while proving its consumer.** The July Suggestion build raced a concurrent Plite rebuild and failed against changing declaration output; running the consumer build after dependency work settled passed. Source: `docs/plans/2026-07-08-plate-next-suggestion-package-review.md:215-217`, with the failed attempt and sequential repair at line 230. Order overlapping artifact writers before interpreting missing declarations as an API defect. This is historical evidence from the former separate packages, not a reproduced race in today's consolidated packages.

- **Resize declarations use an owner-defined length type.** The July 2026 Resizable review found four TS2883 declaration failures after source-first typecheck passed. A dependency-derived CSS type leaked pnpm-internal paths into exported declarations; defining the resize domain locally repaired the build. The current owner still exports its own `ResizeLength = number | string` in `packages/platejs/src/react/features/resizable/Resizable.tsx:20`. Check declaration emission as well as source types when changing a public UI prop. Evidence: `docs/plans/2026-07-13-plate-next-media-mention-resizable-package-reviews.md:421,441`. Limit: the four failures and successful build are historical receipts, not a rerun.

- **A dependency CLI validates external data and passes process arguments separately.** July's depset review found unvalidated package/npm data and shell interpolation behind a green typecheck. The surviving owner, `packages/cli/src/deps/index.ts`, parses package and npm results with schemas and invokes npm through `execFilePromise('npm', [...])`; installation uses `execFileSync(pm, ['install'], ...)`. Keep package/version input in argument values rather than executable shell text. Evidence: `c70bacbd4a:docs/plans/2026-07-13-plate-next-udecode-cmdk-cn-depset-package-reviews.md:416,558-560,569-571`. Limit: depset is now the `plate deps` command, not an independent package.

- **Skipping confirmation does not imply installation.** The July depset review found an install-authority bug behind green static checks. Current `packages/cli/src/deps/index.ts:310-351` starts from `options.install`, prompts only when neither `--install` nor `--yes` is set, and skips installation under `--yes` alone. The historical built-CLI probe updated a dependency from 1.0.0 to 2.0.0 with `--yes` and confirmed that npm install was not invoked. Evidence: `c70bacbd4a:docs/plans/2026-07-13-plate-next-udecode-cmdk-cn-depset-package-reviews.md:559-560,604-605`. Limit: that probe was not rerun; current source preserves the distinction.

- **A command wrapper forwards the arguments it advertises.** July's plate-pkg accepted trailing arguments but silently discarded them. Strip one optional separator, then pass the remaining arguments to the selected command. Evidence: c70bacbd4a:docs/plans/2026-07-14-plate-next-plate-plate-scripts-test-utils-package-reviews.md:250 and :161. Current tooling/scripts/run-with-pkg-dir.cjs:12-14 parses that contract, and its build, lint, test and typecheck branches pass commandArgs onward. This lesson concerns forwarding, not the historical list of eight command paths.

- **Migration exceptions must match live imports in both directions.** The July app audit removed two upstream-Slate quarantine rows whose imports had disappeared, while retaining the genuine comparison pane (`docs/plans/2026-07-15-plate-next-apps-www-migration-closure.md:511-524`, `:535-536`). Check both that every exception still matches source and that every live exceptional import has a reason. A zero-import badge obtained by deleting an independent baseline misrepresents the migration. Current `apps/www/src/registry/examples/huge-document-demo.tsx:26-28` still imports legacy upstream `slate` and `slate-react` directly; Plate construction uses Plite in `packages/platejs/src/lib/editor/withPlite.ts`. This lesson does not carry forward the July exception counts.

- **Validate lifecycle directories before choosing a build root.** The July Media build investigation first preferred INIT_CWD blindly and selected the wrong root. The repair checks both candidate directories, prefers the package cwd and uses INIT_CWD only as a fallback. Current `resolvePlatePackageRoot` accepts a candidate only when it contains package.json and src/index.ts or src/index.tsx (`tooling/config/tsdown.config.ts:15-42`). The invoking-package contract checks package cwd against repository INIT_CWD and helper cwd against package INIT_CWD (`tooling/scripts/check-package-build-artifacts.test.mjs:508-540`). Source: `docs/plans/2026-07-23-plate-next-media-full-colocation.md:736-738`, with the failed first choice recorded at line 758. Limit: this resolves the repository's package build layout; no builds or tests were rerun for this compilation.

- **An archive part is a real module boundary.** The DOCX cleanup retained separate OOXML generators even when each had one assembly consumer, because each produces a distinct zipped document or relationship part. A consumer-count rule alone would merge those format boundaries into the assembler. Source: `c70bacbd4a:docs/plans/2026-07-27-plate-next-sync-all-packages-v17.md:1486-1488`. Current evidence is the separate content-types, document, numbering, font-table and relationship generators under `packages/platejs/src/docx/export/lib/internal/schemas/`. Limit: a one-use helper inside a part generator does not acquire the same independent boundary.

- **Source checks and integration checks can load different package bytes.** In the June automation, source unit and type checks passed after adding a screenshot helper, but Playwright failed with `attachPageScreenshot is not a function` because integration imported the package's old built export. Rebuilding the package made the same rows pass. Establish whether the consumer resolves source or built exports before interpreting its failure, and rebuild the artifact it actually imports. Evidence: `c70bacbd4a:docs/plans/2026-06-10-plite-8h-automation.md:693`. The former `plite-browser` package is now represented by `packages/test`; the historical command is not a current command recipe.

- **Keep build output out of a captured JSON report.** The June async integration repair initially fixed stale package exports by routing Playwright through a build wrapper. That wrapper could print banners before the JSON reporter payload, corrupting `report.json`. The final repair ran the build separately and captured only the reporter's stdout; an actual focused async run then produced parseable JSON. Evidence: `c70bacbd4a:docs/plans/2026-06-10-plite-8h-automation.md:695`, with the smoke run `2026-06-10T16-49-45-156Z` at lines 990-1002. This is a report-producer lesson; the old async runner and commands are historical.

- **Check filename casing through directory entries.** A June draft-Plite audit used `existsSync` for both `README.md` and `Readme.md` and falsely reported duplicate files on a case-insensitive filesystem. Reading the directory entries showed one actual file and supplied the exact casing needed by case-sensitive CI. Source: `docs/plans/2026-06-14-plite-public-api-taste-and-beta-readiness-10h.md:888`. Use directory enumeration when the claim concerns spelling or duplicate casing. Limit: the seven-package README guard was part of the retired draft layout; the reusable lesson is the filesystem distinction.

- **Source JSDoc is not proof of consumer hover documentation.** The June draft-Plite hook documentation pass rebuilt declarations and inspected the emitted declaration bundle so consumers received the new explanations; looking for per-hook declaration files first failed because tsdown flattened them. Source: `docs/plans/2026-06-14-plite-public-api-taste-and-beta-readiness-10h.md:2710-2714`, `:2725-2730`. Inspect the declaration target named by the package export map after a public documentation change. Current hook documentation lives beside `useEditor` in `packages/plitejs/src/react/hooks/use-editor.ts`, while `packages/plitejs/package.json` names the distributed declaration targets. Limit: this does not certify today's emitted bundle or preserve the old bundle layout.

- **Test installation from the packed artifact.** The June 2026 draft passed workspace checks while its packed plite-react manifest still contained a consumer dependency on `workspace:*`; npm rejected installation with `EUNSUPPORTEDPROTOCOL`. Inspect the packed manifest and install the local tarballs in a separate consumer. Workspace resolution cannot prove the published dependency graph. The old split packages are retired; this is historical packaging evidence, not a prescription to replace workspace protocols in today's source manifests. Source: `c70bacbd4a:docs/plans/2026-06-14-plite-public-beta-readiness-review.md:481`.

- **Resolve workspace roots and subpaths through one module graph.** During the June 2026 transplant, package tests mixed built and source imports, and React tests reported `Editor transform registry has not been initialized`. A Bun source resolver and an exact core source alias repaired the split (c70bacbd4a:docs/plans/2026-06-17-plite-transplant-checkpoint-3-tooling-parity.md:172-174, :184, :215-218). Today's resolver derives root and subpath entries from package exports and redirects both package specifiers and built entries to source (`config/plite-source-aliases.ts:8-39`, `config/workspace-source-entries.mjs:29-80`). Identity still matters: Plite keeps plugin registries in a module-local WeakMap (`packages/plitejs/src/core/plugin-registry.ts:126`), and Plate imports both `plitejs` and `plitejs/internal` (`packages/platejs/src/facade.ts`). Check resolution before patching editor initialization when cross-package tests alone fail. Limit: the historical transform-registry error and separate React package belong to the draft fork; this source inspection does not reproduce that old failure.

- **Prism grammar loading has an execution order that import sorting can break.** The August 2026 production route failed because grammar side effects evaluated before global Prism initialization. Current apps/www/src/app/(app)/examples/plite/_examples/utils/prism-runtime.ts requires Prism first and then its CommonJS grammars, with TypeScript before TSX. The helper's comments explain why these calls remain imperative. Source: c70bacbd4a:docs/plans/2026-08-21-fix-plite-package-metadata.md:108. This applies to that Prism 1.x side-effect loader, not to syntax-highlighting modules generally.

- **Import permission and execution dependency answer different questions.** Consolidating packages initially turned every allowed import into required work, rerunning unrelated checks. Keep public entrypoint permissions separate from internal task partitions, and derive each task's dependencies from the imports its source, tests or contracts actually use. Generate runtime-test tasks only for partitions that own tests. Keep builds atomic while one build tool cleans a shared `dist`. Evidence: `c70bacbd4a:docs/plans/2026-08-28-platejs-plitejs-turbo-ci-closure.md:324-340`, following the earlier same-day entrypoint plan. Current `tooling/entrypoints/entrypoint-dag.mjs` and `entrypoint-turbo.mjs:366-413,448-466` retain the partition/import-closure split. Historical task totals are not current graph limits.

## Templates and CI

- **The template updater runs `pnpm dlx shadcn@latest add`.** The `npx shadcn@latest` form failed only in GitHub Actions, with `ERR_MODULE_NOT_FOUND` for the transitive `tinyexec`, and the script has no comment saying so. Code: `tooling/scripts/update-template.sh:134-137`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-03-13-template-update-script-should-not-own-ci-verification.md`.
- **Bun can nest stale workspace packages under a local tarball.** Installing a local `platejs` tarball can still leave stale published workspace packages under `node_modules/<pkg>/node_modules/`, so a new export looks missing ("Export X doesn't exist in target module") while the source build is green. Template prep packs the changed package and its template-facing dependents and writes an `overrides` entry for every packed tarball. The local tarball showing in `bun install` output proves nothing; check for nested workspace copies. Code: `tooling/scripts/prepare-local-template-packages.mjs:487-499`, `prepare-local-template-packages.test.mjs:44`. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-03-28-template-local-package-overrides-must-cover-transitive-exports.md`.
- **Reproduce registry and template workflow failures with `gh act`.** Run `gh act pull_request -W .github/workflows/registry.yml -j validate-registry` or `-W .github/workflows/ci-templates.yml -j ci` before pushing a CI fix. act needs a running Docker daemon and fails at once with "Cannot connect to the Docker daemon" without one. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-03-13-template-update-script-should-not-own-ci-verification.md`.

- **The template updater generates; the workflow verifies.** In March 2026 `registry.yml` ran `pnpm templates:update --local`, and the updater also ran its own lint and typecheck, so a registry sync failed inside the helper on unrelated typecheck noise and looked like a registry problem. Patching template-local lint configuration only moved the failure. Now `tooling/scripts/update-template.sh` always runs `bun lint:fix` after generation and skips its own `bun typecheck` when `TEMPLATE_SKIP_VERIFY=true` (`:20-22`, `:147-157`), which `.github/workflows/registry.yml:70`, `:151`, `release.yml:405` and `sync-templates.yml:53` set; the workflow then builds each template itself (`registry.yml:81-89`). Keep checks out of generator scripts that CI calls. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-03-13-template-update-script-should-not-own-ci-verification.md:26-34`, `:44-74`.

- **Branch on `$#` instead of expanding a possibly empty argument array under `set -u`.** `tooling/scripts/update-templates.sh` runs under `set -euo pipefail` and passes `"$@"` to `update-template.sh` only inside `if (($# > 0))`, calling it with no arguments otherwise (`:3`, `:7-13`). In March 2026 the wrapper expanded an `EXTRA_ARGS` array instead, and `pnpm templates:update` with no arguments died before any template work with `EXTRA_ARGS[@]: unbound variable`, which looked like a template failure. The script's `#!/bin/bash` is bash 3.2 on macOS, and on 2026-10-08 `/bin/bash -c 'set -u; A=(); echo "${A[@]}"'` still failed there with `A[@]: unbound variable`. The branch has no comment, so keep it when simplifying the script. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/solutions/developer-experience/2026-03-25-templates-update-check-need-arg-safe-wrapper-template-scoped-lint-and-ts6-baseurl-opt-out.md:34-42`, `:77-93`. Limit: only macOS bash 3.2 was run; a newer bash may expand an empty array under `set -u` without error.

- **The template updater rewrites React Day Picker calendar output.** The registry's calendar source and `shadcn@latest` can target a different React Day Picker major than the templates install: `apps/www` pins `react-day-picker` 8.10.1 while `templates/plate-playground-template` depends on `^10.0.1`. In May 2026 template validation failed first because v9.14's default class names have `month_grid`, not `table` ("'table' does not exist in type 'Partial<ClassNames>'"), then because v10 replaced `initialFocus` with `autoFocus`. `normalize_react_day_picker_api` in `tooling/scripts/update-template.sh:62-73` runs after `shadcn add` and rewrites `table:` and `defaultClassNames.table` to `month_grid` in `src/components/ui/calendar.tsx` and `initialFocus` to `autoFocus` in `src/components/editor/date.tsx`; the function has no comment. A type error in generated shadcn UI is fixed in this updater or in registry source, never in `templates/**`.
