# Lexical: tables

## Table paste

- **Table paste rows.** `TablesHTMLCopyAndPaste.spec.mjs` pastes tables copied from:
  - Google Docs, with multi-paragraph cells and 11pt text;
  - Google Docs with custom column widths in `<col>` and `<colgroup>`;
  - Quip, where a `b<br>b` cell keeps its line break;
  - Google Sheets.

  It also merges a pasted grid into an existing table, pastes nested block and inline HTML into cells, and fills merged cells, unequal rows and an empty row. The width, merge, rowspan and colspan rows are table-model decisions, not HTML-parser rules. Source: `docs/editor-test-harvester/lexical/plite-processing-ledger.md:180-186`, extracted on 2026-05-09 from an unpinned Lexical checkout. Limit: row topics only, not rerun.

- **Pasting a table into a table.** Lexical's table plugin flattens a single pasted table onto the destination when the selection sits inside table cells (`facebook/lexical@dd5c41b1:packages/lexical-table/src/LexicalTablePluginHelpers.ts:466-485`) through `$insertTableIntoGrid` (`facebook/lexical@dd5c41b1:packages/lexical-table/src/LexicalTableUtils.ts:1446-1560`). From a caret in a cell it places the pasted grid at that cell and adds rows and columns as needed; from a `TableSelection` it starts at the selection's top-left cell and clips the pasted grid to the selected rectangle, never repeating it; it unmerges merged cells in the affected area before writing. `TableSelection.insertRawText` turns tab-separated text into a table and pastes it the same way (`facebook/lexical@dd5c41b1:packages/lexical-table/src/LexicalTableSelection.ts:229-252`), while `insertNodes` falls back to a range over the focus cell (`:280-290`). `TableCellNode` keeps `colSpan`, `rowSpan`, width, background color and vertical alignment (`facebook/lexical@dd5c41b1:packages/lexical-table/src/LexicalTableCellNode.ts:45-105`). Read 2026-10-08; the June run (`docs/plite/research/2026-06-12-table-fragment-semantics/read-log.tsv:12-14`) read an older unpinned checkout and saw only the selection and export side. Limit: source read, no Lexical test run.

## Table tests

- **Table tests rest on the table-selection model.** Lexical's table behavior is tested in:
  - `Tables.spec.mjs`: whole-table, range, merge and rowspan selection;
  - playground regressions #4661 (insert a column under a table selection), #4697 (repeat a table selection), #4872 (merge cells across a full row span), #4876 (unmerge a cell), #6870 (left-arrow table selection) and #7266 (merged cells in a column header), each a file named after its issue under `facebook/lexical@dd5c41b1:packages/lexical-playground/__tests__/regression/`;
  - `lexical-table` unit tests for `TableCellNode`, `TableNode`, `TableRowNode`, `TableSelection` (#2558), `TableUtils`, `TablePlugin`, `TableExtension` and `TableMobileSelection`.

  All of it depends on Lexical's table-cell selection and merge model, so a port goes through a table-selection owner, never a generic selection test, and the mobile file needs touch proof on a device, not a desktop viewport. Source: `docs/editor-test-harvester/lexical/plite-processing-ledger.md:824-833`, `:88-89`, `:877-878`, `:881`; every named file exists at dd5c41b1. Limit: the regression topics come from file names and the ledger's notes, not from their assertions.

- Two Lexical table e2e tests are weaker oracles than they look (facebook/lexical@dd5c41b13193efa9ab1574234d8593d2c9e4f988, bodies reread 2026-10-08, not run). 'Resize row with merged cells spanning multiple rows' rewrites whatever row height the browser produced to the expected `69px` before comparing HTML (facebook/lexical@dd5c41b1:packages/lexical-playground/__tests__/e2e/Tables.spec.mjs:8101, :8197-8202). 'Drag-select column in 2x2 table selects all cells in that column', the regression test for #8079 (:9062, :9211), dispatches synthetic pointer events when the real mouse drag does not produce the expected selection (:9138-9200), so it passes even when the natural drag fails. Neither proves exact natural-drag resizing or selection: a synthetic fallback cannot close a failed natural gesture (docs/plite/research/2026-09-17-table-substrate-ownership/REPORT.md:242-245).

## Table selection tests

- Lexical's table selection tests at dd5c41b1. 'Triple-clicking last cell in table should not select entire document' (`facebook/lexical@dd5c41b1:packages/lexical-playground/__tests__/e2e/Selection.spec.mjs:1404`) triple-clicks the text of a table's last cell and expects the selection to cover only that cell's text. 'Selecting table cell then dragging to outside of table should select entire table' (`:1459`) presses the mouse in the last cell and moves below the table without releasing. The selection then runs from the table's first cell to the end of the paragraph after it, because Lexical promotes a drag that leaves a table to the whole table. 'touch tap on single cell should not create table selection' (`facebook/lexical@dd5c41b1:packages/lexical-table/src/__tests__/unit/LexicalTableMobileSelection.test.tsx:137`) fires a synthetic `pointerdown` with `pointerType: 'touch'` on one cell and expects a range selection, not a table selection. It is a jsdom unit test, not device proof. Source: `docs/editor-test-harvester/lexical/report.md:178-180`; bodies read at dd5c41b1 on 2026-10-08.

- Lexical's table drag regression 'Click and drag to create selection in Firefox #7245' (`facebook/lexical@dd5c41b1:packages/lexical-playground/__tests__/e2e/Tables.spec.mjs:7501`) is named for Firefox but runs in every browser project, skipping only plain text and collaboration. In a 5x5 table it drags with `dragMouse` and `slow: true` (ten mouse moves) from the second cell of the second row to the fourth cell of the fourth row, keeps the button down, and asserts the table HTML for that 3x3 box before mouse-up. Source: `docs/plite/research/2026-06-12-browser-longtask-selection-oracles/read-log.tsv:10`; the June read cited lines 6128-6138, and the body was read at dd5c41b1 on 2026-10-08.

## Selection and resizing

- Lexical's table selection is optional and implements the core `BaseSelection`, table observers own browser behavior, and the playground supplies one editor-level `TableCellResizer` with two handles on the active cell (facebook/lexical@dd5c41b13193efa9ab1574234d8593d2c9e4f988:packages/lexical-table/src/LexicalTableSelection.ts; facebook/lexical@dd5c41b1:packages/lexical-table/src/LexicalTableObserver.ts; facebook/lexical@dd5c41b1:packages/lexical-table/src/LexicalTableSelectionHelpers.ts; facebook/lexical@dd5c41b1:packages/lexical-playground/src/plugins/TableCellResizer/index.tsx; read 2026-09-17, changed hunks reread at 4973ca1782ea4278adc496c75eab464a0887bf00). Structural selection and editing stay available below React, and the newer source fixes earlier cleanup gaps, but explicit cancellation and logical resize directions were not assessed (docs/plite/research/2026-09-17-table-substrate-ownership/REPORT.md:48,140-141; read-log.tsv:74-117).
