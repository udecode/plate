# Slate: clipboard and paste

## Fragment transfer format

- **Slate's fragment transfer format.** On copy, Slate's `setFragmentData` JSON-stringifies the fragment, encodes it as `window.btoa(encodeURIComponent(string))` and writes it to a `data-slate-fragment` attribute in the copied HTML and to `application/${clipboardFormatKey}`; on paste, `insertFragmentData` reads that MIME type and otherwise matches `/data-slate-fragment="(.+?)"/` anywhere in the `text/html` string (`ianstormtaylor/slate@945a484df:packages/slate-dom/src/plugin/with-dom.ts:306-310`, `:329-344`; `ianstormtaylor/slate@945a484df:packages/slate-dom/src/utils/dom.ts:250-256`). `withDOM` and `withReact` have taken `clipboardFormatKey`, default `'x-slate-fragment'`, since PR #5267 (2023-02-09) (`ianstormtaylor/slate@945a484df:packages/slate-dom/src/plugin/with-dom.ts:49-51`), so #3486 and #5233 asked for a key Slate already accepted. The key renames only the MIME type: the HTML attribute stays `data-slate-fragment` and is read whatever the key, so editors with different keys still take each other's HTML fallback, and pasted HTML whose text contains the attribute string matches too (#5328). Plite keeps the same encoding (`packages/plitejs/src/dom/plugin/dom-clipboard-runtime.ts:354-361`), tags the HTML fallback with a `data-editor-fragment-format` attribute that must equal the editor's key (an untagged fragment counts as the default key), and reads both attributes only from opening tags (`packages/plitejs/src/dom/utils/dom.ts:267-295`); the slate issues page's 'Custom clipboard format keys (#3486, #5233)' and 'Paste and copy fragment policy' entries give Plite's tests. #3487 asks why the base64 step exists.
