# Slate: issues and regressions

## Core model, operations, normalization and history

- **Normalization (#3950, #5811, #2039, #3465, #2355, #3275, #4701, #4641).** Plite calls normalizers corrections. A correction runs on a `children`, `content` or `properties` event and receives `{ editor, entry, tx }` (`packages/plitejs/src/interfaces/editor.ts:2435-2456`), so corrections stay entry-based, with no path-only `normalizeNode` (#3275), and no correction event covers the selection (#2355). Plite rechecks a node that a correction changed until it reaches a fixpoint ('rechecks a corrected node until it reaches fixpoint', `packages/plitejs/test/normalization-contract.ts:974`), which is the ledger's fix for #3950 (re-normalizing a transformed node). It fails deterministically when a correction revisits an earlier draft state and reports correction cycles with a deterministic transition fingerprint (`packages/plitejs/test/normalization-contract.ts:931`, `:1251`), which improves Slate's 'Could not completely normalize the editor' loop (#5811); conflicting app corrections stay app or schema work, and no separate named or stack diagnostic is claimed for #2039. An invalid initial value is repaired only by the explicit maintenance call `editor.update.value.repair()` (`packages/plitejs/test/normalization-contract.ts:34`), so automatic normalization of `initialValue` (#3465) is not claimed. Command-owned selection targets survive canonical repair, as 'preserves the caret inside text merged during automatic canonicalization' shows (`packages/plitejs/test/normalization-contract.ts:361`). No custom empty-text factory is claimed for #4701, and #4641's property-update case lacks exact package proof. Source: `c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:21-34`, hydrated on 2026-07-12, which supersedes the older rows for these issues.

- **History and selection (#3534, #3551, #4559, #3499, #3705, #3921, #3756).** The ledger keeps fix claims for four undo reports, each with a matching contract in `packages/plitejs/test/history/history-contract.ts`. #3534 (selection broken after undoing): undo after Enter over a selection spanning three blocks restores the document and that selection ('restores the saved multi-block selection after insertBreak and undo', `packages/plitejs/test/history/history-contract.ts:2148`). #3551 (undoing `move_nodes` gives the wrong state): undo after a `moveNodes` commit restores the original tree and selection (`packages/plitejs/test/history/history-contract.ts:2211`). #4559 (`deleteFragment` undo should select the reinserted fragment): undo reselects the restored text, also after blur and refocus (`packages/plitejs/test/history/history-contract.ts:2078`, `:2100`). #3499 (marks on a selected word moved to a new line): Enter at the start of a bold word moves the bold run into the new block, and undo restores the paragraph, its marks and the selection (`packages/plitejs/test/history/history-contract.ts:2167`). Ledger rows: `c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:223`, `:625`, `:765`, `:776`, `:944`. For #3705 and #3921 ('Cannot apply an incomplete set_selection operation properties', the second after history refocus), the ledger records partial undo coverage as improvements; the nearest current contract is 'does not replay partial selection range patches after selection is cleared' (`packages/plitejs/test/history/history-contract.ts:2029`), and the ignored-template case of #3705 and the refocus browser case of #3921 are unproven. #3756 (slate-history does not undo selection movement) stays related (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:330-332`). Limits: these rows rest on the fork dossier, deleted in `c5a1fc3f17` on 2026-10-08; no test carries an issue tag, so matching tests to issues is inferred from their titles; and the ledger contradicts itself on #3756 (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:331` says cluster-synced, `:617` triage-closed).

- **Collaboration (#5533, #1770, #2288, #3741, #5771).** Plite transactions build a canonical `DocumentChange` rather than a Slate operation list (`docs/vision/plite.md:26-28`). Core replay of text, mark, range-delete and move commits converges three package peers ('converges three peers across text, mark, delete, and move commits', `packages/plitejs/test/collab-history-runtime-contract.ts:290`), and a range delete is stored as one canonical undo batch (`packages/plitejs/test/collab-history-runtime-contract.ts:453`). Through the Yjs binding, offline same-parent and cross-parent moves reconnect with concurrent remote text kept, and undo and redo touch only the local move (`packages/plitejs/test/yjs/move-node-contract.spec.ts:105-258`). For #5771 (an exception between select and anchor operations in collaboration), core contracts keep a local collapsed selection valid through remote prefix bursts, same-offset contention, suffix inserts, split and merge, and removal of the selected node (`packages/plitejs/test/collab-selection-stress-contract.ts:111-199`), and anchor rebasing and remote canonical reconcile have their own contracts (`packages/plitejs/test/collab-anchor-position-contract.ts`, `packages/plitejs/test/collab-canonical-reconcile-contract.ts`). The ledger keeps #5533 (collaboration without Yjs), #1770 (combining operations), #2288 (range operations) and #3741 (a moved-node payload for OT undo) related, and claims an improvement for #5771 (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:440`, `:525`, `:623`, `:626`, `:877`). Limits: Plite ships no first-party OT or Yjs-free protocol, no general operation-composition utility and no moved-node payload; exposing range operations publicly is a separate API decision; and #5771 has no real adapter or browser repro.

- **Core deletes stay inside the selection (#4121, #3965).** For #4121 (deleting selected text deletes all preceding text under some conditions), an expanded delete across bold, plain and italic leaves removes only the selected content and collapses at the selection start ('deletes only the selected formatted leaf window', `packages/plitejs/test/delete-contract.ts:600`). For #3965 (a deletion bug at a marked block start), Backspace at the start of a block whose first leaf is an empty bold leaf merges it into the previous bold paragraph and keeps the text on both sides ('merges same-mark text when Backspace crosses an empty marked block start', `packages/plitejs/test/delete-contract.ts:809`). The ledger claims both fixes (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:835`, `:864`). The `plate-notes` selection page holds the delete lessons for #5972, #5847 and #2500.

- **History grouping, change provenance and undo shortcuts (#3874, #4178, #4046).** Three dossier reports ask for history and change metadata Slate lacks: explicit undo groups instead of groups inferred from the operation stream (#3874), a way to tell local, remote and programmatic changes apart once collaboration middleware strips metadata (#4178), and undo and redo shortcuts that work on a Cyrillic layout (#4046) (`c70bacbd4a:docs/plite-issues/open-issues-dossiers/3878-3798.md:50-97`). Plite's update policy takes `history: 'merge' | 'new-batch' | 'skip'` and `tags` (`packages/plitejs/src/interfaces/editor.ts:882-887`), and 'uses update policy to push, merge, and skip history batches' checks two, one and zero undo entries (`packages/plitejs/test/history/history-contract.ts:1571`). Each commit records its tags, canonical ones such as `collaboration`, `paste`, `native-text-input` and `historic` next to app tags (`packages/plitejs/src/interfaces/editor.ts:860-877`; `packages/plitejs/test/commit-metadata-contract.ts:633`, `:712`). The undo matcher accepts Ctrl with the `KeyZ` physical code when the key is a non-ASCII letter such as `я`, but not on an ASCII remapped layout (`packages/plitejs/test/dom/hotkeys.ts:129`, `:138`). Limits: removing the built-in undo hotkey (#3952) and history memory retention (#3752) are not claimed.

- **Enter at link and mark ends (#4334, #3772, #3964, #4195, #4357, #3841, #4704).** The dossiers hold five reports of Enter going wrong at the end of a link or a marked run: an empty link appears in the next paragraph (#4334, #3772), or the new block is created while the caret or focus stays behind (#3964, #4195, #4357) (`c70bacbd4a:docs/plite-issues/open-issues-dossiers/4390-4269.md:401-449`). In Plite, `insertBreak` at the end of bold text creates a paragraph whose empty leaf keeps the bold mark and puts the selection there (`packages/plitejs/test/snapshot-contract.ts:1508`). In the inlines example, Enter right after a typed URL that became a link moves the caret to the next block, leaves one link, and keeps the next typed text outside it ('places Enter after a typed inline link outside the link', `apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:362`, desktop projects). The `plate-notes` model page gives the cause of the empty link: an inline left holding the caret makes the next Enter split from inside it. Limits: the Firefox caret move after a custom `insertBreak` (#3841) and leaving a trailing inline at the end of the editor (#4704) are not claimed.

- **Deletes next to voids (#4896, #4367, #4350, #3868, #4730, #5435, #5477).** Seven dossier reports delete the wrong thing or lose the caret next to a void: deleting the node after a void also deletes the void (#4896, #4367), deleting a void at a line start sends the caret to the previous line (#4350), `removeNodes` over a selection with voids deletes neighbouring text (#3868), select-all and Backspace with a trailing image leaves the wrong paragraph (#4730), deleting text together with a read-only element crashes (#5435), and deleting the only void leaves a state that throws on the next keystroke (#5477) (`c70bacbd4a:docs/plite-issues/open-issues-dossiers/4963-4842.md:601-649`). Plite path-deletes an adjacent void as one atom and keeps the caret, the mechanism the `plate-notes` selection page states. Delete in a selected block void removes the void, keeps the next paragraph's text and leaves the caret at its start (`packages/plitejs/test/delete-contract.ts:231`). In the images example, Delete at the start of the paragraph after an image removes one character and keeps the image (`apps/plite/tests/plite-browser/donor/examples/images.test.ts:881`, desktop projects), and Backspace in an empty paragraph after an image removes the paragraph first, as the #3991 entry states. Limits: these back #4896 and #4367 by shape, not by replaying them, and #4350, #3868, #4730, #5435 and #5477 have no matched Plite row.

- **Reused node objects (#5874, #4309, #3802).** Three ledger rows trace Slate failures to one node object placed at two paths: inserting the same node more than once desyncs later edits and focus (#5874), inserting several nodes that share one object reference causes a React key error (#4309), and the docs do not explain how node object references behave (#3802) (`c70bacbd4a:docs/plite-issues/open-issues-ledger.md:512`, `:1024`, `:703`). Slate keys DOM lookups by node object: `findKey` caches one key per object, and `findPath` reads one cached index and parent per object (`ianstormtaylor/slate@945a484df:packages/slate-dom/src/utils/weak-maps.ts:21-22`, `:35`; `ianstormtaylor/slate@945a484df:packages/slate-dom/src/plugin/dom-editor.ts:379-417`), so two paths that hold one object share a key and a cached path. Plite stores its own frozen copies: splicing children clones each inserted node by default with `cloneFrozen`, a `structuredClone` followed by a deep freeze unless the value is already one the editor owns (`packages/plitejs/src/core/change/document-index.ts:325`, `:331`; `packages/plitejs/src/core/clone.ts:16-17`, `:33-34`), and 'finds a node path by object identity' resolves the editor's own nodes and returns no path for a structurally equal object from outside (`packages/plitejs/test/state-query-contract.ts:236`). A scratch run on 2026-10-08, not committed, inserted one object twice, in two `tx.nodes.insert` calls and in one array, and got two distinct stored nodes with distinct node keys, neither of them the caller's object; editing one left the other and the caller's object unchanged; and two editors created from the same deep-frozen `initialValue` objects shared no node object, the setup #6016 reports. Limits: the run covered the core only, with no React render or DOM bridge; which entry points reach the cloning splice was not traced; and committed tests pin only the content-slice cases: one slice inserted twice yields distinct objects and node keys (`packages/plitejs/test/content-slice.test.ts:210`), and editor fragments are detached before insertion (`:124`).

## Selection, focus and DOM bridge

- **Nested editors and editable void content (#5212, #2072, #4984, #4842, #3909, #3482, #3367).** Slate's reports here ask for editing inside voids, an island component, void children, or nested editors that do not break DOM point resolution. Plite keeps default voids atomic and answers nested editors with a same-runtime child root that the element declares in its schema. The editable-voids example declares `'editable-void': { contentRoots: { body: ... }, void: 'block' }`, names each body root `editable-void:<id>:body`, and creates it with `tx.roots.create` before it inserts the node (`apps/www/src/app/(app)/examples/plite/_examples/editable-voids.tsx:35`, `:111-123`, `:240-241`). Renderers mount the root with `useContentRoot(element, { slot })` (`packages/plitejs/src/react/hooks/use-plite-content-root.ts:28`), and a content root is `exclusive` or `shared` (`packages/plitejs/src/interfaces/schema.ts:317`). Browser rows cover editing, focus, paste, copy and cut, drop, undo, redo and keyboard selection across the child root, such as 'extends keyboard selection from editable void child root into outer siblings' (`apps/plite/tests/plite-browser/donor/examples/editable-voids.test.ts:960`). The ledger keeps a fix claim only for #4984, which the DOM point family entry states, and holds #5212, #2072, #4842 and #3909 as related or cluster-synced (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:118-122`). Child roots do not answer Slate's inline-void mobile (#5183, #5391), inline-void clipboard (#4806, #4802, #4104, #3926), drop and drag (#4888, #4623), spacer and cursor (#5087, #5411, #3611, #3435, #3449, #4839), Firefox embed caret (#4110), deep-nested emptying (#3858) or external focus (#1769, #3893) reports (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:123-132`). Limits: the 2026-05-24 plan also kept an `editable-island` mode for native controls, which was later removed (`packages/plitejs/src/core/schema-compiler.ts:1353-1354`). Current law requires independent addressing, lifecycle, sharing or transaction semantics for an explicit root, and models a block whose identity stands apart from its editable children as `object: true` with normal children (`docs/vision/plite.md:530-544`).

- **Blur, unfocused updates and spellcheck (#4376, #5171, #5095, #5096).** For #4376 (Safari: the selection becomes null when the editor blurs), Plite keeps the model selection when focus moves to an outside input ('keeps model selection when focus moves outside the editor', `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:3125`). For #5171 (Firefox makes an invalid selection update on editor change while the editor is unfocused), an unfocused editor's update does not import an outside input's DOM selection ('keeps unfocused editor updates from importing external selection', `apps/plite/tests/plite-browser/donor/examples/document-state.test.ts:109`, desktop projects only). The ledger claims both fixes on 2026-05-23 and describes the #4376 WebKit proof as also refocusing and typing at the kept point (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:147-148`). Limits: the current row stops at the selection check, and the `webkit` project runs only on macOS hosts (`apps/plite/playwright.config.ts:72-88`). For #5095 and #5096 (Safari spellcheck with Cyrillic text), 'keeps Cyrillic input stable with spellcheck enabled' (`apps/plite/tests/plite-browser/donor/examples/document-state.test.ts:474`) guards typed Cyrillic text only, not Safari's spellcheck UI or dictionary, so neither issue is claimed (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:149`).

- **Refocus scroll, and what TanStack's iOS fix does not prove (#5826 and others).** For #5826 (unexpected auto-scroll when the editor is refocused), Plite's huge-document row clicks the top block, moves focus out, scrolls to the final block and clicks back in, and then keeps the clicked final-block selection visible instead of restoring the top one ('keeps clicked refocus position visible in a long editor', `apps/plite/tests/plite-browser/donor/examples/huge-document.test.ts:2138`, desktop only). 'does not scroll to top when refocusing a scrollable editor' covers a scrollable richtext editor (`apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:3301`, desktop only). The ledger claims the fix (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:240`, `:353`, `:422`). Plite's virtualized rendering uses TanStack Virtual through an optional `@tanstack/react-virtual` peer (`packages/plitejs/package.json:214`, `:224`; `packages/plitejs/src/react/virtualized/use-virtualized-root-plan.ts`). TanStack's iOS momentum-scroll handling is not proof for Slate's focus and selection scroll reports (#5538, #4995, #5088, #5473), nor for its iOS selection, IME, spellcheck or native toolbar reports (#5391, #5095, #4751, #4354, #3760). Each needs a targeted browser repro or a raw iOS run before any claim (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:241-242`).

- **Zero-width placeholders (#5760, #2597, #1971).** Plite keeps the U+FEFF sentinel in empty-text, inline-edge, void-spacer and mark placeholders and drops it only in line-break placeholders, which render a bare `<br>` (`packages/plitejs/src/react/components/zero-width-string.tsx:7`, `:27-41`; `packages/plitejs/src/react/components/editable-text-flow.tsx:519`). `docs/research/sources/plate-notes/input-and-events.md` gives the IME reason. So the ledger claims neither #2597 (U+FEFF as a zero-width no-break space is deprecated) nor #1971 (use `<br>` for zero-width white space) (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:433`, `:979`). For #5760 (`setStart` called with offset 1 on a zero-length text node), it claims an improvement: the DOM bridge maps a zero-width DOM point back to the Plite start offset and adjusts zero-width DOM offsets when it converts a collapsed Plite range (`packages/plitejs/test/dom/bridge.ts:1321`, `:1519`; ledger `c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:443`). Limits: no raw iOS device run backs #5760, and the real-browser test that the #2597 and #1971 rows cite only checks that a test helper reads both placeholder shapes (`packages/test/test/browser/zero-width.browser.test.ts:5-30`).

- **The 'Cannot resolve a DOM point' family (#4984, #4789, #4564, #4088, #5947, #5938).** Slate throws when a selection or lookup crosses DOM that the editor does not own. Plite imports a native selection only when both endpoints belong to the editor (`docs/research/sources/plate-notes/selection-and-editing.md` states the mechanism), and its DOM bridge resolvers return `null` instead of throwing: `resolveDOMNode`, `resolveDOMPoint`, `resolveDOMRange`, `resolveEventRange`, `resolvePath` and `resolveRangeRect` (`packages/plitejs/src/dom/plugin/dom-editor.ts:188-193`). The ledger claims fixes for two reports. For #4984 (selecting over a nested editor throws), a parent selection that crosses into a same-runtime child root is ignored with no runtime error ('ignores a parent selection that crosses into a same-runtime child root', `apps/plite/tests/plite-browser/donor/examples/editable-voids.test.ts:1381`, desktop only). For #4789 (a selection that starts outside the editor and ends inside it throws), such a native selection is ignored and the editor still takes typing after refocus ('ignores a native selection that starts outside the editor and ends inside it', `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:5778`). It claims improvements for two lookup reports: for #5947 (`toSlatePoint` can find a point in a parent editor), the bridge refuses path-tagged nodes outside its editor and keeps parent and nested editor points apart (`packages/plitejs/test/dom/bridge.ts:367`, `:554`); for #5938 (`findPath` returns no or the wrong path), lookup falls back to mounted path and runtime metadata when the weak maps lag (`packages/plitejs/test/dom/bridge.ts:169`, `:190`). #4564 (removing content programmatically throws) rests only on a model test that replaces the document and clears the selection in one transaction (`packages/plitejs/test/state-tx-public-api-contract.ts:199`). #4088 (the mention example's range logic throws) stays related until a mention browser row replays it, and none of the current mention tests is named for it. Ledger rows: `c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:394`, `:397`, `:670`, `:694`, `:703`, `:847`. Limits: the #4984 proof covers a same-runtime child root, not a second React editor mounted inside a void; the #4789 row builds the outside-to-inside range in script with `addRange` and a dispatched `selectionchange`, with no pointer drag (`apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:5811-5820`), so the reporter's drag from outside the editor is not replayed; and the exact Slate repros of #5947, #5938 and #4564 were not replayed.

- **Block-level gestures around blocks, voids and tables (#3871, #4301, #3991, #6034).** Browser rows on the raw Plite examples prove four Slate reports that the ledger marks fixed. For #3871 (triple-clicking selects part of the block below), a triple-click on the first richtext paragraph selects that block only, from `{ path: [0, 0], offset: 0 }` to `{ path: [0, 6], offset: 1 }` ('selects the current block on browser triple click', `apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:7254`), and Backspace or typing after a triple-click removes or replaces that block (`apps/plite/tests/plite-browser/donor/examples/richtext.test.ts:7310`, `:7353`). For #4301 (a slate-react 0.62 regression broke void selection), Enter or Shift+Enter on a clicked image inserts an editable paragraph after it, and typing lands there (`apps/plite/tests/plite-browser/donor/examples/images.test.ts:911`, `:941`). For #3991 (void delete behavior), Backspace in an empty paragraph right after an image removes the paragraph and selects the image instead of deleting it ('removes an empty paragraph after an image before deleting the image', `apps/plite/tests/plite-browser/donor/examples/images.test.ts:828`). For #6034 (ArrowDown at the end of a table that is the last node moves the caret), after the trailing paragraph is deleted, ArrowDown keeps the caret in the last cell and typed `X` makes the cell text `9X` (`apps/plite/tests/plite-browser/donor/examples/tables.test.ts:112`). Ledger rows: `c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:370`, `:513`, `:671`, `:680`. Limits: every row skips the `mobile` project, #3991's also skips Firefox, which moves the caret after the image, and the `webkit` project runs only on macOS hosts (`apps/plite/playwright.config.ts:72-88`).

- **Caret at inline edges (#3148, #4074, #3429, #4618).** Plite keeps the end of an inline and the start of the following text as distinct caret positions, and its private DOM selection bridge owns that choice. In the inlines example, a DOM selection at offset 0 of the text after the link types outside the link ('keeps the start of following text distinct from the end of an inline', `apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:480`), and a selection at the end of the link text types inside it ('types inside an editable inline at its end', `apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:398`). Those rows back #3148 (Chrome and Safari cannot select the end of an inline) and #4074 (writing inside inline elements). A caret in the text before the padded editable-button inline stays outside it ('places the caret outside a padded inline before typing', `apps/plite/tests/plite-browser/donor/examples/inlines.test.ts:1392`), which backs #3429 (padding puts the caret inside the inline). The ledger claims fixes for all three, for Chromium and, for #3148, WebKit (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:770`, `:830`, `:857`). #4618 asks for a `normalizePoint` method to customize caret movement, and Plite rejects a public cursor-normalization hook (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:747`). The `normalizePoint` that `plitejs/dom` exports is a different helper, which walks a pending DOM text-diff point to a valid text point (`packages/plitejs/src/dom/index.ts:83`, `packages/plitejs/src/dom/utils/diff-text.ts:180-186`). Limits: the three rows skip the `mobile` project, the `webkit` project runs only on macOS hosts (`apps/plite/playwright.config.ts:72-88`), and Slate's tracker #3150 for these boundaries stays related (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:150`).

- **RTL caret after a new line (#1498).** Related only: real-browser tests map RTL DOM selection offsets while keeping the browser's geometry direction, and keep wrapped-line DOM rectangles tied to one editor selection (`packages/test/test/browser/selection.browser.test.ts:165`, `:207`). The exact RTL Enter caret case still needs a browser repro in a real editor (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:980`).

- **Shadow DOM, iframes and other documents (#3917, #3742, #3821, #4275, #4337, #5107).** Six dossier reports break when the editor lives outside the main document: target checks assumed one global `Node` constructor inside an iframe (#3917), `onChange` stopped firing in another window or frame (#3742), `useFocused` misreported focus through portals (#3821), Firefox typed backwards in the shadow-DOM example (#4275), and image drag and `findEventRange` failed DOM-point resolution inside a shadow root (#4337, #5107) (`c70bacbd4a:docs/plite-issues/open-issues-dossiers/3948-3881.md:589-636`). Plite resolves `Node` from the value's own window before its `instanceof` check (`packages/plitejs/src/dom/utils/dom.ts:45-53`, `:75-79`). The iframe example portals the editor into an iframe body (`apps/www/src/app/(app)/examples/plite/_examples/iframe.tsx:187`); browser rows insert text through the browser handle, click its content with no DOM resolution errors, and remove bold from selected iframe text with a toolbar button in the parent page (`apps/plite/tests/plite-browser/donor/examples/iframe.test.ts:9`, `:43`, `:74`). The shadow-DOM example renders inside a nested shadow root, and rows edit it, set the native caret inside it, keep ArrowLeft model-owned, delete RTL text with Backspace and add a line with no console or page errors (`apps/plite/tests/plite-browser/donor/examples/shadow-dom.test.ts:108`, `:169`, `:202`, `:245`, `:310`). - **DOM changed behind the editor (#4010, #4827, #5408, #5032, #4851).** Five dossier reports start with something other than the editor rewriting its DOM: Chrome page translation (#4010), a translation extension (#4827), browser extensions in general (#5408), Prism-style highlighting (#5032) and KaTeX output (#4851). For renderer composition (#3177, `renderElement` is not composable by plugins), raw Plite keeps render props such as `renderElement` on its editable surface (`packages/plitejs/src/react/components/editable-text-blocks.tsx:210`) and owns no renderer registry. Plugin render composition belongs to Plate, and the ledger says removing the registry must not count as fixing the issue. Both stay related (`c70bacbd4a:docs/plite-issues/gitcrawl-v2-sync-ledger.md:714`, `:941`). Limits: the #3557 row planned `onCommit` and `setup` extension slots, and the plugin definition has neither (`packages/plitejs/src/interfaces/editor.ts:3069-3092`); `onCommit` exists only as an `EditorRoot` callback. - **What transforms return (#4722, #3949, #4173, #5129).** Four dossier requests ask Slate transforms to report what they did or to swap a node's shell: insert transforms should return the inserted range (#4722) or the new node entry (#3949), and a rewrap or replace transform should change a node's type without unsafe mutation (#4173, #5129) (`c70bacbd4a:docs/plite-issues/open-issues-dossiers/4741-4643.md:151-199`). Limit: read from the type and the implementation; no test was read for `tx.nodes.replace`.

- **Text limits and refused input (#4795, #5010, #5152, #5050).** Four dossier reports show that Slate cannot reliably refuse input: a text-limit plugin is bypassed because native `beforeinput` flows differ by character class (#4795), overriding `insertText` to reject input leaves the DOM out of sync with the model (#5010), and since slate-react 0.66.0 an `insertText` that does nothing still lets the browser insert the text (#5152); #5050 asks for a `beforeInsertText` hook (`c70bacbd4a:docs/plite-issues/open-issues-dossiers/4839-4742.md:451-499`).
