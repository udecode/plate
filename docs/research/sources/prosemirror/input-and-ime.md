# ProseMirror: input and IME

## Composition overlap

- ProseMirror's view tests pin overlap behavior: a change that fully overlaps, partly overlaps or lies inside the composing range cancels the composition, and a change elsewhere does not (`test/webtest-composition.ts:238-268`). During view-desc sync, `updateChildren()` computes local composition info, updates the node that holds the composition when it can, and calls `protectLocalComposition()` before rendering child descs (`src/viewdesc.ts:767-826`). `compositionend` clears the composing state, records pending DOM mutations, clears the composition node, increments a composition id and schedules cleanup (`src/input.ts:502-525`). Source: `docs/plite/research/2026-06-12-ime-overlap-policy/sources/prosemirror-view-summary.md:1-22`. Limit: unpinned local `prosemirror-view` checkout read on 2026-06-12.

## DOM change reading

- In `readDOMChange`, ProseMirror applies a DOM change confined to one text node as a plain `insertText`, offered first to `handleTextInput` props, and dispatches the parsed DOM change for any more complex change (`ProseMirror/prosemirror-view@ca4c78e9:src/domchange.ts:260-277`). Source: `docs/plite/research/2026-06-14-firefox-inline-void-select-all-replacement/read-log.tsv:6`; lines reread at the pinned commit on 2026-10-08.

## beforeinput target ranges

- prosemirror-view does not import `beforeinput` target ranges as edit ranges. Its only `getTargetRanges` call is a Safari shadow-DOM workaround based on CodeMirror's: when `getComposedRanges` is missing, `safariShadowSelectionRange` fires `execCommand('indent')`, captures and cancels the resulting `beforeinput`, and reads its first target range as the selection inside the shadow root (`ProseMirror/prosemirror-view@ca4c78e9:src/domobserver.ts:332-355`). The 2026-06-13 run searched `../prosemirror` and reported no hit; that search missed this call. Tiptap adds no `getTargetRanges` call of its own (`git grep` over the packages of `ueberdosis/tiptap@91c51be53c`, 2026-10-08). Source: `docs/plite/research/2026-06-13-beforeinput-target-range-selection-policy/read-log.tsv:10-11`.

## Composition and Enter

- prosemirror-view never calls `handleKeyDown` during composition, and it drops one Safari Enter within 500 ms of `compositionend` (`ProseMirror/prosemirror-view@ca4c78e9b56f1b164c0b3758b59d8748f11b7534:src/input.ts:109`, `:435-452`). A menu wired through `handleKeyDown` inherits that guard; a raw DOM keydown listener does not. On Chrome Android, Enter keydowns never reach `handleKeyDown` (`src/input.ts:115`). The view reads the browser's paragraph split and replays a synthetic Enter (`src/domchange.ts:89-91`, `:124-127`, `:181-189`). On Android, compositions time out after 5 s of inactivity, and the view is almost always composing (`src/input.ts:454-455`, `:656-660`). When a decoration change would redraw the focused composition text node, the view keeps that node as a `CompositionViewDesc` (`src/viewdesc.ts:807-848`), so an inline decoration can appear around text mid-composition. prosemirror-inputrules skips during composition and in code but knows nothing about autocomplete (`ProseMirror/prosemirror-inputrules@ea304c0f91a1f2409f17519066fb46c370a78517:src/inputrules.ts:113`, `:119-128`). Source: `docs/plite/research/2026-10-02-autocomplete-query-representation/shards/001-prosemirror-family.md:95-100`.

## Composition

- ProseMirror ignores keydown and keypress while a composition is active or has just ended (`inOrNearComposition`, `src/input.ts:108`, `:144`, `:435-452`); within that check it drops one Enter keydown that Safari fires within 500 ms after `compositionend`, because Safari confirms Japanese IME candidates with Enter. It ends an idle composition after five seconds only on Android (`timeoutComposition`, `:455`, `:492`). Evidence: `ProseMirror/prosemirror-view@c752c6ef7225199f73cb433dd3179e7d69b840d8:src/input.ts`, read 2026-10-08. The composing state, pending-record flush and view-desc protection are under 'Composition overlap' on this page, and paste during composition is on the clipboard page.

## DOM observer timing

- ProseMirror's normal DOM-change path is immediate: the MutationObserver callback flushes at once, reading mutations and the selection and turning them into a transaction through `readDOMChange` synchronously. `flushSoon`'s 20 ms timer (`src/domobserver.ts:83-85`) serves only platform edges such as old IE, Safari composition in table cells, Android composition and selection repair; compositionstart flushes first; and a `beforeinput` fallback timer exists only for Chrome Android `deleteContentBackward` after uneditable content (`src/input.ts:814`). Its changelog favors synchronous display updates for ordinary non-composition input and leaves simple typing and Backspace to the browser where possible. Evidence: `ProseMirror/prosemirror-view@c752c6ef7225199f73cb433dd3179e7d69b840d8`, lines checked 2026-10-08; the run read `src/domobserver.ts:52-94`, `:174-248`, `src/input.ts:457-512`, `:807-825`, `src/domchange.ts:81-145`, `:198-254` and `CHANGELOG.md` (2017 and 2265 entries) unpinned on 2026-06-13.
