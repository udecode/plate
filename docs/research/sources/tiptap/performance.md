# Tiptap: performance

## Performance demo

- **Smoke only.** Tiptap's Performance demo shows React render counts with `shouldRerenderOnTransaction` toggled and `useEditorState` (`ueberdosis/tiptap@91c51be53c:demos/src/Examples/Performance/React/index.jsx:13-63`). Its only test asserts that the editor instance exists and checks no render count or timing (`ueberdosis/tiptap@91c51be53c:demos/src/Examples/Performance/React/index.spec.js:6-11`). It is a smoke test, not performance evidence; a Plite render or latency claim needs Plite's own benchmark or browser harness (`docs/editor-test-harvester/tiptap/report.md:103`). Read on 2026-10-08.

## React subscription ownership

- **Editor-wrapper renders and node-view portal renders have separate subscriptions.** Tiptap's useEditor suppresses per-transaction wrapper rerenders when `shouldRerenderOnTransaction` is false or omitted; useEditorState selects through `useSyncExternalStoreWithSelector`, while EditorContent's Portals component subscribes directly to its renderer collection. Evidence: `ueberdosis/tiptap@91c51be53c4655ef07e29ec489471524debfa0ca:packages/react/src/useEditor.ts:365-380`, `ueberdosis/tiptap:packages/react/src/useEditorState.ts:151-173` and `ueberdosis/tiptap:packages/react/src/EditorContent.tsx:25-35`. Source: `docs/plans/2026-05-08-plite-performance-scalability-plite-issues-ralplan.md:690-698`. Limit: subscription ownership does not itself prove narrow selector cost or bounded render counts.

## Collaboration mapping probe

- **Position mapping is timed separately from the whole transaction.** Tiptap's CollaborationMappingPerformance experiment times mapping its position array and reports the number of positions, then records transaction duration and document size separately; the experiment also varies decorations during simulated typing. Evidence: `ueberdosis/tiptap@91c51be53c4655ef07e29ec489471524debfa0ca:demos/src/Experiments/CollaborationMappingPerformance/React/index.tsx:153-160`, `:246-254`, with the decoration workload cited by `docs/plans/2026-05-08-plite-performance-scalability-plite-issues-ralplan.md:699-704`. Limit: an experiment's instrumentation is not a retained benchmark result or collaboration correctness proof.

## Huge highlighted code

- The 2026-09-03 core-Editor run measured published Tiptap CodeBlockLowlight 3.21.0 with Lowlight 3.3.0 on one 10,000-line × 48-character JavaScript block. After one discarded warmup, five mounts and twenty trusted midpoint edits in four `abcde` bursts gave p95 mount 117.1 ms, input-to-highlighted-frame 474.7 ms and Lowlight source work 200.8 ms; the exact repeat gave 113.3, 451.7 and 196.9 ms. Run: `2026-09-03-tiptap-lowlight-huge-code-benchmark/tiptap-lowlight-10k.json` (an uncommitted run file) and its repeat; measured extension dist SHA-256 `a27989b7657f5fc99b845175aa08a89d5a29b38c1248498f481a2e51f3b4b8f5`, Playwright 1.61.0, Chromium 149.0.7827.55, macOS arm64, 1280×720, DPR 1. Source: `docs/plans/2026-09-03-tiptap-lowlight-huge-code-benchmark.md:247-254`. This is historical midpoint-burst evidence; it does not answer the later React-example TypeScript workload, and older Plate baseline receipts omit their exact Chromium build.

- Tiptap's Lowlight plugin rebuilds syntax decorations synchronously when a document change occurs inside a code block, changes the code-block count or encloses an old code block. It finds code blocks, highlights each block's complete text, flattens the syntax tree and creates a new DecorationSet; other transactions map existing decorations. Source: `ueberdosis/tiptap@91c51be53c4655ef07e29ec489471524debfa0ca:packages/extension-code-block-lowlight/src/lowlight-plugin.ts`; investigation `docs/plans/2026-09-03-tiptap-lowlight-huge-code-benchmark.md:285-300`. The September JavaScript run observed five full-block calls per five-character burst and exact full-DOM text with 20,000 highlighted elements and 60,003 total DOM nodes. The source explains synchronous work but supplies no isolated causal intervention or incremental parser.

- The 2026-09-04 matched React-example packet used the same 10,000-line TypeScript fixture and trusted end insertion `\nconst __plateBenchmark = 1;`, three warmups and fifteen fresh-context measurements per strategy in rotating order. Input-to-frame p95 was 814.0 ms for native Plate, 582.8 ms for official Tiptap Lowlight and 60.9 ms for CodeMirror; highlight settlement was 822.8, 599.0 and 75.0 ms. Tiptap made one complete 448,917-character Lowlight call per insertion, with source-work p95 171.1 ms. Native/Tiptap mounted 30,011/30,001 block descendants and 30,000 tokens; CodeMirror mounted 153 descendants, 37 lines and 111 tokens. Run: `2026-09-04-tiptap-lowlight-huge-code-benchmark/combined.final.receipt.json` (an uncommitted run file); Plate `a6afd55c30e97c74fe895d1ad005ca75413110f3`, Tiptap `91c51be53c4655ef07e29ec489471524debfa0ca`, aggregate SHA-256 `800716b2750cdc617b8a1738031c56a61bb780041ace0fec28e0d9a4cb1fd2fb`, Chromium 149.0.7827.55 on Apple M5 Max, 1280×720, DPR 1. Source: `docs/plans/2026-09-04-tiptap-lowlight-huge-code-benchmark.md:308-317`. All 45 edits passed exact-content and selection guards. Fifteen-sample p95 is the maximum observation; full EditorKit versus minimal Tiptap confounds ownership attribution, and navigation, mount and heap are not comparable across those hosts. This is historical local evidence, not current performance or a causal proof of the DOM explanation.
