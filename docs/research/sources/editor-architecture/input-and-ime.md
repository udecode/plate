# Editor architecture: input and IME

## VS Code composition lifecycle

- VS Code's textarea input (`src/vs/editor/browser/controller/editContext/textArea/textAreaEditContextInput.ts`) keeps an explicit current composition context, stops IME-owned keys from propagating, ignores a duplicate stale `compositionend` and fires typed input from composition updates (`:199-319`); it synthesizes the composition end on blur, off-DOM removal and an Android tap so composition state is never stranded (`:453-482`), and never writes native textarea content while composing (`:639-645`). Its native EditContext path forwards composition start and end into controller and view-model state (`src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts:221-235`). Source: `docs/plite/research/2026-06-12-ime-overlap-policy/README.md:54-61`, `read-log.tsv:8-11`. - VS Code's native EditContext path updates EditContext text and selection from its model, maps `textupdate` to type and composition operations, renders IME text formats as decorations, and computes scroll-adjusted selection, control and character bounds from cached layout data (`src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts:210-590`). Its textarea fallback special-cases macOS long press, treats Android composition event data as unusable and deduces input from the textarea state instead, ignores `selectionchange` during paste and cut windows, and filters noisy `selectionchange` bursts (`src/vs/editor/browser/controller/editContext/textArea/textAreaEditContextInput.ts:235-520`). ## CodeMirror composition lifecycle

- CodeMirror's view tracks composition as a state machine: a composing count, a first-change marker, `compositionEndedAt`, a pending-key window that guards Safari's compositionend-then-keydown order, and a pending-change window after `compositionend` (`src/input.ts:45-63`, `:170-183`). Composition start, update and end maintain that state, flush late on Android and clean up when no DOM change arrives (`:816-846`), and a Safari dead-key `compositionend` is synthesized after `insertText` when the browser drops it (`:901-904`). DOM composition preservation refuses multi-line or model/DOM text-mismatch cases and decides overlap through an explicit helper (`src/docview.ts:606-615`, `:661-666`), and composition changes replay to secondary cursors only when safe (`src/domchange.ts:248-295`). Its tests cover changes that fully overlap, partly overlap or sit inside an active composition (all cancel it), a change elsewhere (it survives), rapid consecutive and multi-cursor compositions, IME span merging, and an Android-style newline after composition (`test/webtest-composition.ts:126-138`, `:220-252`, `:325-375`, `:386-415`). The portable lesson is the interference test list, not the state shape. Source: `docs/plite/research/2026-06-12-oss-input-selection-architecture/shards/001-input-selection-composition.md:1-20`, `read-log.tsv:2-13`. ## contenteditable case catalog

- `easylogic/contenteditable` is a case catalog of browser, OS and IME contenteditable incidents, not an editor. Its Safari Chinese IME case says preventing `insertParagraph` during or right after composition can corrupt later composition input and advises checking composition state before `preventDefault()` (`src/content/cases/ce-0559-insertparagraph-preventdefault-composition-broken-safari-chinese-ko.md:43-89`), and its architecture guide shows `beforeinput` and `keydown` guards that return while composing (`src/pages/editor/history-management.astro:376-490`). ## EditContext

- In EditContext the IME reads context text and selection from the EditContext object and `textupdate` updates its shared text buffer; an app must not call `updateText()` inside a `textupdate` handler, because that can cancel the composition, and must call `updateSelection()`, `updateSelectionBounds()`, `updateControlBounds()` and `updateCharacterBounds()` so selection, scrolling and IME candidate placement stay right (`edit-context/dev-design.md:1-105`). The explainer adds that painting the caret and selection becomes the app's job (`edit-context/explainer.md:157-313`). The WPT tentative tests show typing updating EditContext text and the app view with no DOM mutation, deletion reporting its result through `textupdate` while `beforeinput` has zero target ranges, backward selection endpoints, explicit bounds calls with invalid-argument checks, and text updates stopping once focus leaves the associated element so keystrokes reach the newly focused input (`editing/edit-context/edit-context-input.tentative.html:16-230`, `edit-context-basics.tentative.html:101-205`, `edit-context-focus.tentative.html:16-45`). IME text formats arrive separately through `textformatupdate`. Source: `docs/plite/research/2026-06-13-editcontext-native-input-oracles/read-log.tsv:2-6`, `lead-ledger.tsv:3-7`. Limit: unpinned local checkouts of MSEdgeExplainers and WPT read on 2026-06-13.

- EditContext status on 2026-06-13: MDN marked it limited availability, experimental and not Baseline (https://developer.mozilla.org/en-US/docs/Web/API/EditContext_API); the W3C had published a Working Draft dated 2026-06-10 (https://www.w3.org/TR/edit-context/); and Chrome's guidance scoped support to Chromium-based browsers from Chrome and Edge 121 and said authors must map caret and selection navigation and selection bounds themselves (https://developer.chrome.com/blog/introducing-editcontext-api). Recheck these sources before citing current support. Source: `docs/plite/research/2026-06-13-editcontext-native-input-oracles/web-freshness-ledger.tsv:2-4`, `README.md:67-75`.

## Web Platform Tests editing invariants

- Web Platform Tests pin these contenteditable behaviors. `InputEvent.getTargetRanges()` stays fixed at dispatch even when a listener moves the selection, and the WPT helper caches ranges during propagation because later behavior differs by browser (`input-events/input-events-get-target-ranges-during-and-after-dispatch.tentative.html:14-61`, `input-events/input-events-get-target-ranges.js:20-31`, `:158-180`). Expanded selections can yield target ranges that shrink to text edges or include whitespace-adjusted cross-block joins (`input-events-get-target-ranges-non-collapsed-selection.tentative.html:34-170`). Backspace and Delete target ranges can end on element containers such as `li`, joined `dl` items and inline wrappers, not only on text nodes (`input-events-get-target-ranges-deleting-in-list-items.tentative.html:72-220`, `input-events-get-target-ranges-joining-dl-elements.tentative.html:70-180`, `input-events-get-target-ranges-backspace.tentative.html:74-152`, `input-events-get-target-ranges-forwarddelete.tentative.html:108-144`). Deleting across editing-host boundaries can expose several disjoint target ranges (`input-events-get-target-ranges-deleting-range-across-editing-host-boundaries.tentative.html:167-560`). Contenteditable paste fires `paste`, then `beforeinput` and `input` with `insertFromPaste`, `data === null` and the payload in `dataTransfer` (text/plain and text/html), and `preventDefault` blocks the DOM change while the clipboard still updates; a textarea instead sets `data` and has no `dataTransfer` (`input-events/input-events-cut-paste.html:71-140`, `contenteditable-insertfrompaste-type-inputevent-data.html:10-36`, `textarea-insertfrompaste-type-inputevent-data.html:10-32`, `editing/other/data_transfer_on_input_event_with_insertfrompaste_type.html:17-51`). Typing, Backspace, Delete, Enter and Shift+Enter fire no `beforeinput` while the focused host's selection has zero ranges (`editing/other/no-beforeinput-when-no-selection.html:14-80`). The caret moves before or after a `contenteditable=false` island, never into it (`selection/caret/move-around-contenteditable-false.html:64-150`). Removing an editing host collapses the selection to its parent (`selection/selection-range-after-editinghost-removed.html:13-62`); removing a selected shadow host leaves the active Selection empty although a JS Range can still point into the removed tree (`selection/selection-range-in-shadow-after-the-shadow-removed.tentative.html:16-90`); and `getComposedRanges()` rescopes removed endpoints while earlier StaticRanges stay frozen (`selection/shadow-dom/tentative/Selection-getComposedRanges-dom-mutations-removal.html:15-97`). `Selection.direction` follows anchor and focus order, backward included and across shadow trees (`selection/shadow-dom/tentative/Selection-direction.html:15-62`), and double- and triple-click selections are expanded but directionless (`selection/selection-direction-on-double-click.tentative.html:15-35`, `selection-direction-on-triple-click.tentative.html:15-38`). Source: `docs/plite/research/2026-06-13-wpt-editing-oracles/read-log.tsv:2-33`. Limit: unpinned local WPT checkout read on 2026-06-13; tentative tests are drafts and state intended browser behavior, not what every browser ships.

## beforeinput target ranges in CodeMirror

- CodeMirror treats `beforeinput` as a platform signal (`codemirror/view@fbff59ba`, read 2026-10-08; the 2026-06-13 read was unpinned). On Chrome Android, an Enter or Backspace detected through `beforeinput` or `keydown` makes the DOM observer back off from DOM changes for one animation frame, then flush, and dispatch the key itself only when the flush found no change (`delayAndroidKey`, `codemirror/view@fbff59ba:src/domobserver.ts:288-322`). When Safari offers no `getComposedRanges`, it reads the selection inside a shadow root by firing `execCommand('indent')`, cancelling the resulting `beforeinput` and taking its first target range (`:500-518`). In EditContext mode it handles `insertReplacementText` itself, so spell-check corrections apply, by mapping the first `getTargetRanges()` StaticRange to document positions (`codemirror/view@fbff59ba:src/input.ts:860-870`). CodeMirror has no home, so its facts live on this page. Source: `docs/plite/research/2026-06-13-beforeinput-target-range-selection-policy/read-log.tsv:2-4`.

## Platform event specs

- W3C UI Events states that keyboard events and composition events do not map one to one, so a keyboard trace cannot establish IME state (https://www.w3.org/TR/uievents/, read 2026-06-13); W3C Input Events issue 115 shows that the cancelability and commit behavior of `insertCompositionText` is underspecified across browsers (https://github.com/w3c/input-events/issues/115). Editor tests should capture `beforeinput` target ranges and native event traces instead of assuming one browser contract.
