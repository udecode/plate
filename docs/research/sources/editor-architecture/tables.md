# Editor architecture: tables

## Typora and Milkdown table key evidence

- **Table keys.** Typora's Table Editing page says newer versions add rows when the user presses Tab, and `Milkdown/milkdown@6a4db480b:e2e/tests/crepe/table.spec.ts` presses Tab to move between cells. The audit counted both as support for table-owned Tab and locked EDIT-TABLE-TAB-001, which moves to the next cell, though Typora's page describes Tab only as adding rows. Neither reference documents Shift+Tab, Enter inside a cell, or Backspace at a cell start. Typora scopes destructive table actions to commands: Cmd/Ctrl+Enter inserts a row, and the delete-line command or Shift+Cmd/Ctrl+Backspace deletes the current row. `Milkdown/milkdown@6a4db480b:e2e/tests/input/table.spec.ts` only removes a list item typed after a table. The audit therefore locked Shift+Tab to the previous cell, and Enter and Backspace staying in the cell, as Plate decisions (EDIT-TABLE-STAB-001, EDIT-TABLE-ENTER-001, EDIT-TABLE-BS-START-001). The spec's Table section has since named Google Docs as its table-feel authority, with Notion and Milkdown as secondary checks; the audit did not consult Google Docs. Evidence: `docs/research/history/2026-04-02-markdown-editing-reference-audit.md:173-176`, `../raw/typora/pages/table-editing.json` (fetched 2026-04-02). Limit: docs and tests read, neither editor run; Milkdown is cited at the raw clone's 2026-04-02 head, since the audit pinned no commit.

## Table clipboard ownership

- **Table clipboard needs a table owner.** prosemirror-tables, Tiptap (which wraps it) and ProseMirror forum threads agree on one shape: table copy and paste belongs to a dedicated table owner, not generic nested-block insertion, with an explicit grid owner, selected cells serialized as a normalized cell area, paste sized to a target cell selection, collapsed-cell paste anchored at that cell, spans that cross replacement edges split or rejected by policy, and the post-paste selection part of the contract; strict per-column cell schemas make it harder, and a custom view layer still serializes and parses at the schema boundary. Plite and Plate split it that way: Plite core's slice replacement leaves grid merge to a table plugin, and Plate's table plugin plans the grid paste. Into a rectangular multi-cell selection it fills the selection, clipping and repeating the source as prosemirror-tables does (`packages/platejs/src/features/table/lib/internal/paste.spec.ts:340` 'clips and repeats a partial source tile'; `packages/platejs/src/features/table/lib/BaseTablePlugin.ts:2428-2457`), and it rejects a non-rectangular cell selection; Lexical clips without repeating. The spec states subtable copy, the one-cell anchor, growth and the post-paste rectangle selection (`EDIT-TABLE-PASTE-EXPAND-001`) but has no rule for the multi-cell fill. Sources: `docs/plite/research/2026-06-12-table-fragment-semantics/sources/prosemirror-tables-table-fragment-summary.md:30-40`, `docs/plite/research/2026-06-13-table-clipboard-web-scout/README.md:17-29`; Plate code read 2026-10-08.

## Independent engines

- Among the table implementations compared on 2026-09-17, the independent engines are prosemirror-tables and Lexical's `@lexical/table`; Tiptap, ProseKit and Milkdown wrap prosemirror-tables, so their table behavior is integration evidence, not three more engines (docs/plite/research/2026-09-17-table-substrate-ownership/REPORT.md:39-43; read-log.tsv:26,140,148). Both engines layer optional table selection on an extensible core selection, which shows first-class table selection does not require tables in the core (REPORT.md:46,48). Upstream tests were inspected, not executed.
