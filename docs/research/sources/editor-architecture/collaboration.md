# Editor architecture: collaboration

## Structural diff and merge engines

- **GumTree** keeps node matching apart from edit-script generation. `MappingStore` holds one source-to-destination map and its inverse, so each node maps to at most one node, and `ChawatheScriptGenerator` then derives insert, delete, update and move actions from those mappings. A node map can express a node that moves or changes, but not a span that splits into two nodes or two spans that join into one, which a rich-text comparison needs. Evidence: `GumTreeDiff/gumtree@dc2088281765e456b3574d230881c5a25ff93481:core/src/main/java/com/github/gumtreediff/matchers/MappingStore.java` (read lines 30-105) and `GumTreeDiff/gumtree@dc2088281765e456b3574d230881c5a25ff93481:core/src/main/java/com/github/gumtreediff/actions/ChawatheScriptGenerator.java` (read lines 70-165), verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:9` (2026-09-10). Limit: source read only; no GumTree test was run.

- **Difftastic** searches for the cheapest path through a graph of paired syntax nodes and gives up with `ExceededGraphLimit` once it has seen more than `graph_limit` vertices (`src/diff/shortest_path.rs:56-106`); its caller then falls back to a line-based text diff (`src/main.rs:712-727`). Its manual lists tree-diff cases that are hard to diff or to display clearly, such as adding, changing or expanding delimiters around unchanged content, and says not all of them work well yet (`manual/src/tricky_cases.md:1-97`). Highlighting moved regions is a separate request, open when read on 2026-09-10 (https://github.com/Wilfred/difftastic/issues/508). A correct match does not by itself give readable change markup, and a bounded search needs a declared fallback. Evidence: `Wilfred/difftastic@274d0a8f57291477cfbfb27bace0d82395d15c97:src/diff/shortest_path.rs` and `Wilfred/difftastic@274d0a8f57291477cfbfb27bace0d82395d15c97:manual/src/tricky_cases.md`, verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:10`. Limit: source read only, no executable witness; the `src/main.rs` fallback was checked by the 2026-10-08 compile reader at the same commit, not by the run.

- **jsondiffpatch** reports a move inside one array, together with edits inside the moved item, only when an `objectHash` gives the items identity. Without one it matches objects only by reference or, when asked, by position (`matchItems`, lines 48-66), so a reordered copy of an array shows up as edits at each index and no move. Its array deltas address items by index even with an `objectHash`, and unpatching an insertion delta against a reordered array succeeds without error and yields the wrong items, so a successful patch does not show the target was the delta's baseline. Evidence: `benjamine/jsondiffpatch@a60db8a232f92ee4b987c14f43f77402885d1a5a:packages/jsondiffpatch/src/filters/arrays.ts`, three witnesses in `docs/plite/research/2026-09-10-structural-diff-oss/sources/semantic-probe.mjs:17-39` that passed on bun 1.3.12 (`docs/plite/research/2026-09-10-structural-diff-oss/sources/semantic-probe.json`), verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:11`. Limit: the witnesses confirm documented library behavior, not defects, and rerunning them needs local clones at the pinned commits, because the script imports from absolute local paths.

- **Quill Delta** (`slab/delta`) aligns two documents as text with each embed replaced by one sentinel character, then compares the real inserts on every run the alignment calls equal: a changed embed payload becomes an insert plus a delete, and a formatting-only change becomes a retain carrying `AttributeMap.diff` of the attributes. Text alignment alone would report a changed embed or a formatting-only change as unchanged, so a rich-text diff checks atom payloads and attributes separately from the text it aligns. Evidence: `slab/delta@dc17ca03e1d68ee729c8cd1ff790ebf96eb0fbec:src/Delta.ts:339-391` (`Delta.diff`), verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:12`. Limit: source read only, and Delta is a flat document format, not a tree.

- **node-diff3** keeps the base and both branch alternatives in a conflict region, so `diff3Merge(['local'], ['base'], ['remote'])` returns all three. Its clean output loses review information, though: `diff3Merge` flattens non-conflicting changes from both branches into one `ok` block that no longer says which branch made each change, and when one branch deletes an item the other left alone, `diff3MergeRegions` returns only the surviving base regions, with no region for the deletion. A three-way review that must show branch origins and one-sided deletions keeps both branch deltas instead of working from merged output. Evidence: `bhousel/node-diff3@8226c27e074909241d72276c21215505a931665f:src/diff3.mjs` (read lines 190-475), three witnesses in `docs/plite/research/2026-09-10-structural-diff-oss/sources/semantic-probe.mjs:41-64` that passed on bun 1.3.12 (`docs/plite/research/2026-09-10-structural-diff-oss/sources/semantic-probe.json`), verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:14`. Limit: the witnesses confirm library contracts, not defects.

- **trimerge** merges arrays by key: `trimergeArrayCreator` turns each of the three arrays into a key-to-item map, throws `Duplicate array key` when an array repeats a key, and merges the values per key separately from the key order (`src/trimerge-array.ts:9-60`). When the three-way merge of the key order would place one key twice, as when both branches move the same item to different places, it throws `order conflict` unless the caller passes `allowOrderConflicts`, which keeps the first placement (`src/diff3-keys.ts:3-20`). Order is its own merge decision with an explicit policy. Evidence: `trimerge/trimerge@8f5002584bc892d5dbb5b813e4241323e6593eef:src/trimerge-array.ts` and `trimerge/trimerge@8f5002584bc892d5dbb5b813e4241323e6593eef:src/diff3-keys.ts`, verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:15`. Limit: source read only; `src/diff3-keys.ts` was checked by the 2026-10-08 compile reader, not by the run.

- **Loro** computes a diff between two recorded versions, `LoroDoc::diff(&a, &b)` over frontiers, and validates a diff before `apply_diff` applies it (`crates/loro/src/lib.rs:1473-1498`). It gives moved list items and tree nodes their own identity: its `LoroMovableList` doc says simulating a move as a delete plus an insert fails under concurrency, because two peers moving the same element yield one deletion and two new elements (`crates/loro/src/lib.rs:3265-3273`). Its contract test fixes one concurrent case as an explicit rule: when one peer deletes a parent and another moves a child out of it, the child stays alive under its new parent, the parent is deleted, both peers converge and a snapshot reload keeps that result (`crates/loro/tests/contracts/tree_concurrent_delete_move.rs:10-97`). A comparison that supports moves needs such a rule for each concurrent case. Evidence: `loro-dev/loro@d5da57dd2a91d735656808cbbe2a3f1c755c2441:crates/loro/src/lib.rs` and `loro-dev/loro@d5da57dd2a91d735656808cbbe2a3f1c755c2441:crates/loro/tests/contracts/tree_concurrent_delete_move.rs`, verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:16`. Limit: source read only; no Loro test was run.

- **Automerge** separates a diff between recorded versions from an inferred one. `diff(doc, before, after)` returns patches between two sets of heads, and its doc says the result is empty when either set is missing from the document, so an empty diff does not prove two versions are equal (`javascript/src/implementation.ts:1101-1118`). `updateText` instead diffs the current string against a new one and turns the difference into splices; its doc says this merges worse than capturing the user's input and serves when input cannot be captured (`javascript/src/implementation.ts:1565-1596`). Evidence: `automerge/automerge@1618c976ca23fca8282c4a69ebbb0bb0c3f27ab1:javascript/src/implementation.ts`, verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:17`. Limit: source read only.

- **Spork**'s 3DM three-way merge resolves a raw merge by removing inconsistent parent, predecessor and successor triples, and records the ones it cannot remove as structural conflicts, apart from content conflicts on a single node. When a content conflict cannot be resolved automatically, it returns every revision's content, because later conflict handling may need all of them. Evidence: `ASSERT-KTH/spork@c1b35d81c44d61d883da7ca91ae0088b6b8f3f2f:src/main/kotlin/se/kth/spork/base3dm/TdmMerge.kt:17-104`, verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:18`. Limit: source read only; the run executed no Java or Rust upstream suite (`docs/plite/research/2026-09-10-structural-diff-oss/README.md:65`).

- **diff-match-patch** keeps semantic cleanup (`diff_cleanupSemantic`) apart from patch application. `patch_apply` locates each patch fuzzily (`Match_Threshold` is 0.5 by default) and returns the patched text with one success flag per patch. A patch made from 'The green boat moves slowly.' to 'The green boat moves quickly.' applied cleanly to 'The brown boat moves slowly.', so a successful apply does not show the target was the patch's baseline; fuzzy application suits best-effort text repair, not importing a proposal. Evidence: `google/diff-match-patch@62f2e689f498f9c92dbc588c58750addec9b1654:javascript/diff_match_patch_uncompressed.js:1810-1913` (and `:39` for the threshold), the witness in `docs/plite/research/2026-09-10-structural-diff-oss/sources/semantic-probe.mjs:66-71` that passed on bun 1.3.12 (`docs/plite/research/2026-09-10-structural-diff-oss/sources/semantic-probe.json`), verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:19`. Limit: one same-length witness; the threshold line was checked by the 2026-10-08 compile reader, not by the run.

- **Mergiraf** matches syntax nodes one-to-one and only between nodes of the same kind and language (`src/matching.rs:9-14`, `src/matching.rs:82-97`). After a structured three-way merge it renders the merged text, re-parses it (each of the three sides when conflict markers remain) and discards the merge when one fails to parse or is not isomorphic to the merged tree (`src/structured.rs:102-129`). Matching needs the language's own node semantics, and a rendered merge needs a structural check before it is trusted. Evidence: `codeberg.org/mergiraf/mergiraf@b9a78df83d48a89961310dde67898dd1b355690e:src/matching.rs` and `codeberg.org/mergiraf/mergiraf@b9a78df83d48a89961310dde67898dd1b355690e:src/structured.rs`, https://mergiraf.org/architecture.html read on 2026-09-10, verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:20`. Limit: source read only; no Mergiraf test was run.

- **VS Code**'s moved-line detection pairs a deleted block with an inserted block only when each has at least three lines and their similarity is above 0.90 (`computeMovedLines.ts:64-83`), drops moves shorter than 15 characters or with fewer than two lines of two or more characters (`computeMovedLines.ts:34-39`), and returns no moves when its time budget runs out (`computeMovedLines.ts:27`). These gates are tuned for source code and are not rules for rich-text comparison. Evidence: `microsoft/vscode@df2411cf7d8f2e0cfc79109a3bc8eaab2c69165b:src/vs/editor/common/diff/defaultLinesDiffComputer/computeMovedLines.ts`, verdict at `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:21`. Limit: source read only.

- **No drop-in engine.** GumTree, Difftastic and jsondiffpatch each contribute mechanics, but each works under a narrower contract than rich-text comparison with moves, splits, wrappers and review: one-to-one node maps, code syntax trees with a line-diff fallback, and JSON arrays addressed by index. None can be adopted whole as Plite's structural comparison. The 2026-09-10 run calls this a judgment of scope, not of quality. Evidence: `docs/plite/research/2026-09-10-structural-diff-oss/shards/001-structural-diff.md:33`.

## Suggestions, authorship and review

- Google Docs' public API exposes a suggestion in three views, inline, accepted and rejected, whose positions differ, and its developer-preview write API applies suggestion intent to a whole batch (https://developers.google.com/workspace/docs/api/how-tos/suggestions, retrieved 2026-09-10); its help center documents bulk accept and reject. This confirms observable contracts only and reveals nothing about Google's storage. Source: `docs/plite/research/2026-09-10-authored-changes/assessment.md:38-42`, `read-log.tsv:43-44`.

- Automerge separates human authors from replica actors and offers causal heads, views, writable forks, retained changes and diffs (`automerge/automerge@1618c976:javascript/src/implementation.ts:207-210`, `:270-345`, `:899-919`, `:1070-1125`), but causal history does not decide which dependent edit a reviewer meant to accept. Loro's change metadata records peer, dependencies, timestamp, message and operation count (`loro-dev/loro@d5da57dd:crates/loro-internal/src/change_meta.rs:1-75`), and its `UndoManager` works from one peer's perspective while mapping through remote changes (`loro-dev/loro@d5da57dd:crates/loro-internal/src/undo.rs:154-160`), so it is not an all-authors review engine. Source: `docs/plite/research/2026-09-10-authored-changes/assessment.md:46-47`, `read-log.tsv:36-38`.

- SuperDoc's document API (AGPL-3.0) separates logical review IDs from representation, distinguishes tracked and visible positions, guards decisions with a revision and offers an atomic multi-ID decision (`superdoc/docx-editor@cabf6fae:packages/document-api/src/track-changes/track-changes.ts:1-145`, `:188-297`); its docs say undecided edits survive a saved DOCX and that views differ from decisions (`superdoc/docx-editor@cabf6fae:apps/docs/content/docs/editor/track-changes.mdx:1-150`). The read covered the public contract, not its mutation kernel. Source: `docs/plite/research/2026-09-10-authored-changes/assessment.md:50`, `read-log.tsv:39-40`.

## Accepted deletion of a whole paragraph

- **Each source whose storage was read keeps deleting a paragraph's text apart from deleting the paragraph.** The storage of Fidus Writer, manuscripts-track-changes-plugin and EigenPal is unread. OOXML puts deleted text in `w:del` runs and a deleted paragraph mark in `w:pPr/w:rPr/w:del` (ECMA-376 Part 1, 5th edition, §§17.13.5.14-15, read 2026-10-25). ONLYOFFICE keeps the paragraph's review state on its end run (`onlyoffice/sdkjs@72b0421c0b:word/Editor/Paragraph.js:15943-15965`). LibreOffice's redline is a range that may or may not cross the paragraph end (`libreoffice/core@760394bbad:sw/source/core/doc/docedt.cxx:329-352`). prosemirror-suggest-changes uses an inline deletion mark, a deletion node mark for whole blocks and a boundary mark on the block before a deleted boundary (`handlewithcarecollective/prosemirror-suggest-changes@653fba70ba:src/replaceStep.ts:125-225`). Plite's text claim and block claim are the same split.
- **Accepting a deletion of the paragraph itself joins or removes the paragraph in each source read, except where the editor cannot join it with the one block it checks.** Fidus Writer looks only at the text block before the paragraph and EigenPal only at the next block in the same container, and each keeps the paragraph when that block is missing or of another kind. ONLYOFFICE refuses the deletion on a container's last paragraph. OOXML joins a deleted mark's paragraph with the following one (§17.13.5.15). ONLYOFFICE concatenates the next paragraph into it and keeps the next paragraph's properties (`onlyoffice/sdkjs@72b0421c0b:word/Editor/DocumentContentBase.js:1990-2045,2128-2172`). EigenPal merges forward and keeps the next paragraph's `pPr` when the next block in the same container is a paragraph; before a table, a content control or the container's end, it keeps the paragraph and drops only the revision (`eigenpal/docx-editor@84c46227d4:packages/core/src/store/store/tree-op-revisions.ts:671-707`). LibreOffice deletes the range and joins, copying the end paragraph's style to the start (`libreoffice/core@760394bbad:sw/source/core/doc/DocumentRedlineManager.cxx:645-724`). prosemirror-suggest-changes deletes a block its deletion node mark covers (`src/commands.ts:66-97`, test `src/__tests__/commands.test.ts:179-200`). Fidus Writer joins the paragraph backward only when a text block precedes it with no isolating node between; otherwise it keeps the paragraph and drops only its tracking (`fiduswriter/fiduswriter@e14cc456ac:fiduswriter/document/static/js/modules/editor/track/delete.js:10-57`). manuscripts-track-changes-plugin joins the paragraph into the block above when ProseMirror can join them, and otherwise deletes the paragraph with its content (`atypon-opensource/manuscripts-track-changes-plugin@62f4d19dda:src/tracking/lib/mergeNode.ts:27-41`, `src/tracking/lib/deleteNode.ts:33-47`). The comment above the call in `src/applyChanges.ts:131-133` also names the block below and the parent, but no code path moves content there.
- **Accepting the text alone leaves an empty paragraph.** LibreOffice asserts it in `testTdf135260` (`libreoffice/core@760394bbad:sw/qa/extras/uiwriter/uiwriter4.cxx:1290-1316`); the other sources reach it from code, not a test.
- **A required container keeps one paragraph.** ONLYOFFICE refuses a deleted end mark on the last paragraph of a document or table cell (`onlyoffice/sdkjs@72b0421c0b:word/Editor/Run.js:10888-10902`) and builds a paragraph when a removal empties content (`word/Editor/Document.js:11409-11413`). EigenPal keeps a paragraph that has no following paragraph to merge into. Microsoft Support says Word's end paragraph cannot be deleted. Plite's decision gets the same result from schema completion.
- **No source applies a remembered verdict to a claim that arrives later.** ONLYOFFICE's `disableRevisions` load option and Fidus Writer's offline merge apply every stored deletion, not an earlier verdict (`onlyoffice/sdkjs@72b0421c0b:word/Editor/Serialize2.js:17695-17715`; `fiduswriter/fiduswriter@e14cc456ac:fiduswriter/document/static/js/modules/editor/collab/merge/index.js:335-345`). Plite's settle has no prior art, so what it leaves follows Plite's own rule that settling applies a claim as a decision would (`docs/plans/2026-10-25-settle-empty-block.md`).
- **No source refuses an accept because of a neighbour's pending split or join.** prosemirror-suggest-changes consumes another boundary suggestion in range in the same pass (`src/commands.ts:110-127`); manuscripts turns an orphaned split into an insertion (`src/changeHelpers/structureChange.ts:97-118`).
- **Rejected leads.** SuperDoc's accept mutation lives in `@superdoc/docx-engine`, which `superdoc/docx-editor@cabf6fae68` does not hold; reopen when that source is published. The OOXML and MS-OI29500 texts give no rule for a sole cell, list item or quote paragraph, or for a neighbour's pending split; reopen with a Word run to observe. Next angle: none, since the settle decision does not turn on more prior art.
