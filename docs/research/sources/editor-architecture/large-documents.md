# Editor architecture: large documents

## CodeMirror viewport and selection

- CodeMirror's view package makes the drawn viewport and `visibleRanges` public (`src/editorview.ts:90-103`). When a selection endpoint falls outside the main viewport it draws an extra one-line viewport so the DOM selection never lands in a gap (`src/viewstate.ts:157-204`). It computes the viewport from a measured height map that includes scroll targets (`src/viewstate.ts:393-416`), scales very large document heights around the active viewports (`src/viewstate.ts:693-736`), keeps a scroll anchor through its measure loop and corrects the offset after height changes (`src/editorview.ts:413-496`), and documents coordinate lookup as precise only where DOM exists and estimated elsewhere (`src/editorview.ts:741-765`). Plite took the contract shape, not the code: CodeMirror is a line-block text editor, while Plite needs rich-block DOM coverage and model-owned selection. Source: `c70bacbd4a:docs/plite/research/2026-06-12-huge-doc-architecture/README.md:27-34`, `:1156-1170`, `:1196-1198`. Limit: line numbers come from an unpinned local `codemirror/view` checkout read on 2026-06-12.

- More CodeMirror view mechanics (unpinned local checkout read on 2026-06-13): measurement reads geometry, the visible pixel viewport, line heights and scroll state and recomputes the viewport when geometry or heights change (`src/viewstate.ts:267-372`); the measure loop restarts until the layout is coherent, caps restarts, and runs measure requests only once the viewport is stable (`src/editorview.ts:421-483`); `requestMeasure` schedules a requestAnimationFrame read-then-write request deduplicated by key (`src/editorview.ts:577-590`); long-line gap and visible-range logic never hides the selection endpoints and treats viewport movement apart from mapped changes (`src/viewstate.ts:446-579`); the drawn selection layer redraws on document, selection, viewport or config changes (`src/draw-selection.ts:102-122`) and clips rectangles to the viewport and visible ranges with bidi-aware spans (`src/layer.ts:102-171`). Its tests assert endpoint coordinates inside the scroll box after scrolling a range into view, viewport DOM text equal to the document slice after random changes, visible ranges smaller than the viewport on long wrapped lines, and plugins observing viewport changes (`test/webtest-draw.ts:120-137`, `:155-161`, `:287-296`, `test/webtest-extension.ts:7-31`). The public reference describes `drawSelection` as hiding the native selection and cursor (https://codemirror.net/docs/ref/), and a focused widget needs a native-selection exception under it. Source: `c70bacbd4a:docs/plite/research/2026-06-13-oss-viewport-selection-proof/read-log.tsv:2-19`.

- CodeMirror's print path is a separate viewport lifecycle: on a print media change `onPrint` sets `viewState.printing`, which disables viewport limiting by measuring the full pixel range, and clears it 500 ms later with a new measure (codemirror/view@fbff59ba004d80d8c914f64c42586387b08706ac:src/domobserver.ts:152-160; src/viewstate.ts:147-148,317; read 2026-09-11, rechecked at that commit 2026-10-08, not executed). Together with its selection-endpoint viewports, off-viewport height map and long-line gaps, this argues for separate block-count, single-block and print proof rows in a rich-text editor, not for importing a text-editor height tree (docs/plite/research/2026-09-11-large-documents-contract/shards/001-native-and-lifetime.md:46-51; read-log.tsv:25-26).

## Viewport rendering references

- Wordgard's view and content ownership and persistent text chunks (`wordgard/wordgard@b5ad0d057e2790c8cf971c85a9d2fb7e4a82da54`) are comparison targets for bounded redraw and immutable values, but the measured 2026-09-09 packet was not virtualized. VS Code and Monaco use line-oriented viewport rendering and piece-tree aggregates for large source files, and VS Code's GPU capability check rejects RTL, overlong columns, non-regular decorations and unsupported CSS or pseudo-selectors (`microsoft/vscode@df2411cf7d8f2e0cfc79109a3bc8eaab2c69165b`). TanStack Virtual's imperative adapter owns scroll measurement and range extraction, so Compiler compatibility has to be solved at the immutable values React reads. CSS `content-visibility: auto` keeps the DOM and, unlike `hidden`, still takes part in Find and focus according to MDN, which is a reason to test it, not proof that nested editor geometry, print, selection painting or copied content are correct. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/virtualization.md:23-30`.

## Canvas pagination

- windoc is a canvas document editor with automatic pagination, headers, footers and print; its React wrapper exposes the visible page list, page size, the intersecting page and scale through listeners. Its canvas rendering is a different architecture from DOM contenteditable, so only the visible-page metric carries over. Evidence: `aliansyahFirdaus/windoc@e6576c12659ad0c832a3fee6052edd123b3beda9:README.md:12-19`, `:46-58`, `react/src/Editor.tsx:288-309`, checked 2026-10-08 at the local clone.

## content-visibility and WPT oracles

- The CSS Containment editor's draft of 2026-06-23 separates painting skipped by `content-visibility: auto` from absent DOM and specifies how skipped content interacts with find, selection and accessibility (https://drafts.csswg.org/css-contain/#content-visibility); it is a draft, not evidence of current browser parity. In WPT, `css/css-contain/content-visibility/content-visibility-auto-print.html` is a print rendering comparison and `content-visibility-auto-selection-crash.html` only a crash test (web-platform-tests/wpt@dd54691426c23a08c6f4a0972b2c40965307e5ce), so neither is a selection-fidelity or editor oracle (docs/plite/research/2026-09-11-large-documents-contract/shards/001-native-and-lifetime.md:57-63; read-log.tsv:31-33).

## Layout recomposition

- **Premirror plans page layout around explicit invalidation.** Premirror keeps ProseMirror as the source of document truth and derives page layout through snapshot, Pretext measurement and composition (`samwillis/premirror@29b78634d6496206c84015068eb7d66d9cdc312c:README.md:7`, `:21`). Its design proposal makes incremental recomposition a principle (`samwillis/premirror@29b78634:docs/design-proposal.md:34-37`), maps ProseMirror positions to composed fragment and line locations for overlays and diagnostics (`:94-95`) with mapping round-trip tests planned (`:443`), and plans recomposition by invalidation region, urgent editing updates kept apart from full reflow passes, and per-transaction profiling counters for compose time and invalidated nodes (`:421-426`). This is a stated design, not a measured result. Source: `52625e85025313eebd4eeb9be2254249ded58676:docs/plite/decorations-annotations-cluster.md:669-685`, an April 2026 read of an unpinned clone; reread at the pinned commit on 2026-10-08. Limit: Plite pagination derives layout in its mounted paged component, and page boundaries never become document authority (`docs/vision/plite.md:235-238`, `:749-753`).

- **Premirror paginates one editable root.** Premirror keeps a single ProseMirror `EditorView` and one `contenteditable` root as the interaction source of truth, and its composer splits a paragraph into `BlockFragment` layout records while the paragraph stays one document node (`samwillis/premirror@29b78634d6496206c84015068eb7d66d9cdc312c:docs/design-proposal.md:75-95`). `PremirrorPageViewport` stacks the page surfaces from the layout and mounts one editor layer aligned to the stacked page origin, and ProseMirror decorations position the content fragments, so there is no duplicated text layer (`samwillis/premirror@29b78634d6496206c84015068eb7d66d9cdc312c:packages/react/src/index.tsx:151-156`, `README.md:13-18`). Source: `831f5e5da6a37f7d9095c1a81acc6b3de10bd3ba:docs/analysis/plite-plate-v2-architecture-research.md:706-718`, an unpinned 2026-04-03 read, checked at the pinned commit on 2026-10-08. Limit: source read only; Plite's paged component owns its own page surfaces and never makes page boundaries document authority (`docs/vision/plite.md:749-753`).
