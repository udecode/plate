# Editor architecture: conversion and export

## Incremental parsing and reuse

- **No parser reuse API takes an arbitrary previous result.** Tree-sitter reuses a previous syntax tree only after `ts_tree_edit` aligns it to every source edit, with byte and row/column coordinates (`tree-sitter/tree-sitter@dcdc8cc55e5dfedfc858080835f153999a29ec40:lib/include/tree_sitter/api.h:283-329`). Lezer reuses explicit `TreeFragment` intervals built by `addTree` and `applyChanges` with old and new coordinates and open boundaries, and its `PartialParse` is unfinished computation, not a previous document (`lezer-parser/common@d87b56cbe3d6f54edb5b8343ee794f8f96f9c86c:src/parse.ts:18-167`). Streamdown's `parseMarkdownIntoBlocks` takes no previous tree; one module-global cache keeps the last input and blocks for conservative prefix reuse (`vercel/streamdown@0b6b20d3a85986a39b4bcd454cdcb6aabfc9b3e6:packages/streamdown/lib/parse-blocks.tsx:112-144`). markdown-it builds fresh core state per `parse`, and `env` carries references and metadata, not earlier results (`markdown-it/markdown-it@3c51991c32aaa2b002a52c009334ebe5752c84b3:src/markdownit.ts:377-423`). micromark consumes one input stream statefully, takes no old tree plus edits, and its stream emits HTML at `end` (`micromark/micromark@6577c200155e9c6b85a42b26d298f8affc348f2f:packages/micromark/dev/stream.js:155-171`). A reuse facade must therefore own the source text, edits and parser state itself. Source: `docs/research/probes/2026-09-28-conversion-boundary/prior-art/findings.md:32-44`. Limit: source read on 2026-09-28; nothing was run.

- **Reuse needs more than unchanged text.** Tree-sitter's edit propagation covers lookahead reach and column-sensitive invalidation, and reuse also checks external-scanner state, changed, error, missing and fragile nodes, included ranges and parser compatibility; its changed-range API reports syntactic changes, not every change to a converted value (`tree-sitter/tree-sitter@dcdc8cc55e5dfedfc858080835f153999a29ec40:lib/src/parser.c:783-827`, `tree-sitter/tree-sitter@dcdc8cc55e5dfedfc858080835f153999a29ec40:lib/include/tree_sitter/api.h:466-481`). Lezer Markdown reuses a fragment only when its block context hash matches, trims reuse to line and block boundaries, and keeps indented code and lists open across blank lines unless a following sibling is also reused, so a completed-looking block is not final (`lezer-parser/markdown@30fe1b12a53f58ebab66e156a7847484addf610b:src/markdown.ts:742-758`, `lezer-parser/markdown@30fe1b12a53f58ebab66e156a7847484addf610b:src/markdown.ts:1819-1909`); its tests compare incremental trees with a fresh parse (`lezer-parser/markdown@30fe1b12a53f58ebab66e156a7847484addf610b:test/test-incremental.ts:37-76`). Source: `docs/research/probes/2026-09-28-conversion-boundary/prior-art/findings.md:46-50`. Limit: no Tree-sitter Markdown grammar was read, and the tests were read, not run.

- **Link definitions and footnotes defeat block-local reuse.** Lezer keeps single-pass incremental parsing by parsing unresolved references such as `[a][b]` as links, and it produces syntax trees, not HTML, so it does not prove CommonMark conversion equivalence (`lezer-parser/markdown@30fe1b12a53f58ebab66e156a7847484addf610b:src/README.md:5-19`). micromark collects definitions before inline processing, and markdown-it runs blocks before inlines and stores the first definition per normalized label in `env.references`, so appending a definition can change an earlier unresolved reference and editing or removing one can change distant resolved references; reusing an old markdown-it `env` would keep a removed definition, inferred from the write-if-absent code rather than a tested bug (`micromark/micromark@6577c200155e9c6b85a42b26d298f8affc348f2f:packages/micromark-core-commonmark/dev/lib/label-end.js:245-249`; `markdown-it/markdown-it@3c51991c32aaa2b002a52c009334ebe5752c84b3:src/rules_block/reference.ts:194-219`). Streamdown reuses a prefix only on input growth with prefix equality, a conservative stable boundary and verified slices; a regex-detected link definition disables reuse and detected footnotes return the whole document as one block (`vercel/streamdown@0b6b20d3a85986a39b4bcd454cdcb6aabfc9b3e6:packages/streamdown/lib/parse-blocks.tsx:3-15`, `:137-144`, `:240-340`), and its full-input checks mean its reuse is not constant work per appended character. A complete converter needs dependency invalidation, a global resolution pass or a correct fallback. Source: `docs/research/probes/2026-09-28-conversion-boundary/prior-art/findings.md:52-60`.

- **Incomplete input is three different jobs.** Tree-sitter inserts missing nodes and excludes error and missing nodes from reuse, which is parser recovery, not inferred intent (`tree-sitter/tree-sitter@dcdc8cc55e5dfedfc858080835f153999a29ec40:lib/include/tree_sitter/api.h:577-581`). Lezer accepts EOF inside a fence without inventing a closing marker, markdown-it ends an unclosed fence at the document or parent end, and micromark snapshots and restores tokenizer state when a construct fails, which is parsing the current prefix (`lezer-parser/markdown@30fe1b12a53f58ebab66e156a7847484addf610b:src/markdown.ts:406-435`; `markdown-it/markdown-it@3c51991c32aaa2b002a52c009334ebe5752c84b3:src/rules_block/fence.ts:40-59`; `micromark/micromark@6577c200155e9c6b85a42b26d298f8affc348f2f:packages/micromark/dev/lib/create-tokenizer.js:503-580`). Streamdown runs `remend` over the whole string in streaming mode to close emphasis, replace unfinished destinations with sentinel URLs, strip unfinished HTML and append a zero-width character against an apparent setext heading, which rewrites text and offsets for display (`vercel/streamdown@0b6b20d3a85986a39b4bcd454cdcb6aabfc9b3e6:packages/remend/src/index.ts:49-85`, `vercel/streamdown@0b6b20d3a85986a39b4bcd454cdcb6aabfc9b3e6:packages/streamdown/index.tsx:670-708`). Keep source and speculative display repair distinct when exact conversion or positions matter. Source: `docs/research/probes/2026-09-28-conversion-boundary/prior-art/findings.md:62-68`. Limit: source read on 2026-09-28; nothing was run.

## Pandoc

- Pandoc's DOCX reader keeps comments only when it reads all changes: accepting or rejecting changes removes comment markers and bodies along with the tracked changes (jgm/pandoc@bde8c297ee68c07a037f06971aa0f1cce8a876cb:src/Text/Pandoc/Readers/Docx.hs:389-422). It also marks paragraph insertions and deletions with `paragraph-insertion` and `paragraph-deletion` span classes (Readers/Docx.hs:749-775), while the writer's span serializer recognizes only the exact insertion and deletion classes (src/Text/Pandoc/Writers/Docx/OpenXML.hs:872-922), so a paragraph-revision round trip is a source-inferred gap, not an executed failure (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/pandoc-preview.md:18). Read 2026-09-14; reader lines rechecked at that commit 2026-10-08.

- Pandoc's DOCX conversion drops content without a full loss report: charts and diagrams become placeholders, parser helpers catch errors and return no elements without adding a diagnostic, and raw OpenXML passthrough on write cannot restore content that import already discarded (jgm/pandoc@bde8c297ee68c07a037f06971aa0f1cce8a876cb:src/Text/Pandoc/Readers/Docx.hs:347-367; src/Text/Pandoc/Readers/Docx/Parse.hs:148-154,502-513; src/Text/Pandoc/Writers/Docx/OpenXML.hs:309-326,537-543,947-952; read 2026-09-14). Its warnings, such as the one for the non-paragraph comment content it flattens, help but are not an inventory of dropped OOXML or package parts (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/pandoc-preview.md:20).

## docx-preview

- docx-preview parses comment IDs, authors, initials, dates, bodies and range markers and renders comment ranges with popovers through the browser Highlight API; it parses insertion and deletion metadata and emits `ins` and `del` when change rendering is on. By default it hides comments, shows inserted text without change markup and suppresses deleted text; its paragraph dispatcher has no moveFrom or moveTo case, and no accept, reject or edit API appears (VolodymyrBaydalka/docxjs@191d3e0db009da578fbe4da70d55305cd8d50226:src/document-parser.ts:87-100,479-549,631-654; src/html-renderer.ts:82-84,127-129,947-994,1048-1073; src/docx-preview.ts:29-48). Extended comment parts load, but reply, resolution and thread fidelity was not established (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/pandoc-preview.md:28).

- docx-preview forms pages from section and page-break cues and ignores cached last-rendered page breaks by default; its pagination splits and mutates the parsed paragraph and run children, so the parsed model is not an immutable editing model and gives no Word-equivalent layout or repeat-render guarantee (VolodymyrBaydalka/docxjs@191d3e0db009da578fbe4da70d55305cd8d50226:src/html-renderer.ts:325-367,402-409,421-508). Unknown body or paragraph children get no default diagnostic, unsupported styles at most a debug console warning, render fallback returns null, and the public pipeline returns no structured loss report (src/document-parser.ts:127-150,286-287,493-549,1378-1389; src/html-renderer.ts:870-896). No browser comparison was run (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/pandoc-preview.md:30-32).

## SuperDoc

- SuperDoc's README says v1 made ProseMirror the document authority and v2 uses an OOXML-backed model, and the public shell 2.15.0-next.12 pins the separate proprietary `@superdoc/docx-engine` at 0.14.0-next.11 (superdoc/docx-editor@3bad86724392f1b91685a3b0cc1f82c9d998b410:README.md:75-84; superdoc/docx-editor@3bad8672:packages/superdoc/package.json:4,128-129; read 2026-09-14). OOXML authority is therefore a declared architecture, not an inspected serializer (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/superdoc.md:24).

- SuperDoc's shell export delegates to the mounted editor's `exportDocx` and rethrows a v2 generation error, but returns the original stored file when no exporter is mounted or the export result is falsy, so it is not a never-fall-back contract (superdoc/docx-editor@3bad86724392f1b91685a3b0cc1f82c9d998b410:packages/superdoc/src/core/SuperDoc.ts:4161-4206). Its shared Document API validates the mode and implements no serialization itself (superdoc/docx-editor@3bad8672:packages/document-api/src/export/export.ts:42-72). The shell tests use mocked exporters: a failed v2 generation rejects the export, and a successful one returns the editor's bytes rather than the opened file (superdoc/docx-editor@3bad8672:packages/superdoc/src/core/SuperDoc.export.test.ts:79-117; bodies reread 2026-10-08, not run). They prove boundary intent, not package round-trip integrity (docs/plite/research/2026-09-14-docx-interoperability-oss/shards/superdoc.md:25-27).

## Package preservation

- Open XML SDK keeps an unknown element as lazy raw outer XML until it is parsed, so generic source ownership sits below the semantic APIs (dotnet/Open-XML-SDK@431ab05cf160248cc3885a4a766026d4f8243792:src/DocumentFormat.OpenXml.Framework/OpenXmlUnknownElement.cs:15-218). `OpenSettings` offers `MaxCharactersInPart` and markup-compatibility settings, an optional per-part ceiling rather than a complete browser ZIP budget (src/DocumentFormat.OpenXml.Framework/Packaging/OpenSettings.cs:8-76; read 2026-09-15, not run; docs/plite/research/2026-09-15-docx-post-implementation-oss/read-log.tsv:30-31). The tests the 2026-09-15 read cited as no-op reopen-and-save proof, `W014_MaxCharactersInPart` and `W013_MarkupCompat_ProcessLoadedPartsOnly` (test/DocumentFormat.OpenXml.Tests/DocxTests01.cs:819-857, bodies reread 2026-10-08), open a document read-only with those settings and count validator errors, so they prove the settings, not a package round trip (read-log.tsv:32).

- python-docx loads every reachable OPC part, keeping an opaque blob in a generic `Part` when no specialized part class exists, walks the relationship graph, and writes all reachable parts and relationships back (python-openxml/python-docx@e45454602b53e8e572b179ccf1c91093ec9f4ed7:src/docx/opc/part.py:21-180; src/docx/opc/package.py:46-166,182-219; src/docx/opc/pkgwriter.py:1-115; read 2026-09-15). That is package-level preservation as a substrate; its semantic support stays deliberately narrower than Word (docs/plite/research/2026-09-15-docx-post-implementation-oss/read-log.tsv:33-35; shards/retained-source-and-package-editing.md:19).

- Across DOCX engines that preserve source packages, the shared law is not 'keep the ZIP': preservation state has an identity and a lifetime, and every edit either maps to a retained source unit or invalidates the affected unit (docs/plite/research/2026-09-15-docx-post-implementation-oss/shards/retained-source-and-package-editing.md:21-23, comparing OpenDoc, Scriptor, Folio, EigenPal, docx-cli, docx-redline-js, Open XML SDK and python-docx at the revisions in each entry on this page).

- OpenDoc (CasualOffice, a Rust DOCX and ODT engine) returns from import a normalized document, resources, a compatibility report and an opaque source envelope; export distinguishes semantic, preserve-when-safe and exact-if-unchanged modes and diagnoses a mismatched envelope instead of trusting it (CasualOffice/opendoc@7a408cf034f3efdc1ed2101c640ce296a6ba4d5b:crates/casual-doc-io/src/docx.rs:1-210; CasualOffice/opendoc@7a408cf0:docs/34-OOXML-FIDELITY-ARCHITECTURE.md:1-260). Its entry, expanded-byte and compression limits are host-configurable and apply before retention (CasualOffice/opendoc@7a408cf0:crates/casual-doc-package/src/limits.rs:1-133). Regenerated body references can leave preserved parts unreachable. It had 7 GitHub stars on 2026-09-15, so maturity claims are weak (docs/plite/research/2026-09-15-docx-post-implementation-oss/shards/retained-source-and-package-editing.md:12,27-32; read-log.tsv:9-11; repo-registry.tsv:2).

- Scriptor (truespar, a Rust CRDT DOCX editor) retains the original parts on `from_docx_bytes`, but its CRDT snapshots exclude them, so a document rebuilt from a snapshot saves a minimal package until the caller reattaches the source parts (truespar/scriptor@46559bbb1eac15b18335cd19249120393fddd853:crates/scriptor-crdt/src/doc/lifecycle.rs:120-141; truespar/scriptor@46559bbb:crates/scriptor-crdt/src/doc/import.rs:162-235,390-406). Save clones the retained parts and rewrites model-owned parts and relationships (truespar/scriptor@46559bbb:crates/scriptor-crdt/src/doc/save.rs:26-113). Its corpus notes separate whole-part from inside-part fidelity: a regenerated `document.xml` still loses unmodeled elements unless a raw span or typed node owns them (truespar/scriptor@46559bbb:docs/passthrough.md:1-257). Corpus results are self-reported and the project had 1 star (docs/plite/research/2026-09-15-docx-post-implementation-oss/shards/retained-source-and-package-editing.md:34-40; read-log.tsv:12-16).

- Folio (stella, a ProseMirror DOCX editor) saves by overlaying changed paragraph XML on the original archive when change tracking proves an edit local, and falls back to a full repack for structural or untracked changes, new relationships, unsafe paths, invalid models, orphan comment ranges and other cases the splice cannot explain (stella/folio@b931cd379bf8eed3a0a3ee31128ee0a72ecce18a:packages/core/src/docx/selectiveSave.ts:294-490; stella/folio@b931cd37:packages/core/src/docx/rezip.ts:899-1285). It reports feature-specific compatibility outcomes (stella/folio@b931cd37:packages/core/src/docx/compatibility.ts:13-124), and its corpus edit round-trip test requires the saved package to keep the same part names and every part except the body byte-identical (stella/folio@b931cd37:packages/core/src/docx/__tests__/corpusEditRoundtrip.test.ts:52-80; body reread 2026-10-08, not run). Later repairs show the invalidation table is core architecture, not cleanup (docs/plite/research/2026-09-15-docx-post-implementation-oss/shards/retained-source-and-package-editing.md:42-48; read-log.tsv:17-20).

- EigenPal docx-editor 2.x makes one typed and generic OOXML package tree canonical: XML stays as tree nodes and binary parts as bytes, ProseMirror is a projection, and the reverse binding emits minimal tree operations or refuses edits it cannot map; the editor owns package load and save directly (eigenpal/docx-editor@84c46227d4ce4c4098a04dbccc4516578f2ab72d:docs/site/content/core/architecture.mdx:7-75; eigenpal/docx-editor@84c46227:packages/core/src/store/package/ooxml-package.ts:122-189; eigenpal/docx-editor@84c46227:packages/core/src/binding/tree-binding.ts:1-68; eigenpal/docx-editor@84c46227:packages/core/src/contracts/editor.ts:313-347). That fits a DOCX-native product; in a cross-format editor it would replace the document with Word's vocabulary and duplicate math, emoji, media, table, comment and custom-node ownership. Core is Apache-2.0, editor-api and pro are proprietary (docs/plite/research/2026-09-15-docx-post-implementation-oss/shards/retained-source-and-package-editing.md:50-55; repo-registry.tsv:5).

- Surgical DOCX tools keep unrelated bytes but have no general edit mapping. docx-cli's `Document` facade owns the loaded ZIP and rewrites selected OOXML views for a bounded command vocabulary (kklimuk/docx-cli@e528738ed22d1294be7938d7614525b4a585fa56:src/core/ast/document/package.ts:5-152; kklimuk/docx-cli@e528738e:src/core/ast/document/index.ts:16-164). docx-redline-js keeps original bytes, cloned working entries and a package revision token, validates only introduced errors, rolls back atomic failures, and its test helper inventories allowed part changes, but its custom ZIP reader has no expanded-byte or compression-ratio limit (AnsonLai/docx-redline-js@616b7f515c44a417f3700b84847ad6be21aeea74:node/docx-document.js:51-260; AnsonLai/docx-redline-js@616b7f51:node/zip-archive.js:6-52; AnsonLai/docx-redline-js@616b7f51:tests/helpers/package-fidelity.mjs:26-209). A package-entry inventory makes unrelated part changes observable and complements semantic reopen checks (docs/plite/research/2026-09-15-docx-post-implementation-oss/shards/retained-source-and-package-editing.md:57-61; read-log.tsv:25-29).

- DOCX preservation fails along independent dimensions, so each needs its own proof: package admission, part reachability, source identity, owned-part invalidation, semantic reopen, review behavior, UI persistence and resource cost (docs/plite/research/2026-09-15-docx-post-implementation-oss/shards/retained-source-and-package-editing.md:82-85). Failure history read on 2026-09-15 shows them apart. In EigenPal docx-editor a no-op ProseMirror save dropped page and line breaks (#56) and header images multiplied on every no-op save (#70), both fixed by the 2.x move to OOXML-tree authority; #113, merge-field and formatting damage, stays open with a report not tied to 2.x; and PR #243 aligned the 2.x lossless claims with save and reopen coverage. Folio PR #697 replaced a preservation allowlist that dropped embeddings, macros and unknown parts, PR #795 repaired authored formatting provenance, and issue #806 lost comment edits at the React state boundary despite correct package code. OpenDoc PR #98 added an opaque retained-parts side table, drops invalidated digital signatures, and states that body-referenced opaque parts can survive as orphaned bytes (https://github.com/eigenpal/docx-editor/issues/56, /issues/70, /issues/113, /pull/243; https://github.com/stella/folio/pull/697, /pull/795, /issues/806; https://github.com/CasualOffice/opendoc/pull/98; same shard:63-80; read-log.tsv:36-43).

- CKEditor 5 48.0.1 (`ckeditor/ckeditor5@14e73cc3`, GPL-2.0-or-later or a commercial license) gets data by downcasting the model to a data view and running a configurable data processor, with root and trim options and `stringify(fragment)` (`ckeditor/ckeditor5@14e73cc3:packages/ckeditor5-engine/src/controller/datacontroller.ts:123-156`, `:173-330`).
