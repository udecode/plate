# Editor architecture: performance

## Mount and split cost

- On the nine-editor common fixture of 2026-09-09, at 10,000 equal paragraphs the mount and split p95 were 528.3 ms and 95.7 ms for Plite, 1,018.5 ms and 139.9 ms for Plate, and 51.9 ms and 11.0 ms for ProseMirror. The fixture had 945 cells (933 passing, six unsupported, six failing). These are Chromium measurements of frozen bundles on one M5 Max host, and the interaction clocks stopped at a frame opportunity, not at verified paint. Source: `docs/editor-audits/reports/editor-performance-research-iteration-2-2026-09-09.md:21-26`. Limit: the Plite and Plate source revisions are not pinned in the preserved summary; rerun before citing a current gap.

## React state adapters

- React's `useSyncExternalStoreWithSelector` keeps snapshot and selection memoization local to one concurrent hook instance and commits the rendered selection (`facebook/react@9635257c:packages/use-sync-external-store/src/useSyncExternalStoreWithSelector.js:1-135`). It is the first reference for any editor selector-adapter redesign; mutable caches shared across renders are what to avoid. The September 2026 study set was chosen from source, not popularity: a GitHub search for Compiler use in popular TypeScript repositories returned 275 results with mostly unrelated matches. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/react-compiler.md:29-35`, `read-log.tsv:8`.

- Other state owners studied for Compiler-friendly reads: Zustand selects a store snapshot and delegates equality to React's selector adapter (`pmndrs/zustand@2115efb9:src/react.ts`, `src/traditional.ts:20-58`); Jotai's `useAtomValue` compares value, store and atom identity and owns subscription cleanup (`pmndrs/jotai@3e0b9ffa:src/react/useAtomValue.ts:110-185`); Sanity's Compiler guidance, updated in September 2026, covers library consumers, an experimental Oxc transform, custom-JSX restrictions, inspecting emitted output, and an ESLint setup that can skip TypeScript files while exiting successfully; Excalidraw owns a mutable scene with its own batching and pointer scheduling, which says nothing about text-editor Compiler performance; TanStack Virtual's imperative measurement object sits behind a semantic Compiler exclusion; and tldraw's state-react implementation was not resolved in the checkout. React's Compiler debugging guide separates safe optimization skips from behavior changes and warns against depending on incidental memoization identity, and `useSyncExternalStore` requires a stable snapshot while data is unchanged. Adding Zustand or Jotai beside the editor store would create a second authority. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/react-compiler.md:37-46`, `repo-registry.tsv:20-24`.

## Text buffers

- VS Code's 2018 text buffer reimplementation post (https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation) describes piece-tree subtree aggregates and buffer line starts that avoid large line arrays, and warns that hot-read allocation and boundary costs can erase edit wins; a September 2026 Plite probe saw exactly that when each edit was followed by a full-string read. Source: `docs/plite/research/2026-09-09-editor-performance-iteration-2/read-log.tsv:3`, `experiments.md:107`.

## Markdown parser cost

- **Two micromark paths can grow superlinearly.** Definitions are appended without deduplication and label checks use `Array.includes`, so R reference checks against D definitions can cost O(R × D) (`micromark/micromark@6577c200155e9c6b85a42b26d298f8affc348f2f:packages/micromark/dev/lib/parse.js:31-40`, `micromark/micromark@6577c200155e9c6b85a42b26d298f8affc348f2f:packages/micromark-core-commonmark/dev/lib/definition.js:195-207`, `micromark/micromark@6577c200155e9c6b85a42b26d298f8affc348f2f:packages/micromark-core-commonmark/dev/lib/label-end.js:245-249`); and each closing emphasis sequence scans back through earlier events for an opener, which the code itself flags as a bottleneck on hostile input, with splice costs on success (`micromark/micromark@6577c200155e9c6b85a42b26d298f8affc348f2f:packages/micromark-core-commonmark/dev/lib/attention.js:34-79`, `:144-174`). This is a source-derived argument, not a measurement, and ordinary prose need not hit either path. Separately, reparsing every growing prefix makes a caller's total work quadratic even with a linear parser, and micromark's stream API buffers output until `end` because definitions can arrive later. Source: `docs/research/probes/2026-09-28-conversion-boundary/prior-art/findings.md:70-77`.

- **markdown-it's speed is real, but its benchmark changes semantics.** Delimiter balancing records failed-search lower bounds and jump distances, and inline skipping and backtick state cache earlier scans (`markdown-it/markdown-it@3c51991c32aaa2b002a52c009334ebe5752c84b3:src/rules_inline/balance_pairs.ts:41-111`, `markdown-it/markdown-it@3c51991c32aaa2b002a52c009334ebe5752c84b3:src/parser_inline.ts:90-135`). Its `current-commonmark` benchmark replaces URL and link-text normalization with simple encoding and identity, its published throughput table is historical, and the CommonMark and default presets differ in HTML handling and in nesting caps of 20 and 100, where the inline cap admits an incorrect-link case and the block cap skips nested content (`markdown-it/markdown-it@3c51991c32aaa2b002a52c009334ebe5752c84b3:benchmark/implementations/current-commonmark/index.mjs:3-13`, `markdown-it/markdown-it@3c51991c32aaa2b002a52c009334ebe5752c84b3:src/parser_inline.ts:119-131`, `markdown-it/markdown-it@3c51991c32aaa2b002a52c009334ebe5752c84b3:src/parser_block.ts:69-77`). Compare parsers only with matched dialect, extensions, URL behavior, nesting limits, output and downstream mapping. Source: `docs/research/probes/2026-09-28-conversion-boundary/prior-art/findings.md:79-85`.
