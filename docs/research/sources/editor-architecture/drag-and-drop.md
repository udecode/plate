# Editor architecture: drag and drop

## Drag libraries compared

- Three drag libraries split a block editor's work differently (source reads on 2026-10-02). Pragmatic Drag and Drop (PDD, `atlassian/pragmatic-drag-and-drop@abd224dd`, Apache-2.0) gives native element, text-selection and external adapters with dynamic targets and completion, but source anchors, exact view routing, serialization, final admission and scheduler coordination stay with the editor. Modern `@dnd-kit/dom` (`clauderic/dnd-kit@e522d9c6`, MIT) gives pointer, touch and pen activation, keyboard drag, collision and feedback, but native text, files and other applications still need another driver, and its selection, feedback and scrolling plugins also write the DOM (`clauderic/dnd-kit@e522d9c6:packages/dom/src/core/plugins/selection/PreventSelection.ts`, `clauderic/dnd-kit@e522d9c6:packages/dom/src/core/plugins/feedback/Feedback.ts`, `clauderic/dnd-kit@e522d9c6:packages/dom/src/core/plugins/scrolling/Scroller.ts`). React DnD (`react-dnd/react-dnd@1de654eb`, MIT, npm 16.0.1) gives a manager, monitors and native HTML5 payloads, but touch needs a separate backend whose keyboard option only cancels a drag on Escape (`react-dnd/react-dnd@1de654eb:packages/backend-touch/src/TouchBackendImpl.ts:587-595`), and serialization and provider and backend coordination stay with the editor. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:51-56`. Limit: source reads only; no library ran.

- Modern dnd-kit (`@dnd-kit/dom` 0.5.0) is a different library from legacy `@dnd-kit/core` 6.3.1, so legacy documentation says nothing about it. Its documented sensors are Pointer and Keyboard, and its public core exports `PointerSensor` and `KeyboardSensor` but not `DragSensor` (`clauderic/dnd-kit@e522d9c6:packages/dom/src/core/index.ts:21-29`). `DragSensor` has no native `drop` handler, at that head and at 0.5.0, although it stops its manager on `dragend` (`clauderic/dnd-kit@e522d9c6:packages/dom/src/core/sensors/drag/DragSensor.ts:98`), so complete native drag interoperability is not established. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:58`, `:139`; exports reread at that commit on 2026-10-08.

- Pragmatic Drag and Drop's three adapters (element, text selection, external) fit native interoperability better than dnd-kit, but they do not pick one recipient. Its drop-target walk skips a target whose `canDrop` refuses and keeps climbing to the ancestors, collects every accepting target on the path, and calls `onDrop` on each of them (`atlassian/pragmatic-drag-and-drop@abd224dd:packages/core/src/make-adapter/make-drop-target.ts:132-160`, `:166-193`), so an editor must still choose the one recipient. Its text-selection payload carries the starting `Text` node plus the plain and HTML data, not a mapped source range (`atlassian/pragmatic-drag-and-drop@abd224dd:packages/core/src/adapter/text-selection-adapter.ts:79-92`), so an editor still captures the native source itself. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:60`; code reread at that commit on 2026-10-08.

## Other editors

- BlockNote drags blocks with native side-menu handles, its own serialization and ProseMirror integration, and offers keyboard move shortcuts (`TypeCellOS/BlockNote@1e26f1c5:packages/core/src/extensions/SideMenu/dragging.ts`, `TypeCellOS/BlockNote@1e26f1c5:packages/core/src/extensions/SideMenu/SideMenu.ts`; core is MPL-2.0). Each of its five drag-and-drop end-to-end tests is declared with `test.skipIf(browserName === "firefox")`, because Playwright does not simulate drag events correctly in Firefox (`TypeCellOS/BlockNote@1e26f1c5:tests/src/end-to-end/dragdrop/dragdrop.test.tsx:34-35`, `:54`, `:97`, `:115`, `:135`). The remote head `14e14caefd29f610b3374ecd6fe7559f46d97e35` was not inspected. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:110`, `repo-registry.tsv:8`; test declarations reread at that commit on 2026-10-08, not run.

- All five editors inspected on 2026-10-02 (ProseMirror, Tiptap, BlockNote, Lexical, legacy Slate) commit the drop in the editor engine from native events, with no drag library in that path. That supports engine-owned mutation; it does not show hand-written browser mechanics are the cheapest choice. Several clones predated their upstream heads; the exact commits are in `docs/plite/research/2026-10-02-dnd-library-choice/repo-registry.tsv`. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:106-114`.

## Library proof limits

- A drag library does not supply an editor's coverage. Pragmatic Drag and Drop's testing guidance recommends testing the consuming experience, its text-selection Playwright test returns early unless the browser is Firefox (`atlassian/pragmatic-drag-and-drop@abd224dd:packages/core/__tests__/playwright/text-selection.spec.ts:15-16`), and its accessibility guidelines make the application build accessible alternatives. React DnD's test backend drives the manager directly through `simulateBeginDrag`, `simulateHover`, `simulateDrop` and `simulateEndDrag` (`react-dnd/react-dnd@1de654eb:packages/backend-test/src/TestBackend.ts:54-74`), and its HTML5 backend spec runs against a stubbed manager (`react-dnd/react-dnd@1de654eb:packages/backend-html5/src/__tests__/HTML5Backend.spec.ts:103-109`). None of these establishes touch-device, OS-application, Chromium or WebKit behavior. Source: `docs/plite/research/2026-10-02-dnd-library-choice/README.md:127-129`; test sources reread at those commits on 2026-10-08, not run.

## Block drop landing

- **BlockNote's drop landing.** BlockNote (`TypeCellOS/BlockNote@1e26f1c5e1cd`) lands drops through ProseMirror `dropPoint` over a block-structured schema (doc, blockGroup, blockContainer), so a dragged block fits only into a blockGroup or a column. It can land in any nested children list and in columns, but not in table cells, whose content is inline (`TypeCellOS/BlockNote@1e26f1c5e1cd:packages/core/src/blocks/Table/block.ts:303-305`), and a pointer inside a childless block lands as a sibling (inferred from `dropPoint` order). Every blockContainer at any depth gets a handle: hover climbs to `data-node-type=blockContainer`, then re-probes for the innermost nested block. Column and columnList never get one. Plugin policy adds multi-column edge drops, where the left edge or the right 10% creates a columnList or a new column, and a separate same-table row and column drag that clamps the pointer to the source table and refuses targets that would split merged cells (`TypeCellOS/BlockNote@1e26f1c5e1cd:packages/core/src/extensions/TableHandles/TableHandles.ts:358-500`). Hover costs an unthrottled side-menu mousemove with two `elementsFromPoint` calls, and a document-level dragover queries every `.bn-editor` rect to route cross-editor drags. Source: `docs/plite/research/2026-10-02-dnd-landing-policy/editors.tsv:14-19`.

- **CKEditor 5's drop landing.** CKEditor 5 (`ckeditor/ckeditor5@14e73cc31b86`) lands block drops from schema flags plus geometry. The target is before or after the closest model element with `isBlock`, or a binary-searched child of a container that accepts `$block`, split at the vertical midpoint. Insertion goes through the clipboard pipeline's schema-checked `insertContent`, and the source is deleted only after the insertion succeeds (`ckeditor/ckeditor5@14e73cc31b86:packages/ckeditor5-clipboard/src/dragdroptarget.ts:384-501`, `ckeditor/ckeditor5@14e73cc31b86:packages/ckeditor5-clipboard/src/dragdrop.ts:455-480`). Table cells and block quotes inherit `$container`, so drops land inside them, and disallowed content cancels the move. Widgets and selected top-level blocks can be dragged: the block toolbar button becomes the handle and offsets `clientX` by 100 px into the content. The open-source table, list and quote packages have no row or column drag. Every dragover runs `findDropTargetRange`, which over a container gap filters all children with `getComputedStyle`, and marker writes are throttled to 40 ms. Source: `docs/plite/research/2026-10-02-dnd-landing-policy/editors.tsv:38-43`.

- **Who decides where a dragged block lands.** Across ProseMirror, Tiptap, BlockNote, Lexical, ProseKit, Slate and CKEditor 5, read at their recorded revisions on 2026-10-02, the schema decides where a dragged block may land in every editor with block drag except Lexical, whose block plugin reorders root children only; Slate has no block drag, and normalization repairs its caret-point drop. Rules such as 'rows stay in their table' and 'columns stay in their group' live in a dedicated table or column gesture, never in the generic block drop. Plate's root-only default was the outlier on 2026-10-02 and was then replaced by schema-derived landing, where features keep only the vetoes the schema cannot state (`docs/research/decisions/dnd-ownership.md`). Source: `docs/plite/research/2026-10-02-dnd-landing-policy/README.md:12`.
