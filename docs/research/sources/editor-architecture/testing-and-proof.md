# Editor architecture: testing and proof

## contenteditable playground traces

- The `easylogic/contenteditable` playground records an edit as an event chain: capture listeners record `getTargetRanges()`, the browser selection, `beforeinput` text-node snapshots, deleted rects, input-time DOM changes and composition events (`src/components/Playground.tsx:1889-2029`); its case playground flags missing `beforeinput`, parent or container mismatch, data mismatch, selection jumps, text leaks, node-type changes, composition mismatch and sibling creation (`src/components/CasePlayground.tsx:300-575`); a DOM-change tracker computes deleted rects from target ranges or a selection fallback and classifies added, deleted, modified and moved text nodes (`src/utils/dom-change-tracker.ts:22-170`); and a text-node tracker keys text-node identity and parent signatures in a WeakMap (`src/utils/text-node-tracker.ts:1-95`). Source: `c70bacbd4a:docs/plite/research/2026-06-13-contenteditable-event-trace-oracles/read-log.tsv:2-5`. Limit: unpinned local clone read on 2026-06-13; the catalog UI itself was rejected as a dependency.

## Playwright and contenteditable

- Playwright issues show why a model-owned contenteditable needs real keyboard proof. In microsoft/playwright#40986 a `selectionchange` listener that replaces the selected text node with identical text makes a quick Home then Shift+End leave an empty native selection, because the anchor stays in detached DOM (repro `janpe/playwright-selectionchange-race-repro`, `playwright/tests/home-shift-end.spec.ts:1-56`, with a React variant in `vitest-browser/src/Editor.tsx:1-47`). In #36715 a contenteditable whose `beforeinput` handler prevents the default, mutates a text node and sets the selection makes Firefox `locator.fill()` fail while keyboard input works (repro `ITenthusiasm/playwright-issue-firefox-fill`, `examples.test.ts`). In #39492 `locator.fill()` appends instead of replacing when the editor's focus handling interferes with fill's internal select-all. Lexical discussion facebook/lexical#2659 adds that JSDOM covers contenteditable behavior too weakly for editor tests. Source: `c70bacbd4a:docs/plite/research/2026-06-13-fresh-oss-selection-navigation-scout/README.md:36-51`, `read-log.tsv:2-7`; `c70bacbd4a:docs/plite/research/2026-06-13-playwright-selectionchange-race-oracles/read-log.tsv:2-5`. Limit: issue bodies and unpinned local repro clones read on 2026-06-13; none is a Plite runtime bug.

## IME and device automation limits

- Standard automation cannot prove native IME behavior. W3C WebDriver issue w3c/webdriver#1683 says the actions model cannot simulate IME input well enough for composition scripts; WPT issue web-platform-tests/wpt#13464 records that Input Events tests need real user interaction and that contenteditable selection through WebDriver is weak; the Chrome DevTools Protocol `Input.imeSetComposition` drives Chromium only and proves no OS candidate UI or device keyboard; Appium's Unicode keyboard sends non-ASCII text directly on iOS and through a special keyboard on Android, which is text injection, not composition; and Appium `mobile: performEditorAction` dispatches Done or Search to the focused field without creating composition text. Android's IME framework exposes the primitives a deterministic test IME would drive: `InputMethodService`, `InputConnection`, `setComposingText`, `commitText`, `deleteSurroundingText` and selection-update callbacks (https://developer.android.com/develop/ui/views/touch-and-input/creating-input-method). ProseMirror's forum thread on contenteditable on Android shows keyboard, browser and version variation (https://discuss.prosemirror.net/t/contenteditable-on-android-is-the-absolute-worst/3810). Source: `c70bacbd4a:docs/plite/research/2026-06-13-native-ime-device-proof-methods/README.md:40-60`, `source-registry.tsv:2-9`. Limit: web sources read on 2026-06-13.

- **CDP IME is not an OS input method.** In Chromium, DevTools `Input.imeSetComposition` and `Input.insertText` call the same widget `ImeSetComposition` and `ImeCommitText` that an OS IME reaches, but with empty spans and a `Focus()` call. A real macOS IME first sends a keydown with `VKEY_PROCESSKEY` (229) and then `ImeSetComposition` with IME underline spans; the Mac view forwards that to the same widget host. CDP therefore exercises the renderer path but not the key event, the underline spans or the OS candidate window. Evidence: `chromium/chromium@main:content/browser/devtools/protocol/input_handler.cc:1281-1359`, `chromium/chromium@main:content/app_shim_remote_cocoa/render_widget_host_view_cocoa.mm:155-190`, `:1640-1700`, `chromium/chromium@main:content/browser/renderer_host/render_widget_host_view_mac.mm:2271-2290`, read 2026-10-02 (`docs/plite/research/2026-10-02-agentic-e2e-testing/read-log.tsv:376-378`). Limit: `main` was read, not a pinned commit.

- **Chromium's own IME tests mock the input method.** Chromium's unit tests for the Mac and Aura views call `setMarkedText` or `SetCompositionText` on the view with mock hosts or a mock input method; no OS IME runs. Evidence: `chromium/chromium@main:content/browser/renderer_host/render_widget_host_view_mac_unittest.mm:98`, `chromium/chromium@main:content/browser/renderer_host/render_widget_host_view_aura_unittest.cc:1388-1440`, read 2026-10-02 (`docs/plite/research/2026-10-02-agentic-e2e-testing/read-log.tsv:384-385`). Limit: `main` is not pinned.

- **Driving the real macOS IME.** `CGEventPost` posts an event at a tap location ahead of the taps at that location. Posting and listening need the event post and listen access grants, with preflight and request APIs since macOS 10.15. The HID tap is the point where hardware events enter the window server. `TISSelectInputSource` needs a source that is enabled and select-capable, and an input mode also needs its parent enabled. App activation is cooperative, so an activation request is not guaranteed. On macOS 26, a programmatic switch to a CJKV source may not take effect until the app reactivates: macism waits 150 ms on a temporary window, and rime/squirrel issue 1162 (open) reports the IMK controller staying inactive until the user switches apps. Evidence, all read 2026-10-02: the macOS 26 SDK headers `CoreGraphics/CGEvent.h:347-354,398-408` and `HIToolbox/TextInputSources.h` (`TISSelectInputSource`); Apple's documentation for `NSApplication.activate()` and `CGEventTapLocation.cghidEventTap`; laishulu/macism `README` and `InputSourceManager.swift` (HEAD as of 2026-05-23); rime/squirrel issue 1162. Limit: macism and squirrel were read at HEAD, not at a pinned commit.

- **Select Pinyin by its source id.** `TISCopyInputSourceForLanguage("zh-Hans")` can return another zh-Hans source, such as Shuangpin, Wubi or handwriting. A lane should select `com.apple.inputmethod.SCIM.ITABC` by id and check that its parent `com.apple.inputmethod.SCIM` is enabled and select-capable. Plate's macOS helper does both. Evidence: `docs/plite/research/2026-10-02-agentic-e2e-testing/review/interrogate-pass2-a.md:168` and `interrogate-pass2-b.md:136`; `tooling/ime/macos-ime.swift:125,138`, checked 2026-10-08.

- **No surveyed editor drives a real OS input method in its tests.** Lexical composes through CDP, ProseMirror and CodeMirror dispatch synthetic composition events and edit text nodes, VS Code replays recorded real sequences, Chromium's own view tests use mock input methods, and bromure forwards a captured macOS composition over CDP again (each under its editor's input or testing page, and under 'IME tests from recorded or captured real input' and 'Chromium's own IME tests mock the input method' on this page). A GitHub code search on 2026-10-02 for `TISSelectInputSource` together with `CGEventPost` in test tooling found nothing relevant, so Plate's macOS Pinyin lane (`tooling/ime/macos-ime.swift`, `apps/www/tests/native/homepage-ime.native.ts`) had no editor prior art to copy. Limit: the editors were read at unpinned heads on 2026-10-02, and the search covered GitHub code search only. Source: `docs/plite/research/2026-10-02-agentic-e2e-testing/shards/006-real-ime-for-5137.md:58-65`.

## Randomized and generated tests

- CodeMirror's randomized view tests draw from an unseeded `Math.random`: `can handle replace-all like events` and `correctly handles very complicated transactions` dispatch random change batches and assert the drawn DOM text equals the document slice of the viewport (`codemirror/view@fbff59ba:test/webtest-draw.ts:152-210`), and `properly handles random decorations and changes` applies 50 rounds of random edits and mark decorations and asserts the line's `innerHTML` nests the marks as expected (`test/webtest-draw-decoration.ts:210-262`). None records a seed, a replay command or a reduced case, so a failure cannot be replayed. Source: `c70bacbd4a:docs/plite/research/2026-06-14-generated-stress-replay-reduction/read-log.tsv:9`; tests reread at the pinned commit on 2026-10-08.

- WPT's `editing/data/` holds one fixture table per `execCommand`, 35 in all, such as `bold.js`: each row gives the input HTML with a selection marker, the commands to run, the expected HTML and the expected command-state results (`web-platform-tests/wpt@dd54691426c23a08c6f4a0972b2c40965307e5ce:editing/data/bold.js:1-25`). They are portable invariant corpora to harvest, with no replay or reduction machinery. Source: `c70bacbd4a:docs/plite/research/2026-06-14-generated-stress-replay-reduction/read-log.tsv:10`.

## Agentic and mobile test tools

- **tester-army `e2e` cannot open a website on a phone.** Its mobile engine, built on agent-device, launches an installed app or a build: a `mobile()` target that declares `app.url` fails with `INVALID_CONFIG`, so `e2e` 0.15.2 cannot load a web page in a device browser, and its web engine drives desktop Playwright browsers. Evidence: `tester-army/e2e@c6c39ad3:packages/mobile/src/engine.ts:86-100`, read 2026-10-02 and rechecked 2026-10-08 at that commit. Limit: the error says URL targets are not supported yet; recheck once they land.

- **The `e2e` agent types into a targeted field with `locator.fill`.** The agent's targeted `type` verb sends a `fill` action, which the web engine runs as Playwright `locator.fill`; only the untargeted `typeText` verb types through `page.keyboard.type`. The agent recording of the rich-text benchmark that ships with `e2e` starts with a targeted `type` into the contenteditable editor and then presses keys, so a replay of that act fills the editor; the benchmark's deterministic tests type with `browser.keyboard.type` instead. Plate's harness does not accept `fill()` as editor proof, because it can bypass or mis-model the editor's `beforeinput` path (`packages/test/README.md:162`). Evidence: `tester-army/e2e@c6c39ad3:packages/e2e/src/agent/action-dispatcher.ts:336-344`, `tester-army/e2e@c6c39ad3:packages/web/src/actions.ts:52-54`, `tester-army/e2e@c6c39ad3:packages/web/src/surface.ts:750-770`, `tester-army/e2e@c6c39ad3:apps/web-benchmark/.e2e/cache/16433aa0d367e6f0dfe2857d4621edd499a5f4343337c8803c316fde3eb9da45.json`, `tester-army/e2e@c6c39ad3:apps/web-benchmark/tests/rich-text-editor.e2e.ts:7-13`; rechecked 2026-10-08. Limit: a trial would have to force untargeted typing through a custom executor and assert the model after every act.

- **How the `e2e` replay cache keys and verifies acts.** Recorded agent acts replay from a cache whose key is a SHA-256 of the JCS-canonical key fields: spec and cache-schema versions, a hash of the project id, test, target, platform, engine name, engine version cut to major.minor, engine SPI version, step kind, the call's index among same-signature calls, instruction and parameter digests, app identity and policy version. The model and the executor are not in the key. `verifyAnchors` returns true for an empty anchor set, so a replayed act proves at most that its recorded end anchors are present, not that the act had its effect; issue 686 lists a same-node text mutation, the editor case, among effects that record no anchor. Issue 685 reports that the key holds no `agentContext`, account identity or executor version, and that the replay's route check drops the query string and the origin and folds minted path segments such as numeric ids (`tester-army/e2e@c6c39ad3:packages/e2e/src/cache/route.ts:45-51`, `:65-92`). In CI the defaulted cache mode drops to read-only, and model preflight only checks that a model is configured, without a live request, so CI with no model credential passes fully replayed acts while live acts and judgments still need the model. Evidence: `tester-army/e2e@c6c39ad3:packages/e2e/src/cache/identity.ts:27-45`, `:154-184`, `tester-army/e2e@c6c39ad3:packages/e2e/src/agent/replay.ts:361-366`, `tester-army/e2e@c6c39ad3:packages/e2e/src/config/resolve.ts:322-331`, `:394`, `tester-army/e2e@c6c39ad3:packages/e2e/src/run/worker-models.ts:1-43`, `tester-army/e2e@c6c39ad3:docs/ci.mdx:173-178`; rechecked 2026-10-08. On 2026-10-02 the maintainer closed issues 685 and 686 as not planned, moved to an internal tracker, saying public issues are for user reports, so later work on these gaps may not show publicly. Limit: any replayed editor step needs a deterministic model assertion after it.

- **`e2e` has no editor input surface.** The `browser` fixture's keyboard has only `press` (one key or chord) and `type` (plain text), and its mouse only `move`, `wheel`, `down` and `up`; there is no `insertText`, held-key, IME composition or clipboard API. An editor model oracle or custom matcher would need a wrapper engine around `web()` whose fixtures record assertion steps through the engine context's `fixture` and `expectable`. The raw Playwright `Page` is meant for custom executors: `surfaceOf` reads a WeakMap private to the web engine's module, test modules load in isolated tsx realms, and the docs say `surfaceOf` is not for test code. Evidence: `tester-army/e2e@c6c39ad3:packages/web/src/browser.ts:219-240`, `tester-army/e2e@c6c39ad3:packages/e2e/src/engine/index.ts:179-243`, `tester-army/e2e@c6c39ad3:packages/e2e/src/engine/manifest.ts:151-184`, `tester-army/e2e@c6c39ad3:packages/web/src/engine.ts:30`, `:45-50`, `tester-army/e2e@c6c39ad3:packages/e2e/src/internal/realm-slot.ts:1-6`, `tester-army/e2e@c6c39ad3:docs/migrate/playwright.mdx:400-403`; rechecked 2026-10-08. Limit: that a fixture in a test file cannot reach the live page is inferred, and a wrapper around `web()` was not run.

- **The `e2e` agent cannot see a collapsed caret.** Its text snapshot reports a field's selected text only for a non-collapsed selection and returns nothing for a collapsed caret, and the reader reports no caret position at all, so a caret bug is invisible to the agent unless it uses vision. It also models a contenteditable editing host as one textbox whose blocks are its content. Evidence: `tester-army/e2e@c6c39ad3:packages/web/src/in-page/read-semantics.ts:132-145`, `:710-729`; rechecked 2026-10-08.

- **Accessibility-tree cross-check pattern.** `e2e` checks every node of its web engine's semantic tree against two oracles on the same page: Chrome's accessibility tree over CDP and a Playwright `getByRole(role, { name })` round trip. Each known disagreement is listed with a reason in an expected-disagreement file; a new disagreement fails, and so does a listed one that stopped happening. A third oracle holds the reader to axe-core's role and name expectations. This is a cheap proxy for accessibility-tree claims, not screen-reader proof. Evidence: `tester-army/e2e@c6c39ad3:AGENTS.md:266-297`, `tester-army/e2e@c6c39ad3:packages/web/tests/integration/crosscheck.test.ts`; rechecked 2026-10-08. Limit: Plate's 2026-10-02 proof review promoted the pattern for popup and focus claims (`docs/plite/research/2026-10-02-agentic-e2e-testing/promoted-ledger.tsv:3`), but on 2026-10-08 no Plate test compared the CDP accessibility tree with `getByRole` (`git grep` for `getFullAXTree`, `getPartialAXTree` and cross-check).

- **Strict replay gate.** `e2e`'s benchmarks commit their replay recordings, CI replays them read-only, and `--strict-cache` (or `cache: { strict: true }`) fails a stale recording with `REPLAY_STALE`, exit code 2 and no retry, without calling a model. Evidence: `tester-army/e2e@c6c39ad3:docs/cache.mdx:209-269`, `tester-army/e2e@c6c39ad3:AGENTS.md:359-372`; rechecked 2026-10-08.

- **argent drives Chromium only through CDP.** argent probes for a CDP endpoint at `127.0.0.1` on port 9222, on the ports in `ARGENT_CHROMIUM_PORTS` and on ports it booted, and its `debugger-evaluate` tool runs JavaScript in a Chromium target's V8. - **argent reads Chrome's accessibility tree on Android.** `argent describe` reads the screen through `uiautomator dump`. Chromium builds a WebView's accessibility tree only on the first request for it, so argent re-reads every 250 ms for up to 1.5 s until the web content appears; its comment measures 10-400 ms for a small page on API 35 with WebView 124 and about 600 ms for a Chrome tab over a long article. Chrome web content is therefore readable as native accessibility nodes on Android. Evidence: `software-mansion/argent@a824fcba:packages/tool-server/src/tools/describe/platforms/android/index.ts:71-100`; rechecked 2026-10-08. Limit: it shows what is exposed, such as an option's role, name and selected state, not what a screen reader announces.

## Caret paint and screenshots

- **Chrome's caret blinks unless a style stops it.** Blink's `FrameCaret` blinks.
