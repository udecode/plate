# Editor architecture: testing and proof

## contenteditable playground traces

- The `easylogic/contenteditable` playground records an edit as an event chain: capture listeners record `getTargetRanges()`, the browser selection, `beforeinput` text-node snapshots, deleted rects, input-time DOM changes and composition events (`src/components/Playground.tsx:1889-2029`); its case playground flags missing `beforeinput`, parent or container mismatch, data mismatch, selection jumps, text leaks, node-type changes, composition mismatch and sibling creation (`src/components/CasePlayground.tsx:300-575`); a DOM-change tracker computes deleted rects from target ranges or a selection fallback and classifies added, deleted, modified and moved text nodes (`src/utils/dom-change-tracker.ts:22-170`); and a text-node tracker keys text-node identity and parent signatures in a WeakMap (`src/utils/text-node-tracker.ts:1-95`). ## Playwright and contenteditable

- Playwright issues show why a model-owned contenteditable needs real keyboard proof. In microsoft/playwright#40986 a `selectionchange` listener that replaces the selected text node with identical text makes a quick Home then Shift+End leave an empty native selection, because the anchor stays in detached DOM (repro `janpe/playwright-selectionchange-race-repro`, `playwright/tests/home-shift-end.spec.ts:1-56`, with a React variant in `vitest-browser/src/Editor.tsx:1-47`). In #36715 a contenteditable whose `beforeinput` handler prevents the default, mutates a text node and sets the selection makes Firefox `locator.fill()` fail while keyboard input works (repro `ITenthusiasm/playwright-issue-firefox-fill`, `examples.test.ts`). In #39492 `locator.fill()` appends instead of replacing when the editor's focus handling interferes with fill's internal select-all. Lexical discussion facebook/lexical#2659 adds that JSDOM covers contenteditable behavior too weakly for editor tests. ## IME and device automation limits

- Standard automation cannot prove native IME behavior. W3C WebDriver issue w3c/webdriver#1683 says the actions model cannot simulate IME input well enough for composition scripts; WPT issue web-platform-tests/wpt#13464 records that Input Events tests need real user interaction and that contenteditable selection through WebDriver is weak; the Chrome DevTools Protocol `Input.imeSetComposition` drives Chromium only and proves no OS candidate UI or device keyboard; Appium's Unicode keyboard sends non-ASCII text directly on iOS and through a special keyboard on Android, which is text injection, not composition; and Appium `mobile: performEditorAction` dispatches Done or Search to the focused field without creating composition text. Android's IME framework exposes the primitives a deterministic test IME would drive: `InputMethodService`, `InputConnection`, `setComposingText`, `commitText`, `deleteSurroundingText` and selection-update callbacks (https://developer.android.com/develop/ui/views/touch-and-input/creating-input-method). ProseMirror's forum thread on contenteditable on Android shows keyboard, browser and version variation (https://discuss.prosemirror.net/t/contenteditable-on-android-is-the-absolute-worst/3810).
