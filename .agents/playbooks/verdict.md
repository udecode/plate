# Verdict

Verdict says what to do from an input. Intake reads any input, such as a teammate's doc, a draft, an issue, a PR or a one-line idea, and writes one page that closes at once: pushback, one outcome per item and an order. The deep path judges one ledger scope with the `best-api` lens and writes a Stop, Pursue or Defer into its review page's front matter. This playbook owns both paths, their outcomes and where each stops. [The review ledger](../../docs/research/schema.md#review-history) owns the scope files, the front-matter keys and the helper commands, and it keeps answers. Chips, through `.agents/pstack/rules/chips.md` and the `chips` skill, hold every open question.

## Paths

The deep path runs on:

- `verdict <scope id>` or `review <scope id>` when the argument is exactly the id of a file in `docs/research/review-scopes/`, and the scope is not a PR;
- `audit <scope or group id>` and `verdict <group id>`, which give each scope of the set a verdict;
- a `decide` chip whose topic is `review-<id>`, when `<id>` names a file in `docs/research/review-scopes/` or the chip's `writes:` names `docs/research/review-scopes/<id>.json`;
- a `verdict` that another playbook or skill runs inside its own run, on the scope that owns its target, or on a scope file it adds for that target when no scope owns it, as the schema says, such as Build's verdict on a replaced panel-fix mechanism, Bug fix's verdict on an owner after failed fixes, `best-api repair`'s verdict on a correction and `research`'s Stop, Pursue or Defer assessment. It returns to that run, which owns the close.

Any other `verdict <material>` or "what would you do from <material>" runs intake: a pasted doc, a file path even when `lookup` maps it to one scope, an issue, a PR, a draft or a one-line idea. Intake uses `lookup` only for context. A bare `verdict` takes the material already in the request and asks for some when there is none. A paste with no ask is not a verdict request. A `decide` chip in any other topic, a `review-` topic that names no scope included, answers its question on its own plan page with the deep path's method, and touches the ledger only when a scope owns its question. "review PR <number>" stays with the Babysit playbook, a lone bug report with the Bug fix playbook, and work on a public issue with `maintainer`.

## Intake

Intake judges each item of the input and writes no review. It splits the input into items, one per claim, proposal, defect or question, and gives each one outcome. "Open question" is an item outcome, never the page's `## Open questions` section.

| Outcome | Intake gives it when | Evidence bar | Writes |
| --- | --- | --- | --- |
| Bug | Current behavior breaks a law, a decision or the user's job | The defect at a path and line read this session, within the claim width of `docs/vision/common.md`'s Claim Width table. P0 or P1 only when this session reran the repro or a failing test exists; otherwise P2 with the reported steps | A `fix` chip, a `decide` chip when the fix is itself a design choice, or a `folded` row on the open task that covers it |
| Settled | Current law, a review head, a subject decision or landed code with its test answers the exact question, or the input's own later decision withdrew the proposal | The deciding artifact; a ledger head whose `lookup` freshness is `matching` | Nothing; `open <n>` reverses it |
| Stop | The proposal earns no further work: a false premise, a law it breaks without arguing against it, or a shipped API that already does the job | The law or fact at a path and line, with the incumbent shown. Missing evidence is never Stop, and an argument that the law is wrong is an Open question | Nothing and no scope verdict; `open <n>` reverses it |
| Defer | A named observation or prerequisite can change the answer | What would settle it and which result changes the answer | A chip for that evidence: one that waits on a real task, plan or PR where one exists, a P3 measurement chip when the measure cannot fit the hour, or, for an outside event no wait can name, a P3 chip whose finding names the event and where to look |
| Open question | A real choice remains between owners, stored shapes, APIs or behaviors, the input argues that a standing decision is wrong, or it proposes removing behavior | The question, the evidence and the lanes seen, not judged | A `decide` chip by Topics below. For a proposed removal the owner did not ask for, intake keeps the behavior, as the architecture reference's Hard cut says |

**Depth.** Intake settles an item only on an artifact it read this session, and only as wide as that artifact proves: a source trace shows ownership, not a browser or screen-reader result. It never changes a scope's accepted architecture and never gives a Pursue, because those need the deep path's requirements, lanes and dependents. An outside probe or a confidence label in the input is a claim, not evidence. An item that needs more than its cited spans and the governing law becomes an Open question or a Defer. When in doubt, offer the chip.

**Topics.** A chip reuses topic `review-<scope>` only when that scope's ledger question owns the item; a different question takes `review-<new id>`, and its deep session writes the scope file. Its `writes:` names `docs/plans/topics/<scope>.md` and the paths the answer would change, plus `docs/research/review-scopes/<new id>.json` for a new scope, never the whole `docs/plans` folder, because the chips skill's Offer mode makes a task wait on every active plan whose files it writes. Its priority follows `.agents/pstack/rules/chips.md`'s Priority. Intake reads `node .agents/pstack/decisions-check.mjs chips all --session <id>`, or searches the ledger for each item's terms where the runtime's session tool gives no id, and the `chips brief <task id>` of each task whose title or topic touches an item, because the default board only counts P2 and P3 work. For an Open question or Defer on scope X, the first rule that matches decides:

1. X has a ship item that no task serves and that waits on no plan: the ship item's own offer, with `ship: X`, as `kind: decide` for pursue-not-adopted, with the intake question in its finding.
2. The question challenges a design that an open task or plan builds: a `decide` chip that waits on nothing, whose finding names that task or plan.
3. Otherwise: an offered `decide` chip.

Offer each row through the `chips` skill's Offer mode, which folds a finding into an open task that asks the same question and adds the `run:` and `task:` waits. When `append` refuses one, follow its message. A fold onto a closed task becomes a new offer, and Pushback names the input's stale reference.

**Page.** `docs/plans/<date>-<slug>-intake.md` and its decision log, with no front matter and no `Topic:`, so it changes no scope's head, ship item or subject page. `Status: done: <n> items, <k> chips offered, <f> folded` closes it at once, and `Playbook: verdict`. Its sections are a lead paragraph, Brief, Pushback, Items, Order, Defaults for real picks only, and Close. Pushback names the input's contradictions, doctrine it applies selectively, probes nobody can rerun, stale references and wrong premises. Items is one table: `#`, item, outcome, scope, strongest reason, evidence, and next, a chip id or none. Order says what to do first and why. The page paraphrases the input and cites it by section, because it lands on the public branch. It lands through `land.mjs` before the hand-back, so a card session can read it, and publishes with `page-stop.mjs stop`. Then the lead runs the chips sweep as the deep path's last hand-back step says. The reply is the page link, then the sweep's report, or the count line in a card session, and the landed commit, as `.agents/pstack/rules/land.md`'s Review says.

**Bounds.** Intake runs no lanes, `architect`, panel, arena or research, and writes no review page, subject file, code, test, doc or scope file besides its page and log. It reads the input, the spans it cites, the governing law, `lookup` for the scopes it touches and the chips board as Topics says, plus one repro rerun of at most ten minutes for each claimed P0 or P1 bug. It gives no Pursue, plan, build or scope verdict, sends no public message, runs the chips sweep only at its close and takes one input per session.

## Deep path

### Verdicts

Decide whether further work is justified. Agreement is not the default, and "keep the current design; this change adds no material value" is a successful review.

| Verdict | Meaning | End of this review |
| --- | --- | --- |
| **Stop** | No material benefit, unjustified machinery, a violated hard constraint, or it loses to the current design. | State why and keep the current design. No plan, task or consolation backlog. |
| **Pursue** | Evidence supports a material problem and a better direction, which may replace the proposal. | Name the single next owner, and continue into the Plan playbook when it is that owner. |
| **Defer** | A named evidence gap or external prerequisite can change the verdict. | State what would settle it, offer a chip for that evidence by the intake Defer row, and offer the successor `decide` chip Steps name. |

A governing rule can itself be the obstacle. When a decision in the scope's subject file, or a rule in `VISION.md` or `docs/vision/`, blocks the strongest target, list "the rule is wrong" as a lane: quote the rule, name the job it protected and show why that job no longer holds or another owner now carries it. A Pursue on that lane rewrites a subject-file decision as part of its plan. A rule in Vision binds several scopes, so the plan asks the owner under Open questions before it changes one, and it keeps building whatever does not depend on the answer.

Missing evidence alone is not Stop, and an API that does not exist yet is design work, not an evidence gap. Stop only after the stronger change lanes also fail. Be blunt about the proposal, not the person: lead with the verdict and its strongest reason, without invented minor improvements or a menu of equal choices.

A previous verdict is evidence, not law. Changed requirements, contradictory evidence, source changes or a materially better argument reopen it at the question level: a paint defect does not reopen settled topology or resize decisions. A Pursue whose target already landed is written as a Stop, with the landed work as evidence.

A Stop cited from another workflow, such as a failed-fix escalation, reads `verdict: stop: <reason>`.

**Never leave a verdict unwritten.** A review page carries its `verdict` front matter before the reply. When `node tooling/scripts/review-ledger.mjs check` refuses the page, its message names the fix; fix the front matter in the same run. A new head or fork needs judgment before it is reconciled. Name a page still unfixed in the reply and in the plan's decision log, so a later session finishes it.

## Sessions

One input, one scope or one audit's set per session. Once the lead knows the scope or the input, its first act after loading poteto-mode is to title the session with it, such as `👥 ui (2/7)`. A session that already gave a verdict leaves other inputs and scopes to chips: it offers a chip that runs `verdict` on a new one through the chips skill's Offer mode, and the owner starts it from a card or with "start <id>". "again", a verdict another playbook runs mid-run, and a Pursue's own plan and build, which continue in the same run as Steps say, are the exceptions. A scope needs no verdict when its head's own page or a plan on its basis already landed or closed it and only the record misses that, such as a review page that built its own Pursue without `work_kind`; the lead fixes the record, lands the fix and ends, instead of writing a new verdict.

## Steps

- **In** "Route through the **how** skill", for intake: skip the `how` skill. Read the input in full and split it into items. For each item, read the spans it cites and the law that governs it, run `node tooling/scripts/review-ledger.mjs lookup <scope-or-feature>` for each scope it touches, and read the chips board as Topics says. Rerun a claimed P0 or P1 repro once, for at most ten minutes. Then give each item its outcome under Depth.
- **Before** "Route through the **how** skill", for the deep path that a `decide` chip in a `review-<id>` topic starts: log its task's rows from its brief, as `AGENTS.md`'s Suggested tasks rule says. When the chip's `writes:` names a scope file that does not exist yet, create it for its question, as the schema says. When the scope has no subject file, create `docs/plans/topics/<scope>.md` with its title, a lead that states what has landed and been proven for it, its current owners under `## Main changes`, and `## What other editors do` from its newest review or a `research` pass, because the page refuses to render a subject with a ledger hub and no editor comparison.
- **Before** "Route through the **how** skill", for the deep path: reconcile the scope's history. Before judging a scope or starting an audit, run `node tooling/scripts/review-ledger.mjs lookup <scope-or-feature>` for it and read the sources it links; `unreviewed` does not mean untouched. Read a lookup's `open`, `freshness`, `executions`, `plans`, `documents` and `candidates` even when `head` is null, and use `lookup <scope> --detail` or `show <scope>` when omitted records can change the recommendation. Search `docs/plans`, its subject files under `docs/plans/topics` and retained review records for the user job, older package and API names and related consumers, because a broad audit or regression plan may hold completed work without its own review record. Say "no prior work found" only after the lookup and the plan search, with the search's limits stated; missing bindings and stale evidence stay proof limits. Missing review bindings do not establish that no work happened. Every repeated request then challenges the strongest deletion or replacement alternative; keep unchanged questions settled when the challenge adds no value, and no reassessment flag is required. An unreviewed scope needs a review. A `fork` scope has two current reviews and needs a review that reconciles both. A `pursue-not-adopted` scope has no landed implementation or workflow plan adopting its Pursue and needs a plan, so it goes to the Plan playbook instead. A scope an open plan is working through, whose ship item waits on that plan with `run:`, gets no second review; when that plan is this session's own, continue it. A started `decide` chip is the exception to both. Its finding asks a question the head did not settle, or challenges the design an open plan builds, so it gets a verdict on that question first. A Pursue that keeps the head's target then goes to the Plan playbook, or back to the open plan, which reads the verdict.
- **Replace** "Produce the `how`-shaped output": for intake, write the page under Page, offer its chips under Topics, land the page and its log and publish it. For the deep path, give the scope one verdict from Verdicts above. Inspect the owning implementation, its public types and each materially different consumer, including copied UI and kits that own the policy, because a package-only trace cannot settle ownership. The scope's `lookup` lists its `dependents`, each scope whose code outside plitejs imports it, with the importing files; add what you read of them to `review_inputs`. Judge the call shape with the `best-api` lens and ownership with `.agents/playbooks/references/architecture.md`, reading their decision sections without starting their workflows, and compare the alternatives as `docs/vision/common.md`'s Redesign from First Principles says. Before a lane deletes code that its owners call a workaround, run `pstack:why` on it, and record each cut's predicted benefit in Evidence so the plan's Close marks it held or falsified. When a target changes what an owner accepts, the ingress census records the object each path hands that owner, raw or rebuilt. Write the verdict into the scope's open review iteration or a new `docs/plans/<date>-<scope>-<slug>.md`, before any panel, so the panel's rows land beside it. Its lead paragraph gives the verdict and the strongest reason, `## Public API` pairs the current and proposed normal call sites, or the ownership flow when no public call changes, and Defaults hold the picks among the lanes. Evidence opens with a `### Requirements` list of the scope's current jobs and hard laws, explicit user constraints included, and Evidence holds a `### Lanes` list of at least two lanes considered, the strongest deletion or merger among them, and the proof limits, and a `### Dependents` list naming each dependent beside a `review_inputs` path from it, or beside "unaffected" and the reason. For a Stop or Defer verdict, Defaults record hold, with again and interrogate as the words that change it. `Status:` becomes `planning` for Pursue, `closed: Stop verdict` for Stop, or `blocked: waiting on <evidence>` for Defer. A Defer offers its evidence chip by the intake Defer row and a successor `decide` chip in topic `review-<scope>` that waits on the evidence chip, and also on the started task when a `decide` chip ran the review; the successor owns the renewed verdict. Give the subject file real current call sites under `## Public API` when it lacks them. Before the verdict reply, every material review, Stop and Defer included, sets its page's front matter: `review_scopes` with the scope first, `verdict`, `review_basis` naming the head `lookup` reported and every other head, or `[]` for a first review, `review_commit` naming the commit the review read, and `review_inputs` and `review_upstreams` for anything else it read. An audit's page lists every judged scope in `review_scopes`, gives each its verdict in `verdict: [<scope>=<verdict>, ...]` and names each scope's head in `review_basis`, with one `review_commit`. Evidence has a `Model:` line naming the model that ran the review, or `Model: unknown`, and never reconstructs hidden instructions or invents a historical model name; it names each earlier review and landed plan of the scope that this review retains, reopens or supersedes, and why, and each external checkout and the commit it read. A changed verdict reopens or supersedes its previous review and never retains it. A receipt carried from an earlier review stays current only while every input its run exercised is unchanged; otherwise label it historical and rewrite the claims and limits from the current proof inventory. Run `lookup` for the task's scopes again, and when `coverage` lists source no scope owns, add it to the owning scope's `members`; membership never certifies review. Run `node tooling/scripts/review-ledger.mjs check` last, after the evidence census, the file and line references, those `members` edits and the writing passes, and fix every error it names for the page in the same run. The scope's subject file, `docs/plans/topics/<scope>.md`, is the one home of its current decisions and rejected alternatives: a Stop or Defer verdict that changes a conclusion rewrites that part of the subject file in place, and a Pursue's conclusion folds in when its build closes. A Stop or Defer verdict then lands the page through `land.mjs`, publishes it and closes with the last hand-back step below. A Pursue verdict publishes the page with its verdict first, then continues in the same run into the Plan playbook on the same file, and the plan goes on to its build as the Autopilot rule says. A page that `check` refuses, or a blocked verdict write, follows Never leave a verdict unwritten above.
- **Replace** "Apply the **unslop** skill to the reply": write the reply clean as drafted, with no separate pass, per `AGENTS.md`'s Writing passes rule. The page, the subject file and the page's plan get one `unslop` pass.
- At a deep path's last hand-back, whether a Stop, a Defer, a plan that stops at the plan or a landed build, the lead checks the record before the reply. When the run landed a build of a pursued design and `node tooling/scripts/review-ledger.mjs ship` still lists its item, the lead checks whether only the item's record misses the landing, and if so fixes the record as Sessions says. After the last land and the page's close stop, it runs the `chips` skill's Sweep, as `/chips` does, which offers the ledger's open items and cards what can start (owner's word, 2026-10-21). This sweep replaces the count line of `.agents/pstack/rules/chips.md`'s Close. It overrides chips.md's Sweep rule, `AGENTS.md`'s Suggested tasks rule and the `chips` skill's line that repeats them, which all sweep only on `/chips`. It also replaces the hand-back line of that skill's Offer step 4. A session a card started runs no sweep and prints that count line instead. A runtime without a suggest tool lists the sweep's Ready tasks in the reply, because the page has already landed. A Stop adds no plan or task of its own. The reply is the page link, then the sweep's report, or the count line in a card session, and the landed commits, as `.agents/pstack/rules/land.md`'s Review says, which are the additions to the Plan pages rule's link-only reply.
- After a verdict, a typed word picks the next step. "again" runs the same path once more on the same target and challenges the strongest alternative afresh; a deep page names the last review in `review_basis` and reaffirms or supersedes it, and an intake folds what it finds into its own earlier offers and offers nothing twice. "interrogate" or "panel" runs the panel on the verdict's target with the configured seats. "plan" opens the Plan playbook on the verdict's file anyway. `open <n>` turns an intake item's Settled or Stop into an Open question, offers its chip, updates that row and the page's counts, and lands the page again.
