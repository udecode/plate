# Verdict

This playbook judges a scope with the `best-api` lens. It owns the method and the verdicts below, writes the verdict into the review page and says where to stop.

## Verdicts

Decide whether further work is justified. Agreement is not the default, and "keep the current design; this change adds no material value" is a successful review. Use `audit <scope>` when every candidate in a bounded set needs a verdict.

| Verdict | Meaning | End of this review |
| --- | --- | --- |
| **Stop** | No material benefit, unjustified machinery, a violated hard constraint, or it loses to the current design. | State why and keep the current design. No plan, task or consolation backlog. |
| **Pursue** | Evidence supports a material problem and a better direction, which may replace the proposal. | Name the single next owner, and continue into the Plan playbook when it is that owner. |
| **Defer** | A named evidence gap or external prerequisite can change the verdict. | State what would settle it and recommend only that investigation. |

Missing evidence alone is not Stop, and an API that does not exist yet is design work, not an evidence gap. Stop only after the stronger change lanes also fail. Be blunt about the proposal, not the person: lead with the verdict and its strongest reason, without invented minor improvements or a menu of equal choices.

A previous verdict is evidence, not law. Changed requirements, contradictory evidence, source changes or a materially better argument reopen it at the question level: a paint defect does not reopen settled topology or resize decisions. A Pursue whose target already landed is written as a Stop, with the landed work as evidence.

A Stop cited from another workflow, such as a failed-fix escalation, reads `verdict: stop: <reason>`.

## One item per session

Each item runs in its own session. Once the lead knows the item, its first act is to title the session with the item's scope as the Session title rule's `<name>`, such as `👥 ui (2/7)`, before poteto-mode's first step. When this session already worked on another item, the lead does not start the new one here, so each item keeps its page, log and title in one session. It starts a new session in this checkout with the prompt `verdict <scope>`, through the runtime's tool that starts a session, such as Claude Code desktop's `start_session`. Without that tool, it offers the same prompt as a one-click suggestion, such as `spawn_task`, whose brief names the scope and why it is open. Such a suggestion opens its session in a worktree, so the brief tells that session to move to this checkout before its first step, such as with Claude Code desktop's `change_directory`, and to work only there. A worktree lacks this checkout's uncommitted rules. A runtime with neither tool puts the prompt in its reply, for the owner to start a new session in this checkout. The handing-off session takes no further step on the new item.

**Never leave a verdict unwritten.** A review page carries its verdict before the reply. Name a page still unwritten in the reply and in the plan's decision log, so a later session finishes it.

## Steps

- **Before** "Route through the **how** skill": read the named source first, reconcile relevant plans and research, and choose one bounded owner. An audit is read-only.
- **Before** "Route through the **how** skill", for a named scope or proposal: reconcile its history. Search `docs/plans`, `docs/research/decisions` and retained review records for the user job, older package and API names and related consumers, because a broad audit or regression plan may hold completed work without its own review record. Say "no prior work found" only after the plan search, with the search's limits stated; stale evidence stays a proof limit. Every repeated request then challenges the strongest deletion or replacement alternative; keep unchanged questions settled when the challenge adds no value, and no reassessment flag is required.
- **Replace** "Produce the `how`-shaped output": for a named scope, give it one verdict from Verdicts above. Inspect the owning implementation, its public types and each materially different consumer, including copied UI and kits that own the policy, because a package-only trace cannot settle ownership. Judge the call shape with the `best-api` lens and ownership with `.agents/playbooks/references/architecture.md`, reading their decision sections without starting their workflows, and compare the alternatives from first principles, as the `pstack:principle-redesign-from-first-principles` skill says. Before a lane deletes code that its owners call a workaround, run `pstack:why` on it, and record each cut's predicted benefit in Evidence so the plan's Close marks it held or falsified. When a target changes what an owner accepts, the ingress census records the object each path hands that owner, raw or rebuilt. Write the verdict into a new `docs/plans/<date>-<scope>-<slug>.md`, before any panel, so the panel's rows land beside it. Its lead paragraph gives the verdict and the strongest reason, `## Public API` pairs the current and proposed normal call sites, or the ownership flow when no public call changes, and Defaults hold the picks among the lanes. Evidence opens with a `### Requirements` list of the scope's current jobs and hard laws, explicit user constraints included, and Evidence holds a `### Lanes` list of at least two lanes considered, the strongest deletion or merger among them, and the proof limits. For a Stop or Defer verdict, Defaults record hold, with again and interrogate as the words that change it. `Status:` becomes `planning` for Pursue, `closed: Stop verdict` for Stop, or `blocked: waiting on <evidence>` for Defer. Give the subject file real current call sites under `## Public API` when it lacks them. Evidence has a `Model:` line naming the model that ran the review, or `Model: unknown`, and never reconstructs hidden instructions or invents a historical model name; it names each earlier review and landed plan of the scope that this review retains, reopens or supersedes, and why, and each external checkout and the commit it read. A changed verdict reopens or supersedes its previous review and never retains it. A receipt carried from an earlier review stays current only while every input its run exercised is unchanged; otherwise label it historical and rewrite the claims and limits from the current proof inventory. Update the decision page's text when the verdict changes its conclusion. A Stop or Defer verdict then publishes the page, replies with its link and stops. A Pursue verdict publishes the page with its verdict first, then continues in the same run into the Plan playbook on the same file, and the plan goes on to its build as the Autopilot rule says. A blocked verdict write follows Never leave a verdict unwritten above.
- **Replace** "Apply the **unslop** skill to the reply": write the reply clean as drafted, with no separate pass, per `AGENTS.md`'s Writing passes rule. The decision page and the page's plan get one `unslop` pass.
- After a Stop or Defer verdict, the answer to the page's question, or a typed word, picks the next step. "again" runs `verdict` once more on the same scope and challenges the strongest alternative afresh; its page names the last review and reaffirms or supersedes it. "interrogate" or "panel" runs the panel on the verdict's target with the configured seats. "plan" opens the Plan playbook on the verdict's file anyway. "next" picks a new item.
