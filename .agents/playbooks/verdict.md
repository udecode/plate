# Verdict

Verdict says what to do from an input. Intake reads any input, such as a teammate's doc, a draft, an issue, a PR or a one-line idea, and writes one page that closes at once: pushback, one outcome per item and an order. The deep path judges one ledger scope with the `best-api` lens, picks the scope's next step by comparing it with other editors when the owner names the scope or the audit pass reaches it, and writes a Stop, Pursue or Defer into its review page's front matter. The audit pass starts that comparison on each closed scope in turn, so the owner names none. Explore settles a direction with the owner before the lead judges anything. It runs rounds of pushback and research on a scope or an idea, stops for the owner after each round, and hands the direction to the deep path only when the owner locks it. This playbook owns the three paths and the pass, their outcomes and where each stops. [The review ledger](../../docs/research/schema.md#review-history) owns the scope files, the front-matter keys and the helper commands, and it keeps answers. Chips, through `.agents/pstack/rules/chips.md` and the `chips` skill, hold every open question.

## Paths

Explore runs on `explore <scope or idea>`, when the owner types that word first in a request or as the `verdict` skill's argument, such as `/verdict explore <idea>`. The word picks the path, and its argument never does. A scope id after `explore` runs Explore, and the same id after `verdict` runs the deep path. Its argument names something to build or a direction to settle. A request that asks how existing code works stays with `pstack:how`, even when it opens with the word, and "explore" later in a sentence is plain speech. No audit task, `/loop` or other playbook starts Explore, because each of its rounds waits for the owner's answer. A suggested task, a `decide` chip included, runs Explore only when its brief asks for Explore rounds, because the owner starts its session and answers there. The brief's other writes, such as a subject file, wait for `lock`.

The deep path runs on:

- `verdict <scope id>` or `review <scope id>` when the argument is exactly the id of a file in `docs/research/review-scopes/`, and the scope is not a PR;
- a plain ask for one scope's next step, such as "what should we build next for the board?", which runs as `verdict <scope id>` for the scope whose `pnpm kb` entry the feature names. A bare "next" or "what's next" with no feature stays with the `chips` skill;
- `audit <scope or group id>` and `verdict <group id>`, which give each scope of the set a verdict;
- a `decide` chip whose topic is `review-<id>`, when `<id>` names a file in `docs/research/review-scopes/` or the chip's `writes:` names `docs/research/review-scopes/<id>.json`;
- a `verdict` that another playbook or skill runs inside its own run, on the scope that owns its target, or on a scope file it adds for that target when no scope owns it, as the schema says, such as Build's verdict on a replaced panel-fix mechanism, Bug fix's verdict on an owner after failed fixes, `best-api repair`'s verdict on a correction and `research`'s Stop, Pursue or Defer assessment. It returns to that run, which owns the close.

Any other `verdict <material>` or "what would you do from <material>" runs intake: a pasted doc, a file path even when `lookup` maps it to one scope, an issue, a PR, a draft or a one-line idea. Intake uses `lookup` only for context. A bare `verdict` takes the material already in the request and asks for some when there is none. A paste with no ask is not a verdict request. A bare `audit` or `audit restart` runs neither path. It runs one step of the audit pass, as Audit pass says, and judges no scope itself. A `decide` chip in any other topic, a `review-` topic that names no scope included, answers its question on its own plan page with the deep path's method, and touches the ledger only when a scope owns its question. "review PR <number>" stays with the Babysit playbook, a lone bug report with the Bug fix playbook, triage of a udecode/plate issue with the Triage playbook, and other public GitHub work with `maintainer`.

## Intake

Intake judges each item of the input and writes no review. It splits the input into items, one per claim, proposal, defect or question, and gives each one outcome. "Open question" is an item outcome, never the page's `## Open questions` section.

| Outcome | Intake gives it when | Evidence bar | Writes |
| --- | --- | --- | --- |
| Bug | Current behavior breaks a law, a decision or the user's job | The defect at a path and line read this session, within the claim width of `docs/vision/common.md`'s Claim Width table. P0 or P1 only with the repro evidence `.agents/pstack/rules/chips.md`'s Priority asks, a failing test or exact steps someone ran and saw fail, such as this session, a tester or the reporter; otherwise P2 with the steps as written | A `fix` chip, a `decide` chip when the fix is itself a design choice, or a `folded` row on the open task that covers it |
| Settled | Current law, a review head, a subject decision or landed code with its test answers the exact question, or the input's own later decision withdrew the proposal | The deciding artifact; a ledger head whose `lookup` freshness is `matching` | Nothing; `open <n>` reverses it |
| Stop | The proposal earns no further work: a false premise, a law it breaks without arguing against it, or a shipped API that already does the job | The law or fact at a path and line, with the incumbent shown. Missing evidence is never Stop, and an argument that the law is wrong is an Open question | Nothing and no scope verdict; `open <n>` reverses it |
| Defer | A named observation or prerequisite can change the answer | What would settle it and which result changes the answer | A chip for that evidence: one that waits on a real task, plan or PR where one exists, a P3 measurement chip when the measure cannot fit the hour, or, for an outside event no wait can name, a P3 chip whose finding names the event and where to look |
| Open question | A real choice remains between owners, stored shapes, APIs or behaviors, the input argues that a standing decision is wrong, or it proposes removing behavior | The question, the evidence and the lanes seen, not judged | A `decide` chip by Topics below. For a proposed removal the owner did not ask for, intake keeps the behavior, as the architecture reference's Hard cut says |

**Depth.** Intake settles an item only on an artifact it read this session, and only as wide as that artifact proves: a source trace shows ownership, not a browser or screen-reader result. It never changes a scope's accepted architecture and never gives a Pursue, because those need the deep path's requirements, lanes and dependents. An outside probe or a confidence label in the input is a claim, not evidence. An item that needs more than its cited spans and the governing law becomes an Open question or a Defer. When in doubt, offer the chip.

**Topics.** A chip reuses topic `review-<scope>` only when that scope's ledger question owns the item; a different question takes `review-<new id>`, and its deep session writes the scope file. Its `writes:` names `docs/plans/topics/<scope>.md` and the paths the answer would change, plus `docs/research/review-scopes/<new id>.json` for a new scope, never the whole `docs/plans` folder, because the chips skill's Offer mode makes a task wait on every active plan whose files it writes. Its priority follows `.agents/pstack/rules/chips.md`'s Priority. Intake reads `node .agents/pstack/decisions-check.mjs chips all --session <id>`, or searches the ledger for each item's terms where the runtime's session tool gives no id, and the `chips brief <task id>` of each task whose title or topic touches an item, because the default board only counts P2 and P3 work. For an Open question or Defer on scope X, the first rule that matches decides:

1. X has a ship item that no task serves and that waits on no plan: the ship item's own offer, with `ship: X`, as `kind: decide` for pursue-not-adopted, with the intake question in its finding.
2. The question challenges a design that an open task or plan builds: a `decide` chip that waits on nothing, whose finding names that task or plan.
3. Otherwise: an offered `decide` chip.

Offer each row through the `chips` skill's Offer mode with `via: verdict`, which lets a verdict offer a P2 or P3 task for an item it judges, as chips.md's Offer says. Offer mode folds a finding into an open task that asks the same question and adds the `run:` and `task:` waits. When `append` refuses one, follow its message. A fold onto a closed task becomes a new offer, and Pushback names the input's stale reference.

**Page.** `docs/plans/<date>-<slug>-intake.md` and its decision log, with no front matter and no `Topic:`, so it changes no scope's head, ship item or subject page. `Status: done: <n> items, <k> chips offered, <f> folded` closes it at once, and `Playbook: verdict`. Its sections are a lead paragraph, Brief, Pushback, Items, Order, Defaults for real picks only, Open work for each finding outside the input, naming the subject that owns it, with the chip id of each one that ranks P0 or P1, because chips.md's Offer gives a P2 or P3 finding outside the run's domain no chip and a P0 or P1 one a chip with no owner, and Close. Pushback names the input's contradictions, doctrine it applies selectively, probes nobody can rerun, stale references and wrong premises. Items is one table: `#`, item, outcome, scope, strongest reason, evidence, and next, a chip id or none. Order says what to do first and why. The page paraphrases the input and cites it by section, because it lands on the public branch. It lands through `land.mjs` before the hand-back, so a card session can read it, and publishes no page, because an intake is no page work, as `.agents/pstack/rules/pages.md` defines it. Then the lead cards the run's own offers for items inside the input, and the folded tasks that step names, as the deep path's last hand-back step says. The reply takes the shape of pages.md's Reply bullet, with the items and their order as its comparison, and puts Close's line on the tasks the run offered and carded, or in a card session the tasks it offered, just above its links, which hold the landed commit, as `.agents/pstack/rules/land.md`'s Review says.

**Bounds.** Intake runs no lanes, `architect`, panel, arena or research, and writes no review page, subject file, code, test, doc or scope file besides its page and log. It reads the input, the spans it cites, the governing law, `lookup` and the research pages `pnpm kb <scope>` lists for the scopes it touches, and the chips board as Topics says, plus one repro rerun of at most ten minutes for each claimed P0 or P1 bug. It gives no Pursue, plan, build or scope verdict, sends no public message, runs no chips sweep and takes one input per session.

## Deep path

### Verdicts

Decide whether further work is justified. Agreement is not the default, and "keep the current design; this change adds no material value" is a successful review.

| Verdict | Meaning | End of this review |
| --- | --- | --- |
| **Stop** | No material benefit, unjustified machinery, a violated hard constraint, or it loses to the current design. | State why and keep the current design. No plan, task or consolation backlog. |
| **Pursue** | Evidence supports a material problem and a better direction, which may replace the proposal. | Name the single next owner, and continue into the Plan playbook when it is that owner. |
| **Defer** | A named evidence gap or external prerequisite can change the verdict. | State what would settle it, offer a chip for that evidence by the intake Defer row, and offer the successor `decide` chip Steps name. |

A governing rule can itself be the obstacle. When a decision in the scope's subject file, or a rule in `VISION.md` or `docs/vision/`, blocks the strongest target, list "the rule is wrong" as a lane: quote the rule, name the job it protected and show why that job no longer holds or another owner now carries it. A Pursue on that lane rewrites a subject-file decision as part of its plan. A rule in Vision binds several scopes, so the plan asks the owner under Open questions before it changes one, and it keeps building whatever does not depend on the answer.

Missing evidence alone is not Stop, and an API that does not exist yet is design work, not an evidence gap. Stop only after the stronger change lanes also fail. Be blunt about the proposal, not the person: lead with the verdict and its strongest reason, without invented minor improvements or a menu of equal choices.

A Pursue that rests on a defect shows that defect on a path a user reaches, such as a key, a command or a public call. When only an internal call shows it, the lead paragraph says so and names who can make that call.

A previous verdict is evidence, not law. Changed requirements, contradictory evidence, source changes or a materially better argument reopen it at the question level: a paint defect does not reopen settled topology or resize decisions. A Pursue whose target already landed is written as a Stop, with the landed work as evidence.

Before a review closes another plan, such as a stale plan its scope's ship item waits on, it checks that the tree holds that plan's change. That plan's `Status:` then names what the check found, such as the commit that holds the change or the file that no longer exists.

A Stop cited from another workflow, such as a failed-fix escalation, reads `verdict: stop: <reason>`.

Each open-work item on a Stop or Defer page names its owner and what will bring someone back to it, or says that nothing will.

**Never leave a verdict unwritten.** A review page carries its `verdict` front matter before the reply. When `node tooling/scripts/review-ledger.mjs check <page>` refuses the page, its message names the fix; fix the front matter in the same run. A new head or fork needs judgment before it is reconciled. Name a page still unfixed in the reply and in the plan's decision log, so a later session finishes it.

### Next step

When the owner types `verdict <scope id>` or `review <scope id>`, asks in plain words for that scope's next step, or runs `/loop verdict <scope id>`, the review also picks the scope's next step by what its users gain. So does a review that a task of the audit pass starts, and the review an Explore run converges into. So a closed scope with no new proposal still gets a step to build, cut or redesign. A deep path that answers a narrower question, such as another `decide` chip's, an `audit <scope or group id>` or one another run starts, skips this section.

1. Run `pnpm kb <scope>`, and read the research pages it lists, the scope's subject file and its public docs pages. When it shows the scope in no research area, add the scope to the matching area's `scopes` in `docs/research/areas.tsv`.
2. Under Evidence, write a `### Jobs` table. Each row names a job users pick the scope for, the strongest alternative that does it, such as another editor or library, whether that alternative does it better, as well or worse than this tree, and the source read for that grade. When no page grades a job, run one `research` discovery shard on the ungraded job most likely to change the pick, at most one shard per review, and put its findings on the area page as the research skill's Promotion says. When that shard finds a job that other editors do and no scope's question covers, offer one `decide` chip for it in topic `review-<new id>`, as intake's Topics says, with `via: verdict`, because this review's research judged the job, and with `session: none`, because the new scope lies outside this review's domain and so a `/chips all` cards it. A review offers at most one such chip.
3. Collect the candidates: each job graded worse, each open-work item in the scope's subject file and plans, the strongest deletion or merger, and each redesign that `docs/vision/common.md`'s Redesign from First Principles finds, the rule-is-wrong lane above included. Write `### Lanes` in rank order by what a user gains for the cost, and give each lane its gain and cost. The ranking obeys the Requirements, the owner's constraints included. On a tie, a cut or merge ranks above a redesign, and a redesign above an addition.
4. The top lane is the Pursue, unless no lane's gain is worth its cost, which is a Stop. With a Pursue, a lane that writes none of the pick's files and is worth its cost may become a chip through the `chips` skill's Offer mode with `via: verdict`, so another session can build it at the same time. Every other lane stays on the page, and the next review ranks it again.

### Audit pass

The audit pass runs Next step on every scope that is closed or has no review yet, so the owner names none and misses none. `node tooling/scripts/review-ledger.mjs due` lists the scopes the pass has not reached, each as the task to offer. Its order follows the task board's tiers. Inside a tier, the scope whose owners hold the most commits since its last review began comes first, counted in udecode/plate and in plate-private, because new evidence is what changed a verdict when five October Stops were judged again in November. A scope leaves that list when a review whose Evidence holds a `### Jobs` table with at least one row lists it first in `review_scopes`. The ledger parses no Markdown, so it counts that table only as a head line, a rule line and at least one row that each start with `|` and follow one another, outside code fences and above the page's first line of HTML. A page whose Jobs table it does not count keeps its scope due, and `due` names that page in the scope's finding, so the session reads the page before it judges the scope again.

A bare `audit` runs one step of the pass:

1. Run `node tooling/scripts/review-ledger.mjs coverage`. Add each file it lists as unowned to the `members` of the scope whose question that file serves. When several of those files do a job that no scope's question covers, write a scope file for that question, as the schema says. That scope has no review yet, so `due` lists it too. Land these edits through `land.mjs`.
2. Run `node tooling/scripts/review-ledger.mjs due` from the checkout's root. Take the first three items that have no `waits` and whose topic holds no open `decide` task. Offer each one as written through the `chips` skill's Offer mode, with the item's `id` as its `review-scope:` and this session's own `session:`. An item with no `ship` is a P2 task with `via: verdict`. An item with `ship` is on the ship list, so it is a P1 task with `ship: <that id>` in place of `via:`. When `append` refuses an item, take the next one.
3. Run the `chips` skill's Close, which cards those tasks. The reply names them, gives the number of scopes still due, and names each due scope that waits, with the plan it waits on.

`due` drops an item's wait on a plan the task board dates as idle for a week, because the Long runs rule says such a plan does not resume. The board counts a plan's commits where the waits bullet of `.agents/pstack/rules/chips.md` says, on `origin/next` in this project, and its decision log rows in every checkout. The item of the scope that plan names first then holds the plan in its `writes` and names it in its finding. That scope's verdict decides what becomes of the plan, as Verdicts says of a review that closes another plan. A plan whose `Status:` waits on the owner keeps its wait.

These offers override two limits of the block's Suggested tasks rule, which `.agents/pstack/rules/chips.md`'s Offer states: that a run cards only the findings in its domain, and that a verdict run offers below P1 only an item its own verdict judged. The owner asked on 2026-11-14 for an audit that picks the next scopes itself. So the step and each session of the pass offer the next due scope at the priority step 2 gives, though they judged no part of it, name their own `session:` on the offer, and card it in their own Close. They also override that file's Cards rule, which makes a task wait on an active plan whose files it writes, and which the `chips` skill applies in its Offer mode and before each card. A plan that `due` puts in an item's `writes` is idle, and the item's verdict decides what becomes of it. So the offer and its card take no `run:` wait on that plan, whatever its `Status:` says.

The step also overrides the block's Improve the workflow mid-task rule, which owes a reflect after an audit. The step owes none, because it judges no scope and writes no review page, plan or subject file. One `audit` starts at most three verdicts, because each Pursue goes on to its plan and build.

A session that one of those tasks starts runs `verdict <scope id>` on the task's scope, with Next step. At its last hand-back, before the `chips` skill's Close, it runs `due` again and offers the first item that passes step 2's test, as step 2 says. So each verdict of the pass starts the next one when it ends, and the pass ends when `due` prints an empty list. The owner stops the pass by leaving its cards unstarted.

`audit restart` begins the pass again, such as after a new model comes out. It writes the current UTC time, such as `2026-11-14T09:30:00Z`, to `audit.since` in `.agents/pstack.json`, then runs the step. Step 1's landing carries that edit, even when `coverage` lists no file. `due` then counts only the reviews that began at or after that time, so every closed scope is due again, one reviewed earlier that day included. Nothing else makes a ranked scope due again, a new model included. Five Stops from October, judged again on a new model in November, kept four, and the fifth changed on evidence that landed after its review.

`audit <scope or group id>` is no part of the pass. It gives each scope of its set a verdict in one session and skips Next step. It runs `node tooling/scripts/review-ledger.mjs check <page>` on its first review page before it writes the next, so it fixes a shape the check refuses once, not on every page. That session builds no Pursue. A Pursue page it writes closes with `Status: closed: Pursue verdict, built by its own task`, and `ship` then lists the scope until a plan adopts the Pursue.

## Explore

Explore is for a direction that one pass judges badly, because the owner holds the goal and the lead does not yet, or because the evidence that ranks the steps is not in the tree. The ink verdict of 2026-11-15 answered its card's question in one pass, ended as a Defer on the browser's own handwriting and missed the owner's goal, paper-like pen markup that AI turns into clean edits. So until the owner locks the direction, Explore gives no verdict and writes no plan, code, chip, review page, scope file or subject file. It writes only its run directory and the research pages.

**Run directory.** The run lives in `docs/plans/artifacts/<date>-<slug>-explore/` in the main checkout, written by absolute path. `goal.md` holds the owner's words on the goal, each message verbatim under its date, with no paraphrase. `round-<n>.md` holds round n's reply as sent, then the owner's answer to it, verbatim. Each lane's brief and report sit beside them. After a compaction and in a later session, the lead reads `goal.md` and every round file before its next step. The session keeps its worktree until the run ends.

**Goal.** Round 0 runs no lane and no search. The lead may read the scope's `lookup`, its `pnpm kb` entry and its subject file, so the restatement names what the tree already has. It saves the owner's request in `goal.md`. Its reply gives the goal in one or two sentences, the lead use case as who does what and what they get, and what it takes to be out of scope. Then the run stops. The owner's answer, a correction or a plain yes, goes into `goal.md` and starts round 1.

**Rounds.** From round 1, each round runs these steps:

1. Save the owner's answer in the previous round's file, and in `goal.md` when it changes the goal, the use case or a constraint.
2. List the open questions that evidence can settle and whose answer can move the ranking. Run one research lane for each, as many as the questions need, all at once. Each lane is an evidence seat, run as `AGENTS.md`'s Extraction rule says. Its brief quotes `goal.md`, names what earlier lanes found so the seat repeats none of it, asks for the source, the date read and the grade of each claim, and asks for "not found" in place of a guess.
3. Rank the steps again by what a user gains for the cost, as Next step's step 3 ranks lanes, under the goal in `goal.md`.
4. Put the round's prior art on the research pages as the `research` skill's Promotion says, and land those pages through `land.mjs`, so they outlive a loop the owner never locks.
5. Send the reply below, save it as `round-<n>.md`, and stop.

An answer from the owner that only asks a question gets its answer and starts no round.

**Reply.** A round's reply runs to about 300 words before its links, and the detail stays in the round's files. A round publishes no page, because Explore writes no plan before `lock`; the converged verdict's page publishes at its hand-back, as Steps say. It opens with the pushback, which is harsh honest feedback on the direction as it now stands. The strongest objection comes first, with what the lead would cut and where the direction contradicts the evidence or a law. Agreement is not the default, and a round with no objection says so in one line. The digest follows, in four labeled parts:

- **Learned.** Each finding that bears on the direction, with its source, and what no lane could confirm or nobody ran.
- **Ranking.** The steps in rank order, with the reason for each step that moved, joined or left.
- **Unsure.** What the lead doubts and the evidence that would settle each doubt. These are the next round's candidate lanes.
- **Your calls.** Each call only the owner can make, with the lead's pick.

The reply ends by naming the owner's three answers: `lock`, `drop`, or anything else for another round.

**End.** Only the owner ends the loop. `lock` converges it, as Converge says. `drop` ends the run with no review, and the reply says that the landed research and the run directory stay. A round changes nothing when its lanes moved no rank, added or cut no step and raised no new question. Its reply says so first and asks for `lock`, and it is the last round the lead runs on its own questions. After it, a plain yes counts as `lock`, and only an answer that names a new question, use case or constraint starts another round. A card session runs its close, as `.agents/pstack/rules/chips.md`'s Landing says, after the landing that follows `lock` or `drop`, not after a round's research landing.

**Converge.** On `lock`, the run takes the deep path with Next step, on the scope that owns the direction. When no scope owns it, the lead writes the scope file for its question, as the schema says, and the subject file as Steps say of a `decide` chip's new scope. Explore changes the deep path in four places:

- `### Requirements` opens with the owner's goal, use case and constraints, quoted from `goal.md`.
- The Jobs table and the lanes come from the rounds' research, and the review runs no further shard. `### Lanes` is the last round's ranking. Each lane also names its `owner:`, the scope, playbook or person that takes it next, and its `stop:`, the result or date that ends it or brings someone back to it.
- `lock` is also the owner's word "panel" for the page. The panel runs before the page lands, and its brief lists each outcome that `goal.md` states as an `[ask]` invariant, as `.agents/pstack/rules/panel.md` says of the user's typed ask.
- After the panel's fixes, the lead rewrites the scope's subject file with the direction's decisions, its rejected alternatives and the ranked lanes, without waiting for a build. Then the run builds nothing. A Pursue page closes with `Status: closed: Pursue verdict, built by its own task`, as an `audit <scope or group id>` page does. When its Public API proposes calls, the page also writes `Built by: /loop verdict <scope id>` under its `Status:`, from its first draft. Then the `--folded` render at landing checks its folded rows and leaves its proposed calls on the page. A Defer page closes with `Status: closed: Defer verdict, waiting on <evidence>`, because the subject file already holds the direction and the successor `decide` chip owns the renewed verdict. The reply names `/loop verdict <scope id>`, which builds the lanes one at a time and ranks the rest again after each landing.

**Title.** Until `lock` the session title also carries the round, so the owner sees how far the loop went. It is `🚧 ink (round 2)` while the lead works a round and `🟠 ink (round 2)` from the round's reply until the owner answers, with round 0 for the goal. After `lock` the title follows `.agents/pstack/rules/title.md`.

**Overrides.** Explore overrides four rules, each only as far as this section says. Next step allows one research shard per review, and Explore's rounds run as many lanes as their questions need. `AGENTS.md`'s Autopilot rule runs work to its close without waiting for the owner, and round 0 and every round end in a stop by design; inside a round the lead still takes every call it can. The deep path continues a Pursue into the Plan playbook and its build in the same run, and Explore ends at the subject file. The Session title rule shows only the run's state, and Explore's title also counts rounds.

## Sessions

One input, one scope or one audit's set per session. Once the lead knows the scope or the input, its first act after loading poteto-mode is to title the session with it, such as `🚧 ui`. A session that already gave a verdict leaves other inputs and scopes to chips: for each new one the owner brings, it offers a chip that runs `verdict` on it through the chips skill's Offer mode. That chip takes `via: verdict` at any priority, because its own verdict judges the input. The owner starts it from a card or with "start <id>". "again", a verdict another playbook runs mid-run, and a Pursue's own plan and build, which continue in the same run as Steps say, are the exceptions. So is `/loop verdict <scope id>`, which reviews the same scope again after each Pursue's build lands and ends the loop at its first Stop or Defer. So is an Explore run, which stays in one session where it can, from its goal through its rounds to its converged page, and titles the session as Explore's Title says. A scope needs no verdict when its head's own page or a plan on its basis already landed or closed it and only the record misses that, such as a review page that built its own Pursue without `work_kind`; the lead fixes the record, lands the fix and ends, instead of writing a new verdict.

## Steps

- **In** "Trace the code the question is about", for intake: skip the trace. Read the input in full and split it into items. - **In** "Trace the code the question is about", for Explore: skip the trace. Run round 0 under Explore's Goal and stop. After each answer from the owner, run the next round under Rounds, or end the loop under End. After `lock`, the deep path's changes below apply, with Converge's changes.
- **Before** "Trace the code the question is about", for the deep path that a `decide` chip in a `review-<id>` topic starts: log its task's rows from its brief, as `AGENTS.md`'s Suggested tasks rule says. When the chip's `writes:` names a scope file that does not exist yet, create it for its question, as the schema says. - **Before** "Trace the code the question is about", for the deep path: reconcile the scope's history. Before judging a scope or starting an audit, run `node tooling/scripts/review-ledger.mjs lookup <scope-or-feature>` for it and read the sources it links; `unreviewed` does not mean untouched. Read a lookup's `open`, `freshness`, `executions`, `plans`, `documents` and `candidates` even when `head` is null, and use `lookup <scope> --detail` or `show <scope>` when omitted records can change the recommendation. Search `docs/plans`, its subject files under `docs/plans/topics` and retained review records for the user job, older package and API names and related consumers, because a broad audit or regression plan may hold completed work without its own review record. Say "no prior work found" only after the lookup and the plan search, with the search's limits stated; missing bindings and stale evidence stay proof limits. Missing review bindings do not establish that no work happened. Every repeated request then challenges the strongest deletion or replacement alternative; keep unchanged questions settled when the challenge adds no value, and no reassessment flag is required. An unreviewed scope needs a review. A `fork` scope has two current reviews and needs a review that reconciles both. A `pursue-not-adopted` scope has no landed implementation or workflow plan adopting its Pursue and needs a plan, so it goes to the Plan playbook instead. A scope an open plan is working through, whose ship item waits on that plan with `run:`, gets no second review; when that plan is this session's own, continue it. A started `decide` chip is the exception to both. Its finding asks a question the head did not settle, or challenges the design an open plan builds, so it gets a verdict on that question first. An Explore run after `lock` is another, because its rounds asked the owner's question, so it gets its converged verdict and then builds nothing, as Converge says. A Pursue that keeps the head's target then goes to the Plan playbook, or back to the open plan, which reads the verdict.
- **Replace** "Produce the output": for intake, write the page under Page, offer its chips under Topics, and land the page and its log. For Explore before `lock`, the round's reply under Explore's Reply is the output. For the deep path, and for Explore after `lock` with Converge's changes, give the scope one verdict from Verdicts above, after Next step when it applies. Judge the call shape with the `best-api` lens and ownership with `.agents/playbooks/references/architecture.md`, reading their decision sections without starting their workflows, and compare the alternatives as `docs/vision/common.md`'s Redesign from First Principles says. Write the verdict into the scope's open review iteration or a new `docs/plans/<date>-<scope>-<slug>.md`, before any panel, so the panel's rows land beside it. Evidence opens with a `### Requirements` list of the scope's current jobs and hard laws, explicit user constraints included, and Evidence holds a `### Lanes` list of at least two lanes considered, ranked as Next step says when it applies, the strongest deletion or merger among them, and the proof limits, and a `### Dependents` list naming each dependent beside a `review_inputs` path from it, or beside "unaffected" and the reason. - After a verdict, a typed word picks the next step. "again" runs the same path once more on the same target and challenges the strongest alternative afresh; a deep page names the last review in `review_basis` and retains or supersedes it, and an intake folds what it finds into its own earlier offers and offers nothing twice. "interrogate" or "panel" runs the panel on the verdict's target with the configured seats. "plan" opens the Plan playbook on the verdict's file anyway. `open <n>` turns an intake item's Settled or Stop into an Open question, offers its chip, updates that row and the page's counts, and lands the page again.
