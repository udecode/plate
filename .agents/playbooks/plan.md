# Plan

The third stop of the v2 loop. The plan is the deliverable, and this playbook implements nothing.

- **Before** "Settle open questions by prototype before you write": choose the target by the Architecture decisions section below when the plan picks an API or architecture target. That runs `pstack:architect` for the comparison (reviews: api-plan), then the panel on the finished plan, and records the panel's challenge delta. A row that breaks a public API also passes Best API's hard-cut gate and names its callers, docs, examples and proof.
- **Before** "Settle open questions by prototype before you write": before the plan or a reply states a difficulty, cost or estimate for a behavior change, map what the core already supports and what recent commits removed (`git log -S <symbol>`), because removed paths are often recoverable.
- **Replace** "Copy the skeleton below into the plan file and fill every placeholder": write `docs/plans/<date>-<slug>.md`, or `docs/plans/<issue>-<slug>.md` for an issue. A plan for a reviewed feature declares `review_scopes` (every affected scope ID), `review_basis` (the governing immutable review IDs, empty when none governs) and `work_kind` (`design`, `implementation`, `research`, `workflow` or `verification`) in YAML frontmatter; a plan handed back with Build now declares `implementation`, because the Build playbook refuses a `design` plan, and `design` is for a target no one builds from, and keeps one authoritative `Status:` line with a `Playbook: plan` line under it, so its page leads with the sections this file's frontmatter names. An architecture or API adoption plan reads `.agents/playbooks/references/architecture.md` in full, keeps its decision ledger, and writes the Page sections it names that apply as its delta under the same titles, starting with `## What other editors do`; the subject file keeps the current state until the build folds the delta in. List the review scope that owns the change first in `review_scopes`, because the first scope is the plan's subject and its page; `Topic:` is only for a subject outside the ledger. An accepted API change adds the affected Vision and worker-skill owners to the plan's adoption rows, and the plan cannot be ready while `plate-plugins`, `plate-ui`, Plate Docs, `plate-next` or another affected worker still teaches the rejected shape. A plan whose change readers can see in the public docs, such as a public API, behavior, kit, component or example, names each affected `content/docs` page and gives it one step that runs `plate-docs` on that page: its example coverage audit, the edits and new or updated registered demos it calls for, the Chinese twin, and the docs checks and preview proof as that step's proof. A feature that must reach registry consumers copies `plate-plugins`'s feature template, `.agents/rules/plate-plugins/references/feature/template.md`. Any other plan has `Status:`, Outcome, Scope, Decisions with their reasons, Steps as `- [ ]` boxes that each name the proof closing them, and Proof. Every plan also has the `Defaults` and `Open questions` sections from `AGENTS.md`'s Plan pages when it has any.
- **Replace** "Run `node skills/poteto-mode/scripts/check-plan.mjs <plan.md>`": check an architecture or API plan against the architecture reference's Ready list, or for another plan, that every step names its proof and no decision-changing question is left. A plan with a Start Gates table is ready only when every row resolves Applies and records its evidence or the reason it does not apply. Completion Gates resolve at Done, when `node .agents/pstack/plan-open.mjs <plan>` passes. Before the plan asks Build now, run each step's cheapest control at base in a detached worktree, such as the half of its proof that must fail at `HEAD` or a delete-and-typecheck spike. Rewrite any step whose control does not behave as the step claims, because a citation proves only that its line exists.
- **Replace** "Write under `/technical-writing` in full, then `/unslop`": write the plan with `pstack:technical-writing` as a reference, then run one `unslop` pass, per `AGENTS.md`'s Writing passes rule. The body is one Diátaxis mode, how-to; appendices hold explanation and reference.
- **In** "Hand back. Post the plan path": the plan names the Build playbook as its execution playbook. Record the challenge delta in the plan. When a panel reviews the plan, because a reviews row names it or the user asked for one, its intent names as an invariant to attack that each phase beats keeping the incumbent plus the earlier phases, so a finding that a phase should not be built is in scope. Then publish the page per `AGENTS.md`'s Plan pages, ask the open questions together with the build question, Build now, Another round or Hold after a panel, or Build now, Panel first or Hold without one, and stop. Build now, or "go", accepts every default and runs Build.

## Architecture decisions

State the ideal target before compatibility or current plans constrain it. Compare at least two materially different targets, which differ in ownership, lifetime, data model, public call shape or runtime strategy; renames and wrapper reshuffles do not count. Run `pstack:architect` for the comparison (reviews: api-plan). The panel on the finished plan attacks the winner, and the plan replays architect once only when that attack improves or replaces it; the pstack block's panel round cap bounds the rounds. The first design pass is always `pstack:architect`'s arena, with independent runners and a cross-judge. A comparison the lead writes alone is not one. Before grafting, prove each premise of the base and its grafts that existing code already does something with `pstack:blast-radius`'s run-it step, because a judge's verified citation proves only that the line exists. Finish that census before the first panel round, and apply no panel fix while it runs. After a panel or verification cut, re-score the surviving synthesis against the incumbent in the comparison table; when the margin is gone, keep the incumbent or rerun the arena. Record the challenge delta in the plan: `unchanged`, `improved` with what was deleted, merged, moved or re-owned, or `replaced` with the rejected target, the new target and the decisive evidence. Every removed hook, adapter, owner or public noun names the behavior it carried, its replacement or proven redundancy, and its regression proof. Adopt in at most three phases, each independently valuable and ending with a keep, revert or quarantine decision. Compatibility and difficulty change phase order, never the target. Without implementation authority, stop after the challenged target and adoption plan. Log a change made after the user's approval as the agent's own call; the pstack block's Review rule sends it back through the panel.
