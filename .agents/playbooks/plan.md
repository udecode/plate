# Plan

The third stop of the v2 loop. The plan is the deliverable, and this playbook implements nothing.

- **Before** "Settle open questions by prototype before you write": choose the target by the Architecture decisions section below when the plan picks an API or architecture target. When the plan changes a public API, that runs `pstack:architect` for the comparison (reviews: api-plan), then the panel on the finished plan, and records the panel's challenge delta. A row that breaks a public API also passes Best API's hard-cut gate and names its callers, docs, examples and proof. A hard cut that neither the owner's request, a Pursue verdict this plan continues nor the vision clears becomes a verdict item when the plan is written, as the Hard cut section of `.agents/playbooks/references/architecture.md` says.
- **Replace** "Copy the skeleton below into the plan file and fill every placeholder": write `docs/plans/<date>-<slug>.md`, or `docs/plans/<issue>-<slug>.md` for an issue. A plan for a reviewed feature declares `review_scopes` (every affected scope ID, each once), `review_basis` (the governing review: a review page's file name or a legacy record id, empty when none governs), `work_kind` (`design`, `implementation`, `research`, `workflow` or `verification`) and `review_commit` (the commit its proof read) in YAML frontmatter, and names its tracked proof files, such as its tests, in `review_inputs`, since the review ledger refuses a git-ignored run-directory file; a plan handed back with Build now declares `implementation`, because the Build playbook refuses a `design` plan, and `design` is for a target no one builds from, and keeps one authoritative `Status:` line with a `Playbook: plan` line under it, so its page leads with the sections this file's frontmatter names. An architecture or API adoption plan reads `.agents/playbooks/references/architecture.md` in full, keeps its decision ledger, and writes the Page sections it names that apply as its delta under the same titles, starting with `## What other editors do`; the subject file keeps the current state until the build folds the delta in. List the review scope that owns the change first in `review_scopes`, because the first scope is the plan's subject and its page; `Topic:` is only for a subject outside the ledger. An accepted API change adds the affected Vision and worker-skill owners to the plan's adoption rows, and the plan cannot be ready while `plate-plugins`, `plate-ui`, Plate Docs, `plate-next` or another affected worker still teaches the rejected shape. A plan whose change readers can see in the public docs, such as a public API, behavior, kit, component or example, names each affected `content/docs` page and gives it one step that runs `plate-docs` on that page: its example coverage audit, the edits and new or updated registered demos it calls for, the Chinese twin, and the docs checks and preview proof as that step's proof. A feature that must reach registry consumers copies `plate-plugins`'s feature template, `.agents/rules/plate-plugins/references/feature/template.md`. Start from a template only where a checker reads its format, such as that one and `.agents/rules/benchmark/templates/benchmark.md`. Any other plan has `Status:`, Outcome, Scope, Decisions with their reasons, Steps as `- [ ]` boxes that each name the proof closing them, and Proof. Every plan also has the `Defaults` and `Open questions` sections from `AGENTS.md`'s Plan pages when it has any. Before writing any step's proof or phase exit, load `verify` through the Skill tool, and `benchmark` for a scale gate; reading their references does not count, because the skills decide what proves a visual, native or timing claim.
- **Replace** "Run `node skills/poteto-mode/scripts/check-plan.mjs <plan.md>`": check an architecture or API plan against the architecture reference's Ready list, or for another plan, that every step names its proof and no decision-changing question is left. A plan with review front matter also passes `node tooling/scripts/review-ledger.mjs check <plan>`, which checks only that plan and refuses, for example, a `review_commit` shorter than 40 characters or a `review_inputs` path a fresh checkout lacks. Fix what it names before the plan goes on, because `plan-page.mjs --check` does not read those keys. A plan with a Start Gates table is ready only when every row resolves Applies and records its evidence or the reason it does not apply. A Start gate on another plan's work records that work's own check run at `HEAD`, never that plan's `Status:` line. Completion Gates resolve at Done, when no row is pending. Load `verify` through the Skill tool before running base controls. Before the plan goes on to its build, run each step's cheapest control at base in a detached worktree, such as the half of its proof that must fail at `HEAD` or a delete-and-typecheck spike. Rewrite any step whose control does not behave as the step claims, because a citation proves only that its line exists.
- **Replace** "Write under `/technical-writing` in full, then `/unslop`": write the plan with `pstack:technical-writing` as a reference, then run one `unslop` pass, per `AGENTS.md`'s Writing passes rule. The body is one Diátaxis mode, how-to; appendices hold explanation and reference.
- **In** "Hand back. Post the plan path": the plan names the Build playbook as its execution playbook. When a panel reviewed the plan, record the challenge delta in the plan. When a panel reviews the plan, because a reviews row names it, a pstack step calls for one or the user asked for one, its intent names as an invariant to attack that each phase beats keeping the incumbent plus the earlier phases, so a finding that a phase should not be built is in scope. Then publish the page per `AGENTS.md`'s Plan pages. A request for only a plan, such as "plan" or `plan <goal>`, ends there. Any other route, such as a Pursue verdict, runs Build, as the Autopilot rule says, unless an open question stops the run or the user said "stop at plan". After a stop, "go" accepts every default and runs Build. The page lists every claim made to the user in conversation that the plan reverses, such as which packages or shared code it changes.

## Architecture decisions

State the ideal target before compatibility or current plans constrain it. Compare at least two materially different targets, which differ in ownership, lifetime, data model, public call shape or runtime strategy; renames and wrapper reshuffles do not count. A plan that changes a public API runs `pstack:architect` for the comparison (reviews: api-plan), and its first design pass is always architect's arena, with independent runners and a cross-judge; another architecture plan runs `pstack:architect` only where pstack's own trigger calls for it, such as code that crosses a function boundary, and otherwise compares its targets in the lead's own table, records its must-answer questions in the plan and runs their probes before it picks the target. When a panel reviews the finished plan, it attacks the winner, and the plan replays architect once only when that attack improves or replaces it. When architect runs, no build brief goes out until its judge has picked the base and grafts, because a brief written from one runner's sketch builds a design the judge may reject. Instructions about the arena, its runners and judge apply only when architect runs, and those about the panel, the replay and the challenge delta only when a panel reviews the plan. The comparison, grounding, removal, redundancy and phasing rules apply to every architecture plan. The runner task and the judge's rubric state the outcome the design must reach, never the mechanism, and the comparison includes one candidate or stated control that adds no new artifact. Before grafting, list each case a losing candidate handles that the base drops, such as a dialog, a shadow root or a hidden region, and make each one a graft or a named limit of the plan before the panel. Prove each premise of the base and its grafts that existing code already does something with `pstack:blast-radius`'s run-it step, because a judge's verified citation proves only that the line exists. Every open question or "not verified" flag that the grounding, a runner or the judge raises about a path the target removes goes into the arena prompt as a must-answer item and runs as a probe before the pick, never as a build step. Finish that census before the first panel round, and apply no panel fix while it runs. After a panel or verification cut, re-score the surviving synthesis against the incumbent in the comparison table; when the margin is gone, keep the incumbent or rerun the arena. Record the challenge delta in the plan: `unchanged`, `improved` with what was deleted, merged, moved or re-owned, or `replaced` with the rejected target, the new target and the decisive evidence. Every removed hook, adapter, owner or public noun names the behavior it carried, its replacement or proven redundancy, and its regression proof. Redundancy is proven by running the removed path and its replacement on the same input, read-only and authored policy included; a typecheck proves only that callers compile. Adopt in at most three phases, each independently valuable and ending with a keep, revert or quarantine decision. Phase 1 is the thinnest path a person can drive, such as a flagged demo route or an unexported kit in a spec fixture, and it builds only what that path runs. The plan says that each step lands as its own commit, so the build lands each step once its own proof passes, as `.agents/pstack/rules/long-runs.md` says, and the decision log's `built: step <n>` and `step <n> landed as <sha>` rows take the step's number, so steps count across the whole plan and a later phase never starts again at 1. So each step builds one thing that its proof covers, never a list of features beside the phase's proof. A step that changes a path users can already reach, such as a shared Plite or Plate path, proves that change in its own proof. The phase's acceptance proof is its own step, before the step that lets a user reach the feature. A fix that proof needs lands with it when the cause is in the feature's own code that no user can reach yet, whichever phase built it, and when an earlier step's commit landed that code, the step lands as a `fix` commit whose `Introduced-by:` line names that commit; a cause in a path users can already reach, such as a shared Plite or Plate path or code an earlier phase exposed, becomes its own step, with its own proof, that lands first. That step is built in a worktree of its own cut from `origin/next`, because `land.mjs` commits the whole worktree, and the step that found it logs its `built:` row and lands only after that fix has landed. That worktree carries only the fix's code. The fix step's box, its tick and its decision rows go in the plan and its log in the step worktree, which already holds the last landed row, and reach the branch with the next step's commit, and its close stop runs there. A step added midway, such as that fix, takes the number of the step it goes before with a letter, such as `step 8a`, so the approved numbers stay put. It is a step this plan provides for, so it owes no deviation row and never goes back to this playbook as a slice that cannot follow the plan, and its diff gets the reviews any step gets. A plan that says each phase lands as its own commit keeps that for every phase, its later ones included. It still lands a shared-path fix, or a fix to code an earlier phase landed, first, from a worktree of its own, as its own commit, so the phase's commit never becomes a `fix`, and that step's box and rows take the number of the step it goes before with a letter, as above, while the phase's own rows keep the phase's number. The step that lets a user reach the phase's feature, such as its export or a flag on by default, comes after every other step of the phase but its `plate-docs` steps, and its proof runs the acceptance specs through that export or flag. Those come after it because a docs page needs the export or flag it teaches. While a critical finding waits for a later phase, as the Panel review rule allows, the phase keeps its flag off and its export out, and that step moves to the phase that claims the finding, because that rule holds such a landing until the finding is applied. A revert or quarantine decision reverts the phase's step commits by their shas in one land.mjs commit, never through `review.mjs --revert`, which also reverts the plan and the log that record the decision. Each phase's exit states its claim as the cohorts, the number of peers, the modes and the browser engines it proves. It names each case outside that claim as a limit of the phase, with the later phase that claims it. Each phase also gets its appetite as a Defaults row, as the Run check rule in `.agents/pstack/rules/long-runs.md` says. A critical finding on a named limit waits for the phase that claims it only when the Panel review rule's four conditions for that wait hold, and follows that rule's apply rule in the phase that finds it otherwise. A finding that the stored shape cannot hold a later phase's case never waits and pivots the run, as that rule says. A checker, a test rig, a scale gate or a formal model is a step of the phase whose claim it proves, never a phase of its own, unless the owner's typed ask names it as the deliverable. Benchmark's pre-acceptance probe still runs before the target is picked, on the cohort the stored shape must hold, because a stored shape is costly to change once phase 1 has built on it. For the same reason, a must-answer probe runs each later phase's hardest case against the stored shape alone, with no merge or UI code, before the target is picked. Every other budget joins the phase that claims its cohort, so the feature template's Scale proof box resolves with that probe's receipt alone. Only the next phase to build has steps and proof gates. Each later phase is one paragraph that gives its outcome, the claim it adds and its known risks. It gets its steps when the phase before it lands, as a revision of the same plan, and the Review rule's re-review reads that phase's delta alone. The tables, gates and checklist that a template brings, such as the feature template's Feature Manifest, Work Checklist and Completion Gates, still cover the whole feature. Each of their rows and boxes names the phase that closes it, and one that a later phase closes stays pending without blocking an earlier phase's landing. Start Gates still resolve for the whole feature before the plan is ready. A step this playbook owes for a change, such as a docs page's `plate-docs` step, is written with the steps of the phase that makes that change, and that phase's paragraph names it until then. Work that the phase's drivable outcome does not need is not a step. It goes to a suggested task or to Open work, as chips.md's Offer says. When a confirmed regression opens an audit of its class, the audit inventories the whole class, the phases take only the members the census proved, and the rest go to Open work or a sibling plan; a panel's "you missed member X" is answered by narrowing the claim, not by adding scope. Compatibility and difficulty change phase order, never the target. Log a change made after the user's approval, or to the arena's picked base or grafts after its verdict, as the agent's own call in a deviation row, and name it in the panel brief as a decision to attack; the pstack block's Review rule sends it back through the panel.
