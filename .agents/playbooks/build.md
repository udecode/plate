# Build

The last stop of the v2 loop. "go" runs every slice of the accepted plan without pausing between slices. This playbook applies only to "go" on an accepted plan or to a hard cut; an ad hoc cleanup follows `refactoring.md` alone. The plan already settled the design, so the build does not reopen it.

- **Replace** "`how` over the affected subsystem": reread the plan and the current source, repair stale claims first, and record the execution authority and the packet in the plan. Reproduce each planned guard's or refusal's state through the public entry before building it, because schema validation or an earlier owner can already rule it out. Log an unreachable one as a deviation instead of building it. Copy every Before and After gate below that the plan triggers into the plan's Completion Gates table with a pending cell, which `plan-open` refuses while it stays pending, and replace each cell with the gate's artifact or `skip: <reason>`; a gate kept only in a scratch todo leaves no trace when it is skipped. A plan whose `Status:` is Done, whose `work_kind` is `design`, or that another plan replaces does not build: stop, name the plan that owns the work now, and ask once which one "go" meant.
- **Replace** "`architect` for parallel design exploration": skip, because the plan's target already passed the Plan playbook's Architecture decisions. A slice that cannot follow the plan stops the build and goes back to the Plan playbook. Reversing an approved gate's verdict, such as keeping a phase the plan says to revert, is such a slice. Apply the approved verdict or stop, and keep any continuation separable as a saved patch until the owner answers. Doing less than a slice approved continues with a deviation row. A substituted mechanism, a changed or dropped approved proof, or a reverted step stops that slice for the owner, with the continuation kept as a saved patch.
- **Replace** "Delegate code-writing to a subagent": implement the plan's slices yourself, in order, per `AGENTS.md`'s The lead writes the code rule. Before writing or running a step, load every skill the step or its gate names, such as `benchmark` before a scale step's harness and `verify` before the first proof gate. Run focused proof first, keep edits surgical, and port every shared-primitive improvement to all its consumers and verify each. Subagents only research and review, and no slice commits.
- **After** "Verify on the matching surface": hard-cut the rejected surfaces per the Hard cut section of `.agents/playbooks/references/architecture.md` and sweep callers, exports, tests, docs, examples, browser proof and benchmarks. When a reusable public API changed, run `best-api repair`; the plan stays open while `plate-plugins`, `plate-ui`, `plate-docs`, `plate-next` or another worker still teaches the rejected shape. Rerun every scale-sensitive contract on the final production path through `benchmark`, loaded before the first run.
- **Before** "Delegate code-writing to a subagent": when the plan changes a public API, run `pstack:blast-radius` on the change first, so callers outside the plan's sweep are known before code moves.
- **After** "Verify on the matching surface": run `plate-docs` on every public docs page the plan names or the change affects, including its example coverage audit, so each important reader task has a home in an example, reference section or linked guide before close. A gap that stays open is recorded in the plan with its owner.
- **After** "Verify on the matching surface": a slice that touches code shared across packages or plugins runs `pstack:thermo-nuclear-code-quality-review` on its diff before the next slice. The split law in `.agents/playbooks/refactoring.md` overrides its size-based split advice, and its findings get fixed in the slice that caused them.
- **Replace** "Rebase into small, ordered commits": leave commits to the owner, per `AGENTS.md`'s Delivery rule.
- **Replace** "Run **Opening a PR**": open a PR only when the user asks, per the Delivery rule.
- A plan whose slices preserve behavior runs each slice under `refactoring.md`'s packet law, with the plan's slices as its steps; this playbook's close still applies.
- A published package edit requires its applicable changeset per `changeset`.
- At the close, a feature-delivery plan first passes `node tooling/scripts/check-plate-feature.mjs <plan>`. Then record the evidence and the plan's status, then close it: Completing a design does not complete adoption. At a material checkpoint or closure, finish the plan's `## Close`, evidence, status, file and line references and writing passes, then, when the reviews list names the work or the user asked for one, its panel on the diff, then any decision-trail review, then, for a plan with review scopes, run `draft <plan-path>`, complete its outcome, summary, proof claims and limits from the actual source and proof inputs, and `record <draft-path>` as the last ledger step. A refused record follows `best-api-review`'s Never leave a record pending. A matching hash establishes identity, not that a test ran; a plan with no governing review records an execution with no basis and unknown proof. The plan stays editable after the record. Never close a gap by editing or deleting an immutable record; a later change records a new execution that names the earlier one in `previous`. `status` and `lookup` derive progress without a second status. `research` reuses the same history and keep review, adoption, proof and source freshness independent. `docs/research/schema.md` owns the exact contract; a completed design plan does not establish adoption. Name the run's commits in the plan, fold its delta into its subject file before its `Status:` says executed and render it with `--folded`, or write a one-off plan's own `Public API` and `Main changes`, per the `plan-page` skill, and republish its page, then run `node tooling/scripts/review-ledger.mjs next` and name the next item in the report, and end it with the page link. Stop there.
