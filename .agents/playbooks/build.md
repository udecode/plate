# Build

The last stop of the v2 loop. "go" runs every slice of the accepted plan without pausing between slices. This playbook applies to a plan that goes on to its build, to "go" on an accepted plan and to a hard cut; an ad hoc cleanup follows `refactoring.md` alone. The plan already settled the design, so the build does not reopen it. The todo list names this playbook on its first line, so a resume after compaction reloads it.

- **Replace** "`how` over the affected subsystem": reread the plan and the current source, repair stale claims first, and record the execution authority and the packet in the plan. Reproduce each planned guard's or refusal's state through the public entry before building it, because schema validation or an earlier owner can already rule it out. Log an unreachable one as a deviation instead of building it. A planned check that already fails at the build base, run in a detached worktree, lands with a shrink-only baseline that names each current violation and its owner, per `AGENTS.md`'s Corrections rule, and is never dropped. A baseline captured mid-build can hold the build's own regressions, so a "no new finding" proof against it counts as partial. Copy every Before and After gate below that the plan triggers into the plan's Completion Gates table with a pending cell, and replace each cell with the gate's artifact or `skip: <reason>`; a gate kept only in a scratch todo leaves no trace when it is skipped. A plan whose `Status:` is Done, whose `work_kind` is `design`, or that another plan replaces does not build: name the plan that owns the work now and build that one, recorded as a Defaults row.
- **Replace** "`architect` for parallel design exploration": skip, because the plan's target already passed the Plan playbook's Architecture decisions. A slice that cannot follow the plan goes back to the Plan playbook, which revises the plan and builds on in the same run. Reversing an approved gate's verdict, such as keeping a phase the plan says to revert, is such a slice; the lead logs it as a deviation row, takes the better-evidenced verdict and keeps the other as a saved patch. Doing less than a slice approved continues with a deviation row only when the rest is unreachable or disproven; the time or effort left never shrinks a slice and is never a reason to ask. A changed or dropped approved proof becomes a `look` Defaults row with a saved patch and the word that reverses it, per `AGENTS.md`'s Autopilot rule. A substituted mechanism or a reverted step is a deviation row. A revert restores the text from before the decision it reverts, and a quarantine restores that text only for the parts it unwires. A replacement, a trial's winning arm included, goes back to the Plan playbook as a plan revision, so the Review rule's re-review applies to it, and replacement text whose benefit depends on what agents do also gets a trial of that exact text before it lands.
- **In** "Delegate code-writing to a subagent": hand the plan's slices to delegates in order. Before briefing or running a step, load every skill the step or its gate names, such as `benchmark` before a scale step's harness and `verify` before the first proof gate. A load from before a compaction or for an earlier plan does not count: the gate's cell names this build's own invocation, and a stand-in such as a `git grep` is logged `partial`. A step box whose step names a skill, such as "Through `research` maintain", closes only with this build's invocation of that skill, made before the step's first edit; a step that never ran closes with `skip: <reason>`. Each brief asks for focused proof first and surgical edits, and the lead ports every shared-primitive improvement to all its consumers and verifies each.
- **After** "Verify on the matching surface": hard-cut the rejected surfaces per the Hard cut section of `.agents/playbooks/references/architecture.md` and sweep callers, exports, tests, docs, examples, browser proof and benchmarks. When a reusable public API changed, run `best-api repair`; the plan stays open while `plate-plugins`, `plate-ui`, `plate-docs`, `plate-next` or another worker still teaches the rejected shape. Rerun every scale-sensitive contract on the final production path through `benchmark`, loaded before the first run. That rerun is part of the close's repeated acceptance proof, so it runs after the last panel fix, on the bytes that proof runs on. A measured run that rewrites a tracked result runs after the lint fix and before that proof, so the proof and `pnpm check` read the rewritten result.
- **Before** "Delegate code-writing to a subagent": when the plan changes a public API, run `pstack:blast-radius` on the change first, so callers outside the plan's sweep are known before code moves.
- **After** "Verify on the matching surface": run `plate-docs` on every public docs page the plan names or the change affects, including its example coverage audit, so each important reader task has a home in an example, reference section or linked guide before close. A gap that stays open is recorded in the plan with its owner.
- **After** "Verify on the matching surface": a build that changes what a browser shows runs `verify`'s Hand drive after the last edit to the pages it changed, `pnpm lint:task` on the task's files included, because a later write reopens the cells it touches, and the plan's Completion Gates table gets a Hand drive row whose evidence is the log of `node tooling/scripts/hand-drive.mjs check <the plan's files>`. A drift the drive finds is a finding of this build.
- **After** "Verify on the matching surface": when `node tooling/scripts/playtest.mjs scope <the plan's files>` names a scenario catalog, or the build adds an editor feature that has none, run the playtest's spec runner on each such feature, as its reference's Build close section says, after the last slice's review fixes and before the close's writing passes and panel, writing the missing catalog first. The playtest's agent drive is not part of a build's close. Every product, spec or harness failure the runner reports in the feature's specs is a finding of this build, a pre-existing one included, so the review bullet's deferral of pre-existing code does not apply to it; the playtest reference says which findings go to session cards instead. The plan's Completion Gates table gets a Playtest row whose evidence is the runner's last `specs-a<N>.md`.
- **After** "Verify on the matching surface": before any expensive acceptance run, such as a multi-engine browser matrix or a benchmark packet, run the `pnpm check <step>` steps the slice's edits reach, such as typechecks, the entrypoint graph and the audits. Each can still force a code change, and a code change reopens that run.
- **After** "Verify on the matching surface": every slice that touches code shared across packages or plugins, the last one included, runs `pstack:thermos` on its diff before the next slice, or before the close's writing passes and panel. Its two reviewers read the same diff: `thermo-nuclear-review` for bugs, breakage and security, and `thermo-nuclear-code-quality-review` for code shape. The brief names the plan, so a breakage the plan approves, such as a hard cut, counts as intended. The brief also tells `thermo-nuclear-review` to skip its PR-discussion step, because a slice is not a PR. A build skips this review when, at its first slice, a reviews row such as `api-build` or `push`, or the owner's request, already owes a panel on its diff, because every panel seat applies both lenses. A code-quality finding that panel raises on a defect the build introduced is fixed in the build, whatever its severity. When that panel stops being owed, such as after a revision that drops the plan's public API change, this review runs on the build's diff so far before the next slice. Its reviewers run as fresh-context subagents, never inline on the lead's own diff. The split law in `.agents/playbooks/refactoring.md` overrides its size-based split advice. A finding on a defect the slice introduced, a presumptive blocker included, gets fixed in that slice and is never handed to a spawned task; a finding on deferred or pre-existing code goes to Open work with its `owner:`.
- Before a panel reviews the diff, run `pnpm exec oxlint --type-aware --format=default` on the task's lintable files without fixing, and compare its file count with the paths passed, among the cheap proofs, so a typed rule cannot force an edit after the panel has reviewed the diff. `pnpm lint:fix` stays the last check that edits code.
- A panel fix lands its cheap reproduction as a test in the task's diff in the same round, so the next round reviews it.
- A panel fix that replaces a mechanism's approach is the one replacement `AGENTS.md`'s Panel review rule allows. It revises the plan's step and Defaults in the same plan file, which stays the current iteration and keeps the approved wording visible. `verdict` runs first when the mechanism is a Plate or Plite API or architecture, and the lead revises the plan from its verdict instead of continuing into the Plan playbook. When the verdict rejects the replacement, the lead does not build it. It reverts the defective code to its state before this plan iteration changed it and narrows the claim with a report, and a claim about a wrong record value goes back to planning. Neither a plan panel nor `architect` runs, even for a fix that crosses a function boundary, which the Panel review rule would otherwise send to `architect`. The next diff round reads the revision and its code when the round earned one. This is the panel-fix exception to the `architect` Replace bullet's re-review. When that rule takes the mechanism out of the loop, the revert or removal it asks for restores or deletes code instead of adding a workaround, so it runs without `verdict`. When the goal still needs the mechanism, the new plan iteration that rebuilds it runs `verdict` first for every mechanism, because that exit is the growing workaround chain the Bug fix playbook's Pokayoke names, and its plan gets its own panel. A removal that a later critical finding calls incomplete follows the removal rule in `AGENTS.md`'s Panel review rule, its caller count and its exits included.
- A `/pstack:correct` change made during a build is its own change with its own review. A feature round's warning on it, or on pre-existing code outside the plan's steps such as a neighbouring lint rule, is deferred with its `owner:`.
- **Replace** "Rebase into small, ordered commits": land the build through `node .agents/pstack/land.mjs`, which squashes it into one commit, per `AGENTS.md`'s Delivery rule. A plan that says each of its phases lands as its own commit lands each phase this way, all in one session, as `.agents/pstack/rules/long-runs.md` says, and only the last phase's landing runs the close below.
- **Replace** "Run **Opening a PR**": when the reviews list names the work or the user asked for one, run its panel on the diff before landing. `land.mjs` pushes the commit or opens its PR, as the clone's `pstack.delivery` setting says.
- A plan whose slices preserve behavior runs each slice under `refactoring.md`'s packet law, with the plan's slices as its steps; this playbook's close still applies.
- A published package edit requires its applicable changeset per `changeset`.
- At the close, a feature-delivery plan first passes `node tooling/scripts/check-plate-feature.mjs <plan>`. Then record the evidence and the plan's status, then close it: Completing a design does not complete adoption. At a material checkpoint or closure, finish the plan's `## Close`, evidence, status, file and line references and writing passes, then, when the reviews list names the work or the user asked for one, its panel on the diff. A plan with review scopes keeps `review_scopes`, `review_basis`, `work_kind` and `review_commit` in its front matter and names its proof files in `review_inputs`; its landed `Status:` with `work_kind: implementation` or `workflow` adopts the Pursue its `review_basis` names, so set a landed `Status:` only when the Close's proof supports it, then run `node tooling/scripts/review-ledger.mjs check <plan>`, which checks only that plan and refuses a landed one whose Close does not name each `review_inputs` path, and fix what it names in the same run. A plan that `check` refuses follows the Verdict playbook's Never leave a verdict unwritten. A plan with no governing review adopts nothing. A gap found after close sets the plan's `Status:` back to an open word or opens a new plan on the same `review_basis`; it never edits a legacy record. `status` and `lookup` derive progress without a second status. `docs/research/schema.md` owns the front-matter keys and keeps review, adoption, proof and source freshness independent; a completed design plan does not establish adoption. Name the run's commits in the plan, fold its delta into its subject file before its `Status:` says executed and render it with `--folded`, or write a one-off plan's own `Public API` and `Main changes`, per the `plan-page` skill, and republish its page, then check the record as the Verdict playbook's last deep-path step says, leaving out that step's chips sweep unless the plan's front matter names a `review_basis`. Such a build then runs that sweep and ends with the page link, the sweep's report and its commits. Any other build runs `.agents/pstack/rules/chips.md`'s Close, which cards the run's own Ready offers, and ends with the page link, that Close's line and its commits. Stop there.
