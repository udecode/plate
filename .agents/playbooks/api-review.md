# API review

The first two stops of the v2 loop pick the next ledger item and judge it with the `best-api` lens. `best-api-review` owns the verdicts; this playbook holds the method, records the verdict and says where to stop. [The record contract](../../docs/research/schema.md#review-history) owns the ledger's fields and helper commands.

- **Before** "Route through the **how** skill": pick the item. For "next", or `best-api-review` with no target, run `node tooling/scripts/review-ledger.mjs next` and `node tooling/scripts/review-ledger.mjs status`. Answer on the unit's page, per `AGENTS.md`'s Plan pages: write `docs/plans/<date>-<scope>-review.md` with the scope first in `review_scopes`, `Status: proposed: waiting on review` and `Playbook: api-review`. Its lead paragraph names the unit and why it is open, Evidence holds the prior-work summary and the release counts, and Open questions recommends one move for the unit's state, with another scope and hold as the other options: review for an unreviewed scope or a stale verdict, plan for a Pursue verdict with no bound adoption. "go" takes the recommendation. The pick stays the owner's. The page asks it under Open questions even though it recommends one move, and for this pick this playbook overrides Plan pages' rule that a call with a safe default becomes a Defaults row. When the scope has no subject file, create `docs/plans/topics/<scope>.md` with its title, a lead that states its ledger question and what has landed and been proven for it, and its current owners under `## Main changes`. Give it `## What other editors do` from its newest review or a `research` pass, because the page refuses to render a subject with a ledger hub and no editor comparison. Publish the page, reply with its link, then stop. An unreviewed scope needs a review. A `fork` scope has two current reviews and needs a review that reconciles both. A `pursue-unbound` scope has a landed plan naming its Pursue with no execution recorded, so record that execution through `draft <plan.md>` and `record`, and plan what is still missing. A `pursue-not-adopted` scope has no completed execution standing for its Pursue and needs a plan. `next` skips deferred scopes, which wait on the evidence their verdict names; `status` still counts them. To take a different item, name its scope. When the reviewed scope is not the one `next` returned, say so on the page and in the record's `trigger`, and name any open scope it `dependsOn`.
- **Before** "Route through the **how** skill", for a named scope or proposal: reconcile its history. Before recommending a ledger item or starting an audit, run `node tooling/scripts/review-ledger.mjs lookup <scope-or-feature>` for it and read the sources it links; `unreviewed` does not mean untouched. Read a lookup's `open`, `freshness`, `executions`, `plans`, `documents` and `candidates` even when `head` is null, and use `lookup <scope> --detail` or `show <scope>` when omitted records can change the recommendation. Search `docs/plans`, `docs/research/decisions` and retained review records for the user job, older package and API names and related consumers, because a broad audit or regression plan may hold completed work without its own review record. Say "no prior work found" only after the lookup and the plan search, with the search's limits stated; missing bindings and stale evidence stay proof limits.
- **Replace** "Produce the `how`-shaped output": for a named scope, run `best-api-review` on it. Inspect the owning implementation, its public types and each materially different consumer, including copied UI and kits that own the policy, because a package-only trace cannot settle ownership. Judge the call shape with the `best-api` lens and ownership with `.agents/playbooks/references/architecture.md`, reading their decision sections without starting their workflows, and compare the alternatives as `docs/vision/common.md`'s Redesign from First Principles says. When a target changes what an owner accepts, the ingress census records the object each path hands that owner, raw or rebuilt. Write the verdict into the scope's iteration, the file "next" wrote or a new `docs/plans/<date>-<scope>-<slug>.md`, before any panel, so the panel's rows land beside it. Its lead paragraph gives the verdict and the strongest reason, `## Public API` pairs the current and proposed normal call sites, Defaults hold the picks among the lanes, Evidence holds the lanes considered and the proof limits, and, for a Stop or Defer verdict, Open questions offers again, interrogate or hold. `Status:` becomes `planning` for Pursue, `closed: Stop verdict` for Stop, or `blocked: waiting on <evidence>` for Defer. Give the subject file real current call sites under `## Public API` when it lacks them. Record every material review, Stop and Defer included, before the verdict reply, through the record contract's `draft` and `record` steps. A receipt carried from an earlier record stays current only while every input its run exercised is unchanged; otherwise label it historical and rewrite the claims and limits from the current proof inventory. Run `record <draft-path>` last, after the evidence census, the file and line references, the writing passes and any decision-trail review, then run `lookup` for the task's scopes again. When `coverage` lists source no scope owns, add it to the owning scope's `members`; membership never certifies review. Update the decision page's text when the verdict changes its conclusion. A Stop or Defer verdict then publishes the page, replies with its link and stops. A Pursue verdict continues in the same run into the Plan playbook on the same file, because the owner decides whether to pursue at the plan's Build now or Hold. A refused or blocked record follows that skill's Never leave a record pending.
- A ledger triage audit gives every open unit a fresh verdict and writes no plan. It creates the subject file of each unit that has none, as the first stop does, so the unit's page renders; until then the topic index lists the unit as no page yet.
- **Replace** "Apply the **unslop** skill to the reply": write the reply clean as drafted, with no separate pass, per `AGENTS.md`'s Writing passes rule. The review record, the decision page and the page's plan get one `unslop` pass.
- After a Stop or Defer verdict, the answer to the page's question, or a typed word, picks the next step. "again" runs `best-api-review` once more on the same scope and challenges the strongest alternative afresh; its record reaffirms or supersedes the last one. "interrogate" or "panel" runs the panel on the verdict's target with the configured seats. "plan" opens the Plan playbook on the verdict's file anyway. "next" starts over at the first stop.
