# API review

The first two stops of the v2 loop pick the next ledger item and judge it with the `best-api` lens. This playbook owns the method and the verdicts below, writes the verdict into the review page's front matter and says where to stop. [The review ledger](../../docs/research/schema.md#review-history) owns the scope files, the front-matter keys and the helper commands.

## Verdicts

Decide whether further work is justified. Agreement is not the default, and "keep the current design; this change adds no material value" is a successful review. Use `audit <scope>` when every candidate in a bounded set needs a verdict.

| Verdict | Meaning | End of this review |
| --- | --- | --- |
| **Stop** | No material benefit, unjustified machinery, a violated hard constraint, or it loses to the current design. | State why and keep the current design. No plan, task or consolation backlog. |
| **Pursue** | Evidence supports a material problem and a better direction, which may replace the proposal. | Name the single next owner, and continue into the Plan playbook when it is that owner. |
| **Defer** | A named evidence gap or external prerequisite can change the verdict. | State what would settle it and recommend only that investigation. |

Missing evidence alone is not Stop, and an API that does not exist yet is design work, not an evidence gap. Stop only after the stronger change lanes also fail. Be blunt about the proposal, not the person: lead with the verdict and its strongest reason, without invented minor improvements or a menu of equal choices.

A previous verdict is evidence, not law. Changed requirements, contradictory evidence, source changes or a materially better argument reopen it at the question level: a paint defect does not reopen settled topology or resize decisions. A Pursue whose target already landed is written as a Stop, with the landed work as evidence.

A Stop cited from another workflow, such as a failed-fix escalation, reads `best-api-review: stop: <reason>`.

## One item per session

Each ledger item runs in its own session. Once the lead knows the item, its first act is to title the session with the item's scope as the Session title rule's `<name>`, such as `👥 ui (2/7)`, before poteto-mode's first step. When this session already worked on another ledger item, the lead does not start the new one here, so each item keeps its page, log and title in one session. It starts a new session in this checkout with the prompt `best-api-review <scope>`, through the runtime's tool that starts a session, such as Claude Code desktop's `start_session`. Without that tool, it offers the same prompt as a one-click suggestion, such as `spawn_task`, whose brief names the scope and the ledger's reason. Such a suggestion opens its session in a worktree, so the brief tells that session to move to this checkout before its first step, such as with Claude Code desktop's `change_directory`, and to work only there. A worktree lacks this checkout's uncommitted rules, and `next` skips only the plans it finds in the checkout it runs from. A runtime with neither tool puts the prompt in its reply, for the owner to start a new session in this checkout. The handing-off session takes no further step on the new item.

**Never leave a verdict unwritten.** A review page carries its `verdict` front matter before the reply. When `node tooling/scripts/review-ledger.mjs check` refuses the page, its message names the fix; fix the front matter in the same run. A new head or fork needs judgment before it is reconciled. Name a page still unfixed in the reply and in the plan's decision log, so a later session finishes it.

## Steps

- **Before** "Route through the **how** skill": pick the item. For "next", or `best-api-review` with no target, run `node tooling/scripts/review-ledger.mjs next` and `node tooling/scripts/review-ledger.mjs status`. Answer on the unit's page, per `AGENTS.md`'s Plan pages: write `docs/plans/<date>-<scope>-review.md` with the scope first in `review_scopes`, `Status: proposed: waiting on review` and `Playbook: api-review`. Its lead paragraph names the unit and why it is open, Evidence holds the prior-work summary and the release counts, and Defaults record one move for the unit's state, with another scope and hold as the alternatives: review for an unreviewed scope or a stale verdict, plan for a Pursue verdict that no landed plan adopts. A verdict stale only because doctrine files moved, with no change to the scope's members, may be recommended for plan once the lead reads the law diff, says on the page why the verdict's questions still stand, and logs that call when it makes it. The lead takes that move without waiting. When the scope has no subject file, create `docs/plans/topics/<scope>.md` with its title, a lead that states its ledger question and what has landed and been proven for it, and its current owners under `## Main changes`. Give it `## What other editors do` from its newest review or a `research` pass, because the page refuses to render a subject with a ledger hub and no editor comparison. Publish the page, then continue in the same run with that move. A review runs this playbook's next steps on the scope, and a plan runs the Plan playbook on the same file. An unreviewed scope needs a review. A `fork` scope has two current reviews and needs a review that reconciles both. A `pursue-not-adopted` scope has no landed implementation or workflow plan adopting its Pursue and needs a plan. `next` skips deferred scopes, which wait on the evidence their verdict names; `status` still counts them. It also skips every scope an open plan is working through and lists each under `inFlight` with its plans. Such a scope has a plan that names it in `review_scopes`, carries an active, held or planning `Status:`, and changed in the working tree or within `IN_FLIGHT_DAYS` in `tooling/scripts/review-ledger.mjs`. Never recommend an `inFlight` scope; when its plan is this session's own, continue that plan instead. `next` also lists the returned scope's uncommitted member files under `uncommitted`. Uncommitted work there with no plan behind it belongs to another session, so name it on the page and pick the next open scope from `status`'s queue instead. To take a different item, name its scope. When the reviewed scope is not the one `next` returned, say so in the page's lead paragraph, and name any open scope it `dependsOn`.
- **Before** "Route through the **how** skill", for a named scope or proposal: reconcile its history. Before recommending a ledger item or starting an audit, run `node tooling/scripts/review-ledger.mjs lookup <scope-or-feature>` for it and read the sources it links; `unreviewed` does not mean untouched. Read a lookup's `open`, `freshness`, `executions`, `plans`, `documents` and `candidates` even when `head` is null, and use `lookup <scope> --detail` or `show <scope>` when omitted records can change the recommendation. Search `docs/plans`, `docs/research/decisions` and retained review records for the user job, older package and API names and related consumers, because a broad audit or regression plan may hold completed work without its own review record. Say "no prior work found" only after the lookup and the plan search, with the search's limits stated; missing bindings and stale evidence stay proof limits.
- **Replace** "Produce the `how`-shaped output": for a named scope, give it one verdict from Verdicts above. Inspect the owning implementation, its public types and each materially different consumer, including copied UI and kits that own the policy, because a package-only trace cannot settle ownership. Judge the call shape with the `best-api` lens and ownership with `.agents/playbooks/references/architecture.md`, reading their decision sections without starting their workflows, and compare the alternatives as `docs/vision/common.md`'s Redesign from First Principles says. Before a lane deletes code that its owners call a workaround, run `pstack:why` on it, and record each cut's predicted benefit in Evidence so the plan's Close marks it held or falsified. When a target changes what an owner accepts, the ingress census records the object each path hands that owner, raw or rebuilt. Write the verdict into the scope's iteration, the file "next" wrote or a new `docs/plans/<date>-<scope>-<slug>.md`, before any panel, so the panel's rows land beside it. Its lead paragraph gives the verdict and the strongest reason, `## Public API` pairs the current and proposed normal call sites, or the ownership flow when no public call changes, and Defaults hold the picks among the lanes. Evidence opens with a `### Requirements` list of the scope's current jobs and hard laws, explicit user constraints included, and Evidence holds a `### Lanes` list of at least two lanes considered, the strongest deletion or merger among them, and the proof limits. For a Stop or Defer verdict, Defaults record hold, with again and interrogate as the words that change it. `Status:` becomes `planning` for Pursue, `closed: Stop verdict` for Stop, or `blocked: waiting on <evidence>` for Defer. Give the subject file real current call sites under `## Public API` when it lacks them. Before the verdict reply, every material review, Stop and Defer included, sets its page's front matter: `review_scopes` with the scope first, `verdict`, `review_basis` naming the head `lookup` reported and every other head, or `[]` for a first review, `review_commit` naming the commit the review read, and `review_inputs` and `review_upstreams` for anything else it read. Evidence has a `Model:` line naming the model that ran the review, or `Model: unknown`, and never reconstructs hidden instructions or invents a historical model name; it names each earlier review and landed plan of the scope that this review retains, reopens or supersedes, and why, and each external checkout and the commit it read. A changed verdict reopens or supersedes its previous review and never retains it. A receipt carried from an earlier review stays current only while every input its run exercised is unchanged; otherwise label it historical and rewrite the claims and limits from the current proof inventory. Run `node tooling/scripts/review-ledger.mjs check` last, after the evidence census, the file and line references, the writing passes and any decision-trail review, fix every error it names for the page in the same run, then run `lookup` for the task's scopes again. When `coverage` lists source no scope owns, add it to the owning scope's `members`; membership never certifies review. Update the decision page's text when the verdict changes its conclusion. A Stop or Defer verdict then publishes the page, replies with its link and stops. A Pursue verdict publishes the page with its verdict first, then continues in the same run into the Plan playbook on the same file, and the plan goes on to its build as the Autopilot rule says. A page that `check` refuses, or a blocked verdict write, follows Never leave a verdict unwritten above.
- A ledger triage audit gives every open unit a fresh verdict and writes no plan. Its page lists every judged scope in `review_scopes`, gives each its verdict in `verdict: [<scope>=<verdict>, ...]` and names each scope's head in `review_basis`, with one `review_commit`. It creates the subject file of each unit that has none, as the first stop does, so the unit's page renders; until then the topic index lists the unit as no page yet.
- **Replace** "Apply the **unslop** skill to the reply": write the reply clean as drafted, with no separate pass, per `AGENTS.md`'s Writing passes rule. The decision page and the page's plan get one `unslop` pass.
- After a Stop or Defer verdict, the answer to the page's question, or a typed word, picks the next step. "again" runs `best-api-review` once more on the same scope and challenges the strongest alternative afresh; its page names the last review in `review_basis` and reaffirms or supersedes it. "interrogate" or "panel" runs the panel on the verdict's target with the configured seats. "plan" opens the Plan playbook on the verdict's file anyway. "next" starts over at the first stop.
