# Babysit

It finishes started work and never starts the next feature.

- **Before** "Declare the mode and resolve the forge before any poll": "review PR <number or URL>" on someone else's PR is review-only (reviews: external-pr). Run the panel on its diff, briefed with the PR body, its linked issue and any plan it carries in `docs/plans`, and have it judge whether the change should exist, whether its design is right, and the code. Return the findings in the reply and stop. The run keeps no plan, page or decision log, and it makes no edits, commits, pushes, replies or review submissions.
- **Before** "Declare the mode and resolve the forge before any poll": resolve the candidate, either a PR's diff, body, checks and review threads through `gh`, or the current worktree's change. Lead with a candid verdict on whether the change should exist and its strongest justified cut, running `verdict` when an API or architecture decision changes that verdict. Repair what the verdict keeps at its owner (the Bug fix playbook for a defect, the Refactoring playbook for code shape), so callers, docs, examples, generated registry output, changesets and barrels end coherent, and prove it with `verify`. Before the run first installs or runs the code of a PR whose author is not on `team` in `.agents/pstack.json`, in a local worktree or through a push that starts CI, `pstack:thermo-nuclear-review`, which audits a diff for security and bugs, reads every line the PR adds. Each commit the author adds later gets the same read before the run installs, runs or pushes it. An author's change to a workflow, a package script, a build or test config, a lockfile or a dependency waits for the owner's word before it runs, and so does any line that review finds reading a secret, a token or the environment, or calling the network. For a PR you opened, write its description and history with `make-pr-easy-to-review`. On another person's PR, leave their description and history alone and keep one comment about your commits, as the `plan-page` skill's PR section says. The current worktree skips the Babysit steps, except the code-quality review below, which it runs before it calls the tree clean. An issue PR lands and closes as the Issue PRs bullet below says. On any PR, an assignment that someone other than its author holds on the PR, or on an issue it names, reserves it under `AGENTS.md`'s Routing rule, so the run stops and leaves the PR open, as the Issue PRs bullet does for any other hold. On any other PR, commit the repair and push it to the PR's head branch without asking, under `AGENTS.md`'s Delivery rule, unless that branch is `main` or `next`. The run merges that PR once it is green, as the merge bullet below says. When the PR does not allow maintainer edits, or a push to its head branch is refused, the run delivers the PR's change itself instead of stacking a PR on its head branch (owner's word, 2026-11-04). That carry delivers the author's own work under their credit, so an assignment the author holds does not reserve it from the run, as `AGENTS.md`'s Routing rule otherwise would. It folds the PR's commits and the repair into one commit with one `Co-authored-by:` line for each author of those commits, delivers that commit into the PR's base, and closes the PR with a comment that links what replaced it once our PR is open or the commit has landed, so a later push to the author's branch never needs another fold. The fold is a new branch of ours, not a rebase of the author's, so pstack Babysit's steps 4 and 5 do not stop it. When the PR's commits conflict with the base, the run resolves the conflict in the folded commit. When our PR later falls behind its base or conflicts with it, the run merges the base into our branch and resolves any conflict in that merge, because our branch needs no force-push. Pushing our branch is a push the reviews list's `push` row covers, so a carried change that alters a public API or deletes behavior gets that panel first. Pushing the folded commit, to our branch or through `land.mjs`, also runs the author's code in this repository's CI with its secrets, where a fork's workflow run would wait for the CI approval that `.agents/pstack/rules/land.md` keeps for the owner. So the run pushes the folded commit only once the verdict and the security read above have covered every line the carry adds, on the folded diff. For the rest of the carry, "babysit" is the owner's word for that CI run, the CI approval `land.md` keeps for the owner. That run is not a credential use under `AGENTS.md`'s Git and publication rule, which stops a password, token, key or OAuth prompt that the run itself would answer, because GitHub reads the repository's secrets and the run answers no prompt. The writing passes cover the run's own lines, its conflict resolutions included, and the author's lines change only for a defect a review finds or a conflict the run resolves. When the folded commit's base is newer than the base the run proved the repair on, the run reruns the proofs that difference touches. Right before that close, it re-reads the author's head. When the head moved, it adds the new commits to our PR as one more commit with their authors' `Co-authored-by:` lines, and when the author rewrote their branch, that commit carries only the change between their old and new commits, as `git range-diff origin/<base>..<folded head> origin/<base>..<new head>` shows, so no base commit their rebase brought in enters our PR, because a force-push to our PR's branch needs the owner and the squash merge folds them anyway. Before the merge, that commit gets the verdict, review round and proofs that a moved head gets, as the Main-line PRs bullet says. When those commits conflict with ours, the run resolves the conflict in that commit, and when the verdict cuts them, the run leaves them out and names them in the hand-back. When our PR then stops before its merge, the hand-back names the closed PR, so the owner can reopen it. Until our PR merges, each poll of it also reads the closed PR's new comments, and a reply prepared for the closed PR stays a draft that the hand-back names. That close comment is a plain comment, not the plan's comment render, and it is the one comment about our commits that the closed PR keeps. The folded commit's message names an issue as `plate#<N>` and never puts a closing keyword before it, as `AGENTS.md`'s Git rule says, because main-sync later brings the commit to `next`. A commit into `main` never goes through `land.mjs`, so before the push the run checks that message with `node .agents/pstack/writing-check.mjs`, and reads it, our PR's title and the squash subject for the closing-keyword ban above, which only `land.mjs` enforces. Those two are the only `land.mjs` gates a commit into `main` takes. Its subject follows `../plate`'s Conventional format, as its merges do, and the `Beyond the ask:`, `Introduced-by:` and source lines that `land.mjs` asks for belong to `next`'s history. For a PR into `next`, the run lands that commit through `land.mjs`, as the Issue PRs bullet below does. For a PR into `main`, it opens our own PR as delivery under `AGENTS.md`'s Delivery rule, which the Messages rule exempts, and the merge bullet below merges that PR in place of the author's. From then on, each later step that names the PR, its branch or its number means our PR. Its body is the plan's PR render with the plan's On top of the PR section, in place of the `make-pr-easy-to-review` description a PR you opened gets, so reviewers see what we changed from the author's version. The plan writes that section as it would for a comment on someone else's PR, because our PR carries the author's change. The body leaves out the run's stages, models, Defaults and the plan's link, and every other line the Writing rule keeps out of public text, because anyone can read it. The render prints those parts, so the run cuts them from the rendered file before `gh pr create` and before each `gh pr edit`. Our PR keeps the `auto-release` box the workflow gives a new PR, not the author's choice, because the merge bullet below decides the release, and each `gh pr edit` keeps that block and its checked state, as `.agents/rules/changeset.mdc` says. "babysit" is the owner's word for that close and that comment, the explicit authorization `.agents/pstack/rules/messages.md`'s Messages rule asks for. This replaces the stacked PR that `.agents/pstack/rules/land.md`'s Other people's PRs rule names. Any other PR comment, thread replies, closing and history rewrites each need the owner's word for that action, because this repository is public and a PR's author may be outside the team. Until then, the thread replies the steps below prepare stay drafts, and the run does not wait for them.
- **Issue PRs.** A PR into `next` is an issue PR when its closing references, title, body or head branch, such as `fix/5264-android-long-press`, name a udecode/plate or udecode/plate-private issue. Babysit runs it as `triage fix #<N>` or `triage fix plate-private#<N>` on that issue, the [Triage playbook](./triage.md)'s Fix, with the PR's diff as the candidate fix. The PR and its author's assignment hold the issue, so the claim takes them as Fix's Takeovers say. Any other hold stops the run and leaves the PR open, and so does a device kind, which waits in the Device lane. Before the run keeps any of the candidate, it shows the reporter's steps failing on `next` and passing at the PR's head; a head that still fails them is a failed fix, as the Bug fix playbook says. Before it keeps a change to a file the record's `owner:` does not name, it traces why that file needs the change, and it traces why the fix needs no change to each owner file the PR leaves alone. The record's miss classes, not the PR's own tests, decide which tests the fix adds. The repair runs in a worktree cut from `origin/next`, with the PR's commits cherry-picked onto it. It lands through `land.mjs`, so it passes the message gates that `gh pr merge` skips, and its message has one `Co-authored-by:` line for each author of those commits and names the issue as the Git and publication rule in `AGENTS.md` says. Once it lands, the run records and comments as Fix step 4 says, then runs `gh pr close <number> --comment "<text>"` with a comment that names the landed commit. "babysit" is the owner's word for that close and that comment, the explicit authorization the Messages rule asks for, in place of the merge below.
- **Main-line PRs.** A PR whose base is `main` belongs to `../plate`. Run it with this repository's skills, playbooks and rules; the `.agents` rules and skills in `../plate` are older copies and do not govern. Take only repository facts from `../plate`: its package scripts (`pnpm test <package directory>`, `pnpm check`, `pnpm brl`), its Biome lint and its changeset format. Its repair runs the Bug fix playbook on the PR's defect, not as a fix for an issue the PR names, because Triage's Fix gives an issue that reports `main` no fix yet and its claim would stop the repair. Run a package's tests through the root `pnpm test`, as CI does. `pnpm --filter <package> test` runs every test file in one Bun process, where one file's `mock.module` breaks the next file's tests. Repair in a detached worktree of `../plate` at the PR's live head, with dependencies installed there by `../plate`'s own `pnpm install`, not `.agents/pstack/setup.mjs`, which copies this checkout's env files into it, and never run `gh pr checkout` or switch a branch in `../plate` itself. Put that worktree outside this checkout, such as in `../plate-worktrees/<slug>`, because the desktop app refuses Edit and Write inside this checkout to a worktree session and its subagents. When the PR is red only because `main` is red, fix `main` in a PR of its own, merge it once green as the merge bullet says, and leave the PR's branch alone until then. Then update the PR's branch with `gh pr update-branch <number>`. Re-read the PR's `headRefOid`, body and comments before each review round, each claim taken from the forge and the delivery; when the head moved, bring the repair onto the new head and rerun the proofs it touches. Delivery is one shot under the owner's standing authority in `AGENTS.md`. Push the repair commit to the PR's head branch when maintainer edits are allowed. When they are not, or that push is refused, build the folded commit on `origin/main` in that worktree, push it to a branch of `udecode/plate` and open our own PR into `main`, as this file's second bullet says.
- **Next coverage.** Before the verdict on a PR whose base is `main`, run `review-comment`'s step 2, Gather the Plate v2 evidence, on the job the PR changes, and record one outcome in the run's decision log. The outcome is `covered` when v2's owner already does the job, with its path and a scenario that passes in this checkout as proof, and `moot` when v2 removed the job or gave it to another owner. Either way the PR stays v1-only work. The outcome is `gap` when v2 lacks the job. The run then does that job on `next` itself once the PR merges, in a worktree of its own cut from `origin/next`, and offers no card for it. `verdict` picks the v2 shape when it is an API or architecture choice, and the run takes its pick, as the Autopilot rule says. The Bug fix playbook builds the rest, cherry-picking the PR's code where `next` kept it close enough, and the commit has one `Co-authored-by:` line for each author whose code or tests it carries. The work lands through land.mjs. A merge of `main` into `next` cannot carry a change to a path `next` removed, so without this work the job never reaches v2. The review-only path names the outcome, and the `next` work it would do, in its reply, and does none.
- **Main sync ledger.** `docs/plans/main-sync.tsv` has one row per `main` commit missing from `next`'s history, each `pending`, `gap` or `synced`, and `node tooling/scripts/main-sync.mjs` keeps it. Every main-PR babysit except the review-only one runs the script first. The script appends new `main` commits as `pending` and lists the rows not yet `synced`, and the run names those rows in its reply, so a PR someone merged by hand shows up at the next main-PR babysit. Once the PR merges, the run sets its row with `--set '#<number>' synced` when Next coverage found `covered` or `moot`, or once its own `next` work lands, and lands the ledger with that work or its plan. `<number>` is the PR that merged, which is our own PR when the run carried someone else's. Only work that cannot land in the run leaves the row `gap`, with the reason as its note. Git ancestry never marks a row `synced`, because a merge into `next` can drop the change.
- **Plan page.** A PR babysit that repairs the PR, unlike the review-only one above, keeps its plan and decision log in this repository's `docs/plans`, including a `main` PR worked in `../plate`. It publishes the plan page before the first review round.
- When PR feedback states an objective, low-ambiguity rule, treat it as a confirmed rule violation and run the Bug fix playbook's Pokayoke audit of its whole governed area, decide the ambiguous instances once, and report those extra fixes apart from the comment you answered. A taste or architecture comment gets one decision or a pushback draft; one that changes a reusable public API goes to Best API.
- **Before** "Stop at the human's line": before calling a PR ready, run `pstack:thermo-nuclear-code-quality-review` on its diff, with the split law in `.agents/playbooks/refactoring.md` overriding its size-based split advice. Fix or answer every finding on a defect the candidate introduced, wherever that defect sits, such as a helper its change left without callers. A finding on code it neither changes nor breaks goes to the plan's Open work with its `owner:`, or to the reply when the run keeps no plan, as the Build playbook's review bullet does for pre-existing code.
- **Before** "Stop at the human's line": every PR babysit except the review-only one and an issue PR's runs `drive` and then merges, because "babysit" is the owner's word to merge (owner's word, 2026-10-21). It replaces Shipping for that PR. A merge into `main` is that word for the push and the deploy it starts, so the Autopilot rule's stop for a push to `main` does not hold it. A draft does not stop it either; run `gh pr ready <number>` once the PR is green. The run stops before the merge only when the verdict cuts or rejects the whole change, not a part the repair drops, an author's code waits for the owner's word or another person's assignment holds the PR, as the second bullet says, a call has no clear pick and cannot be undone, or a repair can reach neither the PR's branch nor a carry of the PR, as the Before bullets say. A merge into `main` of a PR whose auto-release box is checked and that carries a changeset would publish every pending changeset to npm, and a release needs the owner's explicit request. So the run leaves the box as it is, writes the squash subject as `<title> (#<number>) [skip release]`, as the owner's own `main` merges do, so `main-sync.mjs` still finds the row by its number, and names the pending release in the hand-back. First read the signed-in user with `gh api user --jq .login`. The method is `--merge` into `next`, the only one its rules allow, and `--squash` into `main`, as its merges do.

Drive until no check is pending or failed and the watcher names no blocker other than `review-required`, the draft state or a settled review thread, then run `gh pr merge <number> --admin --match-head-commit <headRefOid>` with the method. Read back `gh pr view <number> --json state,mergedAt,baseRefName` and confirm the merge commit is on the base. ## Current-tree closure

Clean means:

- no verified in-scope finding remains unresolved, and structured review passed or is recorded as not applicable;
- every accepted code-shape finding (shallow modules, over-splits, fake wrappers, ownership confusion, duplicated helpers, navigation friction) is fixed through the Refactoring playbook, rejected, or routed with owner and reason;
- the coherence audit found no stale dirty fix, fake alias, docs and API mismatch, orphan test, obsolete generated output, weak command, missing changeset where package policy requires one, or violated Slate and Plate boundary;
- when the diff materially changes public API, `best-api review` ran and every P0 and P1 finding is resolved or explicitly rejected;
- required focused proof after the last patch passes or is explicitly N/A;
- generated outputs affected by the diff are synced or intentionally absent;
- docs, API, examples and tests are coherent with current source;
- no dirty speculative half-patch remains;
- the files called clean are in the current checkout; a captured PR or range diff is not current-tree clean until applied and verified here.

Clean is a ledger state, not a vibe: one terse review is not clean.

Review comments become sweeps only where they generalize: prefer one coherent follow-up refactor over many tiny copy-paste fixes, keep the blast radius proportional to confidence, and call out a sweep that depends on another PR. Naming preferences, broad architecture changes without repo evidence, weakly general style choices, public API widened for local convenience, and anything that cannot be explained in one sentence are not sweep targets. An outdated review thread is not stale by default: `isOutdated` means the hunk moved, so relocate the concern by source text, path and surrounding code before deciding.
