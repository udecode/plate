# Hand drive

A Playwright spec checks only what it asserts. In the lint run, eight green cases on Chromium and WebKit hid a demo that scrolled sideways at 375 px and a docs preview that squeezed the editor into a 306 px column, and the drive that found them skipped two pages and the narrowest preview. The hand drive is one check by the agent, in a real browser, of every page a change shows. Desktop width in light is the default. Phone width, the narrowest preview, dark and the Chinese pages are checked only when the change can affect them. `tooling/scripts/hand-drive.mjs` lists the desktop pages that check covers, and judges the drive from the visits the `www-drive` server records.

## When

Every change with a browser-visible result gets one hand drive before it closes, even when Playwright specs cover it. A file can be browser-visible when it sits under `apps/www`, `apps/plite`, `config`, `content/docs` or a package's `src`, and is not a test, Markdown, a `.gitignore`, Playwright config or generated output. `node tooling/scripts/hand-drive.mjs scope <file...>` decides for the change's own files.

## Browser

Drive the Claude desktop app's built-in browser by default. It has no extensions, so no password-manager menu covers a field, though its profile keeps sign-ins across sessions. Its editing keys reach an editor as Chrome's do. Its `type` action and its rendering while the pane is hidden do not, so type and check frames as verify's Drive section says. Use the owner's Chrome through Claude in Chrome only for a claim about Chrome itself, a profile, an extension, the clipboard, a download or printing, or when the built-in browser cannot deliver an input. Codex drives its own browser. A Playwright run never counts as the hand drive. The visit record marks it as a webdriver visit, which `check` counts only for a `load` cell.

The built-in browser cannot start a native drag. Drive a text drag there as a real mouse selection, then `DragEvent`s dispatched from the browser's JavaScript tool. Resize the tab to 1280x900 first, because a hidden pane reports a width of 0, which misplaces the drop, and list demo cells need at least 1,200 px. A dispatched drop proves the editor's drop handling, not a native drag, which [native editor proof](./editor-proof.md) owns.

## Setup

Start the `www-drive` entry of `.claude/launch.json` with `preview_start`, or run its command in Codex. It runs the www dev server with `PLATE_WWW_DRIVE_DIR=docs/plans/artifacts/drive`, and `next.config.ts` turns on a drive flag in the browser when that variable is set. Every `.claude/launch.json` entry also sets `NEXT_PUBLIC_PLATE_WWW_NO_SYSTEM_THEME=1`, so www ignores the browser's color scheme and opens in light unless `localStorage.theme` says otherwise. With the flag on, `apps/www/src/instrumentation-client.ts` starts a reporter on every page before Next's client starts, Next's error page included. The reporter collects the page's errors for the life of the document: window errors, unhandled rejections and every `console.error` call. Those calls include React's string warnings, such as a hydration mismatch, which Next's issue badge counts too. An error belongs to the document, not to an address, so every visit the document posts carries every error it has logged. The reporter posts a visit to `POST /api/dev/drive` as each new error arrives, and the route appends it to `visits.jsonl`. The root layout's beacon asks it to post after each navigation, resize, theme change, pointer or key release, once the document has finished parsing. A page that changes without one of those events, such as a refresh that turns it into a Not Found, posts nothing until the next one. A visit holds the path, the window width, the painted theme, the page's errors, whether the page sits inside a frame, `navigator.webdriver`, the time the server rendered the page and the time the page sent it. Its errors start with a rendered Not Found and the error status the server answered the document with. The reporter keeps the first 20 errors, each cut to 300 characters. It posts each visit once, with `sendBeacon`. The render time comes from a script the server writes into the page's HTML. The browser runs it once while the page loads, and React never runs a script it adds later, so a refresh or a remount cannot replace it. The route refuses a render time later than its own clock and records a visit without one. A production server, or one started without the variable, records nothing.

## The loop

1. Run `scope <file...>` on the change's files. Each line is a cell, one page at desktop width, 1,200 px or wider, in light:
   - every English page that shows the file, a component's own demos and their Plite example pages included;
   - for a Chinese file, a `.cn.mdx` page or a demo value under `examples/values/cn/`, the Chinese pages that show it instead;
   - a file that reaches more than six pages: the desktop cells on its own pages, or on the first page that shows it when it has none, and a `load` cell on each other page, met when the page's latest fresh visit has no page errors. A scripted visit meets it only while the agent has not loaded the page itself; once it has, the agent's own latest visit decides.
2. The cells are the smallest set, not the whole drive. Add only the pages and states the change can affect:
   - 375 px for a layout change that can differ on a phone, such as width, overflow, wrapping or a breakpoint;
   - a tablet width for a breakpoint the change touches;
   - a changed demo's docs preview at its narrowest. The preview's Mobile toggle sets it; where the page shows no toggle, drag its resize handle to the left limit;
   - dark on every page whose colors the change touches;
   - the Chinese pages of an English change that can render differently there, such as one to i18n or to text whose length the layout depends on;
   - each demo whose value holds the changed element, the playground included.

   `check` does not judge these states. Their screenshots are the proof.
3. A file no source maps, such as package code, shared www chrome, the Next config, an env file, a registry build script or a deleted page, shows as `unmapped`. Name the pages a person would check with `route <file> <page...>`, for a deleted page the pages that linked to it, or record that it shows nothing with `route <file> --none "<reason>"`. A route record holds the file's blob and stops applying once the file changes. A registry build script changes what www renders only after `build:registry` runs again, so rerun it and restart `www-drive` before you drive its pages.
4. Keep one tab open on the drive server. A theme change reaches every open tab, and each one posts a visit in the new theme. Run the change's lint fix before you drive, because any later write to a cell's file reopens the cell, a lint fix included. Drive each cell at least 5 s after the last edit to its files, reloading the page first. Set the width with the browser's resize. For a dark check, set the theme with the site's theme toggle, or on a `/blocks` page, which has none, by writing `localStorage.theme` and reloading, then set it back to light, because the browser keeps it for every later drive on that port. www paints from `localStorage.theme`, not from an emulated color scheme. Do the change's interaction, typing as verify's Drive section says, and scroll the changed element into view. Save each script you run through the browser's JavaScript tool, such as a selection, a dispatched drop or a DOM read, as a file in the run directory the first time it runs, so the replay on the final bytes runs the same drive instead of one recovered from the transcript.
5. Take a screenshot of each cell and read it at a legible scale for overflow, clipping, collapsed lists, contrast in any dark check and the changed behavior.
6. Run `check <file...>`. `check` orders visits by the time the page sent them, and of two sent in the same millisecond takes the one with more errors as the later. Except for a `load` cell, it ignores visits inside a frame and visits driven by webdriver. A `load` cell takes the agent's own latest counted visit, or a webdriver visit when the agent has none. A visit is fresh when the server rendered its page at least 5,000 ms after the last write to every file the cell covers. A file's last write is its modification time, or for a deleted file that a route record maps, that record's time. A visit that reports an error and arrived after that last write counts too, fresh or not, so a page whose server render failed shows as `error`. A visit with no render time is never fresh. A cell takes the latest counted visit on its page that either reports an error or shows desktop width in light. The cell is `covered` when that visit is fresh and has no page error, and `error` when it has one, such as a throw, a rendered Not Found or a server error status, so a page that crashed fails every cell of that page. A desktop cell is `stale` when it has such visits and none counts, and its detail says how long after the edit the latest one rendered, or that it has no render time. A cell is `open` when it has no such visit, and so is a `load` cell whose visits all rendered sooner. `check` exits 1 while any cell is not covered or a file is unmapped. Cite its log in the plan's Hand drive gate.

## Drift

A drift is a difference between what the drive shows and what the specs assert, such as a sideways scroll a green spec never measured. Log it when you find it, as a `drift` row whose decision starts with `drift-<n>:` and whose result is `open`. It closes only with a test that fails on it at the old code. Write the test at the smallest boundary that observes it: a unit or component test when one can, and a managed browser spec for layout, paint, focus or input. Run it at the old code through `node tooling/scripts/proof-worktree.mjs <worktree path> <old commit> --with <test file> --dir <run directory> --name <name> --expect-fail <the case title> -- <test command>`, and save that command's own output in the run directory as `drift-<n>-red.log`. Read the log. The case title must sit on the runner's failing-test line, and the failure must be the drift, not a launch failure, a timeout or a generic message. Then fix the code and run the test green. Log the `fixed` row with both logs.

## Stop hook

`hand-drive.mjs --hook` runs at Stop in Claude Code (`.claude/settings.json`) and Codex (`.codex/hooks.json`, after the owner trusts it in `/hooks`). It reads the files the session added, changed, moved or deleted, from Claude Code's Edit and Write calls and from the file changes Codex records when it applies a patch. It refuses the first stop while one of their cells is not covered or a file is unmapped, and lists them. It lets the stop through on the stop after a refusal, and in Claude Code while background tasks or scheduled wakeups are pending; Codex sends no such fields. A message from the owner that starts with "skip drive" waives the edits made before it. The hook reads only the session's own transcript, so it cannot see files edited through shell commands, by a subagent or by a Codex worker. The plan's Hand drive gate runs `check` on the plan's own file list for that reason.

## Limits

- The cells cover desktop width in light. A phone, tablet, narrow-preview or dark check is proven by its screenshot alone. The cells do not prove native input, an IME, a device, Safari or another browser engine, which [native editor proof](./editor-proof.md) owns.
- A covered cell other than a `load` cell proves that a top-level page on the drive server, not driven by webdriver, rendered at least 5 s after the last edit to the cell's files and reported that state. It does not prove which browser posted it, that anyone looked or that the page showed the change. `/docs/clipboard` was once covered while its new sentence sat only in `textContent`, not `innerText`. For a text change, read the changed text from `innerText` or the screenshot, and record that read beside the `check` log. A background tab posts when a theme change in another tab reaches it, and any browser open on the drive port posts too. Reading the screenshot is step 5, and nothing checks it.
- `check` does not read drift rows. Whether a drift closed with a red run is in the log you cite.
- `check` judges when the server rendered a page, not which code it ran. The dev server notices an edit up to about 150 ms after it, and later on a loaded machine, so a page requested sooner runs the old module. Probes of the earlier stamp, the time the layout handed the beacon, ran with every core busy. On a component file and on a docs page with a demo preview, they found no old render stamped later than 400 ms after its write. No probe has measured the stamp in the HTML, which renders in its own Suspense boundary after the layout. No probe measured package source, CSS, JSON demo values, a new route file or a burst of writes.
- A copy that keeps an old modification time, such as `cp -p`, `rsync -a` or `tar -x`, can make an old visit count; edit tools and git checkouts set a new one. A forward jump of the machine's clock between an edit and a render can too, and a backward jump can hold a cell stale or put a later visit before an earlier one, within one page load too, so a clean visit can hide a later error. A deleted file recreated and deleted again after its route record keeps that record's time. Any write to a cell's file reopens the cell, one that restores its earlier bytes included.
- A `load` cell also takes a visit inside a frame, and a visit driven by webdriver while the agent has not loaded the page.
- The reporter sees no failed resource load, such as an image or a script that answers 404. Read the browser's console for those.
- A visit the route never records is lost. `sendBeacon` refuses a visit while the page's unanswered keepalive requests, its earlier visits included, pass 64 KiB. That happens when the server stops answering while the page keeps posting, or when the page logs a burst of long errors in one task. A server restart drops a visit in flight, and the route rejects one whose render time is later than its own clock. Every recorded visit of the page load carries the errors logged before it, so a lost visit hides a failure only when every error visit of the page is lost. An earlier clean visit can then still cover its cells.
- The reporter sees a `console.error` call only because it wraps `console.error` before Next's own wrapper keeps a reference to it. A Next upgrade can change that order, so after one, load a page that logs a missing-key warning and check that its visit reports it.
- The reporter starts when Next's client starts. An error from before that, such as one a raw inline script throws while the document parses, never reaches `check`, and Next's badge may not show it either, so read the browser's console with the browser tool.
- A document whose server render failed carries no render time, so it never covers a cell, and its error status still fails the cell.
- An error marks every later visit of the same page load, so a page reached through a link after another page's error shows as `error` until it is loaded directly. A warning the new page logs while it renders also posts under the address the link left, because Next writes the new address only after the render, so the page you left can show as `error` too. Load each cell's page directly rather than through a link.
- An open tab whose document logged an error before the last edit still fails the cell when it posts again, such as when a theme change in another tab reaches it, until a fresh load of the page posts after it.
- A change to `next.config.ts` restarts the server, but a change to a file it imports does not; restart `www-drive` before you drive one. Data cached across reloads, such as `/api/sidebar-nav` and `'use cache'` data, can stay old in a fresh visit.
- The `www-drive` server serves www only, so a file of `apps/plite` gets its own browser proof, and its `route --none` reason names that proof.
