# Conditional diagnosis

Load this method when the cause is unresolved or the user requests diagnosis.
An already demonstrated cause goes directly through Patch's owning repair and
proof. This reference adapts the unchanged protected
[Diagnosing Bugs](../../diagnosing-bugs/SKILL.md) method; read that full method
for its feedback-loop options, minimization, hypotheses, probes and cleanup.
Do not copy or edit its installed source.

## Authority and stopping

`diagnose`, `diagnose only`, `debug only` and read-only requests authorize causal
investigation, not product repair. Run existing proof and disposable diagnostic
harnesses without retaining product changes. Report the reproduced failure,
falsified alternatives, supported cause and remaining uncertainty. Do not proceed
into the upstream fix phase without repair authority. A fix request already
authorizes the repair; finding the cause is not a reason to ask again.

## Plate adaptation

- Establish a red-capable loop through the reported boundary. Inspection can
  locate that boundary; distinguish source inference from observed causality.
  Improve a slow or intermittent loop without replacing its acceptance.
- Use competing falsifiable hypotheses when they discriminate plausible causes.
  Do not manufacture a fixed hypothesis count or minimize every fixture element
  after the cause is established. Preserve the complete reporter fixture for
  final proof, including authors, modes and interaction history.
- Use Verify Plate's actual Browser/Chrome capabilities for live UI and Benchmark
  for measured performance. A missing native capability remains an explicit
  evidence gap while available source/owner investigation continues.
- Probe one causal variable at a time. Keep tagged instrumentation disposable;
  avoid modifying the product into a different case just to get a clean signal.
- Upstream fix/regression phases use Patch's repair loop and Testing's value
  gate. Missing public-boundary coverage is a finding, not permission to add a
  synthetic test that cannot observe the failure.
- Architecture pressure uses Patch's Best API Review decision as soon as evidence
  supports it. The upstream post-fix architecture recommendation does not delay
  that decision or invoke an unavailable architecture skill.
- Clean up diagnostics and rerun the original scenario within the request's
  authority. A diagnosis-only run may remain red and still deliver a supported
  cause; it must not claim a completed fix.
