# Session title

This file says how the lead names the session at each stage. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Session title.** When the runtime has a tool that renames the current session, such as Claude Code desktop's `set_session_title`, the lead titles the session `<emoji> <name> (<n>/<total>)`, such as `🚧 copilot (4/9)`. `<name>` is the session's title from before the run first renamed it, without an earlier emoji or count. `<name>` is one or two words, and an issue identifier, such as `DEV-2024`, does not count toward them. The lead cuts a longer name down to its one or two most telling words and drops a fork marker such as `(fork)` or `(fork 2)`. Before each rename the lead reads the current title, such as with Claude Code desktop's `get_session`. A title that differs from the last one the lead set means the owner renamed the session, and that title, without a leading emoji or a trailing count, becomes `<name>`. The stages are those of the plan page's flow rail, in its order, each with its emoji: 📝 Plan, 📐 Design, 👥 Plan review, 🚧 Build, ✍️ Writing, 🔎 Code review, 🧪 Verify, 🕵️ Audit, 🚀 Ship and 🧠 Reflect. While the lead works, `<emoji>` is the current stage's. Otherwise it is the run's state: 🟠 while the run waits on the owner, such as for an answer or at a stop it reached, 🔴 while a failure only the owner can fix blocks it, such as a lost browser connection or a refused push, and 💤 while the owner has paused or held it. At the close the title is `👀 <name>`, with no count, when the run landed or pushed a commit for this request, so the sidebar shows which sessions hold commits to review. That rename is the turn's last call, after every closing step such as a second land, a worktree removal or a report, because 👀 tells the owner the session has stopped working. When a later message has the session work again, the lead titles it with that work's stage before its first step; in Claude Code, a UserPromptSubmit hook that runs `node .agents/pstack/title.mjs --hook` reminds the lead when the title still starts with 👀. Otherwise it is the bare `<name>`. `<total>` counts the stages this run will run, and `<n>` is the current stage's place among them in the order the run reaches them. A stage the run reaches again, such as Verify again after a code review's fixes, counts again. That order can differ from the rail's, such as Ship before Audit when the push comes before the decision-trail review. A run that skips Plan review, Audit and Reflect starts at `📝 <name> (1/7)`. Work before Build that has no stage of its own, such as a bug fix's reproduction, counts under Plan or Design. A writing pass or a fix inside a review round stays under that review's stage. A task list the lead writes for the request never sets the count. The lead renames the session each time a stage starts or the state changes, and when the run adds or skips a stage mid-run, the next title shows the new total. `decisions-check.mjs append` prints the stage whenever a batch it writes moves the log into a new one. After a compaction or a resume, the lead reads the title and renames the session before its next step. A new request starts again at its own Plan. A review or plan iteration that a gate owes the current request is not a new request, so it keeps the title's name and adds its stages to the count. A runtime without such a tool skips this rule.
