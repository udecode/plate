# Session title

This file says how the lead names the session as the run's state changes. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Session title.** When the runtime has a tool that renames the current session, such as Claude Code desktop's `set_session_title`, the lead titles the session `<emoji> <name>`, such as `🚧 copilot`. The title shows the run's state, never its stage, so the lead renames the session only when the state changes or the count below updates (owner's word, 2026-11-20). `<name>` is the session's title from before the run first renamed it, without an earlier emoji or count. When the run works one issue, such as a bug report or a triage fix, and the owner has not renamed the session, `<name>` is instead the issue's identifier and one or two words from its title that name the problem, such as `#1234 Media insert` for a GitHub issue or `DEV-2024 Login loop` for a Linear one. A report with no identifier, such as a teammate's chat message, keeps the session's earlier name. The lead uses that name from its first rename after the run knows the issue. `<name>` is one or two words, and an issue identifier does not count toward them. The lead cuts a longer name down to its one or two most telling words and drops a fork marker such as `(fork)` or `(fork 2)`. Before each rename the lead reads the current title, such as with Claude Code desktop's `get_session`. It reads it in an earlier message beside a working call, such as a read, because the block's Calls rule gives bookkeeping no call of its own. When the rename must come before the turn's first step, such as after the owner's answer, the lead reads the title beside the turn's first read, such as of the plan or a rule file, because a read is not a step. That tool and `set_session_title` take `session_id: "self"` for the session the lead runs in. A title that differs from the last one the lead set means the owner renamed the session, and that title, without a leading emoji or a trailing count, becomes `<name>`. The emoji is the run's state: 🚧 while the lead works, even while a question to the owner waits, 🟠 once the lead stops and the run waits on the owner, such as for an answer or at a stop it reached, 🔴 while a failure only the owner can fix blocks it, such as a lost browser connection or a refused push, and 💤 while the owner has paused or held it. At the close the title is `👀 <name>`, with no count, when the run delivered its work for this request, as a pushed commit, a local commit or merge where the project's delivery stops there, or changes in the checkout where the owner makes the commits, so the sidebar shows which sessions hold work to review. Any other close that waits on nobody, such as a read-only review, gets the bare `<name>`. A run that also waits on the owner, such as for an ask it hands back unfinished, or is blocked keeps 🟠 or 🔴 instead, because the owner must act on that first. A landing after which the run builds on, such as a phase's, is not the close, and the title stays 🚧. A rename that ends the turn, to 🟠, 🔴, 💤 or 👀, tells the owner the session has stopped working. So it waits for the result of every other step of the turn before the turn's last other call, such as a land. Then it goes in the same message as the turn's last other call and after it, such as a card session's `scan.mjs --landed` check, Claude Code desktop's `wrap_up` or the todo update that closes the list, and alone only when no other call remains, because the calls of one message run in order. When a call in the rename's message fails and the session works on, the lead titles it 🚧 again. The reply that ends the turn comes after the rename. When a later message, or a Stop hook that blocks the stop, has the session work again, the lead titles it 🚧 before its first step, except a Stop hook that only has the session tell the owner one line, such as one that offered a task for `/chips all`, which starts no work and leaves the title as it was. After the close, a later message that the lead answers without work, such as a question, gets the bare `<name>`, and a question mid-run keeps the title. In Claude Code, a UserPromptSubmit hook that runs `node .agents/pstack/title.mjs --hook` reminds the lead when the title still starts with 👀. While the lead builds a plan that holds checkboxes, the title adds ` (<ticked>/<boxes>)` after the name in 🚧, 🟠, 🔴 and 💤, such as `🚧 copilot (5/20)`, so it shows how much of the plan is done. The lead ticks a box in the plan once the proof its step names exists and any review of that step is settled, without waiting for the close, and unticks it when a finding reopens that proof. A box that names no proof, such as a template's checklist line, ticks once the work it names is done. The lead adds the count when the build starts and updates it when it lands a step or changes the state, never for each box, and a plan that gains or loses a box shows the new total at that rename. When a pivot or a new plan iteration gives the run another plan to build, the lead renames the session to count that plan's boxes. After a resume, the lead reads the title and, when it does not show the run's current state and count, renames the session before its next step. A compaction changes neither the title, the state nor the count, so it is no reason to rename the session. A runtime without such a tool skips this rule.
