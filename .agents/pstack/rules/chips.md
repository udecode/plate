# Suggested tasks

This file says how the lead offers, records and cleans up suggested tasks. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Suggested tasks.** Every runtime follows this rule. A suggested task is side work outside the run's target that the owner can start in a new session, and the ledger is where the project tracks it, in place of an issue tracker. A finding that pivots the run never becomes one, as the Autopilot rule says. Sessions started from these tasks are the owner's own work in this checkout, so overlap with them is this rule's subject, not something the Other sessions rule dismisses.
  - **Ledger.** A task lives as rows in the project's ledger `<plans>/suggested-tasks.decisions.tsv`, under one id it keeps for good, because a task outlives the run that offered it and every card that showed it. A card in a suggest tool, such as Claude Code desktop's `spawn_task` or `start_session`, is only a view of a task. The lead queues and appends ledger rows like any other decision-log row, with phase `chip`, and never in a run's own log.
    - The decision is `<task id> <title>`, repeated unchanged on every later row. A new task takes its id from `node .agents/pstack/decisions-check.mjs chips id`. The card's own id goes in a `card:` token, never in the decision.
    - `node .agents/pstack/decisions-check.mjs chips` prints every open task as Ready, Started, Waiting or Unmigrated, with what each waits on and the checks it owns, then the tasks a dropped card closed as `gone`, the topics with more than one task or a design question, and a Do list. The Do list shows one pass at a time, withdrawals, then ledger rows, then cards, with check items beside it, and `chips` exits 1 when any pass, shown or not, holds a problem: a card on a task that cannot start, a wait that can never clear, or two open design questions in one topic. `chips` leaves a malformed wait on a task with no topic to that task's migration. `chips --fetch` first runs `git fetch --all`, which refreshes the remote branches that PR waits read. `chips --session <id>` names this session, so the Do list asks to check each card another session holds; without it, every card counts as this session's. `chips brief <id>` prints the prompt a card for that task carries; for a task merged into an offered task that has no card, or one an older helper replaced with such a task, it prints that task's brief, and otherwise, as for a closed task, it says there is nothing to start. The board also tells a session a card started to work from `chips brief`, which reaches a card whose prompt predates that instruction.
  - **Title.** The title is an imperative phrase. It ends in ` (xhigh)` when the task runs a whole poteto playbook with design judgment, such as an architecture, API or plan choice, a bug whose cause is unknown or a performance diagnosis. A task that says exactly what to do, such as a named fix, a doc update or a check, has a plain title and runs at `high`. The title keeps `(xhigh)` whatever `maxEffort` allows, so the owner sees the recommendation. No title says when the task can start, because `chips` works that out on every read; `append` refuses a new offer whose title says `Now:` or `After:` or ends in `(high)`.
    - When the suggest tool has an effort setting, such as `start_session`'s `effort` for a task that starts fresh, the card sets it, because a card offered without one runs at the lead's own effort. It passes the `Effort:` level that `chips brief` prints. That level is `xhigh` for a title that ends in ` (xhigh)` and `high` otherwise, capped at the project's `maxEffort` in `.agents/pstack.json` when it sets one. The brief's title, and the task's line on the `chips` board, add ` (xhigh)` to a plain title when the task is a design question, a `folded` row gave it `effort: xhigh` or it covers an `(xhigh)` task. A board line names the effort only where `maxEffort` lowers it. When the tool refuses that level, such as one above the lead's own, the card passes the nearest level the tool takes. The owner can raise the setting on the card.
  - **Offer.** Run `chips` before offering. When the finding belongs to the question an offered task's topic names and that task holds no card, log it as a `folded` row on that task instead of offering a new task. The row lists what the finding adds in `writes:`, `waits:` and `owns:`. It carries `kind: decide` when the finding is a design question, or only `effort: xhigh` when the finding needs design judgment but is not a design question, such as a bug whose cause is unknown. When it belongs to the question of a started task or of a task that holds a card, offer a new task in that topic that waits on it with `task:`, because a started session keeps its own plan and a card cannot show new work; `chips` merges it into the carded task once that card is withdrawn. Otherwise the offer's evidence holds these tokens, each `key: value`, named once and separated by semicolons, and its result is `offered`:
    - `writes: <path>, <path>`, required, each a repository path or directory, or an absolute path in another checkout, with no whitespace, glob, quote, comma or semicolon;
    - `topic: <name>`, required, one lowercase kebab-case name for the owner question, such as `plite-landing`, never an area such as `core` or `pstack`; reuse a topic `chips` lists when the finding belongs to its question;
    - `kind: decide` when the task settles a design question before any fix, and nothing or `kind: fix` otherwise; a topic holds at most one offered `decide` task that waits on no task of its topic, and while its design question is started or holds a card, a new one on that topic waits on it with `task:`;
    - `waits: <wait>, <wait>`, one for each thing the task needs first, never the task itself. `pr:<number>` clears when a commit subject starts `Merge pull request #<number> from` or ends in `(#<number>)`. `chips` reads those subjects on `refs/remotes/<remote>/<branch>` as last fetched, for each remote `git remote` lists, where `<branch>` is the `branch` in `.agents/pstack.json`. With no `branch` there, any remote branch counts. A PR that was closed or rebase-merged never clears it, so the lead logs `updated` with the waits the task has now. `task:<id>` clears when that task lands or is dismissed `done`, following each `dup` to the task it merged into. `run:<plan path>` clears when that plan's `Status:` says it landed, such as `done` or `executed`. A task or plan that closes any other way, such as superseded or cancelled, and a task wait that loops back to the task through the waits of offered tasks, leave the wait stuck, and `chips` asks for an `updated` row. A started task's waits no longer count. A task that needs the current run's result waits on `run:` with the run's plan, and a wait never goes in the title or the why;
    - `owns: <check>, <check>` when the task fixes a check that fails on the base branch, such as `ci:check`.
  - **Cards.** Only a task that `chips` lists as Ready before its card gets one. A task is Ready when it has a topic, each of its waits has cleared and no started task writes an overlapping path. `chips` reads the tasks that have a card first, then the rest, each group in ledger order, and a task that writes a path an earlier Ready task writes waits behind it; a waiting task holds no paths. The card's prompt is `chips brief <id>`, which first tells its session to print the current brief, so the session works from the task as it stands when it starts. The lead adds a card only while the suggest tool's last result lists fewer than 20 pending cards, because a newer card pushes the oldest out; a session that has not offered a card yet has none pending. After each card it logs `carded` with `card: <tool id>` and `session: <id>`. The session id is the one the runtime's session tool gives this session, such as Claude Code desktop's `get_session` with `self`, because a card goes away with the session that offered it.
    - When a card leaves the queue without the owner starting or dismissing it, such as when a newer card pushes it out or its session ends, the lead logs `uncarded` with its `card:`, and the task stays open; `chips` lists it as Ready or Waiting again by the test above. Limits says how the lead tells those cases apart. For a card whose session ended, a later session's sweep logs it, as Sweep says. A task that holds a card takes no `folded` row, no `dismissed dup` into it and no `updated` row, except one that only narrows its `writes:` to paths inside the ones it lists, so its card always shows the whole task. When the dismiss tool or the owner says the owner dismissed the card, the lead logs `dismissed declined` with its `card:`, which closes the task as its card showed it. A task that waited on it then has a stuck wait. Once the lead drops that wait, the task gets its own card, because the owner never saw its work. Before any other dismissal of an offered task whose card this session holds, the lead first withdraws the card as Limits says. When the owner says to drop such a task, the lead withdraws the card and logs `dismissed declined` with its `card:` in place of `uncarded`, so no merge lands between the two rows. When the tool reports the owner started it, the lead logs `started` instead. A started task closes with `landed` or `dismissed stopped` and needs no withdrawal.
  - **Later rows.** A later row's result is one of these, and it takes only the tokens named here:
    - `started`, with `writes:` for any path it adds and `session:` naming the session that runs the task, where the runtime's session tool gives that id. The session a card started logs it before it writes, and the lead logs it when the dismiss tool reports that the owner already started the task, or when the owner says so;
    - `landed` when a commit holds the change, the started session reports it delivered the change as the Delivery rule says, or the owner says so; a half-written change in the tree, or a patch nobody applied, does not count;
    - `updated`, on an offered task with no card, or only to narrow the `writes:` of one that has a card, when its paths, topic, kind, waits or owned checks change, and on a started task only for its owned checks; the row names only the tokens that change, and each replaces that token's whole list;
    - `folded` on an offered task with no card, with `writes:`, `waits:` and `owns:` that join the task's own, `kind: decide`, which makes it a design question, and `effort: xhigh`; `carded` with `card:` and `session:`; or `uncarded` with `card:`, as Offer and Cards say;
    - `reopened` for a task that an older ledger closed as `gone` when its card left the queue, while its work is still owed;
    - `dismissed` with one reason: `done` when the tree already holds the fix of a task nobody started; `dup <task id>` when another offered task covers a task nobody started; `superseded` when the run removed the target of a task nobody started; `declined`, with the task's `card:` when it holds one, when the owner dismissed its card or said to drop it; or `stopped` when a started task's session ended before its change landed. That holds when the session tool reports the session archived, no commit holds the change, its last report neither says it delivered the change nor hands back a patch, and neither this checkout nor the session's own worktree holds an uncommitted edit on the task's paths. It also holds when the owner says they stopped the task or says to drop it. After a `dup`, the kept task keeps its own title, lists the duplicate's title and findings under Also covers in `chips brief`, and takes its paths and owned checks. It also takes the duplicate's waits, except each wait that leads back to it through dup rows, and becomes `decide` when the duplicate was one. A dup that an older helper logged into a started task listed only the duplicate's title and findings under Also covers and took its owned checks.
  - **Checks.** `decisions-check.mjs` judges each chip row against the ledger rows before it. Both `append` and the whole-log check, which skips rows committed at `HEAD`, refuse:
    - a second offer of one id, or a later row whose task's state does not allow it;
    - an offer with no `writes:`, a `writes:`, `topic:`, `kind:`, `effort:`, `waits:`, `owns:` or `session:` value outside the grammar Offer and Cards give, an `updated` row that names no token, an `updated` row on a started task that names anything but `owns:`, or a `carded` row with no `card:`;
    - a `dismissed dup` that names the task itself or a task that is not open, or a `folded` row with `kind: fix`;
    - an offer, `updated`, `reopened`, `folded` or `dismissed dup` row that leaves two offered `decide` tasks in one topic that wait on no task of that topic, or an offered `decide` task that does not wait on its topic's started one, directly or through a `dup`; a `folded` or `dismissed dup` row counts only when it makes its task a design question.
    - Only `append` also refuses the rows below. Each one judges a rule that older ledgers predate, or the live state of git, plans, the ledger or the paths on disk, which can change after the row is written: a chip row in a run's log, which a run that began before the ledger may still hold uncommitted; a new offer with no `topic:` or with a title marked `Now:`, `After:` or `(high)`; a new `dismissed gone` or `dismissed replaced` row; a `topic:`, `kind:`, `effort:`, `card:` or `session:` named twice, or a token the row's result does not take; a row that adds a wait to a loop, so that a task waits on itself or offered tasks wait on each other through their waits and `dup` rows; a `started` row that adds a path another started task writes; a `dismissed dup` into a started task; a `folded` row on, an `updated` row that does more than narrow `writes:` on, or a `dismissed dup` into a task that holds a card; an `uncarded` or `dismissed declined` row whose `card:` is not the task's current card, or that names none on a task that has one; a `dismissed dup` when either task has no `topic:`, or when their topics differ and they are not both design questions; an empty `waits:`; an `updated` row that gives a task with no topic its `topic:` without naming `waits:`, which is `waits: none` for a task that waits on nothing; a `carded` row for a task that already has a card; a `carded` row or an offer whose `card:` has no `session:`, or an offer with `session:` and no `card:`; a `carded` row, or an offer with `card:`, for a task `chips` would not list as Ready without that card; and, in any log, a `base-red:` token that names a check no open ledger task lists in its `owns:`.
  - **Sweep.** The lead runs `chips` before it offers a task, at each hand-back, after each compaction and at the close. A ledger pass holds at most one merge. `chips` prints it for a task that waits on a task of its own topic once neither holds a card, and only when `append` would take the row. The pass leaves every other item on those two tasks to the next pass, which sees what the merge moved. The lead applies the Do list's pass and the steps below in one `append --from` batch, runs `chips` again, and repeats until the Do list holds no item it can apply:
    - When the tree already holds an offered task's fix, the lead logs `dismissed done`. When a started task's change has landed, it logs `landed`. When the run removed a task's target, it logs `dismissed superseded`.
    - When open tasks nobody started answer one question, the lead keeps the earliest design question among them, or the earliest task when none is one, and logs each other one `dismissed dup <kept id>`, first logging `updated` with the kept task's topic on one whose topic differs, unless both are design questions. A dup never goes into a started task, because its session keeps its own plan, or into a task that holds a card; the duplicate waits on it with `task:` instead, and `chips` merges it into a carded one once the card is withdrawn. A task whose work a started task covers waits on it with `task:`, and the lead logs it `dismissed done` once that task lands with the fix.
    - Where the runtime's session tool gives this session's id, the lead runs `chips --session <id>` with it. For each card the Do list says another session holds, it looks that session up with the session tool and logs `uncarded` with its `card:` when the tool reports it archived or gone. For each started task, it looks up the session its `started` rows name. When they name none, it finds that session with the tool, archived sessions included: its transcript opens with the task's card prompt, and a session that only printed the board does not count. The lead then logs `started` with its `session:`. When the tool reports that session archived, the lead logs `landed` when a commit holds the change or the session's last report says it delivered the change. It logs `dismissed stopped` when that report hands back no patch and neither this checkout nor the session's own worktree holds an uncommitted edit on the task's paths. Otherwise, and while the session is not archived or the tool cannot find it, the task stays started. The sweep's report says why, and that the owner's "drop <task id>" closes it. The lead never asks the owner whether a session still runs. A runtime without a session tool logs `uncarded` with its `card:` for a card on the owner's word that its session ended, and `dismissed stopped` for a started task on the owner's word that they stopped it.
    - For each task `chips` lists as Lost, which a dropped card closed as `gone`, the lead logs `reopened`, then `updated` with its topic and waits, or, when its work is already done or its target gone, `dismissed done` or `dismissed superseded` after the reopen.
    - Before the run writes a path that an offered task writes, the lead logs `updated` on that task with its waits plus `run:<the run's plan>`. When the task has a card, the lead first withdraws the card as Limits says, and after `started` follows the next bullet instead.
    - Before the run writes a path a started task writes, the lead waits for that task to land or leaves that path to it. The lead runs both checks whenever the run is about to widen what it writes, not only at a sweep.
    - A session started from a task finds its own row by the id in its brief and skips it in these checks. It runs `chips brief <id>` and works from what it prints rather than from its card's prompt, which can be older, and runs it again right after its `started` row, which names this session in `session:`, because the task can gain work until then. Then it runs `chips`, and when its task is neither Ready nor started, it tells the owner what the task waits on before it writes; a started task means the lead logged the owner's start from its card. Before it writes a path its task does not list, it logs another `started` row whose `writes:` lists the added paths. When `append` refuses that row because another started task writes the path, the session leaves that path alone and tells the owner.
  - **Base branch.** A decision row that blames a failing check on the base branch, rather than on the run, names that check in its evidence as `base-red: <check>`, such as `base-red: ci:check`. Before that row, an open ledger task must list the check in `owns:`. The lead reuses a check name `chips` already shows when it names the same failure, and otherwise offers a task that owns it, such as `Make the base branch green (xhigh)`, or logs `updated` with the whole `owns:` list on the task that already covers it, started or not. A row once appended stays valid after its owning task lands.
  - **Limits.** The tool cannot rename a card or change its prompt, so a card's session prints the current brief first. To withdraw a card, the lead calls the dismiss tool on it, then logs `started` when the tool reports the owner started it, `dismissed declined` with the card's `card:` when it reports the owner dismissed it or the owner said to drop the task, as Cards says, and `uncarded` with that `card:` otherwise. The dismiss tool works only in the session that offered the card. It withdraws a card the owner has not acted on, and for one the owner started or dismissed, it reports which. A suggest tool result that lists the cards still pending in this session, such as an offer's, shows which left, and a card the owner clicked or dismissed leaves that list too. So after each such result, for each task this session carded that is missing from that list and that `chips` still lists as Ready or Waiting, the lead withdraws its card. It leaves a card another session offered alone while that session lives, as Sweep says; that card's prompt has the session check the task before it writes. A runtime without a suggest tool skips Cards. It lists each Ready task in the plan's `## Open work` as `<id> <title>`, with `owner:` the owner, `stop:` started or dismissed and the ledger as where it is tracked, or in its reply when the run has no plan.
  - **Close.** At the close, once the plan's `Status:` says done, which clears every `run:` wait on it, the lead runs the sweep once more and cards each Ready task that has no card while fewer than 20 cards are pending; `chips` keeps listing the rest. A runtime without a suggest tool runs that sweep too, right after the `Status:` change, and in the same edit lists each Ready task in the plan's `## Open work` and the subject file's.
