# Suggested tasks

This file says how the lead offers, records and cleans up suggested tasks. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Suggested tasks.** Every runtime follows this rule. A suggested task is side work outside the run's target that the owner can start in a new session, offered with a tool such as Claude Code desktop's `spawn_task` where the runtime has one. A finding that pivots the run never becomes one, as the Autopilot rule says. Sessions started from these tasks are the owner's own work in this checkout, so overlap with them is this rule's subject, not something the Other sessions rule dismisses.
  - **Title.** The title reads `<tag>: <imperative phrase> (<effort>)`, such as `Now: Fix the stale README badge (high)`. The brief's first line repeats the title, so a session started from it can find its own ledger row.
    - The tag is `Now` only when all of these hold. The lead can name the paths the task will write. None of them is a path the run changed since its intake or a path its open steps name. None of them is a path any open task in the ledger writes. The task also needs no result the run has not produced yet. Its brief lists the paths it must not edit.
    - Every other task is `After`. Its offer's why names what it waits for: this run, another open run such as a paused one, or an open task whose paths it shares. When unsure, the lead picks `After`.
    - At the close this run is over, so a task offered then is `Now` unless it waits for another open run or an open task. The lead does not retag open `After` tasks at the close, because the plan's Close names which are free.
    - The effort is `xhigh` when the task runs a whole poteto playbook with design judgment, such as an architecture, API or plan choice, a bug whose cause is unknown or a performance diagnosis. It is `high` when the task says exactly what to do, such as a named fix, a doc update or a check. A project rule that caps effort wins.
  - **Ledger.** Every suggested task, from any run, lives in the project's ledger `<plans>/suggested-tasks.decisions.tsv`, because a task outlives the run that offered it. The lead queues and appends its rows like any other decision-log row, with phase `chip`, and never in a run's own log.
    - The decision is `<task id> <title>`, repeated unchanged on every later row. A runtime without a suggest tool uses a local id such as `local-20261014-1` and lists the task in the plan's `## Open work` too, so the owner sees it.
    - An offer's evidence lists the paths the task will write as `writes: <path>, <path>`, each a repository path or directory, or an absolute path in another checkout, with no whitespace, glob, quote, comma or semicolon. Its result is `offered`.
    - A later row's result is `started` when the dismiss tool reports that the owner already started the task, or when the owner says so. It is `landed` when the started session reports its change done, the owner says so, or a commit holds the change; a half-written change in the tree does not count. Otherwise it is `dismissed` with one reason:
      - `done` when the tree already holds the fix of a task nobody started;
      - `dup <task id>` when another offered or started task covers a task nobody started;
      - `superseded` when the run removed the target of a task nobody started;
      - `replaced <task id>` when a new offer took the place of a task nobody started, such as under another tag. The new offer's row comes before this row in the ledger, whatever order the tools ran in;
      - `gone` when the tool reports a task nobody started already left the queue, dismissed by the owner or pushed out by newer tasks;
      - `stopped` when the owner says they stopped a started task's session before its change landed.
    - `decisions-check.mjs append` refuses a chip row in a run's log and a row of any other shape. It also refuses a second offer of one id, a later row that its task's state does not allow or that names a closed replacement, a `started` row that adds a path another started task writes, and any batch that leaves a `Now` task sharing a path with an earlier open task or a started one. It runs that last check on the ledger as the whole batch leaves it, so one batch can offer a replacement and dismiss the task it replaces. A replacement or merged task keeps the place of the earliest task it replaces. `node .agents/pstack/decisions-check.mjs chips` prints every task still offered or started, with its paths, notes started tasks that share a path, and exits 1 naming each `Now` task that another open task blocks, such as two offers appended at once.
  - **Sweep.** The lead runs `chips` and checks each open task before it offers a new one, at each hand-back, after each compaction and at the close.
    - When the tree already holds an offered task's fix, the lead dismisses it with `done`. When a started task's change has landed, the lead logs `landed`.
    - When tasks nobody started cover each other, the lead offers one merged task, then dismisses each with `dup` and the merged task's id. A task nobody started that a started task covers is dismissed with `dup` and the started task's id.
    - When the run removed the target of a task nobody started, the lead dismisses it with `superseded`. A started task leaves the ledger only as `landed`, or as `stopped` on the owner's word, because its session may still be writing.
    - When `chips` names a blocked `Now` task, or a `started` row would block one, the lead offers that task again as `After`, waiting for the task that blocks it, and logs `replaced` in the same batch.
    - Before the run writes a path an open `Now` task writes, the lead dismisses that task. When the tool withdrew it, the lead offers the same task as `After` and logs `replaced`. When the tool reports the owner already started it, the lead logs `started`.
    - Before the run writes a path a started task writes, it waits for that task to land or leaves that path to it. The lead runs both checks whenever the run is about to widen what it writes, not only at a sweep.
    - A session started from a task finds its own row by its exact title and skips it in these checks. Before it writes a path its offer did not list, it logs another `started` row for its task whose `writes:` lists the added paths. When `append` refuses that row because another task holds the path, the session leaves that path alone and tells the owner, because only the run that offered the other task can retag it.
  - **Limits.** The tool cannot rename a task, so every retag is a dismissal followed by a new offer. The dismiss tool reaches only tasks the owner has not acted on. An offer's result lists every task still pending, so the lead checks that list against `chips` after each offer. A runtime without the tool learns that a task started or stopped only from the owner.
  - **Close.** The plan's `## Close` names as free to start each `After` task that waited only for this run and shares no path with a started task, a `Now` task or an earlier task the Close already names free. It says what each other open task still waits for.
