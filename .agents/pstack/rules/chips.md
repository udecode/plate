# Suggested tasks

This file says how the lead offers, records and cleans up suggested tasks. A session a card started works from its brief instead, because `chips brief` prints every rule its own task's rows need. It reads this file only to offer or drop another task. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Suggested tasks.** Every runtime follows this rule. A suggested task is side work outside the run's target, or a measurement the block's Time budget rule sends there, that the owner can start in a new session, and the ledger is where the project tracks it, in place of an issue tracker. A finding that pivots the run never becomes one, as the Autopilot rule says. Two of them may write the same project files at once, because each works in its own worktree and lands through land.mjs, as Landing says. Every session, the lead's included, works in its own worktree, so the main checkout holds the only live ledger, in the plans directory's `artifacts/`, which git ignores. `decisions-check.mjs` switches to it for `chips` and for an `append` to the ledger's own path, and reads it for each `base-red:` token, so a session runs every ledger command as written from its own worktree. Agents write in the main checkout only under the plans directory's `artifacts/`, which holds the ledger and the run directories, as `.agents/pstack/rules/land.md` says. No commit on `next` holds the ledger, so starting a session never commits there. Each run of `setup.mjs`, which every session's SessionStart hook and every sweep start, keeps the ledger in step with `refs/pstack/ledger` on origin, or on the companion repository's origin when the project has a companion, so its rows stay durable and shared between clones. The file gains the rows only the ref holds, and the ref gains the rows only the file holds, pushed as a fast-forward. Then it fast-forwards the main checkout. The ledger's former path, `<plans>/suggested-tasks.decisions.tsv`, is a tracked link to it, so helpers that predate the move write the same file. When a plain file is there instead, `setup.mjs` moves its rows into the ledger. A `run:` wait reads its plan from `origin/next` as last fetched, and a plan that only a worktree holds has not landed. The sweep starts with `node .agents/pstack/setup.mjs` run in the main checkout, which fast-forwards it when no local edit is in the way, because the board reads paths there. No path keeps two tasks apart, another repository's file included, because the owner dropped that wait for trunk delivery (owner's word, 2026-10-18). A session that finds such a file changed under it redoes its change on the newer copy.
  - **Ledger.** A task lives as rows in the project's ledger `<plans>/artifacts/suggested-tasks.decisions.tsv`, under one id it keeps for good, because a task outlives the run that offered it and every card that showed it. A card in a suggest tool, such as Claude Code desktop's `spawn_task` or `start_session`, is only a view of a task. The lead queues and appends ledger rows like any other decision-log row, with phase `chip`, and never in a run's own log.
    - The decision is `<task id> <title>`, repeated unchanged on every later row. A new task takes its id from `node .agents/pstack/decisions-check.mjs chips id`. The card's own id goes in a `card:` token, never in the decision.
    - `node .agents/pstack/decisions-check.mjs chips` prints every open task as Ready, Started, Waiting or Unmigrated, with what each waits on and the checks it owns, Ready and Waiting tasks in priority order, as Cards says, with P2, P3 and untagged tasks shown only as counts unless `chips all`, then the tasks a dropped card closed as `gone`, the topics with more than one task or a design question, and a Do list. The Do list shows one pass at a time, withdrawals, then ledger rows, then cards, with check items beside it, and `chips` exits 1 when any pass, shown or not, holds a problem: a card on a task that cannot start, a wait that can never clear, or two open design questions in one topic. `chips` leaves a malformed wait on a task with no topic to that task's migration. `chips --fetch` first runs `git fetch --all`, which refreshes the remote branches that PR waits read. `chips --session <id>` names this session, so the Do list asks to check each card another session holds; without it, every card counts as this session's. `chips brief <id>` prints the prompt a card for that task carries, with a `State:` line that says whether the board has it Ready, Started, Waiting and on what, or Unmigrated, whatever its priority; for a task merged into an offered task that has no card, or one an older helper replaced with such a task, it prints that task's brief, and otherwise, as for a closed task, it says there is nothing to start. The board also tells a session a card started to work from `chips brief`, which reaches a card whose prompt predates that instruction.
    - `chips stale` lists, for each open task, what may have made it stale: its age, a ship item that closed, each path it writes that was deleted since its offer or is missing, the commits on its paths since its offer, its closed PR waits and its card. It reads each repository's history once, along first parents, so it counts the commits that reached the branch. A project path, written relative or absolute, reads the project and its companion repository, and an absolute path outside the project reads the repository that holds it. It counts no commit that only renames a path, and neither half of a move between the project and its companion, which is a delete in one and an add of the same path and content in the other within a day. A path renamed away is missing, not deleted. `chips groups` lists the open tasks that may answer one question, as Sweep's Groups bullet says.
  - **Title.** The title is an imperative phrase. It ends in ` (xhigh)` only for a design question, which is a `kind: decide` task, or for a bug or slowness whose cause nobody has located yet. Every other task has a plain title and runs at `high`. That includes a hard fix whose finding names the cause and the function or file where it lives, because the session that found the cause already did that judgment. A design question stays at `xhigh` through its build. The title keeps `(xhigh)` whatever `maxEffort` allows, so the owner sees the recommendation. No title says when the task can start, because `chips` works that out on every read; `append` refuses a new offer whose title says `Now:` or `After:`, starts with a priority such as `[P1]`, or ends in `(high)` or `(fast)`, because `chips brief` prints the priority that Priority gives the task.
    - **Fast.** An offer or `updated` row takes `fast: yes` for a fix at `high` effort that names its exact change and a check that fails today, and changes no public call. The lead judges those conditions. `append` refuses `fast: yes` only on a design question, a review task or a task whose title shows ` (xhigh)`. `fast: no` drops the mark. A task is fast while it carries `fast: yes`, is a `kind: fix` task and its title shows no ` (xhigh)`, so a fold or dup that raises it drops the mark. The brief's title and the board line add ` (fast)`, and the brief says the owner's start of its card, or their "start <id>", is the word fast for its session, as the Fast rule says.
    - When the suggest tool has an effort setting, such as `start_session`'s `effort` for a task that starts fresh, the card sets it, and so does the lead when it starts a task on "start <id>", because a session started without one runs at the lead's own effort. It passes the `Effort:` level that `chips brief` prints. That level is `xhigh` for a design question. Otherwise it is the task's last `effort:` token, or, when it has none, `xhigh` for a title that ends in ` (xhigh)` or a task that covers one, and `high` for the rest. The project's `maxEffort` in `.agents/pstack.json` caps it when it sets one. The brief's title, and the task's line on the `chips` board, end in ` (xhigh)` exactly when that level is `xhigh` before the `maxEffort` cap, as the Title rule says, so an `updated` row with `effort: high` drops a stored tag from both, while later rows still repeat the stored decision. A `dismissed dup` that brings in an `xhigh` task raises the task it keeps. When the suggest tool has no effort setting, the card session starts at the lead's own effort. An `updated` row that changes a carded task's effort leaves its card at the old level, so `chips` lists that card in the withdrawal pass of the session that holds it, and once that session logs `uncarded`, its card pass offers the task again at the new level. A card session the owner already started keeps its effort, which is the owner's to change. No session can lower its own effort, so a card session that the session tool shows above its brief's level tells the owner in its first reply. A board line names the effort only where `maxEffort` lowers it. When the tool refuses that level, such as one above the lead's own, the card passes the nearest level the tool takes. The owner can raise the setting on the card.
  - **Priority.** Each open task has a priority, so the board puts the work a release needs first instead of listing every task in the order it was filed (owner's word, 2026-10-19). The agent that offers a task judges it, and `append` checks its evidence:
    - `P0` is broken now: a task that owns a check failing on the base branch, which `chips` counts as P0 whatever its token says; a regression, with `regressed: <commit>` naming the commit that broke it; or a major bug, such as data loss, peers that diverge, or a throw or stuck state in a public call, with `repro: <failing test, or exact steps someone ran and saw fail, such as a reporter or a tester>`.
    - `P1` is work a release needs: the open items of the project's ship list, the design questions they wait on and the builds of the designs they settle, each with `ship: <item id>`, and user-visible bugs with `repro:`.
    - `P2` is product work that blocks nothing: refactors, performance that breaks no budget, design questions no ship item waits on, docs fixes such as a dead link, and bugs with no repro yet.
    - `P3` is workflow, repository and agent tooling, such as lint output, and measurements.
    - A task shows the more urgent of its own priority and the priority of each offered task that waits on it through `task:`, directly or through other offered tasks' waits, because the waiting task cannot start until it lands (owner's word, 2026-10-20). A started task's waits no longer count, so it raises nothing. `chips` uses that priority on the board, where the task's line adds `blocks <id>`, in the stale report and in the brief, so the card's title carries it too. The task's `priority:` token keeps its own priority, which a sweep judges, and the task shows it again once no waiting task is more urgent.
    - `append` refuses a new offer with no priority and no owned check, a new P2 or P3 offer with no `via:`, a `via:` other than `verdict`, `babysit`, `time`, `hook` or `panel`, a `via: panel` on an offer whose kind is not `decide`, a P0 claim with no `owns:`, `regressed:` or `repro:`, a P1 claim with no `owns:`, `repro:` or `ship:`, a `regressed:` that names no commit and a `ship:` that names no open item. A task with no `priority:` token and no owned check gets no card until a sweep tags it, even when a waiting task raises it, and each full sweep judges every task's priority again from the stale report, which prints it.
    - A project names its ship list command in `.agents/pstack.json` as `"chips": { "ship": [<argv>] }`. The command prints a JSON array of the open items a release needs, each `{ "id", "title", "finding", "writes", "topic", "kind", "waits" }`, where `waits` lists the waits a task that serves the item starts with, such as `run:<plan>` for a plan already working on it. `chips` orders P1 tasks like every other priority, and its ledger pass offers a P1 task with those waits for each item no open task serves. A project with no such command has no ship list, and its P1 tasks are bugs with a repro.
  - **Milestone.** Where `.agents/pstack.json` sets `triage.experimental`, `chips` sorts the tasks of each priority by the milestone class that triage would give a bug with the same facts, so the work a release waits on comes first (owner's word, 2026-11-05). Each task names the review scope that owns its code as `review-scope: <id>`, or `review-scope: none` when no review scope file names its code, such as workflow tooling. A bug that used to work also names the pages where it works, as `regression: <url>, <url>`. A page counts when the bug's report names it and says the behavior works there, or when the session tries the steps there and they work. Triage takes the same evidence, and where the project's triage names the sites a regression page must be on, only a page on one of those sites counts. A task for a triaged issue takes `review-scope:` from the record's `scope:` and `regression:` from the record's `regression:`. When the record's `priority:` is above the task's, the task takes that priority with the evidence Priority asks, and the highest priority among the current records of the issues it covers stays its floor whenever its priority is judged again. Those facts are the whole task's, and no `dismissed dup`, `folded` or `reopened` row moves them. So a session whose dup, fold or reopen changes the work a task covers logs `updated` on it with the facts of all that work. When a later record of an issue changes either fact, the session that writes the record logs `updated` on each open task that covers the issue, through its own `repro:` or a duplicate it absorbed. That row gives each of the review scope and the regression pages that changes, from the current records of every issue the task covers, with an empty `regression:` when none has one any more, because a row names only the tokens that change. When those records name several scopes, the task takes the one of them that owns most of its writes, after leaving out each scope that `triage.experimental` lists, unless it lists them all, so the task ranks with the work a release needs most. A task that covers no triaged issue, or whose issues' current records name no scope, such as a `dup` or `needs-repro` record, or only scopes whose files `chips.scopes` no longer holds, takes the review scope that owns most of its writes. A task with `ship:` leaves out the experimental scopes the same way, unless they own all of its writes, because a release waits on it. A scope owns a path when its file's `owners` list names that path, a folder that holds it or a file inside it. When the `owners` lists leave a tie, such as between record scopes that own none of its writes, the session picks the tied scope the task's brief is about, with each file's `members` list as evidence, because a broad `members` folder, such as one that holds every browser test, says little about the code a task changes. A task with no record scope whose paths no scope file names takes `none`. A task whose review scope is not `none` is a regression when it names `regression:`, experimental when `triage.experimental` lists its scope, and new otherwise. A regression in an experimental scope is still a regression. A task with no review scope, or with `none`, has no class. Within a priority, `chips` lists and cards the regressions first, then the new tasks and the tasks with no class, then the experimental ones, because a release waits on its regressions and the experimental scopes hold up no release. The class orders tasks inside a priority and never changes one, so a bug in an experimental scope keeps the priority that Priority gives it. The board line and the brief name the class. The stale report says `no review scope` for an offered task that names none, so a sweep judges it, whatever session owns the task, because the row moves no card. The sweep takes `regression:` only from a record or from a page the task's own evidence names as working, and tries no steps for it. A sweep gives no review scope to a started task, because the board lists started tasks apart and ranks only the others. A started task still takes the facts when a record of its issue changes. Where `chips.scopes` in `.agents/pstack.json` names the folder that holds one file per review scope, `append` refuses a `review-scope:` other than `none` that names no file there. A project with no `triage.experimental` keeps the order that Priority and Cards give.
  - **Deferred.** Where `.agents/pstack.json` sets `chips.deferred` to a list of review scope ids, `chips` ranks each open task whose `review-scope:` is on that list after every other task, whatever its priority or milestone class, a regression included, so the owner can set a domain aside without changing a priority (owner's word, 2026-11-06). The board lists deferred Ready and Waiting tasks in their own sections, each after the other Ready or Waiting tasks, the card pass cards them last, and the brief says the task is deferred. Each task keeps its `priority:` token, so taking a scope off the list brings the old order back. Its card's title still starts with that priority, because a deferral changes when the task runs, not how urgent it is. When an offered task that is not deferred waits on a deferred task through `task:`, directly or through other offered tasks' waits, the deferred task counts as not deferred everywhere this rule names, because it holds that work back. So does a task that owns a check failing on the base branch, because that check fails every change, as Priority says. A deferred task raises the priority only of the deferred tasks it waits on, so deferred work moves no other task up the board. Priority and Milestone order the deferred tasks among themselves. `chips` asks to fix a `chips.deferred` that is not a list of ids, or that names an id with no file in `chips.scopes`, before its card pass runs. A deferral changes no triage record, milestone or `review-scope:` pick, so a task takes its scope as Milestone says whether or not that scope is deferred. A deferred regression still holds its milestone open, so a release that waits on that milestone also waits on the deferred task. For a task that no triage record covers, that pick rests on the code its `writes:` names, which is the code of the feature whose behavior the repro shows broken while no session has traced the cause. When a session traces the cause to code that another scope owns, it logs the new paths the way Later rows lets a task in that state take them, such as a `started` row that adds them, and `updated` with the new `review-scope:`, which moves the task into or out of the deferred sections. `chips` reads the list from the `.agents/pstack.json` of the checkout it reads the ledger from, so every session's board ranks alike, and a deferral takes effect once that checkout holds it. Close cards no deferred task. When the Ready tasks outside the list that this session may card outnumber the cards it has room for under the limit Cards gives, `chips` asks it to withdraw its own cards on deferred tasks, one for each task left without room, the lowest-ranked first, and to log each withdrawal as Limits says. Every other card on a deferred task stays.
  - **Tiers.** Where `.agents/pstack.json` sets `chips.tiers`, the tier replaces the milestone class inside each priority, so the owner sets the order layer by layer, such as core before features and experimental work last (owner's word, 2026-11-12). `chips.tiers` is a list in rank order, and each entry has a `name` and may list `paths`, `except` and `scopes`. A task that owns a check failing on the base branch or names `regression:` ranks first, as tier `regression`. Each other task takes the first entry that lists a folder holding one of its `writes:` paths, outside every folder that entry's `except` lists, or that lists its `review-scope:`. So a task that writes core code ranks as core whatever its scope, and an `except` folder keeps a feature that lives inside a core package out of the core tier. A task that no entry matches takes the one entry that lists neither paths nor scopes, or ranks after every entry when there is none. Priority still ranks first and Deferred still ranks last, and the tier changes no priority. The board line and the brief name the tier. `chips` asks to fix a `chips.tiers` that is not such a list, or that has more than one entry with neither paths nor scopes, before its card pass runs. A project without `chips.tiers` keeps the order Milestone gives.
  - **Offer.** A run cards a task only for a finding in its domain (owner's word, 2026-11-11). The domain is the subject the run's plan or target names, such as its topic, its review scope or the input a verdict or babysit run judges, or the feature its target changes when it names none. A finding is in the domain when it is the run's own target, when its fix changes code, docs or a plan that subject owns, a file the run's plan added included, or when it exists only because of the run's own result, such as a rerun of the run's own measurement or a question of how another feature adopts what the run built. The run's change is everything its plan has built, its earlier steps and sessions included. Any other finding is outside the domain at any priority. A bug in another subject's code that also shows without the run's change, such as on the commit before its plan's first step, is outside even when one of its cases shows only with that change, the run found it, its panel raised it, a step or gate of its plan waits on it, its plan edits the same shared code, its fix also changes a file the run's plan added or its symptom shows inside the run's feature. Until a trace finds where its cause lies, a finding other than the run's own target that also shows without the run's change counts as such a bug. The domain decides only who owns the task and which session shows it. Whether the run fixes the finding, leaves it open or pivots stays with the block's Suggested tasks and Autopilot rules and `.agents/pstack/rules/panel.md`. When the run fixes or pivots onto a finding that an open task holds, it logs `started` on that task with `session:` naming itself before it writes, and `landed` once the fix lands. For a finding outside the domain that the run leaves open, the run names the subject that owns the fix in the text of its plan's Open work line, or in its reply when it keeps no plan. It also offers a task for it when it ranks P0 or P1, or when a gate needs one: the design question that two open critical panel findings require, as `.agents/pstack/rules/panel.md` says, or the task that owns a check a `base-red:` row blames, as Base branch says. That offer names `session: none`, so the task has no owner. Neither the run's Close nor a plain `/chips` cards it, in any runtime; only `/chips all` does, as Owner says. A `folded` row joins a finding to a task that answers the same question, so the two lie on the same side of the domain. Inside its domain, a run offers a task only for a new P0 or P1 finding, as Priority defines them, and lists a P2 or P3 finding in its plan's Open work, or in its reply when it keeps no plan (owner's word, 2026-10-23). A verdict run may offer any priority for an item its verdict judges, and offers any other finding only at P0 or P1 (owner's word, 2026-11-04). `append` cannot tell such an item from another finding, so the run keeps that limit itself. A babysit run may offer any priority, and so may a measurement the block's Time budget rule sends to a task. So may a project hook that finds recurring work due, such as an intake once enough fixes have landed. Its task lies outside the domain of the run its hook stops, so its offer names `session: none`, and that session tells the owner in one line that `/chips all` cards it (owner's word, 2026-11-11, which replaces the 2026-11-02 rule that the stopped session cards it). That line is no hand-back and starts no new stage, so the session keeps its title, and the run's Close does not count the hook's task as one the run offered. So may the design question that two open critical panel findings require, as `.agents/pstack/rules/panel.md` says. Such an offer names its route as `via: verdict`, `via: babysit`, `via: time`, `via: hook` or `via: panel`, and `via: panel` goes only on a `kind: decide` offer. A `folded` row adds to a task that already exists, so it needs no route. Run `chips` before offering. When the finding belongs to the question an offered task's topic names and that task holds no card, log it as a `folded` row on that task instead of offering a new task. The row lists what the finding adds in `writes:`, `waits:` and `owns:`. It carries `kind: decide` when the finding is a design question, or only `effort: xhigh` when the finding shows a bug or slowness whose cause nobody has located. When it belongs to the question of a started task or of a task that holds a card, with two kinds of evidence and one fix that removes both, as the Sweep's dup bullet asks, offer a new task in that topic that waits on it with `task:`, because a started session keeps its own plan and a card cannot show new work; `chips` merges it into the carded task once that card is withdrawn. Otherwise the offer's evidence holds these tokens, each `key: value`, named once and separated by semicolons, and its result is `offered`:
    - `writes: <path>, <path>`, required, each a repository path or directory, a path the companion repository tracks included, or an absolute path in another checkout, with no whitespace, glob, quote, comma or semicolon;
    - `topic: <name>`, required, one lowercase kebab-case name for the owner question, such as `plite-landing`, never an area such as `core` or `pstack`; reuse a topic `chips` lists when the finding belongs to its question;
    - `kind: decide` when the task settles a design question before any fix, `kind: review` for a review task, as Review says, and nothing or `kind: fix` otherwise; a topic holds at most one offered `decide` task that waits on no task of its topic, and while its design question is started or holds a card, a new one on that topic waits on it with `task:`;
    - `waits: <wait>, <wait>`, one for each thing the task needs first, never the task itself. `pr:<number>` clears when a commit subject starts `Merge pull request #<number> from` or ends in `(#<number>)`. `chips` reads those subjects on `refs/remotes/<remote>/<branch>` as last fetched, for each remote `git remote` lists, where `<branch>` is the `branch` in `.agents/pstack.json`. With no `branch` there, any remote branch counts. A PR that was closed or rebase-merged never clears it, so the lead logs `updated` with the waits the task has now. Before any row adds a `task:` wait between two open tasks, other than a wait the dup bullet gives a duplicate, the lead checks the two against the Sweep's dup bullet, because `chips groups` skips two tasks a `task:` wait joins. `task:<id>` clears when that task lands or is dismissed `done`, following each `dup` to the task it merged into; when its `landed` row names a `patch:`, it clears only once each path that patch touches is committed, because a new card session starts from the branch's last commit. A path counts as committed when it matches `HEAD` in the project's checkout, untracked files counting as uncommitted, or when a commit made after the `landed` row touched it, since that commit holds the landed work and any difference left is a later edit. `run:<plan path>` clears when that plan's `Status:` says it landed, such as `done` or `executed`. A task or plan that closes any other way, such as superseded or cancelled, and a task wait that loops back to the task through the waits of offered tasks, leave the wait stuck, and `chips` asks for an `updated` row. A started task's waits no longer count. A task that needs the current run's result waits on `run:` with the run's plan, and a wait never goes in the title or the why;
    - `owns: <check>, <check>` when the task fixes a check that fails on the base branch, such as `ci:check`;
    - `priority: P0`, `P1`, `P2` or `P3`, required unless the task owns a check, with the evidence Priority asks of a P0 or P1 claim: `repro: <failing test, or exact steps someone ran and saw fail, such as a reporter or a tester>`, `regressed: <commit>` or `ship: <item id>`;
    - `via: verdict`, `via: babysit`, `via: time`, `via: hook` or `via: panel`, required on a P2 or P3 offer, naming the route that lets the run offer it, as above;
    - `review-scope: <id>` and `regression: <url>, <url>`, where Milestone asks for them;
    - `session: <id>`, the id of the session that offers the task, where the runtime's session tool gives one, as Owner says, and `session: none` on an offer for a finding outside the run's domain, as Offer says; beside `card:`, that session also holds the card. `append` adds `transcript: <id>`, the id of the writing session's transcript file, when it can read it.
  - **Owner.** Each task except a ship-list task belongs to one session, its owner: the session its offer names in `session:`, or, for an offer that names no session or names `session: none`, the first session that carded it. A card session's offer names its own session, like any other offer, and its Close cards it, as Landing says. `/chips` in a session cards only the tasks that session owns, because the owner wants each session's chips to stay in that session (owner's word, 2026-10-17). A task that serves a ship-list item, one with `ship:`, belongs to no session, and neither its card nor an `updated` row's `session:` gives it an owner (owner's word, 2026-10-20). Only `/chips all` cards it once it is Ready, because a session's plain `/chips` cards only its own tasks (owner's word, 2026-10-24). The Close of a run that offered it for its own finding in its domain cards it too, and one offered for a finding outside the domain names `session: none`, so only `/chips all` cards it. A sweep runs no Close, so a ship-list task that a plain sweep's ledger pass offers waits for `/chips all`. Its offer names no `session:`. `chips --session <id>` lists the other open tasks under Other owners, and `append` refuses a `carded` row from a session that does not own the task. A session matches its tasks by its session id or by its transcript id, because switching the owner's Claude account can change the session id. `/chips all` covers the tasks no live session owns, such as those of a parent session the owner archived with work still open, and the ship-list tasks. It runs `chips all --session <id> --sessions <file>` with the session tool's list saved as in Cleanup. That board cards each Ready task no session owns, and the card makes this session the owner of each one that serves no ship-list item.
