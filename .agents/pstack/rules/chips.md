# Suggested tasks

This file says how the lead offers, records and cleans up suggested tasks. A session a card started works from its brief instead, because `chips brief` prints every rule its own task's rows need. It reads this file only to offer or drop another task. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Suggested tasks.** Every runtime follows this rule. A suggested task is side work outside the run's target, or a measurement the block's Time budget rule sends there, that the owner can start in a new session, and the ledger is where the project tracks it, in place of an issue tracker. A finding that pivots the run never becomes one, as the Autopilot rule says. Two of them may write the same project files at once, because each works in its own worktree and lands through land.mjs, as Landing says. Every session, the lead's included, works in its own worktree, so the main checkout holds the only live ledger, in the plans directory's `artifacts/`, which git ignores. `decisions-check.mjs` switches to it for `chips` and for an `append` to the ledger's own path, and reads it for each `base-red:` token, so a session runs every ledger command as written from its own worktree. Agents write in the main checkout only under the plans directory's `artifacts/`, which holds the ledger and the run directories, as `.agents/pstack/rules/land.md` says. No commit on `next` holds the ledger, so starting a session never commits there. Each run of `setup.mjs`, which every session's SessionStart hook and every sweep start, keeps the ledger in step with `refs/pstack/ledger` on origin, so its rows stay durable and shared between clones. The file gains the rows only the ref holds, and the ref gains the rows only the file holds, pushed as a fast-forward. Then it fast-forwards the main checkout. The ledger's former path, `<plans>/suggested-tasks.decisions.tsv`, is a tracked link to it, so helpers that predate the move write the same file. When a plain file is there instead, `setup.mjs` moves its rows into the ledger. A `run:` wait reads its plan from `origin/next` as last fetched, and a plan that only a worktree holds has not landed. The sweep starts with `node .agents/pstack/setup.mjs` run in the main checkout, which fast-forwards it when no local edit is in the way, because the board reads paths there. No path keeps two tasks apart, another repository's file included, because the owner dropped that wait for trunk delivery (owner's word, 2026-10-18). A session that finds such a file changed under it redoes its change on the newer copy.
  - **Ledger.** A task lives as rows in the project's ledger `<plans>/artifacts/suggested-tasks.decisions.tsv`, under one id it keeps for good, because a task outlives the run that offered it and every card that showed it. A card in a suggest tool, such as Claude Code desktop's `spawn_task` or `start_session`, is only a view of a task. The lead queues and appends ledger rows like any other decision-log row, with phase `chip`, and never in a run's own log.
    - The decision is `<task id> <title>`, repeated unchanged on every later row. A new task takes its id from `node .agents/pstack/decisions-check.mjs chips id`. The card's own id goes in a `card:` token, never in the decision.
    - `node .agents/pstack/decisions-check.mjs chips` prints every open task as Ready, Started, Waiting or Unmigrated, with what each waits on and the checks it owns, Ready and Waiting tasks in priority order, with P2, P3 and untagged tasks shown only as counts unless `chips all`, then the tasks a dropped card closed as `gone`, the topics with more than one task or a design question, and a Do list. The Do list shows one pass at a time, withdrawals, then ledger rows, then cards, with check items beside it, and `chips` exits 1 when any pass, shown or not, holds a problem: a card on a task that cannot start, a wait that can never clear, or two open design questions in one topic. `chips` leaves a malformed wait on a task with no topic to that task's migration. `chips --fetch` first runs `git fetch --all`, which refreshes the remote branches that PR waits read. `chips --session <id>` names this session, so the Do list asks to check each card another session holds; without it, every card counts as this session's. `chips brief <id>` prints the prompt a card for that task carries, with a `State:` line that says whether the board has it Ready, Started, Waiting and on what, or Unmigrated, whatever its priority; for a task merged into an offered task that has no card, or one an older helper replaced with such a task, it prints that task's brief, and otherwise, as for a closed task, it says there is nothing to start. The board also tells a session a card started to work from `chips brief`, which reaches a card whose prompt predates that instruction.
  - **Title.** The title is an imperative phrase. It ends in ` (xhigh)` only for a design question, which is a `kind: decide` task, or for a bug or slowness whose cause nobody has located yet. Every other task has a plain title and runs at `high`. That includes a hard fix whose finding names the cause and where it lives, because the session that found the cause already did that judgment. A design question stays at `xhigh` through its build. The title keeps `(xhigh)` whatever `maxEffort` allows, so the owner sees the recommendation. No title says when the task can start, because `chips` works that out on every read; `append` refuses a new offer whose title says `Now:` or `After:`, starts with a priority such as `[P1]`, or ends in `(high)` or `(fast)`, because `chips brief` prints the priority that Priority gives the task.
    - **Fast.** An offer or `updated` row takes `fast: yes` for a fix at `high` effort that names its exact change and a check that fails today, and changes no public call. The lead judges those conditions. `append` refuses `fast: yes` only on a design question, a review task or a task whose title shows ` (xhigh)`. `fast: no` drops the mark. A task is fast while it carries `fast: yes`, is a `kind: fix` task and its title shows no ` (xhigh)`, so a fold or dup that raises it drops the mark. The brief's title and the board line add ` (fast)`, and the brief says the owner's start of its card, or their "start <id>", is the word fast for its session, as the Fast rule says.
    - When the suggest tool has an effort setting, such as `start_session`'s `effort` for a task that starts fresh, the card sets it, and so does the lead when it starts a task on "start <id>", because a session started without one runs at the lead's own effort. It passes the `Effort:` level that `chips brief` prints. That level is `xhigh` for a design question. Otherwise it is the task's last `effort:` token, or, when it has none, `xhigh` for a title that ends in ` (xhigh)` or a task that covers one, and `high` for the rest. The project's `maxEffort` in `.agents/pstack.json` caps it when it sets one. The brief's title, and the task's line on the `chips` board, end in ` (xhigh)` exactly when that level is `xhigh` before the `maxEffort` cap, as the Title rule says, so an `updated` row with `effort: high` drops a stored tag from both, while later rows still repeat the stored decision. A `dismissed dup` that brings in an `xhigh` task raises the task it keeps. When the suggest tool has no effort setting, the card session starts at the lead's own effort. An `updated` row that changes a carded task's effort leaves its card at the old level, so `chips` lists that card in the withdrawal pass of the session that holds it, and once that session logs `uncarded`, its card pass offers the task again at the new level. A card session the owner already started keeps its effort, which is the owner's to change. No session can lower its own effort, so a card session that the session tool shows above its brief's level tells the owner in its first reply. A board line names the effort only where `maxEffort` lowers it. When the tool refuses that level, such as one above the lead's own, the card passes the nearest level the tool takes. The owner can raise the setting on the card.
  - **Priority.** Each open task has a priority, so the board puts the work a release needs first instead of listing every task in the order it was filed (owner's word, 2026-10-19). The agent that offers a task judges it, and `append` checks its evidence:
    - `P0` is broken now: a task that owns a check failing on the base branch, which `chips` counts as P0 whatever its token says; a regression, with `regressed: <commit>` naming the commit that broke it; or a major bug, such as data loss, peers that diverge, or a throw or stuck state in a public call, with `repro: <failing test or exact steps>`.
    - `P1` is work a release needs: the open items of the project's ship list, the design questions they wait on and the builds of the designs they settle, each with `ship: <item id>`, and user-visible bugs with `repro:`.
    - `P2` is product work that blocks nothing: refactors, performance that breaks no budget, design questions no ship item waits on, and edge cases with no repro.
    - `P3` is workflow, agent tooling and measurements.
    - A task shows the more urgent of its own priority and the priority of each offered task that waits on it through `task:`, directly or through other offered tasks' waits, because the waiting task cannot start until it lands (owner's word, 2026-10-20). A started task's waits no longer count, so it raises nothing. `chips` uses that priority on the board, where the task's line adds `blocks <id>`, in the stale report and in the brief, so the card's title carries it too. The task's `priority:` token keeps its own priority, which a sweep judges, and the task shows it again once no waiting task is more urgent.
    - `append` refuses a new offer with no priority and no owned check, a P0 claim with no `owns:`, `regressed:` or `repro:`, a P1 claim with no `owns:`, `repro:` or `ship:`, a `regressed:` that names no commit and a `ship:` that names no open item. A task with no `priority:` token and no owned check gets no card until a sweep tags it, even when a waiting task raises it, and each full sweep judges every task's priority again from the stale report, which prints it.
    - A project names its ship list command in `.agents/pstack.json` as `"chips": { "ship": [<argv>] }`. The command prints a JSON array of the open items a release needs, each `{ "id", "title", "finding", "writes", "topic", "kind", "waits" }`, where `waits` lists the waits a task that serves the item starts with, such as `run:<plan>` for a plan already working on it. `chips` orders P1 tasks like every other priority, and its ledger pass offers a P1 task with those waits for each item no open task serves. A project with no such command has no ship list, and its P1 tasks are bugs with a repro.
  - **Offer.** Run `chips` before offering. When the finding belongs to the question an offered task's topic names and that task holds no card, log it as a `folded` row on that task instead of offering a new task. The row lists what the finding adds in `writes:`, `waits:` and `owns:`. It carries `kind: decide` when the finding is a design question, or only `effort: xhigh` when the finding shows a bug or slowness whose cause nobody has located. When it belongs to the question of a started task or of a task that holds a card, offer a new task in that topic that waits on it with `task:`, because a started session keeps its own plan and a card cannot show new work; `chips` merges it into the carded task once that card is withdrawn. Otherwise the offer's evidence holds these tokens, each `key: value`, named once and separated by semicolons, and its result is `offered`:
    - `writes: <path>, <path>`, required, each a repository path or directory, or an absolute path in another checkout, with no whitespace, glob, quote, comma or semicolon;
    - `topic: <name>`, required, one lowercase kebab-case name for the owner question, such as `plite-landing`, never an area such as `core` or `pstack`; reuse a topic `chips` lists when the finding belongs to its question;
    - `kind: decide` when the task settles a design question before any fix, `kind: review` for a review task, as Review says, and nothing or `kind: fix` otherwise; a topic holds at most one offered `decide` task that waits on no task of its topic, and while its design question is started or holds a card, a new one on that topic waits on it with `task:`;
    - `waits: <wait>, <wait>`, one for each thing the task needs first, never the task itself. `pr:<number>` clears when a commit subject starts `Merge pull request #<number> from` or ends in `(#<number>)`. `chips` reads those subjects on `refs/remotes/<remote>/<branch>` as last fetched, for each remote `git remote` lists, where `<branch>` is the `branch` in `.agents/pstack.json`. With no `branch` there, any remote branch counts. A PR that was closed or rebase-merged never clears it, so the lead logs `updated` with the waits the task has now. `task:<id>` clears when that task lands or is dismissed `done`, following each `dup` to the task it merged into; when its `landed` row names a `patch:`, it clears only once each path that patch touches is committed, because a new card session starts from the branch's last commit. A path counts as committed when it matches `HEAD` in the project's checkout, untracked files counting as uncommitted, or when a commit made after the `landed` row touched it, since that commit holds the landed work and any difference left is a later edit. `run:<plan path>` clears when that plan's `Status:` says it landed, such as `done` or `executed`. A task or plan that closes any other way, such as superseded or cancelled, and a task wait that loops back to the task through the waits of offered tasks, leave the wait stuck, and `chips` asks for an `updated` row. A started task's waits no longer count. A task that needs the current run's result waits on `run:` with the run's plan, and a wait never goes in the title or the why;
    - `owns: <check>, <check>` when the task fixes a check that fails on the base branch, such as `ci:check`;
    - `priority: P0`, `P1`, `P2` or `P3`, required unless the task owns a check, with the evidence Priority asks of a P0 or P1 claim: `repro: <failing test or exact steps>`, `regressed: <commit>` or `ship: <item id>`;
    - `session: <id>`, the id of the session that offers the task, where the runtime's session tool gives one, as Owner says; beside `card:`, that session also holds the card. `append` adds `transcript: <id>`, the id of the writing session's transcript file, when it can read it.
  - **Owner.** Each task except a ship-list task belongs to one session, its owner: the session its offer names in `session:`, or, for an offer that names none, the first session that carded it. A card session's offer for friction it could not fix names the lead's session, as Landing says, and the transcript id `append` stamps beside it is the card session's, which never cards it, because a card session runs no sweep. `/chips` in a session cards only the tasks that session owns, because the owner wants each session's chips to stay in that session (owner's word, 2026-10-17). A task that serves a ship-list item, one with `ship:`, belongs to no session, so any session's `/chips` cards it once it is Ready, and neither its card nor an `updated` row's `session:` gives it an owner (owner's word, 2026-10-20). Its offer names no `session:`. `chips --session <id>` lists the other open tasks under Other owners, and `append` refuses a `carded` row from a session that does not own the task. A session matches its tasks by its session id or by its transcript id, because switching the owner's Claude account can change the session id. `/chips all` covers the tasks no live session owns, such as those of a parent session the owner archived with work still open. It runs `chips all --session <id> --sessions <file>` with the session tool's list saved as in Cleanup. That board cards each Ready task no session owns, and the card makes this session its owner. Its ledger pass lists each task whose owner session the list shows archived or does not list, and the lead logs `updated` with `session: <its id>` on each to take it. A task whose card another session holds stays with that session until a sweep logs `uncarded`.
  - **Cards.** Only a task that `chips` lists as Ready before its card gets one. A task is Ready when it has a topic and each of its waits has cleared. A shared project path holds no task back, because a card session works in its own worktree and redoes its change on the newer file when it clashes, as Landing says; only a real dependency makes it wait. The board's Ready line names each open task that shares one, and before each card the lead judges whether the task needs the result of another open task, those first, or of an open design question its work builds on, such as a title-slot answer a table-of-contents task reads. When it does, the lead logs `updated` with its waits plus `task:<that id>` instead of the card. A full sweep judges the same way each task that already holds a card and shares paths, because someone may have carded it before anyone judged its dependencies. A carded task takes the wait that judgment adds. Before each card, and in a full sweep for each task that already holds one, the lead checks the effort `chips brief` prints against the Title rule and logs `updated` with the right `effort:` when they differ, which a carded task takes. The card's prompt is what `chips brief <id>` prints, verbatim, which leads with the task and ends by telling its session to print the current brief, so the session works from the task as it stands when it starts. The card's title is the brief's first line, which starts with the task's priority in brackets, such as `[P0]`, so the owner's queue shows how urgent each card is (owner's word, 2026-10-19). A card keeps its title when the task's priority changes later, because its session prints the current brief first. When the suggest tool limits a title's length, such as `start_session`'s 60 characters, the lead shortens only the words between the priority and any ` (xhigh)` or ` (fast)` tag. A session the lead starts on "start <id>" takes the same title. The card pass lists at most 10 cards minus the ones this session already holds, highest priority first, so the owner's queue shows the most urgent work (owner's word, 2026-10-19). The lead offers every card the pass lists in one turn and lists each Ready task that limit left uncarded by id and title, with `start <id>`. The owner's "start <id>" starts that task as a new session whose prompt is its brief, with no card, once the lead has judged its dependencies and effort as it does before a card; when the task needs another task's result, the lead logs `updated` with its waits plus `task:<that id>` instead and tells the owner what it waits on. The next sweep cards the rest. After each card it logs `carded` with `card: <tool id>` and `session: <id>`. The session id is the one the runtime's session tool gives this session, such as Claude Code desktop's `get_session` with `self`, because a card goes away with the session that offered it.
    - **Quiet sessions.** The card, and the session the owner's "start <id>" opens, starts in its own worktree, which the lead asks for explicitly, such as `start_session`'s `use_worktree: true`, because the tool's default shares the lead's folder when the lead itself did not start in a worktree. A session that shares the lead's folder edits the lead's branch and cannot be detached. A session still linked to the lead wakes it each time that session ends a turn, and each wake re-reads the lead's whole context, so the task's brief has its session detach itself from the lead's as its first step, as the block's Calls rule says. When a note from such a session still reaches the lead, the lead detaches that session itself, such as with Claude Code desktop's `detach_session`, in the same message as its reply. The task's session sends the lead no message, because a suggested task is side work the lead's run never waits on (owner's word, 2026-10-21). Its ledger rows, its session title and its last report carry its outcome, and the next sweep's Cleanup reads that report and settles its question, as the `chips` skill's Sweep step 6 settles one. A question only the lead could answer does not stop it; it takes the most reversible answer, as the Autopilot rule says, and its report names that pick. When the runtime refuses or lacks the detach, the session stays linked and still wakes the lead at each turn end, which no rule here can stop. The lead then answers such a note only when it reports a landing, a PR or a stop only the owner can settle, in one line, starts no sweep for it and goes on with any work in progress. That line is not a hand-back, even when the note says every linked session has gone idle.
    - When a card leaves the queue without the owner starting or dismissing it, such as when a newer card pushes it out or its session ends, the lead logs `uncarded` with its `card:`, and the task stays open; `chips` lists it as Ready or Waiting again by the test above. Limits says how the lead tells those cases apart. For a card whose session ended, a later session's sweep logs it, as Sweep says. A task that holds a card takes no `folded` row, no `dismissed dup` into it and no `updated` row, except one that only narrows its `writes:` to paths inside the ones it lists, only adds waits and keeps every wait it has, or only sets its effort or its priority with that priority's evidence, which changes no work, so its card always shows the whole task. A wait added that way makes the task wait, so the withdrawal pass pulls a card this session holds. A card another session holds keeps its prompt, whose board check tells its session to stop and say what the task waits on; a session the owner already started keeps running, and the lead tells the owner which dependency it started without. When the dismiss tool or the owner says the owner dismissed the card, the lead logs `dismissed declined` with its `card:`, which closes the task as its card showed it. A task that waited on it then has a stuck wait. Once the lead drops that wait, the task gets its own card, because the owner never saw its work. Before any other dismissal of an offered task whose card this session holds, the lead first withdraws the card as Limits says. When the owner says to drop such a task, the lead withdraws the card and logs `dismissed declined` with its `card:` in place of `uncarded`, so no merge lands between the two rows. When the tool reports the owner started it, the lead logs `started` instead. A started task closes with `landed` or `dismissed stopped` and needs no withdrawal.
  - **Later rows.** A later row's result is one of these, and it takes only the tokens named here:
    - `started`, with `writes:` for any path it adds and `session:` naming the session that runs the task, where the runtime's session tool gives that id. The session a card started logs it before it writes, and the lead logs it when the dismiss tool reports that the owner already started the task, or when the owner says so;
    - `landed` when a commit holds the change, the started session applied its patch to the checkout as Landing says or reports it delivered the change as the Delivery rule says, or the owner says so, with `patch:` naming the patch the session applied when it applied one and `commit:` naming each commit that delivered it, which `append` refuses unless each resolves to a commit in the checkout; a half-written change in the tree, or a patch nobody applied, does not count;
    - `reviewed` on a landed task, logged by the review task's session for each task it reviewed, as Review says;
    - `updated`, on an offered task with no card, or on one that has a card only to narrow its `writes:`, add to its `waits:` or set its `effort:`, `priority:` and their evidence, when its paths, topic, kind, effort, priority, evidence, waits, owned checks, fast mark or owner change, and on a started task only for its owned checks; `effort:` takes `high` or `xhigh`, while a `folded` row takes only `effort: xhigh`; the row names only the tokens that change, and each replaces that token's whole list;
    - `folded` on an offered task with no card, with `writes:`, `waits:` and `owns:` that join the task's own, `kind: decide`, which makes it a design question, `effort: xhigh`, and `priority:` with its evidence, which raises the task's priority and never lowers it; `carded` with `card:` and `session:`; or `uncarded` with `card:`, as Offer and Cards say;
    - `reopened` for a task that an older ledger closed as `gone` when its card left the queue, while its work is still owed;
    - `dismissed` with one reason: `done` when the tree already holds the fix of a task nobody started; `dup <task id>` when another offered task covers a task nobody started; `superseded` when the run removed the target of a task nobody started; `declined`, with the task's `card:` when it holds one, when the owner dismissed its card or said to drop it; or `stopped` when a started task's session ended before its change landed. That holds when the session tool reports the session archived, no commit holds the change, its last report neither says it delivered the change nor hands back a patch, and neither this checkout nor the session's own worktree holds an uncommitted edit on the task's paths. It also holds when the owner says they stopped the task or says to drop it. After a `dup`, the kept task keeps its own title, lists the duplicate's title and findings under Also covers in `chips brief`, and takes its paths and owned checks. It also takes the duplicate's waits, except each wait that leads back to it through dup rows, and becomes `decide` when the duplicate was one. A dup that an older helper logged into a started task listed only the duplicate's title and findings under Also covers and took its owned checks.
  - **Checks.** `decisions-check.mjs` judges each chip row against the rows before it, in `append` and in the whole-log check, which skips rows committed at `HEAD`. It refuses each row the rules above forbid, and each refusal names its route; follow it. Only `append` judges a rule older ledgers predate or a state that can change after the row is written, such as the paths on disk, a plan's status or which task holds a card.
  - **Sweep.** The lead runs `chips` before it offers a task. It runs the sweep below only on `/chips` (owner's word, 2026-10-20). Every other run cards only its own offers, at its last hand-back, as Close says. A ledger pass holds at most one merge. `chips` prints it for a task that waits on a task of its own topic once neither holds a card, and only when `append` would take the row. The pass leaves every other item on those two tasks to the next pass, which sees what the merge moved. The lead applies the Do list's pass and the steps below in one `append --from` batch, runs `chips` again, and repeats until the Do list holds no item it can apply:
    - **Cleanup.** Before the passes below, the lead cleans up after each landed task's card session, because the owner said archiving it is fine (owner's word, 2026-10-16). It saves the session tool's list of every session, archived ones included, as a JSON array in the run directory and runs `node .agents/pstack/decisions-check.mjs chips cleanup --sessions <file> --session <id>`. For each session listed under Archive, it first reads that session's last report with the session tool and fixes each piece of workflow friction the report leaves unsettled, as Landing says. It then archives each session listed under Archive, saves the list again, runs `chips cleanup` once more and runs the `scan.mjs --remove` command it prints under Remove. That command stops each process working in a worktree, saves the worktree's uncommitted changes as a patch under the git folder's `cleanup/` and removes it without judging it, because its task landed. `chips cleanup` lists only a session whose worktree sits under `.claude/worktrees`, never one that is running or pinned, and never this session. The sweep's report opens with the first run's Report lines, one per task with its commit links, so the owner reads what landed without opening its session. A runtime without a session tool skips this step.
    - When the tree already holds an offered task's fix, the lead logs `dismissed done`. When a started task's change has landed, it logs `landed`. When the run removed a task's target, it logs `dismissed superseded`.
    - When open tasks nobody started answer one question, the lead keeps the earliest design question among them, or the earliest task when none is one, and logs each other one `dismissed dup <kept id>`, first logging `updated` with the kept task's topic on one whose topic differs, unless both are design questions. A dup never goes into a started task, because its session keeps its own plan, or into a task that holds a card; the duplicate waits on it with `task:` instead, and `chips` merges it into a carded one once the card is withdrawn. A task whose work a started task covers waits on it with `task:`, and the lead logs it `dismissed done` once that task lands with the fix.
    - Where the runtime's session tool gives this session's id, the lead runs `chips --session <id>` with it. For each card the Do list says another session holds, it looks that session up with the session tool and logs `uncarded` with its `card:` when the tool reports it archived or gone. For each started task, it looks up the session its `started` rows name. When they name none, it finds that session with the tool, archived sessions included: its transcript opens with the task's card prompt, and a session that only printed the board does not count. The lead then logs `started` with its `session:`. When the tool reports that session archived, the lead logs `landed` with `commit:` once a commit on `origin/next` holds the change, because a session whose land.mjs opened a PR has not landed it yet. It logs `dismissed stopped` when no such commit holds it and the session's own worktree is gone or holds no edit on the task's paths. Otherwise, and while the session is not archived or the tool cannot find it, the task stays started. The sweep's report says why, and that the owner's "drop <task id>" closes it. The lead never asks the owner whether a session still runs. A runtime without a session tool logs `uncarded` with its `card:` for a card on the owner's word that its session ended, and `dismissed stopped` for a started task on the owner's word that they stopped it.
    - For each task `chips` lists as Lost, which a dropped card closed as `gone`, the lead logs `reopened`, then `updated` with its topic and waits, or, when its work is already done or its target gone, `dismissed done` or `dismissed superseded` after the reopen.
    - Before the run writes a path an offered task writes, the lead judges whether that task needs the run's result first. When it does, the lead logs `updated` on that task with its waits plus `run:<the run's plan>`, which a carded task takes too; when the withdrawal tool then reports the owner started it, the next bullet applies.
    - A path a started task writes needs nothing before the run writes it, because that session lands on top, as Landing says. The lead runs the check above whenever the run is about to widen what it writes, not only at a sweep.
    - A session started from a task finds its own row by the id in its brief and skips it in these checks.
