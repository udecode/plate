# Panel review and Review

This file says how a panel, `architect` or arena runs, and how a panel reviews a diff. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Panel review.** A plan goes on to its build, as the Autopilot rule says. The lead writes a plan whose panel runs and runs that panel before its first behavior edit; an owner's go on a proposal made in conversation approves the direction, never a skip of that plan or its panel. A diff whose panel runs gets it after the writing passes and before land.mjs lands it. The lead writes the filled prompt once to a file in the run directory, and every seat reads that file. The prompt names run-directory files by their absolute paths in the main checkout, because the run directory is ignored and a seat's worktree holds no copy. A seat reads every path the prompt names, the decision log included, and every repository its probes can scan. The lead runs probes and new tests in a separate copy. Until every reviewing subagent has answered or failed, comment-sicko included, the lead edits none of the files that subagent reads; it queues new decision rows in the run directory until then, logs any slip as a row, and then synthesizes once. The intent quotes the user's typed asks verbatim and names the invariants to attack, never the author's conclusion that they hold. Every brief, an `architect` or arena brief included, tags each invariant and outcome by its source: the user's typed ask, a cited law line or the lead's own conclusion. It lists the lead's own conclusions as premises for the seats to attack. It lists each outcome the user's typed ask states and each property it gives a mechanism it asks the run to change or settle, with that mechanism, as an `[ask]` invariant in the ask's own words, and a later round's brief never narrows one. A later round's brief also lists each earlier critical finding the lead dismissed or left `open`, with the lead's reason, as a premise to attack. Interrogate ranks no findings, so the brief asks each seat to tag each one `critical`, `warning` or `nit`. For a review-only panel, on work this run does not change such as another person's PR, the lead returns the findings in the reply and keeps no plan, page or decision log, whatever Plans and trails or Plan pages would otherwise ask. Each round logs decision-log rows under phase `panel`. Once every seat has answered or failed, the round opens with one row whose decision is `seats` followed by each seat as `<model> @<effort>`, copied from the `seat:` line `seats.mjs` printed for it, with `missing` after a seat that failed. Its evidence names the reviewed tree as a commit or a saved patch, and every before-fix reproduction for that round runs on that tree. Each critical finding then gets its own row whose decision opens `critical [<seat>, ...]:`. The brackets name each seat that raised the issue at any severity, as the round's `seats` row names it, or `lead` when only the lead raised it, so `scorecard.mjs` can count what each seat caught. The brackets never name a seat the `seats` row marks `missing`. The row's result starts with `applied`, `dismissed` or `open` and gives the lead's reason. The round's warnings and nits share one row whose decision starts with `warning` and lists each one with the seats that raised it and its outcome, each deferred one with its `owner:` and `stop:`; its result starts with `applied` when any was applied, otherwise `deferred` when any was deferred, otherwise `dismissed`. Before it logs a confirmed finding, the lead matches it against the rule-only rows of the rules table that `/pstack:correct` keeps. A match is a repeat of that rule, so the lead adds a todo to run `/pstack:correct` on its class before the close. A `dismissed` result that cites a mechanism names where that mechanism stops the seat's case, traced hop by hop with file and line from the caller the seat names. A critical finding's dismissal also names a mutation that removes exactly that mechanism, and the test, or the logged runtime run where no test can reach it, that then fails on the seat's case; a warning's or nit's dismissal needs that mutation only when the trace does not reach the seat's case. A critical finding dismissed because the seat's case did not reproduce counts only once the same probe fails with the seat's mechanism planted, because a probe that cannot see the defect also reports no reproduction, and its row cites that failing run. The lead appends a finding's row only after the work its result claims has run: for `applied`, its fix and its reproduction; for `dismissed`, the proof above; for `open`, what the rule that leaves it open asks for first, such as the seat's case on the base and the edits that state each limit, or the new plan a pivot names. It appends a summary row only once each finding it lists is settled, and an `applied` result names the test or path that applies it; until then the finding waits in the todo list. The lead weighs each finding against the user's ask and applies only what the ask needs, because every fix is new unreviewed code; a critical finding follows the apply-or-open rule below instead. It weighs a critical finding by how often real use reaches it and by its worst outcome, so a rare path with a recoverable outcome may be dismissed with that reason, and a miss on a common flow may not. Before dismissing a critical finding as rare, the lead runs the seat's exact case through the real code on the repository's fixtures, and cites a count of the finding's trigger condition from the most real data the project lets the run read without a stop, naming that environment, the count and when the query ran. A count from fixture-only data supports a rare call only as inferred, and a critical finding whose rarity rests only on an inferred count is not dismissed as rare. The rule grants no new access. After any change the run makes to the same limit or configuration, the lead runs that query again, and a higher count reopens the dismissal. A critical finding about a wrong value written into a clinical, legal or financial record is never dismissed or narrowed on a reviewer's check of text that the same faulty step produced, and it counts as fixed only when the seat's named consumer and harm reproduce as gone. A warning or nit outside the ask is `deferred` with its `owner:`, and a critical finding is applied, dismissed or `open`, never deferred. The lead dismisses a critical finding only on the proof above that its case is no defect or is rare, never because it lies outside the ask or predates the run. A no-defect dismissal may, in place of the trace and mutation, quote a law line that requires the seat's case to behave as it does. That line is older than the run or one the verbatim ask has the run write, and the dismissal shows that the case meets every outcome the user's typed ask states. A line that only permits the behavior never excuses a case that worked on the run's base and fails after its change. The user's typed ask includes, verbatim, the task text of the card or brief that started the session. A finding's age says who caused it, not whether the ask needs it fixed. The lead applies a critical finding, or pivots the run to it as the Autopilot rule says, unless all three of these hold. First, the seat's own case, with its values, path and consumer, fails the same way on the run's base commit. Neither this run's change nor its plan causes it, worsens it or increases exposure to it, such as through a new flow, a default, a frequency or more traffic. A case that cannot run on the base because it needs a flow the run adds fails this condition, and a nearby case the base can run never stands in for it. Second, it breaks no outcome the user's typed ask states and no property the ask gives a mechanism it asks the run to build, change, fix or settle, even one phrased as how that mechanism works today; a file or function the ask names only to point at the work states neither. Third, it shows no requirement of this run's own design unmet in the Autopilot rule's sense, such as a budget the plan froze or a cost of the adopted design that only a new owner or stored shape removes, whether or not the plan lists it; a law line, doc sentence or claim the finding makes false is a line it limits, not such a requirement. The lead judges this against the verbatim ask, never against a brief's tags or paraphrase. A pivot writes a new plan iteration with its own decision log, whose rounds count from zero. The old log logs the finding `open` with `patch:` the new plan's path, `owner:` the owner, `stop:` its build and `proof: none`, and the new log's first row after its `lead` row cites that row; the new plan's first brief lists the old log's dismissed and `open` critical findings as a later round's would. A critical finding for which all three hold stays `open`. Before the first diff round, the lead reruns its case on the built tree, and one that now fails a condition follows the apply rule. Its result gives `patch: none`, `owner:`, `stop:` and each line it limits, and its evidence gives `proof: none` and cites the base run. The lines it limits are each law line, doc sentence or claim the finding makes false. The lead finds them by searching the project's law files, its docs and this run's text for the finding's predicate and its paraphrases. In the same change, each of them states that limit, and each in a law file or plan also names the owner; a public docs page states the limit only. The task or tracked item that owns the fix names each line to restore once the fix lands. A line in a file this run cannot change goes under the page's Open work with its file, owner and stop. The finding's Defaults row states what the fix would cost in this run and names the word that pivots the run into it. The lead rates it `look`, and `answer` once a later round or the decision-trail review raises a finding on the same mechanism and case again, in any wording, because the lead's reading of the ask is then disputed, which leaves the call no clear pick. The pick stays `open`, the more reversible option, since the limit is stated and the word still pivots the run. Only a finding that meets all three conditions gets this row and its `open` pick, however often it is raised. A dismissed critical finding raised again that way, whose dismissal the lead keeps on its proof, gets the same row rated `answer`, with the dismissal as its pick. A finished removal's later finding may also stay `open`, as the removal rule below says. The plan page counts the rounds and lists each one from these rows. Among rounds that review the fixes to a plan's or diff's findings, only a round with an applied critical finding earns another, and a re-review checks only what changed; a change made for another reason gets its own review, as the Review rule says. Whatever the rounds find, a plan gets at most three rounds before its build starts, and that build's diff at most three more. A row of the reviews list triggers only the tool and stage it names, so a row that names a panel on the diff does not by itself run `architect` or a panel on the plan; a pstack step's own trigger still runs them. A change the run makes to agent prose alone gets no panel, `architect` or arena, even where a pstack or project playbook step calls for one, unless the owner asks for one or a reviews-list row names agent instructions (owner's word, 2026-10-28). Agent prose is skills, rules, playbooks, `AGENTS.md` and workflow guides, the plans, decision logs and subject files that record a change to them, and what a sync or build writes from them, such as a workflow manifest, `.agents/pstack.json` or a synced copy of a helper. A plan or subject file for product work is not agent prose, so a plan that changes a public API still gets its reviews. A helper gets its review, or the owner's word to skip it, in its source repository, so a sync never reviews its copy again. A review-only panel on someone else's work still runs. A change confined to agent prose and the helpers, checks or hooks agents run, a helper alone included, gets one round, on its diff. Its fixes land without another round, even after a critical finding, unless that round raised three or more critical findings; then the fixes get one more round on their own diff, and that round's fixes land without another (owner's word, 2026-10-28). A round's fixes are not a build step. `decisions-check.mjs append` refuses a fourth `seats` row until one of two restarts. One is a `build` row whose decision starts with `built:` and names the files a plan's build changed, with a result that starts with applied, fixed, partial, proven, recorded or verified. The other is an `owner` row whose decision starts with `another round:` and quotes the owner asking for one. The helper checks only those prefixes and that result word. A log from before the cap whose completed build has no `built:` row adds one naming that build before its next round. Before it launches seats, the lead runs `decisions-check.mjs rounds <log>`, which exits 1 at the cap. At the cap the lead never hands back. It stops reviewing, settles each open finding as applied, dismissed on the proof above, deferred with its owner when it is not critical, or open with its `patch:`, `owner:`, `stop:` and `proof: none` when the rule above or the removal rule below lets it stay open, and states each remaining limit on the page. A critical finding the lead must apply, as above, is applied before the next gate or pivots the run; naming an unapplied patch does not settle it. A plan then builds, so later rounds read code that runs, and a diff moves on to its next gate; a plan-only or read-only request, or the owner's "stop at plan" or "hold", ends with the published page instead. Before a lessons panel, the lessons' edits get their own `built:` row naming the files they changed. When a seat names the producer of a bad case, the first fix changes that producer instead of adding a guard where the case is read. The replacement loop below applies only to a critical finding the lead must apply, as above. Any fix that replaced a mechanism's approach in a diff round of the current plan iteration, for whichever finding, is that mechanism's one replacement, and a new plan iteration starts that count again. When a round's critical finding is in code an earlier round's fix added and the mechanism has had no replacement, the next fix does not patch that fix again. It reverts the fix and narrows the claim with a report, except a claim about a wrong record value or an outcome the user's typed ask states, or replaces its approach, such as an inference with a value recorded where the change happens. When an earlier round's fix was a removal that no fix has finished yet, the mechanism has had no other replacement, and a later critical finding says the removal is incomplete, such as a cut made only in the types, finishing the removal at runtime replaces its approach, whichever code the finding names. The logged caller count first covers each public entry point the finish edits. A revert never restores an input that no non-test caller uses, placeholder values left out. When that finished removal draws another critical finding, even one that names another missed path, a claim about a wrong record value goes back to planning. A finding that names a live caller the lead verifies adds that caller to the logged count, and a count above zero sends the finish to the rule for any other mechanism below. Otherwise the lead keeps the removal instead of reverting it. When the finding is one the lead must apply, as above, it pivots the run; otherwise it narrows the claim with a report and logs the finding `open` with its `patch:`, `owner:`, `stop:` and `proof: none`. A new plan iteration rebuilds the input only when its caller count or the user's typed ask shows the goal needs it. When a later round's critical finding is against any other mechanism that already had its replacement, the mechanism leaves the loop: the lead reverts it to its code from before this plan iteration changed it, which removes it when that code lacked it, and narrows the claim with a report. That revert goes into the next diff round, and its `applied` row cites the seat's probe failing before it and the narrowed claim. When the user's goal still needs the mechanism, its owner goes back to planning, as a new plan iteration whose plan joins that round's packet and whose panel runs before any further fix to it. The lead decides whether the goal still needs an input by a logged count of its non-test callers, leaving out placeholder values. A mechanism the user's typed ask names is always needed. A claim about a wrong record value is never narrowed, and its mechanism always goes back to planning. A critical finding about real data counts as fixed only after the lead reruns the seat's own probe on that data; a mutation run on the lead's own fixtures is weaker proof, and a fix that rests only on one is logged `partial`. Before shipping, the lead reruns every seat probe the last round's fixes touch. A revert or a removal that resolves a critical finding counts as applying its fix. A plan the panel reviewed goes on to its build as a `look` default whose word is "hold". A panel whose models sheet names seats of one model family runs on them, and the page labels it same-family. The lead that changes a panel seat's model or effort, wherever it is set, such as a models sheet, `/setup-pstack` or a project rule like an effort override, runs `node .agents/pstack/replay.mjs --dir <run directory>` once, before any panel round runs on the new seat. It passes one `--seat` entry for each seat of the new panel and one for each replaced seat at its old model or effort, each naming its effort. The lead puts the replay's table on the page or in the reply. A case the new seat misses and the replaced seat caught is a `look` call, with a Defaults row that names the word reversing the change. When fewer than six cases come from fixes' `Introduced-by:` lines, the lead adds `--case` pairs it traced with `git log -L` or `git bisect`. `git blame` only names a suspect, which counts once the lead has read that commit's diff and the fix. Replay takes the mined cases first and fills the rest from `--case` pairs. When replay reports cases left past its limit, the lead offers the larger run as a suggested task, as the Time budget rule says. A seat or runner that cannot run on the model the models sheet names for it stops the run as blocked, whatever the cause, such as a usage limit or a lapsed subscription. The lead never replaces it with another model, the session's included (owner's word, 2026-10-18). The lead runs no separate check of a seat before its round. A seat cannot run when its run fails again after one rerun on that model; an `opus` seat may rerun as an `Agent` call on the same model and effort. The stop goes under Needs you with the seat's error and two options: fix the account, such as by renewing the plan or running `codex login`, or run `/setup-pstack` to put another model in its place in the sheet. The run resumes on the owner's word after either. When the fix is the user's, it never goes under other owners' work. Agreement counts once per model family among the seats or runners that raised a point, and the lead verifies each critical finding whatever that count. A pick that only one family's seats or runners reached, as in a same-family panel or a code arena, goes to the next panel with a seat of another family as an invariant to attack. A review-only panel has no rounds and logs no rows, so the apply, open, limit, pivot, round, row and page rules above do not apply to it. A project playbook that names `pstack:interrogate`, `pstack:arena` or `pstack:architect` cites the row it serves as `(reviews: <id>)` on the same line. To change the list, the user says so in plain words, such as "from now on best-api design runs architect", and the `sync-pstack` skill edits `reviews` in `.agents/pstack.json`, renders the pstack block again and verifies it. A seat named `codex:<model> @<effort>` runs `node .agents/pstack/cross.mjs --to codex --reach --model <model> --effort <effort> --timeout 1800 --prompt-file <file>`. It replaces the `Agent` call and the rejected-slug fallback the panel skill would use for that entry. An `opus` seat runs `node .agents/pstack/cross.mjs --to claude --timeout 1800 --prompt-file <file>` in both runtimes, adding `--effort <level>` when its models-sheet entry names one; without a level it runs at the project's `maxEffort`, or at Claude's default effort when the project sets none. `cross.mjs` runs no seat above `maxEffort`, and prints the model and effort it ran at on a `seat:` line on stderr. The lead starts a round's seats or read-only runners together in one background command, `node .agents/pstack/seats.mjs --dir <round directory> --prompt-file <file> <name>=<runtime>:<model>@<effort>...`, with `codex` for a `codex:` seat and `claude` for an `opus` seat, and gives that command a timeout longer than the seats' `--timeout`, so it outlives every seat. `seats.mjs` refuses a `--timeout` over 3,300 seconds, so that command still fits the Time budget's hour. It lets each `opus` seat read the main checkout, which a seat started from a worktree otherwise cannot, and `--read-dir <dir>` adds any other folder the brief cites, such as a transcript's. `seats.mjs` runs each seat as the commands above do, writes each answer to `<name>.md` and each failure and `seat:` line to `<name>.err`, and exits once every seat has answered or failed. One command per seat would wake the session once per seat, and each wake re-reads its whole context. A seat's rerun goes through `seats.mjs` with that seat alone, except that an `opus` seat may rerun as an `Agent` call, as the Panel review rule says. `cross.mjs` runs every seat it starts with hooks off and no write access to the project, so a project hook that stages files cannot write from a seat. With `--reach`, a Codex seat loads the user's Codex config, connectors, web search and network, but not exec rules, and writes only a scratch folder. It can search the web, query `gh` and clone upstream sources to check a claim. Its brief says to read and report, and never to post, comment or change anything outside that folder. The lead uses each answer verbatim, and a seat that `seats.mjs` reports failed reruns once on its model and then stops the run, as the Panel review rule says. When the skill expects a seat to write a file, such as an arena candidate's artifact, the seat returns the content and the lead writes it to that path. A code `arena` runs its slots on `opus`, because a `cross.mjs` seat cannot write. For the same reason a seat's brief asks only for read-only checks and an explicit "not run" for anything that writes, such as a test suite with temp files; the lead runs those itself and never counts them as the seat's. An arena or `architect` cross-judge reads copies of the candidates named `cand-1` to `cand-n`, in which each runner's model name is replaced by its label and nothing else changes, and the lead keeps the name map until scoring is done.
- **Review.** These mechanics apply whenever a panel runs on a diff, from the reviews list or the user's word. A row that names a kind of code judges it by what the code gates, not by what the diff touches, and a fix for an unintended write, invite or send counts as that write, invite or send, even when the diff only changes rendering. Review the worktree's diff against `origin/next`, with its uncommitted work, before land.mjs pushes it. Review a PR's branch diff against its base. Package the diff with each caller or entry-point file whose behavior the change can break, such as every wrapper of a changed shared primitive, and rebuild that list each round from what that round's delta can reach. A seat that says something cannot be verified leaves that concern unreviewed; add its files to the package or prove it at runtime before calling it fixed. Verify each critical finding, and the cause it states, against the code or the raw output before logging it, fix the real ones the Panel review rule does not leave `open`, rerun each fixed finding's own reproduction, such as the seat's probe or the interleaving that broke a race, so it fails before the fix and passes after, and rerun the review when a round applied a critical fix, as the Panel review rule says. When that reproduction is a test that already runs on the fixed code, the lead reverts the fix alone in a scratch copy and confirms that the test then fails with its assertion's own message. The reproduction keeps the seat's exact values, ordering and affected consumer, with inputs a shortcut fix would not pass by coincidence. A fix that adds a refusal or a guard also runs a must-still-accept case on the nearest legitimate flow before the next round. Each reproduction fails on its own, as its own test or an isolated run, because a grouped test proves only its first failing assertion. When a critical finding names a rule, fix every writer, reader and matcher of that rule together, and when the new code copies rules an existing function already applies, call that function instead. Treat every confirmed finding as one case of its class. Before patching, list each call site of the pattern and each context where its token means something, such as a mode, an escape or a position, and fix them together. When the class is a third-party grammar too large to list, narrow the claim to a lossless fallback with a report instead of copying more of the grammar. A type system counts as such a grammar, so a new check that reads types enters its first panel claiming only the forms its tests run. The way JavaScript looks up a property counts too, own or inherited, enumerable or not, through a getter or a proxy trap. A check on an options key therefore moves to a closed option set, or the wrapper passes the caller's object untouched to the one owner that reads the key, with no check of its own. Stop when no critical finding remains or every remaining one is dismissed on the Panel review rule's proof or left `open` as that rule allows; warnings and nits never block. A design that changes after its last interrogate or review for a reason other than that review's findings, including cuts the user approved, runs `/pstack:interrogate` again before its first behavior edit, or before it ships when it is already built, except a change confined to agent prose and the helpers, checks or hooks agents run, which gets only the panels the Panel review rule gives it; a fix to a round's findings earns another round only as the Panel review rule says. Every round counts toward that rule's cap, and a design that changes at the cap is reviewed in the diff panel after its build. An approval covers only what the user saw.
