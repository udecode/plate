# Plan pages

This file says which work gets a page, how a plan becomes one, what the page and the hand-back reply hold, and how calls become Defaults or Open questions. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Page work.** Only page work publishes a page, because the owner reads a page only for a new design (owner's word, 2026-11-20). Page work is an architecture or API adoption plan. It is also the verdict an `explore` run converges on, and a `radar` pass. Every other plan keeps its plan file and decision log, publishes nothing and hands back in its reply, as the Reply bullet says. Where a rule puts something on the page or under its Needs you, work without a page puts it in that reply. Work that keeps no plan hands back in its reply too, as the Plans and trails rule says.
- **Plan pages.** In Claude Code, every subject has one page, and every plan that continues it is an iteration on that page, never a page of its own. A plan takes the shape the `plan-page` skill describes, instead of the PR sections Multi-phase plan's step 3 lists. Load the `plan-page` skill before writing or changing a plan, a subject file in `docs/plans/topics/` or its page. It owns their file shapes, picking the subject, the delta and the fold, `node .agents/pstack/plan-page.mjs` and its refusals, publishing, and changes to the page shape; each project playbook names the review sections its plans write. The committed plan and subject files are the durable record, and the rendered page under the plans directory regenerates from them; a project's index of every subject stays local, and the published page is where the user comments on one hand-back. An agent reads a page from its rendered file or from its plan and subject files, never from the published page, because another account may own that page. The one exception is the read of `index.html` by path that a refused publish's `--base` needs. Only `page-stop.mjs` starts from the published page, and it takes only the page file's list of runs from it. Only a page whose work is still active is published again, apart from the close stop's publish after the last land. For page work, Codex sessions render the page, copy the printed file into the run directory, and reply with that copy's path and the plan it renders. Any later render on the subject, `--index` included, rewrites the printed file. When that work next hands back from Claude Code, the lead renders its plan again and publishes the page. For a call the owner would notice, other than one the Autopilot rule stops on, pick the recommended option, record it as a row of the plan's `## Defaults` table (the decision, the pick, the alternative, the word that reverses the pick and its impact, as the `plan-page` skill says), and keep going. An option that leaves the user's stated goal unmet is never a default, and research that overturns the premise of a question the user answered reopens it. Before asking the owner, or running `architect`, about how to build an integration, the lead checks what each product already ships for the job in its own docs and settings, and searches for prior art. An interview the owner asks for covers only outcomes the owner alone can judge, such as what the owner sees, which cost is acceptable and what counts as done. Only a call the Autopilot rule stops on, or a message that waits as a draft as the Messages rule says, goes under `## Open questions` and to the user through `AskUserQuestion` where the runtime allows it, otherwise in the reply, recommended option first; a page shows it under Needs you as a decision memo the user answers in their own words. "go" takes the recommended option of each question shown except a production deploy or release, which takes the user's own answer to that question, typed or picked in `AskUserQuestion`, because the Delivery rule asks for an explicit request; an answer in the user's own words picks exactly what it says, and neither authorizes anything else. An answered question leaves Open questions, as a Defaults row or a decision-log row that quotes the owner's answer verbatim when it arrives. Every stop that hands back page work publishes its page before the reply, or in Codex renders and copies it as above, at whichever of these the run hands back: a plan written, back from review, revised or built, a review verdict other than a review-only panel's, a playbook's close, a blocked run's ask, reflect's list awaiting approval and a subject file update. Between those stops the lead publishes nothing, and a Defaults row or a Needs you item it adds waits for the next stop's publish. In Claude Code every publish goes through `node .agents/pstack/page-stop.mjs stop <plan>`. The helper writes the page file, which lists every run, and this run's header and body under the plans directory's `artifacts/pages/<subject>/`, then prints the publish to send and every file in it. In the next message the lead reads each named file in full, in ranges when one read cannot hold it, and views each named picture. The printed publish then goes out with the next working call. A long call starts in the background, so a publish never waits behind it. The lead never sends a publish the helper did not print or the whole page the renderer prints. When the Artifact tool refuses the publish and returns the page's live version, such as when the session has not viewed it or the page changed, the lead runs the same command again with `--base <the source path the refusal saved>` and sends what it prints; when no file was saved, it reads the page's `index.html` by path first and passes that file. A subagent never publishes a page. A publish sends only the page file and this run's own files, so every other run's files stay. When the page does not open, because it was deleted or another account owns it, the lead runs the command again with `--new` without asking the owner, and follows the `plan-page` skill's Render step for a link that no longer opens. A publish that makes the page, or replaces a dead link, changes a `Page:` line after the last landing, so the lead lands that edit, and the Defaults row `page-stop.mjs` asks for when it replaces a link, right after the publish, as the project's delivery says, and publishes nothing again for it. The lead renders a page between stops only to check its own change. Topic page work renders the plan the stop is for, which leads its subject's page, and publishes to that page. The plan's `## Close` holds what a close used to report: what landed, the proof and its limits, reversals first, and open work with owners and stops; a pstack playbook's Reply line lists what else its Close holds.
- **Reply.** The reply that hands back page work names what landed in a sentence and ends with its link list: the link `stop` prints once its publish went through, 📄 and the page URL plus `#run-<plan slug>`, which lands on that plan's part of the page even after another run publishes, then the link of each commit the session landed for the request, as land.md's Review rule counts them. In Codex, the path of the page's copy takes the page link's place. When the user's reply language differs from the page's, that reply gives the Brief in the user's language next to the link. Any reply or report places and formats its page and commit links as writing.md's Links in replies rule says. After a review-only panel the findings also go in the reply, and a direct question from the owner gets its plain answer first. A direct question or a one-file edit answered in the conversation stays in chat, but an answer that discloses something about page work, such as a skipped gate or a design limit, also goes on that work's page. Leave out an empty part instead of announcing it. A Closing summary, in a reply long enough for writing.md to ask for one, still opens by naming what waits on the owner or saying that nothing does. The reply that hands back other work, planned or not, carries what a page would show, in this order:
  - What changed and why, in a few plain sentences in the `pstack:bro` voice.
  - Each public API change, as the call before and after.
  - The comparison the work made, such as a verdict's grade against other editors.
  - Each pick the owner would notice, with the word that reverses it.
  - What waits on the owner, and the limits of the proof.
  - The link list.
