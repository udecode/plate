# Browser drives

This file says how an agent's browser tools deliver input, draw frames and handle the clipboard, so a drive reaches the page as a person's keyboard and screen would. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/ustack`, so change it there.

- **Typing.** Type key by key whenever the result depends on what typing triggers, such as a keyboard shortcut, a mention or slash menu, autocomplete, an input mask or editor autoformat. Setting a value or inserting a whole string skips those handlers. The key-by-key operation is `browse type` (`browse.type` in `browse execute`, plus `browse press` for keys and shortcuts) in OpenCode `browse`, `pressSequentially` in Codex's browser, `type` in Claude in Chrome, `preview_act` (`action: "type"` / `"press"`, called via `acp-mcp-call` when dropped from agy's native tool list) in T3 Code's preview browser, and `key` with one space-separated token per character in Claude Code's built-in browser, such as `# space h i`. The built-in browser's `type` inserts the whole string as one `insertText` with no key events. Send a shifted character as itself, such as `*`, `A` or `@`; OpenCode `browse type` delivers trusted `keydown`/`input`/`keyup` events for shifted characters directly, while for `shift+8` the built-in browser inserts nothing and Claude in Chrome inserts `8`. Claude in Chrome takes keys only after one real click into the page; script focus alone delivers none. After the input, read back the state the claim is about, because a tool that reports the keys as pressed does not show they arrived.
- **Frames.** An agent's browser can throttle a page nobody is looking at. A hidden Claude Code built-in pane runs one or two animation frames a second while `document.visibilityState` still says `visible`. That pane can also report a 0 by 0 viewport, with `innerWidth`, `innerHeight` and every element's box at 0, so no coordinate read from the page can aim a click. `resize_window` with a width and height gives the tab a real viewport while the pane stays hidden. OpenCode `browse` in background Chrome tabs (~99-111 rAF/s, both default and `keepVisible: true`) and T3 Code's preview browser (~100+ rAF/s) both run unthrottled while hidden, with `document.visibilityState === "visible"`, `navigator.webdriver === false` and a real window viewport, without stealing focus. A Claude in Chrome tab that reports `hidden` runs none and fires no `IntersectionObserver` callbacks either. Before a claim that depends on frames or observers, such as virtualization, lazy loading, scroll anchoring, a floating element's position, drag autoscroll or an animation, count `requestAnimationFrame` callbacks over one second in the page, whichever browser drives it. Below 30, that browser cannot prove the claim. Where the project's rules allow it, prove it with a test the project's own browser suite already runs, whose Playwright Chromium launches without background throttling. Otherwise ask the owner to show the browser and keep other work going until they do. Cmd+Shift+B shows the built-in pane, and Chrome needs its window in front. Never start an ad hoc browser driver for the claim; without either proof it stays open.
- **Local servers.** In the Claude Code desktop app, the built-in pane opens a local server the agent started (`preview_start` with `url`, `navigate` for paths). In T3 Code, open a local dev server with `preview_open` (`target: { kind: "environment-port", port, path }`, via `acp-mcp-call` when omitted from native tools) and close spent tabs with `t3_preview_close`. Note that on heavy pages (>20 KB a11y tree), `preview_snapshot` drops `consoleEntries` under its text cap; verify console errors through the dev server's `visits.jsonl` beacon or `preview_evaluate`. OpenCode `browse` (`browse navigate` / `browse execute`) also reaches `127.0.0.1` and `localhost` directly in Chrome; note that its `eval` / `page.evaluate` runs in an isolated world (sharing the DOM, not main-world `window` globals).
- **Stalls.** After `navigate` in an existing tab, Claude Code's built-in pane can leave a page stuck on its first loading frame, most often while the pane is hidden. A stall also shows as the page's API calls answering 200 and then `net::ERR_ABORTED`, with the page still on its first loading frame. Before recording that a page hangs or does not show something, and on that sign before reading any product code, retry the page in a fresh tab opened with `preview_start`. When a `navigate` call opened the stuck page, give `preview_start` that page's `url`. When an in-app step, such as a click on a link, led to it, open the page the step started from and repeat the step there, because loading the target directly can hide a navigation bug. A page that loads on that retry was a browser stall, not a product finding. The pane holds a limited number of tabs, so close each spent tab with `tabs_close`.
- **Clipboard.** Neither Claude Code's built-in browser nor T3 Code's `preview_act` (`Meta+c`/`Meta+v`/`Meta+a`) triggers native browser `<textarea>` clipboard/select-all events (`preview_act` sends trusted `keydown` for JS handlers only). OpenCode `browse` (`browse press Meta+a` / `Meta+c` / `Meta+v`) does trigger real native `<textarea>` select-all, `copy` and `paste` events even in a background Chrome tab. Drive a native copy or paste in OpenCode `browse`, in Claude in Chrome after one real click, or through the project's clipboard test.
- **Undo.** Cmd+Z sent with the `key` action of Claude Code's built-in browser does not undo a text input's own edit. On 2026-11-17, Backspace and then Cmd+Z in a text input of a public editor demo left the character deleted in that browser, while the same keys in Playwright Chromium brought it back. OpenCode `browse` (`browse press Meta+z`) does run real native undo on both `<textarea>` and `<div contenteditable>` in background Chrome tabs (verified on 2026-11-26). A drive of native undo in a text input or textarea counts in an agent browser only after the same keys bring back an edit, in that browser, on a control page whose undo works in Playwright Chromium. Without a passing control, prove the undo with a test the project's own browser suite runs, or with a replay the project's rules allow, and never record it as broken from that browser.
