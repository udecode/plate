# Plans and trails

This file says where plans and decision logs live and what their rows and proofs must show. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Plans and trails.** When work spans sessions, runs unattended, touches another person's area or goes into a PR, keep its plan in the repository as `docs/plans/<date>-<slug>.md` and its show-me-your-work decision log beside it as `docs/plans/<date>-<slug>.decisions.tsv`, so teammates can read the reasoning later. Every new decision-log row starts its result with a status word (fixed, partial, verified, open, gap and the rest `node .agents/pstack/decisions-check.mjs <log>` enforces). A fixed, verified or proven row puts `scope:` in its evidence, naming the predicate the proof checked and its inputs, in the claim's own terms. When the claim depends on current data, `scope:` also names when that data was read, and a `stop:` that waits on a data event names the query that detects it. A cheaper stand-in for the planned proof is logged `partial` with the gap stated, never `verified`. A new row whose result starts with `partial`, `open`, `gap`, `blocked` or `inconclusive` names the file whose verdict it states in its evidence as `proof: <path>`, with a space after the colon and an existing path under `docs/plans/artifacts/`. A row that grades no file, such as one that tracks a bug or a finding, or a reviewer's verdict, writes `proof: none`. `decisions-check.mjs append` refuses one without a label, a `(missing)` mark does not excuse a label's path, and a review-phase row needs none. Filled rows, with the cells phase, decision, why, evidence and result separated by tabs in the queue file, look like `verify | Prove the send dialog keeps its recipient | acceptance proof | scope: recipient kept after reopen at 1440 and 390 px, fixture demo-a; proof: docs/plans/artifacts/<slug>/send-a1.log | verified, both widths pass`, `verify | Drive the signing lane | acceptance proof | proof: docs/plans/artifacts/<slug>/sign-a1.log | partial, no template was published, so no signature ran` and `build | Track the uncaptured 500 | finding | proof: none | open, no capture task yet`. A deviation row starts its result with a listed word such as `decided` or `superseded`, never `deviated`. When a check refuses an evidence pointer, move the pointer where the check accepts it, such as a decision-log row's `proof:` label. Never replace it with prose such as "evidence in the run directory", which hides the refusal instead of fixing it. A `superseded`, `corrected` or `reverted` row changes no proof's state, so when the proof it replaces no longer holds, the lead also appends a labeled `partial` row on it. `plan-open.mjs` refuses a box closed since the last commit that cites a file whose latest labeled verdict in the plan's own log is not passed. The refusal holds until a later labeled row proves the file, or an `accepted` row names it with `proof: <path>` and `word: <word>`, an option of a Word cell in the plan's Defaults. The check cannot tell a context citation from a proof, so a box moves a context citation of such a file to the decision log. That check passes before the log is committed. The lead queues rows in decision order in a TSV in the run directory, five cells each without a timestamp, and writes them with `node .agents/pstack/decisions-check.mjs append <log> --from <queue>`, which writes the batch only when every row passes and lists every failing row. It empties the queue only after that append exits 0. The append opens its batch with a `lead` row naming the session's model and effort, read from the session's own transcript, whenever they differ from the log's last `lead` row, and the page header shows each one. It writes the queue before anything reads or appends to the log: each `rounds` check and panel launch, each freeze for a reviewer, each commit and hand-back, and any single-row `append <log> <phase> <decision> <why> <evidence> <result>`. While a reviewer that reads the log is running, the queue waits, as the Panel review rule says. A batch's rows share the timestamp of their write. The check also refuses a new row whose evidence cites a path under `docs/plans/artifacts/` that does not exist, read from a code span, a link target or bare text. It skips a row in a `review` phase, a path followed by `(missing)`, a cited path that holds a glob, a range or a placeholder, and a link target written with parentheses or angle brackets. When a shell command makes the edit an append records, chain the queue write after it with `&&` or `set -e`, so a failed edit logs nothing. Phases starting with `review` are reserved for a hand-off reviewer's rows and phase `panel` for the lead's panel rows; the lead logs its other decisions under another phase, such as `plan`, `build` or `trail`. Rows for a stage that the plan page's flow rail shows go under that stage's phase in the `plan-page` skill's shape, such as `architect`, `build`, `writing`, `verify`, `delivery` or `reflect`; the rail ignores every other phase. A plan is marked Done only after `node .agents/pstack/plan-open.mjs <plan>` passes: no unchecked box, TODO, TBD or FIXME, or blank or pending cell in a Start or Completion Gates table is left, every box closed since the last commit names the artifact that closed it (a path, command, commit or link) or `skip: <reason>`, and every deferred or open item added since the last commit, each item under `## Open work` included, names its `owner:` and its `stop:`. It also refuses a box closed since the last commit whose line, or a line indented directly under it with no blank line between, cites a path under `docs/plans/artifacts/` that does not exist, or a `.log` there with no line that reads exactly `exit=<code>`, as `proof.mjs` writes. Both helpers judge lines added since `HEAD`, or since the commit `PSTACK_BASE` names. When `PSTACK_BASE` is set, even to an empty value, and names no commit, they fail. Once the owner commits during a run, the run sets `PSTACK_BASE` to its intake base, and every "since the last commit" in this rule then means since that base. The helper checks those two words on lines added since the last commit and skips committed lines. The item also says where it is tracked, in a place that outlives the plan's close, such as its subject file's `## Open work` or a tracker, which the helper does not check, and its `stop:` is the condition or date that closes or drops it. Its `owner:` names someone who acts without another prompt, such as the owner, a named person or a scheduled run, never a skill. Gaps a pass finds stay on the page that states them, behind one item with such an owner. A count, absence or impossibility claim, or a capability or limit claim about an existing product, tool or system, in a plan, record, README, log row or question option names the check that could falsify it, or says it is inferred, and the lead checks a research claim at its primary source before it reopens an owner's answer. Reading types or docs is not the check for a claim that something cannot be done at runtime, so that check tries each plausible public path, or the claim says it is inferred. A command run as proof writes its own command line and exit status into its log, at a path that carries an attempt index and is never rewritten once a decision row cites it, with `pipefail` set, and records that exit status and output beside a control run where the effect does appear, or beside a bogus input that must fail, so a launch that never happened cannot pass. `node .agents/pstack/proof.mjs --dir <run directory> --name <name> -- <command>` writes such a log at the next free `<name>-a<N>.log`. Under `pipefail`, a consumer that exits early, such as `head`, `grep -m` or an awk `exit`, can make an upstream producer exit 141 after the value was read, so the proof writes the producer's bounded output to a file first and runs that consumer on the file. When the expected exit is non-zero, the proof also asserts the failure's own text, such as the finding line or rule id, because a missing script or a crash also exits non-zero. A claim that content is recoverable, such as "git has it", names `git log -- <path>` as that check, and hand-written content in an uncommitted file is copied to the run directory before a rewrite deletes it. Before changing a script in another run's directory that its rows cite, the lead copies it into this run's directory and changes the copy, so that run's reviewer still reads what its rows cite. Session scratch is temporary, and a restart can wipe it. Anything a later gate, revert, fixture or resume reads goes to the run directory, `docs/plans/artifacts/<slug>/`, which git ignores, as soon as it exists; `<slug>` is the plan's slug, or a short name for a run that writes no plan. That covers a pre-edit copy, a seat's answer, a reader's reply and a proof log. Scratch keeps only throwaway files. A count, verdict or advice keyed to a new derived label holds only after the raw evidence of the first real items it marks has been opened, because a passing test shows only that the code matches its own definition. The same holds for what a new filter or classifier drops, and a zero on real data means the pattern is broken until a raw sample of the records it rejected shows otherwise. When a later proof replaces or narrows an earlier one, append a `superseded` row naming the earlier one and fix every plan step that cites it. A probe's claim names every stub, fixture and stand-in it ran with. When a claim narrows, the lead fixes every plan step, Close, subject file, record draft, commit body and PR text that cites it, found by searching for its predicate and its paraphrases, not only the sentence a reviewer quoted. Right before each commit or push, that search runs over its body and PR text against every finding logged so far, and the lead words a claim that an `open` finding still contests as open. A pick that waits on a later gate, such as a design kept until a later benchmark rerun, writes the gate's check, its frozen budget and what a miss triggers into the step that runs the gate. That step may sit in another plan, and the text there names the pick. An approved plan item that execution changes gets its own deviation row, keeps its approved wording visible in the plan, and opens the plan's `## Close` as a reversal. To revert a decision, the lead diffs every file it touched against the copy or commit from before it, and reverts and logs each side edit, not only the main change. A default that changes or drops what the user approved is such a change, never only a default. When the owner asks for all of something except named keeps, the plan's claim names every further exception the lead keeps as its own pick, each with a Defaults row and the word that reverses it. Ordinary fixes rely on their commit body. Other decision logs and all pause checkpoints stay local. Screenshots and run artifacts are never committed.
