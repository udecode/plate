# Worktrees and landing

This file says how a task works in its own worktree and lands on `next` in a project whose delivery is `trunk`. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Worktrees.** Every session works in its own worktree cut from `origin/next`, and its work reaches `next` only through land.mjs. A session the lead starts gets its own worktree, with `use_worktree: true` in Claude Code, and its brief names this file. The main checkout only pulls; no agent edits or commits there. The project's Claude Code `SessionStart` hook runs `node .agents/pstack/setup.mjs`, which in a new worktree copies the main checkout's untracked `.env` and `.env.local` files and installs dependencies, and in the main checkout fast-forwards `next` when no local edit touches a path the incoming commits change.
- **Landing.** After its writing passes, a task lands with `node .agents/pstack/land.mjs --message <file> [--check <command>]...`. The message file holds one commit message as the Commit and PR text rule says, and its body has a `Beyond the ask:` line that names each change the request did not ask for, or says `none`; land.mjs refuses a message without one. land.mjs commits the worktree, squashes the task into that one commit and rebases it onto `origin/next`. It then runs `pnpm lint:task --allow-ignored` with the changed files appended and each `--check`, and delivers by this clone's `git config pstack.delivery`. With `push` it pushes `next`, and when that push is rejected because `next` moved, it rebases and pushes again, up to three times. Unset, it pushes a topic branch and opens a PR into `next` with `gh`. A rebase conflict stops it with the rebase in progress and the conflicting paths listed; resolve them, `git add` them, run `git rebase --continue`, then run land.mjs again without `--message`. A failed check stops it with the squashed commit still local; fix the cause and rerun it the same way. No task ends with work uncommitted in its worktree. Never force-push `next`; a `PreToolUse` hook denies an agent's force-push or delete of it or of the protected branch, and quotes the command for the owner to run.
- **Other people's PRs.** A repair to a PR whose head is another branch runs in a detached worktree at that head, and the page names the worktree path. The lead commits the repair there and pushes it with `git push origin HEAD:<head branch>` once the remote head still matches the worktree's base, without asking. It keeps the description of a PR it opened true to the pushed diff. On another person's PR it leaves their description alone and keeps its latest comment about its own commits true instead, as the `plan-page` skill's PR section says; that comment is not a message the Messages rule holds back, because like a PR body it reports the lead's own delivery. When maintainer edits on a PR's head branch are not allowed, it opens a PR stacked on that branch instead. Merging, closing, other comments, reviews and CI approval need the user's word.
- **Review.** The owner reviews landed work with `node .agents/pstack/review.mjs`, which lists the commits on `origin/next` since their last `--mark`, grouped by the plan each one links, with each subject and its `Beyond the ask:` line.
