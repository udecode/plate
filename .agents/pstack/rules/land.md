# Worktrees and landing

This file says how a task works in its own worktree and lands on `next` in a project whose delivery is `trunk`. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Worktrees.** Every session works in its own worktree cut from `origin/next`, and its work reaches `next` only through land.mjs. A session the lead starts gets its own worktree, with `use_worktree: true` in Claude Code, and its brief names this file. A code delegate that writes files gets its own worktree as pstack's Feature step says, and the project's Claude Code settings set `worktree.baseRef` to `"head"`, so that worktree starts from the session's last commit. The main checkout only pulls; no agent edits or commits there, except that `decisions-check.mjs` appends suggested-task rows to its ledger, as `.agents/pstack/rules/chips.md` says, and runs write their ignored run directories under the plans directory's `artifacts/`. In Claude Code, `guard.mjs` denies an agent's Edit, MultiEdit, Write or NotebookEdit of a main-checkout file, `.git` included, while that checkout is on `next` or the protected branch, except the ledger and the plans directory's `artifacts/`; a shell command or Codex's `apply_patch` that writes there is not caught. The project's Claude Code `SessionStart` hook runs `node .agents/pstack/setup.mjs`, which in a new worktree copies the main checkout's untracked `.env` and `.env.local` files and installs dependencies, and in the main checkout fast-forwards `next` when no local edit touches a path the incoming commits change.
- **Landing.** After its writing passes, a task lands with `node .agents/pstack/land.mjs --message <file> [--check <command>]...`. The message file holds one Conventional Commit, `type(scope): subject`, whose type is `feat`, `fix`, `docs`, `refactor`, `test`, `chore` or `perf` and whose subject is short, imperative and has no trailing period. Its body says why in a short paragraph and describes the final behavior, and it has a `Beyond the ask:` line that names each change the request did not ask for, or says `none`; land.mjs refuses a subject in any other form and a body without that line. land.mjs commits the worktree, squashes the task into that one commit and rebases it onto `origin/next`. It then runs `pnpm lint:task --allow-ignored` with the changed files appended and each `--check`, and delivers by this clone's `git config pstack.delivery`. With `push` it pushes `next`, and when that push is rejected because `next` moved, it rebases and pushes again, up to three times. Unset, it pushes a topic branch to `origin` and opens a PR into `next` with `gh`. When the task changes exactly one dated plan, the one its `Plan:` line names, land.mjs first renders that plan's page with `plan-page.mjs --pr` and opens the PR with that page as its body and each frame it prints attached; otherwise the body is the commit body. When plan-page.mjs refuses the plan, land.mjs stops before the push; fix the plan and run land.mjs again without `--message`. In a fork clone, one with an `upstream` remote for the canonical repository and `origin` for the fork, it fetches and rebases onto `upstream/next`, pushes the topic to the fork and opens the PR on upstream. A clone that cannot push to `origin` and has no `upstream` stops with one line saying to fork the repository and add the canonical one as `upstream`. A rebase conflict stops it with the rebase in progress and the conflicting paths listed; resolve them, `git add` them, run `git rebase --continue`, then run land.mjs again without `--message`. A failed check stops it with the squashed commit still local; fix the cause and rerun it the same way. No task ends with work uncommitted in its worktree. A task with a plan runs its close stop in its worktree after its last land.mjs run, as the Plan pages rule says, so its plan leads its page while that worktree still holds its frames; no session publishes from the main checkout. The lead holds back one close check, such as reading the pushed commit, to send with that stop's publish; a retry after a refusal may go out alone. Never force-push `next`; a `PreToolUse` hook denies an agent's force-push or delete of it or of the protected branch, and quotes the command for the owner to run. The same hook denies an agent's own `gh pr create` into `next`, or one that names no base, because land.mjs opens those PRs; a PR stacked on another branch names that branch with `--base`.
- **Other people's PRs.** A repair to a PR whose head is another branch runs in a detached worktree at that head, and the page names the worktree path. The lead commits the repair there and pushes it with `git push origin HEAD:<head branch>` once the remote head still matches the worktree's base, without asking. It keeps the description of a PR it opened true to the pushed diff. On another person's PR it leaves their description alone and keeps its latest comment about its own commits true instead, as the `plan-page` skill's PR section says; that comment is not a message the Messages rule holds back, because like a PR body it reports the lead's own delivery. When maintainer edits on a PR's head branch are not allowed, it opens a PR stacked on that branch instead. Merging, closing, other comments, reviews and CI approval need the user's word.
- **Review.** land.mjs ends each commit with a `Session:` line naming the agent session that landed it, and a `Plan:` line when the task changes exactly one dated plan. The owner reviews landed work with `node .agents/pstack/review.mjs`, which lists the commits on `origin/next` not yet reviewed, grouped by session, with each subject, its plan and its `Beyond the ask:` line. `--done <session>` marks one session's commits reviewed, and `--mark` marks them all. The hand-back reply lists each commit this session landed for the request, by short sha and subject, and the session title shows 👀 as the Session title rule says.
