# Worktrees and landing

This file says how a task works in its own worktree and lands on `next` in a project whose delivery is `trunk`. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Worktrees.** Every session works in its own worktree cut from `origin/next`, and its work reaches `next` only through land.mjs. A session the lead starts gets its own worktree, with `use_worktree: true` in Claude Code, and its brief names this file. A code delegate that writes files gets its own worktree as pstack's Feature step says, and the project's Claude Code settings set `worktree.baseRef` to `"head"`, so that worktree starts from the session's last commit. The main checkout only pulls; no agent edits or commits there, except under the plans directory's `artifacts/`, which git ignores. In that directory `decisions-check.mjs` appends suggested-task rows to the ledger, as `.agents/pstack/rules/chips.md` says, and runs write their run directories. A run directory holds logs and small outputs. A checkout a run builds or runs, such as a benchmark tree, an export or a probe, goes in a worktree in a temp folder, never in the run directory, and the run removes it when done, because the `cleanup` skill deletes a run directory's installs and builds after a quiet day. A worktree of another repository, such as a benchmark baseline, installs with that repository's own commands instead of `setup.mjs`. In Claude Code, `guard.mjs` denies an agent's Edit, MultiEdit, Write or NotebookEdit of a main-checkout file, `.git` included, while that checkout is on `next` or the protected branch, except under the plans directory's `artifacts/`; a shell command or Codex's `apply_patch` that writes there is not caught. The desktop app refuses a worktree session's Edit and Write of the main checkout, as the block's Plans and trails rule says, but leaves other repositories alone, so a worktree session edits, commits and pushes another checkout, such as the shared skills repository, as that repository's own rules say. The project's Claude Code `SessionStart` hook runs `node .agents/pstack/setup.mjs --hook`. It works on the checkout the hook payload's `cwd` names, even when the hook starts in the main checkout. In a new worktree it copies the main checkout's untracked `.env` and `.env.local` files and installs dependencies, and in the main checkout keeps the suggested-task ledger in step with `refs/pstack/ledger` on origin and fast-forwards `next` when no local edit touches a path the incoming commits change.
- **Landing.** After its writing passes, a task lands with `node .agents/pstack/land.mjs --message <file> [--check <command>]...`. The message file holds one Conventional Commit, `type(scope): subject`, whose type is `feat`, `fix`, `docs`, `refactor`, `test`, `chore` or `perf` and whose subject is short, imperative and has no trailing period. Its body says why in a short paragraph and describes the final behavior, and it has a `Beyond the ask:` line that names each change the request did not ask for, or says `none`. A `fix` body also has an `Introduced-by: <sha>` line for each landed commit that introduced the bug. When the cause is older than the history or outside the repository, such as a dependency or the platform, it says `Introduced-by: none` instead; code that was broken when it landed names the commit that landed it. Other types need no such line. land.mjs refuses a subject in any other form and a body without the `Beyond the ask:` line. It refuses a message whose subject or body puts the word close, fix or resolve, in any form, right before an issue reference, with whitespace, a colon or both between them. An issue reference is `#<N>`, `<owner>/<repo>#<N>`, `GH-<N>` or a GitHub issue or PR URL. GitHub closes that issue once the commit reaches the default branch, so the message names it as `<repo>#<N>`, which links nothing. It also refuses a `fix` body with no `Introduced-by:` line, with `none` beside another `Introduced-by:` line, or with a line that has no space after its colon. Each other value must be a lowercase sha of 7 to 40 characters that names a commit on the branch it rebases onto. land.mjs commits the worktree, squashes the task into that one commit and rebases it onto `origin/next`. It then runs `pnpm lint:task --allow-ignored` with the changed files appended and each `--check`, and delivers by this clone's `git config pstack.delivery`. With `push` it pushes `next`, and when that push is rejected because `next` moved, it rebases, runs the lint fix and every `--check` again on the rebased commit, and pushes again, up to three times. When that recheck would end more than 55 minutes into the run, judged by how long its last checks took, it exits 75 with the commit local instead. GitHub sometimes declines a push with GH006 and no reason, then accepts a push of the same change later, sometimes more than an hour later. land.mjs pushes such a commit again after 1, 2, 4, 8 and 16 minutes. When GitHub declines every try, or the next wait would end more than 55 minutes into the run, land.mjs exits 75 with the commit local. Each exit 75 is a pending external gate, not an unclear failure for the Blocked rule, so the lead runs land.mjs again with the same `--check` options and no `--message`, up to three more times, before it puts the landing under Needs you. Each rerun is its own command under the Time budget rule, not a piece of one protocol, because it waits on GitHub or the branch and measures nothing, and the lead does other ready work meanwhile. land.mjs records each commit its checks passed on, a rebased one included, and drops that record whenever it starts the checks again, so a failed check is never skipped. A rerun with the same checks skips them when the commit it would push has the recorded tree, parent and message, unless the environment holds an assignment the config's `freshEnv` lists, such as the variables that make the project's checks ignore cached passes. Run land.mjs in the background with an hour's timeout, because its checks and waits can take that long. Unset, outside a checkout that holds the companion's `companion.dir`, it pushes a topic branch to `origin` and opens a PR into `next` with `gh`. When the task changes exactly one dated plan, the one its `Plan:` line names, land.mjs first renders that plan's page with `plan-page.mjs --pr` and opens the PR with that page as its body and each frame it prints attached; otherwise the body is the commit body, and land.mjs refuses a message without a `## Why` and a `## Verification` section, each with text, as pstack's Opening a PR asks. When `next`'s rules require an approval that a later push dismisses, land.mjs then arms GitHub auto-merge with a method those rules allow, so the PR merges once a reviewer approves its latest push; otherwise, or when arming fails, it prints why and leaves the merge to a maintainer. When plan-page.mjs refuses the plan, land.mjs stops before the push; fix the plan and run land.mjs again without `--message`. In a fork clone, one with an `upstream` remote for the canonical repository and `origin` for the fork, it fetches and rebases onto `upstream/next`, pushes the topic to the fork and opens the PR on upstream. A clone that cannot push to `origin` and has no `upstream` stops with one line saying to fork the repository and add the canonical one as `upstream`. Each entry of the config's `generated` list names the globs of output that its `command` rebuilds. When every path a rebase of this checkout conflicts on matches an entry's globs, land.mjs takes `origin/next`'s side of those paths, runs each matching command, stages what it wrote and continues the rebase. When a command fails, land.mjs puts the conflicts back and stops with the rebase in progress, and when it changes a file outside its entry's globs, staged or not, land.mjs stops the same way. A companion rebase never rebuilds. Any other rebase conflict stops it with the rebase in progress and the conflicting paths listed, and names the command for each generated path among them; resolve them, `git add` them, run `git rebase --continue`, then run land.mjs again without `--message`. land.mjs also refuses while a revert still has commits to apply, until `GIT_EDITOR=true git revert --continue` finishes it. A failed check stops it with the squashed commit still local; fix the cause and rerun it the same way. No task ends with work uncommitted in its worktree. With `push`, a task that closes its plan writes that close before its last land.mjs run, so the landing commit carries the record and no commit lands only to record that the plan landed. A task that leaves its plan open, such as one that stops at plan, lands the plan with its open `Status:`. A task that closes its plan first copies the plan and its subject file to the run directory. It writes the `## Close` and any fold into the subject file, and checks a fold with a `--folded` render, which refuses a plan with no Close. Then its close edit, the last edit before land.mjs, ticks each box whose proof exists or is that landing and sets the `Status:` the plan has once that landing is on `next`, such as executed, partial or blocked. The page counts a landed `Status:` as shipped. So from the close edit until land.mjs exits 0, the lead runs no `page-stop.mjs stage`, not even for a decision-log append, and sends no publish; the close stop after that exit publishes. A companion landing exits 0 only once both pushes succeed. When land.mjs stops short and the landing goes under Needs you, the lead copies the plan and subject file back from the run directory, sets `Status: blocked: <why>`, stages and publishes, then writes the Close, any fold and the close edit again before the next rerun. A run that stops after a landing it did not plan as its last lands its Close, its final `Status:` and that landing's row as one more commit. The plan and its decision log name no commit of their own landing, because the landing commit's `Plan:` line links the commit to the plan. land.mjs keeps a `Plan:` line the message already has and adds one only when the task changes exactly one dated plan, so a task that closes a plan writes that plan's `Plan:` line in its message. When a plan's work lands through separate land.mjs runs in several repositories, the plan's repository lands last, so its Close names each other landed commit; a companion pair lands in one run, and its `Lands-With:` line links the two commits. When land.mjs opens a PR instead, the plan keeps its open `Status:` until that PR merges. A task with a plan runs its close stop in its worktree after its last land.mjs run, as the Plan pages rule says, so its plan leads its page while that worktree still holds its frames; no session publishes from the main checkout. The lead holds back one close check, such as reading the pushed commit, to send with that stop's publish; a retry after a refusal may go out alone. Never force-push `next`, and never push it except through land.mjs; a `PreToolUse` hook denies an agent's force-push or delete of it or of the protected branch, and any other push to `next` except a dry run, and quotes the command for the owner to run. A project's release skill alone prefixes a push to `next` with `PSTACK_RELEASE=1`, such as a sync from the protected branch. The same hook denies an agent's own `gh pr create` into `next`, or one that names no base, because land.mjs opens those PRs; a PR stacked on another branch names that branch with `--base`.
- **Companion repository.** When `.agents/pstack.json` names a `companion`, a second git repository tracks the files `companion.list` names, in the same folder, through the git directory `companion.dir`, and this checkout's git ignores those files. Run its git as `git --git-dir=<companion.dir> --work-tree=.`, or through the project's own wrapper. A checkout that holds `companion.dir` lands in push mode, which is what an unset `pstack.delivery` means there. A checkout whose config names a companion it lacks refuses to land until the companion is attached. Every land rebases the companion onto its `origin/next` and runs every check over both repositories, so a task that changes only public files is still checked against the companion's tests. land.mjs pushes `next` first, then the companion commit with the same message and a `Lands-With: <sha>` line that names the first. A refused companion push exits 75 with that commit local, and a rerun with no `--message` rebases, checks and pushes it. A task that changes only companion files lands one companion commit and leaves `next` alone. A branch cut before `companion.list` existed on `origin/next` stops and names `companion.migrate`, which moves its work onto both repositories. guard.mjs denies what would delete or overwrite the companion's files: `git clean -x` or `-X`, any `git clean` through `companion.dir`, and a checkout, switch, reset, merge or rebase to a commit without `companion.list`. setup.mjs keeps the suggested-task ledger on the companion's origin through the main checkout's `companion.dir`, and skips that sync while the main checkout lacks it.
- **Other people's PRs.** A repair to a PR whose head is another branch runs in a detached worktree at that head, and the page names the worktree path. The lead commits the repair there and pushes it with `git push origin HEAD:<head branch>` once the remote head still matches the worktree's base, without asking. It keeps the description of a PR it opened true to the pushed diff. On another person's PR it leaves their description alone and keeps its latest comment about its own commits true instead, as the `plan-page` skill's PR section says; that comment is not a message the Messages rule holds back, because like a PR body it reports the lead's own delivery. When maintainer edits on a PR's head branch are not allowed, it opens a PR stacked on that branch instead. Merging, closing, other comments, reviews and CI approval need the user's word.
- **Review.** land.mjs ends each commit with a `Session:` line naming the agent session that landed it, a `Plan:` line when the task changes exactly one dated plan, and a `Lead:` line with the model and effort that `lead.mjs` reads from the transcript of the agent session running it. land.mjs replaces any `Lead:` line the message has, including the one a rerun takes from its earlier commit. When `lead.mjs` cannot read the session, such as outside an agent session, the line says `unknown` and land.mjs prints why. The owner reviews landed work with `node .agents/pstack/review.mjs`, which lists the commits on `origin/next` not yet reviewed, grouped by session, with a DiffsHub link to each, its plan, its `Beyond the ask:` line and whether it shipped fast. When `.agents/pstack.json` sets `reviewPaths`, it lists only the commits with public changes or weakened tests, `--tier internal` or `--tier all` lists the rest, and a commit that changes only skipped paths or adds tests needs no review. In a checkout that holds the companion's `companion.dir`, it also lists the companion's commits, each after the commit its `Lands-With:` line names, and keeps a reviewed mark in each repository. `--net <session>` prints a session's listed commits as one diff per repository, so a later commit cancels what it undid. `--done <session>` marks one session's commits reviewed in every tier, and `--mark` marks them all. `--revert <session>` undoes a session. It reverts every first-parent commit on `next`, and on the companion's `origin/next`, whose `Session:` line names that session, newest first, so it also undoes that session's own plan and decision-log edits. It lands the result through land.mjs, with each `--check` it got, as one `fix(revert)` commit with an `Introduced-by:` line for each reverted commit. It refuses the main checkout, a worktree with uncommitted changes, a worktree with commits `next` lacks, and a session that landed a merge commit. On a conflict it stops with the revert in progress and prints the commands that finish it. With `--stage` it stops once the revert is staged and prints the land.mjs command, so a review the project asks for before such a push, such as a panel on a push that deletes behavior, reads the staged diff first. The hand-back reply's closing link list holds each commit this session landed for the request, as the block's Links in replies rule says, and the session title shows 👀 as the Session title rule says. land.mjs also refuses a commit whose subject and body name no source, so the owner can redo the work from its issue, card or plan rather than from its diff. A source is an issue of this repository or of the companion, written as `<repo>#<N>`, `<owner>/<repo>#<N>` or its GitHub URL. The id of a card in the suggested-task ledger, such as `t_1a2b3c4d`, is one too, and so is a `Plan:` line that names a dated plan in the plans directory that exists, written in the message or added for the dated plan the task changes. A bare `#<N>` is not one. land.mjs reads the `sourceless` list from the config on `next`, so a task cannot drop it, and reads the lander's login with `gh api user`. Only the logins on that list land without a source. A task with no issue or card keeps a dated plan, and changing that plan names it.
