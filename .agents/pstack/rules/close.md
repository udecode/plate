# Todo list and close, and Decision-trail review

This file says how a run closes: the gates in order, subagent replies, counts and the decision-trail review. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Todo list and close.** A gate that must pass before a mid-run step, such as the trail review before a shared push, gets its own todo placed right before that step. When the runtime has no todo tool, the lead keeps its todo list as a file in the run directory and ticks each gate there before every commit and push. Each todo closes with the artifact that proves it, such as the skill invocation, test run, path or commit, or `skip: <reason>`; a gate is never ticked before that artifact exists. When the design changes, the lead rechecks every `skip:` reason and review trigger against what the changed design installs, sends and changes, and a reason that no longer holds stops closing its gate. Close in this order: the cheap proofs that can still force a code change, such as a recovery path or a one-repeat smoke; the writing passes; the panel review, when one runs, and its fixes, each round's fixes with their own writing passes; the lint fix; the repeated acceptance proof, run once on bytes no pending step can change, which a later edit, a lint fix included, reopens; the decision-trail review, when one runs; then immutable records such as ledger records, attestations and proven decision-log rows; then `/pstack:reflect` once the trail review has returned, so its reviewers see the findings. The push follows the decision-trail review for a new or changed shared script or check in a project, and comes before that review for all other work, except a diff whose last panel round dismissed, narrowed or left open a critical finding, whose decision-trail review runs before its push, the shared source included. The review's Close edits and the records after it then land through the Delivery rule as one more commit. After this run edits an instruction file, such as `AGENTS.md`, a skill or a models sheet, every later subagent brief names those files and tells the subagent its loaded copy is stale and to re-read them from disk. Save every subagent reply that a later gate reads, such as an arena candidate, a judge verdict or a panel seat's answer, to that subagent's folder in the run directory when it arrives, copied verbatim from its transcript, never retyped. `node .agents/pstack/reply.mjs <task output> <dest>` copies a background subagent's final reply once its turn has ended, and refuses an API error the runtime wrote in its place. When the transcript never recorded the turn's end, the lead passes `--notified` once the completion notice has arrived, and the helper then copies a last message that holds text and no `tool_use` block. That mode cannot tell interim text from a final reply, so the lead passes it only after a completion notice, never after a stop or failure notice. The lead waits for a background subagent's completion notice by doing other work or ending its turn, never with a foreground sleep or poll loop in any language, and saves the reply once per notice. A Workflow agent returns its rows in its result, which the workflow journal keeps, never only the path of a file it wrote. A `cross.mjs` seat's answer file is that copy. Each parallel subagent brief names its own folder in the run directory, which also holds that subagent's fallback todo list, and asks for its findings in the reply or a TSV data file, never a report `.md`, which Claude Code subagents refuse to write. Its reply schema keeps a side-findings block apart from its structured rows, and the lead turns each side finding into a todo or a logged drop before the close. A subagent that extracts claims never counts as their verifier. A second reader checks every entry against its source and the current code, a fix applies that reader's exact words, and an error rate is charged to the first stage whose output already holds the error. When a fan-out backs a claim that every file was read in full, its brief allows no size-based skim, and a file too large for one reader gets its own reader, who reads it in line chunks. Each reader returns the lines it read against the file's line count, and the coverage check counts anything short of full as unread. A close of more than ten items states in its Close how many are done, partial, skipped, blocked and open, and those counts add up to the total. A step whose approved proof did not pass counts as partial or open, never done. Its box stays unchecked, so the plan cannot be marked Done, until that proof passes or the lead accepts the narrower proof. The lead accepts it only while the user's stated goal still holds under the narrower proof and that proof does not narrow the run's own exit condition, because a narrower exit condition keeps the plan partial, as the Long runs rule says. To accept it, the lead records a `look` Defaults row, as the Autopilot rule says, and logs an `accepted` row with the proof's `proof:` label and that row's `word:`, after a labeled `partial` row on that file. Otherwise the claim narrows with a deviation row, and the step moves to `## Open work` with its `owner:` and `stop:`. The step keeps its `partial` log row, and the Defaults row names the word that reopens it. A measurement the block's Time budget rule hands to a suggested task takes this accepted route even though it narrows the exit condition, because that rule is the owner's word for it. A resume prompt, whether handed to another session or scheduled as a wakeup or `/loop` prompt, carries the goal, the gate and the plan path, and says to continue at the plan's first open gate, never a list of steps. Shared state changes before it fires, a wakeup fires again after its steps are done, and the plan's next action is the one place that gets corrected.
- **Decision-trail review.** show-me-your-work asks for a reviewer from another model family. It runs for an unattended run, a run that spans sessions, a diff or plan whose panel dismissed, narrowed or left open a critical finding, and a new or changed shared script or check; any other decision log skips it, including one whose panels only applied or deferred findings. That reviewer is a `codex:gpt-6.1-sol` seat in Claude Code and an `opus` seat in Codex, run as the Panel review rule describes. The Claude Code seat runs at the effort the models sheet's `interrogate reviewers` line gives that model. Its brief quotes the user's asks verbatim, and each invariant it names traces to one of them; a decision the lead made itself, such as a deviation or a fix made mid-build, goes in as a decision to attack. The trail review checks the log against the transcript, not the code, so it never counts as review of code no panel read. Its brief points at a frozen commit or a snapshot in the run directory of every plan, log and authored file it names, so the lead keeps working without changing the reviewer's input. A file the run authored outside the repository gets its writing passes at its source first. The lead then copies it byte for byte into the run directory, records its source path and hash, and freezes the copy with the rest before the review launches. The brief cites the transcript by path and line range and never copies it. When it raises a critical finding, its outcome follows the Panel review rule. One that says only that the log misstates the transcript is dismissed only by citing the transcript line that refutes it, and is otherwise corrected; one that disputes a logged outcome of a product finding is that finding raised again, and the lead's own earlier row never refutes it. Only when that seat fails, use a fresh-context subagent of the session's model and label the review same-family in the Close. The review's Attention section, led by `reviewed by <model>`, goes in the plan's `## Close`, so the reply stays the page link.
