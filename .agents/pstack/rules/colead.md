# Neon co-lead

This file says when a Claude Code lead runs Gemini 4 Neon as its co-lead, what the co-lead owns and how the lead checks its work. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Neon co-lead.** In Claude Code, a run that follows a pstack playbook, other than one under "fast", starts one Neon co-lead and keeps it for the whole run (owner's word, 2026-11-25). The co-lead is one agy conversation on the models sheet's `co-lead` line, at that line's effort. The lead starts it with `node .agents/pstack/cross.mjs --to agy --colead <worktree> --effort <level> --stream <run directory>/colead-<n>.jsonl --prompt-file <brief>`. `<worktree>` is the root of the session's own worktree. The lead writes the `conversation:` id the helper prints to `colead.txt` in the run directory. Each later step adds `--conversation <id>`, so the co-lead keeps the run's history the way the lead does. After a compaction the lead reads the id back from that file. Each call is one step and runs in the background. One step runs at a time, so an evidence lane the run needs beside a running step goes to an `opus` subagent, as the Extraction rule says. The helper stops a call after 55 minutes, so a step that cannot finish in that time is split into several calls.
  - **What the co-lead owns.** Research and evidence lanes, explore rounds, architecture and API design sketches, perf and hillclimb iterations, a bug's repro and its failing test, code that is not UI, and the proof of behavior that drives a browser, a simulator or an emulator, such as a repro or an end-to-end test. A drive through a signed-in site stays with the lead in Claude in Chrome, because the co-lead's browser has no sign-ins. The co-lead writes only in the lead's worktree, the run directory and a detached worktree it adds for a base control, such as the `Introduced-by` check. It runs `node .agents/pstack/setup.mjs` in that worktree first, as the Git rule says, and removes it with `git worktree remove --force` once the control is done.
  - **Briefs.** Each brief names the step, the run directory and each project skill the step's work loads, such as `verify` for a repro and its proof or `plate-plugins` for a plugin, and tells the co-lead to read each one's `.claude/skills/<name>/SKILL.md` in full before it works. The first brief also tells it to read `AGENTS.md` in full for the project's rules on code, tests and proof. The helper's own brief tells the co-lead which duties stay the lead's: plans, reviews, the writing passes, landing, messages and the stop for missing pstack skills.
  - **What the lead keeps.** The lead talks to the owner. It keeps plans and plan pages, UI code and anything visual, the writing passes, landing and the final call on a design. Anything visual includes the hand drive of a change a person sees and its demo clip, on a dev server the lead starts itself. The lead also writes every piece of prose, such as replies, docs, commit messages and team messages. While a co-lead step runs, the lead edits no file in that worktree.
  - **Checks.** Before the lead uses a step's answer, it reads the evidence files the step wrote as well as the answer, and puts back each finding the answer dropped. It reviews the step's diff with `git diff` and reruns the proof the step claims, or the narrowest check that proves it. It checks a ranking of options for a cheaper path the co-lead left out. When the lead and the co-lead disagree on a design, the design counts as contested, so it runs an arena as the Panel review rule says, and the lead never overrules the co-lead alone. A disagreement on a fact, such as a bug's cause, is no design question, so the run settles it with the check that tells the two readings apart.
  - **Fresh reviews.** A panel seat, an arena runner, a judge and a second reader never run in the co-lead's conversation, and the co-lead never reviews its own work. A Neon seat on a panel is a fresh `cross.mjs` run, as the Panel review rule says. An independent reviewer that a playbook step asks for is a fresh run too, never the lead's review of the co-lead's diff.
  - **Guards.** `cross.mjs --colead` runs agy with `--dangerously-skip-permissions` and without its sandbox, because the co-lead runs dev servers, browsers and emulators. The helper refuses a folder that is not a worktree's root and refuses a main checkout. It gives git a pre-push hook that refuses every push, gives `gh` an empty config and drops the GitHub tokens from the co-lead's environment, so a plain `git push` or `gh` command fails. A call that changes the main checkout's `git status` or its diff exits 1 and prints its answer after the warning. A write there to a file git ignores, such as one in the run directory, does not count. These guards stop accidents, not an adversary. A co-lead that reads a web page can still run any command, so the lead treats each step's commands and diff as untrusted until it has reviewed them.
  - **Fallback.** When a call fails, such as on a usage limit, the lead runs it once more. When that fails too, the rest of the run's co-lead work goes to one `Agent` subagent on the model and effort the sheet line names after `or`. Unlike a code delegate, it starts without `isolation`, so it works in the lead's worktree. Each later step reaches it through `SendMessage`, so it keeps the run's history. The hand-back says the run fell back.
