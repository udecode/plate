# Neon co-lead

This file says when a Claude Code lead runs Gemini 4 Neon as its co-lead, what the co-lead owns and how the lead checks its work. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Neon co-lead.** In Claude Code, a run that follows a pstack playbook, other than one under "fast", starts one Neon co-lead and keeps it for the whole run (owner's word, 2026-11-25). A small edit, as the How work runs rule in `AGENTS.md` defines it, works directly at any file count and starts no co-lead. The co-lead is one agy conversation on the models sheet's `co-lead` line, at that line's effort. The lead starts it with `node .agents/pstack/cross.mjs --to agy --colead <worktree> --effort <level> --stream <run directory>/colead-<n>.jsonl --prompt-file <brief>`. `<worktree>` is the root of the session's own worktree. The helper writes the stream file as agy works, so the lead can follow a step's progress there. It prints the `conversation:` id on stderr as soon as agy starts, and the lead writes that id to `colead.txt` in the run directory. With the run's next decision-log batch, the lead logs a `colead` row whose decision is the co-lead's model and effort, such as `agy:gemini-4-neon @xhigh`, and whose evidence names `conversation <id>`. The plan page shows that row beside the lead. `levels.mjs` judges it against the models sheet's `co-lead` line. Each later step adds `--conversation <id>`, so the co-lead keeps the run's history the way the lead does. After a compaction the lead reads the id back from that file. Each call is one step and runs in the background. One step runs at a time, so an evidence lane the run needs beside a running step goes to an `opus` subagent, as the Extraction rule says. A ready step of code that is not UI waits for the co-lead, and no delegate that `long-runs.md` would start builds it, because that code is the co-lead's. The helper stops a call only at six hours, even one that prints nothing for a long time, such as a browser run queued behind other worktrees (owner's word, 2026-11-26). A runtime may stop a background command sooner, such as the Claude Code CLI, whose Bash tool stops one at its `timeout`, two hours at most. There the lead sets that limit as high as the runtime allows and passes `--timeout` five minutes under it, so the helper's stop comes first and keeps the answer. `cross.mjs` caps a longer `--timeout` at six hours. Each command the co-lead starts still fits the hour that `time.md` gives. The brief gives the co-lead the time the helper stops the call. It has the co-lead kill a proof that cannot end before then and name that proof's command and log, so the lead runs it. A call that the helper stops, or that fails another way, exits 1 and prints what the co-lead said by then after the reason. When the helper stopped the call at the cap, the lead checks that answer as the Checks bullet says. It runs each proof the answer names itself, a browser, simulator or emulator proof included, as that bullet's rerun. Once those proofs end, it briefs what the step still needs as a new call. Such a stop is no friction and no failed call for the Fallback bullet, unless the helper printed no answer after the reason. When the helper itself dies, such as when the lead's session restarts, a watcher the helper started stops the call within seconds. The last line of the stream file then holds the co-lead's answer up to that point. A restart is a resume, so the lead first rereads its rules as the Long runs rule says. The lead reads that answer, checks it the same way and briefs what the step still needs as a new call with `--conversation`. The watcher runs none of the helper's guards, so those checks also read the main checkout's `git status`, which the next call takes as its baseline. That stop is no friction and no failed call for the Fallback bullet either, unless the stream file holds no answer.
  - **What the co-lead owns.** Research and evidence lanes, explore rounds, architecture and API design sketches, perf and hillclimb iterations, a bug's repro and its failing test, code that is not UI, and the proof of behavior that drives a browser, a simulator or an emulator, such as a repro or an end-to-end test, a UI change's included. The two shapes that the Panel review rule has the lead sketch for `architect` are the co-lead's step, and the lead still picks one. A drive through a signed-in site stays with the lead in Claude in Chrome, because the co-lead's browser has no sign-ins. For code that is not UI, the co-lead takes the place of the code delegate in pstack's Feature step 4, so that code needs no delegate worktree. The co-lead writes only in the lead's worktree, the run directory and a detached worktree it adds for a base control, such as the `Introduced-by` check. It runs `node .agents/pstack/setup.mjs` in that worktree first, as the Git rule says, and removes it with `git worktree remove --force` once the control is done. In a perf or hillclimb iteration, the co-lead's answer gives each attempt's result and proof log, and the lead records them in the plan.
  - **Briefs.** Each brief names the step, the run directory and each project skill the step's work loads, such as `verify` for a repro and its proof or `plate-plugins` for a plugin, and tells the co-lead to read each one's `.claude/skills/<name>/SKILL.md` in full before it works. The first brief also tells it to read `AGENTS.md` in full for the project's rules on code, tests and proof. The helper's own brief tells the co-lead which duties stay the lead's: plans, reviews, the writing passes, landing, messages and the stop for missing pstack skills. An agy call returns only once every background task the co-lead started has ended, and a dev server never ends. So the helper's brief also has the co-lead poll each server it starts instead of waiting for its task, and kill every task and remove every probe or control file and worktree before its final message. A probe that edits a tracked file for a moment, such as to add a trace, makes that edit in a detached worktree, never in the lead's, because a stopped call leaves the edit in place and two probes that edit one file restore each other's edits. It leaves a booted emulator or simulator running, because other runs share it. When a call ends, the helper stops every process that carries the call's `PSTACK_SEAT` variable. So a project helper that boots a device every worktree shares starts it with the environment that `cross.mjs`'s `envOutlivingSeat` returns, which lacks that variable.
  - **What the lead keeps.** The lead talks to the owner. It keeps plans and plan pages, UI code and anything visual, the writing passes, landing and the final call on a design. A code delegate on the playbook's models-sheet line writes the UI code and its unit and component specs in the delegate's own worktree, as pstack's Feature step 4 says. The lead reviews that delegate's diff and applies it to its own worktree only between co-lead steps, and it lands a step only between them too. Anything visual includes the hand drive of a change a person sees and its demo clip, which the lead or its `clip` helper records on a dev server the lead starts itself. The lead also writes every piece of prose, such as replies, docs, commit messages and team messages. While a co-lead step runs, the lead edits no file in that worktree and runs no command there that writes one, such as a build or `pnpm check`.
  - **Checks.** Before the lead uses a step's answer, it reads the evidence files the step wrote as well as the answer, and puts back each finding the answer dropped. It reviews the step's diff with `git diff`, reads each untracked file that `git status` lists, and reruns the proof the step claims, or the narrowest check that proves it. It checks a ranking of options for a cheaper path the co-lead left out. When it finds one, the next step's brief gives that path and its evidence, and the co-lead takes it or says why not. When the lead and the co-lead still disagree on a design after that step, the design counts as contested, so it runs an arena as the Panel review rule says, and the lead never overrules the co-lead alone. A disagreement on a fact, such as a bug's cause, is no design question, so the run settles it with the check that tells the two readings apart. A pick that the co-lead makes and these checks leave standing is the run's pick, and the lead keeps going on it without asking the owner (owner's word, 2026-11-26).
  - **Fresh reviews.** A panel seat, an arena runner, a judge and a second reader never run in the co-lead's conversation, and the co-lead never reviews its own work. A Neon seat on a panel is a fresh `cross.mjs` run, as the Panel review rule says. An independent reviewer that a playbook step asks for is a fresh run too, never the lead's review of the co-lead's diff. While a panel round runs, no co-lead step writes a file its seats read.
  - **Guards.** `cross.mjs --colead` runs agy with `--dangerously-skip-permissions` and without its sandbox, because the co-lead runs dev servers, browsers and emulators. The helper refuses a folder that is not a worktree's root and refuses a main checkout. It gives git a pre-push hook that refuses every push, gives `gh` an empty config and drops the GitHub tokens from the co-lead's environment, so a plain `git push` or `gh` command fails. A call that changes the main checkout's `git status` or its diff exits 1 and prints its answer after the warning. agy's edits never pass the Claude Code hook that refuses an edit past the step budget, so the helper counts the worktree's change as that hook does. When the change builds a plan step, the brief gives the co-lead the count and the budget. A call that leaves the step past the budget exits 1 and prints its answer after the count. The lead then splits the step before it reviews the diff. A write there to a file git ignores, such as one in the run directory, does not count. These guards stop accidents, not an adversary. A co-lead that reads a web page can still run any command, so the lead treats each step's commands and diff as untrusted until it has reviewed them.
  - **Fallback.** When a call fails, such as on a usage limit, the lead runs it once more. When that fails too, the rest of the run's co-lead work goes to one `Agent` subagent on the model and effort the sheet line names after `or`. Unlike a code delegate, it starts without `isolation`, so it works in the lead's worktree. Each later step reaches it through `SendMessage`, so it keeps the run's history. The lead logs another `colead` row that names the subagent's model and effort, such as `opus @high`. The hand-back says the run fell back.
  - **Friction.** Until the owner ends the co-lead trial, a lead reports co-lead friction instead of working around it (owner's word, 2026-11-26). Friction is anything in agy, `cross.mjs` or this file that stops, slows or misleads a co-lead step, other than a stop the Neon co-lead bullet calls no friction. Examples are a call that stays open after its stream shows the co-lead's final message, a call that loses its answer, a guard that misses and a brief that leaves out what the step needs. The lead may stop a call that stays open that way. It then reads that call's answer as the Neon co-lead bullet says for a helper that died, and the call staying open is still friction. A usage limit is no friction, because the Fallback bullet handles it. The lead first reviews the failed call's diff as the Checks bullet says. Reading a lost answer back from the step's stream file is one of those checks, not a workaround, and the report below still goes. Then it takes the newest shared helpers and rules, because the fix may already have landed. It rebases onto the fetched base branch. While the worktree holds uncommitted work, it first saves that work as a temporary commit with `git add -A` and `git commit --no-verify`, rebases, then runs `git reset HEAD~1`, so the work is uncommitted on the new base again, with each new file untracked as before. That commit never leaves the worktree and the reset undoes it, so it is no delivery, and a runtime's rules for a commit, such as asking first or verifying first, do not apply to it. A conflict in that rebase is resolved as `land.md` says for land.mjs's own rebase, a generated path by rerunning its entry's command. In a checkout that holds a companion repository, the lead brings the companion's half up to its fetched base too, because the step's proof reads both halves. Checking out only `.agents/pstack` from the base branch would leave the step's count on the old base, so the helpers' own diff would count against the step budget. Then it reruns what the step still needs from the worktree as the failed call left it. When the friction stays, the lead sends a report to the session titled `📌 pstack` with the runtime's cross-session message tool. The report names the friction, the step, its stream and error files, what the lead tried and what the run holds. That session fixes the shared source and messages back once the fix lands. The lead then takes the newest helpers again and reruns what the step still needs. Until that message, the lead holds every step that needs the co-lead and works on other ready work, as the Autopilot rule says for an external gate. With no other ready work left, it ends its turn, and that session's message starts its next one. It never records the friction as a limit. It never moves the step to the Fallback bullet's subagent and never fixes the shared source itself, because one session owns these fixes while the trial runs. When no session with that title is listed, the lead fixes the friction itself, as the Improve the workflow mid-task rule says. Friction in a Neon panel seat or another agy run is reported the same way, while its round goes on as the Panel review rule says.
