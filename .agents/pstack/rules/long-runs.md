# Long runs

This file says how multi-slice runs keep going, coordinate parallel worktrees, and avoid endless replanning. The pstack block in `AGENTS.md` points here. Edit its shared source in `udecode/ustack`.

- **Long runs.** Use pstack's Autonomous run playbook with a checkable exit condition. If the run narrows that condition itself (other than handing off an over-hour measurement per `time.md` or a timing miss), keep `Status: partial` and put dropped items in `## Open work` with `owner:` and `stop:`; only the owner's words make a narrower condition done. Use `redo` to rerun a prior plan at a higher effort or stronger model.
  - **Continuation and pause.** Claude Code uses `/loop`, Codex uses `/goal`, and T3 Code (Antigravity) uses `schedule` / `schedule_task` or `/goal`. On "pause", keep the checkpoint local without a `wip:` commit; never auto-resume paused work. A plan idle for seven days (no commits or log rows) does not resume unless the owner explicitly asks; its next step is a fresh verdict on its review scope (unless its `Status:` waits on the owner). "go" runs all remaining slices without pausing between them.
  - **Roadmap loops.** When a run executes a scope roadmap loop (`/loop verdict <scope>` or owner-authorized roadmap continuation), closing a plan runs the closing verdict and, on `Pursue`, continues directly into Plan and Build for the next roadmap step instead of stopping at `⚪`; it stops only on `Stop`, `Defer`, or a hard stop (`🟠`). When a single-plan run finishes with remaining roadmap steps awaiting an owner call, end as `🟠 <name>` (not `⚪`) unless the roadmap itself is closed or follow-ups are already launched with no owner question.
  - **Re-reading instructions.** After a compaction, rebase, or mid-run sync, re-read any changed instruction files (`AGENTS.md`, models sheet, `.agents/pstack/rules/`, `.agents/playbooks/`) from disk; disk always wins over stale injected copies. Reload any active skill edited mid-run.
  - **Trunk multi-step builds.** Build every step of a plan in one session, landing each step once its proof passes instead of queuing uncommitted steps. Launch independent steps in parallel delegates (`delegate_task` with `isolation: "worktree"` in T3 Code; `Agent` with `isolation: "worktree"` in Claude Code), having each delegate run `node .agents/pstack/setup.mjs` first. Pull one finished step at a time into the lead's worktree, merge/re-verify against landed steps, run any owed panel round, tick the box in the plan, and land via `land.mjs`. Record `step <n> landed as <sha>` after landing (reaching the branch on the next commit). Only the final landing runs the close stop.
- **Run check.** Multi-phase plans give each phase an appetite (number of steps, never time) as a `look` Defaults row. Whenever built steps pass a multiple of the appetite, or at a pivot, update a "Run check" `look` Defaults row summarizing elapsed hours, panel rounds, critical findings, steps ticked/landed, and a proposed cut if the owner wants to narrow scope. A run check is a report only; keep working unless a stop applies.
- **Second plan.** The lead may make a topic's first pivot or new plan iteration on its own. Before starting a third plan on one topic (whatever landed in between), stop and ask the owner under `## Open questions`. State the concrete failing case, what the base commit does, prior art from other editors/projects, the run-check figures, the cheapest option (keep base behavior and document the limit), and the proposed new plan. While waiting on the answer, do not design or write the new plan; keep landing independent steps. When the owner answers, log their choice and proceed.
