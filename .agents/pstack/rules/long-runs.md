# Long runs

This file says how a long or multi-slice run keeps going, hands off and rereads its rules. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Long runs.** Use pstack's Autonomous run playbook with a checkable exit condition. When the run narrows that condition itself, even through a logged scope decision or a Defaults row, the plan's `Status:` stays partial and each part it dropped goes to `## Open work` with its `owner:` and `stop:`. Only the owner's own words make a narrower condition count as done. The block's Time budget rule counts as those words for a long measurement it hands to a suggested task. `Status: executed` after the run's own narrowing claims work the run did not do. To redo a prior run at a higher effort or on a stronger model, treating its plan as a draft, load the `redo` skill. Claude Code keeps going with `/loop`; Codex uses its native `/goal`. On "pause", run pstack's Pause safely playbook without its `wip:` commit; the checkpoint stays local, and the Delivery rule decides every commit. Automatic continuation or compaction never resumes paused work. A plan with no commit on it or its decision log, and no row in any checkout's copy of that log, for seven days does not resume, whatever its `Status:` says, unless the owner's own message asks for that plan (owner's word, 2026-11-13). Its next step is a fresh verdict on its first review scope. The chips ledger pass offers that verdict for each stale plan a task waits on, as chips.md's waits bullet says. A stale plan whose `Status:` waits on the owner waits for the owner instead. In Codex, read an existing goal before creating one, mark a goal blocked only when a model the models sheet names cannot run, as the Autopilot rule says, or when the goal tool's own repeated-blocking threshold is met and no useful progress remains, never for budget or difficulty, and mark it complete only when its exit condition holds and the plan's checks pass, never just to stop. "go" after a plan, or after a review that proposes one, runs every remaining slice without pausing between slices; it adds no commit authority beyond the Delivery rule. Such a build runs pstack's Autonomous run playbook, so it owes the reflect that the block's Improve the workflow mid-task rule asks for, which land.md runs before the close edit. A plan that says each of its steps lands as its own commit builds every step in one session, because starting another session needs the owner's approval, which stops a one-shot run (owner's word, 2026-10-22). Each step lands once its own proof passes, without waiting for the rest of its phase, so a built step never sits uncommitted behind work it does not need (owner's word, 2026-11-11). In a plan that says each of its phases lands as its own commit, each phase is one step here, and its log rows take the phase's number. The session ticks each step's box in the plan before that step lands, so its landed commit carries the tick. Once a step has landed on the branch, the session runs `.agents/pstack/rules/land.md`'s close stop for it, as it does after a last landing, then builds the next step in the same worktree. Its `step <n> landed as <sha>` row is written after that landing, so it reaches the branch with the next step's commit, and a commit still never names its own sha. It starts no other step, through a delegate either, while one is built and not landed. Several delegates may still build one step, and while a step waits to land or lands, the lead may read or reproduce the next step's cases in a worktree of their own, as long as it edits nothing in the landing worktree and logs no row for that step. Once the log records a landed step, `decisions-check.mjs append` refuses a new step's `built: step <n>` row while another step has a `built: step <n>` row and no delivery row `step <n> landed as <sha>`, or `step <n> dropped` for a step that will not land. Only the plan's last landing also runs its playbook's close. When `land.mjs` opens a PR instead of pushing, the session stops there, and its reply names the next step to build once that PR has merged. Report each reversible call with the word that reverses it. Before each gate, such as a panel launch, a writing pass, the trail review or the close, and after every wakeup, the lead re-reads `AGENTS.md`, the models sheet, the pstack plugin pin, the rule files in `.agents/pstack/rules/` and the project playbooks in `.agents/playbooks/` from disk when any of them changed since its last read, and rewrites its open gates from the new text. A rebase, such as the one `land.mjs` runs, can change any of them mid-run, and the lead follows a playbook's current text, not the copy it read earlier. After every compaction, the lead's first todo is to re-read them from disk whatever changed. When the project's SessionStart hook ran `reread.mjs --hook` after the compaction, its output is that re-read. The lead acts on each changed sentence it printed and does not run `--dir` again before its next gate. Any injected copy of an instruction file, after a compaction, a resume or a reminder, can be older than disk; when one disagrees with disk or with the run's own edits, disk wins. It compares each file with its last-read copy sentence by sentence, never through a diff cut at a column, and makes each changed rule its own todo. The lead makes that comparison with `node .agents/pstack/reread.mjs --dir docs/plans/artifacts/reread/<session id> AGENTS.md ~/.claude/pstack-models.md .claude/settings.json .agents/pstack/rules .agents/playbooks` in Claude Code, or with `~/.codex/pstack-models.md ~/.codex/config.toml` in place of the models sheet and settings in Codex, where any directory the session keeps for itself under `docs/plans/artifacts/reread/` serves. It prints each sentence that changed since its last snapshot in full. For a folder it also prints one line that counts its unchanged Markdown files and names its new and removed ones. The lead acts on each changed sentence in a file its run follows. Outside `--hook`, a call without `--dir` and a file prints only its usage. A project's SessionStart hook can run it with `--hook`, which reads the files in the session's own checkout and prints the absolute path of its snapshot directory to pass as `--dir`. That directory is under the main checkout's `docs/plans/artifacts/reread/`, so it outlives a worktree. A sync or `apply` the lead ran itself counts as such a change. After a pin change it reloads each pstack skill it still uses and takes reference paths from the newest base directory that skill prints. After it edits a skill whose mode it is running, it reloads that skill through the Skill tool before its next step. Claude Code's compaction restores only the first 20,000 characters of each skill. After one, `reread.mjs --hook` names the longer skills on its `reload:` line, and the lead reloads each of those whose mode it is running the same way. A mid-run sync reaches the lead only through a later read.
- **Run check.** A plan with phases gives each phase an appetite, the elapsed time the lead expects the phase to take from its start to its last landing, as a `look` Defaults row whose alternative is the owner's own number. Phase 1 starts at the first row of the plan's first decision log, so its appetite covers its planning and plan review. A pivot's new log does not restart it, and a pivot's new plan keeps the phase's appetite unless the owner gives another number. Each later phase starts at the row that records the last landing of the phase before it. Before each gate, such as a panel launch, a pivot or a land, the lead reads the time since the phase's start, without any time the owner paused or held the run. Each time that elapsed time passes another multiple of the appetite, and at each pivot or new plan iteration after the phase's first, the lead writes or updates a run check. A run check is a `look` Defaults row named "Run check". Its pick is to keep going, and its alternative is the cut the lead would make, with the word that applies it. The row gives the hours each stage has taken, read from the log's timestamps, the panel rounds run, the critical findings applied, dismissed and left `open`, the steps ticked and the steps built but not yet ticked, out of all steps, and what has landed. Each line of the cut names the claim it narrows and the later phase that takes that claim, or the Open work item that does. The lead's next reply names the run check in its first lines. A run check is a report. It changes no decision of the plan, so it owes no deviation row and no review. The lead cuts nothing for it, narrows no proof, skips no gate and keeps working, and only the owner's word applies a cut. An appetite is not a frozen budget, so a phase that passes it is no finding for the Autopilot rule's pivot.
