# Compare project methodologies

Determine whether equivalent requests follow the same engineering method across
the named projects. Comparison inspects sources and reports findings. It does
not edit instructions, install skills, regenerate files, or run product work.
An explicit request to apply the findings supplies a separate mutation scope;
follow the existing maintenance or sync method for that scope.

## Establish the comparison

Resolve the named paths or configured project names. One named peer means the
current project plus that peer; an explicit pair defines the comparison. Ask
only when a target cannot be resolved. Configuration identifies possible
targets without authorizing an all-project scan.

Compare methods by their job, including renamed, merged and split owners.
Exclude domain models, product features, frameworks, fixture data, deployment
targets and project-specific API laws. Do not exclude generic execution choices
merely because they live in a project file: activation, authority, testing value,
review budgets, stopping rules and delegation can change the methodology.

## Inspect the effective instructions

Read applicable AGENTS guidance, the engineering entrypoint, matched references,
relevant helpers/templates, discovery metadata and source/install provenance.
Account for global fallbacks and local overrides. A missing project copy is not
a missing capability when a verified global installation supplies it.

Use file inventories and hashes to locate common methods and changed resources.
Compare complete relevant folders, including playbooks, prompts and helpers;
identical entrypoints can load different methods. Exclude generated caches from
source comparisons. Read each material difference in context and trace its
caller. File size, folder counts and matching names do not establish parity.

Check shared-source revisions where available. Compare each installation with
its own recorded provenance and then with the current owned source. An older
valid installation differs from an unrecorded local edit or a stale generated
mirror. Do not assume either project is the canonical or newer implementation.
A cross-project comparison does not require a fresh whole-upstream audit.

Trace equivalent requests through the affected routes: for example, a small
edit, an implementation, an improvement run, a failed proof or an explicit
review. Inspect lifecycle ownership, method triggers, plan/goal activation,
budget and stop semantics, delegation, proof reuse, test value and publication
authority. Select only scenarios relevant to the differences. Describe these
as instruction traces unless actual executions were observed; source parity
does not prove equal speed, quality or completion rates.

## Classify and report

Classify each material difference as:

- **Aligned:** the same method, even when layout or owner names differ.
- **Product adaptation:** domain-specific mechanics; exclude from drift.
- **Explicit policy difference:** a supported operational choice with different
  behavior, such as a review budget. Report it without automatically normalizing it.
- **Methodology drift:** stale shared teaching, inconsistent triggers, missing
  dependencies, contradictory authority or mismatched source/generated output.
- **Unresolved:** insufficient source, provenance or runtime evidence.

Lead with whether the methods align and the consequential exceptions. For each
finding, give both behaviors, their source paths, practical effect and the
smallest reconciliation. State what was excluded and what was actually checked.
Use a compact table when helpful; avoid a self-awarded quality percentage.
Recommend named source-to-target syncs only after verifying those owners.
Preserve product adaptations and explicit user policies. Reuse the current
report or answer directly. Apply an existing direct or standing user Autogoal
request when it covers the comparison; otherwise no native goal is implied.
Do not add another controller, mandatory plan template or independent review panel.
