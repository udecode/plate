# Full workflow and model audits

Use this reference for an explicit broad audit. Ordinary maintenance stays scoped to the changed behavior.

## Establish evidence

Inventory the complete requested set: owned rules, skills, shared/vendor installs, generators, references, helpers, templates, and runtime model/tool mappings. Follow the source chain instead of treating generated mirrors as independent owners. Read each in-scope method fully, loading large sets in manageable batches.

Fetch the upstream revision and official model guidance relevant to the request. Record source URLs, revision/date, and any unavailable content. Keep preserved source, intentional runtime adaptations, and project-specific requirements distinguishable. Do not silently treat a pinned copy as current upstream.

For a model migration, compare current official guidance with the actual runtime and current user instructions. [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra), published September 11 and read September 12, 2026, motivates shorter specific descriptions, conditional references, fewer compulsory itineraries, contextual project instructions and complete-task follow-through. Its advice is evidence for this maintenance method, not a permanent model choice or permission to weaken project requirements. Refresh official guidance for a later migration.

## Choose the structure

Evaluate each skill as keep, reuse upstream, adapt, merge, split, or remove within the user's capability scope. Record each affected capability's old owner, surviving owner, movement or deletion, and proof. Preserve public names and useful examples, prompts and recovery procedures unless their removal is authorized. A full upstream method can be the best choice even when it is long. For a changed pinned upstream entry, retain source revision, license, hashes, exact adaptation and reasons under one maintained owner; remove duplicate remote ownership.

Trace representative requests through their actual loaded owners:

- A small edit: identify the minimum required instructions, actions, and proof.
- A feature or bug: verify the method reaches the real implementation and verification owners.
- A long autonomous task: verify who owns continuation, state, publication, and stopping.
- A verification-only request: confirm diagnosis does not silently become unauthorized repair.
- A workflow change: confirm shared-source maintenance stays within the task's destination scope.

Compare competing instructions, repeated steps, unconditional loads, and unnecessary gates. Count bytes or tokens only as supporting measurements with an explicit method; they do not establish elapsed time or quality. A split helps only if the relevant caller actually stops loading the unused material.

If the user asks for scores, name the criteria and score against evidence: intent preservation, upstream fidelity, ownership clarity, runtime feasibility, and required work. Do not call a proposal the winner based on a self-assigned total alone.

## Execute and check

Apply the selected design directly when implementation is authorized. Migrate callers before deleting owners. Preserve full domain mechanics and useful upstream recovery paths; do not retain competing instructions merely to avoid a large deletion.

Run affected validators and helper checks. Broad changes to discovery, automatic method selection or completion behavior also require paired task trials before adoption:

1. Freeze current instructions, representative task inputs, existing acceptance checks and runtime settings before editing. Reuse established exercises covering a small edit, implementation, writing/planning, real verification and continuity where those capabilities are affected.
2. Run baseline tasks in fresh contexts before source mutation. Run the revised instructions provisionally installed in fresh contexts with identical model, reasoning, tools, inputs and requests. Avoid concurrent writers to shared fixture state.
3. Inspect actual artifacts, command results and available transcripts. Compare outputs blind to treatment for correctness, completeness, evidence and proportionate execution. Time, tokens and loaded instruction volume are diagnostics; a routing classifier or word count is auxiliary evidence only.
4. Require every revised exercise to meet its acceptance without losing a material baseline outcome. False completion, unauthorized expansion or unsupported proof blocks adoption. Preserve failed evidence, repair the responsible instructions and rerun only affected pairs. Withdraw the responsible changes if the acceptance cannot be met.
5. Check a substantive maintenance request and a small adjacent edit so this audit method does not become another unconditional workflow. Report unavailable live/independent evidence honestly; an unrun trial is pending, not passed.

Keep these trials scoped to broad behavioral migrations. Ordinary maintenance uses affected validators, helper checks and a direct request-path inspection. New automated tests still require the project's test-value gate.

Document the final owners, source provenance, meaningful remaining limits, and suggested downstream changes in the existing audit artifact. Avoid parallel plans that disagree about the final design.
