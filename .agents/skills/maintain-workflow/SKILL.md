# Maintain Workflow

Keep reusable methods in one shared source and project requirements in explicit adaptations. Apply this skill to an authorized workflow change; ordinary product edits and wording-only fixes stay with their current owner.

## Select the work

| Request | Method |
| --- | --- |
| `$maintain-workflow` or an affected workflow change | Inspect the instruction chain, repair authorized owners, verify the change and suggest named downstream syncs. |
| `compare <projects>` or a methodology comparison | Use [compare](references/compare.md); report drift and proposed syncs without applying them. |
| `sync` or `sync <source-or-skill>` | Use [sync](references/sync.md) for all in-scope upstream sources or the named source and dependencies. Read-only requests remain read-only. |
| Explicit full audit or model migration | Also use [audit](references/audit.md) for preservation accounting and paired behavioral evidence. |

These are skill modes, not shell commands. Ordinary maintenance does not start a catalog audit, new plan, review panel or full upstream sync.

## Edit the actual owner

Trace the affected rules, references, helpers, templates and install metadata. Follow symlinks and provenance records: a generated `SKILL.md` is discovery, not its own source.

- **Reusable method:** edit its established shared owner within scope. Keep product names, private paths, release rules and infrastructure in the project adaptation.
- **Project adaptation:** preserve local commands, domain mechanics, fixtures, proof targets and publication policy at the project owner.
- **Upstream/vendor:** preserve the complete useful method and license. A changed pinned entry becomes a declared maintained adaptation with the original revision, hashes, exact diff and reasons; remove duplicate remote ownership. Leave unchanged entries upstream.
- **Duplicate:** migrate useful behavior and callers to the canonical owner, then delete it. Trace unclear ownership before writing; unavailable shared source is a source blocker, not a reason to create a competing copy.

One project's correction is evidence for a shared improvement, not authorization to update every project. A local-only request keeps shared changes as concrete proposals.

## Write instructions that earn their load

State the intended behavior change and what must survive. Inspect the actual loading path, including global/project rules and relevant callers.

- **Precise discovery:** put the specific purpose first in a short description. Trigger on the operation or unresolved decision, not a broad topic, file extension, task size or routine completion. Keep explicit invocation available.
- **Conditional loading:** make multi-purpose entrypoints route to the relevant complete method. Preserve useful examples, prompts, recovery paths and domain guidance in reachable references. Split only when a real condition lets a caller skip material; keep small self-contained methods together.
- **Proportional instructions:** prefer outcomes, source facts and necessary constraints over compulsory itineraries. Remove duplicate policy, stale tool mappings and automatic chains through principles, design exercises, reviews, writing passes or extra logs. A selected method keeps its meaningful sequence and proof.
- **Complete outcomes:** keep acceptance and required verification explicit. Continue through authorized implementation, checks and repairs. Preserve latest-user precedence, exact assignments, standing goal requests, one canonical acceptance record and explicit pause/resume. Compaction does not pause or restart work.
- **Useful checks:** retain the proof needed to establish the outcome, including failed observations. Remove needless repetition and rules that prevent checking work. Tests follow the project's value gate; already-passed proof is reused until a relevant change invalidates it.

Replace overlapping guidance rather than appending another policy layer. A shorter file is not proof of a better workflow. Capability removal follows the user's scope; do not silently cut a useful method while changing how it is selected.

For throughput, repeated tool/fixture friction, premature blockers or paused-work repair, use [execution repairs](references/execution.md). For recurring shell, search or artifact-query failures, use [command execution](references/commands.md). These references are conditional, not another intake sequence.

## Verify and install

Carry authorized changes through the shared source and current-project adaptation. Use the real generator for discovery mirrors and the named installer for shared skills; preserve unrelated changes and protected packages.

Run affected source validators and inspect discovery metadata, reference reachability and changed helper behavior. Trace an intended request and a plausible adjacent request that should stay outside the skill. Exercise a changed helper when it matters; metadata validation alone does not prove execution.

Use the existing task record or a short receipt for small maintenance. Do not add source-text tests or application suites for prose. Broad behavioral migrations require the paired trials in [audit](references/audit.md); minor maintenance does not. Distinguish source inference, actual observed behavior and unavailable live actions.

## Suggest propagation

Find candidate projects from configured repository sets and installation records. If `~/.agents/config.json` exists, inspect `syncedRepositories` for sources, named sets and agent destinations. Configuration identifies candidates, not blanket authorization.

Suggest the named skill/rule, verified source and target, and any adaptation conflict. A source edit is not an installation; an uninspected configured project is not confirmed current.

For authorized propagation, follow current `sync-skills` and `skills-update` instructions. Inspect the named dry run and preserve project forks and explicit destinations. Avoid wildcard/all-project refreshes and old remote revisions over unpublished local changes. Global scope is a separate destination; preserve personal instructions.

Ordinary maintenance creates no automation, commit, push or publication. Close with changes, verification, actual installations and useful named sync suggestions.
