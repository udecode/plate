# Reference journey coverage

Use for reference-product parity, migration fidelity, or a contradicted claim that a complete user journey works. Ordinary maintenance of an unrelated feature does not require reference-product discovery.

Start with the accepted outcome and attributable source authority. Inspect the complete reference journey and its retained source contracts independently of the replacement's inventory, components and existing receipts. A checklist derived only from the replacement cannot discover capabilities it omitted. Existing source behavior identifies candidates; explicit exclusions, current product decisions and exact human assignments still control scope.

For a sharing or report journey, trace configure → preview → send → receive → read/respond → reopen, including sender and recipient surfaces. Adapt the stages to the actual operation. Record source-backed roles, states and configuration branches that change content, actions or consequences; do not manufacture every possible combination.

Extend the existing canonical ledger or acceptance mapping with:

| Retained capability and source authority | Reference route, role, state, configuration | Target owner and surface | Expected visible behavior and consequence | Exact proof or uncovered gap | Disposition and next owner |
| --- | --- | --- | --- | --- | --- |

Keep the source-capability denominator distinct from component, operation and receipt counts. Reconcile each discovered capability with the existing acceptance IDs rather than creating a second tracker or lifecycle per finding. Attribute exclusions; an unvisited or omitted source surface remains uncovered.

## Product behavior versus appearance

Rendering is product behavior when it changes what a person can read, understand or act on: content composition and order, an inline full report, recipient-visible context, consent or response summaries, navigation, persistence and reopening all belong in capability coverage. A file list, separate viewers and a downloadable PDF do not establish that a unified HTML report exists. Verify the retained presentation contract on its actual surface.

Typography, decorative spacing, colors and visual resemblance belong to aesthetic comparison unless they change a required interaction, readability or accessibility. Deferring aesthetic parity does not waive product rendering or interaction coverage.

## Bind proof and blockers narrowly

Compare matching reference and target surfaces through the complete retained journey. Inspect preview content and the received result independently: source code, a provider submission, generated PDF or sender preview cannot prove what the recipient receives, reads, responds to or sees after reopening. Bind evidence to route, role, state, configuration and candidate. Reuse a capture for the claims it actually covers; passing components in aggregate cannot close an unobserved transition or missing product surface.

Separate an exact policy decision or human assignment from independent technical coverage. Record which capability the blocker reserves and why; continue other authorized, independent work. Do not choose the policy, fabricate its result or mark the blocked capability complete. A blocked consent policy, for example, does not itself excuse a missing report renderer; implemented rendering does not settle consent policy.

Report retained capabilities as proved, missing, blocked or explicitly excluded using the project's existing dispositions. Source-only discovery can establish a missing owner but cannot claim live parity. Apply the project's testing gate; this mapping requires no new automated tests, exhaustive matrix, duplicate browser session or extra review.
