---
title: "History Editor API"
description: "Read history state, replay complete batches, and control history grouping."
---

History adds an owner-local read group, a replay service, and transaction
controls for the update being built.

## Read API

#### `editor.read.history(): History`

Read the full history value.

#### `editor.read.history.hasUndo(): boolean`

Return whether the undo branch has a surviving mapped batch.

#### `editor.read.history.hasRedo(): boolean`

Return whether the redo branch has a surviving mapped batch. It returns `false`
while a first write holds the redo, which `redos` still lists.

#### `editor.read.history.pending(): "undo" | "redo" | null`

Return the replay direction currently waiting for a live-session owner. Pending
state belongs to this editor runtime and is not included in History JSON,
snapshots, or collaboration.

Use `editor.read.history().undos` and `editor.read.history().redos` when you need
the full immutable arrays. The same group is available as `state.history` inside
`editor.read((state) => ...)`.

## Replay service

#### `editor.api.history.undo(): HistoryResult`

Claim and replay the current undo batch.

#### `editor.api.history.redo(): HistoryResult`

Claim and replay the current redo batch.

```typescript
type HistorySettlement =
  | Readonly<{ status: "applied" }>
  | Readonly<{ reason: string; status: "blocked" }>
  | Readonly<{ status: "failed" }>;

type HistoryResult =
  | HistorySettlement
  | Readonly<{ status: "busy" | "empty" }>
  | Readonly<{ conflicts: readonly string[]; status: "blocked" }>
  | Readonly<{ settled: Promise<HistorySettlement>; status: "pending" }>;
```

Both methods claim the current branch head and return synchronously. A document
batch has applied when the call returns. A live-session batch whose owner is
still working returns `pending` and publishes its pending direction until
`settled` resolves; `settled` never rejects. Document edits, selection updates,
and collaborative imports continue during that wait; another replay returns
`busy` without claiming a batch. Redo also returns `busy` while a first write
holds the redo it cleared.

`blocked` reports a refusal from the live-session owner. `failed` means the owner or the settlement threw; the error
goes to the editor's `lifecycleErrorSink`. With no sink, it goes to
`reportError`, or to `console.error` where `reportError` does not exist.
`blocked` and `failed` both keep that batch at the branch head, except that a
first write that resolves `blocked` takes its step back even while an undo of
that step waits. Invalid runtime use, such as a replay inside an active read or
update, throws. Replay always applies the complete document-wide batch,
including changes in other roots.

#### `editor.api.history.record(effect, value, options?): HistoryRecordResult`

Record one live-session step in its own update, outside any read or update,
and return `recorded`. A read-only view returns `blocked` with `read-only`, and
a guard that refuses the update returns its reason. `record` throws for an
effect without a `replay` owner or that no installed plugin registers, and for
a first write without a `then` method.

`options.firstWrite` takes the promise of the owner's write while it still
runs. Until it answers, the step stays in undo. When the record cleared a redo
and no other live-session replay is pending, History holds that redo: `redos`
still lists it, `hasRedo()` returns `false` and redo returns `busy`.
`History.toJSON(editor)` leaves it out, and so does a restore of a read taken
while History holds it. A later record with its own first write shares the
hold. An edit that History records, a record without a first write, or an
undo that applies drops the held redo. A skipped edit maps it like any other
redo, and redo returns `empty` when no entry survives.

A first write that resolves `blocked` takes the step back and gives back the
redo it held, once no other first write still holds it. One that resolves
`applied` or rejects keeps the step and drops the held redo. A rejection, or
an answer of any other shape, reports with phase `apply` the way a failure
does. Each undo of the step gets a promise of that answer as `firstWrite` in
its replay context until an undo of the step applies. A redo, and a step
recorded without a first write, get `null`.

```typescript
type HistoryRecordOptions<TValue> = Readonly<{
  firstWrite?: Promise<EditorEffectHistoryReplayResult<TValue>>;
}>;

type HistoryRecordResult =
  | Readonly<{ reason: string; status: "blocked" }>
  | Readonly<{ status: "recorded" }>;
```

## Transaction API

#### `tx.history.skip(): void`

Do not save the current transaction to history.

#### `tx.history.merge(): void`

Merge the current transaction into the previous compatible undo batch.

#### `tx.history.newBatch(): void`

Start a fresh undo batch for the current transaction.

## Update policy

#### `editor.update({ history: "skip" }, fn): R | undefined`

Run one update without saving it to history.

#### `editor.update({ history: "merge" }, fn): R | undefined`

Run one update that merges into the previous compatible undo batch.

#### `editor.update({ history: "new-batch" }, fn): R | undefined`

Run one update where the first write starts a fresh history batch, then the
rest of the callback merges into that batch.

Configure a direct write by calling `editor.update(policy)` first.

```typescript
editor.update({ history: "skip" }).text.insert("draft");
```

## Types

```typescript
import type {
  DocumentChange,
  EditorEffect,
  EditorSchemaIdentity,
  Selection,
} from "plitejs";

type History = {
  readonly redos: readonly Batch[];
  readonly revision: number;
  readonly schema: EditorSchemaIdentity;
  readonly undos: readonly Batch[];
};

type Batch = {
  readonly change: DocumentChange;
  readonly effects: readonly EditorEffect[];
  readonly selectionAfter: Selection;
  readonly selectionAfterRoot?: string;
  readonly selectionBefore: Selection;
  readonly selectionBeforeRoot?: string;
  readonly unsettle?: DocumentChange;
  readonly rest?: DocumentChange;
  readonly carried?: readonly CarriedRun[];
};
```

Persist the installed stacks with `History.toJSON(editor)`. Decode them with
`History.fromJSON(editor, json)`, then install the returned value through
`tx.history.restore(...)`. Custom standalone effects belong to an installed
plugin's `effects` resource so their keyed versioned codecs can decode the
batch. Every envelope, versions 4 to 7, requires the current derived or named
schema identity and rejects `null` or mismatched schema semantics before
decoding a batch.

Compatible typing and same-node property updates coalesce from canonical
`DocumentChange` classifications and changed ranges. Grouping fingerprints are
runtime-only; loading persisted history starts a fresh automatic group.
