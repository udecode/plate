Extensions package reusable Plite behavior that should be installed, ordered,
and removed as one unit. Use them when plain app functions are no longer enough.
Plate uses plugins for product-level configured features; raw Plite calls this
runtime unit an extension.

## Smallest Extension

`defineEditorExtension(...)` preserves the literal extension name and lets
`createEditor(...)` infer the installed surface. A complete schema is also an
extension, created with `defineEditorSchema(...)`.

```ts
import { createEditor, defineEditorSchema, schema } from "@platejs/plite";

const ArticleSchema = defineEditorSchema({
  elements: {
    paragraph: {
      content: schema.content.text({ default: "text", min: 1 }),
    },
  },
  id: "article",
  root: {
    content: schema.content.type("paragraph", {
      default: { type: "paragraph" },
      min: 1,
    }),
  },
  unknown: "reject",
  version: 1,
});

const editor = createEditor({
  extensions: [ArticleSchema] as const,
  initialValue: [{ type: "paragraph", children: [{ text: "" }] }],
});
```

Use feature extensions for reusable behavior and partial schema contributions.
Use one complete schema to close the document vocabulary. See
[Schema](19-schema) for the full declaration and compiler model.

## Read And Write Helpers

Use `state` for read helpers. Use `tx` for model writes; direct-safe methods are
also exposed through the matching `editor.update` group.

```ts
import { createEditor, defineEditorExtension } from "@platejs/plite";

const linkTools = defineEditorExtension({
  name: "link-tools",
  state: {
    link(state) {
      return {
        hasSelection() {
          return state.selection() !== null;
        },
      };
    },
  },
  tx: {
    link(tx) {
      return {
        setHref(href: string) {
          tx.nodes.set({ url: href });
        },
      };
    },
  },
});

const editor = createEditor({
  extensions: [linkTools],
});

const canEditLink = editor.read((state) => state.link.hasSelection());

editor.update.link.setHref("https://example.com");

editor.update((tx) => {
  tx.link.setHref("https://example.com");
});
```

This split is the normal authoring path. Reads cannot write by accident, and
writes can still read transaction-local state after earlier writes in the same
update. Wrap a method with `txOnly(...)` when it requires that active state;
Plite omits it from direct update groups. A `tx` helper should exist to perform
Plite model writes. If a helper only opens UI, reads layout, talks to the
network, or coordinates host state, keep it out of `tx`.

## Extension Order

Extensions are named so Plite can compose them deterministically. Use
`dependencies` when one extension needs another installed first.

```ts
import { createEditor, defineEditorExtension } from "@platejs/plite";

const links = defineEditorExtension({
  name: "links",
  api: {
    links: {
      normalizeHref(href: string) {
        return new URL(href).toString();
      },
    },
  },
});

const mentions = defineEditorExtension({
  name: "mentions",
  dependencies: [links],
  tx: {
    mention(tx) {
      return {
        insert(character: string) {
          tx.nodes.insert({
            type: "mention",
            character,
            children: [{ text: "" }],
          });
        },
      };
    },
  },
});

const editor = createEditor({
  extensions: [mentions],
});

editor.getApi(links).normalizeHref("https://example.com");
```

Plite installs `links` transitively before `mentions` because the dependency is
the extension descriptor, not its name. Shared dependencies activate once and
remain installed until their last direct or transitive owner is removed.
`conflicts` also accepts descriptors. Configuration fails for dependency
cycles, duplicate active names, or installed conflicting descriptors.

Use `editor.getApi(descriptor)` when code needs the API owned by a particular
installed dependency. The descriptor preserves the inferred API type and works
while Plite validates a detached configuration candidate. Do not search
dependencies by string or publish a second capability registry.

## Typed Extension Points

Use `defineExtensionPoint(...)` when another package owns an ordered,
typed contribution channel that is not part of the headless model.

```ts
import {
  defineEditorExtension,
  defineExtensionPoint,
} from "@platejs/plite";

type MeasurementSource = {
  measure(): number;
};

const measurements =
  defineExtensionPoint<MeasurementSource>("app:measurement-source");

const measured = defineEditorExtension({
  name: "measured",
  contributions: [
    measurements.of({
      measure: () => performance.now(),
    }),
  ],
});
```

The extension point owns identity and type. Configuration factories and
validators collect its ordered values with
`context.getContributions(measurements)`, so arbitrary strings do not become a
hidden dependency API.

## Activation And Reconfiguration

Keep schema, state, transaction, command, and API declarations on the extension
descriptor. Use `activate(editor, context)` only for synchronous resource
ownership. Register cleanup before activation returns, and defer external work
that must observe the published configuration to `context.afterPublish(...)`.

```ts
const tableNavigation = defineEditorExtension({
  name: "table-navigation",
  config: { initialMode: "text" as const },
  tx: {
    table(tx) {
      return {
        insertRow() {
          tx.nodes.insert({
            type: "table-row",
            children: [{ type: "table-cell", children: [{ text: "" }] }],
          });
        },
      };
    },
  },
  activate(_editor, context) {
    const controller = createTableNavigationController(context.config);

    context.onCleanup(({ reason }) => controller.dispose(reason));
    context.afterPublish(() => controller.start({ signal: context.signal }));
  },
});
```

Plite compiles and validates a detached immutable configuration candidate before
publication. Every functional `api(editor, context)` factory sees the same
declarative schema and descriptor-resolved dependency APIs. Factory results become
visible together in the final candidate passed to
`validateConfiguration(context)`; factory registration order cannot change what
another factory observes. Ordinary editor reads still see the published
configuration. Activation runs only after the candidate passes every validator.
Lifecycle callbacks are synchronous and cannot publish editor writes. Cleanup
receives `remove`, `replace`, or `rollback` as its reason; lifecycle failures
report through the editor's error sink.

Use a named extension slot when configuration must change after editor creation.
The replacement is staged in the surrounding transaction and becomes visible
with the same commit as any document or state changes.

```ts
import { createEditor, defineExtensionSlot } from "@platejs/plite";

const navigationMode = defineExtensionSlot("navigation-mode");
const editor = createEditor({
  extensions: [navigationMode.of(tableNavigation)] as const,
});

editor.update((tx) => {
  tx.extensions.reconfigure(navigationMode, alternativeNavigation);
});
```

When a replacement schema rejects the current document, pass a `migrate`
callback. It receives the immutable current document and candidate schema and
returns the complete candidate document. Compilation, migration, and validation
finish before one document-plus-configuration commit; failure publishes
nothing. See [Atomic Reconfiguration](19-schema#atomic-reconfiguration).

`editor.extend(...)` is the host-level dynamic form. It publishes through the
same candidate lifecycle, accepts the same schema migration callback, and its
cleanup function publishes the matching removal. Prefer a named slot when the
configuration change must commit atomically with other model writes.

## Schema Contributions

Feature extensions add their document vocabulary through the `schema` slot.
Element-owned properties live with the element; cross-cut properties use a
top-level property declaration with an explicit target.

```ts
import { defineEditorExtension, property, schema } from "@platejs/plite";

const tableModel = {
  schema: {
    elements: {
      tableCell: {
        content: schema.content.group("block", {
          default: { type: "paragraph" },
          min: 1,
        }),
        isolating: true,
        keyboardSelectable: true,
        properties: {
          colSpan: property.number({ default: 1, omitDefault: true }),
          rowSpan: property.number({ default: 1, omitDefault: true }),
        },
      },
    },
  },
} as const;
const tableCell = schema.handle.element(tableModel, "tableCell");
const colSpan = schema.handle.property(tableCell, "colSpan");

const tables = defineEditorExtension({
  ...tableModel,
  name: "tables",
  state: {
    table(state) {
      return {
        selectedCellColSpan(element) {
          return state.schema.getElementProperty(element, colSpan);
        },
      };
    },
  },
});
```

When schema semantics depend on extension configuration, put the immutable
value in `config` and return the declaration from a pure schema factory. The
factory receives only the frozen config and extension name.

```ts
import {
  defineEditorExtension,
  property,
  schema,
  target,
} from "@platejs/plite";

const comments = defineEditorExtension({
  name: "comments",
  config: { prefix: "comment_" },
  schema: ({ config }) => ({
    properties: [
      schema.textProperty(
        schema.key.prefix(config.prefix),
        property.boolean({ default: false, omitDefault: true }),
        {
          split: "preserve",
          target: target.group("element"),
          typeChange: "preserve-if-allowed",
        }
      ),
    ],
  }),
});
```

Elements can describe behavior such as `inline`, `void`, `atom`, `isolating`,
`keyboardSelectable`, `readOnly`, `selectable`, and `markableVoid`.
On a non-void element, `keyboardSelectable` gives its non-editable chrome an
exact `NodeSelection` while keeping child text editable; see
[Selection And DOM](16-selection-and-dom#keyboard-selectable-content).
`void: 'editable-island'` keeps the element void for rendering policy while
allowing Plite cursor projection to enter its text children. `contentRoots`
maps each owned slot to its content grammar; the root key is stored at
`element.childRoots[slot]`. See [Roots](13-roots#content-roots) for rendering
and root ownership.

`properties` are descriptors for element-owned fields. Descriptors use
structural JSON equality and can declare canonical defaults. Defaults are read
through `state.schema` or `tx.schema`; they do not require stored duplicate
values.

## Read Middleware

Use `read` to customize a declared core read without adding a one-off root
hook. Register middleware against an `editorReads` descriptor. The descriptor
infers the input, result, editor, and state types.

```ts
import {
  defineEditorExtension,
  editorReads,
} from "@platejs/plite";

const closedSections = defineEditorExtension({
  name: "closed-sections",
  read: ({ around }) => [
    around(
      editorReads.nodes.isSelectable,
      ({ input: { element }, next }) =>
        element.closed === true ? false : next()
    ),
  ],
});
```

Middleware runs in extension order. `next()` delegates once and accepts a
replacement input when needed. The provided `state` is read-only and observes
the active transaction draft when the caller is already evaluating one.
Generator results keep their iteration and cleanup inside the same read
boundary.

Use `editorReads.slice.export` for ordered export projection:

```ts
const cleanExport = defineEditorExtension({
  name: "clean-export",
  read: ({ around }) => [
    around(editorReads.slice.export, ({ next }) => {
      const slice = next();

      return {
        ...slice,
        content: removeTransientProperties(slice.content),
      };
    }),
  ],
});
```

## Commands And Corrections

Use a typed `defineCommand(...)` when an action needs headless evaluation or
extension policy. Its pure builder and extension handlers return `false` or a
frozen `TransactionSpec`; extension `commands` register typed interceptors
without patching editor methods. Extension configuration determines handler
order. See [Commands](06-commands) for the complete flow.

Use `corrections` for deterministic schema repairs triggered by canonical
changed ranges. A correction writes through its provided transaction and must
converge. Keyboard events and host UI remain React or DOM adapter concerns.

## Clipboard And Fragment Policy

DOM clipboard ingress is a typed extension point owned by
`@platejs/plite-dom`. Add `clipboardHandler(...)` to `contributions`. Its
`insertData` callback receives the `DataTransfer`, `next`, and the ingress
`transaction`. Mutate through that transaction and return `true` when the
handler owns the payload. Return `next()` to keep Plite's slice and plain-text
fallback in the same transaction.
Use [Clipboard And Paste](17-clipboard-and-paste) for the full clipboard
pipeline and proof boundary.

Wrap `editorReads.slice.export` to sanitize copied or dragged Plite content,
such as removing local preview marks before host clipboard serialization. Call
`editor.read.slice.export()` when the result is leaving the editor;
`editor.read.slice.get()` returns the structural selection slice unchanged.

Plite's core slice replacement stays structural and schema-fitted. Grid-aware
table paste, such as mapping copied cells onto existing target cells by row and
column, belongs in the table extension's clipboard policy.

## Slot Reference

Start with `schema`, `state`, and `tx`. Reach for the other slots only when
the behavior needs that runtime phase.

| Slot                    | Use it for                                                       |
| ----------------------- | ---------------------------------------------------------------- |
| `name`                  | stable extension identity                                        |
| `enabled`               | declarative inclusion                                            |
| `dependencies`          | descriptors installed before this extension                      |
| `conflicts`             | descriptors that cannot be installed with this extension         |
| `config`                | immutable schema/API/validation/activation input                  |
| `schema`                | immutable element, property, group, and root contributions        |
| `state`                 | read helpers available inside `editor.read(...)`                  |
| `tx`                    | write helpers for atomic and direct `editor.update` calls         |
| `read`                  | typed middleware over `editorReads` descriptors                   |
| `commands`              | pure typed command interceptors                                   |
| `corrections`           | deterministic changed-range structural repairs                    |
| `stateFields`           | typed persisted or runtime state descriptors                      |
| `effectTypes`           | typed commit-effect descriptors and codecs                        |
| `facetProviders`        | derived state providers                                           |
| `selectionKinds`        | custom selection codecs and behavior                              |
| `api`                   | mounted host/runtime services exposed through `editor.api`        |
| `contributions`         | typed ordered values consumed through an extension point          |
| `on.*`                  | transaction, commit, node, and text change handlers               |
| `activate`              | synchronous resource ownership and cleanup registration           |
| `validateConfiguration` | detached candidate validation                                     |

Do not use `api` as a product command bus. A checklist toggle that changes the
document belongs in `tx.checklist.toggle()`. Host services such as DOM focus,
clipboard ingress, history batching, overlays, measurements, or framework
bridges belong in `api`.

Keep product-specific APIs above these raw slots. Frameworks can build richer
feature conventions on top of Plite's smaller extension substrate.

## Advanced TypeScript

The simple form should be your default:

```ts
import { defineEditorExtension } from "@platejs/plite";

const images = defineEditorExtension({
  name: "images",
  schema: {
    elements: {
      image: {
        void: "block",
      },
    },
  },
});
```

Use the curried generic form when library code must bind an extension to a
custom editor type before passing the descriptor.

```ts
import { type Editor, defineEditorExtension } from "@platejs/plite";

type ImageElement = {
  type: "image";
  url: string;
  children: [{ text: "" }];
};

type CustomEditor = Editor<ImageElement[]>;

const images = defineEditorExtension<CustomEditor>()({
  name: "images",
  tx: {
    image(tx) {
      return {
        insert(url: string) {
          tx.nodes.insert({
            type: "image",
            url,
            children: [{ text: "" }],
          });
        },
      };
    },
  },
});
```

Use module augmentation when you need ambient `state.*`, `tx.*`, or `api.*`
names across editor values instead of relying on the inferred editor instance.
That is a library-authoring move, not the first step for an app.

## Helper Namespaces

Plain helper namespaces are still the right shape for stateless checks.

```ts
import { ElementApi } from "@platejs/plite";

const MyElement = {
  isImage(value: unknown) {
    return ElementApi.isElement(value) && value.type === "image";
  },
};
```

Use helper namespaces for pure utilities. Install typed behavior at editor
creation, use `editor.extend(...)` for host-selected dynamic behavior, or
replace a declared slot through `tx.extensions.reconfigure(...)` when the
configuration must share a model transaction.
