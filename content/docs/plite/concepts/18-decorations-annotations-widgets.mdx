Transient UI has three state owners: decorations for paint, annotations for
durable logical ranges, and widgets for out-of-flow targets. Use this page to
choose among `Editable.decorate`, provider-owned decoration sources,
annotations, widgets, and render props.

## Choose the right owner

Do not put every transient UI concern into `decorate`. Pick the smallest owner
that matches its lifetime.

| Need                                                                 | Start with                                                                                     | Owner                  |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------- |
| One editable needs a simple highlight                                | `Editable.decorate`                                                                            | `plitejs/react` |
| Search, diagnostics, or external highlights are shared with other UI | `usePliteDecorationSource` or `usePliteRangeDecorationSource` plus `<Plite decorationSources>` | `plitejs/react` |
| A range has durable identity                                         | `usePliteAnnotationStore` plus `<Plite annotationStore>`                                       | `plitejs/react` |
| UI is anchored to a selection, node, or annotation                   | `usePliteWidgetStore`, `usePliteWidgets`, and `usePliteWidget`                                 | `plitejs/react` |
| Text paint depends on projected slices                               | `Editable renderSegment`                                                                       | `plitejs/react` |
| The UI claim needs browser-visible proof                             | screenshot, DOM selection, displayed selection, and follow-up typing                           | `@platejs/test`     |

Use decorations for paint. Use annotations when a range needs identity. Use
widgets when UI hangs off a node, selection, or annotation.

## Rendering pipeline

Projection is a React rendering layer, not a second document model.

| Stage          | What happens                                                                                                  | Owner                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| Source         | `decorate`, decoration sources, annotation stores, and selection sources provide ranges.                      | `plitejs/react`                      |
| Projection     | Sources are projected onto runtime text ids and split into slices.                                            | `plitejs/react`                      |
| Render         | `Editable` renders projected text through `renderSegment`, `renderLeaf`, `renderText`, and element renderers. | `plitejs/react`                      |
| Out-of-flow UI | Sidebars, popovers, toolbars, and widgets read annotation or widget snapshots.                                | App UI plus `plitejs/react`          |
| Commit refresh | Editor commits name the affected projection node keys when possible.                                         | `plitejs` and `plitejs/react` |
| Proof          | Browser tests verify visible highlights, selection, focus, and follow-up editing.                             | `@platejs/test`                          |

Keep document data in Plite nodes, roots, and document meta. Keep render
payloads small.

## Decorations

Use `Editable.decorate` for a local highlight that belongs to one editable.

```tsx
<Editable
  decorate={([node, path]) => {
    if (!TextApi.isText(node)) return [];

    const start = node.text.indexOf(query);

    return start === -1
      ? []
      : [
          {
            anchor: { path, offset: start },
            data: { search: true },
            focus: { path, offset: start + query.length },
          },
        ];
  }}
  renderSegment={(segment, children) =>
    segment.slices.some((slice) => slice.data?.search) ? (
      <mark>{children}</mark>
    ) : (
      children
    )
  }
/>
```

Move to provider-owned decoration sources when ranges are shared with sidebars,
toolbars, search panels, diagnostics, or other UI.

```tsx
const searchSource = usePliteRangeDecorationSource(editor, {
  id: "search",
  read: ({ snapshot }) => findSearchRanges(snapshot, query),
  revision: query,
});

return (
  <Plite decorationSources={[searchSource]} editor={editor}>
    <Editable renderSegment={renderSearchMatch} />
  </Plite>
);
```

Use `decorateDirtiness` and `decorateRuntimeScope` when a decoration callback
depends on external projection state and can name which runtime targets should
refresh.

## Annotations

Annotations attach durable ids to ranges. They are the right owner for comments,
suggestions, external diagnostics, and review markers.

```tsx
const annotations = comments.map((comment) => ({
  anchor: comment.anchor,
  data: comment,
  id: comment.id,
  projection: { tone: comment.tone },
}));

const annotationStore = usePliteAnnotationStore(editor, annotations);

return (
  <Plite annotationStore={annotationStore} editor={editor}>
    <Editable renderSegment={renderCommentSegment} />
    <CommentsSidebar />
  </Plite>
);
```

`data` is app-facing metadata. `projection` is the small render-facing payload
copied into text slices. Keep comment bodies, permissions, resolved state, and
audit events in the app or sync service.

## Widgets

Widgets describe UI anchored to nodes, selections, or annotations. They are
useful for comment popovers, inline toolbars, floating action buttons, and
side-panel rows that need resolved visibility.

```tsx
const widgets = comments.map((comment) => ({
  data: { label: comment.label },
  id: `comment-widget:${comment.id}`,
  target: { annotationId: comment.id, type: "annotation" },
}));

const widgetStore = usePliteWidgetStore(editor, widgets, {
  annotationStore,
});
```

Use `usePliteWidgetIds(widgetStore)` when a list needs stable membership,
`usePliteWidget(widgetStore, id)` when one component watches one widget, and
`usePliteWidgets(widgetStore)` only when a deliberate aggregate consumer needs
the complete snapshot. Position one widget with
`usePliteWidgetGeometry(widgetStore, id, { editableRef })`; the exact Editable
ref prevents geometry from leaking between mounted views.

## Performance Rules

Transient rendering should reduce render work, not hide it.

| Rule                           | Why                                                                                                                    |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Hoist render callbacks         | Stable `renderElement`, `renderLeaf`, `renderText`, and `renderSegment` props avoid avoidable text rerenders.          |
| Prefer source-scoped refresh   | Decoration and annotation sources can refresh the ranges they own instead of rerunning one global `decorate` callback. |
| Keep projection payloads small | Large objects in `projection` make text-slice comparison and rerender debugging harder.                                |
| Prove visible behavior         | Overlay correctness needs screenshot or DOM-visible proof when the bug is visual.                                      |

Use [Improving Performance](../walkthroughs/09-performance) for render and
huge-document guidance.
