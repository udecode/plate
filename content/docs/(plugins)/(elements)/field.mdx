A field is a typed blank in a document that one role fills, such as a tenant's name, a start date, a checkbox or a signature. Each field is an inline void `field` element with a `kind`, a `role`, a `label` and a `fieldId` that no other field in the document holds. A field's `condition` names another field by that id. Plate checks roles, never users. Your app decides which person fills which role.

<ComponentPreview name="field-demo" height="1340px" />

The demo is a lease template for a landlord and a tenant. Insert a field from the toolbar's menu, click a field to change its settings, and read the HTML, Markdown and Word panels under the editor. Pick Fill as landlord or Fill as tenant above the editor to fill the lease as that role. Submit checks that role's answers after the answers of the roles that submitted before it. The Submission panel then shows each refusal, or the filled document as static output with the roles it still waits on.

<PackageInfo>

## Features

- Inline void `field` element of six kinds: text, number, date, checkbox, choice and signature.
- A role per field, a label, and an optional required flag, default, choice options and value, each checked against the field's kind.
- A condition that names another field by its `fieldId` and tests that field's value. A field whose condition fails is skipped, so it needs no answer.
- An optional `name` that gives the fields of one role one answer, so a question the document asks twice is answered once.
- `insert` and `update` commands that refuse a setting or condition that does not fit, and reads that report what is wrong with each field and whether it applies.
- A fill-only view of one role, which takes that role's answers, refuses every other local change and undoes only that role's answers.
- `applyFieldValues`, which checks each role's answers against the template on a server and builds the filled document.
- New ids for the fields a paste, a drag copy, a duplicate or a table fill copies, which keep their names, with copied conditions that name the copies.
- HTML and Markdown that keep every property, and Word export that keeps each answer and reports the settings it drops.
- A field chip with a settings popover that mutes a skipped field, an insert menu, and a static renderer that shows each answer in place or a blank line, in the registry UI.

</PackageInfo>

## Value shape

A field sits inside a paragraph, like a date or a mention.

```json
{
  "type": "paragraph",
  "children": [
    { "text": "Tenant name: " },
    {
      "type": "field",
      "fieldId": "f_k2x9",
      "kind": "text",
      "role": "tenant",
      "label": "Tenant name",
      "name": "tenant_name",
      "required": true,
      "children": [{ "text": "" }]
    },
    { "text": "" }
  ]
}
```

| Property | Type | Notes |
|----------|------|-------|
| `type` | `'field'` | Inline void element owned by `BaseFieldPlugin`. |
| `fieldId` | `string` | Unique in the document. A new field gets a random `nanoid`. |
| `kind` | `FieldKind` | `'text'`, `'number'`, `'date'`, `'checkbox'`, `'choice'` or `'signature'`. Required. |
| `role` | `string` | The role that fills the field, such as `'tenant'`. Required. |
| `label` | `string` | Required. The chip shows it, and HTML, Word and plain text show it in brackets when the field has no answer. |
| `name` | `string` | Fields of one role that share a name hold one answer, see [Names](#names). |
| `required` | `boolean` | Marks a field that needs a filled answer while it applies. `applyFieldValues` refuses a submission that leaves it unfilled. |
| `defaultValue` | `FieldValue` | A value of the field's kind. |
| `options` | `FieldOption[]` | Choice fields only. Each option is `{ value, label }`, and no two share a `value`. |
| `value` | `FieldValue` | The answer. A field is unfilled without one, or when `fillsField` says its answer does not fill it. |
| `condition` | `FieldCondition` | `{ ref, test, value? }`, see [Conditions](#conditions). |
| `children` | `[{ text: '' }]` | Required child of an inline void element. |

## Kinds

Each kind fixes the shape of its value and the tests a condition on it may use. `fitsField(field, value)` from `platejs/field` says whether a value fits a field's kind, and `FIELD_TESTS` lists each kind's tests.

| Kind | Value | Tests |
|------|-------|-------|
| `text` | a string | `filled`, `blank`, `equals`, `not-equals` |
| `number` | a finite number | `filled`, `blank`, `equals`, `not-equals`, `above`, `below` |
| `date` | an ISO date, `YYYY-MM-DD` | `filled`, `blank`, `equals`, `not-equals`, `above`, `below` |
| `checkbox` | `true` or `false` | `equals`, `not-equals` |
| `choice` | one option's `value` | `filled`, `blank`, `equals`, `not-equals` |
| `signature` | a string your app owns, such as a stored image's id | `filled`, `blank` |

A choice stores the option's `value`, so renaming an option's `label` keeps every answer and condition that names it.

`fillsField(field, value)` from `platejs/field` says whether a value is a filled answer for a field. `required` and the `filled` and `blank` tests read the same rule. A filled answer is a ticked checkbox, or a value that fits the field's kind. A text or signature answer also needs a character that JavaScript's `\s` does not match. So `false`, an empty text and a text of spaces fit a field but do not fill it, and `0` fills a number field.

```ts
import { fillsField } from 'platejs/field';

fillsField({ kind: 'text' }, '  '); // false
fillsField({ kind: 'number' }, 0); // true
fillsField({ kind: 'checkbox' }, false); // false
```

## Roles

Each field names the role that fills it, such as `landlord` or `tenant`. A role is any string. Plate stores it and never checks who a user is. Your app maps each person to a role, as it maps each comment to its author.

A [fill-only view](#fill-as-one-role) stops one role from changing another role's field, or the text around it, in that editor. An app that collects answers from several people still checks each role's answers on its server, with [`applyFieldValues`](#apply-answers-on-the-server).

The settings popover offers the roles the document's fields already use, and takes a new one.

## Names

A `name` says that fields of one role ask for the same answer, such as a lease that asks for the tenant's name at the top and again by the signature. Fields of one role that share a name hold one answer. The same name in two roles is two answers. A field with no name works by its `fieldId` alone.

A name is a text that is not empty, has no whitespace at either end, and holds no control character, line or paragraph separator or lone surrogate. Loading, `insert`, `update` and a plain `tx.nodes.set` refuse any other name. In the registry UI, the settings popover's Name input sets a field's name and shows an error for a name the rule refuses.

`update` writes a `value`, a cleared one included, to every field of the role that shares the field's name, in the same commit and the same undo step. No other setting reaches the other fields. In the demo, the lease asks for the tenant's name twice under one name, so typing it in one place fills the other, and undo takes it back in both.

Fields of one role that share a name must share their kind, the values of their options and their condition. A default takes no part. Two conditions match when they name the same field, or fields of one role and name, with the same test and value. Each field of a name whose fields differ reads `name-conflict`, and `update` then writes a value to its own field alone. `insert` and `update` never refuse a name conflict, so an author can change the fields of a name one at a time.

Each field of a name whose fields hold different values reads `answer-conflict`. An empty text and no value differ, and so do `false` and no value. `insert` and a paste write no other field. So a field that joins a name with another value, or with none, reads `answer-conflict` until an `update` writes a value to a field of that name, which writes every field of it.

## Insert and update

`insert` takes a field's settings and returns its new `fieldId`. Its second argument takes node insert options, such as `at` and `select`.

```tsx
import { BaseFieldPlugin } from 'platejs/field';

const fieldId = editor.plugin(BaseFieldPlugin).update.insert({
  kind: 'text',
  label: 'Tenant name',
  name: 'tenant_name',
  required: true,
  role: 'tenant',
});
```

`insert` throws when a value, default or options do not fit the kind, when the settings name a `fieldId` or a name the [name rule](#names) refuses, or when the condition names no field, or a test or value that the named field's kind does not take.

`update` changes the settings or value of the field that holds a `fieldId`. A setting given as `undefined` is removed. A `value` also goes to every other field of the role and name.

```tsx
editor.update((tx) => {
  tx.plugin(BaseFieldPlugin).update(fieldId, { value: 'Ada Lovelace' });
});
```

`update` throws, and changes nothing, when:

- no field holds `fieldId`;
- a setting the patch names does not fit the field's kind;
- the patch names a `name` the name rule refuses;
- the patch removes `kind`, `role` or `label`, or names `fieldId`;
- the condition names no field, a test or value that the named field's kind does not take, or a field it did not name before whose chain of conditions leads back to this one.

A patch that changes `kind` or `options` also drops each value, default and options that the field no longer fits. Turning a number field with a default into a date field drops the default. The field keeps its `fieldId`.

## Conditions

A condition says when a field applies. It applies when the field whose `fieldId` is `ref` passes `test`. Every test but `filled` and `blank` compares against `value`, which takes the shape of the named field's value. The demo's Pet name field, which the tenant fills, applies when the landlord's Pets allowed choice is `yes`:

```tsx
editor.update((tx) => {
  tx.plugin(BaseFieldPlugin).update(petNameId, {
    condition: { ref: petsId, test: 'equals', value: 'yes' },
  });
});
```

The popover's Show when list offers the field the condition names and every other field whose conditions do not lead back to this one. Its test list offers only the tests that field's kind takes.

The editor never hides a field. A field whose condition fails is skipped. It needs no answer even when it is `required`, and `applyFieldValues` refuses a filled answer for it. A condition tests the answer of the field it names:

- `equals` holds when the answer is `value`, and `not-equals` when it is not, no answer included.
- `above` and `below` compare numbers, and ISO dates as dates. Neither holds without an answer.
- An answer that does not fit its field's kind counts as no answer, and so does the answer of a field that is skipped itself.
- A checkbox with no answer reads as `false` once its role is done answering. In the editor, that holds for a checkbox of the role that fills the field being read. In `applyFieldValues`, it holds once the checkbox's role has submitted.

`update` refuses a condition that would close a loop, such as A naming B while B names A, or a field naming itself. A new test or value on a field of a loop passes. A loop can still come from a loaded document, a plain node write or two peers' updates made at the same time, and each of its fields then reports `condition-loop`.

## Read fields and their problems

`read.field(fieldId)` returns the field that holds an id, in any root, or `null`. It looks up that field, then one field for each condition it follows along the chain. `read.fields()` returns every field of the document in reading order. Each read is a `FieldRead`: `{ applies, fieldId, node, problems }`.

```tsx
import { BaseFieldPlugin } from 'platejs/field';

const fields = editor.plugin(BaseFieldPlugin).read;

const tenant = fields.field(tenantId);
const broken = fields.fields().filter((field) => field.problems.length > 0);
const skipped = fields.fields().filter((field) => field.applies === false);
```

| Problem | When |
|---------|------|
| `missing-target` | No field holds the id its condition names, such as after that field is deleted. |
| `unsupported-test` | The kind of the field its condition names does not take the condition's test. |
| `invalid-value` | Its value, default or options do not fit its kind, or its condition's value does not fit the test or the named field's kind. |
| `condition-loop` | Its condition names a field whose chain of conditions leads back to it, such as A naming B while B names A. |
| `name-conflict` | A field of its role and name has another kind, other option values or another condition. |
| `answer-conflict` | A field of its role and name holds another value, or none. |

`insert` and `update` refuse a write that would cause one of the first four problems. They never refuse a name or answer conflict, which the read reports. A problem comes from a later edit, such as deleting or changing the field a condition names, or from a write that skipped the commands, such as a plain `tx.nodes.set` or a loaded document.

`applies` says whether the field applies under its condition. It reads the answers the document holds now, along the whole chain of conditions, as the field's own role reads them:

- `true` for a field with no condition, a condition that has a problem or one in a loop, and a condition that holds.
- `false` for a skipped field, whose condition fails.
- `null` while it depends on an answer another role has not given, such as the tenant's Pet name before the landlord picks Pets allowed. Only `applyFieldValues` knows which roles have submitted, so the editor reads such a field as waiting.

A field whose condition names a skipped field is decided, even when another role owns that field.

In React, `useFieldRead(fieldId)` from `platejs/field/react` reads one field, its problems and whether it applies. A commit that changes an element reads it again, and the component renders again only when the field, its problems or `applies` changed. The registry chip uses it to show a warning when the field its condition names is deleted, and an undo clears the warning. The chip also mutes a field whose `applies` is `false` and marks it skipped. The chip of a field that waits is not muted.

```tsx
import { useFieldRead } from 'platejs/field/react';

const field = useFieldRead(element.fieldId);
const problems = field?.problems ?? [];
const skipped = field?.applies === false;
```

## Fill as one role

Set `fillRole` to open a fill-only view of one role. The editor then takes answers for that role's fields and refuses every other local change, so a tenant fills the tenant's fields and changes nothing else.

```tsx
import { FieldPlugin } from 'platejs/field/react';
import { useCreateEditor } from 'platejs/react';

import { FieldElement } from '@/components/editor/field';

const editor = useCreateEditor({
  initialValue: template,
  plugins: [
    // ...otherPlugins,
    FieldPlugin.configure({
      component: FieldElement,
      initialState: { fillRole: 'tenant' },
    }),
  ],
});
```

The demo switches one editor between authoring and each role through the plugin store, and `null` returns to authoring:

```tsx
editor.plugin(FieldPlugin).store.set({ fillRole: 'landlord' });
editor.plugin(FieldPlugin).store.set({ fillRole: null });
```

`usePluginStore(FieldPlugin, 'fillRole')` from `platejs/react` reads the role in a component. The role is editor state, so every view of one editor fills as the same role. Switch it between updates. A switch writes nothing to the document and leaves undo and redo as they are.

While a role is set:

- The registry chip of the role's field opens a popover with an input for the answer and a Clear button, and the role's checkbox ticks and unticks on click. A chip whose answer holds a pending suggestion says it waits for review and opens nothing. Another role's chip opens nothing, no chip drags, and the insert menu is disabled.
- The editor refuses a local commit that writes anything besides a fitting or cleared answer on the role's fields. Typing, paste, cut, a drop, Enter and AI writes change nothing. A refused update throws nothing to its caller and changes nothing.
- Selection, state fields without `persist` and effects that neither persist nor sync to peers pass, so a person can still select and copy.
- Undo and redo take back only the role's own answers. Undo stops at the first step that changed anything else, such as the author's edit, and returns `{ reason, status: 'blocked' }`. The first answer after a switch is its own undo step, so an answer typed right after a switch takes two undos.
- A document replacement, such as `tx.value.replace` or loading another template, is refused, and so is a plugin reconfiguration. Load the template and configure plugins before you set the role, or clear the role first.
- A comment lands, because creating its thread is a local effect. Your app decides whether people may comment in a fill view. The comment adds an undo step, and undo stops at that step, so the answers before the comment can no longer be undone.

A peer's change passes whole. Every commit tagged `collaboration` passes, so collaborators keep one document. Apply a peer's Yjs update from your provider's events, never from inside an editor update. A local write made inside a peer's change takes its `collaboration` tag, passes and never reaches peers. For the same reason, a Yjs `UndoManager` that your app drives itself, or a local update that your app tags `collaboration`, passes the fill check.

The fill check runs in the field plugin's `activate`, and the undo step boundary in its `corrections`. A plugin that extends the field plugin with its own `activate` or `corrections` replaces them, so put that work in a companion plugin.

The fill check runs in the person's browser, where anyone can run their own code. Your server assigns each person's role and checks each submission with `applyFieldValues`.

## Submit answers

A client reads one role's answers from the editor and posts them. The server checks every role's answers against the template it saved, and keeps the filled document.

### Read a role's answers

`read.submission(role)` returns a `FieldSubmission`, `{ role, values }`. `values` holds the `value` of each field of the role that has one, keyed by `fieldId`.

```tsx
import { FieldPlugin } from 'platejs/field/react';

const submission = editor.plugin(FieldPlugin).read.submission('tenant');
// { role: 'tenant', values: { tenant: 'Grace Hopper', 'pet-name': 'Milo', rules: true } }
```

Fields of one name keep their own keys, so the submission holds the answer once for each of them. The submission keeps `false`, `0`, an empty text, a text of spaces and a value that no longer fits its field's kind, so the server judges each of them. It leaves out a field with no `value`, so a checkbox never touched and one ticked and then unticked stay apart.

### Apply answers on the server

`applyFieldValues(template, submissions, options?)` from `platejs/field` checks each role's answers and builds the filled document. It imports no React and checks each submission's shape itself, so a server passes parsed JSON straight in. In this route, `frozenTemplate` is the template your app saved, `accepted` holds the submissions it accepted before, and `saveFilled` stores the result.

```ts
import { applyFieldValues } from 'platejs/field';

const result = applyFieldValues(frozenTemplate, [...accepted, submission]);

if (!result.ok) {
  return Response.json({ refusals: result.refusals }, { status: 400 });
}

await saveFilled(result.document);
```

- `template` is the authored document as your app saved it, with its `fieldId`s and no answers, so the fill view and `applyFieldValues` start from the same ids. It takes a `Value` or a document with named roots, and `result.document` has the same shape. `applyFieldValues` reads fields in the main root and each named root, never in `meta` or records.
- `submissions` lists each role's submission in the order the roles submitted. Each one is checked against the roles before it plus its own answers.
- `options.type` names the field element's type when your app renamed it with `schema.override`. It defaults to `field`.

The filled document is the template with each accepted answer set as its field's `value`. A default stays a setting and never becomes an answer.

On success, `pending` lists each role that has not submitted and holds a required field that applies or waits. It also lists the role whose answer each such waiting field needs next. An optional field never puts a role in `pending`. The demo shows `pending` as Waiting on.

### Refusals

On a refusal, `result` is `{ ok: false, refusals }` with at least one refusal. When the template has refusals, the result lists all of them and checks no submission. Otherwise it lists the refusals of the first submission that has any.

| Code | When |
|------|------|
| `invalid-template` | A template field holds an answer (`answered`), lacks a `fieldId`, holds anything but one text or has a kind, role, label, setting or condition of the wrong shape (`malformed`), repeats a `fieldId` (`duplicate-id`), or has a problem a read reports, `condition-loop` and `name-conflict` included. The refusal names the `problem`, the field's `path`, its `root` in a named root, and its `fieldId` and `name` when it has them. |
| `invalid-submission` | A submission is not an object with a `role` string and a `values` object. The refusal names its `index`. |
| `duplicate-role` | A role already in the list submits again. |
| `unknown-role` | The role owns no field. |
| `unknown-field` | An answer names no field of the template. |
| `wrong-role` | An answer is for another role's field. |
| `invalid-value` | An answer does not fit its field. |
| `waiting` | A field of the role waits on a role that has not submitted, which `waitsOn` names. It is reported even when the field's answer is refused too. |
| `skipped` | A field of the role is skipped and holds a filled answer. An unfilled answer stays as written, so clearing the answer or unticking the box ends the refusal. |
| `missing-required` | A required field of the role applies and has no filled answer. |
| `answer-conflict` | Once the role's answers apply, the fields of one of its names hold different values. The refusal names the `name` and lists every field of the name in document order as `fieldIds`. A name gets none when the submission already refused one of its fields as `invalid-value`, `waiting` or `skipped`. A required field left out does not stop it, so it can come beside `missing-required`. |

`invalid-submission`, `duplicate-role` and `unknown-role` come alone. The other submission refusals name the `role`, and the `fieldId` of their field and its `name` when it has one. An `answer-conflict` names `fieldIds` instead of a `fieldId`. The result lists every refusal of that submission.

In a template whose landlord's Rent field is named `rent`, and whose tenant's two name fields share `tenant_name`:

```ts
applyFieldValues(template, [{ role: 'landlord', values: {} }]);
// { ok: false, refusals: [{ code: 'missing-required', fieldId: 'rent', name: 'rent', role: 'landlord' }] }

applyFieldValues(template, [
  { role: 'tenant', values: { tenant: 'Ada Lovelace', 'tenant-again': 'Ada' } },
]);
// { ok: false, refusals: [{ code: 'answer-conflict', fieldIds: ['tenant', 'tenant-again'], name: 'tenant_name', role: 'tenant' }] }
```

In the demo, the tenant's Submit before the landlord's gets a `waiting` refusal, because Pet name waits on the landlord's Pets allowed. When the landlord submits No, a pet name the tenant types anyway is refused as `skipped` until it is cleared.

A template where two roles each wait on the other passes, because a third role's answer can end the wait by making a field along the chain skip. While both fields still wait, the role that submits first is refused as `waiting` on the other.

### Print the filled document

Render the filled document with `BaseFieldKit` through `platejs/static`, and make its PDF from that output. Static output shows a field other than a checkbox as a blank line when it has no filled answer, while `editor.api.html.serialize()` writes the label in brackets for a field with no answer.

```tsx
import { createEditor } from 'platejs';
import { renderStaticHtml } from 'platejs/static';

import { BaseFieldKit } from '@/components/editor/field-static';

const filled = createEditor({
  initialValue: result.document,
  plugins: [
    // ...otherPlugins,
    ...BaseFieldKit,
  ],
});

const { data } = await renderStaticHtml(filled);
```

## Copy and paste

A field keeps its `fieldId` through a move, a drag move included, through an undo that brings it back and when a saved document loads. A copy gets new ids:

- A paste, a drag copy, `tx.blocks.duplicate` and a table fill give each field they copy a new id and keep its name. A copied condition that names a field in the same copy names that field's copy.
- A copied clause can hold a named field together with the unnamed field its condition names. The copy's condition then names the copied field, so the two fields of the name test different fields and both read `name-conflict`. Give the condition's field and its copy one name, and the conflict ends.
- A copied condition whose field was not copied, or did not land, keeps naming the original.
- A paste into a table cell selection copies once per cell, so a condition in each cell names the copy in its own cell.
- A paste into another document gets new ids too.
- Cut and paste gives the field a new id, so a condition elsewhere that named it reports `missing-target` until an undo.
- An app that copies a field with `tx.schema.copy` and inserts the result gets a new id, and the copy's condition keeps naming the original.

In Suggesting mode, a change from a field to a mention shows the field as deleted beside the inserted mention, so rejecting it keeps the field and its `fieldId`.

## HTML

`editor.api.html.serialize()` writes each field as a `span` with one `data-field-*` attribute per property. The span's text is the answer, a choice as its option's label, or the label in brackets when the field has no answer. The id, kind, label, name and role attributes hold plain text, and the others hold JSON:

```html
<p>Pets allowed? <span data-field-id="pets" data-field-kind="choice" data-field-label="Pets allowed" data-field-name="pets_allowed" data-field-options="[{&quot;label&quot;:&quot;Yes&quot;,&quot;value&quot;:&quot;yes&quot;},{&quot;label&quot;:&quot;No&quot;,&quot;value&quot;:&quot;no&quot;}]" data-field-required="true" data-field-role="landlord" data-field-value="&quot;yes&quot;">Yes</span> Pet name: <span data-field-condition="{&quot;ref&quot;:&quot;pets&quot;,&quot;test&quot;:&quot;equals&quot;,&quot;value&quot;:&quot;yes&quot;}" data-field-id="pet-name" data-field-kind="text" data-field-label="Pet name" data-field-name="pet_name" data-field-required="true" data-field-role="tenant">[Pet name]</span></p>
```

Parsing that HTML reads every property back. A span needs `data-field-kind`, `data-field-label` and `data-field-role` to read as a field. A pasted HTML template gets new ids, and its conditions name the copies.

The demo's HTML panel serializes with `lossPolicy: 'allow'`, because the date element has no HTML encoder. The panel lists one `html-unsupported-content` line for the date it drops.

## Markdown

Markdown writes each field as a `<field>` tag with every property, the `fieldId` and the condition included:

```md
Pets allowed? <field kind="choice" label="Pets allowed" name="pets_allowed" options="[{&quot;label&quot;:&quot;Yes&quot;,&quot;value&quot;:&quot;yes&quot;},{&quot;label&quot;:&quot;No&quot;,&quot;value&quot;:&quot;no&quot;}]" required role="landlord" value="yes" fieldId="pets" /> Pet name: <field kind="text" label="Pet name" name="pet_name" required role="tenant" condition="{&quot;ref&quot;:&quot;pets&quot;,&quot;test&quot;:&quot;equals&quot;,&quot;value&quot;:&quot;yes&quot;}" fieldId="pet-name" />
```

The reader needs `kind`, `label` and `role`. A tag without them stays as text, with a `markdown-unsupported-node` diagnostic. A pasted Markdown template gets new ids, and its conditions name the copies.

## Word

Word has no field element. Word export writes each field's answer as text, a choice as its option's label, or the label in brackets when the field has no answer. It needs no static field component, so a headless export keeps the answers.

```tsx
import { exportDocx } from 'platejs/docx/export';

const result = await exportDocx(editor);
const dropped = result.diagnostics.filter(
  (diagnostic) => diagnostic.code === 'property-dropped'
);
```

The export drops each field's id, kind, role, name, settings and condition. It reports them with one `property-dropped` warning whose message is "Word keeps each field answer and drops its name and settings.", whose `feature` is `field` and whose `count` is the number of fields. The warning never refuses an export, under `lossPolicy: 'allow'` or `'reject'`. The demo's Word panel shows that warning, and its count goes up as you insert fields.

Plain text, through `serializePlainText` from `platejs`, writes the same text as Word.
