字段是文档中由一个角色填写的有类型的空白处，例如租客姓名、起租日期、复选框或签名。每个字段是一个行内 void `field` 元素，带有 `kind`、`role`、`label`，以及文档中其他字段都不持有的 `fieldId`。字段的 `condition` 通过 `fieldId` 检查一个或多个字段。Plate 只检查角色，从不检查用户。由你的应用决定哪个人填写哪个角色。

<ComponentPreview name="field-demo" height="1340px" />

示例是一份房东、租客和 `应用` 角色之间的租赁合同模板，`应用` 角色持有地址和月租。从工具栏的菜单插入字段，点击字段修改它的设置，并查看编辑器下方的 HTML、Markdown 和 Word 面板。在编辑器上方选择以房东身份填写或以租客身份填写，即可以该角色填写合同。在编辑模板视图中，Fill from sample data 用一条示例记录提交应用的答案，并打开租客的填写视图，其中租客姓名取自同一条记录。Submit 会在之前已提交角色的答案之后检查该角色的答案。随后 Submission 面板显示每条拒绝原因，或者以静态输出显示填写后的文档，以及它仍在等待的角色，Answers 面板按名称列出每个角色的答案。

<PackageInfo>

## 功能特性

- 行内 void `field` 元素，共六种类型：文本、数字、日期、复选框、选择和签名。
- 每个字段有一个角色、一个标签，以及可选的必填标记、默认值、选择选项和值，每一项都按字段的类型检查。
- 条件可以是单个测试，或是由两个及以上测试组成的 `all` 或 `any` 列表，每个测试通过 `fieldId` 指向一个字段。条件不成立的字段被跳过，因此不需要答案。
- 可选的 `name`，让一个角色的多个字段共用一个答案，因此文档问两次的问题只需回答一次。
- `insert` 和 `update` 命令拒绝不符合的设置或条件，读取会报告每个字段的问题以及它是否适用。
- 一个角色的只填写视图，只接受该角色的答案，拒绝其他所有本地修改，撤销时只撤回该角色的答案。
- `applyFieldValues` 在服务器上按模板检查每个角色的答案，并生成填写后的文档。
- `fieldSubmission`、`startFieldValues` 和 `readFieldAnswers`，分别按名称从应用数据构建提交、用应用的值开始一个角色，以及按名称读取保存的文档中的答案。
- 粘贴、拖动复制、创建副本和表格填充复制的字段会获得新 id 并保留名称，复制的条件指向复制出的字段。
- HTML 和 Markdown 保留每个属性，Word 导出保留每个答案并报告它丢弃的设置。
- 注册表 UI 提供带设置弹出框、会把被跳过的字段显示为淡色的字段标签、插入菜单，以及在原处显示每个答案或一条空白线的静态渲染组件。

</PackageInfo>

## 值的结构

字段像日期或提及一样位于段落中。

```json
{
  "type": "paragraph",
  "children": [
    { "text": "Tenant name: " },
    {
      "type": "field",
      "fieldId": "f_k2x9",
      "kind": "text",
      "role": "tenant",
      "label": "Tenant name",
      "name": "tenant_name",
      "required": true,
      "children": [{ "text": "" }]
    },
    { "text": "" }
  ]
}
```

| 属性 | 类型 | 说明 |
|------|------|------|
| `type` | `'field'` | 由 `BaseFieldPlugin` 拥有的行内 void 元素。 |
| `fieldId` | `string` | 在文档中唯一。新字段获得一个随机的 `nanoid`。 |
| `kind` | `FieldKind` | `'text'`、`'number'`、`'date'`、`'checkbox'`、`'choice'` 或 `'signature'`。必需。 |
| `role` | `string` | 填写该字段的角色，例如 `'tenant'`。必需。 |
| `label` | `string` | 必需。字段标签显示它，字段没有答案时 HTML、Word 和纯文本会显示方括号中的它。 |
| `name` | `string` | 同一角色中名称相同的字段共用一个答案，见[名称](#names)。 |
| `required` | `boolean` | 标记字段适用时需要已填答案。提交让它保持未填写时，`applyFieldValues` 会拒绝该提交。 |
| `defaultValue` | `FieldValue` | 符合字段类型的值。 |
| `options` | `FieldOption[]` | 仅用于选择字段。每个选项为 `{ value, label }`，任意两个选项的 `value` 都不相同。 |
| `value` | `FieldValue` | 答案。没有答案，或 `fillsField` 判断它的答案不算填写时，字段未填写。 |
| `condition` | `FieldCondition` | `{ ref, test, value? }`、`{ all: tests }` 或 `{ any: tests }`，见下文的条件一节。 |
| `children` | `[{ text: '' }]` | 行内 void 元素必需的子节点。 |

## 类型

每种类型决定其值的结构，以及对它的条件可以使用哪些测试。`platejs/field` 中的 `fitsField(field, value)` 判断一个值是否符合字段的类型，`FIELD_TESTS` 列出每种类型的测试。

| 类型 | 值 | 测试 |
|------|----|------|
| `text` | 字符串 | `filled`、`blank`、`equals`、`not-equals` |
| `number` | 有限数字 | `filled`、`blank`、`equals`、`not-equals`、`above`、`below` |
| `date` | ISO 日期，`YYYY-MM-DD` | `filled`、`blank`、`equals`、`not-equals`、`above`、`below` |
| `checkbox` | `true` 或 `false` | `equals`、`not-equals` |
| `choice` | 某个选项的 `value` | `filled`、`blank`、`equals`、`not-equals` |
| `signature` | 由你的应用决定的字符串，例如存储图片的 id | `filled`、`blank` |

选择字段保存选项的 `value`，因此修改选项的 `label` 后，指向它的答案和条件都保持不变。

`platejs/field` 中的 `fillsField(field, value)` 判断一个值是否是字段的已填答案。`required` 以及 `filled` 和 `blank` 测试使用同一条规则。已填答案是已勾选的复选框，或者符合字段类型的值。文本或签名答案还需要包含至少一个 JavaScript 的 `\s` 不匹配的字符。因此 `false`、空文本和只含空格的文本符合字段，但不算填写，而 `0` 算作数字字段的已填答案。

```ts
import { fillsField } from 'platejs/field';

fillsField({ kind: 'text' }, '  '); // false
fillsField({ kind: 'number' }, 0); // true
fillsField({ kind: 'checkbox' }, false); // false
```

## 角色

每个字段指定填写它的角色，例如 `landlord` 或 `tenant`。角色可以是任意字符串。Plate 只保存它，从不检查用户是谁。由你的应用把每个人对应到一个角色，就像把每条评论对应到它的作者。

[只填写视图](#fill-as-one-role)会在该编辑器中阻止一个角色修改另一个角色的字段或周围的文本。从多人收集答案的应用仍应在服务器上用 [`applyFieldValues`](#apply-answers-on-the-server) 检查每个角色的答案。

设置弹出框提供文档中字段已经使用的角色，也可以输入新角色。

## 名称 [#names]

`name` 表示一个角色的多个字段询问同一个答案，例如租赁合同在开头和签名处各询问一次租客姓名。同一角色中名称相同的字段共用一个答案。两个角色中的相同名称是两个答案。没有名称的字段只通过它的 `fieldId` 工作。

名称是一个非空文本，两端没有空白，并且不包含控制字符、行分隔符、段落分隔符或孤立的代理项。加载、`insert`、`update` 和直接的 `tx.nodes.set` 都会拒绝其他名称。在注册表 UI 中，设置弹出框的 Name 输入框设置字段的名称，名称规则拒绝的名称会显示错误。

`update` 把 `value`（包括清空的值）写入该角色中与该字段同名的每个字段，并在同一个提交和同一个撤销步骤中完成。其他设置不会传到其他字段。在示例中，租赁合同以同一个名称询问两次租客姓名，因此在一处输入会填写另一处，撤销会同时撤回两处。

同一角色中名称相同的字段必须有相同的类型、相同的选项值和相同的条件。默认值不参与比较。两个条件形式相同（单个测试、`all` 或 `any`），且它们的测试可以按任意顺序一一对应时，它们相同。两个测试指向同一个字段，或指向同一角色中同名且该名称组没有 `name-conflict` 的字段，并且测试和值相同时，这两个测试相同。名称下的字段不一致时，其中每个字段都读到 `name-conflict`，此时 `update` 只把值写入它自己的字段。`insert` 和 `update` 从不拒绝名称冲突，因此作者可以逐个修改同名的字段。

名称下的字段持有不同的值时，其中每个字段都读到 `answer-conflict`。空文本与没有值不同，`false` 与没有值也不同。`insert` 和粘贴不会写入其他字段。因此以不同的值或没有值加入某个名称的字段会读到 `answer-conflict`，直到某次 `update` 向该名称下的一个字段写入值，这次写入会写入该名称下的每个字段。

## 插入与更新

`insert` 接收字段的设置并返回新字段的 `fieldId`。第二个参数接收节点插入选项，例如 `at` 和 `select`。

```tsx
import { BaseFieldPlugin } from 'platejs/field';

const fieldId = editor.plugin(BaseFieldPlugin).update.insert({
  kind: 'text',
  label: 'Tenant name',
  name: 'tenant_name',
  required: true,
  role: 'tenant',
});
```

当值、默认值或选项不符合类型，设置中指定了 `fieldId` 或[名称规则](#names)拒绝的名称，或者条件包含指向不存在字段的测试，或使用了被指向字段的类型不接受的测试或值时，`insert` 会抛出错误。

`update` 修改持有某个 `fieldId` 的字段的设置或值。传入 `undefined` 的设置会被移除。`value` 还会写入该角色中同名的每个其他字段。

```tsx
editor.update((tx) => {
  tx.plugin(BaseFieldPlugin).update(fieldId, { value: 'Ada Lovelace' });
});
```

在以下情况下，`update` 抛出错误且不做任何修改：

- 没有字段持有 `fieldId`；
- 补丁中的某项设置不符合字段的类型；
- 补丁指定了名称规则拒绝的 `name`；
- 补丁移除了 `kind`、`role` 或 `label`，或者指定了 `fieldId`；
- 条件中的某个测试出现了补丁之前同一测试没有的问题（`missing-target`、`unsupported-test` 或 `invalid-value`），无论这是补丁新增的测试，还是补丁修改字段的类型或选项所致；
- 补丁新增的测试指向一个条件路径会指回该字段的字段。

补丁前已有同一问题的测试可以通过，因此作者可以在另一条规则仍损坏时逐条修复，或者在损坏规则旁边移除一条正常规则。

修改 `kind` 或 `options` 的补丁还会丢弃字段不再符合的值、默认值和选项。把带默认值的数字字段改为日期字段会丢弃默认值。字段保留它的 `fieldId`。

## 条件

条件说明字段何时适用。它可以是单个测试 `{ ref, test, value? }`，或是包含两个及以上测试的列表 `{ all: tests }` 或 `{ any: tests }`。除 `filled` 和 `blank` 外，每个测试都与 `value` 比较，`value` 使用被指向字段的值的结构。列表不能嵌套列表，可以重复同一个测试。加载、`insert`、`update` 和直接的 `tx.nodes.set` 会拒绝少于两个测试的列表、嵌套列表、同时带有 `all` 和 `any` 的对象，以及同时带有 `ref` 和列表的对象。单个测试或列表会保留其持有的任何额外键。

示例中由租客填写的宠物名字字段，在房东的允许养宠物选择为 `yes` 且租客勾选我有宠物时适用：

```tsx
editor.update((tx) => {
  tx.plugin(BaseFieldPlugin).update(petNameId, {
    condition: {
      all: [
        { ref: petsId, test: 'equals', value: 'yes' },
        { ref: hasPetId, test: 'equals', value: true },
      ],
    },
  });
});
```

在注册表 UI 中，弹出框的 Show when 区域从 `read.conditionTargets(fieldId)` 读取可选的目标字段。属于其他角色的目标会在标签后显示它的角色。测试列表只提供那个字段的类型接受的测试。点击 Add rule 构建 `all` 或 `any` 列表，切换 Match all 与 Match any，或把规则删减到一条以保存为单个测试。

编辑器从不隐藏字段。条件不成立的字段被跳过。即使它是 `required`，它也不需要答案，并且 `applyFieldValues` 会拒绝它的已填答案。条件检查它指向的每个字段的答案：

- `equals` 在答案等于 `value` 时成立，`not-equals` 在答案不等于它时成立，没有答案也算不等于。
- `above` 和 `below` 比较数字，并按日期比较 ISO 日期。没有答案时两者都不成立。
- 不符合字段类型的答案算作没有答案，本身被跳过的字段的答案也算作没有答案。
- 没有答案的复选框在它的角色完成作答后读作 `false`。在编辑器中，这适用于填写被读取字段的那个角色的复选框。在 `applyFieldValues` 中，这在复选框的角色提交之后适用。

列表在三种状态上折叠其测试：成立、不成立和等待。

- `all` 列表只要有任一测试不成立就立即不成立，即使另一项测试仍在等待。否则，只要有测试在等待就等待，全部测试都成立时才成立。
- `any` 列表只要有任一测试成立就立即成立，即使另一项测试仍在等待。否则，只要有测试在等待就等待，全部测试都不成立时才不成立。
- 列表中任一测试有问题时，整个条件视为损坏，该字段适用。

当补丁新增的测试指向一个条件路径会指回该字段的字段时（例如 A 指向 B 而 B 指向 A，或者字段指向自身），`update` 会拒绝该条件。对条件原本已指向的 `ref` 更换测试或值可以通过，已经在循环中的字段仍可添加指向循环外字段的新测试。循环仍可能来自加载的文档、直接的节点写入或两个协作者同时进行的更新，此时循环中的每个字段都会报告 `condition-loop`。只指向循环内部字段的外部字段会把循环中的字段读作适用。

## 读取字段及其问题

`read.field(fieldId)` 返回持有该 id 的字段（可在任意根中），没有时返回 `null`。`read.fields()` 按阅读顺序返回文档中的每个字段。读取会按文档版本构建一次条件图并在各次读取之间共享，每个读取角色对每个字段只判断一次。每次读取得到一个 `FieldRead`：`{ applies, fieldId, node, problems }`。

`read.conditionTargets(fieldId)` 按文档顺序返回所有没有条件路径指回 `fieldId` 的其他字段，以及该条件已经指向的每个字段（若测试指向自身，也包含该字段本身）。id 不指向任何字段时返回空列表。

```tsx
import { BaseFieldPlugin } from 'platejs/field';

const fields = editor.plugin(BaseFieldPlugin).read;

const tenant = fields.field(tenantId);
const broken = fields.fields().filter((field) => field.problems.length > 0);
const skipped = fields.fields().filter((field) => field.applies === false);
const targets = fields.conditionTargets(petNameId);
```

| 问题 | 何时出现 |
|------|----------|
| `missing-target` | 没有字段持有其条件指向的某个 id，例如那个字段被删除之后。 |
| `unsupported-test` | 条件指向的某个字段的类型不接受该测试。 |
| `invalid-value` | 它的值、默认值或选项不符合它的类型，或者某个测试的值不符合测试或被指向字段的类型。 |
| `condition-loop` | 从该字段出发的条件路径指回它自身，例如 A 指向 B 而 B 指向 A。 |
| `name-conflict` | 同一角色中同名的某个字段的类型、选项值或条件不同。 |
| `answer-conflict` | 同一角色中同名的某个字段持有不同的值，或者没有值。 |

即使列表中多条测试触发同一个问题，每个问题代码在 `problems` 中最多出现一次。`insert` 和 `update` 会拒绝引入前四种问题的写入。它们从不拒绝名称冲突或答案冲突，由读取报告这些问题。问题来自之后的编辑，例如删除或修改条件指向的字段，或者来自绕过这些命令的写入，例如直接的 `tx.nodes.set` 或加载的文档。

`applies` 说明字段在它的条件下是否适用。它依据文档当前持有的答案，以字段自己的角色的视角沿所有条件路径读取：

- 字段没有条件、条件有问题或处于循环中、条件成立，或 `any` 列表中至少有一项测试成立（即使另一项仍在等待）时，为 `true`。
- 字段被跳过，即条件不成立，包括 `all` 列表中至少有一项测试不成立（即使另一项仍在等待）时，为 `false`。
- 条件仍依赖另一个角色尚未给出的答案时为 `null`，例如租客勾选我有宠物后、房东选择允许养宠物之前的宠物名字。只有 `applyFieldValues` 知道哪些角色已经提交，因此编辑器把这样的字段读作等待中。

条件指向被跳过字段的字段是确定的，即使那个被跳过的字段属于另一个角色。

在 React 中，`platejs/field/react` 的 `useFieldRead(fieldId)` 读取一个字段、它的问题以及它是否适用。修改元素的提交会重新读取它，只有字段、其问题或 `applies` 变化时组件才会重新渲染。注册表中的字段标签用它在条件指向的字段被删除时显示警告，撤销后警告消失。字段标签还会把 `applies` 为 `false` 的字段显示为淡色，并标记为 skipped。等待中的字段的标签不会变淡。

```tsx
import { useFieldRead } from 'platejs/field/react';

const field = useFieldRead(element.fieldId);
const problems = field?.problems ?? [];
const skipped = field?.applies === false;
```

## 以一个角色填写 [#fill-as-one-role]

设置 `fillRole` 打开一个角色的只填写视图。编辑器只接受该角色字段的答案，并拒绝其他所有本地修改，因此租客只能填写租客的字段，不能修改其他内容。

```tsx
import { FieldPlugin } from 'platejs/field/react';
import { useCreateEditor } from 'platejs/react';

import { FieldElement } from '@/components/editor/field';

const editor = useCreateEditor({
  initialValue: template,
  plugins: [
    // ...otherPlugins,
    FieldPlugin.configure({
      component: FieldElement,
      initialState: { fillRole: 'tenant' },
    }),
  ],
});
```

示例通过插件 store 在编辑模板和每个角色之间切换同一个编辑器，`null` 回到编辑模板：

```tsx
editor.plugin(FieldPlugin).store.set({ fillRole: 'landlord' });
editor.plugin(FieldPlugin).store.set({ fillRole: null });
```

在组件中用 `platejs/react` 的 `usePluginStore(FieldPlugin, 'fillRole')` 读取角色。角色是编辑器状态，因此同一个编辑器的每个视图都以同一个角色填写。在两次更新之间切换角色。切换不会写入文档，也不会改变撤销和重做。

设置角色后：

- 注册表中该角色字段的标签打开一个弹出框，带有答案输入框和 Clear 按钮，该角色的复选框点击即可勾选或取消。答案带有待审阅建议的标签会提示它在等待审阅，并且不会打开任何内容。其他角色的标签不会打开任何内容，标签不能拖动，插入菜单被禁用。
- 编辑器拒绝除该角色字段上符合的答案或清空答案之外的任何本地提交。输入、粘贴、剪切、拖放、回车和 AI 写入都不会改变文档。被拒绝的更新不会向调用者抛出错误，也不会改变任何内容。
- 选区、没有 `persist` 的状态字段，以及既不持久化也不同步给其他协作者的副作用都可以通过，因此仍然可以选择和复制。
- 撤销和重做只撤回该角色自己的答案。撤销在第一个修改了其他内容的步骤处停止，例如作者的编辑，并返回 `{ reason, status: 'blocked' }`。切换后的第一个答案是单独的撤销步骤，因此切换后立即输入的答案需要撤销两次。
- 替换文档，例如 `tx.value.replace` 或加载另一个模板，会被拒绝，重新配置插件也会被拒绝。先加载模板并配置插件，再设置角色，或者先清除角色。
- 评论可以添加，因为创建评论线程是一个本地副作用。由你的应用决定是否允许在只填写视图中评论。评论会增加一个撤销步骤，撤销会停在这个步骤，因此评论之前的答案无法再撤销。

其他协作者的修改整体通过。每个带有 `collaboration` 标签的提交都会通过，因此协作者保持同一份文档。从 provider 的事件中应用其他协作者的 Yjs 更新，不要在编辑器更新内部应用。在其他协作者的修改内部进行的本地写入会带上它的 `collaboration` 标签，通过检查，并且永远不会发送给其他协作者。同理，由你的应用自己驱动的 Yjs `UndoManager`，或你的应用标记为 `collaboration` 的本地更新，也会通过填写检查。

填写检查运行在字段插件的 `activate` 中，撤销步骤的边界运行在它的 `corrections` 中。用自己的 `activate` 或 `corrections` 扩展字段插件的插件会替换它们，因此把这部分逻辑放在一个配套插件中。

填写检查运行在用户的浏览器中，任何人都可以在那里运行自己的代码。由你的服务器分配每个人的角色，并用 `applyFieldValues` 检查每个提交。

## 提交答案 [#submit-answers]

客户端从编辑器读取一个角色的答案并发送出去。服务器按它保存的模板检查每个角色的答案，并保存填写后的文档。

### 读取一个角色的答案 [#read-a-roles-answers]

`read.submission(role)` 返回一个 `FieldSubmission`，即 `{ role, values }`。`values` 以 `fieldId` 为键，保存该角色每个有 `value` 的字段的值。

```tsx
import { FieldPlugin } from 'platejs/field/react';

const submission = editor.plugin(FieldPlugin).read.submission('tenant');
// { role: 'tenant', values: { tenant: 'Grace Hopper', 'pet-name': 'Milo', rules: true } }
```

同名的字段保留各自的键，因此提交为其中每个字段各保存一次答案。提交保留 `false`、`0`、空文本、只含空格的文本，以及不再符合字段类型的值，由服务器判断每一个。它不包含没有 `value` 的字段，因此从未勾选过的复选框和勾选后又取消的复选框可以区分开。

### 在服务器上应用答案 [#apply-answers-on-the-server]

`platejs/field` 中的 `applyFieldValues(template, submissions, options?)` 检查每个角色的答案并生成填写后的文档。它不导入 React，并自己检查每个提交的结构，因此服务器可以直接传入解析后的 JSON。在这个路由中，`frozenTemplate` 是你的应用保存的模板，`accepted` 保存它之前接受的提交，`saveFilled` 保存结果。

```ts
import { applyFieldValues } from 'platejs/field';

const result = applyFieldValues(frozenTemplate, [...accepted, submission]);

if (!result.ok) {
  return Response.json({ refusals: result.refusals }, { status: 400 });
}

await saveFilled(result.document);
```

- `template` 是你的应用保存的编辑后文档，带有它的 `fieldId`，不带答案，因此只填写视图和 `applyFieldValues` 从相同的 id 开始。它接受 `Value` 或带命名根的文档，`result.document` 的结构与之相同。`applyFieldValues` 读取主根和每个命名根中的字段，从不读取 `meta` 或记录中的字段。
- `submissions` 按角色提交的顺序列出每个角色的提交。每个提交都按之前的角色加上它自己的答案进行检查。
- 你的应用用 `schema.override` 重命名了字段元素的类型时，`options.type` 指定这个类型。默认为 `field`。

填写后的文档是模板加上每个被接受的答案，答案作为其字段的 `value`。默认值始终是设置，从不变成答案。

成功时，`pending` 列出每个尚未提交、且有适用或等待中的必填字段的角色。它还列出尚未提交的角色下所有等待中字段（无论必填还是可选）所需的每个角色，沿每条等待路径取最远且尚未提交的角色。可选字段从不会让它自己的角色出现在 `pending` 中。示例把 `pending` 显示为 Waiting on。

### 拒绝 [#refusals]

拒绝时，`result` 为 `{ ok: false, refusals }`，至少包含一条拒绝。模板有拒绝时，结果列出所有这些拒绝，并且不检查任何提交。否则，它列出第一个有拒绝的提交的所有拒绝。

| 代码 | 何时出现 |
|------|----------|
| `invalid-template` | 模板字段持有答案（`answered`），缺少 `fieldId`、包含的不是恰好一个文本，或者 kind、role、label、设置或条件的结构不对（`malformed`），重复了 `fieldId`（`duplicate-id`），或者有读取会报告的问题，包括 `condition-loop` 和 `name-conflict`。拒绝会给出 `problem`、字段的 `path`、字段在命名根中时的 `root`，以及字段有 `fieldId` 和 `name` 时的 `fieldId` 和 `name`。 |
| `invalid-submission` | 提交不是一个带有 `role` 字符串和 `values` 对象的对象。拒绝会给出它的 `index`。 |
| `duplicate-role` | 已在列表中的角色再次提交。 |
| `unknown-role` | 该角色不拥有任何字段。 |
| `unknown-field` | 答案指向的字段不在模板中。 |
| `wrong-role` | 答案属于另一个角色的字段。 |
| `invalid-value` | 答案不符合它的字段。 |
| `waiting` | 该角色的字段在等待一个或多个尚未提交的角色。`waitsOn` 给出其中按 UTF-16 码元顺序排在最前的角色。即使该字段的答案也被拒绝，仍会报告这条拒绝。 |
| `skipped` | 该角色的字段被跳过，却持有已填答案。未填写的答案按原样保留，因此清空答案或取消勾选即可消除这条拒绝。 |
| `missing-required` | 该角色的必填字段适用，但没有已填答案。 |
| `answer-conflict` | 该角色的答案应用后，它的某个名称下的字段持有不同的值。拒绝会给出 `name`，并按文档顺序在 `fieldIds` 中列出该名称的每个字段。如果提交已经以 `invalid-value`、`waiting` 或 `skipped` 拒绝了该名称下的某个字段，则不报告这条拒绝。漏填的必填字段不会阻止它，因此它可能与 `missing-required` 一起出现。 |

`invalid-submission`、`duplicate-role` 和 `unknown-role` 单独出现。其他提交拒绝会给出 `role`、所属字段的 `fieldId`，以及字段有名称时的 `name`。`answer-conflict` 给出 `fieldIds` 而不是 `fieldId`。结果会列出该提交的每一条拒绝。

在一个房东的租金字段名为 `rent`、租客的两个姓名字段共用 `tenant_name` 的模板中：

```ts
applyFieldValues(template, [{ role: 'landlord', values: {} }]);
// { ok: false, refusals: [{ code: 'missing-required', fieldId: 'rent', name: 'rent', role: 'landlord' }] }

applyFieldValues(template, [
  { role: 'tenant', values: { tenant: 'Ada Lovelace', 'tenant-again': 'Ada' } },
]);
// { ok: false, refusals: [{ code: 'answer-conflict', fieldIds: ['tenant', 'tenant-again'], name: 'tenant_name', role: 'tenant' }] }
```

在示例中，宠物名字在房东的允许养宠物为 `yes` 且租客勾选我有宠物时适用。租客勾选我有宠物并在房东之前点击 Submit，会得到一条 `waiting` 拒绝，因为宠物名字在等待房东的允许养宠物。如果租客不勾选我有宠物，`all` 列表无需等待房东就已不成立，宠物名字被跳过，租客可以先提交。房东提交否时，租客仍然输入的宠物名字会被拒绝为 `skipped`，直到清空它。

两个角色互相等待对方的模板可以通过，因为第三个角色的答案可以让链上的某个字段被跳过，从而结束等待。两个字段都仍在等待时，先提交的角色会被拒绝为 `waiting`，等待另一个角色。

### 打印填写后的文档 [#print-the-filled-document]

通过 `platejs/static` 用 `BaseFieldKit` 渲染填写后的文档，并用这份输出生成 PDF。静态输出把没有已填答案的非复选框字段显示为一条空白线，而 `editor.api.html.serialize()` 为没有答案的字段写入方括号中的标签。

```tsx
import { createEditor } from 'platejs';
import { renderStaticHtml } from 'platejs/static';

import { BaseFieldKit } from '@/components/editor/field-static';

const filled = createEditor({
  initialValue: result.document,
  plugins: [
    // ...otherPlugins,
    ...BaseFieldKit,
  ],
});

const { data } = await renderStaticHtml(filled);
```

[静态渲染](/cn/docs/static)介绍 `EditorStatic` 和 `renderStaticHtml`。

### 应用数据 [#app-data]

给你的应用自己填写的字段一个单独的角色，例如 `app`，并在任何人签署之前提交这个角色的答案。其他每个角色的[只填写视图](#fill-as-one-role)都会拒绝写入这些字段，`applyFieldValues` 也会把其他角色为这些字段给出的答案拒绝为 `wrong-role`，因此应用的值保持锁定。你的服务器保存应用的提交，并在每个列表中把它放在第一位发送。

在一个 `app` 角色拥有名为 `address` 和 `rent` 的字段、租客的两个姓名字段共用 `tenant_name` 的租赁合同中，应用填写它自己的字段，并用同一条记录为租客姓名提供起始值：

```ts
import {
  applyFieldValues,
  BaseFieldPlugin,
  fieldSubmission,
  readFieldAnswers,
  startFieldValues,
} from 'platejs/field';

const record = {
  address: '1 Main St',
  rent: 1200,
  tenant_name: 'Ada Lovelace',
};

// 应用自己的角色在任何人签署之前填写锁定的值。
const app = fieldSubmission(template, 'app', record);

// 租客的只填写视图打开时带有应用的答案，并以记录中的值作为起始值。
const start = startFieldValues(
  template,
  [app],
  fieldSubmission(template, 'tenant', record)
);
if (!start.ok) throw new Error(start.refusals[0].code);

// 租客在 fillRole 为 'tenant' 的编辑器中填写 start.document。
const tenant = editor.plugin(BaseFieldPlugin).read.submission('tenant');

// 服务器应用每个角色的答案。
const result = applyFieldValues(template, [app, tenant]);
if (!result.ok) throw new Error(result.refusals[0].code);

// 保存的文档按名称读回。
readFieldAnswers(result.document).tenant?.tenant_name;
// 租客保留起始姓名时为 { kind: 'text', value: 'Ada Lovelace' }
```

#### 按名称构建提交 [#build-a-submission-by-name]

`fieldSubmission(template, role, values, options?)` 把一个以字段 `name` 为键的记录转换为一个角色的 `FieldSubmission`，以 `fieldId` 为键。`role` 中名称是 `values` 自有键的每个字段都得到该键的值，因此该角色询问两次的名称会写到两个字段上。

- `null` 和 `undefined` 不包含该字段。
- 该角色没有的名称、不指向任何字段的键和没有名称的字段都会被忽略，因此一条宽记录可以用于每个角色。记录继承的键，例如 `constructor`，从不计入。
- 它不检查任何值。`applyFieldValues` 判断每一个值，并把漏填必填字段的应用提交拒绝为 `missing-required`，同时给出该字段的 `name`。
- `options.type` 指定重命名后的字段类型，与 `applyFieldValues` 中相同。

#### 用应用的值开始一个角色 [#start-a-role-from-app-values]

`startFieldValues(template, submissions, start, options?)` 像 `applyFieldValues` 一样检查 `submissions`，然后把 `start` 的值写入该角色的字段。`start` 是一个尚未提交的角色的 `FieldSubmission`。它返回与 `applyFieldValues` 相同的结果结构。成功时，`document` 是该角色开始填写时的已填写文档，用于在该角色的只填写视图中打开。

- 一个值写入它的字段，以及该角色中同名的每个其他字段，与 `update` 的写入方式相同。
- `start` 没有给值的字段从空白开始，即使它有 `defaultValue`。
- 条件读取之前角色的答案和 `start` 自己的值，就像该角色已经提交一样。被跳过的字段，或者在等待一个尚未提交的角色的字段，它的值会被略去且不产生拒绝，该字段从空白开始。因此应用可以在每个角色都回答之前，从一条宽记录开始。
- `pending` 只来自 `submissions`，因此 `start` 从不会把它的角色从中移除。

填写的人保留、修改或清空每个起始值。他们的提交就是他们自己的答案，`applyFieldValues` 像判断其他提交一样判断它。它会把清空的必填值拒绝为 `missing-required`，把保留在随后因另一个答案而被跳过的字段上的值拒绝为 `skipped`，直到清空它。

`startFieldValues` 首先拒绝 `applyFieldValues` 对 `submissions` 拒绝的内容。然后，`start` 结构不对时，它单独把 `start` 拒绝为 `invalid-submission`，`index` 等于 `submissions.length`；它的角色已经提交时拒绝为 `duplicate-role`；该角色不拥有任何字段时拒绝为 `unknown-role`。否则，它一起列出每个不指向任何字段、属于另一个角色的字段或不符合其字段的值的 `unknown-field`、`wrong-role` 或 `invalid-value`，以及 `start` 为同一个名称给出两个不同值时该名称的 `answer-conflict`。它从不把 `start` 拒绝为 `missing-required`、`skipped` 或 `waiting`，因为起始值可以让任何字段保持空白。

#### 按名称读取保存的答案 [#read-saved-answers-by-name]

`readFieldAnswers(document, options?)` 读取一个保存的文档，返回每个角色以名称为键的答案，即 `answers[role][name]`。每个拥有命名字段的角色得到一个记录，没有名称的字段不包含在内。两层都是没有原型的记录，因此 `constructor` 这样的角色或名称会作为它自己的键读取。它像 `applyFieldValues` 一样读取字段，因此不是有效字段的节点会被跳过，重复的 `fieldId` 从它的第一个持有者读取。`options.type` 指定重命名后的字段类型。

每个答案是一个 `FieldAnswer`：

| 答案 | 何时出现 |
|------|----------|
| `{ kind, value }` | 该名称的字段持有一个符合 `kind` 的值。复选框的 `value` 是 `boolean`，数字是 `number`，其他每种类型是 `string`。 |
| `{ kind }` | 这些字段没有值，或持有一个不符合 `kind` 的值。 |
| `{ kind, problem: 'answer-conflict' }` | 这些字段持有不同的值。 |
| `{ problem: 'name-conflict' }` | 这些字段的类型、选项值或条件不同，因此该名称没有唯一的类型。 |

先检查 `'problem' in answer`，再按 `kind` 收窄以读取 `value`：

```ts
const rent = readFieldAnswers(result.document).app?.rent;

if (rent && !('problem' in rent) && rent.kind === 'number') {
  rent.value; // number | undefined
}
```

这个读取不保存任何提交记录，因此它不说明哪些字段适用。没有提交任何内容的角色和让每个字段都保持空白的角色读起来相同。需要知道哪些字段适用的应用从 `applyFieldValues` 的结果中获取这一信息。

## 复制与粘贴

字段在移动（包括拖动移动）、被撤销恢复以及加载已保存的文档时保留它的 `fieldId`。复制会获得新 id：

- 粘贴、拖动复制、`tx.blocks.duplicate` 和表格填充会给它们复制的每个字段新 id，并保留它的名称。在复制的条件中，每个指向同一份副本内字段的测试都会指向该字段的副本。
- 复制的条款可以同时包含一个有名称的字段及其条件指向的无名称字段。副本的条件随后指向复制出的字段，因此该名称下的两个字段检查不同的字段，两者都读到 `name-conflict`。给条件指向的字段及其副本取同一个名称，冲突就会消失。
- 每个目标未被复制或在同文档粘贴中未落下的测试都会继续指向原字段。跨文档粘贴时，目标未落下的测试若在目标文档中找不到持有该 id 的字段，会报告 `missing-target`。
- 粘贴到表格单元格选区时每个单元格复制一次，因此每个单元格中的条件指向它自己单元格里的副本。
- 粘贴到另一个文档同样获得新 id。
- 剪切后粘贴会给字段新 id，因此在撤销之前，其他地方指向它的条件会报告 `missing-target`。
- 应用用 `tx.schema.copy` 复制字段并插入结果时得到新 id，副本的条件继续指向原字段。

在建议模式下，把字段改为提及会显示为被删除的字段旁边插入的提及，因此拒绝该修改会保留字段及其 `fieldId`。

## HTML

`editor.api.html.serialize()` 把每个字段写成一个 `span`，每个属性对应一个 `data-field-*` 属性。span 的文本是答案：选择字段为所选选项的标签，没有答案的字段为方括号中的标签。id、kind、label、name 和 role 属性保存纯文本，其他属性保存 JSON：

```html
<p>Pets allowed? <span data-field-id="pets" data-field-kind="choice" data-field-label="Pets allowed" data-field-name="pets_allowed" data-field-options="[{&quot;label&quot;:&quot;Yes&quot;,&quot;value&quot;:&quot;yes&quot;},{&quot;label&quot;:&quot;No&quot;,&quot;value&quot;:&quot;no&quot;}]" data-field-required="true" data-field-role="landlord" data-field-value="&quot;yes&quot;">Yes</span> Pet name: <span data-field-condition="{&quot;ref&quot;:&quot;pets&quot;,&quot;test&quot;:&quot;equals&quot;,&quot;value&quot;:&quot;yes&quot;}" data-field-id="pet-name" data-field-kind="text" data-field-label="Pet name" data-field-name="pet_name" data-field-required="true" data-field-role="tenant">[Pet name]</span></p>
```

解析这段 HTML 会读回每个有效属性，丢弃格式错误的条件并保留该字段。span 需要 `data-field-kind`、`data-field-label` 和 `data-field-role` 才会被读成字段。粘贴的 HTML 模板会获得新 id，其中的条件指向副本。

示例的 HTML 面板使用 `lossPolicy: 'allow'` 序列化，因为日期元素没有 HTML 编码器。面板为丢弃的日期列出一行 `html-unsupported-content`。

## Markdown

Markdown 把每个字段写成一个 `<field>` 标签，包含每个属性，`fieldId` 和条件也在其中：

```md
Pets allowed? <field kind="choice" label="Pets allowed" name="pets_allowed" options="[{&quot;label&quot;:&quot;Yes&quot;,&quot;value&quot;:&quot;yes&quot;},{&quot;label&quot;:&quot;No&quot;,&quot;value&quot;:&quot;no&quot;}]" required role="landlord" value="yes" fieldId="pets" /> Pet name: <field kind="text" label="Pet name" name="pet_name" required role="tenant" condition="{&quot;ref&quot;:&quot;pets&quot;,&quot;test&quot;:&quot;equals&quot;,&quot;value&quot;:&quot;yes&quot;}" fieldId="pet-name" />
```

读取器需要 `kind`、`label` 和 `role`，并会丢弃格式错误的条件同时保留字段。缺少它们的标签保留为文本，并返回 `markdown-unsupported-node` diagnostic。粘贴的 Markdown 模板会获得新 id，其中的条件指向副本。

## Word

Word 没有字段元素。Word 导出把每个字段的答案写成文本：选择字段为所选选项的标签，没有答案的字段为方括号中的标签。它不需要静态字段组件，因此无界面的导出也会保留答案。

```tsx
import { exportDocx } from 'platejs/docx/export';

const result = await exportDocx(editor);
const dropped = result.diagnostics.filter(
  (diagnostic) => diagnostic.code === 'property-dropped'
);
```

导出会丢弃每个字段的 id、类型、角色、名称、设置和条件。它用一个 `property-dropped` 警告报告这些损失，消息为 "Word keeps each field answer and drops its name and settings."，`feature` 为 `field`，`count` 为字段数量。无论 `lossPolicy` 是 `'allow'` 还是 `'reject'`，这个警告都不会使导出失败。示例的 Word 面板显示这个警告，插入字段时它的数量随之增加。

通过 `platejs` 的 `serializePlainText` 导出的纯文本与 Word 写入的文本相同。
