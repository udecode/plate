## Features

- Opens from its Find button or with `Mod+F` in the main editor or a nested
  Editable (such as a board note), and seeds the query from the active view's
  expanded selection.
- Searches the main document and every named content root in document reading
  order.
- Highlights every match per mounted view without writing marks into the
  document or history.
- Finds a match that runs across text leaves and inline elements within one
  block.
- Moves between results with `Enter`, `Shift+Enter`, or the arrow buttons,
  revealing culled targets such as off-camera board notes.
- Updates the results after each document change. Typing or formatting inside a
  block searches only that root's changed block again, and only text whose
  highlights changed repaints.
- Keeps the active result on its match through edits.
- Opens independently in each mounted editor presentation, with `useFind` for
  custom controls.

</PackageInfo>

## Installation

```bash
npx shadcn@latest add @plate/find
```

## Usage

Install `FindKit` with the rest of your editor plugins:

```tsx
import { createEditor } from 'platejs/react';

import { FindKit } from '@/components/editor/find';

const editor = createEditor({
  plugins: [
    // ...otherPlugins,
    ...FindKit,
  ],
});
```

`BaseFindPlugin` owns the current query, matches, navigation and transient
decoration data. `FindKit` supplies the Find button, the shortcut, deferred
input and accessible search bar. The button sits where the bar opens and lets
a touch screen without `Mod+F` open Find. The open bar takes the button's place.
Its configured `decorate.attributes` supplies ordinary and active match styling. Each mounted Editable owns its open bar, draft, focus and scroll
requests. Views of the same editor share committed queries and results; opening
one bar does not open another. Open bars follow the committed query when they
have no pending draft. Only the focused bar scrolls its view. Detaching a view
preserves the shared search. Search state stays outside the document and history.

## Search API

Use the headless feature for search and replacement without the copied bar:

```ts
import { createEditor } from 'platejs';
import { BaseFindPlugin } from 'platejs/find';

const editor = createEditor({ plugins: [BaseFindPlugin] });
const find = editor.plugin(BaseFindPlugin);

find.api.search('example', { caseSensitive: true, wholeWord: true });
find.api.move(1);
find.api.matches();
find.store.get('activeMatch');
find.update.select();
find.update.replace('sample');
find.update.replaceAll('sample');
```

`api.search(query, options?)` applies a query across the main document and every
named content root in document reading order (merging each named root at its
first owner's position). An empty query clears results. Omitted `FindOptions`
fields (`caseSensitive`, `wholeWord`, `regexp`) default to `false`. Main-root
matches keep rootless `Range` coordinates, and named-root matches carry `root`
on both `anchor` and `focus`. Inline voids break text runs so matches never
bridge across them.

`api.move(1 | -1)` wraps through the current results without searching again,
and `api.setActiveIndex(index)` selects a result by zero-based reading-order
index (returning `false` when out of range). `api.matches(options?)` returns a
frozen snapshot of matches in reading order (or for one `{ root }`), and
`api.matchAt(point)` resolves the match and global index covering `point`
(inclusive of range endpoints).

Every commit that changes the main document or any named root updates the
results, including when no view is mounted. It searches again only the edited
root's smallest changed block, such as the paragraph the user types in, and
refreshes decoration observers only for affected roots. A commit that leaves
every root's content unchanged, such as a selection change, searches only when
the results went stale: after a schema change or after a search inside an update
that threw. `api.search` searches every root even when called on a named root's
view.

`update.select()` selects the active match in its root from any view and returns
whether it did; view focus remains the caller's responsibility.
`update.replace(replacement)` replaces the active match with literal
`replacement` text as its own undo step (when no history tag is already set) and
advances the active match past the replacement end.
`update.replaceAll(replacement)` replaces every writable, content-only match in
reverse document order per root as one undo step and returns the number of
matches mutated. Both commands refuse read-only views and skip locked ranges,
inline voids, and non-content leaves (such as struck suggestions).

The active result follows its match through edits. It stays on that match while
the search still finds the same text there. When an edit breaks the match, the
active result moves to the first match that ends after where the old one
started, or wraps to the first match. A new query starts on its first match.

`FindPluginState` holds scalar `query`, `caseSensitive`, `wholeWord`, `regexp`,
`activeIndex`, `error`, and `version`. The `count` and `activeMatch` read-only
store selectors read the plugin's private index. Each `FindMatch` contains a
range and an opaque ID preserved across unrelated edits and block shifts. A
commit that leaves every match, the active result, and `error` unchanged
notifies no store subscriber. Match data is transient and never stored as
document marks. Custom renderers can style `data-find-match` and
`data-find-active` attributes.

## Custom controls

`FindKit` already shows a Find button in each Editable. For another opening
control, use `useFind` in a component rendered by that Editable's
`beforeEditable` or `afterEditable` slot. `FindKit` supplies the context through `wrapRoot`, so a
custom control addresses one mounted view without subscribing to search results:

```tsx
import { useFind } from '@/components/editor/find';

export function FindButton() {
  const { open } = useFind();

  return (
    <button onClick={() => open()} type="button">
      Find
    </button>
  );
}
```

In the copied `FindKit` configuration, add `beforeEditable: FindButton` alongside
`wrapRoot: FindRoot`. A sibling of `<Editor>` outside those slots does not have
the exact view's Find context.

`open(query?)` opens and focuses this view's bar. An explicit query becomes its
input; otherwise it uses the committed search query. `close()` closes this
view's bar, clears the shared query and returns focus to this view's editor.
Typing stays local until the bar applies its deferred query.

Search controls use `editor.plugin(BaseFindPlugin)` directly. Controls that
display results can subscribe with `usePluginStore(BaseFindPlugin, 'count')`,
`'activeIndex'`, or `'error'`. Opening controls do not need these subscriptions.

To select a result and focus the current view from an Editable slot, call the
existing selection and DOM commands:

```tsx
import { BaseFindPlugin } from 'platejs/find';
import { useEditor } from 'platejs/react';

const editor = useEditor();

const selectMatch = () => {
  if (editor.plugin(BaseFindPlugin).update.select()) {
    editor.api.dom.focus();
  }
};
```

## Keyboard behavior

| Key | Behavior |
| --- | --- |
| `Mod+F` | Open Find from the main editor or a nested Editable. The active view's expanded selection becomes the initial query. |
| `Enter` | Move to the next result in reading order and scroll within the focused presentation. |
| `Shift+Enter` | Move to the previous result in reading order and scroll within the focused presentation. |
| `Escape` | Close Find and return focus to the originating editable when connected. |
