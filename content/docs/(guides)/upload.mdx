`UploadPlugin` owns draft slots and upload tasks. The Files SDK transfers bytes;
your application owns the gateway, document access, and durable download URLs.
Add the [media plugins](/docs/media) for the completed image, video, audio, and
file nodes.

For manual setup, install the package and SDK:

```bash
npm install platejs files-sdk
```

The R2 recipe sets up `/api/files`. Set `FILES_R2_BUCKET`,
`FILES_R2_ACCOUNT_ID`, `FILES_R2_ACCESS_KEY_ID`,
`FILES_R2_SECRET_ACCESS_KEY`, a stable `FILES_API_SECRET` of at least 32
characters, and a positive `FILES_MAX_UPLOAD_SIZE`. Implement
`resolveFilesAccess` in the copied `lib/files.ts` for your session and document
ACL before accepting requests. It checks read and write access, including on
the proxy upload `PUT`. The route's `documentId` is an application document ID,
not an authorization token. Use 1 to 128 letters, digits, underscores, or hyphens
for that ID. Return a stable tenant/document namespace shared by authorized
collaborators.

The S3 recipe uses `FILES_S3_BUCKET` and `FILES_S3_REGION`. Supply credentials
through the AWS credential chain. Both persistent providers reuse the same
copied gateway policy in `lib/files.ts`; their route files only construct the
selected adapter. Install `files-api` directly when building another provider
recipe.

## Configure the editor

Create one client and plugin configuration for the editor's document lifetime.
`getUrl` is synchronous: it maps the SDK's `UploadOutcome` key to an absolute,
durable address. Keep the origin in application configuration so this setup
also works during server rendering.

```tsx
import { createFilesClient } from 'files-sdk/client';
import { UploadPlugin } from 'platejs/upload/react';
import { createEditor } from 'platejs/react';

import { UploadElement } from '@/components/editor/upload';
import { MediaKit } from '@/components/editor/media';

export function createDocumentEditor(documentId: string, appOrigin: string) {
  const endpoint = `/api/files?documentId=${encodeURIComponent(documentId)}`;
  const client = createFilesClient({ endpoint });

  return createEditor({
    plugins: [
      ...MediaKit,
      UploadPlugin.configure({
        component: UploadElement,
        initialState: {
          client,
          getUrl: ({ key }) => {
            const url = new URL(endpoint, appOrigin);
            url.searchParams.set('op', 'download');
            url.searchParams.set('key', key);
            return url.href;
          },
          onError: (failure) => console.error(failure),
        },
      }),
    ],
  });
}
```

The gateway authorizes each download, then redirects to a short-lived storage
URL or proxies trusted inline media.
Persist the gateway URL returned by `getUrl`, rather than a signed storage URL.
Use same-origin cookies for browser media requests and proxy uploads; those
requests do not inherit `FilesClient.headers`. To display private media inline,
configure the copied gateway's `trustedInlineType` from validated bytes or a
trusted ingestion record. Without that policy, files download as attachments.

If you use the copied `UploadKit`, edit its endpoint and URL resolver to include
the active `documentId`, as in the configuration above.

## Submit and observe files

```tsx
editor.plugin(UploadPlugin).update.submit(files, { after: blockKey });
editor.plugin(UploadPlugin).update.submit(files, { slot: draftKey });
editor.plugin(UploadPlugin).api.cancel(draftKey);
editor.plugin(UploadPlugin).api.fitsAfter(draftKey);
```

`submit` accepts `File[]` or `FileList`. It validates the whole batch before
changing the document and starts one SDK upload per file after commit. Each
upload starts once every commit listener has heard the commit that added its
draft. A cancel, a removal of the draft, a later update that replaces the whole
document, or a destroyed editor before then sends no request, and an undo that
brings the draft back does not restart it. A slot
option fills an existing draft; block placement options insert new drafts.
A slot submit of several files gives the draft the first file and inserts a
draft for each other file after it. When those drafts do not fit there,
`submit` refuses the batch as `does-not-fit`.
Without a placement option, `submit` inserts at the selection and replaces the
selection's block when it is empty, as a paste does.
Cancellation leaves an idle draft. A failed live task keeps its `File` for
explicit retry. Reloaded drafts need a new file selection.

The copied `UploadElement` subscribes to the task keyed by the draft
element. A custom renderer can read
`editor.plugin(UploadPlugin).store.get('task', key)` and subscribe through its
`getSnapshot` and `subscribe` methods. Its progress is the SDK's
`AggregateProgress` with `loaded`, `total`, and `fraction` (`0` to `1`).
Unmounting a renderer does not restart an upload.

`api.fitsAfter(draftKey)` says whether a second draft of the same kind fits
after the draft, where a slot submit puts the draft of a second file. It writes
nothing and returns `false` for a key that names no upload draft. It reads the
committed document, so inside an update it does not see the drafts that update
inserted. The copied `UploadElement` asks it each time its file picker opens, and
the picker takes several files only when the answer is `true`. So a draft that is
the only block its container holds, such as the draft in a board's
[image shape](/docs/board#picture-files), picks one file.

## Insert drafts yourself

`submit` inserts its drafts as blocks. A container that wraps each draft in an
element of its own, such as a gallery card or a board's
[image shape](/docs/board#picture-files), inserts the drafts itself. In one
update, check the batch with `admit`, insert the drafts it returns, then name
each file's draft with `fill`:

```ts
import { BaseUploadPlugin } from 'platejs/upload';

editor.update((tx) => {
  const batch = tx.plugin(BaseUploadPlugin).admit(files, { kind: 'image' });

  if (!batch || 'failure' in batch) return;

  tx.blocks.insert(
    batch.drafts.map((draft) => ({ children: [draft], type: 'card' })),
    { at: [0] }
  );
  batch.fill(
    batch.drafts.flatMap((_draft, index) => tx.key([index, 0]) ?? [])
  );
});
```

Here `card` is an element of your app whose content takes one `image` or
`upload` element. The sample puts each draft in a card at the top of the
document, then reads each draft's key from the place where it sits.

`admit(files, { kind })` writes nothing and returns one of three values:

| Value | When |
| --- | --- |
| `undefined` | There is nothing to do: the list is empty, the view is a preview, or the editor is read-only or destroyed. |
| `{ failure }` | Upload refuses the batch. It passes `failure` to `onError` once, after the update commits. |
| `{ drafts, fill }` | The batch passed. `drafts` holds one new draft per file, in file order. |

With `kind`, a file of another upload kind refuses the batch before every other
check. The failure is `unsupported-file-type`. Its `files` hold only the files
of another kind and its `allowedTypes` hold the file types of `kind`, so you
can call `admit` again without those files. After that check, `admit` runs the
checks that `submit` runs: `rules`, `maxFiles`, the `client` and `getUrl`, and
an installed media plugin for each kind.

Upload does not track the drafts that `admit` returns. Insert them anywhere in
the same update, then call `fill(keys)` with the node key of each file's draft,
in file order. `fill` checks every key before it gives any file a draft:

- It takes one key per file, and no key twice.
- Each key names a live upload draft of its file's kind, outside a read-only
  element.
- No named draft got a file earlier in the same update, from `submit` or `fill`.
- The batch has not been filled yet.

A failed check throws an error that names `fill` and gives no file a draft, and
a correct `fill` can follow a caught error. Each upload starts after the update
commits, as with `submit`. A draft that no `fill` names stays an idle draft and
uploads nothing. The batch lives for the update that admitted it, so call
`fill` inside that update.

## Dropped files

The React `UploadPlugin` lands files dropped into the editor at the block edge
under the pointer, through the same landing rules as a
[block drag](/docs/dnd). A refused drop inserts nothing. The copied DnD kit
draws the drop line while files hover. An editor with only `BaseUploadPlugin`
treats a dropped file like a pasted one. It replaces the empty block at the drop
point or inserts after that block, without landing rules or vetoes, and HTML in
the drop wins.

To keep uploads but refuse dropped files, veto the files landing. The veto needs
the React `UploadPlugin`:

```tsx
import { transferVeto } from 'platejs';
import { definePlugin } from 'platejs/react';

export const RefuseFileDropsPlugin = definePlugin('refuseFileDrops', {
  contributions: [transferVeto.of(({ payload }) => payload.kind === 'files')],
});
```

To handle dropped files yourself, list a plugin before `UploadPlugin` that
claims both `dragover` and `drop`. Plugin handlers run in plugin order, and the
first that returns `true` stops the rest:

```tsx
import { definePlugin } from 'platejs/react';

const carriesFiles = (event: React.DragEvent) =>
  event.dataTransfer.types.includes('Files');

export const MyFileDropPlugin = definePlugin('myFileDrop', {
  on: {
    dragOver: ({ event }) => {
      if (!carriesFiles(event)) return;
      event.preventDefault();
      event.dataTransfer.dropEffect = 'copy';
      return true;
    },
    drop: ({ event }) => {
      if (!carriesFiles(event)) return;
      event.preventDefault();
      // Handle event.dataTransfer.files here.
      return true;
    },
  },
});
```

## Pasted pictures

An editor whose `UploadPlugin` has a `client`, a `getUrl`, and a rule with
`kind: 'image'` uploads the pictures whose bytes come with a paste. These are
raster `data` addresses in pasted HTML or in the editor's own clipboard, the
pictures that [Word paste](/docs/docx#paste-from-word) rebuilds from the RTF
copy, and pictures with a `blob` address, such as a picture copied from Word in
Safari. A `blob` address works only in the tab that pasted it, so the paste
reads its bytes while it runs. Each picture becomes an upload draft where it
landed, so the document never stores its `data` or `blob` address. Its upload
starts after the paste commits, and the finished image keeps the picture's alt
text, width, and caption. Without those three settings, pasted pictures stay as
pasted. The copied `UploadKit` sets all three.

A `blob` picture uploads only when its bytes are a GIF, JPEG, PNG or WebP
image. Its file takes that type from the bytes and a name such as `image.png`.
A `blob` picture whose read fails, or whose bytes are of another kind, such as
SVG, keeps its pasted address while the other pictures upload. The paste reads
with a synchronous request. So a page whose Content Security Policy sets
`connect-src` without `blob:` keeps every `blob` picture as pasted, and so does
a page whose Permissions Policy blocks `sync-xhr` in Chromium. A real Word paste
in Safari is not yet tested.

The paste checks its pictures as one batch against `rules` and `maxFiles`, as
`submit` does. When those rules refuse the batch, every picture keeps the
address it was pasted with, and `onError` runs once. The paste reads its
pictures in document order and stops once it holds more than the batch allows,
so `onError` gets the pictures read up to then. The kit's image rule allows
three files, so a paste of four or more pictures keeps them all as pasted. A
picture whose address does not decode, or whose draft cannot sit where the
picture landed, also stays as pasted while the other pictures upload.

One undo removes the paste and its drafts and stops their uploads. Redo brings
back the drafts without starting an upload. A paste in a Suggesting view or into
a preview keeps every picture as pasted.

A paste does not upload:

- A picture with an `http` or `https` address. It keeps linking to that
  address, and the image plugin turns a plain-text picture link into such an
  image.
- A picture that was in the document before the paste.
- A picture inside a content root the paste adds, such as a copied card's body.
  A paste that adds such a root also keeps every `blob` picture as pasted.

An HTML drop uploads its pictures the same way. With the React `UploadPlugin`,
a drop that carries files uploads those files instead, as
[Dropped files](#dropped-files) describes.

## API reference

| Surface | Purpose |
| --- | --- |
| `BaseUploadPlugin` from `platejs/upload` | Headless draft schema, admission, task, and completion owner. |
| `UploadPlugin` from `platejs/upload/react` | React adapter that lands dropped files at the block edge under the pointer. |
| `UploadPlugin.configure({ initialState })` | Set `client: UploadClient`, synchronous `getUrl: (file: UploadOutcome) => string`, `rules`, `maxFiles`, and `onError`. |
| `editor.plugin(UploadPlugin).update.submit(files, options)` | Insert a validated batch or fill a draft slot. Slot and block placement options are mutually exclusive. |
| `tx.plugin(BaseUploadPlugin).admit(files, { kind? })` | Check a batch for drafts the caller inserts itself. It writes nothing and returns `undefined`, an `UploadRefusal` or an `UploadAdmission`. |
| `fill(keys)` of an `UploadAdmission` | Give each file the draft its node key names, in file order. It throws when a key fails a check. |
| `editor.plugin(UploadPlugin).api.cancel(key)` | Abort the live task for one draft. |
| `editor.plugin(UploadPlugin).api.fitsAfter(key)` | Say whether a second draft of the same kind fits after the draft at `key`. It writes nothing. |

The draft has persisted type `upload` and a required `kind`, while its
`File`, progress, and failure stay in editor state. Completed media stores a
URL and ordinary media fields. JSON preserves unresolved drafts; external HTML,
Markdown, and static rendering omit them. An editor that loads drafts for
static rendering must include `BaseUploadPlugin`; completed media alone needs only the media
plugins.
