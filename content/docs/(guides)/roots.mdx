---
title: "Roots"
description: "Use extra roots for headers, footers, synced blocks, captions, and other editable regions."
---

Plate stores the primary document as a normal block array. Extra roots let one
editor own headers, footers, synced blocks, captions, side panels, and other
editable regions without creating separate editor instances. Use roots when the
content should share editor state, history, collaboration, schema, and commands.

## Value shape

The shortest editor value is still an array of blocks. Plate treats it as the
primary document.

```tsx
const editor = createEditor({
  initialValue: [{ type: "paragraph", children: [{ text: "Body" }] }],
});
```

Pass `initialValue.children` plus `initialValue.roots` when the editor owns
extra roots.

```tsx
const editor = createEditor({
  initialValue: {
    children: [{ type: "paragraph", children: [{ text: "Body" }] }],
    roots: {
      header: [{ type: "paragraph", children: [{ text: "Draft" }] }],
      footer: [{ type: "paragraph", children: [{ text: "Internal" }] }],
    },
  },
});
```

Each root is a normal Plate block array. Rootless transforms, points, and
selections resolve against the current editor or view root. A root-bound view
resolves rootless locations against its own root.

A live node or node key reaches its own root from any editor or view. Plugin
commands follow their target the same way. Given a node from the header, a
command edits the header. Called with no target, it edits the root that holds
the caret. Code outside a plugin command that writes by a bare path on the
editor writes the primary document, so pass a node or use
`useRootEditor(root)` there.

Persist roots through the full [Document Meta](/docs/document-meta) value
instead of saving only one mounted root. When an application publishes a
complete external snapshot, use only `tx.value.replace({ children, roots,
meta, selection })`. It fits the combined document atomically, removes omitted
roots, resets omitted persisted meta, and clears selection when `selection` is
omitted. An invalid combined payload returns `false` and publishes nothing.
Use `tx.roots.*` only for a targeted named-root change.

## Reading and writing roots

Read the primary document with `editor.read.children()`. Read an extra root by key.

```tsx
const body = editor.read.children();
const header = editor.read.root("header");
```

Create, fork, replace, or delete extra roots inside `editor.update`.

```tsx
editor.update((tx) => {
  tx.roots.create("aside:1", [
    { type: "paragraph", children: [{ text: "Aside" }] },
  ]);
});
```

Mutate the primary document with normal node and text transforms instead of
`tx.roots`.

## Rendering roots

Pass `root` to `EditorContent` when one React tree renders a named root.

```tsx
<EditorRoot editor={editor}>
  <EditorContent aria-label="Header" root="header" />
  <EditorContent aria-label="Body" />
  <EditorContent aria-label="Footer" root="footer" />
</EditorRoot>
```

Use `useRootChrome(root)` on non-editable wrappers that should participate
in mouse selection and focus restoration for that root.

```tsx
const chrome = useRootChrome("header");

return (
  <section {...chrome.props}>
    <EditorContent root="header" />
  </section>
);
```

Use `useRootState(root, selector)` for UI that reads one root without
subscribing to every editor change. Use `useRootEditor(root)` for commands
that must run against a specific root. While an `EditorContent` shows that
root, its `editor.api.dom` calls run in the same view of the root as its
commands. [Views](/docs/api/dom#views) lists the calls that run elsewhere and
how the editor `createEditor` returns picks a view.

## Content roots

Content roots attach a separately addressed editable root to an element in
another root. `element.childRoots[slot]` stores the root key, and the detached
content lives in `editor.read.root(rootKey)`. Keep ordinary structural content
in the element's `children`.

```tsx
import { definePlugin, schema } from 'platejs/react';

const SyncedBlockPlugin = definePlugin('syncedBlock', {
  schema: {
    element: {
      content: schema.content.text({ default: 'text', min: 1 }),
      contentRoots: {
        body: {
          content: schema.content.type('paragraph', {
            default: { type: 'paragraph' },
            min: 1,
          }),
          ownership: 'shared',
        },
      },
    },
  },
});
```

Install `SyncedBlockPlugin` in the editor's `plugins` array.

Create a persistent content root by storing the root key on the owning element
and creating the named root in the same transaction.

```tsx
const bodyRoot = `synced-block:${crypto.randomUUID()}:body`;

editor.update((tx) => {
  tx.roots.create(bodyRoot, [
    { type: "paragraph", children: [{ text: "Synced body" }] },
  ]);
  tx.nodes.insert({
    type: "syncedBlock",
    childRoots: { body: bodyRoot },
    children: [{ text: "" }],
  });
});
```

Owner-first and root-first creation are both valid inside one transaction.

Each `contentRoots` entry declares a slot, child-root grammar, and ownership.
An entry that gives only its grammar, such as
`body: schema.content.type('paragraph')`, declares an exclusive root.
`childRoots[slot]` is the persisted ownership link that survives save/load and
collaboration.

Use `ownership: "shared"` when several owners intentionally project the same
root, as with synced blocks. Shared aliases stay attached to one root, and a
copy of an owner keeps the root's key, as
[Copy, paste, and drag](#copy-paste-and-drag) describes. Removing even the last
owner preserves the root. A schema with `unknown: "reject"` cannot hold a root
that no element owns, so there the root goes with its last owner. Use
`ownership: "exclusive"` for a separately mounted document that belongs to
exactly one element, such as an element-owned annotation surface. The schema
refuses a second owner of an exclusive root. Moving an owner preserves its root
key. Removing, retargeting, or changing the type of an exclusive owner removes
the root only when it becomes orphaned, so an exclusive root goes with its last
owner in every schema. In an
[authored](/docs/authored-changes#configure-a-view) `propose` view, deleting an
owner keeps its root until someone accepts the deletion.

To detach one shared copy into its own root without dropping the caret or
duplicating nested shared roots, call `tx.roots.fork(nextRoot, { at, slot })`.
When another holder remains on the old root, nested exclusive roots get copies
of their own, `unique` properties and references renew together, and nested
shared roots stay linked; when the element is the sole holder, the root moves
under `nextRoot` intact. A text or node selection shown by that slot (or in a
copied nested exclusive root) moves into the fork at the same path and offset,
while a selection in a nested shared root stays put.

```tsx
editor.update((tx) => {
  tx.roots.fork(nextRoot, { at: path, slot: "body" });
});
```

### Copy, paste, and drag

Copy and paste, `tx.blocks.duplicate` and drag carry each content root that a
copied owner names, and the root's ownership decides the key it lands under.

A copy of an exclusive root's owner gets its own copy of the root, under a key
that no earlier copy took: `<root>:copy:<n>`, or `<root>:copy:<clientID>:<n>`
in an editor bound to Yjs, so two collaborators' copies never share a key.

A copy of a shared root's owner keeps the root's key, so both blocks show and
edit the same content. When the document holds the root and every block that
names the key declares it the same way, the copy names that root and keeps the
document's content, not the copied content. When the document lacks the root,
the copy creates it under the same key from the copied content. When the
document holds the root and no block names it, as after a cut, the copy names
that root if its content fits the copied owner's grammar. So a cut then paste
keeps the key, in one update or in two.

A shared key must be unique across every document a copy can reach. A paste
into a document that holds an unrelated root under the same key links the
pasted block to that root. Build the key from a random id, such as
`crypto.randomUUID()`, never from a counter that restarts in each document.

A shared root still gets its own copy, as an exclusive root does, when:

- The editor is bound to a shared room or a Yjs document.
- A paste fills or replaces table cells, or pastes a copied table.
- The paste lands inside the root's own content, directly or through another
  root that the shared root holds.
- A block that names the key declares it differently from the copy.
- The document holds the key with no block that names it, and the schema
  declares a root under that key or the root's content does not fit the copied
  owner's grammar. In a `propose` view, the check includes the blocks the view
  hides.
- A [`propose` view](/docs/authored-changes#configure-a-view) reserves the key
  without showing it, as after a cut in that view.

Within one landed copy, owners of one shared root share one new root.

A drag into another document is a copy. When the target's root under that key
holds other content, the drag keeps the target's content and lands with a
`lossy` report. The content matches only when each root holds the same blocks
and the dragged owners share their roots the way the target's owners do. Then
the drag names that root with no report.

`ContentSlice` carries the transitive detached-root payload across clipboard
and insertion boundaries, including a collapsed target. Cut captures that
payload before deleting the owner and root in one transaction. Undo and redo
restore the owner, root content, and root-qualified selection together. One
undo of a paste removes the pasted owner, and the root as well when the paste
created it.

### Set roots

Declare `structure: { kind: 'set' }` on an exclusive content root when each of
its top-level blocks is a separate item, such as the shapes of a
[board](/docs/board). Each top-level block of the root is then a member of the
set.

```tsx
import { definePlugin, schema } from 'platejs/react';

const NotePlugin = definePlugin('note', {
  schema: {
    element: {
      content: schema.content.types(['paragraph'], {
        default: { type: 'paragraph' },
        min: 1,
      }),
      object: true,
    },
  },
});

const CanvasPlugin = definePlugin('canvas', {
  schema: {
    element: {
      contentRoots: {
        shapes: {
          content: schema.content.types(['note'], { min: 0 }),
          ownership: 'exclusive',
          structure: { kind: 'set' },
        },
      },
      void: 'block',
    },
  },
});
```

The schema refuses a set root unless its ownership is `'exclusive'`, its owner
is a void element, and each block type the root admits is an object or a void
element. Every reader then treats the members as separate items:

- A text selection stays in one member. A selection write that crosses
  members, such as Select All, settles in one member and raises no error.
- Removing text or a fragment over a range across members refuses and
  changes nothing. A delete over all of one member's text keeps the member,
  emptied.
- Comparison reports a changed member as one change. Members keep their stored
  order.

A plugin can refuse a type change, wrap, or unwrap of its own owner before the
write applies. Contribute a `nodeWriteVeto` that returns `true` for the writes
it refuses:

```tsx
import { definePlugin, nodeWriteVeto } from 'platejs';

const SyncedBlockGuardPlugin = definePlugin('syncedBlockGuard', {
  contributions: [
    nodeWriteVeto.of(({ node }) => node.type === 'syncedBlock'),
  ],
});
```

The veto receives `{ kind, node, path, root }`. `kind` is `'retype'`,
`'wrap'`, or `'unwrap'`, and a `'retype'` input also carries the new `type`.
`tx.nodes.set`, `tx.blocks.set`, `tx.blocks.reset` and `tx.blocks.toggle`
retype. `tx.nodes.wrap` and a wrapping toggle wrap. `tx.nodes.unwrap` unwraps.
`tx.nodes.lift` counts as an unwrap of the lifted node's parent, except when it
lifts the last of several children, which leaves the parent whole.
`tx.nodes.merge` counts as an unwrap of the node it merges into the node
before, unless that node before is empty and the merge removes it instead. A
merge also counts as an unwrap of each ancestor it empties and removes, such as
a holder whose only child merges into a block outside it, and a delete that
joins two blocks merges them the same way.
One refusal from any contributed veto rolls back the whole update, as a
[refused update](/docs/api/editor-api#updating-state) does. Remote imports and
history replays never consult a veto. Removing the owner is not one of these
writes, so the orphan rule above still applies to it.

Render the child root from the plugin component with `slots.contentRoot(slot)`.

```tsx
const SyncedBlock = ({ attributes, element, slots }) => (
  <section {...attributes}>
    <header>Synced block</header>
    {slots.contentRoot("body", {
      ariaLabel: "Synced block body",
      placeholder: "Empty synced block",
    })}
  </section>
);
```

Undo and redo keys pressed in an editable move focus to the view that made the
step, when that view shows another root inside the same `<Editable>`. Type in
the second of two copies of a synced block, click the page and press Mod+Z.
Focus goes to the second copy, and the caret goes back to where it was before
that typing. Focus stays where the key was pressed when the view that made the
step is gone, hidden or read-only, when that view is outside the `<Editable>`,
or when the step's selection ran from one view into another. It also stays for
a step whose plugin history effect settles after the replay, such as creating a
comment thread. A history control from `useEditorHistory`, an external control
wired to history and the browser handle's `undo()` never move focus to the view
that made the step.

A root whose blocks are selected as whole objects, such as a board's shapes,
can give focus to an element of its own instead of its editable. Pass
`nodeSelectionFocus`, a ref to that element, and give the element
`contentEditable={false}`. That element takes focus when the editor moves focus
into the root, as after an undo, on a click that selects an object in the root
or on a call to `editor.api.dom.focus()`. It takes focus only while no range is
shown into the root and the root's own selection is none or a node selection of
its top-level blocks. A node selection the root kept while the caret was in
another root becomes the selection again once the element holds focus, so a key
the element handles acts on it. It does not come back when the element's focus
handler leaves focus on another element, asks for focus elsewhere or changes the
selection. A focus call made inside an update or a read focuses the editable
instead. Keep the element mounted across renders. When the render that follows
a focus call replaces it, focus falls to the page. An element that inherits
editing runs the editable's own focus handler, which in Firefox moves focus to
the editable. Unless the element is a control, such as a button, the editor
reads no keys from it, so it must handle the keys it needs, such as undo and
redo through the `onKeyDown` of `useEditorHistory`. An undo or redo key leaves
focus where it was pressed when the view that made the step, or the view where
the key was pressed, renders inside a slot that passes `nodeSelectionFocus`. So
an undo pressed in the document of a step made on a board leaves focus and the
caret in the document. An undo pressed on the board of a step made in the
document leaves them on the board.

```tsx
const Board = ({ attributes, children, slots }) => {
  const focusTarget = useRef<HTMLDivElement>(null);
  const history = useEditorHistory();

  return (
    <div {...attributes}>
      <div
        ref={focusTarget}
        tabIndex={-1}
        contentEditable={false}
        onKeyDown={history.onKeyDown}
      />
      {slots.contentRoot("shapes", { nodeSelectionFocus: focusTarget })}
      {children}
    </div>
  );
};
```

Use content roots for synced blocks, editable cards, and element-owned editable
regions. Use [DOM coverage boundaries](/docs/dom-coverage)
when the content is in the same root but intentionally not mounted, such as a
closed accordion body or inactive tab panel.
