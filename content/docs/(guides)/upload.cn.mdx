`UploadPlugin` 管理草稿位和上传任务。Files SDK 传输文件字节；应用负责网关、
文档访问权限和持久下载 URL。已完成的图片、视频、音频和文件节点需要
[媒体插件](/cn/docs/media)。

手动配置时安装软件包和 SDK：

```bash
npm install platejs files-sdk
```

R2 配方会配置 `/api/files`。设置 `FILES_R2_BUCKET`、
`FILES_R2_ACCOUNT_ID`、`FILES_R2_ACCESS_KEY_ID`、
`FILES_R2_SECRET_ACCESS_KEY`、至少 32 个字符且跨进程稳定的
`FILES_API_SECRET`，以及大于零的 `FILES_MAX_UPLOAD_SIZE`。
在复制的 `lib/files.ts` 中实现 `resolveFilesAccess`，按会话和文档 ACL
检查读写权限，包括代理上传的 `PUT` 请求。路由中的 `documentId` 是应用的
文档 ID，不是授权凭证。ID 长度为 1 到 128 个字符，只能包含字母、数字、下划线
和连字符。返回经授权协作者共享的稳定租户/文档命名空间。

S3 配方使用 `FILES_S3_BUCKET` 和 `FILES_S3_REGION`，凭证由 AWS 凭证链提供。
两个持久化提供程序复用 `lib/files.ts` 中同一份网关策略；各自的路由文件只创建
所选适配器。构建其他提供程序配方时，可以直接安装 `files-api`。

## 配置编辑器

在编辑器的文档生命周期内创建一次客户端和插件配置。同步 `getUrl` 将 SDK
`UploadOutcome` 的 key 映射为持久的绝对 URL。将源站地址保存在应用配置中，
使服务端渲染也能使用这段配置。

```tsx
import { createFilesClient } from 'files-sdk/client';
import { UploadPlugin } from 'platejs/upload/react';
import { createEditor } from 'platejs/react';

import { UploadElement } from '@/components/editor/upload';
import { MediaKit } from '@/components/editor/media';

export function createDocumentEditor(documentId: string, appOrigin: string) {
  const endpoint = `/api/files?documentId=${encodeURIComponent(documentId)}`;
  const client = createFilesClient({ endpoint });

  return createEditor({
    plugins: [
      ...MediaKit,
      UploadPlugin.configure({
        component: UploadElement,
        initialState: {
          client,
          getUrl: ({ key }) => {
            const url = new URL(endpoint, appOrigin);
            url.searchParams.set('op', 'download');
            url.searchParams.set('key', key);
            return url.href;
          },
          onError: (failure) => console.error(failure),
        },
      }),
    ],
  });
}
```

网关会为每次下载检查权限，然后重定向到短时有效的存储 URL，或代理可信的内联媒体。持久化 `getUrl`
返回的网关 URL，不要持久化签名存储 URL。浏览器媒体请求和代理上传请求不会
继承 `FilesClient.headers`；请为它们使用同源 Cookie。要内联显示私有媒体，
请通过已验证的文件字节或可信的导入记录配置网关的 `trustedInlineType`。
未配置该策略时，文件作为附件下载。

如果使用复制的 `UploadKit`，请按上面的配置修改 endpoint 和 URL 解析函数，
加入当前 `documentId`。

## 提交和查看任务

```tsx
editor.plugin(UploadPlugin).update.submit(files, { after: blockKey });
editor.plugin(UploadPlugin).update.submit(files, { slot: draftKey });
editor.plugin(UploadPlugin).api.cancel(draftKey);
editor.plugin(UploadPlugin).api.fitsAfter(draftKey);
```

`submit` 接受 `File[]` 或 `FileList`。它在修改文档前验证整个批次，在提交后
为每个文件启动一次 SDK 上传。每个上传在所有提交监听器都收到添加其草稿的提交后才开始。在此之前取消、移除草稿、之后的更新替换整个文档或销毁编辑器，都不会发出请求；撤销恢复草稿也不会重新开始上传。`slot` 填充现有草稿位；块位置选项插入新草稿。用 `slot` 提交多个文件时，第一个文件填充该草稿，其余每个文件各有一个新草稿插入到它之后；这些草稿放不进那里时，`submit` 以 `does-not-fit` 拒绝整个批次。不传位置选项时，`submit` 插入到选区处；选区所在区块为空时会被替换，与粘贴一致。
取消任务会保留空闲草稿。失败的实时任务保留 `File`，可显式重试；重新加载的
草稿需要重新选择文件。

复制的 `UploadElement` 根据草稿节点的 key 订阅任务。自定义组件可以读取
`editor.plugin(UploadPlugin).store.get('task', key)`，并通过任务的
`getSnapshot` 和 `subscribe` 订阅。进度使用 SDK 的 `AggregateProgress`：
`loaded`、`total` 和 `fraction`（`0` 到 `1`）。组件卸载不会重启上传。

`api.fitsAfter(draftKey)` 返回同类的第二个草稿能否放在该草稿之后，也就是 `slot` 提交为第二个文件放置草稿的位置。它不写入任何内容；key 不是上传草稿时返回 `false`。它读取已提交的文档，因此在更新内部看不到该更新插入的草稿。复制的 `UploadElement` 每次打开文件选择器时都会调用它，只有结果为 `true` 时才允许选取多个文件。因此，如果草稿是其容器中唯一的块，例如白板[图片图形](/cn/docs/board#图片文件)中的草稿，文件选择器只接受一个文件。

## 自行插入草稿

`submit` 把草稿作为块插入。如果容器要把每个草稿包在自己的元素中，例如图库卡片或白板的[图片图形](/cn/docs/board#图片文件)，就由容器自己插入草稿。在同一次更新中，先用 `admit` 检查批次，插入它返回的草稿，再用 `fill` 指明每个文件的草稿：

```ts
import { BaseUploadPlugin } from 'platejs/upload';

editor.update((tx) => {
  const batch = tx.plugin(BaseUploadPlugin).admit(files, { kind: 'image' });

  if (!batch || 'failure' in batch) return;

  tx.blocks.insert(
    batch.drafts.map((draft) => ({ children: [draft], type: 'card' })),
    { at: [0] }
  );
  batch.fill(
    batch.drafts.flatMap((_draft, index) => tx.key([index, 0]) ?? [])
  );
});
```

这里的 `card` 是你的应用中的一个元素，其内容接受一个 `image` 或 `upload` 元素。示例把每个草稿放进文档顶部的一张卡片，然后从草稿所在的位置读取它的 key。

`admit(files, { kind })` 不写入任何内容，并返回以下三种值之一：

| 返回值 | 情况 |
| --- | --- |
| `undefined` | 无事可做：列表为空、视图是预览，或编辑器只读或已销毁。 |
| `{ failure }` | 上传拒绝了这个批次。更新提交后，它把 `failure` 传给 `onError` 一次。 |
| `{ drafts, fill }` | 批次通过检查。`drafts` 按文件顺序为每个文件提供一个新草稿。 |

传入 `kind` 时，只要批次中有其他上传类型的文件，它就会在其他所有检查之前被拒绝。失败的 code 是 `unsupported-file-type`，它的 `files` 只包含其他类型的文件，`allowedTypes` 包含 `kind` 的文件类型，因此可以去掉这些文件后再次调用 `admit`。这项检查之后，`admit` 执行 `submit` 所做的检查：`rules`、`maxFiles`、`client` 和 `getUrl`，以及每种类型的媒体插件是否已安装。

上传不会跟踪 `admit` 返回的草稿。在同一次更新中把它们插入任意位置，然后按文件顺序，用每个文件的草稿的节点 key 调用 `fill(keys)`。`fill` 在把任何文件交给草稿之前检查每个 key：

- 每个文件对应一个 key，且 key 不重复。
- 每个 key 指向一个仍在文档中、类型与文件相符的上传草稿，且该草稿不在只读元素内。
- 被指向的草稿在同一次更新中尚未通过 `submit` 或 `fill` 得到文件。
- 这个批次尚未被填充过。

检查失败时会抛出一个提到 `fill` 的错误，任何文件都不会得到草稿；捕获错误后可以再次正确调用 `fill`。与 `submit` 一样，每个上传在更新提交后才开始。没有被任何 `fill` 指向的草稿保持为空闲草稿，不会上传任何内容。批次只在接收它的那次更新中有效，因此要在该更新内调用 `fill`。

## 拖入的文件

React 版 `UploadPlugin` 会把拖入编辑器的文件放在指针所在区块的边缘，并遵循与
[区块拖拽](/docs/dnd)相同的放置规则。被拒绝的拖放不会插入任何内容。文件悬停时，
复制的 DnD 套件会画出放置指示线。只安装 `BaseUploadPlugin` 的编辑器会像粘贴一样
处理拖入的文件：替换放置点处的空区块或插入到该区块之后，不经过放置规则和否决，
拖入内容带有 HTML 时以 HTML 为准。

要保留上传、但拒绝拖入的文件，就否决文件的放置。否决需要 React 版 `UploadPlugin`：

```tsx
import { transferVeto } from 'platejs';
import { definePlugin } from 'platejs/react';

export const RefuseFileDropsPlugin = definePlugin('refuseFileDrops', {
  contributions: [transferVeto.of(({ payload }) => payload.kind === 'files')],
});
```

要自己处理拖入的文件，就在 `UploadPlugin` 之前放一个同时接管 `dragover` 和 `drop` 的插件。
插件处理器按插件顺序运行，第一个返回 `true` 的处理器会阻止后面的处理器：

```tsx
import { definePlugin } from 'platejs/react';

const carriesFiles = (event: React.DragEvent) =>
  event.dataTransfer.types.includes('Files');

export const MyFileDropPlugin = definePlugin('myFileDrop', {
  on: {
    dragOver: ({ event }) => {
      if (!carriesFiles(event)) return;
      event.preventDefault();
      event.dataTransfer.dropEffect = 'copy';
      return true;
    },
    drop: ({ event }) => {
      if (!carriesFiles(event)) return;
      event.preventDefault();
      // 在这里处理 event.dataTransfer.files。
      return true;
    },
  },
});
```

## 粘贴的图片

如果编辑器的 `UploadPlugin` 设置了 `client`、`getUrl`，以及一条 `kind: 'image'` 的规则，粘贴时自带字节的图片会被上传：粘贴的 HTML 或编辑器自身剪贴板中的栅格 `data` 地址，[Word 粘贴](/cn/docs/docx#从-word-粘贴)从 RTF 副本中重建的图片，以及带 `blob` 地址的图片，例如在 Safari 中从 Word 复制的图片。`blob` 地址只在执行粘贴的标签页中有效，因此粘贴会在执行时读取它的字节。每张图片会在落入的位置变成上传草稿，因此文档不会保存它的 `data` 或 `blob` 地址。粘贴提交后才开始上传，完成的图片保留原图片的替代文本、宽度和图注。缺少这三项设置时，粘贴的图片保持原样。复制的 `UploadKit` 已设置这三项。

只有字节是 GIF、JPEG、PNG 或 WebP 图片时，`blob` 图片才会上传。它的文件类型取自字节，文件名形如 `image.png`。读取失败，或字节属于 SVG 等其他格式的 `blob` 图片保留粘贴时的地址，其余图片照常上传。粘贴用同步请求读取字节，因此页面的内容安全策略设置了 `connect-src` 却没有列出 `blob:` 时，所有 `blob` 图片都保持原样；在 Chromium 中，权限策略禁用了 `sync-xhr` 的页面也是如此。在 Safari 中真实粘贴 Word 内容的情况尚未测试。

粘贴会像 `submit` 一样，按 `rules` 和 `maxFiles` 把所有图片作为一个批次验证。批次被拒绝时，每张图片都保留粘贴时的地址，`onError` 只调用一次。粘贴按文档顺序读取图片，一旦超出批次允许的数量就停止读取，因此 `onError` 收到的是到那时为止读取的图片。Kit 的图片规则最多允许三个文件，所以一次粘贴四张或更多图片时，所有图片都保持原样。地址无法解码的图片，或草稿无法放在其落入位置的图片，也会保持原样，其余图片照常上传。

撤销一次会移除这次粘贴及其草稿，并停止它们的上传。重做会恢复草稿，但不会重新开始上传。在建议视图中或向预览中粘贴时，所有图片都保持原样。

以下图片不会被粘贴上传：

- 地址为 `http` 或 `https` 的图片。它继续链接到原地址；图片插件会把纯文本的图片链接变成这样的图片。
- 粘贴前已在文档中的图片。
- 粘贴新增的内容根中的图片，例如复制的卡片正文中的图片。新增这类根的粘贴也会让所有 `blob` 图片保持原样。

拖入的 HTML 中的图片也会这样上传。使用 React 版 `UploadPlugin` 时，带有文件的拖放会改为上传这些文件，详见[拖入的文件](#拖入的文件)。

## API 参考

| 接口 | 用途 |
| --- | --- |
| `platejs/upload` 的 `BaseUploadPlugin` | 无 React 的草稿 schema、接收、任务和完成逻辑。 |
| `platejs/upload/react` 的 `UploadPlugin` | React 适配器，把拖入的文件放在指针所在区块的边缘。 |
| `UploadPlugin.configure({ initialState })` | 配置 `client: UploadClient`、同步 `getUrl: (file: UploadOutcome) => string`、`rules`、`maxFiles` 和 `onError`。 |
| `editor.plugin(UploadPlugin).update.submit(files, options)` | 插入已验证批次或填充草稿；`slot` 与块位置选项不能混用。 |
| `tx.plugin(BaseUploadPlugin).admit(files, { kind? })` | 为调用方自行插入的草稿检查批次。不写入任何内容，返回 `undefined`、`UploadRefusal` 或 `UploadAdmission`。 |
| `UploadAdmission` 的 `fill(keys)` | 按文件顺序把每个文件交给其节点 key 指向的草稿；有 key 未通过检查时抛出错误。 |
| `editor.plugin(UploadPlugin).api.cancel(key)` | 中止一个草稿的实时任务。 |
| `editor.plugin(UploadPlugin).api.fitsAfter(key)` | 返回同类的第二个草稿能否放在 `key` 处的草稿之后。不写入任何内容。 |

草稿持久化类型是 `upload`，并且需要 `kind`。`File`、进度和错误只留在
编辑器状态中。已完成的媒体保存 URL 和普通媒体字段。JSON 保留未完成草稿；
外部 HTML、Markdown 和静态渲染会省略它们。为静态渲染加载草稿的编辑器须包含
`BaseUploadPlugin`；只渲染已完成媒体时只需媒体插件。
