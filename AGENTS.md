## pstack overrides

- **Delivery.** Each task works in its own worktree cut from `origin/next` and lands only through `node .agents/pstack/land.mjs`. Before the first edit, read `.agents/pstack/rules/land.md` in full. When a change alters what an operation promises, search the plans and agent instructions for the old promise, fix this task's own docs, and flag the rest on the page. Production deploys and releases need an explicit request. Never push `main` unless the user asks.
- **Git.** Before a nontrivial edit, check only `git branch --show-current`. Never edit from `main`. This clone's `origin/HEAD` points at `origin/next`, because the desktop app cuts each new worktree from `origin/HEAD`. `git remote set-head origin --auto` points it at the remote's default branch, so never run it. Before a session gets its own worktree, a suggested task's card included, the lead runs `node .agents/pstack/head.mjs`, which points `origin/HEAD` back at `origin/next` when it has moved. Ignore unrelated diffs and never pause to ask about them. Never reset or discard work this run did not write. Reset a proof case in a fresh detached worktree; never run `git stash` in this repository or any of its worktrees, because every worktree shares one stash list. Remove only a worktree the run created, its own once its task lands, or one the `cleanup` skill marks safe. Remove it with `git worktree remove --force <path>` and confirm with `git worktree list`; never run `git worktree prune`, which edits the worktree registry every checkout shares. Before anything runs in a worktree the run creates for a proof or a seat, run the project's `SessionStart` setup command there, `node .agents/pstack/setup.mjs` with the hook's arguments, which copies the main checkout's env files and installs dependencies.
- **Proof.** The `verify` skill is pstack's driver skill here. Bug fixes reproduce and verify through it, and its proof replaces the swarm lanes of pstack's Multi-phase plan.
- **Calls.** Each call the lead makes re-reads the session's whole context, so in a long session the number of calls, not their size, sets the cost. Read several files or line ranges in one command, or as parallel calls in one message, instead of one small read per call. Bookkeeping never takes a call of its own: a retitle, a todo update, a decision-log append, a beacon's set or a plan-page render goes out in the same message as the next working call, and several decision rows go in one append (owner's word, 2026-10-17).
- **Extraction.** The session's own model keeps every judgment: plans, designs, the code the lead writes, synthesis, explainers, judges, cross-judges, a second reader that checks extracted claims, and reflect's synthesis with every decision on what it applies. In Claude Code, a role that only finds evidence for the lead to judge runs on Codex when the models sheet gives it a `codex:<model> @<effort>` value; today that is the `how explorer` role, which gets pstack's explorer prompt. It runs through `cross.mjs --reach`, which loads the user's Codex config, connectors, web search and network but writes only a scratch folder, never the project. Before using an answer, the lead checks that it covers every source and lookup its brief asked for. A seat that fails, returns nothing, or leaves an asked-for source or lookup uncovered, reported or not, reruns once on its model for the part still missing, and the page names any gap left. In Claude Code, when the lead would otherwise read several files it has not read to find where a change goes, it asks such a seat for the spans and call sites instead, confirms the call sites with its own `git grep` of each changed symbol, then reads in full the function it changes and each caller whose behavior the change can break. A read-only fan-out reader the lead starts itself whose sources are all files on disk, such as a map, inventory or sweep lane, runs the same way on the `how explorer` line's model with `cross.mjs` and the lead's brief, which excludes build output.
- **Panel review.** A pstack panel, `/pstack:interrogate` with the configured seats, runs without asking for the work this project's reviews list names and wherever a pstack playbook step or skill calls for it, such as a contested design. `architect` and arena run the same way, such as for Feature's design exploration or a fix that crosses a function boundary. On the user's word, "panel" runs a panel on the current plan or diff, "arena" runs an arena bakeoff of the current artifact, and "full" runs `architect`, then a panel on the plan and another on the diff. Before you launch any panel, `architect` or arena seat, or log a panel row, read `.agents/pstack/rules/panel.md` in full; it holds the Panel review and Review rules. A row of the reviews list triggers only the tool and stage it names, so a row that names a panel on the diff does not by itself run `architect` or a panel on the plan; a pstack step's own trigger still runs them. The reviews list, each row named by its id:
  - `api-plan`: A plan that changes a public API runs `architect` to pick the target, then a panel on the finished plan.
  - `api-build`: A build of an `api-plan` plan gets a panel on its diff.
  - `push`: A push that changes a public API or Plite core, or deletes behavior, gets a panel on its diff first.
  - `external-pr`: Someone else's PR, asked for as "review PR <number>", gets a review-only panel on its diff, briefed with its body, linked issue and plan.
- **Messages and shared resources.** Who can read a message decides its stop, not its channel. A message that anyone outside the team can read, such as a send to customers, an email to a client, or a comment, review, label or close on a public repository's issue or PR, needs explicit authorization from the active request. A PR, its title and its body opened under the Delivery rule are not such a message. A message only team members can read, and shared quota, proceed without asking, as pstack's Autonomy says; a private repository or tracker grants nothing by itself. A message that waits for authorization, or that the runtime's own instructions refuse, goes as a draft under the page's Needs you, or in the reply when there is no page. The owner sends it, and the run keeps going. A "can we X?" question gets a measured answer and a proposal, not the action. An access grant is approved per target and runs as its own command; never widen an approved grant to a new target.
- **Tests.** Before you write, change or cut a test, read `.agents/pstack/rules/tests.md` in full.
- **Browser drives.** Before you type into a page through a browser tool, or judge anything on it that scrolls, animates or loads lazily, read `.agents/pstack/rules/browser.md` in full; it holds how each runtime's browser delivers keys, draws frames and handles the clipboard.
- **Plans and trails.** When work spans sessions, runs unattended, touches another person's area or goes into a PR, keep its plan in the repository as `docs/plans/<date>-<slug>.md` and its show-me-your-work decision log beside it as `docs/plans/<date>-<slug>.decisions.tsv`. A command run as proof writes its log through `node .agents/pstack/proof.mjs --dir <run directory> --name <name> -- <command>`, which records the command line and exit status, and the row that claims the proof cites that log. The lead queues rows in decision order in a TSV in the run directory, five tab-separated cells each, phase, decision, why, evidence and result, and writes them with `node .agents/pstack/decisions-check.mjs append <log> --from <queue>`, which writes the batch only when every row passes. Each result starts with a status word, such as fixed, partial, verified, open, gap or decided. A fixed, verified or proven row puts `scope:` in its evidence, naming what the proof checked and its inputs. A `partial`, `open`, `gap`, `blocked` or `inconclusive` row names `proof: <path>`, an existing file under `docs/plans/artifacts/`, or `proof: none` when it grades no file, and each artifact path a row cites must exist. An `accepted` row names the file it accepts as `proof: <path>` and the plan's Defaults word that accepts it as `word: <word>`. An earlier labeled row must have graded that file partial, open, gap, blocked or inconclusive. The run directory is the main checkout's `docs/plans/artifacts/<slug>/`, written by absolute path, because git ignores it and removing a worktree deletes that worktree's copy. Never commit proof logs, pre-edit copies or other run artifacts.
- **Plan pages.** Before you draft or change a plan, in plan mode or a plan file, and at every stop that hands work back, read `.agents/pstack/rules/pages.md` in full; it holds what the page and the hand-back reply contain. In Claude Code, each decision-log append and each `Status:` change also runs `node .agents/pstack/page-stop.mjs beacon <plan>` in the same command.
- **Autopilot.** Work runs to its close without waiting for the owner. Each call the owner could make gets an attention level, as the `plan-page` skill's memo rules define it: `safe` when the pick is easy to undo and the lead is sure, `look` when it is costly or hard to undo or the lead is unsure, and `answer` when it cannot be taken back or has no clear pick. The lead takes the pick of every call, records it as a Defaults row with the word that reverses it, and keeps going; a call with no clear pick takes its most reversible option. Only these stop the run under Open questions, whatever their level: a production deploy or release, a push to `main`, a force-push to a shared branch, deleting data the run did not create and a models-sheet model that cannot run. What the `cleanup` skill's scan marks safe is not data, and the skill deletes it without asking. That is an idle Next.js cache folder no running server holds, other than an app's own `.next` build. It is also a worktree an agent made that no running session or process, and no recent session transcript, uses. The skill first saves its uncommitted changes as a patch. A message anyone outside the team can read waits as a draft, as the Messages rule says, while the run keeps going. A pending external gate, such as a staging release, a quota reset or a running seat, is not a stop either, and neither is a status question from the owner, which never counts as go. Unless the run is paused, held or at a stop it has reached, whoever or whatever set it, the lead keeps working on ready work and schedules a wakeup for a gate with a known time, chaining wakeups past the scheduler's limit. A prototype, an arena or `architect` picks its winner and keeps going, and the page names the other options. A finding that the accepted design cannot meet a requirement pivots the run when it is found. Such findings include a conclusive miss of a frozen budget and a cost that only a new owner or a new stored shape removes. A hillclimb expects most iterations to miss. A miss there is such a finding only when the loop stops with its stop predicate unmet, such as when only marginal ideas remain, or when a proven cause shows that only a change to a stored shape or an owner, which no iteration can make, closes the gap. A profile alone proves no cause, and one noisy or partial iteration never counts. The lead runs `architect` on the finding, writes the plan that adopts the winner and builds that next. Under "fast", the lead's own design pass replaces `architect`. Until it lands, steps that only finish, document or prove the design it replaces wait, and independent work goes on. Such a finding never waits in Open work, in a suggested task or in a deferred row, unless the owner kept that row until a date in their own words. A request that asks only for a plan or a prototype ends there and builds nothing, a pivot plan included, and the page shows its picks. The owner adds a stop for one request with "stop at plan", which waits once the plan is written, "stop at design", which waits for the owner's pick among the design options, or "stop before ship", which waits before delivery. "panel" and "hold" work at any point. A project's standing stop goes in its own rules outside this block.

The lead fixes in the run a discovery that blocks it, and a skill, rule or helper in the way, as the Improve the workflow mid-task rule says.

## Routing

pstack's poteto-mode picks the playbook, and the Plate owner below supplies the domain method and proof inside it.

- Exact human assignments remain reserved. Read-only mapping and review are allowed; broader cleanup or full execution cannot absorb someone else’s work.
- An audit remains read-only unless its request authorizes repairs.
- **Owner phrases.** "Only uncommitted" means summarize only uncommitted work, never older branch history. "Long term most precise and performant" means choose the architecture or API owner, not another local example condition. "Make it perfect" means stabilize behavior first, then improve performance, then clean the API and DX, then prove readiness. "Go faster" or "it's getting long" means less narration and independent waits run in the background; it never drops a slice, a slice review, a skill load, a whole read of a rule or a gate. Add a phrase here only when the owner's wording, not the rule behind it, changes what to do.
- **Hard cuts.** A hard cut runs when the owner asked to remove that feature, when its plan continues a Pursue verdict on a review the owner asked for, or when `VISION.md` or a `docs/vision/` file already rules the removal or gives the removed job to another owner. Any other hard cut becomes a verdict item, not an owner question. The run keeps the behavior and adds the cut's question to the review ledger. The Hard cut section of `.agents/playbooks/references/architecture.md` holds the rule.
- **Public API.** Any change to a reusable public API runs `best-api repair` before closeout. It edits the rule's one owner, the scope's subject file or, for a rule that binds several scopes, its Vision file, fixes every artifact that still teaches the rejected shape, and regenerates and proves mirrors. A read-only task reports the required repair without implementing it.
- **Workflow changes.** Before you change agent instructions, commands or tooling, read `.agents/playbooks/references/workflow-change.md`.

| Performance inventory, measurement, causal diagnosis and rerun | the Perf issue playbook with `benchmark`; Benchmark review supplies the lens |

Older plans, ledger records and decision pages name retired commands such as `$task`, `$patch` and `$plate-plan`; [docs/development/agent-skills.md](docs/development/agent-skills.md#retired-commands) maps each to today's route. `dropped` in `.agents/pstack.json` keeps a sync or a reflect from restoring them, which overrides the block's rule to keep every typed command as an entry point.

**Playbooks.** The project playbooks in `.agents/playbooks/` rank with this file's rules outside the pstack block, so a playbook change overrides any block rule it names. Any entry that opens a project playbook directly, a skill such as `verdict` included, first loads `pstack:poteto-mode`, runs `check-playbooks.mjs` and follows the steps of the pstack playbook its `extends` names, with the project playbook's deltas applied.

**Workflow guide.** [docs/development/agent-skills.md](docs/development/agent-skills.md) restates this workflow for contributors. Update it when a panel, plan or delivery rule changes.

## Git and publication

- Never auto-approve a payment or a credential use, such as a password, token, API key or OAuth grant prompt. It stops for the owner like the Autopilot rule's always-stop list, and neither a Defaults pick nor "go" approves it.
- An authorized PR includes the entire current checkout, including modified and untracked files, unless the user narrows it. Write multiline `gh` bodies with `--body-file`, stdin or a heredoc, never a literal `\n`; keep the `auto-release` block that Changeset owns, and read the final body back with `gh pr view --json body`. Public issue and PR claims follow Maintainer's truth gates.
- When the user explicitly says to merge a PR, merge it: do not wait for CI, do not ask again, and use an admin merge when needed. This replaces pstack's Shipping verification for that merge.

## Worktrees

- **Pin `origin/HEAD` to `next`.** The desktop app cuts a new worktree from `origin/HEAD`, and GitHub's default branch stays `main` for v1 (`docs/plans/artifacts/2026-10-15-worktree-head/worktree-base-probes.md`). The pstack block's Git rule says how to keep `origin/HEAD` on `next`, and the Claude Code SessionStart hook runs `.agents/pstack/head.mjs` to do it.

## Proof and tooling

- Invoke the `verify` skill itself before checking, skipping, deferring or moving a plan's proof gate to limits; its command recipes (`.agents/rules/verify/references/commands.md`) alone do not carry its proof law.
- Any work that can change latency, payload size, query count, database access, cache or index behavior, runtime pooling, repeated-unit work, subscription fan-out, background throughput or scaling with data, document or DOM size selects Benchmark's performance pack and its pre-acceptance probe.
