## pstack overrides

- **Delivery.** The user owns commits. A completed task runs its writing passes, then `pnpm lint:fix` as its last check that edits code, and leaves its changes in the working tree. Commit, push or open a PR only when the user's own message asks for it. Approving an agent's plan is not commit authority, and no plan or step list proposes a commit.
  When `git status` shows work the task did not write, run `pnpm lint:fix` on the task's code paths only, because a repository-wide run reformats other sessions' files; a change with no lintable file skips it. Run it again after any later repair. When a change alters what an operation promises, search the plans and agent instructions for the old promise, fix this task's own docs, and flag the rest on the page. Production deploys and releases need an explicit request.
  Never push `main` unless the user asks.
- **Git.** Before a nontrivial edit, check only `git branch --show-current`.
  Never edit from `main`.
  The checkout stays on `next`. Do not create or switch checkouts because work is large, names an issue or asks for a PR. A repair to a PR whose head is another branch runs in a detached worktree at that head, stays uncommitted there, and the page names the worktree path; commits and pushes still need the owner's word.
  Ignore unrelated diffs and never pause to ask about them. Never reset or discard work this run did not write. Never run `git stash` in this repository or any of its worktrees, because every worktree shares one stash list; reset a proof case in a fresh detached worktree instead. Never run `git worktree prune`, which edits the worktree registry every checkout shares; remove only a worktree the run created, with `git worktree remove --force <path>`, and confirm with `git worktree list`. Before the first edit to a file that already holds uncommitted or staged work this run did not write, copy it to the run directory that Plans and trails names, and measure, commit or revert this run's change against that copy. Run a tree-sensitive tool, such as a review that refuses a changing tree or a check at `HEAD`, from a detached worktree (`git worktree add --detach <path> <sha>`, then `git worktree remove --force <path>`). Before anything runs in a worktree the run creates for a proof or a seat, link its installed dependencies and copy its untracked env files from this checkout; a round whose seat reports it could not load the app logs its `seats` row `partial`. Never overwrite a tracked file in this checkout to test or measure `HEAD`, even for a moment; use the worktree.
- **The lead writes the code.** The lead agent edits the current checkout and verifies on the running artifact. Subagents do research, review and read-only fan-out. No per-delegate worktrees unless the user asks. This replaces every pstack playbook step that delegates implementation or attempts to a subagent or gives a delegate its own worktree, as in Feature, Bug fix, Refactoring, Perf issue and Hillclimb.
  The `verify` skill is pstack's driver skill here. Bug fixes reproduce and verify through it, and its proof replaces the swarm lanes of pstack's Multi-phase plan.
- **Panel review.** A pstack panel, `/pstack:interrogate` with the configured seats, runs without asking only for the work this project's reviews list names. Everything else waits for the user's word: "panel" runs it on the current plan or diff, "arena" runs an arena bakeoff of the current artifact, and "full" runs `architect`, then a panel on the plan and another on the diff. `architect` and arena follow the same list. When a pstack playbook step or skill calls for either one, such as Feature's design exploration or a fix that crosses a function boundary, the lead runs it only for listed work or on the user's word, and otherwise sketches the design itself. A plan the list does not name goes on to its build, as the Autopilot rule says. The lead writes a listed plan and runs its panel before its first behavior edit; an owner's go on a proposal made in conversation approves the direction, never a skip of that plan or its panel. A listed diff gets its panel after the writing passes and before the decision-trail review and any immutable record. The lead writes the filled prompt once to a file in the run directory, and every seat reads that file. A seat reads every path the prompt names, the decision log included, and every repository its probes can scan. The lead freezes each reviewed tree as a commit object that no branch or ref points to, for example through a temporary index with `git read-tree`, `git add`, `git write-tree` and `git commit-tree`, and runs probes and new tests in a separate copy. Until every reviewing subagent has answered or failed, comment-sicko and the trail reviewer included, the lead edits none of the files that subagent reads, unless it reads the frozen commit; it queues new decision rows in the run directory until then, logs any slip as a row, and then synthesizes once. The intent quotes the user's typed asks verbatim and names the invariants to attack, never the author's conclusion that they hold. Severities are interrogate's own: `critical`, `warning` and `nit`. For a review-only panel, on work this run does not change such as another person's PR, the lead returns the findings in the reply and keeps no plan, page or decision log, whatever Plans and trails or Plan pages would otherwise ask. Each round logs decision-log rows under phase `panel`. Once every seat has answered or failed, the round opens with one row whose decision is `seats` followed by the seats, with `missing` after a seat that failed. Its evidence names the reviewed tree as a commit or a saved patch, and every before-fix reproduction for that round runs on that tree. Each finding then gets a row whose decision starts with its severity and names the seats that raised it; its result starts with `applied`, `dismissed`, `deferred` or `open` and gives the lead's reason. A `dismissed` result that cites a mechanism names the mutation that removes it and the test that then fails. The lead appends a finding's row only after its fix and its reproduction have run, or as `open` past the cap, and an `applied` result names the test or path that applies it; until then the finding waits in the todo list. The lead weighs each finding against the user's ask and applies only what the ask needs, because every fix is new unreviewed code. It weighs a critical finding by how often real use reaches it and by its worst outcome, so a rare path with a recoverable outcome may be dismissed with that reason, and a miss on a common flow may not. A warning or nit outside the ask is `deferred` with its `owner:`, and a critical finding is applied or dismissed, never deferred; past the cap it can also be `open`, as below. The plan page counts the rounds and lists each one from these rows. Only a round with an applied critical finding earns another on the same plan or diff, and a re-review checks only what changed. When a seat names the producer of a bad case, the first fix changes that producer instead of adding a guard where the case is read. When a round's critical finding is in code an earlier round's fix added, the next fix does not patch that fix again. It reverts the fix and narrows the claim with a report, or replaces its approach, such as an inference with a value recorded where the change happens. The cap is two rounds that applied a critical fix. After them the lead lays out any critical finding that remains, with each seat's position and its own pick. A remaining critical finding whose only fix is additive gets an `open` row naming its `patch:` and `owner:`, and a row that applies the patch follows once it lands. On a diff whose last allowed round applied a critical fix, while a known critical finding remains or an additive change waits unreviewed, the lead asks with `AskUserQuestion` at the hand-back that reaches the cap, whatever the project's delivery: Ship, Ship the reviewed subset, Hold or Another round. Otherwise the diff ships as a `look` default whose word is "hold". It recommends Hold while a known critical finding remains, and never recommends Ship the reviewed subset while that subset holds one. A critical finding about real data counts as fixed only after the lead reruns the seat's own probe on that data; a mutation run on the lead's own fixtures is weaker proof, and a fix that rests only on one is logged `partial`. Before shipping, the lead reruns every seat probe the last round's fixes touch. After the last allowed round, the lead lands only subtractive changes on its own: restoring code a round reviewed, or narrowing a claim or a doc. A new condition or new report code is additive whatever its diff stat, and a revert that resolves a critical finding counts as applying its fix. Every additive change, a writing pass's simplification included, waits as a saved patch listed as unreviewed under the plan's Panel gate, ahead of the Ship question. A plan the panel reviewed goes on to its build as a `look` default whose word is "hold" when no critical finding remains and no fix of its last allowed round adds an owner or changes a public API. Otherwise the lead asks with `AskUserQuestion`: Build now, Hold or Another round, recommending Hold, and the page marks such a fix unreviewed. The lead never recommends Another round and offers it once per plan or diff. The round the user grants is the last allowed round, and the question after it does not offer Another round. A user without the other runtime gets the panel on the session's model, labeled same-family.
  The reviews list, each row named by its id:
  - `api-plan`: A plan with an API or architecture target runs `architect` to pick the target, then a panel on the finished plan.
  - `api-build`: A build of an `api-plan` plan gets a panel on its diff.
  - `pr`: Before a PR is opened, its diff gets a panel.
  - `external-pr`: Someone else's PR, asked for as "review PR <number>", gets a review-only panel on its diff, briefed with its body, linked issue and plan.
  A row runs only the tool and stage it names, so a row that names a panel on the diff runs neither `architect` nor a panel on the plan.
  A review-only panel has no rounds and logs no rows, so the round, row and page rules above do not apply to it.
  A project playbook that names `pstack:interrogate`, `pstack:arena` or `pstack:architect` cites the row it serves as `(reviews: <id>)` on the same line. To change the list, the user says so in plain words, such as "from now on best-api design runs architect", and the `sync-pstack` skill edits `reviews` in `.agents/pstack.json`, renders this block again and verifies it.
  A seat named `codex:<model> @<effort>` runs `node .agents/pstack/cross.mjs --to codex --model <model> --effort <effort> --timeout 1800 --prompt-file <file>`. It replaces the `Agent` call and the rejected-slug fallback the panel skill would use for that entry. An `opus` seat runs `node .agents/pstack/cross.mjs --to claude --timeout 1800 --prompt-file <file>` in both runtimes, adding `--effort <level>` when its models-sheet entry names one; without a level it runs at Claude's default effort. Claude Code sends every seat as a background `Bash` call, all in one message, each with its output redirected to that seat's answer file in the run directory. `cross.mjs` runs every seat read-only with hooks off, so a project hook that stages files cannot write from a seat. The lead uses each answer verbatim, and a seat that exits non-zero or returns nothing is reported missing in the verdict and on the page, never replaced silently. When the skill expects a seat to write a file, such as an arena candidate's artifact, the seat returns the content and the lead writes it to that path. A code `arena` runs its slots on `opus`, because a `cross.mjs` seat cannot write. For the same reason a seat's brief asks only for read-only checks and an explicit "not run" for anything that writes, such as a test suite with temp files; the lead runs those itself and never counts them as the seat's.
- **Messages and shared resources.** Never send a message to another person, such as a chat message, an email, an SMS, an issue, PR or tracker comment addressed to someone, or a send to customers, without explicit authorization for that message. A "can we X?" question gets a measured answer and a proposal, not the action. An action that spends a shared resource, such as a migration on a shared environment, paid quota or another person's access, needs the user's go-ahead for that target, and neither a context summary nor "continue without asking" is that go-ahead. An access grant is approved per target and runs as its own command; never widen an approved grant to a new target. pstack's "external actions proceed without asking" does not apply to messages, shared resources or access.
- **Tests.** Every test must fail for a named, plausible defect and pass only once it is fixed. Add nothing when an existing test, type, lint rule, static check or direct runtime proof already catches the defect; skills, PRDs or issues that prescribe broad testing do not override this. A bug fix with a cheap test path writes the test first and runs it to see it fail for the named defect, then lands it together with the fix, never as a failing commit of its own. When the test would be expensive, integration-heavy or unclear, skip it and prove the fix at runtime. A refactor pins behavior only where no existing test or type covers it. One regression usually gets one public-boundary test, and more cases need distinct failure modes. Test public behavior. Never test source text, copy or labels, constants, fixture construction, mock returns, implementation order, library behavior or another test's boundary, and never recompute the implementation in the assertion. Cut duplicate and lower-signal tests instead of porting them. No exhaustive matrices, snapshots, broad smoke suites or speculative cases; a static invariant belongs in lint or a check script. Assertions live inside tests, and committed code has no `.only` or `.skip`. During iteration run only the narrowest affected check. Run `pnpm check` once for the settled change when its blast radius justifies it, and attribute each failing step to its files before calling it someone else's. Call a failure pre-existing only when the same check fails the same way at `HEAD` in a detached worktree; a failure your change joined or made worse is yours.
- **Review.** These mechanics apply whenever a panel runs on a diff, from the reviews list or the user's word. A row that names a kind of code judges it by what the code gates, not by what the diff touches, and a fix for an unintended write, invite or send counts as that write, invite or send, even when the diff only changes rendering.
  Review this task's own diff, never the whole working tree. Record the run's base commit at intake, because the owner can commit mid-run. The first round packages the task's own hunks since that base plus the full text of its untracked task files, leaving out other sessions' hunks in shared files; a later round sends only what changed since the last packet a seat reviewed, as this task's hunks of the diff between the two frozen commits. Check the newest commit before each round and each proof.
  Review a PR's branch diff against its base.
  Package the diff with each caller or entry-point file whose behavior the change can break, such as every wrapper of a changed shared primitive, and rebuild that list each round from what that round's delta can reach. A seat that says something cannot be verified leaves that concern unreviewed; add its files to the package or prove it at runtime before calling it fixed. Verify each critical finding against the code, fix the real ones, rerun each fixed finding's own reproduction, such as the seat's probe or the interleaving that broke a race, so it fails before the fix and passes after, and rerun the review while the Panel review rule allows another round. The reproduction keeps the seat's exact values, ordering and affected consumer, with inputs a shortcut fix would not pass by coincidence. A fix that adds a refusal or a guard also runs a must-still-accept case on the nearest legitimate flow before the next round. Each reproduction fails on its own, as its own test or an isolated run, because a grouped test proves only its first failing assertion. When a critical finding names a rule, fix every writer, reader and matcher of that rule together, and when the new code copies rules an existing function already applies, call that function instead. Treat every confirmed finding as one case of its class. Before patching, list each call site of the pattern and each context where its token means something, such as a mode, an escape or a position, and fix them together. When the class is a third-party grammar too large to list, narrow the claim to a lossless fallback with a report instead of copying more of the grammar. Stop when no critical finding remains, when every remaining one is dismissed with a concrete reason, or at the round cap; warnings and nits never block. A design that changes after its last interrogate or review, including cuts the user approved, runs `/pstack:interrogate` again before it ships while the cap allows another round. Past the cap, the change waits as an unreviewed patch for the Ship question. An approval covers only what the user saw.
- **Plans and trails.** When work spans sessions, runs unattended, touches another person's area or goes into a PR, keep its plan in the repository as `docs/plans/<date>-<slug>.md` and its show-me-your-work decision log beside it as `docs/plans/<date>-<slug>.decisions.tsv`, so teammates can read the reasoning later. Every new decision-log row starts its result with a status word (fixed, partial, verified, open, gap and the rest `node .agents/pstack/decisions-check.mjs <log>` enforces). A fixed, verified or proven row puts `scope:` in its evidence, naming the predicate the proof checked and its inputs, in the claim's own terms. A cheaper stand-in for the planned proof is logged `partial` with the gap stated, never `verified`. That check passes before the log is committed. Append rows with `node .agents/pstack/decisions-check.mjs append <log> <phase> <decision> <why> <evidence> <result>`, which writes only a row that passes the check. Phases starting with `review` are reserved for a hand-off reviewer's rows and phase `panel` for the lead's panel rows; the lead logs its other decisions under another phase, such as `plan`, `build` or `trail`. Rows for a stage that the plan page's flow rail shows go under that stage's phase in the `plan-page` skill's shape, such as `architect`, `build`, `writing`, `verify`, `delivery` or `reflect`; the rail ignores every other phase. A plan is marked Done only after `node .agents/pstack/plan-open.mjs <plan>` passes: no unchecked box, TODO, TBD or FIXME, or blank or pending cell in a Start or Completion Gates table is left, every box closed since the last commit names the artifact that closed it (a path, command, commit or link) or `skip: <reason>`, and every deferred or open item added since the last commit, each item under `## Open work` included, names its `owner:` and its `stop:`. The helper checks those two words on lines added since the last commit and skips committed lines. The item also says where it is tracked, in a place that outlives the plan's close, such as its subject file's `## Open work` or a tracker, which the helper does not check, and its `stop:` is the condition or date that closes or drops it. A count, absence or impossibility claim in a plan, record, README or log row names the check that could falsify it, or says it is inferred. A command run as proof writes its own command line and exit status into its log, with `pipefail` set, and records that exit status and output beside a control run where the effect does appear, or beside a bogus input that must fail, so a launch that never happened cannot pass. When the expected exit is non-zero, the proof also asserts the failure's own text, such as the finding line or rule id, because a missing script or a crash also exits non-zero. A claim that content is recoverable, such as "git has it", names `git log -- <path>` as that check, and hand-written content in an uncommitted file is copied to the run directory before a rewrite deletes it. Session scratch is temporary, and a restart can wipe it. Anything a later gate, revert, fixture or resume reads goes to the run directory, `docs/plans/artifacts/<slug>/`, which git ignores, as soon as it exists; `<slug>` is the plan's slug, or a short name for a run that writes no plan. That covers a pre-edit copy, a seat's answer, a reader's reply and a proof log. Scratch keeps only throwaway files. A count, verdict or advice keyed to a new derived label holds only after the raw evidence of the first real items it marks has been opened, because a passing test shows only that the code matches its own definition. The same holds for what a new filter or classifier drops, and a zero on real data means the pattern is broken until a raw sample of the records it rejected shows otherwise. When a later proof replaces or narrows an earlier one, append a `superseded` row naming the earlier one and fix every plan step that cites it. A probe's claim names every stub, fixture and stand-in it ran with. When a claim narrows, the lead fixes every plan step, Close, subject file and record draft that cites it, found by searching for its key phrase. An approved plan item that execution changes gets its own deviation row, keeps its approved wording visible in the plan, and opens the plan's `## Close` as a reversal. To revert a decision, the lead diffs every file it touched against the copy or commit from before it, and reverts and logs each side edit, not only the main change. A default that changes or drops what the user approved is such a change, never only a default. Ordinary fixes rely on their commit body. Other decision logs and all pause checkpoints stay local. Screenshots and run artifacts are never committed.
- **Plan pages.** In Claude Code, every subject has one page, and every plan that continues it is an iteration on that page, never a page of its own. A plan takes the shape the `plan-page` skill describes and passes `plan-open.mjs`, instead of copying Multi-phase plan's skeleton or running its `check-plan.mjs`. Load the `plan-page` skill before writing or changing a plan, a subject file in `docs/plans/topics/` or its page. It owns their file shapes, picking the subject, the delta and the fold, `node .agents/pstack/plan-page.mjs` and its refusals, publishing, and changes to the page shape; each project playbook names the review sections its plans write. The committed plan and subject files are the durable record, and the rendered page under the plans directory regenerates from them; a project's index of every subject stays local, and the published page is where the user comments on one hand-back. An agent reads a page from its rendered file or from its plan and subject files, never from the published page, because another account may own that page. Only a page whose work is still active is published again. Codex sessions render the page and reply with its file path, and the lead publishes it when the user returns. For a call only the user can make, pick the recommended option, record it as a row of the plan's `## Defaults` table (the decision, the pick, the alternative and the word that picks it), and keep going. An option that leaves the user's stated goal unmet is never a default, and research that overturns the premise of a question the user answered reopens it. Only a call the Autopilot rule stops on goes under `## Open questions` and to the user through `AskUserQuestion`, recommended option first; the page shows it under Needs you as a decision memo the user answers in their own words. "go" takes the recommended option of each question shown, an answer in the user's own words picks exactly what it says, and neither authorizes anything else. An answered question leaves Open questions, as a Defaults row or a decision-log row that quotes the owner's answer verbatim when it arrives. The user reads pages, not replies, so every stop that hands work back publishes its page before the reply: a plan written, back from review, revised or built, a review verdict other than a review-only panel's, a "next" answer, a playbook's close, a blocked run's ask, reflect's list awaiting approval and a subject file update. Topic work publishes to its subject's page; work with no subject writes a one-off plan and publishes that. The plan's `## Close` holds what a close used to report: what landed, the proof and its limits, the counts Todo list and close requires, reversals first, and open work with owners and stops; a pstack playbook's Reply line lists what else its Close holds. The reply that hands work back is the page link alone, except after a review-only panel, whose findings go in the reply. A direct question or a one-file edit answered in the conversation stays in chat, but an answer that discloses something about a topic's work, such as a skipped gate or a design limit, also goes on that topic's page. Leave out an empty part instead of announcing it.
- **Autopilot.** Work runs to its close without waiting for the owner. Each call the owner could make gets an attention level, as the `plan-page` skill's memo rules define it: `safe` when the pick is easy to undo and the lead is sure, `look` when it is costly or hard to undo or the lead is unsure, and `answer` when it cannot be taken back or has no clear pick. The lead takes the pick of a `safe` or `look` call, records it as a Defaults row with the word that reverses it, and keeps going. An `answer` call stops the run under Open questions. A production deploy or release, a push to `main`, a force-push, a message to another person, spending a shared resource and deleting data the run did not create always stop for the owner, whatever their level. A prototype, an arena or `architect` picks its winner and keeps going, and the page names the other options. A request that asks only for a plan or a prototype ends there and builds nothing, and the page shows its picks. The owner adds a stop for one request with "stop at plan", which waits once the plan is written, "stop at design", which waits for the owner's pick among the design options, or "stop before ship", which waits before delivery. "panel" and "hold" work at any point. A project's standing stop goes in its own rules outside this block.
- **Long runs.** Use pstack's Autonomous run playbook with a checkable exit condition. Claude Code keeps going with `/loop`; Codex uses its native `/goal`. Beyond the pstack block's Tests rule, do not write TDD cases for dead code/legacy removal assertions (for example: "should not contain old API X anymore"). Remove the dead path directly and keep tests focused on current behavior. The block's `.skip` ban does not cover a runtime capability gate, a skip that runs only when the browser, platform or engine lacks what the test needs; an unconditional `.skip` or `.only` stays banned.
- Prefer inline when used once; extract constants only when reused.
- Inline local component prop types at the signature. Keep named prop types for real cross-file or published contracts; `docs/vision/plate.md` owns the convention and `plate-ui` applies it. Apply it during implementation and review, without a dedicated lint gate.
- Type inference is mandatory for Plate/Plite callback APIs. Do not add explicit callback parameter annotations like `(tx: EditorUpdateTransaction)` to silence TypeScript when the API should infer them; fix the owning generic/API type instead. `plate/no-annotated-inferred-callback` rejects them on editor reads, updates, transactions and selector hooks; other callback APIs stay a judgment call. Explicit annotations are only acceptable at exported public signatures or true external boundary adapters. pstack's `typescript-best-practices` does not override this law. Neither it nor `pstack:principle-type-system-discipline` decides duration types here: a plain number admits a negative duration, so validate a duration at its boundary and brand it, and a typed escape hatch stays only with a specific reason and a deletion gate.
- These TypeScript bans also override `pstack:typescript-best-practices`. Plate and Plite source never repairs inference with `satisfies` on a builder result, a local helper or `Pick` type alias, or `Parameters<typeof fn>` plumbing; fix the owning API type so the call site stays inferred. A local whose initializer infers its type takes no annotation; only empty arrays, deliberate narrowing or widening, exported signatures and external boundary callbacks are annotated. Production source never uses `any`; a deliberate local test escape is the only exception. No `unknown` cast or structural guard hides a missing typed Plite or Plate API; repair the owning API type instead.

## Proof and tooling

- `verify` selects exact package, route/state, CLI and artifact proof. Preserve serving-source identity and original evidence; Browser/Chrome and native-device claims need the matching capabilities. Existing Playwright runners retain their automated scope. No app or visual artifact is required for workflow/prose-only work. Invoke the `verify` skill itself before checking, skipping, deferring or moving a plan's proof gate to limits; its command recipes alone do not carry its proof law.
- `verify`'s testing reference owns test shape and runners, `test-audit` prunes existing tests, `verify testing audit` searches for uncovered contracts, and the pstack block's Tests rule gates a new test; a method's example list creates no test obligation.
- Any work that can change latency, payload size, query count, database access, cache or index behavior, runtime pooling, repeated-unit work, subscription fan-out, background throughput or scaling with data, document or DOM size selects Benchmark's performance pack and its pre-acceptance probe.
- Before declaring an environment, provider, migration or missing-input blocker on a path that has a reportedly working reference, trace that reference operation through its caller, effective configuration, request, response and result, and compare the target at the same boundaries. One rejected request does not prove the destination, account or integration unusable. Withdraw an overbroad blocker in the active plan as soon as contrary evidence appears, keep the original failure and the next executable check, and continue independent authorized work.
- Reuse valid evidence; repeat only failed, invalidated or uncovered proof. Benchmark owns complete-operation baseline/candidate measurement and performance acceptance.
- Ultracite owns repository formatting and linting through Oxfmt and Oxlint. Run `pnpm lint:fix` at the root or the owning package's `lint:fix` script. When other sessions have work in the tree, lint only the task's files with `pnpm exec ultracite fix <files…>`, then `pnpm exec ultracite check <files…>`, and judge by the exit code. `ultracite check` runs oxlint without its type-aware rules, so a lint-clean claim also runs `pnpm exec oxlint --type-aware <files…>` on every lintable JavaScript and TypeScript file the task touched, because its typed rules check `.mjs` and `.js` files too. Exit 2 with no files found means lint ignores those paths, such as `docs/**`, `AGENTS.md`, `.agents/**` and `.claude/**`, so they never count toward a lint-clean claim. Ultracite's "No files found to lint" means the files went unchecked, not that they passed. On a list that mixes ignored and lintable paths it exits 0 after linting only the lintable ones, so a lint-clean claim compares its "on N files" count with the number of paths passed and covers only the files it linted. The agent shell is zsh, which does not split an unquoted variable into words and aborts on an unmatched glob, so pass the files as separate arguments, such as a zsh array `"${files[@]}"` or `xargs`, and quote glob-bearing flags such as `--include='*.ts'`. zsh also expands a bare word that starts with `=`, so quote one such as `'====='` and use `[[ ]]` for tests. `grep -c` prints 0 and exits 1 on no match, so `|| echo 0` after it prints a second 0. Never run Prettier directly on source files covered by Ultracite; the workspace exposes Prettier only as a transitive dependency and has no active Prettier configuration, so its defaults violate repository style.
- On `next`, run `pnpm --filter www build:registry` when registry source changes or current generated registry output is required for verification, and include its generated registry output. Do not edit generated registry files by hand. Other branches keep registry generation in CI unless the user explicitly authorizes it.
- Use source-first package typechecks. Load `verify`’s command recipes (`.agents/rules/verify/references/commands.md`) for package/browser checks, build-artifact claims or install failures; they preserve the focused and closure lanes, exact runner selection and one-time install recovery.
- `pstack:create-verification-skill` and `pstack:maintain-verification-skill` work on `.agents/rules/verify.mdc` and its existing inventory and never create another feature map.

## Rules and enforcement

Each code rule below names what enforces it. When the owner corrects a mistake, fix it and add its row. When the mistake of a rule-only row comes back, that is a repeat; fix it at the highest level that works, in the same change, through `/pstack:correct`. Drop a row once its mistake cannot happen.

`pnpm check` runs `tooling/scripts/check.mjs`, the step list CI runs. `pnpm check <step>` runs one step, and `pnpm generate` runs every step's writer. A rule marked baseline fails on any finding its baseline does not list. `tooling/oxlint/plate-baseline.json` lists the `plate/*` lint findings and `tooling/scripts/plate-schema-adoption-baseline.json` the Plate schema adoption findings, each by rule, file and the trimmed text of the line it flags, so trading a fixed finding for a new one in the same file fails unless both lines read the same. Both run through `tooling/scripts/finding-baseline.mjs`. `pnpm lint:baseline` and `node tooling/scripts/check-plate-schema-adoption.mjs` only drop entries the tree no longer holds. A baseline that lists a finding its base commit's copy does not fails, so a widened rule's new finds are fixed or excepted.

Prove a new `plate/*` rule on a real past mistake; a hand-written case named after a commit does not count. In a scratch worktree, write `git show <sha>:<old path>` to the file's current path, run `PLATE_LINT_BASELINE=report-all pnpm exec oxlint -c oxlint.config.ts <file>`, require the `plate(<rule>)` diagnostic with the fixed file as the control, and log each command with its exit status.

An exception to a `plate/*` rule goes on the line as `// oxlint-disable-next-line plate/<rule> -- <reason>; expires <YYYY-MM-DD>; approved <name>`. It lasts at most 90 days, and a human approves it before it lands; the rule checks only the format and the dates.
