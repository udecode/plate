## pstack overrides

- **Delivery.** The user owns commits. A completed task runs its writing passes, then `pnpm lint:fix` as its last check that edits code, and leaves its changes in the working tree. Commit, push or open a PR only when the user's own message asks for it. Approving an agent's plan is not commit authority, and no plan or step list proposes a commit.
  When `git status` shows work the task did not write, run `pnpm lint:fix` on the task's code paths only, because a repository-wide run reformats other sessions' files; a change with no lintable file skips it. Run it again after any later repair. When a change alters what an operation promises, search the plans and agent instructions for the old promise, fix this task's own docs, and flag the rest on the page. Production deploys and releases need an explicit request.
  Never push `main` unless the user asks.
- **Git.** Before a nontrivial edit, check only `git branch --show-current`.
  Never edit from `main`.
  The checkout stays on `next`. Do not create or switch checkouts because work is large, names an issue or asks for a PR. A repair to a PR whose head is another branch runs in a detached worktree at that head, and the page names the worktree path.
  The repair stays uncommitted there for the owner's commit.
  Ignore unrelated diffs and never pause to ask about them. Never reset or discard work this run did not write. Never run `git stash` in this repository or any of its worktrees, because every worktree shares one stash list; reset a proof case in a fresh detached worktree instead. Never run `git worktree prune`, which edits the worktree registry every checkout shares; remove only a worktree the run created, with `git worktree remove --force <path>`, and confirm with `git worktree list`. Before the first edit to a file that already holds uncommitted or staged work this run did not write, copy it to the run directory that Plans and trails names, and measure, commit or revert this run's change against that copy. Run a tree-sensitive tool, such as a review that refuses a changing tree or a check at `HEAD`, from a detached worktree (`git worktree add --detach <path> <sha>`, then `git worktree remove --force <path>`). Before anything runs in a worktree the run creates for a proof or a seat, link its installed dependencies, or install them offline where its bundler refuses links, and copy its untracked env files from this checkout; a round whose seat reports it could not load the app logs its `seats` row `partial`. Never overwrite a tracked file in this checkout to test or measure `HEAD`, even for a moment; use the worktree.
- **Other sessions.** Other agent sessions may edit this checkout, the shared source and the projects it syncs at any time. Never plan, review or build around a conflict with them that has not happened: a plan adds no lock, mirror, carry or race step for other sessions, and a panel finding whose only trigger is another agent session editing these files is dismissed with this rule as its reason. Concurrency inside the product, such as two users saving one record, is not this rule's subject. Another repository's rules for its own sessions, such as how they commit, are how to work there, never an invariant a plan or panel attacks. Act only when a conflict blocks the work, such as a refused fast-forward or push, a merge conflict, or a file this run is editing that changed under it. When the blocking change has already landed, rebase or merge onto it, resolve any conflict in this run's own hunks, rerun the checks and retry. When a conflicting hunk is another session's uncommitted work, run `git rebase --abort` first. A hook failure is fixed like any failing check. While it is still uncommitted in another session, pause only that part, keep going on other ready work, and resume once it lands. A block that still holds after an hour goes under Needs you, and the run keeps going.
- **The lead writes the code.** The lead agent edits the current checkout and verifies on the running artifact. Subagents do research, review and read-only fan-out. That covers comment-sicko in `no-comments`: its brief forbids every edit and asks for each verdict with its exact replacement text, and the lead applies the ones it accepts. No per-delegate worktrees unless the user asks. This replaces every pstack playbook step that delegates implementation or attempts to a subagent or gives a delegate its own worktree, as in Feature, Bug fix, Refactoring, Perf issue and Hillclimb.
  The `verify` skill is pstack's driver skill here. Bug fixes reproduce and verify through it, and its proof replaces the swarm lanes of pstack's Multi-phase plan.
- **Panel review.** A pstack panel, `/pstack:interrogate` with the configured seats, runs without asking for the work this project's reviews list names and wherever a pstack playbook step or skill calls for it, such as a contested design. `architect` and arena run the same way, such as for Feature's design exploration or a fix that crosses a function boundary. On the user's word, "panel" runs a panel on the current plan or diff, "arena" runs an arena bakeoff of the current artifact, and "full" runs `architect`, then a panel on the plan and another on the diff. A plan goes on to its build, as the Autopilot rule says. The lead writes a plan whose panel runs and runs that panel before its first behavior edit; an owner's go on a proposal made in conversation approves the direction, never a skip of that plan or its panel. A diff whose panel runs gets it after the writing passes and before the decision-trail review and any immutable record. The lead writes the filled prompt once to a file in the run directory, and every seat reads that file. The prompt names run-directory files by their absolute paths in the main checkout, because the run directory is ignored and a seat's worktree holds no copy. A seat reads every path the prompt names, the decision log included, and every repository its probes can scan. The lead freezes each reviewed tree as a commit object that no branch or ref points to with `node .agents/pstack/freeze.mjs --dir <run directory> [--parent <previous frozen commit>] <paths>`, which leaves its temporary index in the run directory and, with `--parent`, refuses when a path differs between `HEAD` and that commit's tree, its working copy differs from `HEAD` and no named path covers it. That usually means the new tree would reset an earlier round's uncommitted path to `HEAD`; a path the owner committed after that freeze and then changed again also triggers it, and omitting `--parent` starts a new chain. The lead runs probes and new tests in a separate copy. Until every reviewing subagent has answered or failed, comment-sicko and the trail reviewer included, the lead edits none of the files that subagent reads, unless it reads the frozen commit; it queues new decision rows in the run directory until then, logs any slip as a row, and then synthesizes once. The intent quotes the user's typed asks verbatim and names the invariants to attack, never the author's conclusion that they hold. For a review-only panel, on work this run does not change such as another person's PR, the lead returns the findings in the reply and keeps no plan, page or decision log, whatever Plans and trails or Plan pages would otherwise ask. Each finding then gets a row whose decision starts with its severity and names the seats that raised it; its result starts with `applied`, `dismissed`, `deferred` or `open` and gives the lead's reason. The lead weighs each finding against the user's ask and applies only what the ask needs, because every fix is new unreviewed code. It weighs a critical finding by how often real use reaches it and by its worst outcome, so a rare path with a recoverable outcome may be dismissed with that reason, and a miss on a common flow may not. Before dismissing a critical finding as rare, the lead runs the seat's exact case through the real code on the repository's fixtures, and cites a count of the finding's trigger condition from the most real data the project lets the run read without a stop, naming that environment, the count and when the query ran. The lead decides whether the goal still needs an input by a logged count of its non-test callers, leaving out placeholder values. A mechanism the user's typed ask names is always needed. A claim about a wrong record value is never narrowed, and its mechanism always goes back to planning. A critical finding about real data counts as fixed only after the lead reruns the seat's own probe on that data; a mutation run on the lead's own fixtures is weaker proof, and a fix that rests only on one is logged `partial`. - **Messages and shared resources.** Who can read a message decides its stop, not its channel. A message that anyone outside the team can read, such as a send to customers, an email to a client, or a comment, review, label or close on a public repository's issue or PR, needs explicit authorization from the active request. A PR, its title and its body opened under the Delivery rule are not such a message. A message only team members can read, and shared quota, proceed without asking, as pstack's Autonomy says; a private repository or tracker grants nothing by itself. A message that waits for authorization, or that the runtime's own instructions refuse, goes as a draft under the page's Needs you, or in the reply when there is no page. The owner sends it, and the run keeps going. A "can we X?" question gets a measured answer and a proposal, not the action. An access grant is approved per target and runs as its own command; never widen an approved grant to a new target.
- **Tests.** Every test must fail for a named, plausible defect and pass only once it is fixed. Add nothing when an existing test, type, lint rule, static check or direct runtime proof already catches the defect; skills, PRDs or issues that prescribe broad testing do not override this. A bug fix with a cheap test path writes the test first and runs it to see it fail for the named defect, then lands it together with the fix, never as a failing commit of its own. When the test would be expensive, integration-heavy or unclear, skip it and prove the fix at runtime. A refactor pins behavior only where no existing test or type covers it. One regression usually gets one public-boundary test, and more cases need distinct failure modes. Test public behavior. Never test source text, copy or labels, constants, fixture construction, mock returns, implementation order, library behavior or another test's boundary, and never recompute the implementation in the assertion. Cut duplicate and lower-signal tests instead of porting them. No exhaustive matrices, snapshots, broad smoke suites or speculative cases; a static invariant belongs in lint or a check script. Assertions live inside tests, and committed code has no `.only` or `.skip`. During iteration run only the narrowest affected check. Run `pnpm check` once for the settled change when its blast radius justifies it, and attribute each failing step to its files before calling it someone else's. Call a failure pre-existing only when the same check fails the same way at `HEAD` in a detached worktree; a failure your change joined or made worse is yours.
- **Review.** These mechanics apply whenever a panel runs on a diff, from the reviews list or the user's word. A row that names a kind of code judges it by what the code gates, not by what the diff touches, and a fix for an unintended write, invite or send counts as that write, invite or send, even when the diff only changes rendering.
  Review this task's own diff, never the whole working tree. Record the run's base commit at intake, because the owner can commit mid-run. The first round packages the task's own hunks since that base plus the full text of its untracked task files, leaving out other sessions' hunks in shared files; a later round sends only what changed since the last packet a seat reviewed, as this task's hunks of the diff between the two frozen commits. Check the newest commit before each round and each proof.
  Review a PR's branch diff against its base.
  Package the diff with each caller or entry-point file whose behavior the change can break, such as every wrapper of a changed shared primitive, and rebuild that list each round from what that round's delta can reach. A seat that says something cannot be verified leaves that concern unreviewed; add its files to the package or prove it at runtime before calling it fixed. Verify each critical finding, and the cause it states, against the code or the raw output before logging it, fix the real ones, rerun each fixed finding's own reproduction, such as the seat's probe or the interleaving that broke a race, so it fails before the fix and passes after, and rerun the review when a round applied a critical fix, as the Panel review rule says. When that reproduction is a test that already runs on the fixed code, `node .agents/pstack/mutate.mjs --dir <run directory> <spec>` reverts each fix alone in a fresh export it makes of a frozen commit that holds the fix and its test, links this checkout's `node_modules` into it, copies no env file, and removes the export afterwards unless the run is killed. Only one run at a time may use a run directory. A test that needs env files, or a bundler that refuses linked `node_modules`, cannot run through it. It counts a fix when the test then fails, the last 16 MB of its output holds the expected text that the passing control run's output does not, and the file's bytes come back unchanged; the lead names the assertion's own message as that text and reads the mutant's log, because a match does not show which assertion printed it. The reproduction keeps the seat's exact values, ordering and affected consumer, with inputs a shortcut fix would not pass by coincidence. A fix that adds a refusal or a guard also runs a must-still-accept case on the nearest legitimate flow before the next round. Each reproduction fails on its own, as its own test or an isolated run, because a grouped test proves only its first failing assertion. When a critical finding names a rule, fix every writer, reader and matcher of that rule together, and when the new code copies rules an existing function already applies, call that function instead. Treat every confirmed finding as one case of its class. Before patching, list each call site of the pattern and each context where its token means something, such as a mode, an escape or a position, and fix them together. When the class is a third-party grammar too large to list, narrow the claim to a lossless fallback with a report instead of copying more of the grammar. A type system counts as such a grammar, so a new check that reads types enters its first panel claiming only the forms its tests run. The way JavaScript looks up a property counts too, own or inherited, enumerable or not, through a getter or a proxy trap. A check on an options key therefore moves to a closed option set, or the wrapper passes the caller's object untouched to the one owner that reads the key, with no check of its own. Stop when no critical finding remains or every remaining one is dismissed with a concrete reason or is a finished removal's `open` finding; warnings and nits never block. A design that changes after its last interrogate or review for a reason other than that review's findings, including cuts the user approved, runs `/pstack:interrogate` again before its first behavior edit, or before it ships when it is already built; a fix to a round's findings earns another round only as the Panel review rule says. - **Plans and trails.** When work spans sessions, runs unattended, touches another person's area or goes into a PR, keep its plan in the repository as `docs/plans/<date>-<slug>.md` and its show-me-your-work decision log beside it as `docs/plans/<date>-<slug>.decisions.tsv`, so teammates can read the reasoning later. A fixed, verified or proven row puts `scope:` in its evidence, naming the predicate the proof checked and its inputs, in the claim's own terms. When the claim depends on current data, `scope:` also names when that data was read, and a `stop:` that waits on a data event names the query that detects it.
