## pstack overrides

- **Delivery.** The user owns commits. A completed task runs its writing passes, then `pnpm lint:fix` as its last check that edits code, and leaves its changes in the working tree. Commit, push or open a PR only when the user's own message asks for it. Approving an agent's plan is not commit authority, and no plan or step list proposes a commit.
  When `git status` shows work the task did not write, run `pnpm lint:fix` on the task's code paths only, because a repository-wide run reformats other sessions' files; a change with no lintable file skips it. Run it again after any later repair. When a change alters what an operation promises, search the plans and agent instructions for the old promise, fix this task's own docs, and flag the rest on the page. Production deploys and releases need an explicit request.
  Never push `main` unless the user asks.
- **Git.** Before a nontrivial edit, check only `git branch --show-current`.
  Never edit from `main`.
  The checkout stays on `next`. Do not create or switch checkouts because work is large, names an issue or asks for a PR. A repair to a PR whose head is another branch runs in a detached worktree at that head, stays uncommitted there, and the page names the worktree path; commits and pushes still need the owner's word.
  Ignore unrelated diffs and never pause to ask about them. Never stash, reset or discard work this run did not write. Before the first edit to a file that already holds uncommitted or staged work this run did not write, copy it to scratch, and measure, commit or revert this run's change against that copy. Run a tree-sensitive tool, such as a review that refuses a changing tree or a check at `HEAD`, from a detached worktree (`git worktree add --detach <path> <sha>`, then `git worktree remove --force <path>`). Never overwrite a tracked file in this checkout to test or measure `HEAD`, even for a moment; use the worktree.
- **The lead writes the code.** The lead agent edits the current checkout and verifies on the running artifact. Subagents do research, review and read-only fan-out. No per-delegate worktrees unless the user asks. This replaces every pstack playbook step that delegates implementation or attempts to a subagent or gives a delegate its own worktree, as in Feature, Bug fix, Refactoring, Perf issue and Hillclimb.
  The `verify` skill is pstack's driver skill here. Bug fixes reproduce and verify through it, and its proof replaces the swarm lanes of pstack's Multi-phase plan.
- **Panel review.** A pstack panel, `/pstack:interrogate` with the configured seats, runs without asking only for the work this project's reviews list names. Everything else waits for the user's word: "panel" runs it on the current plan or diff, "arena" runs an arena bakeoff of the current artifact, and "full" runs `architect`, then a panel on the plan and another on the diff. `architect` and arena follow the same list. When a pstack playbook step or skill calls for either one, such as Feature's design exploration or a fix that crosses a function boundary, the lead runs it only for listed work or on the user's word, and otherwise sketches the design itself. A plan the list does not name ends by asking with `AskUserQuestion`: Build now, Panel first or Hold. The lead writes a listed plan and runs its panel before its first behavior edit; an owner's go on a proposal made in conversation approves the direction, never a skip of that plan or its panel. A listed diff gets its panel after the writing passes and before the decision-trail review and any immutable record. The lead writes the filled prompt once to a file in its scratch directory, and every seat reads that file. A seat reads every path the prompt names, the decision log included, and every repository its probes can scan. Until every seat has answered or failed, the lead edits none of them, unless the seats work from a detached worktree at a commit or a snapshot in scratch; it queues new decision rows in scratch until then, logs any slip as a row, and then synthesizes once. The intent quotes the user's typed asks verbatim and names the invariants to attack, never the author's conclusion that they hold. Severities are interrogate's own: `critical`, `warning` and `nit`. For a review-only panel, on work this run does not change such as another person's PR, the lead returns the findings in the reply and keeps no plan, page or decision log, whatever Plans and trails or Plan pages would otherwise ask. Each round logs decision-log rows under phase `panel`. Once every seat has answered or failed, the round opens with one row whose decision is `seats` followed by the seats, with `missing` after a seat that failed. Its evidence names the reviewed tree as a commit or a saved patch, and every before-fix reproduction for that round runs on that tree. Each finding then gets a row whose decision starts with its severity and names the seats that raised it; its result starts with `applied`, `dismissed` or `deferred` and gives the lead's reason. The lead appends a finding's row only after its fix and its reproduction have run, and an `applied` result names the test or path that applies it; until then the finding waits in the todo list. The lead weighs each finding against the user's ask and applies only what the ask needs, because every fix is new unreviewed code; a warning or nit outside the ask is `deferred` with its `owner:`, and a critical finding is applied or dismissed, never deferred. The plan page counts the rounds and lists each one from these rows. Only a round with an applied critical finding earns another on the same plan or diff, and a re-review checks only what changed. After two such rounds the lead lays out any critical finding that remains, with each seat's position and its own pick. On a diff whose last allowed round applied a critical fix, the lead asks with `AskUserQuestion` before any shared push: Ship, Another round or Ship the reviewed subset. A critical finding about real data counts as fixed only after the lead reruns the seat's own probe on that data; a mutation run on the lead's own fixtures is weaker proof, and a fix that rests only on one is logged `partial`. Before shipping, the lead reruns every seat probe the last round's fixes touch. After the last allowed round, the lead lands only subtractive changes on its own, such as a revert to reviewed behavior or a narrower claim with a report. Every additive change, a writing pass's simplification included, waits as a saved patch listed as unreviewed under the plan's Panel gate, ahead of the Ship question. For a plan the panel reviewed, the lead then asks with `AskUserQuestion`: Build now, Another round or Hold, recommending Build now when no critical finding remains and its own pick otherwise. When the last allowed round's critical fix adds an owner or changes a public API, the page marks that fix unreviewed and the recommendation is Another round or Hold. A user without the other runtime gets the panel on the session's model, labeled same-family.
  The reviews list, each row named by its id:
  - `api-plan`: A plan with an API or architecture target runs `architect` to pick the target, then a panel on the finished plan.
  - `api-build`: A build of an `api-plan` plan gets a panel on its diff.
  - `pr`: Before a PR is opened, its diff gets a panel.
  - `external-pr`: Someone else's PR, asked for as "review PR <number>", gets a review-only panel on its diff, briefed with its body, linked issue and plan.
  A row runs only the tool and stage it names, so a row that names a panel on the diff runs neither `architect` nor a panel on the plan.
  A review-only panel has no rounds and logs no rows, so the round, row and page rules above do not apply to it.
  A project playbook that names `pstack:interrogate`, `pstack:arena` or `pstack:architect` cites the row it serves as `(reviews: <id>)` on the same line. To change the list, the user says so in plain words, such as "from now on best-api design runs architect", and the `sync-pstack` skill edits `reviews` in `.agents/pstack.json`, renders this block again and verifies it.
  A seat named `codex:<model> @<effort>` runs `node .agents/pstack/cross.mjs --to codex --model <model> --effort <effort> --timeout 1800 --prompt-file <file>`. It replaces the `Agent` call and the rejected-slug fallback the panel skill would use for that entry, and Claude Code sends it as a background `Bash` call in the same message as the other seats' `Agent` calls. In Codex, an `opus` seat runs `node .agents/pstack/cross.mjs --to claude --timeout 1800 --prompt-file <file>`. `cross.mjs` runs every seat read-only with hooks off, so a project hook that stages files cannot write from a seat. The lead uses each answer verbatim, and a seat that exits non-zero or returns nothing is reported missing in the verdict and on the page, never replaced silently. When the skill expects a seat to write a file, such as an arena candidate's artifact, the seat returns the content and the lead writes it to that path. A code `arena` runs its slots on `opus`, because a `cross.mjs` seat cannot write. For the same reason a seat's brief asks only for read-only checks and an explicit "not run" for anything that writes, such as a test suite with temp files; the lead runs those itself and never counts them as the seat's.
- **Messages and shared resources.** Never send a message to another person, such as a chat message, an email, an SMS, an issue, PR or tracker comment addressed to someone, or a send to customers, without explicit authorization for that message. A "can we X?" question gets a measured answer and a proposal, not the action. An action that spends a shared resource, such as a migration on a shared environment, paid quota or another person's access, needs the user's go-ahead for that target, and neither a context summary nor "continue without asking" is that go-ahead. An access grant is approved per target and runs as its own command; never widen an approved grant to a new target. pstack's "external actions proceed without asking" does not apply to messages, shared resources or access.
- **Tests.** Every test must fail for a named, plausible defect and pass only once it is fixed. Add nothing when an existing test, type, lint rule, static check or direct runtime proof already catches the defect; skills, PRDs or issues that prescribe broad testing do not override this. A bug fix with a cheap test path writes the test first and runs it to see it fail for the named defect, then lands it together with the fix, never as a failing commit of its own. When the test would be expensive, integration-heavy or unclear, skip it and prove the fix at runtime. A refactor pins behavior only where no existing test or type covers it. One regression usually gets one public-boundary test, and more cases need distinct failure modes. Test public behavior. Never test source text, copy or labels, constants, fixture construction, mock returns, implementation order, library behavior or another test's boundary, and never recompute the implementation in the assertion. Cut duplicate and lower-signal tests instead of porting them. No exhaustive matrices, snapshots, broad smoke suites or speculative cases; a static invariant belongs in lint or a check script. Assertions live inside tests, and committed code has no `.only` or `.skip`. During iteration run only the narrowest affected check. Run `pnpm check` once for the settled change when its blast radius justifies it, and attribute each failing step to its files before calling it someone else's. Call a failure pre-existing only when the same check fails the same way at `HEAD` in a detached worktree; a failure your change joined or made worse is yours.
- **Review.** These mechanics apply whenever a panel runs on a diff, from the reviews list or the user's word. A row that names a kind of code judges it by what the code gates, not by what the diff touches, and a fix for an unintended write, invite or send counts as that write, invite or send, even when the diff only changes rendering.
  Review this task's own diff, never the whole working tree. Record the run's base commit at intake, because the owner can commit mid-run. The first round packages the task's own hunks since that base plus the full text of its untracked task files, leaving out other sessions' hunks in shared files; a later round sends only what changed since the last packet a seat reviewed. Check the newest commit before each round and each proof.
  Review a PR's branch diff against its base.
  Package the diff with each caller or entry-point file whose behavior the change can break, such as every wrapper of a changed shared primitive. A seat that says something cannot be verified leaves that concern unreviewed; add its files to the package or prove it at runtime before calling it fixed. Verify each critical finding against the code, fix the real ones, rerun each fixed finding's own reproduction, such as the seat's probe or the interleaving that broke a race, so it fails before the fix and passes after, and rerun the review. Each reproduction fails on its own, as its own test or an isolated run, because a grouped test proves only its first failing assertion. When a critical finding names a rule, fix every writer, reader and matcher of that rule together, and when the new code copies rules an existing function already applies, call that function instead. Treat every confirmed finding as one case of its class. Before patching, list each call site of the pattern and each context where its token means something, such as a mode, an escape or a position, and fix them together. When the class is a third-party grammar too large to list, narrow the claim to a lossless fallback with a report instead of copying more of the grammar. Stop when no critical finding remains or every remaining one is dismissed with a concrete reason; warnings and nits never block. A design that changes after its last interrogate or review, including cuts the user approved, runs `/pstack:interrogate` again before it ships; an approval covers only what the user saw.
- **Plans and trails.** When work spans sessions, runs unattended, touches another person's area or goes into a PR, keep its plan in the repository as `docs/plans/<date>-<slug>.md` and its show-me-your-work decision log beside it as `docs/plans/<date>-<slug>.decisions.tsv`, so teammates can read the reasoning later. Every new decision-log row starts its result with a status word (fixed, partial, verified, open, gap and the rest `node .agents/pstack/decisions-check.mjs <log>` enforces). A fixed, verified or proven row puts `scope:` in its evidence, naming the predicate the proof checked and its inputs, in the claim's own terms. A cheaper stand-in for the planned proof is logged `partial` with the gap stated, never `verified`. That check passes before the log is committed. Append rows with `node .agents/pstack/decisions-check.mjs append <log> <phase> <decision> <why> <evidence> <result>`, which writes only a row that passes the check. Phases starting with `review` are reserved for a hand-off reviewer's rows and phase `panel` for the lead's panel rows; the lead logs its other decisions under another phase, such as `plan`, `build` or `trail`. A plan is marked Done only after `node .agents/pstack/plan-open.mjs <plan>` passes: no unchecked box, TODO, TBD or FIXME, or blank or pending cell in a Start or Completion Gates table is left, every box closed since the last commit names the artifact that closed it (a path, command, commit or link) or `skip: <reason>`, and every deferred or open finding names its `owner:` and where it is tracked, in a place that outlives the plan's close, such as its subject file's `## Open work` or a tracker. A count, absence or impossibility claim in a plan, record, README or log row names the check that could falsify it, or says it is inferred. A command run as proof writes its own command line and exit status into its log, with `pipefail` set, and records that exit status and output beside a control run where the effect does appear, or beside a bogus input that must fail, so a launch that never happened cannot pass. A claim that content is recoverable, such as "git has it", names `git log -- <path>` as that check, and hand-written content in an uncommitted file is copied to scratch before a rewrite deletes it. A count, verdict or advice keyed to a new derived label holds only after the raw evidence of the first real items it marks has been opened, because a passing test shows only that the code matches its own definition. The same holds for what a new filter or classifier drops, and a zero on real data means the pattern is broken until a raw sample of the records it rejected shows otherwise. When a later proof replaces or narrows an earlier one, append a `superseded` row naming the earlier one and fix every plan step that cites it. A probe's claim names every stub, fixture and stand-in it ran with. When a claim narrows, the lead fixes every plan step, Close, subject file and record draft that cites it, found by searching for its key phrase. An approved plan item that execution changes gets its own deviation row, keeps its approved wording visible in the plan, and opens the plan's `## Close` as a reversal. To revert a decision, the lead diffs every file it touched against the copy or commit from before it, and reverts and logs each side edit, not only the main change. A default that changes or drops what the user approved is such a change, never only a default. Ordinary fixes rely on their commit body. Other decision logs and all pause checkpoints stay local. Screenshots and run artifacts are never committed.
- **Plan pages.** In Claude Code, every subject has one page, and every plan that continues it is an iteration on that page, never a page of its own. A plan takes the shape the `plan-page` skill describes and passes `plan-open.mjs`, instead of copying Multi-phase plan's skeleton or running its `check-plan.mjs`. Load the `plan-page` skill before writing or changing a plan, a subject file in `docs/plans/topics/` or its page. It owns their file shapes, picking the subject, the delta and the fold, `node .agents/pstack/plan-page.mjs` and its refusals, publishing, and changes to the page shape; each project playbook names the review sections its plans write. The rendered file under the plans directory is the durable page, and a project's index of every subject stays local; the published page is where the user comments on one hand-back. Codex sessions render the page and reply with its file path, and the lead publishes it when the user returns. For a call only the user can make, pick the recommended option, record it as a row of the plan's `## Defaults` table (the decision, the pick, the alternative and the word that picks it), and keep going. An option that leaves the user's stated goal unmet is never a default, and research that overturns the premise of a question the user answered reopens it. Only a call with no safe default, because it is irreversible, outward or has no clear recommendation, goes under `## Open questions` and to the user through `AskUserQuestion`, recommended option first; the page shows it under Needs you and says that go takes every recommendation. "go", or a pasted answer line, is the user's explicit answer to each question shown, for exactly the option it picks, and authorizes nothing else. An answered question leaves Open questions, as a Defaults row or a decision-log row. The user reads pages, not replies, so every stop that hands work back publishes its page before the reply: a plan written, back from review, revised or built, a review verdict other than a review-only panel's, a "next" answer, a playbook's close, a blocked run's ask, reflect's list awaiting approval and a subject file update. Topic work publishes to its subject's page; work with no subject writes a one-off plan and publishes that. The plan's `## Close` holds what a close used to report: what landed, the proof and its limits, the counts Todo list and close requires, reversals first, and open work with owners; a pstack playbook's Reply line lists what else its Close holds. The reply that hands work back is the page link alone, except after a review-only panel, whose findings go in the reply. A direct question or a one-file edit answered in the conversation stays in chat, but an answer that discloses something about a topic's work, such as a skipped gate or a design limit, also goes on that topic's page. Leave out an empty part instead of announcing it.
- **Long runs.** Use pstack's Autonomous run playbook with a checkable exit condition. Claude Code keeps going with `/loop`; Codex uses its native `/goal`. On "pause", run pstack's Pause safely playbook without its `wip:` commit; the checkpoint stays local, and the Delivery rule decides every commit. Automatic continuation or compaction never resumes paused work. In Codex, read an existing goal before creating one, mark a goal blocked only when the goal tool's own repeated-blocking threshold is met and no useful progress remains, never for budget or difficulty, and mark it complete only when its exit condition holds and the plan's checks pass, never just to stop. "go" after a plan, or after a review that proposes one, runs every remaining slice without pausing between slices; it adds no commit, message or shared-resource authority beyond the options an answer to Needs you picks, as Plan pages says. Report each reversible call with the word that reverses it. Before each gate, such as a panel launch, a writing pass, the trail review or the close, and after every compaction or wakeup, the lead re-reads `AGENTS.md` and the models sheet from disk when either changed since its last read, and rewrites its open gates from the new text. A mid-run sync reaches the lead only through a later read.
- **Todo list and close.** Where pstack opens a todo list, add after the playbook steps one todo per explicit user ask, quoted, and one per gate this file makes the work trigger, such as proof, the writing passes, then review, then the last check and delivery. A gate that must pass before a mid-run step, such as the trail review before a shared push, gets its own todo placed right before that step. Each todo closes with the artifact that proves it, such as the skill invocation, test run, path or commit, or `skip: <reason>`; a gate is never ticked before that artifact exists. Close in this order: the cheap proofs that can still force a code change, such as a recovery path or a one-repeat smoke; the writing passes; the panel review, when one runs, and its fixes; the lint fix; the repeated acceptance proof, run once on bytes no pending step can change, which a later edit, a lint fix included, reopens; the decision-trail review, when one runs; then immutable records such as ledger records, attestations and proven decision-log rows; then `/pstack:reflect` once the trail review has returned, so its reviewers see the findings. After this run edits an instruction file, such as `AGENTS.md`, a skill or a models sheet, every later subagent brief names those files and tells the subagent its loaded copy is stale and to re-read them from disk. Save every subagent reply that a later gate reads, such as an arena candidate, a judge verdict or a panel seat's answer, to that subagent's scratch directory when it arrives, copied verbatim from its transcript, never retyped. Each parallel subagent brief names its own scratch directory, which also holds that subagent's fallback todo list, and asks for its findings in the reply or a TSV data file, never a report `.md`, which Claude Code subagents refuse to write. Before every final reply, reread this run's user messages, corrections included; add any ask that has no todo, then finish it or skip it with a reason. A close of more than ten items states in its Close how many are done, skipped, blocked and open, and those counts add up to the total. A resume prompt, whether handed to another session or scheduled as a wakeup or `/loop` prompt, carries the goal, the gate and the plan path, and says to continue at the plan's first open gate, never a list of steps. Shared state changes before it fires, a wakeup fires again after its steps are done, and the plan's next action is the one place that gets corrected.
- **Writing passes.** pstack triggers four separate writing passes; run one per kind of change. A pass counts only when the lead invokes its skill in the current context; a reread from memory is not the pass, and its todo stays open. Product code gets `deslop`, then `no-comments`, before any review and before it is committed or handed back. Docs, plans, agent files, commit bodies and PR text get one `unslop` pass after drafting. Run the writing passes and review fixes before an expensive runtime proof; a finding that changes behavior reopens the proof it touches, or the claim narrows to the bytes actually proven. `technical-writing` is a reference for plans, PRDs and RFCs, not a required pass. Replies are written clean as drafted, with no separate pass.
- **Commit and PR text.** Commits use Conventional Commits, `type(scope): subject`. The type is one of `feat`, `fix`, `docs`, `refactor`, `test`, `chore` or `perf`, and the scope is the changed area. The subject is short and imperative, names a real symbol when one carries the change, and has no trailing period. The body explains why in a short paragraph and describes the final behavior; it never restates the subject or lists intermediate attempts. A PR targets `next` and opens ready, not as a draft, and never while `pnpm check` fails unless the user says so.
  It never targets `main`.
  Its body links its plan first, then follows pstack's Opening a PR for its sections.
- **Principles in replies.** pstack's principle skills still apply. Read the leaf skill for any principle a decision rests on, as poteto-mode's Principles list says. Only the rule to name each principle in the reply is dropped; name one only when it explains a choice the reader would otherwise question.
- **Decision-trail review.** show-me-your-work asks for a reviewer from another model family. It runs for an unattended run, for work that went through a panel and for a new or changed shared script or check; any other decision log skips it. That reviewer is a `codex:gpt-6.1-sol @xhigh` seat in Claude Code and an `opus` seat in Codex, run as the Panel review rule describes. Its brief quotes the user's asks verbatim, and each invariant it names traces to one of them; a decision the lead made itself, such as a deviation or a fix made mid-build, goes in as a decision to attack. The trail review checks the log against the transcript, not the code, so it never counts as review of code no panel read. Only when that seat fails, use a fresh-context subagent of the session's model and label the review same-family in the Close.
- **Blocked.** For an unclear tool or access failure, allow two informed attempts or ten minutes, whichever comes first. Then finish a bounded repair, ask once for the exact human action under the page's Needs you, or move to other ready work. Never claim a skipped or unavailable proof passed.
- **Improve the workflow mid-task.** When a skill, rule, script or helper gets in the way, fix it then, separately from the task's change, and keep working. When applying a lesson, reread the destination section for a rule the new text contradicts and resolve it in the same edit.
