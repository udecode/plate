## How work runs

- pstack's `poteto-mode` is the engineering method. The `pstack@pstack-claude` plugin is pinned to GitHub tag `v0.9.158` in `.claude/settings.json`, and each person's Codex marketplace pins the same tag. Its session hook routes multi-file, design and unexplained-bug work into poteto-mode, which picks the playbook. Questions, small edits and one-file changes work directly and are verified on the real artifact. A small edit is one whose every changed line the lead can write down before it starts, and that keeps every signature other files call. A typo, a wording fix and the same one-line fix in several files are small edits. A small edit works directly at any file count, so it follows no playbook.
- Project playbooks in `.agents/playbooks/` build on pstack's, as poteto-mode's Project playbooks paragraph describes. `check-playbooks.mjs` ships with pstack, not the project. After a project playbook changes and before one applies, run `node <plugin>/skills/poteto-mode/scripts/check-playbooks.mjs` from the project root, where `<plugin>` is the directory above `skills/` in the base directory a pstack skill prints. This project's playbooks are:
  - `.agents/playbooks/babysit.md`, on top of pstack's `babysit`. Use it to finish, perfect or clean up an existing PR or the current tree, merging the PR once it is green, or for "review PR <number>" on someone else's PR.
  - `.agents/playbooks/bug-fix.md`, on top of pstack's `bug-fix`. Use it for a Plate or Plite bug report, a regression, a screenshot or recording of wrong behavior, or "diagnose <report>".
  - `.agents/playbooks/build.md`, on top of pstack's `feature`. Use it for a plan that goes on to its build, "go" or "Build now" after a plan, "build now" or "complete the build", `execute <plan>`, or removing a feature (a hard cut).
  - `.agents/playbooks/perf-issue.md`, on top of pstack's `perf-issue` and `hillclimb`. Use it to benchmark, profile or compare Plate, Plite or Slate speed, to find, explain or repair a performance regression or a lying benchmark, or for `benchmark [scope]` and `benchmark only <lane-or-target>`.
  - `.agents/playbooks/plan.md`, on top of pstack's `multi-phase-plan`. Use it for a Pursue verdict, which continues into it, for "plan", `plan <goal>`, "design plan", or an architecture or API adoption plan.
  - `.agents/playbooks/refactoring.md`, on top of pstack's `refactoring`. Use it to audit or simplify Plate or Plite code ownership, such as "clean up <code surface>", "simplify <package>" or a structural audit that deletes, merges, inlines or splits code; retiring docs goes to `research` instead.
  - `.agents/playbooks/triage.md`, on top of pstack's `investigation`. Use it for `triage`, `triage label:<label>`, `triage discussions [<category>]`, `triage #<N>`, `triage plate-private#<N>`, `triage fix #<N>`, `triage fix plate-private#<N>`, `triage fix <domain>`, `triage fix next` or `triage status`, for `maintainer issues`, and for a udecode/plate or udecode/plate-private issue URL. A Slate issue stays with `maintainer slate-issue`, and a security-shaped report with `maintainer security`.
  - `.agents/playbooks/verdict.md`, on top of pstack's `investigation`. Use it for `verdict` on any input, "what would you do from <material>", "what should we build next for <feature>" or another plain ask for one scope's next step, "review <scope id>" when the scope is not a PR, `explore <scope or idea>` when the owner wants to steer the research in rounds before any verdict, `audit`, `audit restart`, `audit <scope or group id>`, or "again" after a verdict.
- If no `pstack:*` skills are available, stop and ask the user to install the plugin before engineering work. In Claude Code they trust the folder and run `claude plugin install pstack@pstack-claude --scope project`. In Codex they run `codex plugin marketplace add michael-denyer/pstack-claude --ref v0.9.158` and `codex plugin add pstack@pstack-claude` from their home directory, then trust the session hook in `/hooks`. - The latest user correction wins over every rule. This file's rules outside this block win over the overrides inside it, and those win over pstack. pstack's hook itself says project instructions take precedence.

- **T3 orchestration.** Pick the child tier by who owns the result and what model or isolation it needs:
  - `invoke_subagent` (`Model: "inherit"`, never `pro`, `flash`, or `flash_lite`): default for same-provider, same-model child work where the parent waits on and consumes the result (research lanes, package audits, `operator` normal fixes or judges, parallel plan steps, `verdict` exploration).
  - `delegate_task` (`mode: "async"`): parent still owns the result, when needing another provider (`claude-opus-5-5` for UI/visual, `gpt-6.2-sol`, `claude-fable-5-2`), higher effort (`gemini-4-neon @xhigh` for stuck debugging or arena), or T3-managed `isolation: "worktree"`.
  - `t3_thread_launch`: only for standalone top-level threads that outlive the parent and talk directly to the user in their own worktree (`workspaceStrategy`): launching an independent queued task, a standalone feature thread explicitly spun off, or a pinned daemon (`📌 operator`). Never for subtasks, parallel steps, `verdict`, routine `operator` fixes, or panels.
- **Effort cap.** No role or seat runs above `xhigh`, the `maxEffort` in `.agents/pstack.json`. `cross.mjs` caps every run it starts.
- **Helper effort.** Helpers start at the lead's effort, capped by `maxEffort` (Antigravity defaults to `high`; Claude reads `node .agents/pstack/lead.mjs`; Codex reads `codex-session-effort.mjs` then `lead.mjs`; fallback `maxEffort` or `high`, never ask). Pass effort explicitly on Claude `Agent` (`effort`) and Codex `spawn_agent` (`reasoning_effort`). Use `medium` for routine lanes (`operator`, routine Local CI fixers, docs/registry/changelog/sync, pure evidence/research subagents, `clip`, `video transcripts`), `high` for core coding, plans, verdicts, UI/visual and panel seats, and `xhigh` for `arena runners`, `strongest judgment`, and stuck debugging after `high` fails. Swarm workers, panel seats, code delegates and arena runners use their models-sheet level.

## pstack overrides

- **Delivery.** Each task works in its own worktree cut from `origin/next` and lands only through `node .agents/pstack/land.mjs`. Before the first edit, or the first write to the forge such as opening a PR, posting a comment, approving a CI run or pushing, read `.agents/pstack/rules/land.md` in full. When a change alters what an operation promises, search the plans and agent instructions for the old promise, fix this task's own docs, and flag the rest on the page. Production deploys and releases need an explicit request. Never push `main` unless the user asks.
- **Git.** Before a nontrivial edit, check only `git branch --show-current`. Never edit from `main`. Read `.agents/pstack/rules/git.md` in full before editing a branch, adding or removing a worktree, or resetting a proof case; it holds the worktree, `origin/HEAD`, setup and unrelated-diff rules.
- **Proof.** The `verify` skill is pstack's driver skill here. Bug fixes reproduce and verify through it.
- **Calls.** Every lead turn re-reads the full context, so call count and raw payload bloat set the cost. Batch independent reads, searches, and edits in parallel in one message, and route multi-file `read_file` exploration and raw test/CI logs through short-lived subagents (`medium` when pure extraction) so only tight spans and summaries enter the main thread. A session started by another reads `.agents/pstack/rules/linked.md` in full first; a lead reads it before starting a waited-on session. Never spend a turn on bookkeeping alone: send retitles, todo updates, and batched decision-log appends with the next working call, or end-of-turn renames (🟠/⏳) per `title.md` (owner's word, 2026-10-17).
- **Extraction.** The lead's own model keeps every judgment: plans, design calls, code, synthesis, `how` explainers, judges (except an arena's cross-judge pool), second readers and reflect decisions. Route multi-file `read_file` exploration, raw test/CI logs, and pure evidence lookups to short-lived evidence subagents (`medium` effort when pure extraction; `invoke_subagent`/`delegate_task` in T3 Code, `Agent` on `opus` in Claude Code); signed-in site drives use OpenCode `browse` (`~/.local/bin/browse`), T3 `preview_*` or Claude in Chrome. Verify every requested source was covered (rerun once on gaps, report any remaining gap), confirm call sites with `git grep`, and read modified functions and breakable callers in full.
- **Panel review.** A pstack panel, `/pstack:interrogate` with the configured seats, runs without asking for the work this project's reviews list names and wherever a pstack playbook step or skill calls for it, such as a contested design. An arena runs the same way. `architect` is pstack's own sketch, and a large or contested design runs an arena. A change to agent prose alone gets none of them, except as `.agents/pstack/rules/panel.md` says. On the user's word, "panel" runs a panel on the current plan or diff, "arena" runs an arena bakeoff of the current artifact, and "full" runs `architect`, then a panel on the plan and another on the diff. Before you launch any panel or arena seat, or log a panel row, read `.agents/pstack/rules/panel.md` in full; it holds the Panel review and Review rules. The reviews list, each row named by its id:
  - `api-plan`: A plan that changes a public API runs `architect` to pick the target, then a panel on the finished plan.
  - `external-pr`: Someone else's PR, asked for as "review PR <number>", gets a review-only panel on its diff, briefed with its body, linked issue and plan.
- **Messages and shared resources.** A "can we X?" question gets a measured answer and a proposal, not the action. Before you send or draft a message another person can read, such as an email, a chat message, or a comment, review, label or close on an issue or PR, before you spend shared quota, and before you run an access grant, read `.agents/pstack/rules/messages.md` in full.
- **Tests.** Before you write, change or cut a test, read `.agents/pstack/rules/tests.md` in full.
- **Browser drives.** Before you type into a page through a browser tool, or judge anything on it that scrolls, animates or loads lazily, read `.agents/pstack/rules/browser.md` in full; it holds how each runtime's browser delivers keys, draws frames and handles the clipboard.
- **Plans and trails.** Before you draft or write a plan, in plan mode or a plan file, or write a decision-log row or a proof log, read `.agents/pstack/rules/trails.md` in full.
- **Plans and hand-backs.** Before you draft or change a plan, in plan mode or a plan file, and before the reply that hands back playbook work, planned or not, read `.agents/pstack/rules/pages.md` in full; it holds plan/topic shape, PR rendering, Defaults vs Open questions, and what the hand-back reply holds.
- **Autopilot.** Work runs to its close without waiting for the owner, stopping only for production deploys/releases, pushing `main`, force-pushing a shared branch, deleting non-run data, a missing product sign-in, a blocked models-sheet model, or a third plan on one topic. Before taking a reversible default, pivoting a design, or stopping on an open question, read `.agents/pstack/rules/autopilot.md` in full.
- **Fast.** The owner's word "fast" runs the request on the main lane, with no subagent or seat. Before you run one that way, read `.agents/pstack/rules/fast.md` in full.
- **Long runs.** Before a multi-slice build after "go", `/loop`, `/goal`, a pause or a resume, and after every compaction, read `.agents/pstack/rules/long-runs.md` in full.
- **Time budget.** No command or proof that a run starts takes more than an hour, except a stress run, and nothing waits for the host's load to drop (owner's word). Read `.agents/pstack/rules/time.md` in full before you start one that may run long, such as a proof or a benchmark protocol, after a gate fails under load, and before you offer a measurement that cannot fit the hour.
- **Todo list and close.** Add one quoted todo per explicit user ask (including mid-run messages) and per triggered gate (proof, writing passes, review, final check, delivery); keep `<slug>.todo.md` in the run directory. Keep standing user preferences (e.g. reply language) open as constraint todos until close. Before every final reply, reread all user messages and corrections, add any missed ask, and finish or skip it with a reason.
- **Session title.** When the runtime has a tool that renames the current session, read `.agents/pstack/rules/title.md` before the run's first step and after a compaction or a resume, and retitle the session whenever that file says to.
- **Writing.** Read `.agents/pstack/rules/writing.md` in full before a session's first reply and after a compaction. Everything you write follows it.
- **Writing passes.** Run `deslop` then `no-comments` once per batch of product code before review or hand-back, and `unslop` once over docs, plans, agent files, commit bodies and PR text; `technical-writing` is a reference only, and replies need no separate pass. Read `.agents/pstack/rules/writing.md` for full pass rules and panel-round `writing` rows.
- **Auto-merge.** Each PR an agent opens anywhere gets `gh pr merge <url> --auto` with a method its base allows; report a refusal (owner's word, 2026-11-12).
- **Principles in replies.** pstack's principle skills still apply. Read the leaf skill for any principle a decision rests on, as poteto-mode's Principles list says. Only the rule to name each principle in the reply is dropped; name one only when it explains a choice the reader would otherwise question.
- **Blocked.** For an unclear tool or access failure, allow two informed attempts or ten minutes, whichever comes first. Then finish a bounded repair, ask once for the exact human action under the page's Needs you, or move to other ready work.
- **Improve the workflow mid-task.** When a skill, rule, script or helper gets in the way, fix it then, separately from the task's change, and keep working. When the user corrects the same mistake a second time, in code or in a shell or tool command a rule already forbade, run `/pstack:correct` on that class, which fixes it with architecture, types or a check before any rule text. Run `/pstack:reflect` only when the owner asks for it, as pstack does (owner's word, 2026-11-20). Before `/pstack:reflect`, `/pstack:correct`, a new or changed check, or an edit to an agent file such as a skill, a rule or `AGENTS.md`, read `.agents/pstack/rules/reflect.md` in full; it holds the rest of this rule and the Corrections and Agent files rules.

## Plate rules

Full Plate rules: [plate-workflow.md](docs/development/plate-workflow.md) (read the matching section before acting).

- **Plate overrides.** Operator (pinned watcher, `medium` for routine Local CI fixers, `high` for complex bugs, Neon `@xhigh` on 2nd-attempt escalation), Radar painter (`codex exec` @low), Potion (`../potion` lands on `next` without `land.mjs`), Second plan stops (probe first; offer full/narrowed; never self-answer): [plate-workflow.md#role-and-project-overrides](docs/development/plate-workflow.md#role-and-project-overrides).
- **Source authority.** Read the user-named source first; challenge GitHub/Linear items. Search with `rg --hidden` / `rg --files --hidden`. Never browse GitHub files; inspect or clone deps at `../{repo-name}` beside the main checkout. Doctrine: `VISION.md` -> scoped `docs/vision/{common,plite,plate}.md`; single-scope law: `docs/plans/topics/<scope>.md`; editor behavior law: `docs/editor-behavior/markdown-editing-spec.md`.
- **Routing.** `pstack:poteto-mode` picks playbooks (`.agents/playbooks/`); Plate skills own domain method ([agent-skills.md](docs/development/agent-skills.md)). Human assignments stay reserved; audits stay read-only unless authorized. Read `.agents/playbooks/references/workflow-change.md` before changing agent files/tooling. Owner phrases, hard cuts, `best-api repair`, Yjs hold: [plate-workflow.md#routing-and-owner-phrases](docs/development/plate-workflow.md#routing-and-owner-phrases).
- **Git & publication.** Betas from `next` publish without asking; `main` takes only security fixes, dep bumps and contributor PRs. Never auto-approve payments/credentials. Never use closing keywords before `#<N>` into `next` (write `plate#<N>`). Explicit "merge" merges immediately. See [plate-workflow.md#git-and-publication](docs/development/plate-workflow.md#git-and-publication).
- **Team.** `team` in `.agents/pstack.json` holds roles/Discord IDs; `notify.mjs` posts to `#plate-next`. `Team:`/`Team-Action:` lines, plan `Demo:` lines, and zbot `shots.md`: [plate-workflow.md#team](docs/development/plate-workflow.md#team).
- **Proof & tooling.** `origin/HEAD` pins to `next`. `land.mjs` runs `--check 'pnpm check --affected'` + `review-ledger.mjs land`; slow/formal checks run in Local CI (`operator`). Load `verify` before checking/skipping/deferring gates; run active light formal checks for touched Coverage records pre-panel/land (`authored-invariants`/`yjs-peer-order` are `--audit` opt-in). Work counts gate perf (`time.md`); manual-only checks file a `plate-private` issue post-land: [plate-workflow.md#worktrees-proof-and-tooling](docs/development/plate-workflow.md#worktrees-proof-and-tooling).
- **Friction reporting.** On real, reproducible tooling, skill, `pstack`, or T3 friction (broken CLI/script/hook, stale doc, rule conflict, missing Antigravity/T3 support), send a 3-line `t3_thread_send` to pinned `operator`: `FRICTION [tooling|skill|pstack|t3]`, exact file/command/error, and `blocking: no|yes` (with your `threadId`). On `blocking: no`, keep working. On `blocking: yes` (core tool/gate blocked with no clean workaround; never hack past a broken CLI like raw GraphQL past `triage.mjs`), stop and wait for `operator` to fix and wake you. Never send speculative audits or style nitpicks.
