## pstack overrides

- **Delivery.** The user owns commits on `next`. A completed task runs its writing passes, then `pnpm lint:fix` as its last check that edits code, and leaves its changes on `next` in the working tree; commit or push `next` only when the user's own message asks for it. Approving an agent's plan is not commit authority, and no plan or step list proposes a commit on `next`. On every other branch the lead commits and pushes its work without asking, another person's PR head branch included. It keeps the description of a PR it opened true to the pushed diff. On another person's PR it leaves their description alone and keeps its latest comment about its own commits true instead, as the `plan-page` skill's PR section says. A runtime whose own instructions refuse to post that comment leaves it as a draft under the page's Needs you. When maintainer edits on a PR's head branch are not allowed, it opens a PR stacked on that branch instead; any other PR waits for the user's word. Merging, closing, other comments, reviews and CI approval need the user's word. When `git status` shows work the task did not write, run `pnpm lint:fix` on the task's code paths only, because a repository-wide run reformats other sessions' files; a change with no lintable file skips it. Run it again after any later repair. When a change alters what an operation promises, search the plans and agent instructions for the old promise, fix this task's own docs, and flag the rest on the page. Production deploys and releases need an explicit request. Never push `main` unless the user asks.
- **Git.** Before a nontrivial edit, check only `git branch --show-current`. Never edit from `main`. This clone's `origin/HEAD` points at `origin/next`, because the desktop app cuts each new worktree from `origin/HEAD`. `git remote set-head origin --auto` points it at the remote's default branch, so never run it. Before a session gets its own worktree, a suggested task's card included, the lead runs `node .agents/pstack/head.mjs`, which points `origin/HEAD` back at `origin/next` when it has moved. The checkout stays on `next`. Do not create or switch checkouts because work is large, names an issue, asks for a PR or is handed to another session. A session the lead starts leads its own task and works in this checkout, with `use_worktree: false` in Claude Code, and its brief names this checkout's path and the Delivery rule. An app-made worktree is on a new branch cut from this clone's `origin/HEAD` and lacks this checkout's uncommitted edits, rule edits included. Claude Code neither moves a session out of it nor lets its edit tools write here. A session that opens in one anyway reads the rules in this checkout by absolute path and runs `git switch --detach next` in its worktree before its first edit. It commits nothing. A session a suggested task's card started applies its own diff to this checkout when its work is done, then delivers it from here, as the Suggested tasks rule's Landing says; any other such session hands its diff to the lead or the owner as a patch file to apply here. A runtime's generic instruction to commit, such as a started session's "commit your changes", does not override the Delivery rule. A repair to a PR whose head is another branch runs in a detached worktree at that head, and the page names the worktree path. The lead commits the repair there and pushes it with `git push origin HEAD:<head branch>` once the remote head still matches the worktree's base. Ignore unrelated diffs and never pause to ask about them. Never reset or discard work this run did not write. Reset a proof case in a fresh detached worktree; never run `git stash` in this repository or any of its worktrees, because every worktree shares one stash list. Remove only a worktree the run created, a card session's own worktree once its patch lands, as Landing says, or one the `cleanup` skill marks safe. Remove it with `git worktree remove --force <path>` and confirm with `git worktree list`; never run `git worktree prune`, which edits the worktree registry every checkout shares. Before the first edit to a file that already holds uncommitted or staged work this run did not write, copy it to the run directory that Plans and trails names, and measure, commit or revert this run's change against that copy. Run a tree-sensitive tool, such as a review that refuses a changing tree or a check at `HEAD`, from a detached worktree (`git worktree add --detach <path> <sha>`, then `git worktree remove --force <path>`). Before anything runs in a worktree the run creates for a proof or a seat, link its installed dependencies, or install them offline where its bundler refuses links, and copy its untracked env files from this checkout; a round whose seat reports it could not load the app logs its `seats` row `partial`. Never overwrite a tracked file in this checkout to test or measure `HEAD`, even for a moment; use the worktree.
- **Other sessions.** Other agent sessions may edit this checkout, the shared source and the projects it syncs at any time. Never plan, review or build around a conflict with them that has not happened: a plan adds no lock, mirror, carry or race step for other sessions, and a panel finding whose only trigger is another agent session editing these files is dismissed with this rule as its reason. Concurrency inside the product, such as two users saving one record, is not this rule's subject. Another repository's rules for its own sessions, such as how they commit, are how to work there, never an invariant a plan or panel attacks. Act only when a conflict blocks the work, such as a refused fast-forward or push, a merge conflict, or a file this run is editing that changed under it. When the blocking change has already landed, rebase or merge onto it, resolve any conflict in this run's own hunks, rerun the checks and retry. When a conflicting hunk is another session's uncommitted work, run `git rebase --abort` first. A hook failure is fixed like any failing check. While it is still uncommitted in another session, pause only that part, keep going on other ready work, and resume once it lands. A block that still holds after an hour goes under Needs you, and the run keeps going.
- **The lead writes the code.** The lead agent edits the current checkout and verifies on the running artifact. Subagents do research, review and read-only fan-out; a Codex worker the Codex workers rule starts also writes. That covers comment-sicko in `no-comments`: its brief forbids every edit and asks for each verdict with its exact replacement text, and the lead applies the ones it accepts. No per-delegate worktrees unless the user asks. This replaces every pstack playbook step that delegates implementation or attempts to a subagent or gives a delegate its own worktree, as in Feature, Bug fix, Refactoring, Perf issue and Hillclimb. The `verify` skill is pstack's driver skill here. Bug fixes reproduce and verify through it, and its proof replaces the swarm lanes of pstack's Multi-phase plan.
- **Extraction.** The session's own model keeps every judgment: plans, designs, the code the lead writes, synthesis, explainers, judges, cross-judges, a second reader that checks extracted claims, and reflect's synthesis with every decision on what it applies. In Claude Code, a role that only finds evidence for the lead to judge runs on Codex when the models sheet gives it a `codex:<model> @<effort>` value; today that is the `how explorer` role, which gets pstack's explorer prompt. It runs through `cross.mjs --reach`, which loads the user's Codex config, connectors, web search and network but writes only a scratch folder, never the project. Before using an answer, the lead checks that it covers every source and lookup its brief asked for. A seat that fails, returns nothing, or leaves an asked-for source or lookup uncovered, reported or not, reruns once as pstack's `Agent` call on `opus` for the part still missing, and the page names any gap left. In Claude Code, when the lead would otherwise read several files it has not read to find where a change goes, it asks such a seat for the spans and call sites instead, confirms the call sites with its own `git grep` of each changed symbol, then reads in full the function it changes and each caller whose behavior the change can break. A read-only fan-out reader the lead starts itself whose sources are all files on disk, such as a map, inventory or sweep lane, runs the same way on the `how explorer` line's model with `cross.mjs` and the lead's brief, which excludes build output.
- **Codex workers.** In Claude Code, on the owner's word, such as "have Codex do it", the lead hands a task or a slice of one to Codex itself instead of asking the owner to prompt Codex. In a long run it also hands Codex, without that word, a mechanical slice that a command proves done: a rename or codemod across packages, a benchmark protocol run, or a fix loop that ends when typecheck or lint passes. A protocol run's `--timeout` fits the Time budget rule, so one that cannot fit goes to a suggested task instead. After a worker times out, the lead diffs what it wrote before going on. Such a worker never writes or changes a test, a doc or a changeset; the lead writes those (owner's word, 2026-10-15). A Claude session that has located a fix's cause or settled a design, and planned the change, also hands Codex the coding without that word when the change is more than a few lines or needs its own test loop. It writes the change itself when the brief would be longer than the diff. That worker writes the change's regression tests too, while docs and changesets stay the session's (owner's word, 2026-10-16). UI design, layout, styling and every judgment made from a screenshot, such as a pixel match, stay in the Claude session (owner's word, 2026-10-16). So a change judged by how it looks never goes to Codex, though the logic inside a UI component may. The session fills `.agents/pstack/codex-build.md` with the task, the cause or design, the planned change, the files and the checks. It saves the brief in its own working tree under `codex/<task id>/` in the plans artifacts folder, which git ignores, and runs `cross.mjs` from that tree with `--effort xhigh --timeout 21600`, writing the output to `codex.log` beside the brief. A coding run may take up to six hours, because stopping a long fix wastes its work, and `cross.mjs` accepts that under `--bypass`. The session waits for the run to exit. Then it reads the whole diff and each caller of every changed symbol, checks that each new test fails without the change and passes with it, and reviews every test against the Tests rule, rewriting or cutting each one that falls short. The session sends a diff that fails review back to Codex once with its findings, then finishes it itself. The writing passes, the proof and the landing run as usual. `/chips codex`, or `"chips": { "codex": "always" }` in `.agents/pstack.json`, forces the handoff on a card whatever the size of its change, a design question's or an `(xhigh)` fix's included, once its session has found the cause or settled the design. On a forced card the session reads the diff and runs the checks, and rewrites only a test that does not fail before the change or asserts nothing. A card session ends its report with the workflow friction it hit, and the chips lead fixes each item as the Improve the workflow mid-task rule says. It writes the brief to a file in the run directory and runs `node .agents/pstack/cross.mjs --to codex --bypass --timeout <seconds> --prompt-file <file>` from the project root in the background. `--bypass` starts a new `codex exec` run with the owner's Codex config, hooks, connectors and web search, and with no sandbox or approvals. The worker searches, runs commands and writes files as the owner's Codex CLI does. The project's rules and skills limit what it writes, as they limit the lead. The owner's word also gives the worker any judgment the task needs, such as a research verdict, as an exception to the Extraction rule. The lead reviews what the worker wrote as it reviews a subagent's work before it hands back. The brief says the lead delivers, so the worker commits and pushes nothing, whatever the project's delivery rule says.
- **Panel review.** A pstack panel, `/pstack:interrogate` with the configured seats, runs without asking for the work this project's reviews list names and wherever a pstack playbook step or skill calls for it, such as a contested design. `architect` and arena run the same way, such as for Feature's design exploration or a fix that crosses a function boundary. On the user's word, "panel" runs a panel on the current plan or diff, "arena" runs an arena bakeoff of the current artifact, and "full" runs `architect`, then a panel on the plan and another on the diff. Before you launch any panel, `architect` or arena seat, or log a panel row, read `.agents/pstack/rules/panel.md` in full; it holds the Panel review and Review rules. A row of the reviews list triggers only the tool and stage it names, so a row that names a panel on the diff does not by itself run `architect` or a panel on the plan; a pstack step's own trigger still runs them. The reviews list, each row named by its id:
  - `api-plan`: A plan that changes a public API runs `architect` to pick the target, then a panel on the finished plan.
  - `api-build`: A build of an `api-plan` plan gets a panel on its diff.
  - `pr`: Before a PR is opened, its diff gets a panel.
  - `external-pr`: Someone else's PR, asked for as "review PR <number>", gets a review-only panel on its diff, briefed with its body, linked issue and plan.
- **Messages and shared resources.** Who can read a message decides its stop, not its channel. A message that anyone outside the team can read, such as a send to customers, an email to a client, or a comment, review, label or close on a public repository's issue or PR, needs explicit authorization from the active request. A PR, its title and its body opened under the Delivery rule are not such a message. A message only team members can read, and shared quota, proceed without asking, as pstack's Autonomy says; a private repository or tracker grants nothing by itself. A message that waits for authorization, or that the runtime's own instructions refuse, goes as a draft under the page's Needs you, or in the reply when there is no page. The owner sends it, and the run keeps going. A "can we X?" question gets a measured answer and a proposal, not the action. An access grant is approved per target and runs as its own command; never widen an approved grant to a new target. The comment the Delivery rule keeps on another person's PR is not such a message either, because like a PR body it reports the lead's own delivery.
- **Tests.** Before you write, change or cut a test, read `.agents/pstack/rules/tests.md` in full.
- **Browser drives.** Before you type into a page through a browser tool, or judge anything on it that scrolls, animates or loads lazily, read `.agents/pstack/rules/browser.md` in full; it holds how each runtime's browser delivers keys, draws frames and handles the clipboard.
- **Plans and trails.** Before you draft or write a plan, in plan mode or a plan file, or write a decision-log row or a proof log, read `.agents/pstack/rules/trails.md` in full.
- **Plan pages.** Before you draft or change a plan, in plan mode or a plan file, and at every stop that hands work back, read `.agents/pstack/rules/pages.md` in full; it holds what the page and the hand-back reply contain.
- **Autopilot.** Work runs to its close without waiting for the owner. Each call the owner could make gets an attention level, as the `plan-page` skill's memo rules define it: `safe` when the pick is easy to undo and the lead is sure, `look` when it is costly or hard to undo or the lead is unsure, and `answer` when it cannot be taken back or has no clear pick. The lead takes the pick of every call, records it as a Defaults row with the word that reverses it, and keeps going; a call with no clear pick takes its most reversible option. Only these stop the run under Open questions, whatever their level: a production deploy or release, a push to `main`, a force-push to a shared branch and deleting data the run did not create. What the `cleanup` skill's scan marks safe is not data, and the skill deletes it without asking. That is an idle Next.js cache folder no running server holds, other than an app's own `.next` build. It is also a worktree an agent made that no running session or process, and no recent session transcript, uses. The skill first saves its uncommitted changes as a patch. A message anyone outside the team can read waits as a draft, as the Messages rule says, while the run keeps going. A pending external gate, such as a staging release, a quota reset or a running seat, is not a stop either, and neither is a status question from the owner, which never counts as go. Unless the run is paused, held or at a stop it has reached, whoever or whatever set it, the lead keeps working on ready work and schedules a wakeup for a gate with a known time, chaining wakeups past the scheduler's limit. A prototype, an arena or `architect` picks its winner and keeps going, and the page names the other options. A finding that the accepted design cannot meet a requirement pivots the run when it is found. Such findings include a conclusive miss of a frozen budget and a cost that only a new owner or a new stored shape removes. The lead runs `architect` on the finding, writes the plan that adopts the winner and builds that next. Under "fast", the lead's own design pass replaces `architect`. Until it lands, steps that only finish, document or prove the design it replaces wait, and independent work goes on. Such a finding never waits in Open work, in a suggested task or in a deferred row, unless the owner kept that row until a date in their own words. A suggested task holds only side work outside the run's target or a measurement the Time budget rule sends there, and its ledger row names what it waits for, such as this run, so `chips` shows when the owner can start it. A request that asks only for a plan or a prototype ends there and builds nothing, a pivot plan included, and the page shows its picks. The owner adds a stop for one request with "stop at plan", which waits once the plan is written, "stop at design", which waits for the owner's pick among the design options, or "stop before ship", which waits before delivery. "panel" and "hold" work at any point. A project's standing stop goes in its own rules outside this block.

- **Fast.** The owner's word "fast" runs the rest of that request on the main lane, in the lead's own thread, for work the owner is confident in and wants to iterate on. It drops only what spawns a subagent or a seat; every other rule still applies, plans, plan pages, decision logs, proofs, tests and delivery included. "fast" lasts until the request ends or the owner says "full". - **Long runs.** Before a multi-slice build after "go", `/loop`, `/goal`, a pause or a resume, and after every compaction, read `.agents/pstack/rules/long-runs.md` in full.
- **Time budget.** No command, proof or seat that a run starts takes more than an hour, so development stays fast (owner's word, 2026-10-16); only a stress run, below, takes longer. No wait on the machine's state, such as a quiet host, lasts longer either. When such a wait reaches its hour, the lead logs the line it guards `inconclusive` with `proof:` its last log, names its next probe and goes on. The budget keeps a lead from holding long work while other chips wait to land, so long work runs in a dedicated chip. A background wake signal, such as `chips wait`, holds no work, so it has no time limit. Before a proof that may run long, the lead times one sample and narrows the proof to fit. It never runs one protocol as pieces that together pass the hour. A measurement that a decision waits on, such as a probe before a design is accepted, narrows to fit as well, and an inconclusive narrowed result leaves that decision open with its next probe named. Any other measurement that cannot fit, such as a soak, a large-cohort sweep, a multi-round interleaved timing protocol or a final rerun of built code, never blocks the run or its close. When it is still worth running, the lead offers it as a suggested task through the `chips` skill's Offer mode. The offer names the command, the source identity it must measure, its budget, what a miss triggers and the plan step it settles, and says that its measurement lands no patch. When the change is not yet on the branch a card's worktree starts from, the task waits `pr:<number>` on the PR that carries it. When no PR carries it, the offer names the absolute path of a patch of it saved in the run directory. The task goes to `## Open work` with `owner:` the owner and `stop:` that task landing or being dropped. This hand-off is the owner's word that the narrower exit condition counts as done. The lead takes the close rule's accepted route: a `look` Defaults row whose word runs the measurement in the run, a labeled `partial` row and then an `accepted` row on the last log the run wrote for that measurement, such as its timed sample, and the step's box closed citing the task. The Close claims only what the run measured. The lead can then mark the plan done, which frees the task's `run:` wait. The task's session confirms that its tree holds that source identity before it runs, because a card's worktree lacks uncommitted work. It applies the named patch when its tree lacks the change, and stops and tells the owner when the patch does not apply. It writes its proof logs with `proof.mjs --dir` set to the checkout's run directory, appends its verdict to that plan's decision log from the checkout with `decisions-check.mjs append`, and delivers that row by the project's Delivery rule. Its measurement lands no patch, so its `landed` row names no `patch:`. A conclusive miss it finds is a pivot finding, which that session logs in the plan's decision log and leads as the Autopilot rule says. Only that session, or the run once the owner says the Defaults row's word, passes `--stress`. Without `--stress`, `proof.mjs` stops a command after 3,600 seconds or its shorter `--timeout`, kills every process still in the command's process group and logs the run as timed out. `proof.mjs` and `cross.mjs` refuse a longer `--timeout` without `--stress`, except a `cross.mjs --bypass` coding run, which the Codex workers rule gives six hours, and `mutate.mjs` refuses a spec timeout over 3,600 seconds and stops its whole run at an hour.

## Worktrees

- **Pin `origin/HEAD` to `next`.** The desktop app cuts a new worktree from `origin/HEAD`, and GitHub's default branch stays `main` for v1 (`docs/plans/artifacts/2026-10-15-worktree-head/worktree-base-probes.md`). The pstack block's Git rule says how to keep `origin/HEAD` on `next`, and the Claude Code SessionStart hook runs `.agents/pstack/head.mjs` to do it.
- **Troubleshooting.** A skill or session that works in its own worktree, such as a card session, a panel seat, a proof worktree or a PR repair, checks these first:
  - When it starts on `main` or lacks recent `next` commits, the pin is missing. Set the pin for later worktrees, and in this one run `git switch --detach next` before the first edit. A plain `git switch next` fails, because the main checkout has `next` checked out.
  - When it lacks work that landed in the main checkout, nothing is wrong. A worktree starts from `next`'s last commit, and a landed card patch stays uncommitted until the owner commits it, so a task that builds on one waits for that commit, as `chips` shows.
  - When its rules or skills look older than the main checkout's, read `AGENTS.md`, `.agents/` and `.claude/skills/` in the main checkout by absolute path, because uncommitted rule edits exist only there.
  - When it cannot build or test, link the main checkout's installed dependencies, or install them offline, and copy its untracked env files, as the Git rule says.
  - When its patch fails `git apply --check` on the main checkout, another landed patch changed the same lines. Copy the main checkout's copy of each refused file into the worktree, redo the change there and save the patch again, as the chips rule's Landing says.
  - Clean-up removes only a worktree the run created, a card session's own worktree once its patch lands, or one the `cleanup` skill marks safe, with `git worktree remove --force <path>`, and never runs `git worktree prune` or `git stash`, as the Git rule says.
