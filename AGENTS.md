## pstack overrides

- **Delivery.** Each task works in its own worktree cut from `origin/next` and lands only through `node .agents/pstack/land.mjs`. Before the first edit, or the first write to the forge such as opening a PR, posting a comment, approving a CI run or pushing, read `.agents/pstack/rules/land.md` in full. When a change alters what an operation promises, search the plans and agent instructions for the old promise, fix this task's own docs, and flag the rest on the page. Production deploys and releases need an explicit request. Never push `main` unless the user asks.
- **Git.** Before a nontrivial edit, check only `git branch --show-current`. Never edit from `main`. This clone's `origin/HEAD` points at `origin/next`, because the desktop app cuts new worktrees from it. `git remote set-head origin --auto` follows the remote's default, which need not be `next`, so never run it. Before a session gets its own worktree, a suggested task's card included, the lead runs `node .agents/pstack/head.mjs`, which points `origin/HEAD` back at `origin/next` when it has moved. Ignore unrelated diffs and never pause to ask about them. Never reset or discard work this run did not write. Reset a proof case in a fresh detached worktree; never run `git stash` in this repository or any of its worktrees, because every worktree shares one stash list. Remove only a worktree the run created other than its own, or one the `cleanup` skill marks safe; a session leaves its own for the cleanup scan, which removes it after a quiet day. Remove it with `git worktree remove --force <path>` and confirm with `git worktree list`; never run `git worktree prune`, which edits the worktree registry every checkout shares. Before anything runs in a worktree of this repository the run adds for a proof or a seat, run `node .agents/pstack/setup.mjs` from inside it, with each `--install` and `--env` value the project's `SessionStart` hook passes that script, quoted as the hook quotes it, and without `--hook` or the hook's `cd`. It copies the main checkout's env files and installs dependencies. When it exits 1, fix the install before anything else runs there. A project helper that makes and sets up its own worktree replaces this step.
- **Proof.** The `verify` skill is pstack's driver skill here. Bug fixes reproduce and verify through it.
- **Calls.** Each call the lead makes re-reads the session's whole context, so in a long session the number of calls, not their size, sets the cost. Read several files or line ranges in one command, or as parallel calls in one message, instead of one small read per call. A session that another session started reads `.agents/pstack/rules/linked.md` in full before its first step, and a lead reads it before it starts a session its run waits on. Bookkeeping never takes a call of its own: a retitle, a todo update, a decision-log append, a page publish or a plan-page render goes out in the same message as the next working call, a rename that ends the turn, such as to 🟠 or 👀, as the Session title rule says, and several decision rows go in one append (owner's word, 2026-10-17).

## Routing

pstack's poteto-mode picks the playbook, and the Plate owner below supplies the domain method and proof inside it.

- Exact human assignments remain reserved. Read-only mapping and review are allowed; broader cleanup or full execution cannot absorb someone else’s work.
- An audit remains read-only unless its request authorizes repairs.
- **Owner phrases.** "Only uncommitted" means summarize only uncommitted work, never older branch history. "Long term most precise and performant" means choose the architecture or API owner, not another local example condition. "Make it perfect" means stabilize behavior first, then improve performance, then clean the API and DX, then prove readiness. "Go faster" or "it's getting long" means less narration and independent waits run in the background; it never drops a slice, a slice review, a skill load, a whole read of a rule or a gate. "Formal intake" runs `verdict` on where a new formal check is worth building. It starts from the newest `docs/plans/*-formal-*-intake.md`, reads only the fixes, tests, plans and open tasks since the date in that plan's name, and names its own plan the same way, so the next run finds it. When a session that landed work stops and 50 fixes have landed on `next` since that date, or since the last formal intake task closed, the Stop hook `tooling/scripts/formal-intake-due.mjs` offers a formal intake task at P3, because it is workflow tooling no ship item waits on, with no owner, which `/chips all` cards, and has the session say so. Add a phrase here only when the owner's wording, not the rule behind it, changes what to do.
- **Hard cuts.** A hard cut runs when the owner asked to remove that feature, when its plan continues a Pursue verdict on a review the owner asked for, or when `VISION.md` or a `docs/vision/` file already rules the removal or gives the removed job to another owner. Any other hard cut becomes a verdict item, not an owner question. The run judges the cut on its merits, because nobody asking only stops the run from making it. It keeps the behavior, offers the cut's question as a `decide` chip when the cut lies in the run's domain, and otherwise lists it in the plan's Open work with the subject that owns it. The Hard cut section of `.agents/playbooks/references/architecture.md` holds the rule.
- **Public API.** Any change to a reusable public API runs `best-api repair` before closeout. It edits the rule's one owner, the scope's subject file or, for a rule that binds several scopes, its Vision file, fixes every artifact that still teaches the rejected shape, and regenerates and proves mirrors. A read-only task reports the required repair without implementing it.
- **Workflow changes.** Before you change agent instructions, commands or tooling, read `.agents/playbooks/references/workflow-change.md`.

## Git and publication

- Never auto-approve a payment or a credential use, such as a password, token, API key or OAuth grant prompt. It stops for the owner like the Autopilot rule's always-stop list, and neither a Defaults pick nor "go" approves it.
- An authorized PR includes the entire current checkout, including modified and untracked files, unless the user narrows it. Write multiline `gh` bodies with `--body-file`, stdin or a heredoc, never a literal `\n`; keep the `auto-release` block that Changeset owns, and read the final body back with `gh pr view --json body`. Public issue and PR claims follow Maintainer's truth gates.
- A commit message, and a PR title or body an agent writes into `next`, never closes an issue. Name an issue as `plate#<N>`. Never put a closing keyword, any form of close, fix or resolve, right before `#<N>`, `udecode/plate#<N>` or the issue's URL, even with a colon between them. So a message writes the command `triage fix #<N>` as `triage fix plate#<N>`, and land.mjs refuses a message that does not. `next` is GitHub's default branch, so a closing keyword closes the issue when the commit lands or the PR merges, as `f512cc3bed`'s body closed plate#5228 before its reporter could retest. The Triage playbook's GitHub state says when an issue closes.
- When the user explicitly says to merge a PR, merge it: do not wait for CI, do not ask again, and use an admin merge when needed. This replaces pstack's Shipping verification for that merge.

## Team

- `team` in `.agents/pstack.json` maps each teammate's GitHub login to a role and a Discord user ID. Tools read a teammate's role there instead of keeping lists of names, so adding a teammate takes one entry. A `maintainer` lands code and makes triage calls, and their triage records read current. A `qa` teammate tests and records each retest through the Triage playbook's retest command, which closes the issue once the retest passes, but lands no code, so on GitHub they hold the Triage role, which closes and labels issues but cannot push. Their triage records read `unconfirmed` until a maintainer records the issue again (owner's word, 2026-11-02).
- Plate-bot posts to the team's #plate-next Discord channel, which only the `dev` role can read. `tooling/scripts/notify.mjs` mentions only the `dev` role or a login on `team`, so its messages proceed without asking, as the Messages rule says for a message only team members can read.
- A land message gets a `Team:` line only for what a teammate would want to know. Teammates work through Claude and run no script by hand. So the line says in plain words what changed for them: a result they see in the product, a demo or a beta, a fix a reporter can retest, something new they can ask Claude for, a contribution policy, or a step only a person can take, like signing in. It holds no shell command, script, flag or file path. When teammates must act, it names the skill command that does it, such as `/triage retest plate-private#<N>`, or what to ask Claude for when no skill does it. Use `Team-Action:` instead when every teammate must act, which pings @dev. A change only agents act on, such as a skill's or script's internal steps, a new check, a refactor or a test, gets neither line. A Team line may wrap, and it ends at a blank line or a trailer such as `Beyond the ask:`. `node tooling/scripts/notify.mjs check`, one of the config's `landChecks`, refuses a Team line that holds a shell command in backticks. zbot, the plate-bot router on the owner's Mac, posts each line once the commit reaches `next`, with screenshots or a clip of the change when the commit changes a page. While that Mac is off no line posts, and zbot posts the ones it missed when it comes back. Before land.mjs pushes a commit whose Team line names a change a teammate sees on a page, the session leaves its demo for zbot. It picks the form as `/notify`'s Show it step says and makes each clip with the `clip` skill, so a change to something a teammate already saw gets one before-and-after clip instead of two images. Without that skill, such as on a machine that lacks Bun or ffmpeg, it takes stills from its proof. It copies one to four of those files into `~/.local/share/plate-bot/shots/landed/<session>/`. It writes `shots.md` there with one `[[shot: <absolute path> | <a few words>]]` line per file. `<session>` is what land.mjs writes as the commit's `Session:` line, `$CLAUDE_CODE_HOST_SESSION_ID`, or `$CLAUDE_CODE_SESSION_ID` when that is unset. zbot then posts the Team line with those files instead of recording a demo itself.
- A plan with steps picks its demo when it is written. Under its `Status:` line it writes `Demo: step <id>, <what the clip shows>`, naming the step whose landing first gives a teammate something to try on a page. The run records one clip for each such outcome, not one per step. A plan with nothing worth a clip writes `Demo: none, <why>`. A step whose scope changes moves the line. The named step records its demo before land.mjs runs, after its hand drive, writing passes and review fixes, on the server its hand drive started. Its land message carries the Team line. The plan's `## Demo` reuses the same frames. A helper on the models sheet's `clip` line records the clip with the `clip` skill. The lead reads its stills before the landing and asks for at most one retake, naming what to fix (owner's word, 2026-11-20). `notify.mjs check` refuses a landing that adds a plan with steps and no Demo line, drops a plan's Demo line, or names a step the plan lacks. It also refuses a landing that ticks the Demo step without a `shots.md` naming one to four existing files in its session folder or, once land.mjs has made the commit, without a Team line.
- When the owner passes on a teammate's questions, such as a pasted Discord message, the session answers that teammate. When it finds a teammate's setup or workflow off, such as a missing private half, a PR opened by hand, an issue filed outside the draft flow or a land refused for a missing source, it tells that teammate what is off and the skill command, or the request to Claude, that fixes it. Either way the session sends the message itself through the `notify` skill, which holds the house style and the send command, and tells the owner what it sent, instead of drafting a reply for the owner to paste. ## Proof and tooling

- Every `land.mjs` run passes `--check 'pnpm check --affected'`. It runs only the steps marked `land` in `tooling/scripts/check.mjs`: `typecheck`, the fast test files of `pnpm test:fast`, the plitejs, platejs and @platejs/test test files that import a changed file directly, other than the slow ones (owner's word, 2026-11-19), the checks that take a second or two (owner's word, 2026-11-17), and the `knowledge` and `api-reference` checks, which take under a minute (owner's word, 2026-11-18). Each runs only when the task's paths reach it, so a task that changes only plans, decision logs or agent instructions outside `.agents/rules/` skips typecheck and the tests, a change to a script under `tooling/scripts/` or `.agents/` runs the fast tests that name it, and a change to other code runs only the fast test files whose imports load it and the package test files that import it directly. A test file is slow when its cases took 2 seconds or more the last time any run timed it. land.mjs lints the changed files itself. Any other step joins the landing list only when the step log shows it under a minute at p90 and its rule reaches only the changes that can turn it red (owner's word, 2026-11-18), because a red step after landing costs a fix run. Every other step, the slow test files of `pnpm test:slow` and the formal checks included, runs in Local CI after landing. A step passes when `.agents/expected-failures.json` lists each of its failures and each listed failure's owner task is still open. A listed failure that stops failing fails the step until its line goes (owner's word, 2026-11-19). Every landing also runs `node tooling/scripts/review-ledger.mjs land` from the config's `landChecks`. It refuses a review fork only when a review page that the landing adds, deletes or relinks makes the fork. It checks only the plans that the landing adds or changes, so another plan's open problems never block the landing. It also refuses a source file that the landing adds when no review scope's `members` name it, and its error says how to give the file a scope. Every `pnpm check` run and every `pnpm lint:task` run records each step that passes against the exact files of both halves of the checkout, and every worktree of the clone reads those records. A later run skips a step that passed on the same files and prints the pass it used, and `pnpm check --affected` also skips one that none of the files changed since a recorded pass reaches. A step whose result depends on files git ignores, other than the `.env` files every record covers, never skips this way. The opt-in `pnpm check --reads` reruns the Node scripts of each cached step and fails when one reads a tracked file its rule does not reach or an ignored file its `ignoredReads` does not list. `TURBO_FORCE=true` or `FAST_CHECK_SEED=random` ignores every recorded pass. land.mjs keeps its own record of a commit whose checks passed and pushes that same commit again without running them, unless the environment holds either assignment, which `freshEnv` in `.agents/pstack.json` lists. Because a landing skips steps and replays one fast-check seed, Local CI checks `origin/next` after landing, as the `local-ci` skill says. A launchd job on the owner's Mac runs every step a landing skips, with the `--build --browser` steps, on each new tip of `next`, and once a day runs `FAST_CHECK_SEED=random TURBO_FORCE=true pnpm check --build --browser --reads`. For each step whose new failure fails again when rerun, it names the first bad commit and offers a suggested task, and the watcher session starts a fix run. Nothing in Local CI posts to the team channel (owner's word, 2026-11-17).
- Invoke the `verify` skill itself before checking, skipping, deferring or moving a plan's proof gate to limits; its command recipes (`.agents/rules/verify/references/commands.md`) alone do not carry its proof law.
- **Formal checks first.** Before a step's diff gets its panel round, the lead runs the `pnpm check` step of each formal check skill whose `## Coverage record` names a file the diff changes or a folder that holds one, such as `pnpm check undo-redo-history`, and puts each result in the seats' brief. When the step's diff gets no panel, the lead runs those checks as proof before the step lands. A critical finding a seat raises in a file a Coverage record names, after that record's check passed, is a gap in that check. The lead logs it in a decision row whose result starts with `gap` and names the check, so the next formal intake reads it with the plans (owner's word, 2026-11-19).

- **Timing gates.** A wall-clock timing line settles in the run that froze it. The work count gates the change, and a line that stays inconclusive closes as `.agents/rules/benchmark.mdc` says. This replaces the Time budget rule's hand-off of a timing rerun to a suggested task, because this host never gets quiet (owner's word, 2026-11-20).
- **Manual tests.** A check that only a person can run, such as one on a real device, with an OS input method, with a paste from another app or with a native drag, never opens or blocks a plan step, a build or a landing (owner's word, 2026-11-15). Opening an exported file in Word is not such a check. The Open a DOCX in Word section of `verify`'s command recipes drives it through Word for the web (owner's word, 2026-11-17). The run proves what an agent can drive, such as a mouse, synthetic pointer events or a simulator, names the check it did not run in its limits and keeps going. The check never waits on the owner, who rarely tests by hand, so it is no Needs you line, no open question and no suggested task.
