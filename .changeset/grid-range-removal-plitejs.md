'plitejs': patch
---

- Keep every row and cell of a grid, an element whose schema declares `structure: { kind: 'grid' }`, when an expanded range runs from inside it to outside it. A cell the range covers whole keeps only its first block, emptied, when that block is an editable text block, and otherwise takes its schema's default child. A cell at the range's edge loses only the covered text, and text outside the grid never joins a cell. This holds for delete, typing, Enter, slice writes, node insert, split and merge over a range passed as `at` or set with `tx.selection.set`, except that a node insert or split whose range ends at the start of a grid's first cell still lands in that cell. Before, the covered cells and rows were dropped, or the text after the grid joined a cell
- Treat a grid that is a void, an atom or read-only, or sits inside one, like any other non-editable block, and keep the content of a void, atom or read-only cell when a range crosses its edge. A delete or typing inside one such cell still removes the cell, a paste there still writes into it, and a range that also reaches a non-editable grid still takes the ordinary removal for every grid it reaches, as before
- Write typed, pasted or inserted content over such a range at the range's start, in the first cell the range covers that can take text, right after or right before what it removed, or in a new default block when every top-level block is a grid the range removes whole, whichever comes first and can take text. When none can, typing, slice writes, node insert and split refuse and change nothing. A merge after the removal stops at a cell's edge.
- Remove a grid whole when the range covers it and reaches past one of its edges. A range that spans a grid exactly keeps it and clears its cells, except that `fragment.delete` with an explicit `at` still removes the grid and the `text.insert` command still replaces it with one block holding the typed text, as before. Both commands now keep a grid when the range runs from a paragraph to the grid's last text and the grid's last row holds no cells, as a transaction does
- Keep the empty blocks a delete inside one block never reached, and the block where it started. Only the blocks the delete emptied at its end are removed. Before, a delete inside a container also removed empty blocks elsewhere in that container
- Read a node's start or end with `editor.point` and `state.points` from its first or last text, so a node whose last child holds no text no longer throws or returns nothing. `editor.point` throws only when the node holds no text
- Refuse a text move as lossy when removing its source would keep a grid, instead of copying the grid's rows to the target
- Keep an empty cell, and the empty blocks of any cell beside it, when a delete removes a cell's text across several text runs
- Join the blocks a delete inside one cell crosses when its ends sit at different depths, as the same delete outside a grid does
- Fix a merge over a range across blocks, which joined the next block's text in front of the merged block
- Keep a grid cell whose content is `schema.content.text()` whole. Enter, a split and a block insert that would land in it change nothing, and a paste of several lines or of copied cells into it refuses. Copied cells then fall back to their plain text, which lands only when it is one line, as a spreadsheet row's text is. A line break at the end of that text, as Excel adds to a copied cell, does not start a second line. Plite writes each copied cell on its own line, so cells copied in Plite change nothing there, except two cells whose second is empty, which land as the first one's text. A paste over cells selected as nodes changes nothing when it would add cells. A one-line paste still lands in the cell. Before, each of them added cells to the row
- Paste several lines over a range that removes a whole grid as paragraphs. Before, they made a new grid
- Compare grids row by row and cell by cell in `plitejs/diff`
