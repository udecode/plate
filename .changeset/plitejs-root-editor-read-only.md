- Fix `useRootEditor`, `useCommand` and `useEditorHistory` ignoring the read-only state and authored view of the view that shows their root. Inside a read-only `EditorRoot`, or beside a read-only `Editable` of their root, a root editor and a command throw on a write, and undo and redo do nothing. In suggesting mode, a root editor records its edits as proposals. When several views show the root, they follow the one the user focused or pressed most recently. Releasing the mouse does not move them, so a drag that ends over another `Editable` leaves them where it began
- Fix `useEditorHistory` with a `root` and no `editor` when several views show that root or none does. Undo and redo run in the view of that root the user focused or pressed most recently, even while focus is outside the editor, such as on a toolbar button. `canUndo` and `canRedo` are false while that view composes text or while no `Editable` shows the root. With or without an `editor`, `onKeyDown` leaves the shortcut to the browser when no `Editable` can run it
- Fix `useCommand` without `root`, outside an `Editable`, running a command in the root the caret was in when its component last rendered. The command runs in the root the caret is in when it is called, so a call from the focus handler of a read-only `Editable` throws instead of writing in the root the caret left
- Fix `useEditorHistory` with neither `editor` nor `root` turning off after the shown root changes. It follows the change its next undo or redo takes back. `canUndo` and `canRedo` are each true while shown, writable `Editable`s reach every root that direction's change edits. A content root whose slot is not shown counts as reached through the root that shows its owner. Undo and redo run in the writable `Editable` the user used most recently, so focus stays where they work
- Fix undo and redo taking back a change in a root that no `Editable` shows, or that every shown `Editable` shows read-only, when they come from a keyboard shortcut, a native history input or a `useEditorHistory` control with neither `editor` nor `root`. They change nothing. A refused shortcut or native history input reports `{ status: 'unavailable', reason: 'hidden' | 'read-only', root }` to `onHistoryReplay`. A control with neither `editor` nor `root` is off and reports nothing. `editor.api.history.undo()` and `redo()`, and a control with an `editor` or a `root`, still take back any change
- Fix an `EditorRoot` staying read-only after its read-only `Editable` unmounts. An `EditorRoot` is read-only while it has `readOnly`, or while every `Editable` that shows its root is read-only and at least one does
- Fix a view made from another view with `createEditorView` keeping the read-only state and authored view its source had at creation. It follows its source while both exist
